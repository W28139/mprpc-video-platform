# 视频转码平台 — 快速启动指南

> 目标：**5 分钟跑通全链路**（提交视频 → 转码 → 合并 → 查看结果 → 看监控面板）。
> 两种部署方式任选其一，本文分别给出完整步骤。

## 0. 先清场（每次运行前执行，防止多套服务并存）

> ⚠️ **最容易踩的坑**：残留进程没杀干净就启动新服务，导致**多套并存**——端口被两套同时监听、ZK 注册节点冲突，提交任务卡死不动（2026-08-08 实测踩坑）。
> 残留进程包括：旧的手工服务（`./job_service` 或 `./bin/job_service` 两种命令行形态）+ Docker 容器。

```bash
# 1. 杀掉所有本机平台服务进程（两种命令行形态都覆盖）
pkill -9 -f "job_service|scheduler_service|worker_manager|transcode_worker|result_collector"

# 2. 停掉 Docker 容器（没跑过 docker 会报错，忽略即可）
docker compose down 2>/dev/null

# 3. 等 ZK 临时节点过期（3 秒），避免注册冲突
sleep 3

# 4. 确认无残留（应输出"无残留"）
ps aux | grep -E "job_service|scheduler_service|worker_manager|transcode_worker|result_collector" \
  | grep -v grep && echo "⚠️ 还有残留！" || echo "✓ 无残留，可以启动"

# 5. 删除 Docker 容器（root）写出的日志文件——否则手工服务打开会 Permission denied：
#    [AsyncLogger] Failed to open log file: ./program_log/<date>-log.txt
find program_log -user root -delete
```

> 中间件（ZK 2181 / MySQL 3306 / Redis / RabbitMQ）**不用清**，平台服务依赖它们。
> 日志目录 `program_log/` 是 Docker 和手工**共用**的：Docker 容器以 root 写日志，文件属主为 root（644），手工服务（wevix）追加写同一文件会被拒绝。第 5 步把它删掉，服务重启后会以当前用户重新创建。

## 1. 先选一种方式

| | **方式 A：逐个启动（手工部署）** | **方式 B：Docker 一键启动（推荐）** |
|--|--|--|
| 前置条件 | 本机已装 ZooKeeper / MySQL / ffmpeg | 只需要 Docker |
| 环境 | 复用本机中间件（标准端口 2181/3306） | 全新环境，版本锁死（ZK 3.8 / MySQL 8.0 / Redis 7 / RabbitMQ 3.12） |
| 适合 | 开发调试、看日志、逐服务排查 | 演示、验收、干净环境、多 Worker 扩容 |
| 首次耗时 | ~10 分钟（含依赖检查） | ~5 分钟（含镜像构建） |
| 提交任务 | 本机直接跑 `bin/job_client` | 进容器跑（或 `docker compose exec`） |

> 已经手工部署在跑（本机 9001-9005 被占用）时，**不要**同时起 Docker（端口冲突），两者选一个。

# 方式 A：逐个启动（手工部署）

## A1. 前置检查

```bash
# ZooKeeper 是否运行
echo stat | nc -w 1 localhost 2181

# MySQL 是否可连（专用账号/密码，见记忆文档或 schema.sql）
mysql -uvideo_platform -pvideo_platform123 -h127.0.0.1 -e "SELECT 1" video_platform

# ffmpeg 是否安装（Worker 启动时会自动检查，缺失会拒绝启动）
which ffmpeg ffprobe

# Redis / RabbitMQ（阶段 10 起为可降级组件，不在也能跑，缺了调度自动回退 Pull 轮询）
redis-cli ping        # 期望 PONG
rabbitmqctl status    # 期望 Running
```

MySQL 首次部署初始化（建库建账号，表由服务启动时自动创建）：

```bash
mysql -uroot -p <<'EOF'
CREATE DATABASE IF NOT EXISTS video_platform DEFAULT CHARACTER SET utf8mb4;
CREATE USER IF NOT EXISTS 'video_platform'@'localhost' IDENTIFIED BY 'video_platform123';
CREATE USER IF NOT EXISTS 'video_platform'@'%' IDENTIFIED BY 'video_platform123';
GRANT ALL PRIVILEGES ON video_platform.* TO 'video_platform'@'localhost';
GRANT ALL PRIVILEGES ON video_platform.* TO 'video_platform'@'%';
FLUSH PRIVILEGES;
EOF
```

## A2. 构建

```bash
cd /home/wevix/muduo_im
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)
```

产物：服务 `bin/{job_service, scheduler_service, worker_manager, transcode_worker, result_collector}`，客户端 `bin/job_client`。

## A3. 启动 5 个服务

```bash
cd /home/wevix/muduo_im

./bin/job_service       -i video_platform/conf/job_service.conf &
./bin/scheduler_service -i video_platform/conf/scheduler.conf &
./bin/worker_manager    -i video_platform/conf/worker_manager.conf &
./bin/result_collector  -i video_platform/conf/result_collector.conf &
./bin/transcode_worker  -i video_platform/conf/transcode_worker_9004.conf &

# 多 Worker 并行（可选，负载自动均衡）：
./bin/transcode_worker -i video_platform/conf/transcode_worker_9010.conf &
./bin/transcode_worker -i video_platform/conf/transcode_worker_9011.conf &

sleep 2
echo "全部启动完成"
```

> ⚠️ 不要重复执行启动脚本，多组进程会导致 ZK 注册冲突。

## A4. 提交任务

**生成测试视频**（没有现成视频时）：

```bash
ffmpeg -y -f lavfi -i testsrc=duration=30:size=1280x720:rate=30 \
       -f lavfi -i sine=frequency=440:duration=30 \
       -c:v libx264 -preset ultrafast -c:a aac -shortest \
       /tmp/test_video.mp4
```

**管道提交（推荐）**：

```bash
printf 'test_user\n/home/wevix/muduo_im/path/test_video.mp4\n/home/wevix/muduo_im/path/temp_out\nmp4\n720p\n2000\n0\n15\n' \
    | ./bin/job_client -i video_platform/conf/job_client.conf
```

输入顺序：`user_id → input_path → output_dir → format → resolution → bitrate → priority → shard_duration`

| 参数 | 示例 | 说明 |
|------|------|------|
| user_id | `test_user` | 用户标识 |
| input_path | `/tmp/test_video.mp4` | 输入视频路径 |
| output_dir | `/tmp/output` | 输出目录 |
| format | `mp4`/`mkv`/`flv` | 目标容器格式 |
| resolution | `720p`/`1080p` | 目标分辨率 |
| bitrate | `2000` | 目标码率（kbps），0=保持原码率 |
| priority | `0` | 调度优先级，越大越优先 |
| shard_duration | `15` | 每 shard 时长（秒），0=默认 15s |

提交成功输出：

```
✓ Job submitted successfully!
  Job ID: job_1785481763677_000000_1437
  Status: SCHEDULING
```

## A5. 查看结果

**查询单个任务**：

```bash
./bin/job_client -i video_platform/conf/job_client.conf --query <job_id>
```

```
┌─ Job: job_1785481763677_000000_1437
│  Status:      SUCCESS (6)
│  Output:      /tmp/output/job_xxx_merged.mp4   ← 合并后的完整视频
│  Shards (2):
│    ✓ [0] job_xxx_shard_0  status=SUCCESS  worker=worker_001  screenshot=yes
│    ✓ [1] job_xxx_shard_1  status=SUCCESS  worker=worker_001  screenshot=yes
│  Progress: [====================] 2/2 (100%)
└──────────────────────────────────
```

**轮询直到终态**（每 2s 刷新，Ctrl+C 停止）：

```bash
./bin/job_client -i video_platform/conf/job_client.conf --query <job_id> --watch
```

**看日志**（所有服务写同一个日志文件，按天轮转）：

```bash
LOG="program_log/$(date +%Y-%m-%d)-log.txt"
tail -f $LOG                                    # 实时跟踪
grep "FfmpegExecute"    $LOG | tail -20         # 转码执行
grep "assigned shard"   $LOG | tail -5          # Worker 分配
grep "JOB_SUCCESS\|JOB_FAILED" $LOG | tail -3   # 终态
```

**预期时间线**：提交后 0s PENDING→SCHEDULING（ffprobe 探测时长）；1-2s RUNNING（调度分配 shard）；3-6s SUCCESS（转码完成 + 合并 + 截图）。产物：`{output_dir}/{job_id}_merged.mp4`。

## A6. 使用监控面板（Prometheus + Grafana）

**0 依赖快速验证**（服务起来后直接 curl，不需要装任何东西）：

```bash
curl -s http://127.0.0.1:9091/metrics | head     # job_service：任务计数
curl -s http://127.0.0.1:9092/metrics | grep shard_   # scheduler：shard 分布
curl -s http://127.0.0.1:9093/metrics | grep worker_  # worker_manager：负载
curl -s http://127.0.0.1:9094/metrics | grep job_     # result_collector：成功/失败
curl -s http://127.0.0.1:9095/metrics | grep transcode # worker：转码耗时
```

**完整面板**（Prometheus + Grafana 部署与导入，详见 `video_platform/observability/README.md`，3 步）：

```bash
sudo apt install prometheus
prometheus --config.file=video_platform/observability/prometheus.yml
# Grafana 登录 → Data sources 加 Prometheus(127.0.0.1:9090)
# → Dashboards → Import 上传 video_platform/observability/grafana-dashboard.json
```

面板 4 行怎么看：**Row1 Job 吞吐**（提交/成功/失败速率，失败线抬头即异常）→ **Row2 Shard 分布**（饼图看当前积压、时间线看何时开始堆积）→ **Row3 Worker 负载热力图**（颜色深=持续满载=扩容信号）→ **Row4 RPC 延迟**（P99 持续抬升而 P50 平稳 = 长尾劣化）。

**不装 Grafana 也能收告警**：服务日志直接打 `ALERT [xxx] firing/recovered`（进程内告警兜底，30s 一轮）。

## A7. 停止

```bash
pkill -9 -f "job_service|scheduler_service|worker_manager|transcode_worker|result_collector"
sleep 1
pgrep -f "job_service|scheduler_service|worker_manager|transcode_worker|result_collector" \
  && echo "还有残留！" || echo "已全部停止"
```

# 方式 B：Docker 一键启动（推荐）

## B1. 前置：安装 Docker

```bash
# WSL2 下二选一：
# 1) Docker Desktop for Windows（启用 WSL2 集成）
# 2) apt：
sudo apt install docker.io docker-compose-v2
sudo usermod -aG docker $USER    # 重新登录生效
```

## B2. 一键启动（9 个容器）

```bash
cd /home/wevix/muduo_im
docker compose up -d --build      # 首次构建镜像需几分钟

docker compose ps                 # 等全部 running（MySQL 首次初始化稍慢）
```

启动内容：**4 中间件**（ZooKeeper/MySQL/Redis/RabbitMQ，版本锁死）+ **5 平台服务**。顺序由 healthcheck 保证——中间件确认就绪后服务才启动。

## B3. 提交任务

视频经挂载卷共享：宿主 `data/videos/` = 容器内 `/data/videos/`，产物同理在 `data/output/`。

```bash
# 先把视频放进 data/videos/（或用 ffmpeg 生成）
ffmpeg -y -f lavfi -i testsrc=duration=30:size=320x240:rate=10 \
       -pix_fmt yuv420p -c:v libx264 -preset ultrafast \
       data/videos/sample.mp4

# 容器内提交（交互输入用管道）
docker compose exec job_service sh -c \
  'printf "%s\n" "test_user" "/data/videos/sample.mp4" "/data/output" "mp4" "720p" "0" "0" "0" \
   | ./bin/job_client -i /app/conf/job_client.conf'
```

## B4. 查看结果 / 日志 / 面板

```bash
# 查询任务（容器内）
docker compose exec job_service sh -c \
  './bin/job_client -i /app/conf/job_client.conf --query <job_id> --watch'

# 服务日志（compose 统一管理，不用找文件）
docker compose logs -f scheduler_service

# 监控指标（宿主端口）：http://localhost:19091/metrics（job_service）…19094
# Grafana 部署同上（方式 A 第 A6 节），Prometheus 抓取端口照用 9091-9097 容器内不变
```

合并产物在 `data/output/{job_id}_merged.mp4`，宿主可直接播放。

## B5. 扩容 Worker（一行命令）

```bash
docker compose up -d --scale transcode_worker=3
```

3 个 Worker 自动注册（唯一 worker_id 由 环境变量 > 配置 > hostname 保证），调度自动负载均衡。日志可见 `assigned shard` 分散到不同 worker。

## B6. 停止 / 清理

```bash
docker compose down          # 停止并删除容器（保留 MySQL 数据卷）
docker compose down -v       # 连 MySQL 数据一起删（彻底清空环境）
```

# 常见问题

**Q: 服务启动后 Worker 一直是 NOT alive？**
旧进程残留导致 ZK 注册冲突。全部停掉（A7 命令）等 3 秒（ZK 临时节点过期）重新启动。

**Q: Worker 启动时报 "ffmpeg/ffprobe not found in PATH"？**
`sudo apt install ffmpeg`；或临时改用 mock 模式（`executor_mode=mock`，不依赖 ffmpeg，用 sleep 模拟执行）。

**Q: 提交任务后卡在 SCHEDULING 不动？**
1. Worker 是否注册：`grep "RegisterWorker success" program_log/*.txt`
2. 是否有 ONLINE Worker：`grep "ONLINE workers" program_log/*.txt`
3. 输入视频路径是否正确、文件存在（ffprobe 探测失败会回退 fallback 时长）

**Q: Docker 端口冲突？**
compose 默认用替代宿主端口（ZK 21810 / MySQL 23306 / Redis 63790 / RabbitMQ 56720 / 服务 19001-19005 / metrics 19091-19094），容器内不变。本机无占用时可改回标准端口（compose 里一处映射即可）。

**Q: 多 Worker 时如何确认负载均衡生效？**
`grep "SchedulerMetrics" program_log/$(date +%Y-%m-%d)-log.txt | tail -5`——`running=4/8` 接近总容量即均匀；`grep "assigned shard" ... | tail -10` 看分配是否分散到不同 worker。
