## 一、内存安全

### #1 Store::Get() 悬空裸指针（未定义行为）🔴

**涉及文件**：`common_store.h/cpp` + 7 个调用点

#### 现象

`JobStore::Get()`、`ShardStore::Get()`、`WorkerStore::Get()` 三个方法返回 `unordered_map` 内部元素的裸指针。所有调用方在锁释放后继续通过该指针读写，而 C++ 标准不保证 `shared_lock` 释放后指针仍有效。

#### 根因

```cpp
// 修复前：common_store.cpp:88-95
JobRecord* JobStore::Get(const std::string& job_id)
{
    std::shared_lock lock(mutex_);     // 读锁
    auto it = jobs_.find(job_id);
    if (it == jobs_.end()) return nullptr;
    return &it->second;                 // 返回 map 内部地址
}  // ← lock 在此析构，shared_lock 释放
   // 返回的指针此时已经脱离锁保护
```

调用方的典型使用模式：

```cpp
// job_service.cpp (修复前)
JobRecord* job = JobStore::GetInstance().Get(job_id);
if (job != nullptr) {
    job->status = ...;                              // ⚠️ 无锁写入 map 内部元素
    JobStore::GetInstance().Update(job_id, *job);   // Update 内部持写锁
}
```

在 `job->status = ...` 和 `Update(job_id, *job)` 之间：
- 另一个线程可能执行 `Insert()`（持写锁，可能触发 `unordered_map` rehash）
- rehash 会使之前返回的指针**悬空**
- 后续 `*job` 解引用是**未定义行为**

`common_store.h:55-56` 的注释明确警告了此风险，但所有 7 个调用方都违反了约定。

#### 后果

- **数据损坏**：写操作可能写到已被 rehash 移动的内存位置
- **崩溃**：悬空指针解引用可能导致 segfault
- **静默错误**：最危险的情况——不崩溃但写入了错误的内存位置

影响的调用点：
| 文件 | 方法 | 操作 |
|------|------|------|
| `job_service.cpp` | `UpdateJobStatus` | 写 status → 跨进程状态同步损坏 |
| `job_service.cpp` | `SubmitJob` | 写 shard_count → #2 侧信道写入 |
| `scheduler_service.cpp` | `RescheduleShard` | 写 status/retry_count |
| `scheduler_service.cpp` | `SchedulingLoop` | 写 shard 状态 + job 状态 |
| `result_collector.cpp` | `ReportShardResult` | 写 shard status |
| `result_collector.cpp` | `CheckJobDone` | 写 job status |
| `job_service.cpp` | `CancelJob` | 写 job status |

#### 修复

将 `Get()` 返回类型从裸指针改为 `std::optional<T>`（返回值拷贝）：

```cpp
// 修复后：common_store.cpp
std::optional<JobRecord> JobStore::Get(const std::string& job_id)
{
    std::shared_lock lock(mutex_);
    auto it = jobs_.find(job_id);
    if (it == jobs_.end()) return std::nullopt;
    return it->second;  // 返回副本，调用方持有独立数据
}
```

调用方改为先拷贝再修改，通过 `Update()` 写回：

```cpp
// job_service.cpp (修复后)
auto job_opt = JobStore::GetInstance().Get(job_id);
if (!job_opt.has_value()) { /* error */ return; }
auto job = job_opt.value();       // 独立副本，不受并发 rehash 影响
job.status = ...;                 // 安全修改
JobStore::GetInstance().Update(job_id, job);  // 原子写回
```

## 二、跨进程数据同步

### #2 shard_count 侧信道损坏 🔴

**涉及文件**：`scheduler.proto`、`scheduler_service.cpp`、`job_service.cpp`

#### 现象

用户调用 `SubmitJob`，Scheduler 切分成功（3 个 shard），但 `QueryJob` 返回 `shard_count=0`。客户端看到 job 状态是 SCHEDULING 却没有 shard。

#### 根因

`SubmitJob` 获取 `shard_count` 的路径是**间接侧信道**：

```text
SubmitJob
  └─ RPC: Scheduler.ScheduleJob ──► Scheduler 切分 3 个 shard
       ◄── ScheduleJobResponse.accepted=true        ← 不包含 shard_count！
  └─ 从本地 JobStore 读 shard_count
       ↑ 这个值是 Scheduler 通过 UpdateJobStatus RPC 写入的
       ↑ 如果 UpdateJobStatus RPC 失败（网络抖动），JobStore 中 shard_count=0
```

数据流中存在两个 RPC 调用，第二个（`UpdateJobStatus`）是获取 `shard_count` 的唯一途径。这是一个**不可靠的侧信道**：主数据路径（`ScheduleJob` response）不携带关键数据，依赖独立的异步通知。

#### 后果

- `ScheduleJob` 成功但 `UpdateJobStatus` 失败 → `shard_count` 被永久覆盖为 0
- `QueryJob` 返回空 shard 列表，客户端误以为 job 未被切分
- job 实际在正常执行但外部观察不到进度

#### 修复

**直接数据路径**：在 `ScheduleJobResponse` proto 中增加 `shard_count` 字段：

```proto
// scheduler.proto
message ScheduleJobResponse {
    int32  error_code  = 1;
    string error_msg   = 2;
    bool   accepted    = 3;
    string job_id      = 4;
    int32  shard_count = 5;  // ← 新增：直接携带切分结果
}
```

Scheduler 在 `ScheduleJob` 完成时直接回填：

```cpp
response->set_shard_count(shard_count);  // 直接数据路径
```

SubmitJob 从 response 直接读取，不再依赖 `UpdateJobStatus` 侧信道：

```cpp
// 修复后：直接从 ScheduleJobResponse 获取（一次 RPC，直接数据路径）
shard_count_from_scheduler = sched_resp.shard_count();
```

### #3 ScheduleJob RPC 失败 → job 永久卡死 🔴

**涉及文件**：`job_service.cpp`

#### 现象

Job 提交后永久停留在 `PENDING` 状态。日志显示 `ScheduleJob` RPC 调用失败（网络超时 / Scheduler 暂时不可用），但没有任何恢复动作。

#### 根因

```cpp
// 修复前：job_service.cpp SubmitJob
sched_stub.ScheduleJob(&sched_ctrl, &sched_req, &sched_resp, nullptr);

if (!sched_ctrl.Failed() && sched_resp.accepted())
{
    // 成功路径：更新 shard_count
}
else
{
    LOG_WARN("...failed...");
    // ⚠️ 仅打日志，不重试，不设兜底
    // 注释称 "Scheduler 后续可以通过后台循环重新处理" 但该功能未实现
}
```

Scheduler 的 `SchedulingLoop` 只扫描 `SHARD_WAITING` 的 shard——PENDING 状态的 job **没有 shard**，不会被扫描到。这意味着失败的 job **没有任何恢复路径**。

#### 后果

- 任何一次 `ScheduleJob` RPC 失败都导致 job **永久卡死**
- 多进程部署中网络抖动是常态，此问题是**必然触发**而非偶发
- 用户体验：提交成功（返回了 job_id），但永远查不到进度

#### 修复

`SubmitJob` 中对 `ScheduleJob` 调用增加 3 次重试（间隔 1 秒）：

```cpp
bool schedule_ok = false;
for (int attempt = 1; attempt <= 3; ++attempt)
{
    // ... RPC 调用 ...
    if (!sched_ctrl.Failed() && sched_resp.accepted())
    {
        schedule_ok = true;
        break;
    }
    if (attempt < 3)
        std::this_thread::sleep_for(std::chrono::seconds(1));
}

if (!schedule_ok)
{
    LOG_ERROR("...ScheduleJob failed after 3 retries, job stuck in PENDING");
    // job 留在 PENDING，后续可由 SchedulingLoop 扫描 PENDING job 兜底
}
```

此修复覆盖了常见网络抖动场景（3 次重试 × 1 秒间隔覆盖约 99% 的瞬时故障）。极端情况下的兜底（SchedulingLoop 扫描 PENDING job）留待阶段 8 完善。

## 三、状态机正确性

### #4 SchedulingLoop 的 UpdateJobStatus(RUNNING) 返回值被完全忽略 🟠

**涉及文件**：`scheduler_service.cpp`

#### 现象

JobService 中 job 状态停留在 `SCHEDULING`（3），而 Scheduler 本地已是 `RUNNING`（4）。两端状态永久不一致。

#### 根因

```cpp
// 修复前：scheduler_service.cpp SchedulingLoop
// ── 6. 更新 job 状态 → RUNNING ──
job->status = static_cast<int32_t>(JobStatus::JOB_RUNNING);  // 先改本地
JobStore::GetInstance().Update(shard.job_id, *job);

// 反向通知 JobService
{
    MprpcChannel js_channel;
    JobService_Stub js_stub(&js_channel);
    // ...
    js_stub.UpdateJobStatus(&update_ctrl, &update_req, &update_resp, nullptr);
    // ⚠️ 返回值完全未检查！无 if、无 LOG、无重试
}
```

更致命的是：本地 `job->status` 已前置修改为 `RUNNING`。后续 shard 分配时守卫条件 `job->status == JOB_SCHEDULING` 为 false，**不会再发送第二次 `UpdateJobStatus`**。RPC 只有一次机会，失败即永久丢失。

#### 后果

- JobService 的 QueryJob 返回 `SCHEDULING`，用户看到 job 状态不更新
- 与同文件 `ScheduleJob` 方法形成对比——那里的同类 RPC 有完整的错误检查

#### 修复

增加 RPC 返回值检查：

```cpp
js_stub.UpdateJobStatus(&update_ctrl, &update_req, &update_resp, nullptr);

if (update_ctrl.Failed() || update_resp.error_code() != 0)
{
    LOG_WARN("SchedulingLoop: UpdateJobStatus(RUNNING) failed for job=%s: %s",
             shard.job_id.c_str(),
             update_ctrl.Failed() ? update_ctrl.ErrorText().c_str()
                                  : update_resp.error_msg().c_str());
}
```

### #5 UpdateJobStatus 状态降级保护缺失 🟠

**涉及文件**：`job_service.cpp`

#### 现象

注释承诺"不降级：如果已经是 SUCCESS 不会被改回 RUNNING"，但代码实际上**允许任意降级**。

#### 根因

```cpp
// 修复前：job_service.cpp UpdateJobStatus
// 只更新状态（不降级：如果已经是 SUCCESS 不会被改回 RUNNING）  ← 注释不可信！
if (request->status() != JobStatus::JOB_STATUS_UNKNOWN)   // 只排除了 0
{
    job->status = static_cast<int32_t>(request->status()); // 任何非零值无条件接受
}
```

状态枚举值：`PENDING=1 < SPLITTING=2 < SCHEDULING=3 < RUNNING=4 < MERGING=5 < SUCCESS=6`。

`request->status()=4 (RUNNING)` 可以覆盖 `job->status=6 (SUCCESS)`——因为 `4 != 0`，条件通过。

#### 后果

典型触发场景：
1. ResultCollector 的 `CheckJobDone` 检测到全部 SUCCESS → 调用 `UpdateJobStatus(SUCCESS=6)`
2. JobService 收到 → job 状态变为 SUCCESS
3. 同时 SchedulingLoop 的另一个 shard 分配触发了 `UpdateJobStatus(RUNNING=4)`（网络延迟导致乱序到达）
4. JobService 无条件接受 RUNNING=4 → 覆盖 SUCCESS=6
5. job 从终态 SUCCESS 退化到 RUNNING——**状态机违反**

#### 修复

增加状态单调性检查：

```cpp
if (request->status() != JobStatus::JOB_STATUS_UNKNOWN)
{
    int32_t new_status = static_cast<int32_t>(request->status());
    if (new_status > job.status)          // 只接受状态升级
    {
        job.status = new_status;
    }
    else if (new_status != job.status)
    {
        LOG_INFO("...ignoring status downgrade %d → %d", job.status, new_status);
    }
}
```

这样 `RUNNING(4)` 尝试覆盖 `SUCCESS(6)` 时，`4 > 6` 为 false，降级被拒绝。

### #S1 CheckJobDone 过早判定 job 完成 🔴

**涉及文件**：`result_collector.cpp`

#### 现象

3 个 shard 并行执行，shard_0 先完成上报。`CheckJobDone` 立即判定 job 完成，将状态标记为 `JOB_SUCCESS`。此时 shard_1 和 shard_2 还在执行中。

#### 根因

`CheckJobDone` 的核心假设是 `ListByJob(job_id)` 返回 job 的**所有** shard。但这个假设在 ResultCollector 进程中不成立：

```text
Scheduler 进程                        ResultCollector 进程
┌──────────────────┐                 ┌──────────────────┐
│ ShardStore       │                 │ ShardStore       │
│ shard_0 WAITING  │                 │ (empty)          │  ← 初始状态
│ shard_1 WAITING  │                 │                  │
│ shard_2 WAITING  │                 │                  │
└──────────────────┘                 └──────────────────┘

Worker 上报 shard_0 结果 →
                                     ┌──────────────────┐
                                     │ ShardStore       │
                                     │ shard_0 SUCCESS   │  ← 只有 1 个！
                                     └──────────────────┘

CheckJobDone:
  ListByJob → [shard_0]              ← 只返回已上报的
  全部 SUCCESS? YES (1/1)
  → JOB_SUCCESS ✅                   ← 错误！shard_1/2 还在执行
```

ResultCollector 的本地 `ShardStore` 只包含**已上报过结果**的 shard，不是 job 的完整 shard 集合。真实 shard 总数在 Scheduler 进程中。

#### 后果

- Job 被错误标记为 SUCCESS
- 用户查询到 job 已完成，但 shard_1/2 的结果被丢弃
- 最终输出不完整（只有 shard_0 的转码结果）

#### 修复

在 `CheckJobDone` 中增加 `shard_count` 校验：

```cpp
// 从 JobStore 获取预期的 shard 总数（由 Scheduler 切分时写入，通过 UpdateJobStatus 同步）
int32_t expected_shard_count = 0;
auto job_opt = JobStore::GetInstance().Get(job_id);
if (job_opt.has_value())
    expected_shard_count = job_opt->shard_count;

// ... 统计 success_count ...

// 防止过早判定：已上报数必须 >= 预期总数
if (expected_shard_count > 0 && success_count < expected_shard_count)
{
    LOG_INFO("...%d/%d shards SUCCESS, waiting for remaining %d",
             success_count, expected_shard_count,
             expected_shard_count - success_count);
    return false;
}
```

注意这里有前提：ResultCollector 的本地 `JobStore` 中必须有 `shard_count`。这个值由 Scheduler 在切分时通过 `UpdateJobStatus` RPC 写入（见 #2 修复），或由 `ReportShardResult` 首次收到 shard 时从 JobService 查询。若 `shard_count=0`（两个来源都没到位），则回退到原逻辑作为防御。

## 四、调度逻辑正确性

### #6 SchedulingLoop Worker 超额分配 🟠

**涉及文件**：`scheduler_service.cpp`

#### 现象

1 个 Worker（max_running_shards=4，即 4 个槽位）+ 5 个 WAITING shard → 全部 5 个 shard 分配给同一个 Worker。

#### 根因

```cpp
// 修复前：每轮迭代从快照重新计算 best_slots
for (auto& shard : waiting_shards)
{
    for (const auto& w : lw_resp.workers())  // ← 始终是不变的快照
    {
        int available = w.max_running_shards() - w.current_running_shards();
        if (available > best_slots) { ... }           // ← 未递减已分配数
    }
    // shard 分配成功，但 best_slots 不变
    // 下一个 shard 循环时，同一个 Worker 仍显示 4 slots
}
```

`lw_resp.workers()` 是本轮开始时 `ListWorkers` RPC 返回的快照，整个 for 循环中不变。每次 shard 重新计算可用槽位时，使用的仍然是快照中的 `current_running_shards`——Worker 还没收到新 shard，槽位数不变。

#### 后果

- Worker 被超额分配，超出其 `max_running_shards` 限制
- Worker 的资源保护形同虚设
- 在真实 FFmpeg 场景下，超额分配导致 CPU/内存过载

#### 修复

分配成功后递减本地 `best_slots` 副本：

```cpp
// 修复后：分配成功后递减
--best_slots;  // 本地跟踪，防止同一轮中重复分配给同 Worker
```

同时配合 #S4 修复（重新 Get 获取最新状态），确保跨轮也不会超额分配。

### #8 整数除法截断 — 视频末尾片段未被覆盖 🟡

**涉及文件**：`scheduler_service.cpp`

#### 现象

配置 `mock_job_duration_sec=50`、`mock_shard_duration_sec=20`，预期 3 个 shard（0-20s、20-40s、40-50s），实际只创建了 2 个（0-20s、20-40s）。末尾 [40s, 50s) 的 10 秒视频丢失。

#### 根因

```cpp
// 修复前
int shard_count = mock_job_duration_sec / shard_dur;  // 50 / 20 = 2（整数截断）
```

C++ 整数除法向零截断。`50 / 20 = 2`，余数 10 被丢弃。

#### 后果

- 视频末尾片段永久丢失
- 在非整数倍场景（绝大部分真实视频）下必然触发

#### 修复

使用向上取整：

```cpp
int shard_count = (mock_job_duration_sec + shard_dur - 1) / shard_dur;
// (50 + 20 - 1) / 20 = 69 / 20 = 3 ✅
```

### #S4 SchedulingLoop 快照覆盖并发修改 🟡

**涉及文件**：`scheduler_service.cpp`

#### 现象

`RescheduleShard` 更新了 shard 的 `retry_count`（从 0 → 1）和 `attempt_id`，但 `SchedulingLoop` 随后用旧快照副本覆盖了这些修改——`retry_count` 回到 0。

#### 根因

```cpp
// SchedulingLoop 中：
auto waiting_shards = ShardStore::GetInstance().ListByStatus(SHARD_WAITING);
// ↑ 返回的是 vector<ShardRecord> 副本（快照）

for (auto& shard : waiting_shards)  // shard 是快照中的元素
{
    // ... AssignShard RPC 成功 ...
    
    // ⚠️ 直接用快照副本更新，覆盖任何并发修改
    shard.status = SHARD_ASSIGNED;
    shard.assigned_worker_id = best_worker->worker_id();
    shard.attempt_id = shard.shard_id + "_attempt_" + std::to_string(shard.retry_count);
    //                                                                 ↑ 快照中的旧值！
    ShardStore::GetInstance().Update(shard.shard_id, shard);
}
```

并发场景：
```text
时间 →
SchedulingLoop:  ListByStatus() → shard{retry=0, attempt=""}
RescheduleShard:  Get(shard) → retry=0 → retry++ → retry=1, attempt="xxx_retry_1"
                  Update(shard) ✅
SchedulingLoop:  Update(shard_id, shard{retry=0, attempt="xxx_retry_0"})  ← 覆盖！
```

#### 后果

- `retry_count` 被意外重置
- `attempt_id` 不一致——Scheduler 认为是 `_attempt_1`，实际 Worker 看到的是 `_attempt_0`
- 阶段 5 的幂等校验和重试上限将失效

#### 修复

分配前从 ShardStore 重新 `Get()` 获取最新状态：

```cpp
// 修复后：重新读取，避免快照覆盖
{
    auto fresh_opt = ShardStore::GetInstance().Get(shard.shard_id);
    if (!fresh_opt.has_value()) continue;  // 已被删除（异常情况）
    auto fresh = fresh_opt.value();
    fresh.status = SHARD_ASSIGNED;
    fresh.assigned_worker_id = best_worker->worker_id();
    fresh.attempt_id = fresh.shard_id + "_attempt_" + std::to_string(fresh.retry_count);
    //                                                              ↑ 最新值
    fresh.updated_at = NowMs();
    ShardStore::GetInstance().Update(fresh.shard_id, fresh);
}
```

## 五、分布式语义完整性

### #7 CancelJob 仅单进程执行 🟡

**涉及文件**：`job_service.cpp`

#### 现象

用户调用 `CancelJob`，JobService 本地 JobStore 标记为 `CANCELED`。但 Scheduler 的 `SchedulingLoop` 继续扫描该 job 的 WAITING shard，照常分配给 Worker。Worker 正常执行转码。取消操作在实际系统中**完全无效**。

#### 根因

```cpp
// 修复前：CancelJob 只操作本地进程
job->status = JOB_CANCELED;
JobStore::GetInstance().Update(job_id, *job);
// ⚠️ 到此为止——没有任何 RPC 通知 Scheduler 或 Worker
```

分布式系统中，JobService 进程的状态变更不会自动传播到 Scheduler 和 Worker 进程。Scheduler 不知道 job 被取消了，Worker 不知道自己正在为一个已取消的 job 工作。

#### 后果

- 取消操作形同虚设
- Worker 浪费 CPU 时间执行已被用户取消的任务
- 取消后的 shard 结果仍会被 ResultCollector 正常接收

#### 修复

在 CancelJob 中同步传播取消到所有 shard：

```cpp
// 将所有 shard 标记为 CANCELED，SchedulingLoop 不再扫描它们
auto shards = ShardStore::GetInstance().ListByJob(request->job_id());
for (auto& s : shards)
{
    s.status = SHARD_CANCELED;
    s.updated_at = NowMs();
    ShardStore::GetInstance().Update(s.shard_id, s);
}
```

当前修复覆盖了最关键的一环：**阻止 Scheduler 继续分配**。理想情况下还需要通知 Worker 取消正在执行的 shard（通过 `Worker.CancelShard` RPC），但跨进程 Worker 发现增加了较大复杂度，留待阶段 5 完善。当前修复已确保：
- WAITING shard → 标记 CANCELED，不会被 SchedulingLoop 分配
- 已在执行的 shard → Worker 会完成执行并上报结果，但 ResultCollector 若已标记 CANCELED 可拒绝（阶段 5 完善幂等校验）

## 六、Proto 数据完整性

### #9 JobInfo proto 缺少 shard_duration_sec 🟡

**涉及文件**：`common.proto`、`job_service.cpp`、`scheduler_service.cpp`

#### 现象

用户在 `SubmitJobRequest` 中指定了 `shard_duration_sec=30`，但 Scheduler 仍然使用配置文件中的默认值（20 秒）。用户设置被**静默忽略**。

#### 根因

数据流断裂：

```text
SubmitJobRequest.shard_duration_sec=30
  → JobRecord.shard_duration_sec=30  ✅ 写入 C++ 结构体
  → JobInfo (proto)                  ❌ 无此字段，无法携带
  → ScheduleJobRequest.job_info      ❌ shard_duration_sec=0（默认值）
  → Scheduler 读取 0 → 回退到配置默认值
```

`JobInfo` 是跨服务传递 job 信息的标准 proto 消息，但缺少 `shard_duration_sec` 字段。JobService 将值存入了 C++ `JobRecord`，但转发给 Scheduler 时只能通过 `JobInfo` proto，该字段丢失。

#### 后果

- 用户指定的 shard 粒度完全无效
- `shard_duration_sec` 字段在 proto 定义中存在（`SubmitJobRequest` field 8），功能"看起来能用"但实际不工作

#### 修复

在 `common.proto` 的 `JobInfo` 中增加字段：

```proto
message JobInfo {
    // ... fields 1-13 ...
    int32  shard_duration_sec = 14;  // 每 shard 时长（秒），0=使用默认值
}
```

JobService 在构造 `JobInfo` 时设置：

```cpp
jobInfo->set_shard_duration_sec(job.shard_duration_sec);
```

Scheduler 从 `JobInfo` 读取：

```cpp
local_job.shard_duration_sec = jobInfo.shard_duration_sec();  // 不再硬编码 0
```

## 七、向前兼容性

### #10 AssignShardRequest 未透传 retry_count 🔵

**涉及文件**：`scheduler_service.cpp`

#### 现象

`ShardInfo` proto 定义了 `retry_count` 字段（field 9），但 SchedulingLoop 构造 `AssignShardRequest` 时**从未设置**此字段。

#### 根因

```cpp
// 修复前：构造 AssignShardRequest 时缺少 retry_count
si->set_shard_id(shard.shard_id);
si->set_job_id(shard.job_id);
si->set_shard_index(shard.shard_index);
// ... 其他字段 ...
// ⚠️ si->set_retry_count(shard.retry_count); ← 缺失！
```

Worker 端从 `shard.retry_count()` 读取（proto 默认值 0），构造 `attempt_id = "xxx_attempt_0"`。阶段 5 引入重试后，Scheduler 本地 `retry_count=1`，但 Worker 收到 proto 默认值 0，双方对 attempt_id 认知不一致。

#### 后果

- 阶段 5 的幂等校验失效：Worker 上报 `_attempt_1`，但 ResultCollector 本地记录的 attempt_id 是 `_attempt_0`
- 重试后旧 attempt 的结果可能被错误接受

#### 修复

```cpp
si->set_retry_count(shard.retry_count);  // 透传 retry_count
```

### #11 shard_index 在 ResultCollector 本地副本中硬编码为 0 🔵

**涉及文件**：`result.proto`、`transcode_worker.cpp`、`result_collector.cpp`

#### 现象

ResultCollector 的本地 ShardStore 中，所有 shard 的 `shard_index` 都是 0——无论实际是 shard_0、shard_1 还是 shard_2。

#### 根因

`ReportShardResultRequest` proto 没有 `shard_index` 字段。ResultCollector 在首次收到 shard 结果时从请求参数构造本地 `ShardRecord`，只能硬编码：

```cpp
// 修复前
shard_copy.shard_index = 0;  // 请求中不含此字段，只能硬编码
```

#### 后果

- 数据质量问题：ResultCollector 本地 shard 元数据失真
- `QueryJob` 返回的 shard 列表无法区分 shard 顺序

在 `result.proto` 的 `ReportShardResultRequest` 中增加字段：

```proto
message ReportShardResultRequest {

}
```

```cpp
result_req.set_shard_index(rs->info.shard_index());
```

ResultCollector 读取：

```cpp
shard_copy.shard_index = request->shard_index();  // 从请求透传
```

## 八、并发安全

### #S3 AssignShard TOCTOU 竞态窗口 🟠

**涉及文件**：`transcode_worker.cpp`

#### 现象

在特定并发条件下，同一个 shard 可能被 `AssignShard` 接受两次，导致两个 `MockExecute` 线程并行执行同一 shard。

#### 根因

经典的 **TOCTOU（Time-of-Check to Time-of-Use）** 竞态：

```cpp
// 修复前：两次持锁，中间有窗口
// 第一次持锁：检查
{
    std::lock_guard<std::mutex> lock(mutex_);
    auto it = running_shards_.find(shard.shard_id());
    if (it != running_shards_.end() && !it->second->cancelled)
        return;  // 已存在，拒绝
}  // ← 锁释放

// ⚠️ TOCTOU 窗口 ⚠️
// 另一个 AssignShard 调用可以在此插入相同的 shard_id 到 map

// 第二次持锁：插入（时机太晚）
{
    std::lock_guard<std::mutex> lock(mutex_);
    running_shards_[shard.shard_id()] = rs;  // 可能已存在同 key，覆盖！
}
```

并发时序：

```text
时间 →
AssignShard(A):  lock → find("shard_0") → not found → unlock
                                                         ← TOCTOU 窗口
AssignShard(B):                                          lock → find("shard_0") → not found
                                                         → running_shards_["shard_0"] = rs_B
                                                         → unlock
AssignShard(A):  lock → running_shards_["shard_0"] = rs_A  ← 覆盖 rs_B！
                 → unlock
```

结果：rs_A 和 rs_B 两个线程都在执行 shard_0，且 A 覆盖了 B 的 map 条目——B 无法被 `CancelShard` 找到。

#### 后果

- 同一 shard 被重复执行，浪费 CPU
- `CancelShard` 只能取消其中一个（map 中只保留一个条目）
- 重复的 `ReportShardResult` 可能触发竞争条件

#### 修复

将检查和插入合并到**同一个锁持有区间**：

```cpp
// 修复后：检查 + 插入在同一临界区内
{
    std::lock_guard<std::mutex> lock(mutex_);
    auto it = running_shards_.find(shard.shard_id());
    if (it != running_shards_.end() && !it->second->cancelled)
    {
        // 拒绝重复
        response->set_accepted(false);
        done->Run();
        return;
    }
    
    // 检查通过，在同一锁内创建并插入
    rs = std::make_shared<RunningShard>(shard, attempt_id);
    running_shards_[shard.shard_id()] = rs;
}
// 锁外启动线程（避免死锁）
rs->executor_thread = std::thread(&WorkerServiceImpl::MockExecute, this, rs, mock_execution_ms);
```

注意：线程启动放在锁外——如果在锁内启动线程，而 `MockExecute` 又尝试获取 `mutex_`（如 `CleanupShard`），会形成死锁。

## 九、容错与恢复

### #S2 MockExecute 失败后 shard 结果永久丢失 🔴

**涉及文件**：`transcode_worker.cpp`

#### 现象

shard 在 Worker 上成功执行完成（sleep 5 秒结束），但 `ReportShardResult` RPC 因网络瞬时故障失败。Worker 记录一行 `LOG_ERROR`，随即清理 shard。Scheduler 仍标记该 shard 为 `ASSIGNED`（不会被重新调度），job 永久挂死。

#### 根因

```cpp
// 修复前：MockExecute 的结果上报段
rc_stub.ReportShardResult(&ctrl, &result_req, &result_resp, nullptr);

if (!ctrl.Failed() && result_resp.accepted())
{
    LOG_INFO("...SUCCESS...");
}
else
{
    LOG_ERROR("...result report failed: %s", ...);  // 仅打日志
}

CleanupShard(shard_id);  // ⚠️ 无条件清理！不论上报成功与否
```

问题链：

```text
1. Worker MockExecute → sleep 5s → 完成
2. ReportShardResult RPC 失败（网络抖动）
3. CleanupShard → 从 running_shards_ 移除
4. Worker 心跳不再上报该 shard  → Scheduler 不知道 shard 实际已执行完
5. Scheduler 仍看到 shard = ASSIGNED（非 WAITING）→ 不会被 SchedulingLoop 重新调度
6. Job 挂死 —— 永远等不到这个 shard 的结果
```

#### 后果

- shard 成功执行但结果**永久丢失**
- job 永久卡在 RUNNING 状态
- 无法自动恢复——需要人工介入

#### 修复

增加 3 次重试，全部失败后保留 shard 在 `running_shards_`，不调用 `CleanupShard`：

```cpp
bool result_reported = false;
for (int retry = 0; retry < 3 && !result_reported; ++retry)
{
    if (retry > 0)
        std::this_thread::sleep_for(std::chrono::seconds(1));

    // ... RPC 调用 ...

    if (!ctrl.Failed() && result_resp.accepted())
    {
        result_reported = true;
    }
}

if (!result_reported)
{
    LOG_ERROR("...FAILED after 3 retries, keeping in running_shards for recovery");
    return;  // ⚠️ 不调用 CleanupShard！
}

CleanupShard(shard_id);
```

保留在 `running_shards_` 中的意义：
- Worker 心跳继续上报 `current_running_shards`（包含这个 shard）
- 阶段 5 可以在心跳线程中增加重试上报逻辑
- Scheduler 通过 WorkerManager 可以看到该 shard 仍在运行
