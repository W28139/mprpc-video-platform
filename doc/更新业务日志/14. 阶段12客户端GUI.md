## 关键架构决策

### Q: GUI 与 mprpc 服务怎么通信——复用 mprpc consumer 还是 REST API？

路线图给出两个选项（Qt Network 调 REST / 直接嵌入 RPC client）。REST API 是阶段 14 的规划内容，本轮选择**直接嵌入 mprpc consumer**：link `video_common`（PUBLIC 传播 include + mprpc/protobuf/mysqlclient 等），复用 `MprpcChannel` 的 ZK 服务发现 + 连接池 + 超时 + 重试，GUI 零网络栈额外依赖，与 job_client 同源。

### Q: mprpc stub 是同步阻塞的，GUI 线程直接调会卡死——怎么异步化？

`MprpcChannel::CallMethod` 同步等响应（超时 5s），若在 UI 线程调用，RPC 期间界面冻结（拖动/点击全无响应）。方案：**QRunnable + QThreadPool 异步封装**（`rpc_client.h/.cpp`）——每个 RPC 一次任务，后台线程执行同步调用，结果经 Qt 信号（跨线程队列投递）回 UI 线程。单实例 stub 跨线程安全（MprpcChannel 内部连接池 + 互斥）。UI 侧只需连接信号，无需关心线程。

### Q: 任务列表没有数据源——为什么要加 ListJobs RPC？

现有接口只有 `QueryJob`（单 job 查询），GUI 任务列表需要"全部 job 概要"。两选项：GUI 直连 MySQL（破坏分层，GUI 只能走 RPC）或新增 ListJobs RPC。选后者：`ListJobsRequest{limit}` → `ListJobsResponse{repeated JobInfo}`，handler 仿 QueryJob 但**无 Redis 缓存、不查 shard**（列表 2s 高频查询，单表 SQL <1ms，缓存引入一致性复杂度且无收益）。`JobStore::ListRecent(limit)` SQL = ListAll + `ORDER BY created_at DESC LIMIT n`。

### Q: 实时进度为什么用 2s RPC 轮询而不是 WebSocket 推送？

路线图明确"WebSocket 或定时 RPC 拉取"。当前架构（阶段 10）已为高频 QueryJob 建好 Redis 进度缓存（TTL 60s），2s 轮询命中缓存直接返回，服务端开销 = 一次反序列化；且 RPC 链路已有连接池/超时/降级全套可靠性。WebSocket 需要服务端新增监听端口 + 连接管理 + 推送协议，是阶段 14 REST/推送的事——本轮选轮询，与现有架构契合。

### Q: 视频预览为什么用 ffplay 子进程而不是 Qt Multimedia？

qt6-multimedia 需要额外 apt 包（QMediaPlayer 播放本地文件）且 WSLg 下音视频管线复杂。ffplay 已随 ffmpeg 安装（阶段 6 依赖），`QProcess::startDetached` 一行启动独立窗口，`-autoexit` 播完自关，失败弹提示。功能等价、依赖最少。

### Q: 日志面板为什么 tail 本地文件而不是服务端推送？

路线图"服务端推送的关键日志"是完整形态；当前 5 服务同机部署（`program_log/` 按天轮转），LogPanel 每 2s 读最新文件新增部分（记录偏移），等价"实时滚动"，零服务端改动。推送留待阶段 14 统一做事件流。

### Q: 拖拽怎么实现？

SubmitDialog `setAcceptDrops(true)` + `dragEnterEvent`（只接受 `mimeData()->hasUrls()`）+ `dropEvent`（解析 `urls().first().toLocalFile()` 自动填 input_path）。路线图"拖拽视频文件 → 自动填充路径"达成。

### Bug 1：MqClient 消费锁占用 → mq=push 误判 + WARN 刷屏（阶段 10 验证发现，已修复）

**现象**：服务全新重启后 `consume lock busy (>1s, consumer may be stuck), degrade to Pull polling` 立即出现并持续刷（昨天 23:15 → 今早 08:02 共 1067 条/天）；SchedulingLoop 永远 `interval=2000ms (mq=pull)`，mq=push 状态从未被识别。

**根因**：`ConsumeBlocking` 在 `consume_mutex_` 锁内 `poll(2s)`。消费线程无消息时 2s 超时 → 释放锁 → 立即下一轮再持锁 poll——**锁几乎 100% 被占**。SchedulingLoop 每轮 `connected()` 的 `try_lock_for(1s)` 永远失败 → 误判 MQ 掉线（阶段 11 Bug 6 修复引入的降级路径在正常 MQ 下被永久触发）。

**修复**（`mq_client.h/.cpp`）：
1. **poll 移出锁**：poll 只操作 fd、不触碰 conn 内部状态；消费连接的销毁/重建只发生在消费线程自身（故障分支）或启动期——poll 期间无并发写者，无需持锁。锁只保护 `basic_consume` / read / 销毁的毫秒级窗口。
2. **`connected()` 无锁**：新增 `std::atomic<bool> consume_alive_`（连接重建置 false、成功置 true），`connected()` 直接返回标志——不再 try_lock_for 降级。
3. 销毁分支持锁并**先置标志再 destroy**（防止别的线程读到悬垂指针）。

**验证**：重启后 `SchedulingLoop thread started, interval=5000ms (mq=push)`（首次正确识别）；`consume lock busy` 刷屏消失；新任务 Push 分配 24ms、JOB_SUCCESS。
