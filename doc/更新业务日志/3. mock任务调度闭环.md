# 3. mock 任务调度闭环

**日期**：2026-07-28

**背景**：阶段 3 完成了 Worker 注册与心跳，WorkerManager 已能维护 Worker 生命周期。但 SchedulerService / TranscodeWorker / ResultCollector 的 RPC 方法全是空壳（只打日志返回成功），没有实际业务逻辑。阶段 4 的目标是打通从用户提交 Job 到最终返回 SUCCESS 的完整链路，用 sleep 模拟视频转码执行。

**设计决策**：
- Scheduler 按 mock 配置的时间参数切片（mock_job_duration_sec / mock_shard_duration_sec），不依赖真实视频探测
- 调度采用 Pull 模式：Scheduler 后台线程周期扫描 WAITING shard，匹配 ONLINE Worker，直连分配
- Worker 每个 shard 用独立线程 sleep 模拟执行，每秒上报进度，完成后上报 SUCCESS
- ResultCollector 做简单幂等处理（已 SUCCESS 的重复上报直接返回），通过扫描 shard 列表判断 job 是否全部完成

---

## 踩坑记录：跨进程内存存储不可见

### 现象

首轮联调时，`job_client` 提交 job 后，Scheduler 返回 `job not found`：

```
[JobService] SubmitJob created job_id=job_1785220070852_000000_2444
[Scheduler]  ScheduleJob job_id=job_1785220070852_000000_2444
[JobService] Scheduler.ScheduleJob failed: job not found: job_1785220070852_000000_2444
```

同时 ResultCollector 也无法找到 Worker 上报的 shard 结果。

### 根因

`JobStore`、`ShardStore`、`WorkerStore` 都是**进程内单例**（`static` 局部变量 + `std::unordered_map`），每个服务进程有自己独立的存储实例：

```
JobService 进程          SchedulerService 进程       ResultCollector 进程
┌──────────────┐        ┌──────────────┐           ┌──────────────┐
│ JobStore A   │        │ JobStore B   │           │ JobStore C   │
│ job_xxx ✓    │        │ (empty)      │           │ (empty)      │
│ ShardStore A │        │ ShardStore B │           │ ShardStore C │
│ (empty)      │        │ (empty)      │           │ (empty)      │
└──────────────┘        └──────────────┘           └──────────────┘
```

JobService 把 job 写入了 JobStore A，但 Scheduler 的 RPC handler 去查 JobStore B —— 空的。同理，Scheduler 切分出的 shard 只在 ShardStore B 中，Worker 上报给 ResultCollector 时 ResultCollector 查 ShardStore C —— 也是空的。

这是从单进程骨架（阶段 2）过渡到多进程联调（阶段 4）时暴露出的架构假设差异。阶段 2 每个服务独立测试、不相互调用，所以各进程独立存储没有暴露出问题。

### 修复

三个 RPC 入口在收到远程请求时，若本地 Store 没有对应记录，则从请求参数中构造本地副本：

| 文件 | RPC 方法 | 修复方式 |
|------|---------|---------|
| `scheduler_service.cpp` | `ScheduleJob` | 从 `request->job_info()` 构造 `JobRecord` 写入本地 `JobStore` |
| `result_collector.cpp` | `ReportShardResult` | 从 `request` 参数构造 `ShardRecord` 写入本地 `ShardStore` |
| `result_collector.cpp` | `CheckJobDone` | 若本地 `JobStore` 无此 job，创建最小副本记录终态 |

修复后数据流变为：

```text
JobService                SchedulerService              ResultCollector
┌────────────┐    RPC     ┌────────────┐     RPC        ┌────────────┐
│ JobStore   │ ──job──►  │ JobStore   │               │ JobStore   │
│ job_xxx ✓  │  request  │ job_xxx ✓  │               │ job_xxx ✓  │
│            │           │ (本地副本)  │               │ (按需创建)  │
│            │           │ ShardStore │               │ ShardStore │
│            │           │ shard_0 ✓  │ ──result──►   │ shard_0 ✓  │
│            │           │ shard_1 ✓  │  ReportResult │ shard_1 ✓  │
│            │           │ shard_2 ✓  │               │ shard_2 ✓  │
└────────────┘           └────────────┘               └────────────┘
```

### 后续改进方向（阶段 8 考虑）

当前每个进程独立存储是刻意为之（避免单点存储依赖、简化测试）。如果后续需要跨服务统一查询（如 JobService.QueryJob 要看到 Scheduler 更新的 shard_count），可选方案：
- A) 各进程定期从 "主" 进程同步状态（如 Scheduler → JobService 回推）
- B) 引入独立存储服务（如 Redis / etcd）
- C) 让 QueryJob 接受"可能不完整"的 shard 列表（当前已是这样，job 有 shard_count 但 shards 列表可能为空）

### 实施：跨进程状态同步（UpdateJobStatus RPC）

采用方案 A 的变体 — 在关键状态转换点通过 RPC 回调：

**proto 新增**（`job.proto`）：
```proto
rpc UpdateJobStatus(UpdateJobStatusRequest) returns (UpdateJobStatusResponse);
```

**调用链**：

```text
状态转换                         谁来通知 JobService
─────────────────────────────────────────────────────
PENDING → SCHEDULING (+shard_count)  Scheduler.ScheduleJob 完成后 RPC 回调
SCHEDULING → RUNNING                Scheduler.SchedulingLoop 首次分配 shard 时 RPC 回调
RUNNING → SUCCESS                   ResultCollector.CheckJobDone 全部完成时 RPC 回调
```

### 实施：job_client 查询模式

`job_client.cpp` 新增三种运行模式：

| 模式 | 命令 | 说明 |
|------|------|------|
| Submit | `./bin/job_client -i conf` | 交互式提交（原有） |
| Query | `./bin/job_client -i conf --query <job_id>` | 单次查询 |
| Watch | `./bin/job_client -i conf --query <job_id> --watch` | 每 2 秒轮询，终态自动停止 |

Query 输出包含：job 状态、shard 列表（含状态标记 ✓/✗/○）、进度条、重试次数。

## 一、框架层改动

### 1.1 MprpcChannel — 新增直连模式

**文件**：`mprpc/include/mprpcchannel.h` + `mprpc/src/mprpcchannel.cc`

**问题**：原 MprpcChannel 只支持通过 ZK 服务发现获取 endpoint，然后轮询选择实例。但 Scheduler → Worker 的 `AssignShard` 调用需要指定**特定** Worker（根据 `worker_id` 选择），不能随机轮询。

**改动**：

- **新增构造函数** `MprpcChannel(const std::string& ip, uint16_t port)`

  ```cpp
  MprpcChannel(const std::string& ip, uint16_t port)
      : direct_ip_(ip), direct_port_(port), use_direct_(true) {}
  ```

  调用方传入目标 Worker 的 IP 和端口，内部设置 `use_direct_ = true`。被 `SchedulingLoop()` 调用，用于直连特定 Worker 的 `AssignShard`。

- **新增私有成员**：

  ```cpp
  std::string direct_ip_;       // 直连目标 IP
  uint16_t direct_port_ = 0;   // 直连目标端口
  bool use_direct_ = false;    // 是否使用直连模式
  ```

- **修改 `CallMethod()` 的服务发现段**（第 775-817 行）：

  原逻辑：无条件走 ZK 服务发现 → `GetHostData()` → `ParseHostData()` 获取 ip/port。

  新逻辑：先判断 `use_direct_` 标志。若为 true，直接用 `direct_ip_` / `direct_port_`，跳过 ZK。若为 false，走原 ZK 发现流程不变。

- **修改 `CallMethod()` 的连接失败重试段**（第 827-843 行）：

  新增 `!use_direct_` 条件守卫：直连模式下不执行 `InvalidateHostData()` / `QueryEndpointList()` 等 ZK 缓存失效逻辑（这些变量在直连模式下为空/未初始化）。

- **修改 `CallMethod()` 的失败日志段**（第 845-852 行）：

  直连模式下用 `direct_ip_ + ":" + port` 构造日志中的 endpoint 字符串；否则用原 `host_data`。

**调用链**：
```
SchedulingLoop() 
  → MprpcChannel(worker.ip, worker.port)  // 构造直连 channel
  → WorkerService_Stub(&channel)
  → stub.AssignShard(...)                 // 内部调用 CallMethod()
      → use_direct_=true → 跳过 ZK，直接用 ip/port 连接
```

### 2.1 JobRecord — 新增 shard_duration_sec 字段

**新增字段**：

struct JobRecord {

**用途**：记录用户在 `SubmitJobRequest` 中指定的 `shard_duration_sec`。在 `ScheduleJob` 切分时优先使用此值，若为 0（用户未指定）则回退到 scheduler.conf 的 `mock_shard_duration_sec` 配置。

**读取方**：`SchedulerServiceImpl::ScheduleJob()` — 判断 `job->shard_duration_sec > 0` 来决定 shard 切分粒度。

### 2.2 ShardStore — 新增 ListByStatus 方法

**文件**：`video_platform/include/video_platform/common_store.h`（声明） + `video_platform/src/common_store.cpp`（实现）

**新增方法**：

```cpp
/// @brief 按状态过滤列出 shard。
/// @param status_filter 状态值，传 -1 表示列出全部。
/// 用途：Scheduler 调度循环查找 SHARD_WAITING 的待分配 shard。
std::vector<ShardRecord> ListByStatus(int32_t status_filter) const;
```

**实现**（`common_store.cpp` 第 177-187 行）：

```cpp
std::vector<ShardRecord> ShardStore::ListByStatus(int32_t status_filter) const
{
    std::shared_lock lock(mutex_);       // 读锁，允许多线程并发查询
    std::vector<ShardRecord> result;
    for (const auto& kv : shards_)
    {
        if (status_filter < 0 || kv.second.status == status_filter)
            result.push_back(kv.second);
    }
    return result;
}
```

线程安全：使用 `std::shared_lock`（读锁），与 `Insert/Update/Delete` 的写锁互斥。

**调用方**：`SchedulingLoop()` — 每轮扫描时调用 `ShardStore::GetInstance().ListByStatus(SHARD_WAITING)` 获取待分配 shard 列表。

## 三、SchedulerService 重写

**文件**：`video_platform/src/scheduler_service/scheduler_service.cpp`

这是阶段 4 改动最大的文件，从骨架升级为完整实现。

### 3.1 ScheduleJob RPC — 任务切分

**函数签名**：

```cpp
void SchedulerServiceImpl::ScheduleJob(
    google::protobuf::RpcController* controller,
    const ScheduleJobRequest* request,
    ScheduleJobResponse* response,
    google::protobuf::Closure* done) override
```

**调用方**：`JobServiceImpl::SubmitJob()` — 在创建 JobRecord 并写入 JobStore 后，通过 ZK 发现的 `SchedulerService_Stub` 发起 RPC 调用。

**执行流程**（5 步）：

1. **校验 job**：从 `JobStore::GetInstance().Get(job_id)` 获取 JobRecord。若不存在返回 error_code=1。
2. **读取 mock 配置**：
   - `MprpcApplication::GetConfig().LoadInt("mock_job_duration_sec", 60, 1, 86400)` — mock 视频总时长，默认 60 秒
   - `MprpcApplication::GetConfig().LoadInt("mock_shard_duration_sec", 20, 1, 3600)` — 每 shard 视频时长，默认 20 秒
   - 优先使用 `job->shard_duration_sec`（用户 SubmitJob 时指定），若为 0 则用配置默认值
   - `shard_count = mock_job_duration_sec / shard_dur`（默认 60/20 = 3 个 shard）
3. **更新状态 → JOB_SPLITTING**：`JobStore::Update(job_id, *job)`
4. **创建 ShardRecord**：循环 `shard_count` 次，每个 shard：
   - `shard_id = "{job_id}_shard_{i}"`
   - `start_ms = i * shard_duration_ms`，`duration_ms = shard_duration_ms`
   - `status = SHARD_WAITING`
   - `max_retry = 3`
   - 调用 `ShardStore::Insert(shard)` 写入
5. **更新状态 → JOB_SCHEDULING**：回填 `job->shard_count`，`JobStore::Update(job_id, *job)`

### 3.2 RescheduleShard RPC — 重新调度

**函数签名**：

```cpp
void SchedulerServiceImpl::RescheduleShard(
    google::protobuf::RpcController* controller,
    const RescheduleShardRequest* request,
    RescheduleShardResponse* response,
    google::protobuf::Closure* done) override
```

**调用方**：阶段 4 尚未有调用方（阶段 5 将由 ResultCollector 在 shard 失败时调用）。

**执行流程**：
1. 从 `ShardStore::Get(shard_id)` 获取 ShardRecord
2. 重置为 WAITING 状态，清空 `assigned_worker_id`，`retry_count++`
3. 写入 ShardStore → 后台 `SchedulingLoop` 会在下一轮扫描到它并重新分配

### 3.3 SchedulingLoop — 后台调度线程

**函数签名**：

```cpp
static void SchedulingLoop(std::atomic<bool>& stop_flag)
```

**调用方**：`main()` — 在 Provider 启动前创建 `std::thread(SchedulingLoop, std::ref(scheduling_stopped))`，Provider 退出后设置 `stop_flag=true` 并 `join()`。

**常量**：
- `kScheduleIntervalMs = 2000` — 每 2 秒扫描一轮
- `kAssignTimeoutMs = 5000` — AssignShard RPC 超时（5 秒）

**RPC Stub 初始化**：
- `WorkerManagerService_Stub wm_stub(new MprpcChannel())` — 通过 ZK 发现 WorkerManager，用于每轮查询在线 Worker 列表
- 每个 worker 分配时创建 `MprpcChannel(ip, port)` 直连 + `WorkerService_Stub` — 用于调用特定 Worker 的 AssignShard

**每轮执行流程**：

```
while (!stop_flag) {
    sleep(2s)
    
    // 1. 扫描 WAITING shard
    waiting_shards = ShardStore.ListByStatus(SHARD_WAITING)
    if empty → continue
    
    // 2. 查询 ONLINE Worker (RPC: WorkerManager.ListWorkers)
    wm_stub.ListWorkers(WORKER_ONLINE) → lw_resp
    if failed or empty → continue
    
    // 3. 对每个 WAITING shard 选 Worker
    for each shard in waiting_shards:
        // 选 available_slots 最大的 worker
        //   available_slots = max_running_shards - current_running_shards
        best_worker = argmax(available_slots)
        if best_slots <= 0 → continue (下一轮重试)
        
        // 4. 直连 Worker (RPC: WorkerService.AssignShard)
        worker_channel = MprpcChannel(best_worker.ip, best_worker.port)
        worker_stub.AssignShard(shard) → as_resp
        if failed → continue (下一轮重试)
        
        // 5. 更新 shard → SHARD_ASSIGNED
        shard.status = SHARD_ASSIGNED
        shard.assigned_worker_id = best_worker.worker_id
        shard.attempt_id = "{shard_id}_attempt_{retry_count}"
        ShardStore.Update(shard)
        
        // 6. 首次分配时更新 job → JOB_RUNNING
        if job.status == JOB_SCHEDULING:
            job.status = JOB_RUNNING
            JobStore.Update(job)
}
```

**Worker 选择策略**（贪心最优槽位）：

```cpp
int available = w.max_running_shards() - w.current_running_shards();
// 选 available 最大的 worker
```

当前为最简单的贪心算法，阶段 7 将扩展为 `score = available_slots * 10 - cpu_usage * 0.5 - memory_usage * 0.2` 的资源感知评分。

### 3.4 main — 启动流程改动

**改动前**（阶段 3）：启动 `PeriodicListWorkers` 线程（只查询打印 Worker 列表）。

**改动后**（阶段 4）：启动 `SchedulingLoop` 线程（扫描 WAITING shard + 分配 Worker）。

```cpp

```

## 四、TranscodeWorker 重写

**文件**：`video_platform/src/transcode_worker/transcode_worker.cpp`

从骨架升级为完整实现。TranscodeWorker 拥有双重角色：作为 Provider 接收 Scheduler 命令，作为 Consumer 调用 ResultCollector 上报。

### 4.1 RunningShard — 新增内部结构体

```cpp
struct RunningShard {
    ShardInfo   info;                      // shard 元信息（proto 拷贝）
    std::string attempt_id;               // 执行尝试 ID
    std::atomic<int> progress{0};        // 执行进度 0-100（原子变量，无锁读取）
    std::atomic<bool> cancelled{false};  // 取消标志（原子变量，无锁读取）
    std::thread executor_thread;         // mock 执行线程句柄
};
```

**存储位置**：`WorkerServiceImpl` 私有成员 `std::unordered_map<std::string, std::shared_ptr<RunningShard>> running_shards_`，由 `mutable std::mutex mutex_` 保护。

**生命周期**：在 `AssignShard` 中创建 → `MockExecute` 线程运行 → `CleanupShard` 从 map 移除 + detach 线程。

### 4.2 RunningShardCount — 新增查询方法

```cpp
int RunningShardCount() const {
    std::lock_guard<std::mutex> lock(mutex_);
    int count = 0;
    for (const auto& kv : running_shards_) {
        if (!kv.second->cancelled) ++count;
    }
    return count;
}
```

**调用方**：`RunHeartbeatLoop()` — 每 3 秒心跳时调用，获取真实的 `current_running_shards` 上报给 WorkerManager。

### 4.3 AssignShard RPC — 接收任务并启动 mock 线程

**函数签名**：

```cpp
void WorkerServiceImpl::AssignShard(
    google::protobuf::RpcController* controller,
    const AssignShardRequest* request,
    AssignShardResponse* response,
    google::protobuf::Closure* done) override
```

**调用方**：`SchedulingLoop()` — 通过直连 `MprpcChannel(ip, port)` 调用本 RPC。

**执行流程**：
1. **重复检查**：若 `running_shards_` 中已有同 `shard_id` 且未被取消的记录，返回 `accepted=false`
2. **生成 attempt_id**：`"{shard_id}_attempt_{retry_count}"`
3. **创建 RunningShard**：`std::make_shared<RunningShard>(shard, attempt_id)`
4. **读取 mock 配置**：`MprpcApplication::GetConfig().LoadInt("mock_execution_time_ms", 5000, 500, 120000)` — 默认 5 秒
5. **启动 mock 线程**：`rs->executor_thread = std::thread(&WorkerServiceImpl::MockExecute, this, rs, mock_execution_ms)`
6. **加入 map**：`running_shards_[shard.shard_id()] = rs`
7. 返回 `accepted=true`

### 4.4 MockExecute — mock 执行器（核心方法）

**函数签名**：

```cpp
void WorkerServiceImpl::MockExecute(
    std::shared_ptr<RunningShard> rs,  // 共享所有权，保证线程安全
    int mock_execution_ms)             // mock 执行总时长（毫秒）
```

**调用方**：`AssignShard()` — 作为 `std::thread` 的入口函数在新线程中运行。

**执行流程**：

```
total_steps = mock_execution_ms / 1000  (每秒一个 step)

for step = 1 to total_steps:
    sleep(1000ms)
    
    if rs->cancelled:  // 被 CancelShard 取消了
        CleanupShard(shard_id)
        return
    
    progress = step * 100 / total_steps
    rs->progress = progress
    
    // ── RPC: ResultCollector.ReportShardProgress ──
    rc_stub.ReportShardProgress(shard_id, job_id, worker_id, attempt_id, progress)
    
// 执行完成
rs->progress = 100

// ── RPC: ResultCollector.ReportShardResult ──
rc_stub.ReportShardResult(shard_id, job_id, worker_id, attempt_id, 
                          is_success=true, exit_code=0, output_path, elapsed_ms)

CleanupShard(shard_id)
```

**ResultCollector Stub**：使用 `MprpcChannel()` 无参构造 → 通过 ZK 发现 `ResultCollectorService` 的 endpoint。

**错误处理**：进度上报失败只打 WARN 日志不中断执行（下一轮继续重试）；结果上报失败打 ERROR 日志（但 shard 实际已执行完成，后续重试机制可兜底）。

### 4.5 CleanupShard — 清理方法

```cpp
void CleanupShard(const std::string& shard_id)
```

从 `running_shards_` map 中移除指定 shard，并对线程执行 `detach()`（线程即将结束，detach 让系统回收资源，避免 join 阻塞）。

在锁外操作线程句柄，避免与 `AssignShard` / `CancelShard` 死锁。

### 4.6 CancelShard RPC — 取消任务

**函数签名**：

```cpp
void WorkerServiceImpl::CancelShard(...) override
```

**调用方**：Scheduler 在需要中止 shard 时调用（阶段 4 尚不触发，阶段 5 用于心跳超时恢复）。

**执行流程**：在锁内查找 `running_shards_` → 设置 `rs->cancelled = true` → mock 线程在下一个 sleep 周期检测到标志并提前退出。

### 4.7 QueryShard RPC — 查询进度

**函数签名**：

```cpp
void WorkerServiceImpl::QueryShard(...) override
```

**调用方**：Scheduler 或外部查询工具。

**执行流程**：在锁内查找 `running_shards_` → 返回 `rs->progress`（原子变量读取）+ ShardInfo。若 shard 不在本 Worker，返回 `progress=-1`。

**改动后**（阶段 4）：

```cpp
static void RunHeartbeatLoop(std::string worker_id, int cpu_cores, int memory_mb,
                              int max_running_shards,
                              WorkerServiceImpl* worker_service,  // 新增参数
                              std::atomic<bool>& stop_flag)
```

**改动点**：
- 新增参数 `WorkerServiceImpl* worker_service`，用于获取真实的运行中 shard 数量
- 心跳构造时：`load->set_running_shards(worker_service ? worker_service->RunningShardCount() : 0)` — 不再硬编码为 0
- `worker_service` 可能为 nullptr（若 Provider 尚未初始化），此时回退为 0

**调用方**：`main()` — 创建 `WorkerServiceImpl*` 后传给此函数。

## 五、ResultCollector 重写

**文件**：`video_platform/src/result_collector/result_collector.cpp`

### 5.1 ReportShardProgress RPC — 进度上报

**改动**：阶段 2 骨架只打日志不记录。阶段 4 仍然只打日志（ShardRecord 没有 progress 字段），但增加了详细的调试信息（worker / attempt_id / progress%）。

### 5.2 ReportShardResult RPC — 结果聚合（核心）

**函数签名**：

```cpp
void ResultCollectorServiceImpl::ReportShardResult(
    google::protobuf::RpcController* controller,
    const ReportShardResultRequest* request,
    ReportShardResultResponse* response,
    google::protobuf::Closure* done) override
```

**调用方**：`WorkerServiceImpl::MockExecute()` — shard 执行完成后调用，通过 ZK 发现的 `ResultCollectorService_Stub` 发起 RPC。

**执行流程**（4 步）：

1. **查找 shard**：`ShardStore::Get(shard_id)`。不存在返回 `accepted=false`。
2. **幂等检查**：若 `shard->status == SHARD_SUCCESS`，表示已处理过（可能因网络问题重复上报），直接返回 `accepted=true, job_done=CheckJobDone(job_id)`。不重复更新状态。
3. **更新 shard**：`shard->status = SUCCESS/FAILED`，回填 `attempt_id`、`output_path`，`ShardStore::Update(shard_id, *shard)`。
4. **判断 job 完成**：调用私有方法 `CheckJobDone(job_id)` → 若返回 true 则 `response->set_job_done(true)`。

### 5.3 CheckJobDone — job 完成判断（新增私有方法）

```cpp
bool CheckJobDone(const std::string& job_id)
```

**调用方**：`ReportShardResult()` — 每次收到 shard 结果时调用。

**执行流程**：

```
shards = ShardStore.ListByJob(job_id)         // 获取 job 下所有 shard
if shards.empty() → return false              // 防御：job 可能没有 shard

for each shard:
    if shard.status != SHARD_SUCCESS → return false  // 有未完成的 shard

// 所有 shard 都是 SUCCESS
job = JobStore.Get(job_id)
job.status = JOB_SUCCESS
JobStore.Update(job_id, job)
return true
```

**原子性考虑**：`ListByJob` 获取快照（shared_lock 读锁），`Update(job)` 获取写锁。两个操作之间有窗口，但由于幂等检查的存在（已 SUCCESS 的不再处理），多次并发调用 `CheckJobDone` 的结果是安全的（最后一个到达的发现已经是 JOB_SUCCESS，不会重复写入）。

## 六、JobService 改动

**文件**：`video_platform/src/job_service/job_service.cpp`

### 6.1 SubmitJob RPC — 新增 Scheduler 串联

**改动点**：

1. **新增参数校验**：`input_path` 为空时返回 error_code=1（防用户误操作）
2. **新增字段写入**：`job.shard_duration_sec = request->shard_duration_sec()` — 将用户指定的 shard 粒度传递给 Scheduler
3. **新增 RPC 调用**：在 `done->Run()` 之前，通过 ZK 发现 `SchedulerService` 并调用 `ScheduleJob`：

```cpp
MprpcChannel sched_channel;                    // ZK 发现 SchedulerService
SchedulerService_Stub sched_stub(&sched_channel);
ScheduleJobRequest sched_req;
*sched_req.mutable_job_info() = *jobInfo;      // 拷贝 SubmitJob 响应的 JobInfo
sched_stub.ScheduleJob(&sched_ctrl, &sched_req, &sched_resp, nullptr);
```

4. **容错设计**：`ScheduleJob` 调用失败不阻塞 `SubmitJob` 响应 — job 已成功创建并写入存储，Scheduler 的后台 `SchedulingLoop` 可以通过重新扫描发现未切分的 job（后续增强）。

**调用链**：

```
job_client
  → JobService_Stub.SubmitJob (ZK 发现)
    → JobServiceImpl::SubmitJob()
        ├── JobStore.Insert(job)              // 写入 job
        ├── response.set_job_id(job_id)       // 构造响应
        ├── SchedulerService_Stub.ScheduleJob (ZK 发现)
        │     → SchedulerServiceImpl::ScheduleJob()
        │         ├── JobStore.Get(job_id)    // 校验
        │         ├── 创建 N 个 ShardRecord
        │         ├── ShardStore.Insert(shard) * N
        │         └── JobStore.Update(job → SCHEDULING)
        └── done->Run()                       // 返回 SubmitJob 响应给 client
```

## 八、完整调用链路

以下是一个 job 从提交到完成的完整 RPC 调用链：

```text
[步骤 1] job_client
    │
    └─ RPC: JobService.SubmitJob ─────────────────────► JobService
         (ZK 发现 /mprpc/services/JobService/SubmitJob)    │
                                                           ├─ GenerateId("job") → job_id
                                                           ├─ JobStore.Insert(job)    [PENDING]
                                                           │
    [步骤 2]                                               ├─ RPC: Scheduler.ScheduleJob ───► SchedulerService
                                                           │        (ZK 发现)                    │
                                                           │                                      ├─ JobStore.Get(job_id)
                                                           │                                      ├─ 读取 mock_job_duration_sec=60
                                                           │                                      ├─ 读取 mock_shard_duration_sec=20
                                                           │                                      ├─ shard_count=60/20=3
                                                           │                                      ├─ JobStore.Update → SPLITTING
                                                           │                                      ├─ 循环 3 次: ShardStore.Insert(shard)
                                                           │                                      │   shard_id=job_xxx_shard_0/1/2
                                                           │                                      │   status=SHARD_WAITING
                                                           │                                      └─ JobStore.Update → SCHEDULING
                                                           │
                                                           └─ 返回 SubmitJobResponse → job_client
                                                              (job_id, status=PENDING)

[步骤 3 — 后台异步] SchedulingLoop (SchedulerService 后台线程, 每 2s 扫描)
    │
    ├─ ShardStore.ListByStatus(SHARD_WAITING) → [shard_0, shard_1, shard_2]
    │
    ├─ RPC: WorkerManager.ListWorkers(WORKER_ONLINE) → WorkerManager
    │        (ZK 发现)                     │
    │                                       └─ WorkerStore.ListByStatus(ONLINE)
    │                                          → [worker_001:9004, worker_002:9010, worker_003:9011]
    │
    ├─ 对 shard_0: 选 worker_001 (slots=2)
    │   ├─ RPC: WorkerService.AssignShard ────────────► TranscodeWorker (worker_001:9004)
    │   │        (直连 MprpcChannel 127.0.0.1:9004)          │
    │   │                                                     ├─ 创建 RunningShard
    │   │                                                     ├─ 读取 mock_execution_time_ms=5000
    │   │                                                     └─ 启动 MockExecute 线程
    │   └─ ShardStore.Update(shard_0 → ASSIGNED, worker_001)
    │
    ├─ 对 shard_1: 选 worker_002 (slots=4) → AssignShard → 9004
    ├─ 对 shard_2: 选 worker_003 (slots=2) → AssignShard → 9005
    │
    └─ JobStore.Update(job → RUNNING)

[步骤 4 — Worker 后台异步] MockExecute 线程 (每个 shard 一个线程)
    │
    ├─ loop step=1..5 (5000ms/1000ms=5 步):
    │   ├─ sleep(1000ms)
    │   ├─ rs->progress = step*20%
    │   └─ RPC: ResultCollector.ReportShardProgress ──► ResultCollector
    │            (ZK 发现)                                   │
    │                                                        └─ LOG_INFO 记录日志  [recorded=true]
    │
    └─ 完成后:
        ├─ rs->progress = 100
        └─ RPC: ResultCollector.ReportShardResult ────► ResultCollector
                 (ZK 发现)                                   │
                                                            ├─ ShardStore.Get(shard_id)
                                                            ├─ 幂等检查: status != SUCCESS → 继续
                                                            ├─ ShardStore.Update(shard → SUCCESS)
                                                            ├─ CheckJobDone(job_id):
                                                            │   ├─ ListByJob() → 检查所有 shard
                                                            │   ├─ 若全部 SUCCESS → JobStore.Update(job → SUCCESS)
                                                            │   └─ 返回 true/false
                                                            └─ response.job_done = true/false

[步骤 5] job_client 查询
    │
    └─ RPC: JobService.QueryJob(job_id) ──────────────► JobService
                                                             ├─ JobStore.Get(job_id) → SUCCESS
                                                             ├─ ShardStore.ListByJob(job_id) → 3 个 SUCCESS shard
                                                             └─ 返回完整 job + shards 列表
```

## 九、验收清单

| 验收项 | 对应功能 | 验证方式 |
|--------|---------|---------|
