# 2. Worker 注册与心跳

## 日期

2026-07-27

## 背景

阶段 2 骨架中，TranscodeWorker 只是一个纯 Provider（接收 AssignShard 等 RPC 命令），WorkerManager 已实现 RegisterWorker / Heartbeat / ListWorkers 的 RPC 处理逻辑，但缺少两个关键能力：

1. **TranscodeWorker 不主动注册和发心跳** — 它没有 Consumer 端逻辑
2. **WorkerManager 不检测心跳超时** — 没有后台线程把超时 Worker 标为 OFFLINE

本阶段按照 `doc/视频转码平台/04_开发路线图.md` 的阶段 3 规划，实现 Worker 的完整生命周期管理：启动注册 → 周期心跳 → 超时检测 → OFFLINE 标记 → 重新注册。

另外，阶段 2 中规划的 `job_client`（SubmitJob 命令行客户端）也在本阶段补充完成。

## 1. TranscodeWorker 双角色重写

改造前，TranscodeWorker 是一个纯 Provider：启动 RpcProvider → 注册 WorkerService → 阻塞等待调度命令。改造后增加了 Consumer 角色，变为双角色服务。

### 1.1 `RunHeartbeatLoop()` — 心跳后台线程

新增静态函数，在独立线程中运行，负责与 WorkerManager 的所有 Consumer 端交互。

**参数**：`worker_id`、`cpu_cores`、`memory_mb`、`max_running_shards`（从配置文件读取后传入）、`stop_flag`（主线程控制的退出信号）。

**执行流程**：

1. **读取自身地址**：从配置中获取 `rpcserverip` / `rpcserverport`，作为注册时上报的监听地址
2. **创建 RPC Stub**：`WorkerManagerService_Stub`，通过 ZooKeeper 自动发现 WorkerManager 服务地址
3. **RegisterWorker**：向 WorkerManager 注册自身，携带硬件信息（CPU 核心数、内存大小、最大并发 shard 数）。带退避重试机制（最多 3 次、间隔 1 秒），全部失败则线程退出
4. **Heartbeat 循环**：注册成功后，每 3 秒发送一次心跳，上报 `WorkerLoad`（其中 `cpu_usage`、`memory_usage`、`running_shards` 等字段当前阶段暂为 0，后续阶段接入真实指标采集）

**设计要点**：
- 心跳线程在 `provider.Run()` 之前启动，确保 Worker 先注册再对外提供服务
- 线程使用 `std::atomic<bool>&` 接收停止信号，主线程在 Provider 退出后设置标志并 join
- `MprpcChannel::CallMethod()` 是同步阻塞调用、线程安全，与 Provider 的事件循环不冲突

### 1.2 `main()` 重构

启动流程从原来的 3 步扩展为 6 步：

```
1. AsyncLogger::init()
2. MprpcApplication::Init(argc, argv)
3. 读取 Worker 配置（worker_id / cpu_cores / memory_mb / max_running_shards）
   - worker_id:         LoadRequired，缺少则启动失败
   - cpu_cores:         LoadInt 带哨兵 -1，范围 1~1024
   - memory_mb:         LoadInt 带哨兵 -1，范围 128~1048576
   - max_running_shards: LoadInt 带哨兵 -1，范围 1~1024
4. 启动心跳线程 RunHeartbeatLoop()
5. RpcProvider 注册 WorkerServiceImpl → provider.Run() 阻塞
6. 退出清理：设置 stop_flag → join 心跳线程 → logger.stop()
```

## 2. WorkerManager 增强

### 2.1 `HeartbeatTimeoutCheck()` — 心跳超时检测线程

新增静态函数，在独立线程中运行，周期性扫描 WorkerStore，将超时未心跳的 Worker 标记为 OFFLINE。

**参数**：`stop_flag`（主线程控制的退出信号）。

**核心常量**：
- `kHeartbeatTimeoutMs = 10000`（10 秒）
- `kCheckIntervalMs = 2000`（每 2 秒扫描一次）

**执行流程**：

1. 每 2 秒调用 `WorkerStore::ListAll()` 获取所有 Worker 快照
2. 对每个 ONLINE 状态的 Worker，检查 `NowMs() - last_heartbeat > 10s`
3. 对疑似超时的 Worker，通过 `WorkerStore::Get()` 做二次确认（重新获取最新记录后再次检查，减少 TOCTOU 竞争窗口）
4. 确认超时后，将状态修改为 `WORKER_OFFLINE`，写入 WorkerStore，记录 WARN 日志

**验收保证**：Worker 心跳周期 3s + 检测间隔 2s + 超时阈值 10s，允许 Worker 最多连续丢失 3 次心跳才被标 OFFLINE。

### 2.2 `RegisterWorker()` — 重新注册支持

原有逻辑仅调用 `WorkerStore::Insert()`，worker_id 已存在时静默失败（`try_emplace` 返回 false）。改造后增加 fallback：

```
if (!WorkerStore::GetInstance().Insert(worker))
    WorkerStore::GetInstance().Update(worker.worker_id, worker)
```

**目的**：Worker 进程重启后使用配置文件中的相同 `worker_id` 重新注册，覆盖旧的（OFFLINE）记录，恢复到 ONLINE 状态。

## 3. JobClient — 命令行客户端

### 3.1 `main()` — 交互式作业提交

为阶段 2 补充的 SubmitJob 客户端工具，用于端到端验证。

**执行流程**：

1. 初始化 mprpc 框架 + 创建 `JobService_Stub`（通过 ZK 发现 JobService）
2. 逐项交互式输入：`user_id`、`input_path`、`output_path`、`target_format`、`target_resolution`、`target_bitrate`、`priority`、`shard_duration_sec`
3. 调用 `stub.SubmitJob()` 同步 RPC
4. 打印结果：成功则显示 `job_id` + `JobInfo`，失败则显示错误码和错误信息

### 3.2 `safeReadInt()` — 安全整数输入

辅助函数，封装 `std::stoi` 的异常处理。输入非法字符时提示重新输入，不会崩溃。空输入（直接回车）返回 false，表示跳过该字段使用默认值。

**配置**：`job_client.conf` 只需 ZK 地址（`zookeeperip` / `zookeeperport`），不需要 `rpcserverip`，因为客户端通过 ZK 发现服务。

## 4. 配置文件变更

### 4.1 Worker 配置统一命名

三个 Worker 配置文件统一使用 `transcode_worker_{port}.conf` 格式：

| 文件 | 端口 | worker_id | CPU 核心 | 内存 | 最大 shard |
|------|------|-----------|---------|------|-----------|
| `transcode_worker_9004.conf` | 9004 | worker_001 | 4 | 8192MB | 2 |
| `transcode_worker_9010.conf` | 9010 | worker_002 | 8 | 16384MB | 4 |
| `transcode_worker_9011.conf` | 9011 | worker_003 | 4 | 8192MB | 2 |

### 4.2 新增配置项

每个 Worker 配置文件新增 4 个必填键：

| 配置键 | 类型 | 范围 | 说明 |
|--------|------|------|------|
| `worker_id` | string | — | 全局唯一 Worker 标识（重启时保持不变） |
| `cpu_cores` | int | 1~1024 | 上报给调度器的 CPU 核心数 |
| `memory_mb` | int | 128~1048576 | 上报给调度器的总内存（MB） |
| `max_running_shards` | int | 1~1024 | Worker 允许的最大并发 shard 数 |

### 4.3 可选的线程数配置

每个 Worker 配置支持 `rpcserverio_threads` 和 `rpcserverwork_threads`，用于控制 IO 线程和业务线程数量。测试环境建议设为 2，减少线程开销。

### 5.1 `MprpcConfig::LoadConfigFile()` — 行内注释支持

配置解析器新增行内注释识别：解析 `key=value` 后，如果 value 中包含 `#` 字符，则 `#` 及之后的内容被视为注释并被截断。

```

# 现在也支持行尾注释：

```

## 8. Bug 修复（2026-07-27）

针对 Code Review 发现的 P0/P1/P2 问题逐一修复，全部编译通过。

### 8.1 WorkerStore 新增 3 个原子方法（修复 Bug #1, #2）

**修改文件**：`video_platform/include/video_platform/common_store.h`、`video_platform/src/common_store.cpp`

新增方法（均在 `unique_lock` 内完成读-改-写，消除 TOCTOU 竞争窗口）：

```cpp
// 原子更新心跳：查找 → 更新 last_heartbeat/status/running_shards，全程持写锁
bool UpdateHeartbeat(const std::string& worker_id, int32_t running_shards);

// 原子超时标记：查找 → 确认 ONLINE → 确认超时 → 标记 OFFLINE，全程持写锁
bool MarkOfflineIfTimeout(const std::string& worker_id, int64_t now, int64_t timeout_ms);

// 原子 upsert：key 不存在则插入，存在则覆盖，全程持写锁
bool InsertOrUpdate(const WorkerRecord& worker);
```

`common_store.cpp` 需要 `#include "worker.pb.h"` 以使用 `WorkerStatus` 枚举。

### 8.2 worker_manager.cpp 调用方重构（修复 Bug #1, #2）

**修改文件**：`video_platform/src/worker_manager/worker_manager.cpp`

| 方法 | 旧代码模式 | 新代码 |
|------|-----------|--------|
| `RegisterWorker` | `Insert()` → 失败则 `Update()` | `InsertOrUpdate()` 一次调用 |
| `Heartbeat` | `Get()` → 裸指针修改 → `Update()` | `UpdateHeartbeat()` 一次调用 |
| `HeartbeatTimeoutCheck` | `Get()` → 二次确认 → 裸指针修改 → `Update()` | `MarkOfflineIfTimeout()` 一次调用 |

旧代码中 `Get()` 返回裸指针后锁已释放，后续通过该指针修改字段和调用 `Update()` 之间存在竞争窗口。新代码所有操作在 `unique_lock` 内完成，与并发的 `UpdateHeartbeat`（心跳 RPC）互斥。

### 8.3 MprpcChannel 栈分配消除泄漏（修复 Bug #3）

**修改文件**：`video_platform/src/transcode_worker/transcode_worker.cpp`

```cpp
// 旧：堆分配，Stub 析构不释放 channel → 泄漏
WorkerManagerService_Stub stub(new MprpcChannel());

// 新：栈分配，channel 和 stub 同生命周期自动析构
```

### 8.4 配置解析器 `#` 截断收窄（修复 Bug #4）

**修改文件**：`mprpc/src/mprpcconfig.cc`

### 9.1 新增 PeriodicListWorkers 后台线程
