# 5. 阶段5失败重试与故障恢复

## 日期

2026-07-29

## 前置状态

阶段 4（commit `da71d14`）已完成 mock 任务调度闭环并修复了 15 项代码审查 bug。系统能跑通 submit → split → assign → execute → collect → success 的完整链路，但在 Worker 失败、进程崩溃等故障场景下完全缺乏自动恢复能力。

## 阶段目标

使系统在以下 5 种故障场景下具备自动恢复能力（摘自路线图）：

| 场景 | 描述 | 恢复机制 |
|------|------|----------|
| 1. Worker 执行失败 | shard 执行过程中返回非零退出码 | ResultCollector → RescheduleShard → 重试 |
| 2. Worker 进程退出 | Worker 崩溃或被 kill -9 | 心跳超时检测 → NotifyWorkerOffline → 重调度 |
| 3. Worker 上报超时 | Worker 存活但网络故障无法上报结果 | 心跳超时兜底 |
| 4. 重复上报结果 | Worker 重试后旧 attempt 的结果延迟到达 | attempt_id 幂等校验 |
| 5. Scheduler 重启 | Scheduler 本身崩溃后恢复 | 启动恢复扫描残留 shard |

对应 3 项验收标准：
- 杀掉正在执行任务的 Worker，任务最终仍能完成
- 同一个 shard 重复上报 SUCCESS，不影响最终结果
- 超过最大重试次数后 job 变 FAILED

## 架构设计

### 重试链路全景

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         阶段 5 故障恢复链路                              │
│                                                                          │
│  TranscodeWorker                   ResultCollector                      │
│  ┌──────────────┐                 ┌───────────────────┐                │
│  │ MockExecute  │──FAILED────────►│ ReportShardResult │                │
│  │ (mock_fail   │                 │                   │                │
│  │  _ratio=40)  │                 │ ① attempt_id 校验 │                │
│  │              │                 │ ② 标记本地 FAILED │                │
│  │              │                 │ ③ ──RPC─────────►│──RescheduleShard─►│
│  └──────────────┘                 └───────────────────┘                  │
│                                                                          │
│  WorkerManager                     SchedulerService                      │
│  ┌──────────────────┐             ┌────────────────────────┐            │
│  │ HeartbeatTimeout │             │ RescheduleShard        │            │
│  │ Check (每2s)      │             │                        │            │
│  │                  │             │ retry >= max?          │            │
│  │ 检测到超时(10s)  │             │  YES → SHARD_FAILED    │            │

│                                    │ SchedulingLoop (每2s)  │            │
│                                    │ 扫描 WAITING shard     │            │
│                                    │ 拉取 ONLINE Worker     │            │
│                                    │ AssignShard → Worker   │            │
│                                    └────────────────────────┘            │
└─────────────────────────────────────────────────────────────────────────┘
```

### 关键设计决策

**Q: ResultCollector 收到 FAILED 后由谁触发重试？**

A: ResultCollector 主动调用 Scheduler.RescheduleShard。这样设计的理由：
- ResultCollector 是发现 FAILED 的第一站，立即触发重试延迟最小
- Scheduler 不需要额外的心跳或轮询来发现 FAILED shard
- 如果 RescheduleShard RPC 失败（Scheduler 暂时不可用），shard 保留在本地 FAILED 状态，
  SchedulingLoop 不扫描 FAILED shard，但 CheckJobDone 会因为 in_progress > 0 而等待。
  阶段 8 可增加 Scheduler 定时扫描 FAILED shard 的兜底机制

**Q: attempt_id 格式为什么选择 `{shard_id}_attempt_{N}`？**

A: 这种自描述格式有两个好处：
- 不需要额外的 RPC 来查询 retry_count——从字符串直接解析
- 在日志中可以直接看到是第几次重试，便于排查问题
- Scheduler 在 AssignShard 时从 ShardRecord.retry_count 构造 attempt_id，
  Worker 透传到所有 RPC 调用中

**Q: WorkerManager 检测到心跳超时后，为什么不直接操作 ShardStore 而是通过 RPC？**

A: ShardStore 是进程内单例，WorkerManager 进程中没有 shard 数据。
shard 到 worker 的映射关系只在 Scheduler 进程的 ShardStore 中维护。
WorkerManager 只能通过 RPC 通知 Scheduler"某 Worker 离线了"，
由 Scheduler 自主查找并处理该 Worker 的 shard。这保持了各服务 Store 的边界清晰。

**Q: Scheduler 启动恢复为什么不增加 retry_count？**

A: 这是 Scheduler 自身崩溃导致的问题，不是 Worker 执行失败。如果增加 retry_count，
会导致无意义的"惩罚"——shard 可能还没被执行过就被计了一次重试。
合理的做法是：不增加 retry_count，将残留 shard 重置为 WAITING 重新分配。

## 实现步骤

### Step 1: Proto 变更

**文件**：`video_platform/proto/scheduler.proto`

新增 `NotifyWorkerOffline` RPC，让 WorkerManager 能通知 Scheduler 某 Worker 离线：

```proto
message NotifyWorkerOfflineRequest {
    string worker_id = 1;  // 已离线的 Worker ID
    string reason    = 2;  // TIMEOUT / GRACEFUL_SHUTDOWN
}

message NotifyWorkerOfflineResponse {
    int32  error_code        = 1;
    string error_msg         = 2;
    int32  rescheduled_count = 3;  // 被重新调度的 shard 数量
}
```

在 `service SchedulerService` 中新增：
```proto
rpc NotifyWorkerOffline(NotifyWorkerOfflineRequest) returns (NotifyWorkerOfflineResponse);
```

### Step 2: Worker mock 随机失败注入

**文件**：`video_platform/src/transcode_worker/transcode_worker.cpp`

在 `MockExecute` 方法的结果上报段增加随机失败逻辑。关键设计：

1. **配置驱动**：`mock_fail_ratio` 配置项（0-100），不需要重新编译即可切换测试场景
2. **线程安全随机**：使用 `thread_local std::mt19937`，每个 MockExecute 线程独立生成器
3. **错误信息携带**：失败时 `is_success=false`, `exit_code=-1`，`error_msg` 中包含 ratio 和 roll 值便于调试

```cpp
int mock_fail_ratio = MprpcApplication::GetConfig().LoadInt("mock_fail_ratio", 0, 0, 100);
if (mock_fail_ratio > 0) {
    thread_local std::mt19937 rng(std::random_device{}());
    int roll = std::uniform_int_distribution<int>(0, 99)(rng);
    mock_success = (roll >= mock_fail_ratio);
}
```

3 个 Worker 配置文件均添加 `mock_fail_ratio=0`（默认不注入故障）。

### Step 3: ResultCollector 重构

**文件**：`video_platform/src/result_collector/result_collector.cpp`

这是阶段 5 改动量最大的文件，涉及 3 个核心变更。

#### 3a. attempt_id 幂等校验

新增工具函数 `parseRetryFromAttempt`，从 `{shard_id}_attempt_{N}` 格式的字符串中解析重试次数。

在 `ReportShardResult` 的步骤 2，shard 已存在时比较新旧 attempt：
- 若 `incoming_retry < stored_retry`：这是旧 attempt 的过期结果 → 拒绝（`accepted=false`）
- 若 `incoming_retry >= stored_retry`：接受，继续处理

这个校验防止了以下场景：
```
时间 →
AssignShard(retry=0) → Worker_A 开始执行 attempt_0
                      → Worker_A 网络延迟，ReportShardResult 未到达
RescheduleShard → retry=1 → AssignShard(retry=1) → Worker_B 开始执行 attempt_1
                      → Worker_A 的 attempt_0 结果此刻才到达 ← 被 attempt_id 校验拒绝！
```

#### 3b. FAILED → RescheduleShard 重试链路

当 `request->is_success() == false` 时（Worker 执行失败，非 RPC 失败），新增步骤 5：
```cpp
// RPC 调用 Scheduler.RescheduleShard(shard_id, job_id, "WORKER_FAILED")
// 若 accepted=true → 本地状态改为 SHARD_RETRYING（防 CheckJobDone 过早判 FAILED）
// 若 accepted=false → 已超 max_retry，本地保持 FAILED
```

**为什么 RescheduleShard 成功后要改本地状态为 RETRYING？**
这是因为 `CheckJobDone` 在每次 `ReportShardResult` 结束时调用。如果不改状态，
它会看到 2 个 SUCCESS + 1 个 FAILED + 0 个 in_progress → 判定 JOB_FAILED。
但实际上 Scheduler 已经接受了重试，新的 attempt 马上会被分配和执行。
改为 RETRYING 后 `CheckJobDone` 看到 in_progress=1 → 继续等待。

#### 3c. CheckJobDone 增强

三阶段终态判定：

1. **如果 expected_shard_count 未知**：从 JobService 查询（跨进程 RPC，最多 3 次重试）。
   查询成功后将 shard_count 缓存到本地 JobStore，避免后续重复 RPC。
   这是为避免 ZK 负载均衡到不同 job_service 实例导致"查不到"的问题。

2. **JOB_SUCCESS**：`success_count >= expected_shard_count`

3. **JOB_FAILED**：`in_progress == 0 && failed_count > 0 && success_count + failed_count >= expected_shard_count`
   - 即所有 shard 都在终态（SUCCESS/FAILED/CANCELED），且至少有一个 FAILED

#### 3d. MarkJobTerminal 提取

将原本内联在 `CheckJobDone` 中的"标记终态 + 通知 JobService"逻辑提取为独立方法。
JOB_SUCCESS 和 JOB_FAILED 共用一个实现。

### Step 4: Scheduler 核心重试逻辑

**文件**：`video_platform/src/scheduler_service/scheduler_service.cpp`

#### 4a. RescheduleShard 完整实现

重写阶段 4 的简单占位实现为完整逻辑：

```
输入：shard_id, job_id, reason
  1. 从 ShardStore 获取 shard（不存在 → 拒绝）
  2. retry_count >= max_retry?
     YES → 标记 SHARD_FAILED → CheckAndMarkJobFailed(job_id)
          → response.accepted=false, error="max retry exceeded"
     NO  → retry_count++
          → SHARD_RETRYING → SHARD_WAITING
          → 清除 assigned_worker_id 和 attempt_id
          → response.accepted=true
```

其中 `SHARD_RETRYING` 只是一个短暂过渡状态（立即转为 WAITING），
它的存在价值是让状态机具备可观测性——在日志中可以明确看到重试发生。

#### 4b. NotifyWorkerOffline 实现

WorkerManager 的心跳超时检测线程在标记 Worker OFFLINE 后调用此 RPC。

```
输入：worker_id, reason
  1. ShardStore.ListByWorker(worker_id) → 找到所有 shard
  2. 过滤：只处理 ASSIGNED 或 RUNNING 状态的
  3. 对每个 shard（内联 RescheduleShard 逻辑，避免递归 RPC）：
     - retry_count >= max_retry → SHARD_FAILED → CheckAndMarkJobFailed
     - 否则 → retry_count++ → SHARD_WAITING → rescheduled_count++
  4. 返回 rescheduled_count
```

#### 4c. 启动恢复扫描

在 `SchedulingLoop` 首次进入主循环前，扫描 `ShardStore` 中状态为 `SHARD_ASSIGNED`
或 `SHARD_RUNNING` 的 shard，重置为 `SHARD_WAITING`。不增加 retry_count。

这是 Scheduler 崩溃后重启的恢复措施，防止残留 shard 成为永久的"孤儿"。

#### 4d. CheckAndMarkJobFailed 辅助方法

当 `RescheduleShard` 将 shard 标记为 `SHARD_FAILED` 后调用。
遍历该 job 的所有 shard，若全部在终态且至少有一个 FAILED → 标记 JOB_FAILED。
通过 `NotifyJobServiceStatus` RPC 推送到 JobService。

#### 4e. NotifyJobServiceStatus 辅助方法

提取 Scheduler → JobService 的状态同步逻辑为独立方法。
复用 `UpdateJobStatus` RPC，携带 shard 状态快照。

### Step 5: WorkerManager 集成

**文件**：`video_platform/src/worker_manager/worker_manager.cpp`

在 `HeartbeatTimeoutCheck` 中，`MarkOfflineIfTimeout` 成功后增加：

MprpcChannel sched_channel;

## 测试中发现的 Bug 及修复

### Bug #1: CheckJobDone 过早判定 JOB_SUCCESS

**现象**：`mock_fail_ratio=40` 测试中，shard_0 mock 失败→`RescheduleShard` 接受→重试正在进行，
但 `CheckJobDone` 在 shard_2 上报 SUCCESS 时过早判定 JOB_SUCCESS。
查询显示 Status=SUCCESS 但只有 1 个 shard 真正完成。

**根因**：
```cpp
// 修复前：当 expected_shard_count=0 时，success_count >= 0 始终为 true
if (success_count >= expected_shard_count || in_progress == 0 && failed_count == 0)
    → JOB_SUCCESS  // bug: expected_shard_count=0 时成功数 >= 0 恒为真
```

**修复**：当 `expected_shard_count` 未知时，从 JobService 跨进程查询（`QueryJob` RPC，
最多 3 次重试）。查询成功后缓存到本地 JobStore。若仍然未知，`return false`（defer 判定）。

**为什么用 QueryJob 而不是其他方式？**
- `JobService.QueryJobResponse.job_info.shard_count` 由 Scheduler 切分时通过
  `UpdateJobStatus` RPC 写入 JobService 的 JobStore
- 这是已知的可靠数据源，在 SubmitJob 回复中就包含了

### Bug #2: FAILED 后本地状态未更新导致过早 JOB_FAILED

**现象**：shard mock 失败 → `RescheduleShard` 接受 → 但 `CheckJobDone` 立即判 JOB_FAILED。
因为本地 shard 状态是 FAILED，而重试的结果还没到达。

**根因**：
```cpp
// 修复前：标记本地 FAILED 后调用 RescheduleShard，但本地状态保持 FAILED
shard.status = SHARD_FAILED;  // 本地保持 FAILED
ShardStore::GetInstance().Update(shard_id, shard);
sched_stub.RescheduleShard(...);  // Scheduler 端接受了但本地不知道
// → CheckJobDone 看到 FAILED + 0 in_progress → JOB_FAILED
```

**修复**：`RescheduleShard` 成功后，本地状态改为 `SHARD_RETRYING`：
```cpp
if (rs_resp.accepted()) {
    shard.status = SHARD_RETRYING;  // 告知 CheckJobDone：重试进行中
    ShardStore::GetInstance().Update(shard_id, shard);
}
```

| SchedulingLoop 中间状态推送 | 阶段 4 遗留 | shard 在 ASSIGNED/RUNNING 时 JobService 的 ShardStore 不更新，QueryJob 返回的状态滞后。阶段 5 未解决 |
| NotifyWorkerOffline RPC 重试 | 选择不重试 | RPC 失败时直接打 WARN 跳过。心跳检测每 2s 运行一次，下轮会再次触发 |
| CancelJob → Worker 通知 | ✅ 已实现（见下方 Step 6） | 取消 job 时通过 Scheduler 直连 Worker 发送 CancelShard RPC

## Step 6: CancelJob Worker 通知（阶段 4 遗留补齐）

这是阶段 4 的遗留项 —— `CancelJob` 调用后只标记本地 ShardStore 为 CANCELED，
但没有通知正在执行 shard 的 Worker 取消任务。Worker 的 `MockExecute` 会继续执行直到自然结束，
造成计算资源浪费和状态不一致。

### 为什么不能直接在 JobService 里通知 Worker

核心矛盾：`assigned_worker_id` 只存在于 **Scheduler 进程**的 ShardStore 中。

```
SubmitJob 时 Scheduler 创建 shard，assigned_worker_id 为空
  → ScheduleJobResponse 回传 shard 列表（无 assigned_worker_id）
  → JobService 写入本地 ShardStore（assigned_worker_id = ""）

SchedulingLoop 分配 worker:
  → Scheduler 本地 ShardStore 写入 assigned_worker_id = "worker_001"
  → 但 JobService 的副本永远不会收到这个更新
```

因此 JobService 的 CancelJob 知道要取消哪些 shard，但不知道它们分配给了哪个 Worker。

### 方案：委托 Scheduler 转发取消通知

新增 `Scheduler.CancelJobShards` RPC，调用链路：

```
JobService.CancelJob
  ├─ 标记本地 ShardStore → CANCELED（原有逻辑）
  └─ RPC → Scheduler.CancelJobShards(job_id, reason)
       ├─ 查本地 ShardStore.ListByJob(job_id)
       ├─ 筛选 RUNNING/ASSIGNED 且 assigned_worker_id 非空的 shard
       ├─ RPC → WorkerManager.ListWorkers（获取 ip:port 映射）
       └─ 直连 Worker → Worker.CancelShard（MprpcChannel(ip, port)）
```

### Proto 变更

**文件**：`video_platform/proto/scheduler.proto`

    string reason = 2;
}
message CancelJobShardsResponse {
    int32 error_code     = 1;
    string error_msg      = 2;
    int32 total_shards   = 3;
    int32 notified_count = 4;
    int32 skipped_count  = 5;
}

### Scheduler handler 实现

**文件**：`video_platform/src/scheduler_service/scheduler_service.cpp`

在 `SchedulerServiceImpl` 中新增 `CancelJobShards` 方法，核心逻辑：

1. `ShardStore::ListByJob(job_id)` 查出所有 shard
2. 筛选 `status == RUNNING/ASSIGNED && !assigned_worker_id.empty()` 的 shard
3. `WorkerManager.ListWorkers` RPC 获取所有 Worker 的 ip:port，构建 `worker_id → (ip, port)` 映射
4. 对每个需通知的 shard，`MprpcChannel(ip, port)` 直连 Worker，调用 `CancelShard`
5. 全程 best-effort：任何失败点只记 WARN 日志，不返回错误码

### 设计要点

- **不修改 Scheduler 本地 shard 状态**：标记 CANCELED 由 JobService 负责，Scheduler 侧通过
  `SchedulingLoop` 的后续扫描自然发现（CANCELED shard 不会被当作 WAITING 分配）
- **Worker 端已有完整实现**：`transcode_worker.cpp:157-183` 的 `CancelShard` handler
  设 `cancelled=true`，`MockExecute` 每 1 秒检查该标志，检测到后 `CleanupShard` 退出
- **ListWorkers RPC 失败时跳过通知**：`SchedulingLoop` 每 2 秒重新分配 WAITING shard，
  已标记 CANCELED 的 shard 会被忽略
