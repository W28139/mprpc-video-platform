# 10. 阶段9数据持久化MySQL

## 日期

2026-08-03

## 前置状态

阶段 8 完成代码审查与 Bug 修复。此时 JobStore / ShardStore / WorkerStore 仍是进程内 `unordered_map` 单例：
- 进程重启数据全部丢失，Scheduler 启动恢复只能靠"扫残留状态拼凑"
- 各进程 Store 完全隔离，跨进程数据靠 RPC 携带快照同步（10+ 处"从 RPC 请求构造本地副本"）
- JobService 的 QueryJob 查不到 assigned_worker_id、ResultCollector 判终态要跨进程 QueryJob 查 shard_count（最多重试 3 次）

## 阶段目标（摘自路线图）

1. 设计 3 张核心表：jobs / shards / workers
2. 封装轻量 MySQL 访问层（libmysqlclient）+ 连接池（固定大小、预创建、线程安全借用/归还）
3. Store 层以 MySQL 为唯一数据源，服务重启后数据不丢失、多进程天然共享
4. 删除跨进程同步逻辑（不再需要从 RPC 请求构造本地副本）

### 验收标准

- 杀掉所有服务进程再重启，job 状态和 shard 进度不丢失
- 多个服务进程读写同一 MySQL，数据一致
- 连接池复用，单次 Store 操作延迟 < 2ms

## 关键架构决策

### Q: 为什么选"纯 MySQL 直读直写"而不是路线图字面的"双写内存缓存 + MySQL"？

路线图的"双写 + 读内存缓存"与"删除跨进程同步逻辑"存在内在矛盾：读内存缓存时，进程 B 看不到进程 A 写入 MySQL 的更新，删除同步逻辑后各进程内存缓存会永久陈旧（如 Scheduler 读不到 ResultCollector 写的 job 终态）。

纯 MySQL 方案：MySQL 是唯一数据源，读（SELECT）写（INSERT/UPDATE/DELETE）全部走数据库，一致性由数据库保证——写入后所有进程立刻可见（跨主机部署同样成立，只要连同一个 MySQL 实例）。RPC 框架保留"功能调用"职责（ScheduleJob / RescheduleShard / 心跳 / 通知），卸下"数据复制"职责。

本机 MySQL 单条 PK 查询 <0.2ms，满足 2ms 验收；数据量级小（千级），无需缓存。阶段 15 性能优化时再加缓存。

### Q: MySQL 化后"Get → 修改 → Update"模式为什么必须条件化？

原内存版各进程操作自己的副本，互相不可见，无冲突。MySQL 化后所有进程写同一行——**后写覆盖先写**，旧快照会覆盖其他进程已推进的状态。典型场景：
- Scheduler 超时重扫把 RUNNING shard 重置 WAITING，同时 RC 已写入 SUCCESS → 全量 Update 会把 SUCCESS 覆盖回 WAITING，破坏终态判定
- Scheduler 分配循环把 WAITING→ASSIGNED，同时用户 CancelJob 已标记 CANCELED → 全量 Update 复活已取消的 shard

**修复**：所有状态推进点改用 `UpdateIfStatus(id, {快照前置状态}, record)` 条件更新——SQL 层面 `WHERE id=? AND status IN (...)`，MySQL 单语句原子，条件不满足则不覆盖。这也是原"Get 重读防御快照覆盖"（阶段 4 #S4）的天然替代。

### Q: 为什么删除 UpdateJobStatus / NotifyJobCanceled 两个 RPC？

- `UpdateJobStatus`（Scheduler/RC → JobService 推状态 + shard 快照）：MySQL 化后 JobService 的 QueryJob 直接读共享数据，快照写入反而会污染权威数据（旧快照覆盖 Scheduler 刚写的 assigned_worker_id）
- `NotifyJobCanceled`（JobService → RC 收敛 shard 状态）：CancelJob 直接写 MySQL 标记 CANCELED，RC 的 CheckJobDone / TerminalSweepLoop 读取同一份数据自动收敛

### Q: 跨进程同步逻辑删除后，谁兜底"Scheduler 崩溃恢复"？

三个兜底循环全部保留（数据源从内存变为 MySQL，行为不变）：
- Scheduler 启动恢复扫描：残留 ASSIGNED/RUNNING shard 重置 WAITING（条件更新）
- JobService PendingScanLoop（10s）：PENDING job 重调 ScheduleJob
- ResultCollector TerminalSweepLoop（15s）：非终态 job 重扫判定

新增的简化：RC 的 CheckJobDone 不再需要"跨进程 QueryJob 查 shard_count 重试 3 次"（阶段 5 痛点），直接从 MySQL 读取。

## 表设计

3 张表（`video_platform/sql/schema.sql`，服务启动时自动 `CREATE TABLE IF NOT EXISTS` 幂等建表）：

- **jobs**：路线图 DDL + 补齐 `shard_duration_sec`（JobRecord 有该字段，路线图 DDL 遗漏）
- **shards**：全字段对齐 ShardRecord（`assigned_worker` 列名对齐），5 个索引（PRIMARY + idx_job + idx_worker + idx_status）
- **workers**：统一列名 `current_running_shards` / `max_running_shards`，补 `gpu_count`（预留）

## 实现步骤

### Step 1: MySQL 连接池（`mysql_pool.h/.cpp`）

libmysqlclient C API 封装：

- **固定大小预创建**：启动时创建 `mysql_pool_size`（默认 4）条连接，预创建失败拒绝服务启动（与 ffmpeg 启动检查同策略）
- **借用/归还**：`mutex + condition_variable` 空闲队列，Acquire 阻塞等待（默认 1s 超时返回 nullptr），Release 归还并 notify
- **保活**：借用时 `mysql_ping`，死连接销毁重建
- **CLIENT_FOUND_ROWS**：UPDATE 值未变化时 affected_rows 仍返回匹配行数——否则"全量覆盖更新"会被误判为未命中
- **utf8mb4**：路径等字段可含中文
- **自动建表**：Init 时执行 CREATE TABLE IF NOT EXISTS（与 schema.sql 一致，部署零步骤）
- **转义**：`MysqlConnectionGuard::Escape`（mysql_real_escape_string），input_path 等客户端输入防注入
- **RAII**：`MysqlConnectionGuard` 构造借用、析构归还，提供 Execute / Query / AffectedRows / Errno（1062=duplicate key）/ Escape

### Step 2: Store 改造（`common_store.h/.cpp`）

**接口完全不变**，内部实现从 `unordered_map + shared_mutex` 换成 SQL：

| 原方法 | MySQL 实现 |
|--------|-----------|
| Insert | INSERT，duplicate key(1062) → false |
| Update | UPDATE ... WHERE id（委托 UpdateIfStatus 空条件） |
| Delete | DELETE ... WHERE id，affected_rows 判断 |
| Get | SELECT ... WHERE id LIMIT 1 |
| ListAll / ListByStatus(-1) | SELECT 全表 |
| ListByJob / ListByWorker / ListByStatus | SELECT ... WHERE 条件 |
| InsertOrUpdate | INSERT ... ON DUPLICATE KEY UPDATE（affected==1 → 新插入） |
| UpdateHeartbeat | 单条 UPDATE ... WHERE worker_id |
| MarkOfflineIfTimeout | 单条条件 UPDATE ... WHERE status=ONLINE AND last_heartbeat < 阈值（行级原子，替代锁内检查） |
| **UpdateIfStatus（新增）** | UPDATE ... WHERE id AND status IN (expect...)，空 expect 等价 Update |

行解析：SELECT 显式列清单（常量 kJobColumns 等）+ ParseRow 按列序转换，不依赖表结构顺序。

头文件顶部注释更新：从"进程内单例、跨进程隔离、靠 RPC 构造副本"改为"MySQL 唯一数据源、多进程天然共享"。

### Step 3: 服务接入

4 个有 Store 的服务（job_service / scheduler_service / worker_manager / result_collector）在 `MprpcApplication::Init` 后调用 `MysqlPool::GetInstance().Init()`，失败拒绝启动。transcode_worker / job_client 不调用（不使用 Store，零 MySQL 依赖）。

### Step 4: 清理跨进程同步逻辑

**删除的 RPC**（proto + handler + 全部调用方）：

| RPC | 原调用方 | 删除原因 |
|-----|---------|---------|
| `JobService.UpdateJobStatus` | Scheduler ×2（ScheduleJob 切分完成 / 首次分配 RUNNING）、RC MarkJobTerminal | JobService 直接读 MySQL；旧快照写入会污染权威数据 |
| `ResultCollector.NotifyJobCanceled` | JobService.CancelJob | CancelJob 直接写 MySQL 标记 CANCELED，RC 自动收敛 |

**删除的"从 RPC 请求构造本地副本"**：

| 位置 | 原逻辑 |
|------|--------|
| job_service SubmitJob | 从 ScheduleJob 响应构造 shard 副本 Insert（QueryJob 直接读 MySQL） |
| job_service PendingScanLoop | 同上（InsertOrUpdate） |
| result_collector CheckJobDone | 跨进程 QueryJob 查 shard_count + 缓存副本（阶段 5 的 3 次重试逻辑消失） |
| result_collector ReportShardResult | 本地无 shard 时从请求构造副本（改为查不到即拒绝，数据异常可观测） |
| result_collector MarkJobTerminal | 反向通知 JobService（UpdateJobStatus）+ 通知 Scheduler（CancelJobShards JOB_TERMINAL） |
| scheduler NotifyJobServiceStatus | 方法整体删除 |

**保留的 RPC**（功能调用，非数据复制）：ScheduleJob / RescheduleShard / NotifyWorkerOffline / CancelJobShards（直连 Worker 发 CancelShard）/ RegisterWorker / Heartbeat / ListWorkers / ReportShardResult / ReportShardProgress / AssignShard / CancelShard / QueryShard / SubmitJob / QueryJob / CancelJob。

**条件化改造**（Update → UpdateIfStatus，全部状态推进点）：

| 位置 | 前置状态条件 |
|------|-------------|
| Scheduler 启动恢复扫描 | {ASSIGNED, RUNNING}（防覆盖 RC 已写入的终态） |
| Scheduler 超时重扫 ×4 | {ASSIGNED} / {RUNNING} |
| Scheduler 分配循环 → ASSIGNED | {WAITING} |
| Scheduler job → RUNNING | {SCHEDULING} |
| RescheduleShard 各分支 | 快照前置状态 / {RETRYING} |
| NotifyWorkerOffline ×2 | {ASSIGNED, RUNNING} |
| CancelJobShards → CANCELED | 快照前置状态 |
| CheckAndMarkJobFailed job → FAILED | 快照前置状态 |
| RC ReportShardResult → SUCCESS/FAILED | 快照前置状态 |
| RC → RETRYING ×2 | {FAILED} |
| RC MarkJobTerminal job 终态 | 快照前置状态（配合原有单调性检查） |
| JobService CancelJob job/shard → CANCELED | 快照前置状态；shard 跳过已终态（SUCCESS/FAILED/CANCELED） |
| JobService SubmitJob / PendingScanLoop job → SCHEDULING | 快照前置状态 / {PENDING} |

## 测试验证

### 测试环境

- MySQL 8.0.46 @ 127.0.0.1:3306（专用账号 video_platform，库 video_platform）
- ZooKeeper 3.4.10 @ 127.0.0.1:2181
- 5 个服务进程 + 1 个 Worker（worker_001），executor_mode=ffmpeg
- 测试视频：30s / 120s testsrc（libx264 ultrafast）

### 测试 1：全链路 SUCCESS + 数据落盘

**结果**：✅ 30s 视频 → 2 shard → JOB_SUCCESS（~3 秒完成）

```
┌─ Job: job_1785740972293_000000_2459
│  Status:      SUCCESS (6)
│  Shards (2):
│    ✓ [0] ..._shard_0  status=SUCCESS  worker=worker_001   ← assigned_worker 直接可见！
│    ✓ [1] ..._shard_1  status=SUCCESS  worker=worker_001
```

MySQL 直查确认三表落盘：jobs（status=6, shard_count=2）、shards（status=5, assigned_worker=worker_001, attempt_id 完整）、workers（status=1 ONLINE，心跳持续更新 last_heartbeat）。

**改进点**：QueryJob 现在能显示 `assigned_worker_id`（此前该数据只在 Scheduler 进程，JobService 永远查不到）。

### 测试 2：全部服务重启，数据不丢失（验收标准 1、2）

**结果**：✅ kill -9 全部 5 个服务 → 重启 → QueryJob 旧 job 状态、shard 进度、assigned_worker 完整保留。

### 测试 3：执行中杀 Scheduler，重启后继续调度

**结果**：✅ 120s 视频（8 shard）执行中 `kill -9 scheduler_service` → 已分配的 2 个 shard 完成，剩余 6 个停在 WAITING → 重启 Scheduler → SchedulingLoop 从 MySQL 扫到 WAITING shard 继续分配 → 最终 8/8 SUCCESS。

### 测试 4：同时杀 Scheduler + Worker（完整故障恢复）

**结果**：✅ 任务执行中 `kill -9` 两个进程 → 重启后残留 shard 从 MySQL 恢复重新分配 → 8/8 SUCCESS。

### 测试 5：Scheduler 不可用时提交（PendingScanLoop 兜底）

**结果**：✅ Scheduler 停机时提交 → JobService 重试 3 次失败 → job 排队 PENDING → Scheduler 重启后 10s 内 PendingScanLoop 自动重调 ScheduleJob → 8 shard 创建 → SUCCESS。

### 测试 6：Store 操作延迟（验收标准 3）

**结果**：✅ 临时 C++ 打点程序（300 次循环，复用连接池）：

```
Insert:          avg=0.186 ms   max=12.4 ms
UpdateIfStatus:  avg=0.166 ms   max=0.5 ms
Get:             avg=0.168 ms   max=0.5 ms
ListAll:         0.173 ms
ShardUpdate:     0.621 ms
ShardListBySt:   0.253 ms
```

平均延迟 ~0.2ms，远低于 2ms 验收线。

## 测试中发现的问题

### 偶发 15ms 写入峰值（环境特性，非代码问题）

`Insert` 偶发 12-16ms 峰值（Get/Update 无）。排查：`SHOW PROFILES` 显示 mysql CLI 直连时所有 DML 也 11-20ms，而 C++ 连接池 300 次中绝大多数 <0.2ms。根因：WSL2 虚拟磁盘的 `fsync` 延迟不稳定（InnoDB `innodb_flush_log_at_trx_commit=1` 每次提交落盘），偶发命中慢 fsync 即 15ms 左右。系统调度/心跳间隔为秒级，完全不受影响。已知问题记录，阶段 15 性能优化时可评估。
