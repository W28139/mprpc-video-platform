## 一、正常负载下的重复转码（最严重）

### #1 30s ASSIGNED 超时重扫误伤正常转码 🔴

**涉及文件**：`scheduler_service.cpp:921-983`（SchedulingLoop 超时重扫）、`:1204`（唯一 ASSIGNED 写入点）、`transcode_worker.cpp:155-156`（attempt_id 生成）、`result_collector.cpp:184-187`（stale 检查只比 retry 数值）

#### 现象一：Scheduler 侧 shard 分配后永远停在 SHARD_ASSIGNED，updated_at 冻结在分配时刻

1. **Scheduler 从不写 RUNNING**：grep 证实全文件唯一的 ASSIGNED 状态写入是 `:1204`（AssignShard 成功回调），**没有任何路径写 SHARD_RUNNING**（其余行都是 ListByStatus 读取/比较）。原因是 Worker 执行期间的进度/结果上报**只发给 ResultCollector**（transcode_worker.cpp 中只有 `rc_stub`，没有任何 Scheduler 客户端），Scheduler 对「shard 是否真的在跑」没有任何信号来源。
2. 因此 RUNNING 5 分钟超时分支（`:985` 起）永远扫不到任何 shard，是**死代码**；真正生效的只有 ASSIGNED 30s 超时分支。

#### 现象二：30s 重扫的动作（SchedulingLoop 每 2s 一轮，`:926` `metrics_round % 15 == 0` → 每 30s 触发一次）

- **命中条件**：`now - updated_at > 30s`，即「分配后 30s 内仍停在 ASSIGNED」；
- **对命中 shard**（job 非终态时 `:949` 的终态守卫不命中）：**无条件置 WAITING + 清空 assigned_worker_id / attempt_id**（`:973-977`），**不通知原 Worker CancelShard、不递增 retry_count**，2s 后由下一轮扫描重新分配。

#### 时序（T0 分配，单 shard 转码耗时 > 30s 即必现）

```
T0      Scheduler AssignShard → shard=ASSIGNED，updated_at=T0，retry_count=N（未递增）
        Worker 生成 attempt_id = {shard_id}_attempt_{N}（transcode_worker.cpp:155-156）
T0+30s  重扫命中（updated_at 冻结在 T0，shard 仍在正常转码中）
        → 置 WAITING + 清 assigned_worker_id/attempt_id；不 Cancel 原 Worker、retry_count 不变
T0+32s  调度循环扫到 WAITING → AssignShard 给另一台 Worker
        原 Worker 的 running_shards_ 已有该 shard_id → 拒绝
        （transcode_worker.cpp:196-206 "already running, rejecting"）
        → 新 Worker 以相同 retry_count=N 生成完全相同的 attempt_id = {shard_id}_attempt_{N}
```

结果：**两台 Worker 以完全相同的 attempt_id 并发转码同一 shard**，且原 Worker 从未收到取消通知，ffmpeg 会一直跑到出结果。

#### 后果：双份转码 + 结果上报错乱 + 重试预算双倍消耗

1. **双份转码、双倍资源**：原 Worker 的 ffmpeg 不被取消、跑完整轮；新 Worker 从 0 再转一遍。两 Worker 的 output_path 命名相同（同一 shard_id + attempt），**后完成者覆盖先完成者的产物文件**。
2. **结果上报错乱**：RC 的 stale 检查（`result_collector.cpp:184-187`）**只比较 retry 数值大小**（`incoming < stored` 才拒），**同号 attempt 完全放行**；且 RescheduleShard 成功后 RC 本地只改状态为 RETRYING、**不推进 attempt_id**（`:301-303`）——同号的后到结果会被当作合法新上报处理：
   - **两台都 SUCCESS**：先到者被接受，后到者被「已 SUCCESS」幂等（`:200`）放行，无害但白跑一轮；
   - **一成一败**：FAILED 先到 → 置 FAILED → RescheduleShard 把 Scheduler 侧 retry 推进到 N+1 并重新分配 → 后到的同号 SUCCESS 不被 stale 拒绝，把 RETRYING **覆盖回 SUCCESS** → RC 判定成功、Scheduler 侧却已推进到 N+1 继续第三次分配，两边状态分叉，成功产物被丢弃、白白再转一遍；
   - **两台都 FAILED**：第二次 FAILED 在 RETRYING 状态下不被 3.5 幂等（`:214`，仅拦「FAILED 且同 attempt」）拦截 → 再次触发 RescheduleShard → **retry_count 双倍消耗**，max_retry=3 下实际只执行 1-2 次就提前 JOB_FAILED。
3. **死代码隐患**：RUNNING 5 分钟超时分支永远不会触发，「转码时间过长」这类本应由它兜底的场景全部落入 30s 分支，被误判为「卡死」重扫。

#### 修复建议

① 首选：Worker 执行期间向 Scheduler 刷新 `updated_at`（心跳携带执行中 shard 列表，或进度上报同步一份给 Scheduler），让「正常执行中」与「真卡死」可区分；② 重扫命中时递增 retry_count 并通知原 Worker CancelShard，使两次执行的 attempt_id 不同、RC 的 attempt 检查能区分新旧；③ 至少把 30s 阈值与真实执行时长对齐（shard 默认 15s（scheduler.conf）/ 20s（代码 fallback），`-preset fast` 重编码在慢机器/双 Worker 并发下转码耗时普遍可超 30s）。

### #2 ScheduleJob 幂等早退的 check-then-act 竞态 🔴

**涉及文件**：`scheduler_service.cpp:104`（`existing_shards.empty()` 检查）、`:160`（ffprobe 探测）

#### 现象

fix #14 的幂等早退「已有 shard 直接返回旧计划」与「ffprobe + 建 shard」之间无锁无原子化。SubmitJob 的内联重试与新增的 PendingScanLoop（每 10s 扫描 PENDING job）可对**同一 job** 并发调用 ScheduleJob，两个请求都看到空 shard 集。

#### 后果

两套不同分片计划交错落库：一个请求探测失败走 fallback 60s→4 片，另一个成功得真实 120s→8 片，`ShardStore::Insert` 是 try_emplace（同 shard_id 静默丢弃、返回值未检查）→ 4 片版的 0-3 与 8 片版的 4-7 混合 → shard 集合与 `shard_count` 不一致 → 视频片段缺失/重复，Merge 产物损坏或 job 卡死非终态。

#### 修复建议

Scheduler 侧对 ScheduleJob 加 per-job 互斥（或把「检查+探测+建 shard」整体放入 JobStore 写锁），幂等早退与创建路径共享同一把锁。

### #3 fix #8 幂等检查被 RETRYING 状态绕过，重试预算双倍消耗 🔴

**涉及文件**：`result_collector.cpp:214`（幂等检查）、`:301/:313`（两条分支都置 RETRYING）、`scheduler_service.cpp:399`（retry_count++）

#### 现象

fix #8 的幂等检查只拦截 `status==SHARD_FAILED && 同 attempt` 的重复上报；但步骤 5 的两条分支（RescheduleShard 成功 / 3 次全失败）都把状态改为 **SHARD_RETRYING**。重复 FAILED 上报到达时状态已是 RETRYING，检查被绕过。

#### 后果

Worker 首次 FAILED 上报被 RC 处理后响应丢失（worker 默认 5s 超时 < RC 处理最长约 18.5s——RescheduleShard 重试 3×5s+退避）→ 心跳重试队列重发同一 attempt_0 → 3.5 检查放行 → 再次触发 RescheduleShard → retry_count 无条件再 +1 → **max_retry=3 下 2 次真实失败即永久 SHARD_FAILED、job 错误 FAILED**。fix #8 与 fix #5 两个新修复互相抵消，FAILED 状态存活时间远短于重试间隔，检查在正常快路径下几乎拦不住任何重复。

#### 修复建议

幂等判据改为「attempt_id 与已处理 attempt 的并集」：在 ShardRecord 上记录已处理的 attempt 集合（或至少记录最近处理 attempt 的 is_success），重复 FAILED/SUCCESS 一律跳过步骤 4/5；Scheduler 的 RescheduleShard 同样按 attempt 幂等。

### #4 RescheduleShard 缺终态守卫，已取消 shard 被复活 🔴

**涉及文件**：`scheduler_service.cpp:398`（RescheduleShard）、`:455/:950/:1109`（其余三处均有守卫）

#### 现象

本轮给 NotifyWorkerOffline、ASSIGNED 超时、RUNNING 超时、分配循环四处 shard 状态变更点都加了「job 终态 → CANCELED」守卫，**唯独 RescheduleShard 漏了**：它把任意状态的 shard（含 CANCELED）覆盖为 WAITING + retry_count++，无任何终态/状态校验。

#### 后果

用户 CancelJob → CancelJobShards 把 shard 标 CANCELED（注意：不修改 Scheduler 侧 job 状态，job 仍 RUNNING）→ 取消窗口内 worker 的 FAILED 上报到达 RC → RescheduleShard 把 CANCELED shard 复活为 WAITING → 分配循环的终态检查查 job 状态（RUNNING 非终态）不命中 → **已取消 job 的 shard 被重新分配并真实转码**；RC 侧该 shard 同时被置 RETRYING，CheckJobDone 永不终态。proto 状态机注释明确 CANCELED 是终态，CANCELED→WAITING 是终态回退。

#### 修复建议

RescheduleShard 入口加与其余三处相同的终态/终态 shard 守卫；或把守卫下沉到 `ShardStore::Update` 的唯一入口（见「清理建议」Q1）。

### #5 NotifyWorkerOffline 重试不复查存活且非幂等 🔴

**涉及文件**：`worker_manager.cpp:245`（pending_notify 重试）、`transcode_worker.cpp:1206`（worker_id 来自配置）

#### 现象

fix #11 的失败重试集合：重试循环只重发 RPC，**不复查 WorkerStore 中该 worker 当前是否已恢复 ONLINE**；Scheduler 端 NotifyWorkerOffline 无存活校验，收到通知即重置该 worker 的 ASSIGNED/RUNNING shard。worker_id 来自配置文件，跨重启复用同一 ID。

#### 后果

触发①（worker 复活）：网络分区 20s 被标 OFFLINE → 通知失败入集合 → worker 心跳恢复（UpdateHeartbeat 置回 ONLINE）→ 重试成功 → Scheduler 把**存活 worker** 正在执行的 shard 重置 WAITING 重新分配 → 双份转码。触发②（响应丢失）：首次通知成功但响应丢失 → 重试对已被重新分配的 shard 再次 retry_count++ + 置 WAITING → retry 预算双倍消耗、attempt 顺序混乱触发 RC 拒绝。

#### 修复建议

重试前检查 worker 当前状态，已 ONLINE 则从集合移除；Scheduler 的 NotifyWorkerOffline 对「shard 的 assigned_worker_id 已变更/attempt 已推进」的 shard 跳过；重试加去重与上限。

### #6 已完成 job 的终态保护单点失败 🔴

**涉及文件**：`result_collector.cpp:649`（CancelJobShards 通知）、`scheduler_service.cpp`（job 状态写入点 grep：仅 PENDING/SPLITTING/SCHEDULING/RUNNING/FAILED）

#### 现象

Scheduler 侧 job 状态**永远不会被置为 SUCCESS**——防重复转码的终态检查（#4 的守卫们）100% 依赖 RC 单次 best-effort 的 `CancelJobShards(JOB_TERMINAL)`，该 RPC 失败只打 WARN 无重试。注释声称的兜底「Scheduler 启动恢复扫描」是死代码（进程内 Store 启动时为空）。

#### 后果

job 全部 shard SUCCESS → RC 的 CancelJobShards RPC 网络失败 → Scheduler 侧 job 仍 RUNNING、残留 ASSIGNED shard → 随后 worker 死亡（NotifyWorkerOffline 终态检查不命中）或 30s 超时重扫 → shard 重置 WAITING 重新分配 → **已完成 job 的 shard 被重复转码**——正是本轮修复想消灭的 Bug #2/#3，在单点 RPC 失败窗口内原样复现。

#### 修复建议

终态通知带重试（复用 result_collector 已有的 3 次退避模式）；或 Scheduler 侧把 job 置 SUCCESS（由 RC 通过 UpdateJobStatus 类 RPC 同步），让终态检查不依赖「恰好成功」的取消通知。

## 二、状态机 / 终态问题

### #7 PendingScanLoop 无条件覆写，终态可被回退 🟠

**涉及文件**：`job_service.cpp:511`（`refreshed.status = JOB_SCHEDULING` 直接 Update）、`:388-401`（UpdateJobStatus 的单调性保护）

#### 现象

PendingScanLoop 用 `JobStore::Update` 直接覆写状态为 JOB_SCHEDULING，完全绕过 UpdateJobStatus 的单调性保护（`new_status > job.status` 才更新）。

#### 后果

变体①（响应丢失）：Scheduler 已切分执行、RC 完成并 UpdateJobStatus(SUCCESS=6) 后，扫描把 SUCCESS 覆写为 SCHEDULING(3) → job 永久停在 SCHEDULING（RC 的 TerminalSweepLoop 只扫自己 Store 的非终态 job，不会重推 SUCCESS）。变体②（取消竞争）：用户 CancelJob 置 CANCELED(8) 与扫描竞争 → **已取消的任务被复活为 SCHEDULING 并继续执行完成**。均为终态回退，与单调性设计的初衷相悖。

#### 修复建议

PendingScanLoop 更新前重读状态，仅当仍为 PENDING 时才置 SCHEDULING（读-改-写在锁内或先 check 再 Update）。

### #8 确定性拒绝也置 RETRYING，RC 与 Scheduler 终态永久分叉 🟠

**涉及文件**：`result_collector.cpp:305-316`、`scheduler_service.cpp:378-395`（max_retry 拒绝路径）

#### 现象

fix #5 让 RescheduleShard 3 次重试全失败时无条件标记 RETRYING，不区分「网络失败」与「确定性拒绝」——max_retry 耗尽时 Scheduler 返回 accepted=false 且**已把 shard 置 FAILED + CheckAndMarkJobFailed 通知 JobService**，RC 仍改 RETRYING。

#### 后果

RC 的 CheckJobDone 把 RETRYING 计为 in_progress → RC 侧 job 永不 FAILED；TerminalSweepLoop 预筛排除 RETRYING 也解决不了（注释声称的兜底「RUNNING 超时重扫」只扫 ASSIGNED/RUNNING，FAILED 不会被重扫）→ RC 与 Scheduler/JobService 的终态永久分叉，每 15s 空扫一次直至进程退出。

#### 修复建议

区分拒绝与网络失败：`accepted=false` 时保持 FAILED（尊重 Scheduler 的终态判定），仅网络失败（ctrl.Failed）才置 RETRYING 等待重扫兜底。

### #9 CancelJob 不通知 ResultCollector，已取消 job 永不收敛 🟠

**涉及文件**：`job_service.cpp:286`（CancelJob）、`transcode_worker.cpp:565-573`（取消后无上报）

#### 现象

CancelJob 只更新 JobService 本地状态 + 通知 Scheduler.CancelJobShards，从不通知 RC；worker 收到 CancelShard 后 CleanupShard 直接返回、不上报任何结果。

#### 后果

执行中的 shard 此前上报过一次失败（RC 有副本）后被取消 → worker 取消后无上报 → RC 侧 shard 永久停在 RETRYING → CheckJobDone 永不终态；新增的 TerminalSweepLoop 预筛要求全 shard 终态也解决不了 → 已取消 job 在 RC 永久卡非终态，每 15s 被扫描直至进程退出。

#### 修复建议

CancelJob 同步通知 RC（或 worker 取消时上报「cancelled」结果让 RC 标记 CANCELED）。

### #10 MergingJobs 集合只增不删，merge 失败永不重试 🟠

**涉及文件**：`result_collector.cpp:511`（insert 先于 Merge）、`:567-571`（失败只 WARN）、全文件无 erase

#### 现象

fix #7 的「merge-once」标志在 Merge 执行前就 insert，merge 失败只打 WARN；集合无任何 erase 路径。TerminalSweepLoop 跳过已终态 job，重复上报路径也 goto skip_merge。

#### 后果

merge 首次执行因 ffmpeg 异常/磁盘满失败 → job_id 永久留在集合 → 后续所有 MarkJobTerminal 全部跳过 → `{job_id}_merged.mp4` **永久缺失**、中间 shard 文件也不清理（清理在成功分支内），job 显示 SUCCESS 但成品视频不存在，无任何恢复路径；集合只增不删，长跑进程内存无限增长。

#### 修复建议

merge 成功后再置位（或失败时从集合移除）；「正在 merge」与「已 merge 完成」分开表示；由 TerminalSweepLoop 对「全 shard 终态但产物缺失」的 job 重试 merge。

## 三、并发 / IO 问题

### #11 Merge filelist 固定名竞态，产物串片 🟠

**涉及文件**：`result_collector.cpp:503-512`（锁作用域）、`:550`（Merge 在锁外）、`ffmpeg_executor.cpp:684`（固定名 filelist.txt）

#### 现象

fix #7 的互斥锁只覆盖「检查+insert」块，**Merge 调用在锁外**（锁 512 行提前释放）；不同 job_id 的并发 MarkJobTerminal（RPC work 线程 rpcserverwork_threads=2 + TerminalSweepLoop 线程）都能通过检查。RC 的 JobStore 从不写入 `job.output_path`（JobRecord 创建时未设置）→ output_dir 必然回退到各 Worker 共享的 `ffmpeg_work_dir`；`FfmpegExecutor::Merge` 仍写固定名 `filelist.txt`（:543-545 注释声称的 job_id 唯一名**未实现**，ffmpeg_executor.cpp:662-665 自己承认此问题）。

#### 后果

两个 job 同时到达 JOB_SUCCESS → 并发 Merge → 交错 `fopen("/tmp/transcode_worker/filelist.txt","w")` → concat 读到对方 job 的 file 条目 → 合并产物串片/损坏，终态仍为 SUCCESS（merge 失败只打 WARN）。

#### 修复建议

把整个「检查+insert+Merge+清理」放入锁内，或 Merge 内部改用含 job_id 的唯一 filelist 名。

### #12 Channel 回调提前 return 吞掉 EPOLLOUT，连接悬挂 🟠

**涉及文件**：`wevix_muduo/src/Channel.cpp:94-97`、`Connection.cpp:242-249`（`if (!channel_->isWriting())`）

#### 现象

UAF 修复的「回调后立即 return」在 **ET 模式**（`Channel.cpp:29 events_ |= EPOLLET`）下吞掉同批次 EPOLLOUT：EPOLLIN|EPOLLOUT 同批时 readCallback 先执行并 return，writeCallback 被跳过。注释声称「sendInLoop 的 EPOLL_CTL_MOD 保证 EPOLLOUT 重新触发」不成立——sendInLoop 仅在 `!isWriting()` 时才 enableWriting，已有 pending 输出时**连 MOD 都不会发生**，ET 下事件已被消费且无状态迁移可再触发。

#### 后果

连接有未发完的大响应（部分写出、EPOLLOUT 已注册）时客户端又发来请求 → 同批 IN|OUT → read 处理请求后 return → outputBuffer 排队数据**永久卡死**，请求-响应协议下对端在等响应不再发数据 → 连接悬挂直到 RPC 超时。64KB 大报文（正是此前触发 UAF 的场景）在真实网络（16-64KB 发送缓冲）下必现，属本提交引入的回归；loopback 压测发送缓冲大不触发。

#### 修复建议

保持 return 防护不变，但交换分支顺序（先 writeCallback 再 readCallback）；或按 muduo 方案用 tie()/weak_ptr 提升保证 handleEvent 期间对象存活，恢复同批全量处理。

### #13 Probe() 无超时无 cancel，ffprobe 挂死瘫痪 Scheduler 🟠

**涉及文件**：`ffmpeg_executor.cpp:420-434`（Probe 裸阻塞 read）、`scheduler_service.cpp:160-165`（ScheduleJob 内同步调用）

#### 现象

Probe() 重写为 fork+execvp 后，read() 循环是无限阻塞且无 poll 超时/无 cancel/无看门狗——同 diff 的 ExecuteCommand 有 1s poll + 1 小时看门狗，Probe 什么都没有。

#### 后果

输入文件损坏/慢挂载点导致 ffprobe 挂起 → ScheduleJob 在 work 线程（scheduler.conf `rpcserverwork_threads=2`）内同步调 Probe 永久阻塞 → 2 个并发 ScheduleJob 即占满线程池 → RescheduleShard/CancelJobShards 全部排队，平台实质瘫痪且无任何超时兜底。

#### 修复建议

Probe 复用 ExecuteCommand 的 poll+超时机制（给 ExecuteCommand 增加 stdout 捕获参数），或至少加 read 超时 + kill + waitpid 兜底。

### #14 RetryPendingReports：无限入队 + 阻塞心跳线程 🟠

**涉及文件**：`transcode_worker.cpp:842-856`（重新入队）、`:1122`（心跳线程内同步执行）

#### 现象

fix #6 的待重试队列对任何非成功结果（ctrl 失败或 accepted=false）都无差别重新入队，PendingReport 无重试计数/过期字段；且该函数在心跳线程内串行同步执行，每条 RPC 未设 SetTimeoutMs（走框架默认 5000ms）。

#### 后果

① stale-attempt 拒绝是确定性的（shard 已被重调度到更高 attempt 后旧 attempt 补报永远 accepted=false）→ 条目以 3s 间隔无限重试 + WARN 刷屏直到进程退出；② RC 半开时 N 条 pending 每条阻塞 5s → 心跳循环停摆 ≥20s → WM 判 worker OFFLINE → 正在真实转码的 shard 被重调度 → 双份转码（修复 #6 把重试挂在了唯一心跳发送者上且无时间预算）。

#### 修复建议

accepted=false（确定性拒绝）直接丢弃条目；重试移出心跳线程或带上限/退避；设置 RPC 超时。

### #15 CPU 指标改用 cutime/cstime，转码中恒为 ~0 🟠

**涉及文件**：`transcode_worker.cpp:888-913`（/proc/self/stat 解析）、`:178`（过载门）、`scheduler_service.cpp:1141`（评分公式）

#### 现象

fix #15 改用 `/proc/self/stat` 的 utime+stime+cutime+cstime，但 **cutime/cstime 只统计已被 waitpid 收割的已终止子进程**——运行中的 ffmpeg 子进程不被计入，worker 自身 utime/stime 只是 poll/read/RPC/日志开销。

#### 后果

转码进行中心跳上报 `cpu_usage≈0`（子进程结束后才出现滞后尖峰）→ Worker 的过载门（`current_cpu>90` reject）与 Scheduler 加权评分（`-cpu*0.5`）同时失效 → 忙 Worker 被当空闲继续堆 shard，机器饱和、转码速度骤降——阶段 7 资源感知调度的核心指标被本修复抽空。

#### 修复建议

改读 `getrusage(RUSAGE_CHILDREN)` 的当前值（含未收割子进程），或按子进程集合（`/proc` 下所有后代）聚合 CPU；至少在心跳中携带「正在执行 shard 数」作为过载门的主判据。

## 四、次要问题（未计入 15 条上限）

### #16 ExecuteCommand 1 小时看门狗对持续输出的进程失效

**涉及文件**：`ffmpeg_executor.cpp:187-207`

`total_elapsed_ms` 只在 poll 超时（ret==0）分支累加，数据可读分支不累加；ffmpeg `-progress pipe:1` 每 ~0.5s 输出一行，poll 几乎总是立即返回 → elapsed 几乎不增长 → 超过 1 小时的转码（或持续吐输出的病态进程）永远不会被 `kMaxExecMs` SIGKILL。头注释宣称的「总执行时长上限 1 小时」未兑现（对静默挂死仍有效）。

**修复**：改用 `steady_clock` 实际耗时或每轮循环都累加。

### #17 Scheduler 侧 4 处重复的「job 终态检查」块（清理）

`NotifyWorkerOffline`/ASSIGNED 超时/RUNNING 超时/分配循环 4 处各贴一份 ~15 行的 job_terminal 判断 + 置 CANCELED 块，且已发生漂移（WAITING 分支漏了 `assigned_worker_id.clear()/attempt_id.clear()`）。提取 `IsJobTerminal(status)` + `MarkShardCanceledIfJobTerminal()` helper 统一维护——本次 #4（RescheduleShard 漏守卫）正是这类拷贝漏贴的实例。

### #18 字段拷贝 3-4 处散落（清理）

ShardInfo↔ShardRecord 14-15 字段手写拷贝在 job_service 3 处、scheduler 3 处；PendingReport 入队 2 处；ReportShardResult 请求拼装 4 处。历史上 max_retry/target_resolution 丢字段 bug（#18/#15）正是这类拷贝漏字段的实例。提取 `FromShardInfo()` 转换函数与 `QueuePendingReport()` 统一收敛。
