# 6. 阶段6接入FFmpeg执行器

## 日期

2026-07-31

## 前置状态

阶段 5（commit `7be000c`）已完成失败重试和故障恢复。系统具备 mock 随机失败注入、RescheduleShard 重试链路、attempt_id 幂等校验、Worker 心跳超时恢复、Scheduler 启动恢复等完整容错能力。Worker 执行环节仍为 `MockExecute`（sleep 模拟），需要替换为真实 ffmpeg 命令。

## 阶段 6 补充修订（同日）

后续测试中发现并修复了以下问题：

1. **切片不精确**：原 `Slice()` 使用 `-c copy` 流复制，在非关键帧处无法精密切割。改为 `libx264 -preset ultrafast` 重编码切片
2. **切片+转码两步合并**：`FfmpegExecute` 去掉独立 Slice 步骤，`-ss`/`-t` 直接传给 `Transcode()`，一 pass 完成，更快且精确
3. **Scheduler 自动探测时长**：`ScheduleJob` 调用 `FfmpegExecutor::Probe()` 获取真实视频时长，不再依赖 `mock_job_duration_sec`
4. **配置项重命名**：清理 mock 命名——`mock_job_duration_sec` → `job_duration_fallback_sec`，`mock_shard_duration_sec` → `shard_duration_sec`。Worker 配置删除 `mock_execution_time_ms` / `mock_fail_ratio`，默认 `executor_mode=ffmpeg`
5. **多进程残留问题**：多次启停导致多组服务实例并存、ZK 节点冲突，表现为任务被分发给旧二进制

## 阶段目标

将 TranscodeWorker 的执行器从 sleep 模拟替换为真实的 ffmpeg/ffprobe 命令调用，让 Worker 能对真实视频文件执行切片、转码等操作（摘自路线图）。

8 项开发内容：

| # | 内容 | 对应实现 |
|---|------|----------|
| 1 | 实现 `FfmpegExecutor` | 新增独立类，封装 ffmpeg/ffprobe 命令行 |
| 2 | 视频信息探测 | `Probe()` — 调用 ffprobe 获取时长/分辨率/编码 |
| 3 | 按时间切片 | `Slice()` — ffmpeg -ss -t 流复制切片 |
| 4 | shard 转码 | `Transcode()` — ffmpeg 编码 + 实时进度回调 |
| 5 | 截图 | `Screenshot()` — ffmpeg -vframes 1 截图 |
| 6 | 结果合并 | `Merge()` — ffmpeg concat demuxer 合并 |
| 7 | 捕获 FFmpeg 返回码 | `ExecuteCommand()` 通过 pclose 获取退出码 |
| 8 | 失败时记录 stderr | error_msg 保留最后 512 字节的 stderr 输出 |

3 项验收标准：

- 能提交一个真实 mp4 文件
- 能生成多个 shard 输出
- 某个 shard 转码失败时能重试

> **注意**：第一版不追求完美音视频切片。切片不精确或合并有瑕疵可以接受，重点是分布式任务链路。

## 架构设计

### 核心思路：最小侵入式替换

保持 `WorkerServiceImpl` 的进度上报/结果上报/cancel 检测架构完全不变，只在执行环节替换为 ffmpeg 子进程调用。

```
MockExecute (旧)                     FfmpegExecute (新)
  sleep(1s)          →   ffmpeg 子进程执行，解析 stderr 获取进度
  progress++          →   progress = 解析 ffmpeg time= 输出
  mock random fail    →   ffmpeg 真实返回码判断成功/失败
  其余逻辑不变         其余逻辑（进度上报、结果上报、重试、cancel）完全不变
```

### 配置驱动的执行器切换

`AssignShard` 中根据 `executor_mode` 配置选择执行器：

```
AssignShard
  │
  ├─ executor_mode == "ffmpeg"
  │     └─ std::thread(&WorkerServiceImpl::FfmpegExecute, this, rs)
  │
  └─ executor_mode == "mock"（或其他值）
        └─ std::thread(&WorkerServiceImpl::MockExecute, this, rs, mock_execution_ms)
```

这样设计的好处：
- 不需要重新编译即可在 mock/ffmpeg 模式间切换
- MockExecute 完全保留，阶段 5 的 mock_fail_ratio 测试能力不受影响
- 新增代码与现有代码解耦，风险隔离

### FfmpegExecutor 类设计

全静态方法工具类，天然线程安全（无共享状态，每次调用创建独立子进程）：

```
FfmpegExecutor (video_platform/ffmpeg_executor.h)
│
├── CheckAvailable()          → 检查 ffmpeg/ffprobe 是否在 PATH 中
│
├── Probe(input_path)         → ffprobe 探测视频元信息
│     └─ 返回 VideoInfo（duration_ms, width, height, codec_name, format_name）
│
├── Slice(input, start, dur, output)
│     └─ ffmpeg -ss -t -i -c copy → 时间切片
│
├── Transcode(input, output, resolution, bitrate, progress_cb)
│     └─ ffmpeg -i -s -b:v -c:v libx264 -progress pipe:1 → 转码+实时进度
│
├── Screenshot(input, timestamp_ms, output)
│     └─ ffmpeg -ss -i -vframes 1 → 截图
│
├── Merge(input_paths, output)
│     └─ ffmpeg -f concat -c copy → 视频合并
│
└── [private] ExecuteCommand(cmd, progress_cb)
      └─ popen() → 逐行读取 → ParseProgress() → pclose() 获取退出码
```

### FfmpegExecute 执行流程

```
FfmpegExecute(rs)
  │
  ├─ 1. 创建工作目录：{ffmpeg_work_dir}/{shard_id}/
  │
  ├─ 2. 判断是否需要切片
  │     ├─ 需要（start_ms > 0 或 duration_ms > 0）
  │     │     ├─ FfmpegExecutor::Slice() → 切片文件
  │     │     ├─ 失败 → ReportShardResult(FAILED) → CleanupShard → return
  │     │     └─ 成功 → transcode_input = 切片文件
  │     └─ 不需要 → transcode_input = 原始 input_path
  │
  ├─ 3. 转码（带进度回调）
  │     ├─ progress_cb: 解析 ffmpeg 输出 → rs->progress = pct
  │     ├─ progress_cb: 检测 rs->cancelled
  │     ├─ progress_cb: RPC 上报 ReportShardProgress
  │     └─ FfmpegExecutor::Transcode() 返回结果
  │
  ├─ 4. cancel 检查
  │     └─ rs->cancelled → CleanupShard → return
  │
  ├─ 5. 上报最终结果（3 次重试，与 MockExecute 相同逻辑）
  │     └─ ReportShardResult(SUCCESS/FAILED)
  │
  └─ 6. CleanupShard
```

### Step 2: 新增 FfmpegExecutor 实现

**文件**：`video_platform/src/transcode_worker/ffmpeg_executor.cpp`（+387 行）

#### 2a. ExecuteCommand — 子进程执行核心

```cpp
FfmpegResult ExecuteCommand(const std::string& cmd, progress_cb)
{
    FILE* pipe = popen(cmd + " 2>&1", "r");   // 合并 stderr 到 stdout
    while (fgets(buf, sizeof(buf), pipe)) {    // 逐行读取
        stderr_tail += line;                   // 保留尾部 512 字节
        if (progress_cb) {
            int pct = ParseProgress(line, 0);  // 解析进度
            progress_cb(pct);
        }
    }
    int status = pclose(pipe);                 // 获取退出码
    result.exit_code = WEXITSTATUS(status);
    if (exit_code != 0) result.error_msg = stderr_tail;
}
```

#### 2b. ParseProgress — 进度解析

支持两种 ffmpeg 输出格式：

- `-progress pipe:1` 模式：`out_time_ms=5120000`（微秒时间戳，首选）
- 普通 stderr 模式：`time=00:00:05.00`（回退方案）

```cpp
// 优先匹配 out_time_ms=<microseconds>
if (const char* pos = strstr(line, "out_time_ms="))
    → 解析微秒值 → 与 total_duration_ms 比较 → 返回 0-100

// 回退匹配 time=HH:MM:SS.ms
if (const char* pos = strstr(line, "time="))
    → sscanf("%d:%d:%lf", &hh, &mm, &ss) → 毫秒 → 返回百分比
```

#### 2c. Probe — ffprobe 视频探测

```bash
ffprobe -v quiet -print_format json -show_format -show_streams -select_streams v:0 <input>
```

手动解析 JSON（不依赖第三方库），提取字段：
- `"duration"` → `duration_ms`
- `"width"` → `width`
- `"height"` → `height`
- `"codec_name"` → `codec_name`
- `"format_name"` → `format_name`

#### 2d. Slice — 视频切片

```bash
ffmpeg -y -ss {start_sec}s -t {duration_sec}s -i "{input}" -c copy -avoid_negative_ts make_zero "{output}"
```

- `-ss` 放在 `-i` 前实现 input seeking（快速 seek）
- `-c copy` 流复制（不重新编码，速度快）
- 切片后验证输出文件存在且大小 > 0

#### 2e. Transcode — 视频转码

```bash
ffmpeg -y -i "{input}" [-s {W}x{H}] [-b:v {bitrate}k] \
       -c:v libx264 -preset fast -c:a aac \
       -progress pipe:1 -nostats "{output}"
```

- `-progress pipe:1`：输出结构化进度到 stdout
- `-nostats`：隐藏默认统计输出
- 编码器：libx264 + aac（通用性好，速度较快）
- `-preset fast`：快速预设
- 进度回调包装：将微秒值换算为 0-100 百分比

#### 2f. Screenshot — 截图

```bash
ffmpeg -y -ss {ts}s -i "{input}" -vframes 1 "{output}"
```

#### 2g. Merge — 视频合并

```bash
# 1. 生成 filelist.txt（concat demuxer 格式）
# 2. ffmpeg -y -f concat -safe 0 -i filelist.txt -c copy "{output}"
# 3. 清理 filelist.txt
```

使用 `-c copy` 流复制，要求所有输入编码参数一致。

## 关键设计决策

### Q: 为什么 FfmpegExecutor 使用全静态方法？

A: 三个原因：
1. FFmpeg 命令行工具本身是无状态的——每次 `popen()` 创建独立进程，不需要跨调用共享状态
2. 天然线程安全——`FfmpegExecute` 在自己的 std::thread 中运行，多个 shard 同时转码时无需同步
3. 调用简单——不需要创建实例、管理生命周期

### Q: 为什么使用 popen() 而不是 fork()+exec()？

A: 第一版优先简洁性。`popen()` 自动处理 shell 解析、管道创建、子进程回收，代码量少很多。
代价是无法在运行中 kill 子进程（不暴露 PID）。cancel 检测在每次进度回调中执行，
但子进程只能自然结束。后续如果 cancel 延迟成为问题，可升级为 fork()+exec()+pipe()。

### Q: 为什么切片用 -c copy 而不是重新编码？

A: `-c copy` 是流复制，不重新编码，速度极快（接近文件复制速度）。代价是切片点必须在
关键帧（IDR 帧）上，可能偏移几秒——第一版接受这个限制。后续如需精确切片，改用 `-c:v libx264`
重新编码即可。

### Q: Worker 如何知道目标分辨率和码率？

A: 当前从 Worker 配置文件读取 `target_resolution` 和 `target_bitrate`。这是简化实现——
理想情况下这些参数应该由用户在 SubmitJob 时指定，随 JobInfo 传递到 ShardInfo 中再下发到 Worker。
这留待阶段 8（压测和文档整理）改进。

### Q: ffprobe JSON 解析为什么不依赖第三方库？

A: 尽量减少外部依赖。本项目的依赖只有 pthread、protobuf、ZooKeeper C 库。
引入 JSON 库（如 nlohmann/json）会增加构建复杂度。ffprobe 的 JSON 结构简单，
只需要提取 5 个字段，手动字符串搜索足够。

## 与阶段 5 的关系

阶段 5 的容错机制为阶段 6 提供了关键保障：

- **失败重试链路**（RescheduleShard）：FFmpeg 失败率远高于 mock，重试机制确保单个 shard 的 ffmpeg 异常不会导致整个 job 失败
- **attempt_id 幂等校验**：Worker 重试后旧 attempt 的延迟结果被拒绝，防止覆盖新 attempt 的状态
- **Worker 心跳超时恢复**：如果 ffmpeg 子进程卡死导致 Worker 不响应，心跳超时机制会自动触发重调度

阶段 6 的代码只负责"执行"，容错完全依赖阶段 5 已建好的基础设施。

### 遗留项 3：popen → fork+exec

**问题**：`popen()` 不暴露子进程 PID，无法在 cancel 时 kill 子进程。`CancelShard` RPC 到达后，ffmpeg 只能自然运行到结束。

**方案**：用 `pipe() + fork() + execl() + fdopen()` 替代 `popen()`，记录子进程 PID，在 `should_cancel` 回调返回 true 时 `kill(pid, SIGTERM)`。

**ExecuteCommand 重写**（`ffmpeg_executor.cpp`）：

```
popen 版本（旧）:
  FILE* pipe = popen(cmd + " 2>&1", "r");
  while (fgets(buf, sizeof(buf), pipe)) { ... }
  pclose(pipe);

fork+exec 版本（新）:
  int pipefd[2];
  pipe(pipefd);
  pid_t pid = fork();

  if (pid == 0) {  // 子进程
      close(pipefd[0]);
      dup2(pipefd[1], STDOUT_FILENO);
      dup2(pipefd[1], STDERR_FILENO);
      close(pipefd[1]);
      execl("/bin/sh", "sh", "-c", cmd.c_str(), nullptr);
      _exit(127);
  }

  // 父进程
  close(pipefd[1]);
  FILE* pipe = fdopen(pipefd[0], "r");
  while (fgets(buf, sizeof(buf), pipe)) {
      // ... 解析进度 ...
      if (should_cancel && should_cancel()) {
          kill(pid, SIGTERM);
          // 优雅等待 5s，超时则 SIGKILL
          for (int i = 0; i < 10; ++i) {
              if (waitpid(pid, &status, WNOHANG) > 0) break;
              std::this_thread::sleep_for(500ms);
          }
          if (waitpid(pid, &status, WNOHANG) == 0) {
              kill(pid, SIGKILL);
              waitpid(pid, &status, 0);
          }
          break;
      }
  }
  fclose(pipe);
  waitpid(pid, &status, 0);
```

**API 变更**：
```cpp
// ExecuteCommand — 新增 should_cancel 参数
static FfmpegResult ExecuteCommand(const std::string& cmd,
    std::function<void(int)> progress_cb = nullptr,
    std::function<bool()> should_cancel = nullptr);  // 新增

// Transcode — 新增 should_cancel 参数，透传给 ExecuteCommand
static FfmpegResult Transcode(..., std::function<bool()> should_cancel = nullptr);
```

**调用方改动**（`transcode_worker.cpp` FfmpegExecute）：
```cpp
auto cancel_cb = [&rs]() -> bool { return rs->cancelled.load(); };
auto transcode_result = FfmpegExecutor::Transcode(
    input_path, output_path, target_resolution, target_bitrate,
    start_ms, duration_ms, progress_cb, cancel_cb);
```

**优雅终止策略**：
1. `SIGTERM` → 等待 500ms × 10 次（共 5s），每次检查子进程是否已退出
2. 5s 后仍未退出 → `SIGKILL` 强制终止
3. 退出码：被信号终止时 `exit_code = -WTERMSIG(status)`（负值），被杀时 `error_msg = "cancelled by user request"`

**技术要点**：
- 子进程 `execl()` 失败时 `_exit(127)`，与 shell 的 "command not found" 退出码一致
- `fdopen(pipefd[0], "r")` 将管道 fd 包装为 FILE*，兼容现有 fgets 逐行读取
- `fclose(pipe)` 同时关闭 fd，无需单独 `close(pipefd[0])`

## 遗留项关键设计决策更新

### Q: 合并为什么放在 ResultCollector 而不是 JobService？

A: ResultCollector 拥有所有 shard 的 output_path 信息（通过 ReportShardResult 收集），是唯一能收集完整输出路径列表的服务。放在这里避免了额外的跨进程数据聚合。Merge 本身是纯本地 ffmpeg 调用，不依赖其他服务。

### Q: 转码参数透传为什么改动这么多文件？

A: ShardInfo 是跨 4 个服务（Scheduler → Worker → ResultCollector → JobService）传递的核心数据结构。每个 RPC 同步点都需要显式设置新字段，否则接收方收到的 proto 字段为空。这是 protobuf 跨进程通信的固有特征——没有"自动透传"，每个序列化点都要手动处理。

### Q: fork+exec 的 SIGTERM 等待为什么是 5 秒？

A: ffmpeg 收到 SIGTERM 后需要写文件尾部（moov atom）、关闭编码器、清理临时文件。5 秒给大多数转码任务足够的清理时间。超时后用 SIGKILL 兜底，确保 cancel 操作最终完成。

### Q: 截图为什么在转码后而不是转码前？

A: 转码后截图的是输出文件（已按目标分辨率/码率处理），更直观反映最终结果。如果截图输入文件（转码前），看到的是原始画质而非用户期望的输出效果。
