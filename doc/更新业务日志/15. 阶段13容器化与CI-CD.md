## 关键架构决策

### Q: 路线图说"每个服务独立 Dockerfile"，为什么用单镜像多阶段？

本项目**一个 CMake 工程编译一次产出全部二进制**（5 服务 + job_client + 测试/压测）。写 5 个独立 Dockerfile 内容 90% 重复且构建 5 次（builder 阶段完全相同）。单 `docker/Dockerfile`（builder + runtime 两阶段）+ compose 按 `command` 区分服务，一次编译、镜像最小化。`--scale` 作用于 service 定义与镜像无关，天然支持。若要拆独立镜像（如分别推送 Docker Hub），builder 阶段的产物 COPY 出来即可，成本极低。

### Q: `docker compose up --scale transcode_worker=3` 为什么能自动得到 3 个唯一 worker？

原实现 `worker_id` 只来自配置（三个 conf 分别是 worker_001/002/003），scale 副本共用同一 conf 会互相覆盖注册。改为 `ResolveWorkerId()` 三源解析：**环境变量 WORKER_ID > 配置 worker_id > hostname**。docker conf 不写 worker_id，各副本的容器 hostname（=容器 ID）天然唯一。本机行为不变（显式配置优先）。

### Q: 为什么必须改两个 CMakeLists？

1. **Qt6 REQUIRED**（`video_platform/CMakeLists.txt:93`）：CI/Docker 镜像不装 Qt6（桌面应用不参与容器化），`find_package(Qt6 REQUIRED)` 会导致整个 cmake configure 失败，连带服务二进制都构建不了。改为 QUIET + `if(Qt6_FOUND)` 包裹 video_gui 目标，本机装 Qt6 时 GUI 照常构建。
2. **`-march=native`**（根 CMakeLists）：Release 默认追加 `-march=native`，编译出的二进制只能在构建机同型号 CPU 上跑。Docker 镜像可能在别的机器构建/运行（如 CI runner 构建 → 服务器运行），必须可移植。新增 `ENABLE_NATIVE_MARCH` 选项（默认 ON 保持本机行为），Dockerfile 和 CI 都传 `-DENABLE_NATIVE_MARCH=OFF`。

### Q: 端口映射策略——为什么 transcode_worker 不映射端口？

`--scale transcode_worker=3` 时若映射 `9004:9004`，compose 直接报端口冲突无法启动。容器间互通走 ZK 服务发现（容器 IP + 容器内端口 9004），不需要宿主映射。仅 9001/9002/9003/9005 + metrics 9091-9094 映射宿主（调试 + Prometheus 抓取）。

### Q: 启动顺序怎么保证（Provider 在 ZK 不可用时直接退出）？

`RpcProvider::Run()` 连 ZK 失败直接返回 false 退出进程（不重试）。compose 用 **healthcheck + `depends_on: condition: service_healthy`**：

- zookeeper：`ZOO_4LW_COMMANDS_WHITELIST: ruok` + bash `/dev/tcp` 探测（debian 镜像必有 bash，不依赖 nc；**ZK 3.8 默认禁用 4lw 命令，必须显式放行**）
- mysql：`mysqladmin ping`（initdb 完成后才算 healthy，天然等待建库建账号）
- rabbitmq：`rabbitmq-diagnostics -q ping`
- redis：可降级组件（阶段 10 语义），不设健康依赖

平台服务再叠加 `restart: unless-stopped` 兜底。Worker 注册时序：compose 依赖拓扑保证 ZK healthy → WM 先启动 → worker 才启动，注册重试窗口 15s+ 覆盖 WM 就绪时间。

### Q: MySQL 初始化怎么做的？

mysql:8.0 镜像环境变量（`MYSQL_DATABASE/MYSQL_USER/MYSQL_PASSWORD`）+ 挂载 `video_platform/sql/schema.sql` 到 `/docker-entrypoint-initdb.d/`（首次启动自动建库建表）。服务启动时还会自动建表（幂等 CREATE TABLE IF NOT EXISTS），双保险。数据持久化到 `mysql-data` 卷。

### Q: 集成测试脚本怎么提交任务（job_client 是交互式的）？

`job_client` 无 submit 子命令，提交靠 stdin 逐行提示（user_id → input_path → output_path → format → resolution → bitrate → priority → shard_duration）。脚本用 `printf` 管道喂 8 行输入，从输出 `  Job ID: <id>` 提取 job_id。提交在 `job_service` 容器内执行（`docker compose exec -T`），ZK 服务发现走容器网络。

## CI 设计（4 jobs，产物复用）

```
build ─┬─ unit-test   （test_buffer / test_threadpool / test_rpc_protocol）
       ├─ integration（compose 全链路：Dockerfile 的唯一真实验证点）
       └─ benchmark   （rpc_echo_server + bench_rpc_stress --direct --keepalive -c 50 -m 200 -s 64）
```

- build 上传 `bin/` artifact，其余 job 下载复用（retention 1 天）
- integration：`docker compose up -d --build` → `scripts/integration_test.sh` → 失败时 `docker compose logs` 转储（调 Bug 的关键信息源）→ 清理 `down -v`
- 集成测试素材：CI runner 上 `ffmpeg -f lavfi -i testsrc` 生成 30s 测试视频（挂载卷直达容器），不依赖任何外部媒体文件

## 实测发现并修复（2026-08-04，本机安装 Docker 后全链路实测）

> 本机此前无 Docker，compose/Dockerfile 的正确性只能靠实测暴露。装上 Docker
> （apt 镜像加速器解决 Docker Hub 超时）后按集成测试推进，**连排 4 个真实缺陷 + 2 个部署问题**：

1. **（构建阻断）Ubuntu 22.04 的 protobuf 3.12 与提交的 generated 代码不兼容**：
   仓库内 `proto/generated/*.pb.h` 由本机 protoc 3.21（24.04）生成，22.04 的
   libprotobuf-dev 3.12 头文件编译报 `RpcResponseHeader ... abstract type`（
   `Message::New()` 纯虚接口差异）。**Dockerfile 基础镜像 + CI runner 全部升到
   ubuntu:24.04**（与开发环境一致），runtime 库包名相应改为 24.04 版
   （`libprotobuf32t64` / `libhiredis1.1.0` / `libzookeeper-mt2` / `libmysqlclient21` /
   `librabbitmq4`）。
2. **（构建阻断）ZooKeeper 3.9.1 的同步 API 被 THREADED 宏包裹**：noble 的
   `libzookeeper-mt-dev` 3.9.1 头文件里 `zoo_create/zoo_exists/...` 仅在 `#ifdef THREADED`
   下可见（开发机手动装的旧版头文件无此限制，本机编译掩盖了问题）。修复：
   `mprpc/include/ZookeeperUtil.h` 在 include zookeeper.h 前加 `#define THREADED`。
3. **（运行时阻断）Provider 注册到 ZK 的地址是 0.0.0.0 死地址**：docker conf
   `rpcserverip=0.0.0.0`（全接口监听），但 ZK 服务发现、Worker 注册上报都直接拿
   `rpcserverip` 值 → 消费者连 `0.0.0.0:9002` 报 errno 111。修复：新增
   `mprpc/include/mprpcutil.h` 的 `GetLocalIp()`（getifaddrs 探测首个非 loopback IPv4），
   `RpcProvider::Run()` 注册地址与 `RunHeartbeatLoop()` 上报地址在 rpcserverip 为
   0.0.0.0/空时自动替换为容器实际 IP（实测注册 `ip=172.18.0.12:9004` ✓）。
4. **（运行时阻断）worker 启动仍走 `LoadRequired("worker_id")` 必填校验**：改造
   `ResolveWorkerId()` 时只改了执行路径（MockExecute/FfmpegExecute），漏了 main 的
   启动校验 → docker conf 不写 worker_id 时启动即 EXIT_FAILURE 崩溃循环。修复：
   main 改用 `ResolveWorkerId()`，hostname 兜底；探测失败（unknown_worker）才拒绝启动。
5. **（部署问题）ZK healthcheck 用 bash /dev/tcp 但 CMD-SHELL 走 sh=dash**：dash
   不支持 /dev/tcp → healthcheck 恒失败。修复：显式 `bash -c '...'`。
6. **（部署问题）宿主端口全被本机手工部署占用**（ZK/MySQL/Redis/MQ + 5 平台服务）：
   docker 部署改用替代宿主端口（21810/23306/63790/56720/19001-19005/19091-19094），
   容器内端口不变，集成测试走 `docker compose exec` 不依赖宿主端口。

> 前 4 项是**本机编译无法发现的真实环境缺陷**——本机依赖都是手工安装/旧版本，
> 掩盖了 protobuf 版本、ZK 头文件、0.0.0.0 注册地址三个兼容性问题。这正是
> CI integration job 存在的意义：push 到 GitHub 后这 4 项修复会被自动复验。

## 使用方法

```bash
# 1. 安装 Docker（WSL2 下二选一）
#    Docker Desktop for Windows（启用 WSL2 集成），或
#    sudo apt install docker.io docker-compose-v2 && sudo usermod -aG docker $USER

# 2. 一键启动全环境（首次构建镜像需几分钟）
docker compose up -d --build

# 3. 检查状态
docker compose ps

# 4. 提交任务（容器内交互式，或本机 GUI/bin/job_client）
docker compose exec job_service sh -c 'printf "%s\n" "1001" "/data/videos/xxx.mp4" "/data/output" "mp4" "720p" "0" "0" "0" | ./bin/job_client -i /app/conf/job_client.conf'

# 5. 扩展 Worker（副本自动获得唯一 worker_id）
docker compose up -d --scale transcode_worker=3

# 6. 日志 / 停止
docker compose logs -f scheduler_service
docker compose down -v   # -v 会删除 MySQL 数据卷
```

- 视频输入：`data/videos/`（容器内 `/data/videos/`）；转码产物：`data/output/`（容器内 `/data/output/`）
- 服务日志：`program_log/`（挂载出容器）；Prometheus 抓 `localhost:19091-19094/metrics`
- **端口映射**：本机已有手工部署占用标准端口，compose 默认用替代宿主端口
  （21810/23306/63790/56720/19001-19005/19091-19094，容器内端口不变）。宿主无
  占用时可改回标准端口（如 `9001:9001`），一行改动。
