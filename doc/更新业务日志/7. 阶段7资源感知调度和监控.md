# 7. 阶段7资源感知调度和监控

## 日期

2026-07-31

## 前置状态

阶段 6（commit `7be000c` + 遗留项完成）已具备完整的 FFmpeg 执行能力：真实转码、fork+exec 子进程管理、cancel 即时生效、参数透传、合并输出、截图集成。调度策略仍为简单贪心（选 `available_slots` 最大的 Worker），Worker 心跳中 CPU/内存使用率硬编码为 0。

## 阶段目标

让调度器不再简单轮询，而是根据 Worker 实时资源状态（CPU 使用率、内存使用率、运行中 shard 数）进行加权评分分配。同时增加优先级队列、Worker 过载保护和 metrics 输出。

6 项开发内容：

| # | 内容 | 对应实现 |
|---|------|----------|
| 1 | Worker 上报真实 CPU/内存/running shard | `CollectCpuUsage()` / `CollectMemUsage()` 采集 /proc 数据，心跳填入真实值 |
| 2 | Scheduler 维护 Worker 资源快照 | `WorkerRecord` 加 cpu_usage/memory_usage；`UpdateHeartbeat` 存储；`ListWorkers` 返回 |
| 3 | 资源匹配策略（加权评分） | `score = available_slots * 10 - cpu_usage * 0.5 - memory_usage * 0.2` |
| 4 | 优先级队列 | waiting shards 按 job.priority 降序 + created_at FIFO 排序 |
| 5 | Worker 过载保护 | `AssignShard` 中检查 running>=max 或 cpu>90% → 拒绝分配 |
| 6 | 输出 metrics | 每 5 轮（10s）打印 `[SchedulerMetrics]` 快照 |

3 项验收标准：

- 高负载 Worker 不再被继续分配任务
- 低负载 Worker 会获得更多 shard
- 可以看到任务队列长度和 Worker 负载分析

## 架构设计

### 核心思路：增强而非重写

阶段 7 不改动任何现有架构，只在现有流程中替换数据源和决策逻辑：

```
阶段 6（旧）                         阶段 7（新）
  心跳 cpu=0, mem=0        →   心跳 cpu=真实采集, mem=真实采集
  WorkerRecord 无负载字段   →   WorkerRecord + cpu_usage + memory_usage
  ListWorkers 不返回负载    →   ListWorkers 返回 cpu_usage/memory_usage
  调度选 max(slots)         →   调度选 max(slots*10 - cpu*0.5 - mem*0.2)
  shard FIFO 无序          →   shard 按 priority 降序
  AssignShard 不检查负载    →   AssignShard 过载拒绝
  无 metrics               →   每 10s 输出 [SchedulerMetrics]
```

### Step 3: Worker 端 CPU/内存采集

**文件**：`video_platform/src/transcode_worker/transcode_worker.cpp`

#### 3a. CollectCpuUsage() — CPU 使用率采集（~35 行）

```cpp
static int CollectCpuUsage()
{
    thread_local uint64_t prev_total = 0, prev_idle = 0;

    // 读 /proc/stat 第一行
    std::ifstream stat("/proc/stat");
    std::string line; std::getline(stat, line);
    // 解析: cpu user nice system idle iowait irq softirq steal
    uint64_t total = user + nice + system + idle + iowait + irq + softirq + steal;
    uint64_t idle_sum = idle + iowait;

    // 两次采样间计算差值百分比
    int usage = 0;
    if (prev_total > 0) {
        uint64_t d_total = total - prev_total;
        uint64_t d_idle  = idle_sum - prev_idle;
        if (d_total > 0) usage = (d_total - d_idle) * 100 / d_total;
    }
    prev_total = total; prev_idle = idle_sum;
    return usage;  // 首次调用返回 0
}
```

**设计要点**：
- `thread_local` 保存上次采样值——心跳线程独立采集，无锁
- `iowait` 计入 idle（等待 IO 不算 CPU 忙碌）
- 首次调用返回 0（需要两个采样点才能算差值）

#### 3b. CollectMemUsage() — 内存使用率采集（~20 行）

```cpp
static int CollectMemUsage()
{
    std::ifstream mem("/proc/meminfo");
    // 解析 MemTotal 和 MemAvailable
    return (mem_total - mem_available) * 100 / mem_total;
}
```

#### 3c. 心跳填入真实数据

### Step 4: 加权评分调度 + 优先级队列

**文件**：`video_platform/src/scheduler_service/scheduler_service.cpp`

#### 4a. 优先级排序（+15 行）

```cpp
// 批量查询 job 优先级并缓存
std::unordered_map<std::string, int32_t> job_priority_cache;
for (const auto& s : waiting_shards) {
    if (!job_priority_cache.count(s.job_id)) {
        auto job = JobStore::GetInstance().Get(s.job_id);
        job_priority_cache[s.job_id] = job.has_value() ? job->priority : 0;
    }
}
// priority 降序，同优先级 FIFO
std::sort(waiting_shards.begin(), waiting_shards.end(),
    [&](const ShardRecord& a, const ShardRecord& b) {
        int pa = job_priority_cache[a.job_id];
        int pb = job_priority_cache[b.job_id];
        if (pa != pb) return pa > pb;
        return a.created_at < b.created_at;
    });
```

#### 4b. 加权评分（替换原贪心 `best_slots`）

```cpp
// 本地槽位追踪：防同一轮对同一 Worker 超额分配
std::unordered_map<std::string, int> round_assigned;

for (auto& shard : waiting_shards) {
    const WorkerInfo* best_worker = nullptr;
    double best_score = -999.0;

    for (const auto& w : lw_resp.workers()) {
        int already   = round_assigned[w.worker_id()];
        int available = w.max_running_shards() - w.current_running_shards() - already;
        if (available <= 0) continue;

        double score = available * 10.0
                     - w.cpu_usage() * 0.5
                     - w.memory_usage() * 0.2;

        if (score > best_score) { best_score = score; best_worker = &w; }
    }

    if (!best_worker) continue;  // 无可用 Worker

    round_assigned[best_worker->worker_id()]++;  // 本地槽位 +1
    // ... AssignShard RPC ...
}
```

**评分公式解读**：
- `available_slots * 10`：空闲槽位权重最高（每空槽 +10 分）
- `cpu_usage * 0.5`：CPU 使用率惩罚（100% CPU → -50 分，约等于 5 个空槽位）
- `memory_usage * 0.2`：内存使用率惩罚（100% 内存 → -20 分，约等于 2 个空槽位）
- 结果：空槽多的 Worker 优先，同槽位下负载低的优先

**`round_assigned` map**：替代原来的 `--best_slots` 变量。因为改为加权评分后不再有单一 `best_slots` 变量，用 map 按 worker_id 追踪每轮已分配数，在计算 `available` 时扣除。

### Step 5: Worker 过载保护

**文件**：`video_platform/src/transcode_worker/transcode_worker.cpp`

在 `AssignShard` 中，接收 shard 前检查自身负载（+20 行）：

```cpp
int current_cpu = CollectCpuUsage();
{
    std::lock_guard<std::mutex> lock(mutex_);
    int running = 0;
    for (const auto& kv : running_shards_) {
        if (!kv.second->cancelled) ++running;
    }
    int max_shards = config.LoadInt("max_running_shards", 2, 1, 1024);
    if (running >= max_shards || current_cpu > 90) {
        response->set_error_code(2);
        response->set_error_msg("worker overloaded");
        response->set_accepted(false);
        done->Run();
        return;
    }
}
```

**设计要点**：
- 双重条件：槽位满 **或** CPU > 90% 均触发拒绝
- 在锁内检查 `running_shards_` 和 cancelled 状态
- 拒绝后 Scheduler 在下一轮会自动分配给其他 Worker（加权评分会自然避开高负载 Worker）

## 关键设计决策

### Q: 为什么 CPU 采集用 thread_local 而不是全局变量？

A: `CollectCpuUsage()` 被两处调用——心跳线程（`RunHeartbeatLoop`）和 IO 线程（`AssignShard` 过载保护）。如果共享全局变量，两次采样间的竞争会导致 CPU 读数异常。`thread_local` 确保每个线程有独立的采样历史，解耦两处的采样时序。

### Q: 为什么评分公式权重是 10 / 0.5 / 0.2？

A: 
- `slots * 10`：1 个空槽 = 10 分。2 槽 Worker 基础分 20，4 槽 Worker 基础分 40
- `cpu * 0.5`：100% CPU 惩罚 50 分，相当于 -5 个空槽。满载的 4 槽 Worker（40-50=-10）低于空闲的 1 槽 Worker（10-0=10）
- `mem * 0.2`：100% 内存惩罚 20 分，相当于 -2 个空槽。内存影响小于 CPU（转码是 CPU 密集型）

这些权重经过设计确保：**空闲槽位是首要因素，CPU 负载是次要调节因素，内存是辅助因素**。

### Q: 为什么 priority 排序需要批量查询 JobStore？

A: `ShardRecord` 是 POD struct，不含 `priority` 字段（priority 在 `JobRecord` 中）。如果 N 个 shard 每个都调用 `JobStore::Get()`，有 N 次锁开销。用 `unordered_map` 缓存已查询的 job priority，最多只需要 `distinct_job_count` 次锁操作。

### Q: 过载保护为什么不用内存使用率？

A: 转码是 CPU 密集型任务，内存使用率通常稳定在 40-60%（取决于文件缓存）。CPU 使用率是更敏感的过载信号——ffmpeg 转码会导致 CPU 飙升至接近 100%。内存检查在 `running >= max_running_shards` 的槽位控制中已间接覆盖。

### Q: Metrics 为什么只打日志不暴露 HTTP endpoint？

A: 阶段 7 保持简单。日志格式 `[SchedulerMetrics]` 前缀便于 grep/脚本解析。阶段 8（压测和文档）或后续迭代可加入 Prometheus endpoint 等标准监控接口。

## 与阶段 6 的关系

阶段 6 的 fork+exec cancel 机制与阶段 7 的过载保护协同工作：
- Scheduler 的加权评分避免将 shard 分配给高负载 Worker（预防性）
- Worker 的过载保护在负载飙升时直接拒绝新 shard（兜底性）
- 即使分配后 Worker 过载，cancel 也能即时终止执行并重新调度（恢复性）

三道防线确保系统在负载波动下稳定运行。
