## 关键架构决策

### Q: 指标库放在哪一层？为什么放 mprpc 而不是 video_platform？

`rpc_latency_ms` 必须插桩在 RPC 客户端热路径（`MprpcChannel::CallMethod`），
mprpc 是框架层，不能反向依赖业务子项目（与阶段 10 第三批 MprpcRedisClient 的
理由一致：`mprpc 是独立框架层，不应反向依赖业务子项目`）。所以指标库
`mprpcmetrics.h/.cc` 放在 mprpc 层（仿 mprpcredis 风格），video_platform 各服务
经 `video_common → mprpc` 传递依赖自动可用，**零重复代码**。

### Q: 为什么不用 prometheus-cpp 等现成库，而是自研 ~700 行指标库？

两个理由。其一，项目哲学是自研：网络库、RPC 框架、内存池、日志全部自建，
Prometheus text format 0.0.4 是公开规范，直方图/分位/标签转义 ~200 行能覆盖；
引入 prometheus-cpp 会带来依赖与 ABI 风险，而本项目只需要 3 种指标类型。
其二，**HTTP endpoint 也要落地**——本项目没有 HTTP 栈，用自研 wevix_muduo
TcpServer 起独立线程就能提供 `/metrics` 服务（prometheus-cpp 的
`promhttp` 模块同样依赖嵌入式 HTTP 实现）。自研方案把「指标库 + HTTP 服务 +
Gauge 采样器 + 日志告警兜底」统一在一个组件里，职责内聚。

### Q: 每个服务绑 9090 会冲突（单机 5 个服务实例），端口怎么分？

规格写 `:9090/metrics` 是单服务主机的写法。本仓库单机部署 5 个服务，必须互斥：
新增配置项 `metrics_port`（`LoadInt("metrics_port", 0, 0, 65535)`，`<=0` 关闭），
分配 9091-9097（见下文端口表）。**可降级组件语义**（与 Redis/MQ 一脉相承）：
metrics_port 未配置/配置 0 时 `MetricsHttpServer::enabled()==false`，Start/Stop
为 no-op，服务照常运行——指标是观测面，绝不能成为服务可用性的依赖。

### Q: 直方图桶计数为什么「Observe 只加命中桶、导出时前缀和」？

Prometheus 直方图的 `_bucket{le=x}` 是**累计**语义。朴素实现每次 Observe 对
`i >= 命中桶` 的全部桶自增（写 N 个原子量）。改为「命中桶 +1，导出/分位计算时
前缀和」：热路径只写 1 个原子量 + count + sum，rpc_latency_ms 在 RPC 框架热路径
上（毫秒级调用频率），这个差别是真实存在的。代价是导出瞬间的桶快照可能轻微
不一致（导出时逐桶读原子量），对监控用途可忽略。

### Q: `scheduler_queue_size` 和 `shard_waiting` 都是 WAITING 数，不重复吗？

规格同时要这两个 gauge。`shard_waiting` 严格等于 WAITING 状态 shard 数；
`scheduler_queue_size` 定义为 **WAITING + ASSIGNED**（调度器手中"已接受但尚未
进入 RUNNING"的全部工作，即真正的调度积压）。任务提交瞬间 ASSIGNED 短暂存在、
Worker 满载时两者差值变大——语义上更贴合「调度堆积」告警，也和 `shard_waiting`
区分开。文档（README + 本日志）写明口径。

### Q: `shard_count{status=...}` 为什么要对全状态枚举显式 Set（含 0）？

Grafana 饼图/时间线按 `sum by (status) (shard_count)` 聚合。若只更新"有数据的
状态"，某状态归零后其系列停止更新，Prometheus 保留旧值 → **饼图上出现永不消失
的残留扇区**。采样器对 ShardStatus 全枚举（0-8）逐状态 Set，查不到的置 0，
曲线实时归零。

### Q: 告警「至少日志打印」如何落地？为什么内置评估器而只交付 alerts.yml？

验收要求"告警规则触发后能收到通知（至少日志打印）"。Prometheus 的
`alerts.yml` 规则需要 Prometheus + Alertmanager 才能真正通知，本机未部署。
因此 `MetricsRegistry` 内置 **AlertLoop**（每 30s 一轮）：注册
`AlertRule{name, severity, eval, threshold, above, for_ms, description}`，
触发打 `LOG_WARN/LOG_ERROR("ALERT [%s] firing: value=..., threshold=...")`，
恢复打 `LOG_INFO`。**Prometheus 未部署时也能发现异常**；部署后 alerts.yml
提供集群级 PromQL（口径见下文），双轨并存。
rate 型规则（job_failed_rate）用 `RateEstimator`：环形缓冲存 `(ts, counter_value)`，
窗口内 `(v_last - v_oldest) / (t_last - t_oldest)` 估算增量速率，计数器重启
（进程重启清零）钳制为 0 防负速率误报。

### Q: job_failed_rate 的内置口径为什么是「失败数/终态数」而不是「失败数/提交数」？

`job_submitted_total` 在 job_service 进程自增，`job_success/failed_total` 在
result_collector 进程自增——**单进程内拿不到对方 counter**（不做跨进程指标聚合，
那是 Prometheus 的职责）。RC 进程内可得的两个 counter 是 success 和 failed，
所以内置规则口径 = `rate(failed) / rate(failed + success)`（失败占终态比例）。
Prometheus 侧（alerts.yml）用集群级 `rate(failed)/rate(submitted)` 跨实例 sum。
两者阈值一致（0.3），数值在稳态下近似；README 与代码注释都写明口径差异。

### Q: 为什么用自研 TcpServer 起 HTTP 服务而不是手写 socket？

框架无 HTTP codec（`Connection::onMessage` 无 codec 时收到**原始 read chunk**，
可能半个请求头或粘多个请求）。方案：独立线程构造
`TcpServer("127.0.0.1", port, threadNum=1)` 并 `start()`（阻塞在
`mainLoop_->run()`），onMessage 里按 fd 维度累积缓冲、`\r\n\r\n` 定位请求头、
只解析请求行路由（GET /metrics → 200；其余 404；>8KB 头直接 400）。
响应用 `send + shutdown()`（只关写端让内核 flush 完数据）——**不用 forceClose**
（`forceClose` 走 handleClose 会丢弃 outputBuffer 未发完的数据）。`stop()`
跨线程安全（EventLoop::stop 带 eventfd wakeup，ThreadPool::stop 内部 join），
main 线程退出时 `metrics_server.Stop()` join HTTP 线程。

### Q: rpc_latency_ms 插桩为什么用 RAII 守卫而不是手动计时？

`MprpcChannel::CallMethod` 有 **~10 个 early return**（序列化失败、帧过大、
服务发现失败、超时、解析失败、request_id 不匹配……）。手动在每个 return 前
Observe 必然漏测，而且漏掉的恰好都是"异常路径"——告警关心的正是异常延迟。
RAII 守卫声明在函数体顶部（`service_name/method_name` 计算后），析构覆盖
**所有** return 路径，异常路径同样进直方图。SchedulingLoop 主循环同理：
循环体内 20+ 个 continue（超时重扫、分配循环提前退出），迭代体顶部的 RAII
计时器天然覆盖全部分支。**这是"插桩正确性靠作用域，不靠调用点纪律"的实践。**

### Q: 直方图 p99 怎么算（内置告警 rpc_latency_p99_high 用）？

`HistogramQuantile(q)`：累计计数 `cum[i]` 中找第一个 `cum[i] >= q*total` 的桶，
桶内线性插值（首桶下界按 0 处理；落在 +Inf 尾桶时上界取最后一个有限桶）。
与 Prometheus 的 `histogram_quantile` 算法一致（累计 + 线性插值），数值可比。
告警规则 eval = `registry.HistogramQuantile("rpc_latency_ms", 0.99)`，
聚合该 name 全部 method 系列后插值——即"本进程所有出站 RPC 的 P99"。

## 实现步骤

### Step 1: mprpcmetrics 指标库（mprpc 框架层）

新增 `mprpc/include/mprpcmetrics.h` + `mprpc/src/mprpcmetrics.cc`
（~700 行，仿 mprpcredis 风格：中文注释、`// ====` 分隔、单例 GetInstance），
`mprpc/src/CMakeLists.txt` SRC_LIST 追加 `mprpcmetrics.cc`。组件结构：

```
MetricsRegistry（单例，mutex 保护注册/导出，更新路径无锁）
├── Counter  ── atomic<uint64_t>，Inc/Value
├── Gauge    ── AtomicDouble（位模式 CAS：C++17 不保证 atomic<double> fetch_add）
├── Histogram─ 固定桶 + 逐桶 atomic（Observe 只加命中桶）+ 前缀和导出
│              + Quantile（线性插值，聚合全 method 系列）
├── RegisterSampler(fn, interval_ms) → 采样线程（各采样器独立间隔，兜底 1s）
├── RegisterAlertRule(AlertRule)     → AlertLoop（30s 一轮，触发/恢复打日志）
└── ExportText() → text format 0.0.4（#HELP/#TYPE/系列字典序）
```

线程安全设计要点：**注册/导出加 registry mutex；Inc/Observe 无锁**。
采样线程与告警线程**不得持有 mutex_ 执行用户回调**（回调会再进 registry 加锁，
死锁）——先拷贝到期 fn/规则快照，锁外执行。采样失败（MySQL 查询失败）由
fn 内部跳过本轮保持旧值，避免 0 值尖刺误告警。

`RpcLatencyHistogram(method)` 热路径缓存：首次调用注册进 registry 并缓存
`MetricHistogram*`（注册后系列不再增删，指针稳定），后续调用仅一次
`unordered_map` 查找 + 两次原子自增，微秒级开销。

### Step 2: mprpcchannel.cc 插桩 rpc_latency_ms

`MprpcChannel::CallMethod` 入口（计算 `service_name/method_name` 后）声明 RAII
守卫 `RpcLatencyGuard`，析构时 `RpcLatencyHistogram(service + "." + method).Observe(ms)`。
**一次插桩，全部服务自动获得 rpc_latency_ms**（所有服务都是 MprpcChannel 客户端）。
标签 `method` 形如 `SchedulerService.ScheduleJob`、`WorkerManagerService.Heartbeat`，
基数 = 平台 RPC 方法数（~15），不会标签爆炸。

### Step 4: 业务指标插桩（6 处）

| 指标 | 插桩点 | 说明 |
|------|--------|------|
| `job_submitted_total` | job_service `SubmitJob`（参数校验通过后、Insert 前） | 校验失败的请求不计数，保证失败率分母=平台实际受理数 |
| `job_success_total` / `job_failed_total` | result_collector `MarkJobTerminal` 函数体顶部（单入口） | SUCCESS/FAILED 两路共用；MQ 消费线程与 TerminalSweepLoop 并发调用安全（原子计数） |
| `shard_retry_total` | scheduler **4 处** `retry_count++`：RescheduleShard、NotifyWorkerOffline、SchedulingLoop ASSIGNED 卡死重扫、RUNNING 超时重扫 | 计划文档写 2 处，实现时补齐 4 处保证口径完整（离线重试、超时重试都算"重试"） |
| `transcode_duration_ms` | transcode_worker `FfmpegExecute` 内 Transcode 已有计时（`transcode_elapsed`）后一行 Observe | cancel 的耗时同样计入（转码被中断也是观测对象） |
| `schedule_loop_duration_ms` | SchedulingLoop 主循环 `++metrics_round` 后 RAII 守卫 | 覆盖 20+ 个 continue 路径；桶 [10..10000]ms |
| shard 状态 Gauge | scheduler main 注册 5s 采样器 → `ShardStore::CountByStatus()` | 一次 GROUP BY 查询刷新 5 个 gauge（见 Step 5） |
| worker 系列 Gauge | worker_manager main 注册 5s 采样器 → `WorkerStore::ListAll()` | `worker_online` + 每 Worker 负载 |

### Step 5: `ShardStore::CountByStatus()`（新增 Store 方法）

```sql
SELECT status, COUNT(*) FROM shards GROUP BY status
```

单条查询替代 9 次 `ListByStatus().size()`（5s 一次采样，MySQL 往返成本低）。
返回 `std::map<int32_t, size_t>`（仅含有数据的 status；查询失败返回空 map，
采样器据此跳过本轮）。`mysql_pool.h` 的 `MysqlConnectionGuard::Query` 接受原始
SQL，GROUP BY 天然支持。

### Step 6: 内置日志告警（4 条规则，各服务 main 注册）

| 规则 | 注册进程 | eval | 触发 |
|------|---------|------|------|
| `rpc_latency_p99_high` | 全部 5 服务 | `HistogramQuantile("rpc_latency_ms", 0.99)` | > 1000ms，WARN |
| `worker_offline` | worker_manager | `Gauge("worker_online").Value()` | < 1，ERROR |
| `scheduler_backlog` | scheduler | `Gauge("scheduler_queue_size").Value()` | > 100，WARN |
| `job_failed_rate_high` | result_collector | RateEstimator 5min 窗口：`rate(failed)/rate(failed+success)` | > 0.3，WARN |

**alerts.yml PromQL**（集群级口径）：
- `WorkerOffline`: `sum(worker_online) < 1`，for 1m
- `SchedulerQueueBacklog`: `sum(scheduler_queue_size) > 100`，for 2m
- `JobFailureRateHigh`: `rate(job_failed_total[5m]) / clamp_min(rate(job_submitted_total[5m]), 0.001) > 0.3`，for 5m

**Grafana 面板 4 行**：

- Row 4：RPC 延迟 heatmap（`format:"heatmap"` + `calculate:false`，le 桶直方图）
  + P50/P90/P99 折线（`histogram_quantile` 三线，p99 红色高亮）

## 过程中发现并修复的 Bug（6 项）

### 1.（严重）AlertLoop 线程从未启动：StartSamplers 的 CAS 逻辑写反

```cpp
// 错误写法
if (alertRunning_.compare_exchange_strong(expected, true)) return;
alertThread_ = std::thread([this] { AlertLoop(); });
```

`compare_exchange_strong` **成功**（false→true）时返回 true → 误走 `return`，
告警线程永远不创建。症状：日志里只有 `sampler thread started`，没有
`alert evaluator thread started`；worker 被杀后无任何告警日志。
修复：告警线程改用 `exchange(true)` 返回旧值判断（旧值 false → 创建；
true → 已在运行跳过）。**教训：CAS 返回的是"是否发生交换"，不是"新值"；
幂等启动线程用 exchange 更不易错。**（采样线程用的 `!CAS → return` 写法恰好正确，
两种语义并存导致自查时极易混淆——已用注释标注。）

### 2. 直方图 le 标签格式错误：`{method="..."},le="1.000000000"}`

第一版 ExportText 把 `FormatLabels()` 返回的完整 `{method="..."}` 又拼了
`,le=...` 再补 `}`，产生多逗号/多余花括号的非法标签。
修复：labels 非空时先 `substr(0, size()-1)` 去掉结尾 `}`，再拼 `,le="..."}`。

### 3. `std::vector<std::atomic<uint64_t>>` 无法 resize 编译失败

atomic 不可拷贝/移动，`vector::resize` 触发 static_assert。
修复：`std::unique_ptr<std::atomic<uint64_t>[]>` + 原地 placement new。

### 4. 工作区文件迁移导致构建失败（非本阶段引入）

发现时 `video_platform/src/worker_manager/worker_manager.cpp` 已不存在
（git status 显示 D，文件被移动至 `src/transcode_worker/worker_manager/`
未提交），CMake 引用旧路径导致 configure 失败。已把 CMakeLists 同步为新路径
（CMake 与工作区现状对齐，文件移动由用户侧确认）。

### 5.（严重）ZooKeeper 同步调用无限阻塞：SchedulingLoop 卡死 9 分钟

**现象**：Grafana 实测部署中，Scheduler 的 SchedulingLoop 在
`wm_stub.ListWorkers`（服务发现）处卡死（线程 wchan=`futex_wait_queue`），
调度停摆 7-9 分钟，残留 WAITING shard 无人分配。卡死点：ZK 客户端连接处于
「会话未建立」（ZK `stat` 显示该连接 `[0]`、`sent=0`——TCP 已连但 AMQP 式
握手未完成）时，`zoo_get` 同步 API 内部无限等待连接就绪（zookeeper_mt 的
同步调用无超时）。首次触发是 MprpcRedisClient/ZkClient 的**懒初始化**：
服务启动后长时间只用 Redis 快照，第一次真正需要 ZK 时才 `zookeeper_init`，
而 `zookeeper_init success` 只表示对象创建成功，不代表连接就绪。

**修复**（`mprpc/src/ZookeeperUtil.cc`）：
1. `GetData` / `GetChildren` 改用**异步 API（zoo_aget / zoo_aget_children）+
   信号量 3s 超时等待**；超时按「发现失败」返回（调用方已有失效缓存/重试回退）
2. **异步回调的 UAF 防护**：ctx 堆分配 + `caller_gone` 标记——超时后调用方
   不再碰 ctx，回调线程完成后自回收（sem_post 建立 happens-before，无竞态）
3. 入口 `zoo_state()` 快速失败：非 `ZOO_CONNECTED_STATE` 直接返回（省 3s）
4. `Create`（服务注册）保留同步（Start 已确保连接），行为不变

**效果**：ZK 异常时调度线程最多阻塞 3s → RPC 失败 → 下一轮重试，调度不停摆。
（ZK 连接为何「会话未建立」未彻底定位——疑似 ZK 3.4.10 老版本偶发；修复后
无论何种原因系统都有界。）

### 6.（严重）RabbitMQ 消费锁死导致调度停摆：`amqp_consume_message` 无限阻塞

**现象**：修复 Bug 5 后新进程仍卡死，且**每轮调度循环（含 metrics sampler）
全部静默**。定位：消费线程（MqConsumeLoop）持 `consume_mutex_` 卡在
`amqp_consume_message`（wchan=`do_sys_poll` 持续 8+ 分钟），SchedulingLoop
每轮调 `MqClient::connected()` 等同一把锁 → 调度停摆。根因：rabbitmq-c 0.11
的 `amqp_consume_message` 虽带 timeval 参数，但**内部 poll 超时行为不可靠**
（poll 返回可读后 read 阻塞、或 poll 无限等待），RabbitMQ 连接进入半开状态
后消费线程无限持锁。

**修复**（`video_platform/src/mq_client.cpp` + `mq_client.h`）三层防护：
1. **消费改自控 poll**：`ConsumeBlocking` 不再依赖 amqp 的 tv 超时——自己
   `poll(fd, timeout_ms)`（超时完全可控），有数据后 `amqp_consume_message`
   传 `{0,0}` 立即尝试；读半帧则下轮再 poll，**消费线程绝不无限阻塞**
2. **消费锁改 `std::timed_mutex`**：`connected()` / `Ack()` / `Reconnect()`
   用 `try_lock_for(1s)`——锁被卡时 1s 降级返回（`consume lock busy, degrade
   to Pull polling`），**SchedulingLoop 转 Pull 轮询兜底，调度不停摆**
3. **socket 收发超时**：`OpenChannel` 连接建立后 `setsockopt(SO_RCVTIMEO/
   SO_SNDTIMEO, 2s)` 兜底 login/握手/read（amqp 同步 RPC 也有界）

**效果**：MQ 连接异常时：消费线程最多阻塞 2s → `connected()` 1s 降级 →
Pull 轮询（2s）接管调度，任务照常完成（实测 MQ 半死状态下 5/5 SUCCESS）；
MQ 恢复后 Push 自动切回（实测重启后 Push 分配立即恢复，`MqConsume: assigned`
日志复现）。**这是"可降级组件"哲学的完整落地：组件故障 → 快速失败 → 兜底路径
接管，而不是调用线程陪葬。**
