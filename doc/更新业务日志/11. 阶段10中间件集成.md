## 阶段目标（摘自路线图）

### 11a. Redis 缓存

1. **ZK 服务地址缓存**：MprpcChannel 进程内缓存 → Redis `HSET` 集中管理，多进程共享
2. **Worker 负载快照**：Scheduler 从 Redis 直接读 Worker 最新心跳数据，不走 WorkerManager ListWorkers RPC
3. **Job 进度缓存**：高频 QueryJob 的进度数据写入 Redis（TTL 60s），减少 JobService→ShardStore 反复扫描
4. **分布式锁**：多 Scheduler 实例下用 Redis `SETNX` 防止同一个 shard 被重复分配

### 11b. 消息队列（RabbitMQ）

- JobService → Exchange `job.events` → Queue `shard.waiting` → Scheduler 消费 → AssignShard
- Worker 完成 → Exchange `shard.events` → Queue `result.pending` → ResultCollector 消费 → 聚合
- 选型：RabbitMQ（消息量 shard 级，AMQP 标准后续可迁移；Kafka 杀鸡用牛刀）

### 验收标准

- Redis 故障不影响核心转码链路（降级为本地缓存）
- MQ 模式下 shard 调度延迟从平均 2s 降到 < 100ms
- MQ 宕机后消息不丢失（持久化队列 + 手动 ACK）

# 第 1 批：Redis 缓存（本批主体）

## 关键架构决策

### Q: Redis 与 MySQL 的故障语义为什么不同——MySQL 预创建失败拒绝启动，Redis 失败只降级？

MySQL 是唯一数据源，连不上服务无法工作，启动即失败是快速失败（fail-fast）。Redis 只是**读路径加速**：负载快照的真相源是 MySQL（心跳仍写 MySQL，Redis 只是镜像）、进度的真相源是 MySQL、锁是防御性保护——Redis 故障时退化为第 9 阶段的行为即可，系统完全可用。所以 `RedisClient::Init()` 连接失败只 `LOG_WARN`，**不拒绝服务启动**。

### Q: Worker 负载快照为什么用 `HSET worker:load {worker_id} → "cpu|mem|running|ts"` 而不是每 worker 一个 key？

Scheduler 分配循环需要**一次拿全部 ONLINE Worker**。HSET 单 key 多 field 正好对应"一个 hash 存所有 worker 快照"：`HGETALL` 一次 RTT 取全量，与 ListWorkers RPC 一次返回全量等价。每 worker 一个 key 则需要 `SCAN worker:load:*`（多轮 RTT + 游标）或额外维护 worker 集合，复杂且多一次往返。

field 过期问题：HSET 的 field 不能单独 TTL。解法是**值内嵌时间戳**，读侧按 20s（心跳超时阈值）过滤——读取时 `now - ts > 20000` 视为过期丢弃。残留 field 由下次同名 worker 心跳覆盖，无内存泄漏问题。

### Q: Scheduler 读 Redis 为什么不重构打分循环，而是把数据源塞回 `ListWorkersResponse`？

分配循环（`scheduler_service.cpp:1319-1420`）的打分逻辑（阶段 7 加权评分、round_assigned 槽位防超额、优先级排序）与 `lw_resp.workers()` 数据结构强耦合。抽一个 `LoadOnlineWorkers(ListWorkersResponse&)` helper：内部先试 Redis 快照（构造等价的 WorkerInfo），失败/无数据回退 `wm_stub.ListWorkers` RPC——调用方代码零改动，降级路径与主路径天然同构。Redis 读取失败的降级是**按次**的：本轮 Redis 挂了就本轮走 RPC，下一轮 Redis 恢复自动切回，无需状态机。

### Q: 进度缓存为什么缓存整个 `QueryJobResponse` 序列化串而不是只缓存 shard 列表？

QueryJob 的响应 = job_info + 全部 shard，构造成本主要在 `ShardStore::ListByJob`（一次 SQL）。缓存整个响应串（`SerializeToString` + `SETEX`），命中时 `ParseFromString` 直接返回——一次反序列化替换一次 SQL 扫描，是收益最大、改动最小的形态。只缓存 shard 列表反而要改响应构造逻辑，收益相同、风险更高。只缓存 `error_code==0` 的响应，miss 时走原逻辑并写回。

### Q: 分布式锁为什么要带 value 校验释放？

`SETNX shard:lock:{id}` 的 TTL（10s）防止持锁进程崩溃后死锁。释放时的经典陷阱：A 持锁执行变慢超过 TTL，锁被 B 抢走，A 完成后 `DEL` 把 B 的锁删了。解法：锁 value 用进程唯一标识（`pid@start_time`），释放前 `GET` 校验值相同才 `DEL`（检查后删除的两步之间仍有竞窗，但锁的语义是"防重复分配"，多实例下最坏情况是重复分配一次，由第 2 批的消费幂等兜底；当前单实例部署下此竞窗不存在）。TTL 未过期前的锁正常释放，TTL 兜底防崩溃泄漏。

### Step 1: 环境与依赖

- Redis 6.0.16 @ 127.0.0.1:6379 可用（systemd 托管，`redis-cli ping` PONG）
- hiredis 已安装（libhiredis-dev 1.2.0，`/usr/include/hiredis/`）
- RabbitMQ 未安装（第 2 批再装，本批不依赖）
- `video_platform/CMakeLists.txt`：`video_common` 新增 `src/redis_client.cpp`，link 增加 `hiredis`

### Step 2: RedisClient 封装（`redis_client.h/.cpp`，~180 行）

hiredis 同步 API 封装，与 MysqlPool 的关键差异——**Redis 是可降级组件**：

- `Init()` 连接失败只 `LOG_WARN` 并置 `enabled_=false`，**不拒绝服务启动**（MySQL 连不上必须 fail-fast，Redis 只是读路径加速，故障退化为阶段 9 行为即可）
- 单连接 + `mutex`：调用频率低（心跳 3s/worker、QueryJob、分配锁），连接池无收益；redisContext 非线程安全，所有命令锁内执行
- 命令失败自动 `redisFree` 重建连接重试 1 次（断连后 context 不可复用）；仍失败本次返回 false，调用方降级
- connect/command 均设 2s 超时，Redis 卡死不阻塞业务线程
- 命令集（第一批）：`HSet / HGetAll / Get / SetEx / SetNxEx / Del`

### Step 3: Worker 负载快照双写（A2）

**WorkerManager `Heartbeat`**（`worker_manager.cpp`）：`UpdateHeartbeat` 成功后（alive=true 才写，避免幽灵快照）从 MySQL `Get` 全量记录拼快照串，`HSET worker:load {worker_id} → "ip|port|cpu_cores|memory_mb|max_running|current_running|cpu_usage|memory_usage|ts"`。

- 为什么心跳时还要读一次 MySQL：心跳请求只带 WorkerLoad（cpu/mem/running），ip/port/max_running 是注册时写入的——MySQL 是唯一真相源，读一次 PK 查询（<0.2ms）拼完整快照，逻辑最简
- 快照串值内嵌 ts，field 无单独 TTL 的问题靠读侧过期过滤解决

**Scheduler `LoadOnlineWorkers`**（`scheduler_service.cpp`）：分配循环的 ListWorkers 调用抽成 helper——先 `HGETALL worker:load` 解析快照（`now - ts > 20s` 视为 OFFLINE，与 WorkerManager 心跳超时阈值一致），**有存活数据直接构造 `ListWorkersResponse` 返回**；快照空/全过期/Redis 不可用时回退 `wm_stub.ListWorkers` RPC。调用方打分循环零改动。降级是**按次**的：本轮降级下轮自动恢复。

### Step 4: Job 进度缓存（A3）

**JobService `QueryJob`**（`job_service.cpp`）：先 `GET job:progress:{job_id}`，命中 `ParseFromString` 直接返回；miss 走原 MySQL 查询，`error_code==0` 时 `SerializeToString` 写回（`SETEX` TTL 60s）。

- 缓存整个响应串而非只缓存 shard 列表：一次反序列化替换一次 `ShardStore::ListByJob` SQL 扫描，改动最小、收益最大
- 只缓存成功响应，失败响应不污染缓存

**ResultCollector `ReportShardResult`**：shard 状态推进（SUCCESS/FAILED）后 `DEL job:progress:{job_id}`——结果落定不滞后；进行中进度（ReportShardProgress）靠 TTL 过期自然刷新，接受最多 60s 滞后（进度本为近似值，GUI 实时进度留待阶段 12）。

### Step 5: 分布式锁（A4）

**Scheduler 分配循环**（`scheduler_service.cpp`）：AssignShard 前 `SET shard:lock:{shard_id} scheduler:{pid} NX EX 10`：

- 取得锁 → 分配；锁被占用（GET 确认值存在）→ 本实例跳过该 shard（其他实例正在分配）
- **Redis 故障（GET 失败/key 不存在）→ 降级放行**——MySQL 条件更新（WAITING→ASSIGNED）兜底防重复分配，核心链路不受影响
- 释放：GET 校验 value 相同才 DEL（防 TTL 未过期前锁被抢、持锁方完成时误删他人锁）；AssignShard 失败分支同样释放，下轮可重试
- TTL 10s 防持锁进程崩溃后死锁

# 第 2 批：RabbitMQ 事件驱动（本批主体）

## 关键架构决策

### Q: 路线图写"JobService → Exchange job.events"，为什么发布端实现在 Scheduler？

路线图是业务视角（"提交任务的一方发通知"），但 shard 的**切分动作发生在 Scheduler.ScheduleJob**（JobService 只调 ScheduleJob RPC）。shard 创建完成、进入 WAITING 的瞬间在 Scheduler 进程内——发布端自然在 Scheduler。若在 JobService 发布，需要等 ScheduleJob 响应返回（多一跳 RPC 延迟），且幂等早退分支的语义更难处理。同理，**任何 shard 状态变为 WAITING 的路径**（新建/重试/离线重置/超时重置/启动恢复）都发布事件，消费端统一处理。

### Q: 消息体为什么"分配事件只带 shard_id，结果事件带完整序列化请求"？

两条事件流语义不同：
- **shard.waiting（通知通道）**：只是"有活可干"的信号。消费端（Scheduler）收到后**重新查 MySQL** 拿最新状态——MySQL 是唯一数据源，消息携带快照反而有陈旧风险（与阶段 9"不构造本地副本"原则一致）。且 shard 可能已被其他路径分配，查库才能幂等判断。
- **result.pending（数据通道）**：执行结果（is_success/exit_code/output_path/screenshot_path/elapsed_ms）**不在 MySQL 中**（shard 表只存输出路径等静态字段），必须随消息传递，RC 消费后走与 RPC 完全相同的 `HandleReportShardResult` 聚合逻辑。消息体 = `ReportShardResultRequest` 序列化串。

### Q: MqClient 为什么是"双连接 + 双锁"？单连接单锁有什么问题？

rabbitmq-c 连接非线程安全，初版单连接 + 单锁，`ConsumeBlocking` 持有锁阻塞等待消息（最长 2s）。后果：**ScheduleJob RPC 的 work 线程切分完调 `PublishShardWaiting` 要等同一把锁，RPC 处理超过客户端超时**——实测报 `recv response header error! errno:11`，任务无法提交。

修复：发布（publish_conn_/publish_mutex_）与消费（consume_conn_/consume_mutex_）严格分连接分锁。消费阻塞只等消费锁；发布持锁时间 = 单条 publish（微秒级）。拓扑声明由发布连接完成（幂等），消费连接只登录 + channel。

### Q: MQ 在线时 SchedulingLoop 为什么降频到 5s 而不是完全停掉？

SchedulingLoop 承担两类职责：**分配**（可被 MQ 替代）与**可靠性**（超时重扫/启动恢复/卡死检测，与 MQ 无关）。分配完全停掉的风险：消息发布失败（网络抖动）或消息丢失时，shard 永远无人分配——Push 模式引入新的故障面。保留 5s 兜底扫描：正常路径 <100ms（消息触发），异常路径保底 5s（扫描兜底），可靠性与延迟兼得。超时重扫由"每 15 轮"改为**按时间（30s）**——interval 随 MQ 状态在 2s↔5s 间变化，按轮次会导致重扫周期漂移（15×5s=75s）。

### Q: MQ 掉线/恢复如何与轮询自动切换？

状态由 `MqClient::connected()`（消费连接对象是否存在）单点决定：
- **掉线**：`ConsumeBlocking` 检测到连接故障 → 销毁消费连接 → 消费线程 2s 周期 `Reconnect()`；SchedulingLoop 每轮检查 connected()==false → 自动恢复 2s 全量扫描。系统降级为阶段 9 行为，任务仍可完成（Worker 结果上报同时回退直连 RPC）。
- **恢复**：`Reconnect()` 成功 → 消费线程继续消费；SchedulingLoop 检测到 connected()==true → 自动降频 5s。**无状态机、按次判断**，与 Redis 降级同哲学。

### Q: 消费消息为什么无条件 ACK（包括分配失败）？

消息的"职责"是触发一次检查（该 shard 是否可分配），检查已做即完成职责。分配失败（无 worker/过载/锁占用）不该重回队列——那会导致无限重投风暴；由 SchedulingLoop 兜底扫描再试（5s 内）。重复投递（Broker 重发）由消费侧幂等处理：查 MySQL 发现非 WAITING 即跳过，配合 TryAssignShard 的状态复核 + 分布式锁 + 条件更新三重防护。

### Step 1: MqClient 封装（`mq_client.h/.cpp`，~380 行）

rabbitmq-c (AMQP 0-9-1) 封装：

- interval 动态：MQ 在线 5000ms（兜底）/ 掉线 2000ms（全量）

- Worker：`TryPublishResultToMq()` 优先（序列化 ReportShardResultRequest publish result.pending），失败回退直连 RPC（3 处上报点统一改造，带原 3 次重试）

# 第 3 批：ZK 服务地址缓存改造（本批主体）

## 关键架构决策

### Q: mprpc 自建轻量 Redis 客户端，而不是把 video_platform 的 RedisClient 下沉到框架层？

log11 交接时标注"推荐后者"（自建）。mprpc 是独立框架层，下沉业务代码会形成 mprpc → video_platform 的反向依赖，破坏分层。自建只需 4 个命令（HGET/HSET/EXPIRE/HDEL），~150 行；hiredis 是系统库，link 成本为零。与业务层 RedisClient 保持同构的**可降级语义**：Init 失败只 WARN 不拒绝任何调用、命令失败重建重连 1 次、connect/command 2s 超时。

与业务层的关键差异——**懒初始化**：业务层在 main 里显式 `Init()`（框架层无法要求所有调用方改 main），MprpcRedisClient 在**首次命令调用时**用 `std::once_flag` 读配置并连接。未调用 `MprpcApplication::Init` 的程序（如压测工具）读默认配置（redis_enable=1 / 127.0.0.1:6379），连不上只 WARN 走原路径，行为与改造前完全一致。

### Q: 本地缓存为什么要加 30s TTL？原来的进程内缓存是无限期的

两个理由：
1. **集中管理的新鲜度**：Redis 缓存的共享价值在于"实例变更后其他进程及时感知"。若本地缓存无限期，每个进程永远吃自己的旧缓存，Redis 集中管理名存实亡。30s TTL 保证最多 30s 后所有进程重新发现。
2. **热路径零交互**：`GetHostData` 是**每个 RPC 调用**的热路径（12 万 QPS 量级）。本地缓存 30s 内命中直接返回，零 Redis/ZK 往返——性能不回退；TTL 过期后每 method 每 30s 才一次 Redis HGET（~0.1ms），摊薄后可忽略。

### Q: 连接失败时 `InvalidateHostData` 为什么要 HDEL Redis 字段？

连接失败意味着该 endpoint 可能已下线。只清本地缓存的话，其他进程 30s 内仍会轮询到死实例。HDEL 集中字段后**所有进程同时失效**，下次发现一起重拉 ZK——"多进程共享失效"是集中管理相对进程内缓存的核心收益。Redis 不可用时 HDEL 失败无碍：各进程本地缓存 30s TTL 到期后自愈。

### Q: 缓存键/值格式和 TTL 怎么定的？

- 键：`mprpc:endpoints`（一个 hash 存所有 method 的发现结果，与 `worker:load` 同哲学——一次 HGETALL 全量）
- field：`method_path`（如 `/mprpc/services/SchedulerService/ScheduleJob`）
- value：CSV endpoint 列表（`ip:port,ip:port`，endpoint 不含逗号，拼接/解析安全）
- TTL：30s（本地与 Redis 统一）。HSET 后 EXPIRE 整个 key；EXPIRE 失败只影响共享新鲜度，由 HDEL 失效兜底
- 轮询 index（nextIndex）仍需本地维护：Redis 只存列表本身，轮询状态是进程视角的（多进程各自轮询，负载均衡语义仍然成立）

| `mprpc/src/mprpcchannel.cc` | ① 常量：`kEndpointsHashKey="mprpc:endpoints"`、`kEndpointCacheTtlSec=30`（本地与 Redis 统一 TTL）。② `EndpointCacheEntry` 加 `fetchedAtMs`（本地缓存写入时间戳，超 30s 视为过期）。③ 新增 `JoinEndpoints`（CSV 拼接）/`ParseCsvEndpoints`（CSV 解析）。④ `QueryEndpointList`：ZK 拉取后**先**写 Redis（`HSET` + `EXPIRE` 30s，不持本地缓存锁——网络操作 2s 超时若持锁会卡死发现热路径），**后**写本地缓存（带 `fetchedAtMs`）；写回失败不影响本进程。⑤ `GetHostData` 三层链路：本地缓存（30s TTL 命中直接返回，热路径零 Redis/ZK 交互）→ Redis `HGET`（多进程共享命中，填本地缓存返回）→ ZK 拉取（兜底）。Redis 故障/不可用直落第 3 层，与改造前行为完全一致。⑥ `InvalidateHostData`：清本地缓存 + `HDEL` 集中字段——连接失败意味着实例可能下线，**所有进程的缓存同时失效**，避免集体轮询到死实例 | 进程内缓存 → Redis HSET 集中管理：多进程共享服务发现结果；实例变更最多 30s 全集群感知；连接失败 HDEL 全集群失效 |
