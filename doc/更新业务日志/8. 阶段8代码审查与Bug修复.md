## 日期

2026-08-01

## 背景

阶段 5-7 已交付（`da71d14..HEAD`，约 2,700 行有效代码改动）：失败重试与故障恢复、FFmpeg 执行器接入、资源感知调度与监控。功能链路均已跑通，但经系统性代码审查（10 角度发现 → 去重 → 逐项 1 票验证 → 遗漏排查，10 + 32 + 3 = 45 个 agent 参与），发现 **15 个已确认问题 + 若干次要问题**。

审查结论一句话概括：**「故障恢复」是本次审查的重灾区——代码注释声称存在的恢复机制（心跳重报、启动恢复、PENDING 兜底扫描）实际大多不存在**；其次是无互斥的终态处理（Merge 竞态）与多处重试预算被重复消耗的路径。

本文档记录每个问题的现象、根因、后果与修复建议。问题编号与修复后提交对应（修复进行中）。

## 一、服务重启即瘫痪（最严重）

### #1 WorkerManager 重启后 Worker 永久失联 🔴

**涉及文件**：`transcode_worker.cpp`（RegisterWorker 调用点 ~:872）、`worker_manager.cpp`、`common_store.cpp:293`

#### 现象

Worker 只在 `RunHeartbeatLoop` 启动阶段调用一次 `RegisterWorker`（3 次重试后永不再试）。WorkerStore 是进程内 `unordered_map`，WM 崩溃/重启后记录全丢；Worker 后续心跳走 `UpdateHeartbeat` 对未知 worker_id 返回 `alive=false`，Worker 只打 WARN 继续心跳，**永不重新注册**。

#### 后果

Scheduler 每次 `ListWorkers` 拿到空列表，日志刷 "no ONLINE workers available"，新任务永远无法分配；只有手动重启全部 Worker 进程才能恢复，且无任何日志指明根因。

#### 修复建议

Worker 心跳发现 `alive=false` 时自动重新 `RegisterWorker`（幂等，WM 端重复注册覆盖即可）；或 WM 的 `UpdateHeartbeat` 对未知 worker 改为「隐式注册」。

### #2 Scheduler 重启后 shard 状态全丢，「启动恢复」是死代码 🔴

**涉及文件**：`scheduler_service.cpp:775-817`

#### 现象

ShardStore/JobStore 均为进程内存储（`common_store.h` 明确注明「多进程部署时各进程 Store 完全隔离」），无任何持久化或启动时跨服务重同步。阶段 5 的「启动恢复」扫描（`ListByStatus(ASSIGNED/RUNNING)` → 重置 WAITING）**必然运行在空 store 上**，`recovered` 恒为 0。

#### 后果

Scheduler 被 kill -9 后重启：
- 未分配的 WAITING shard 永久孤儿 → ResultCollector 端 `CheckJobDone` 永远等不到 `success+failed >= expected`，job 无限挂起；
- 期间任何 FAILED 上报触发 `RescheduleShard` → 返回 "shard not found"（`:329-337`）→ RC 端 shard 留 FAILED → 不可逆 JOB_FAILED。

#### 修复建议

二选一：① JobService/ResultCollector 在 Scheduler 启动时把未终态 job 的 shard 计划推回（RPC 重同步）；② 给 Scheduler 引入持久化（文件/DB）。另需给 SchedulingLoop 加「RUNNING 超时重扫」作为兜底（见 #10 关联）。

### #3 SubmitJob 的 ScheduleJob 重试耗尽后 job 永久 PENDING，客户端被告知成功 🔴

**涉及文件**：`job_service.cpp:107-195`

#### 现象

`SubmitJob` 对 ScheduleJob RPC 做 3 次重试（各 5s 超时 + 1s 间隔），全部失败后：job 留在 PENDING（:72 创建），但响应早在 :83 就置 `error_code=0` 且**从未更正**。代码注释声称「SchedulingLoop 可通过扫描 PENDING job 兜底」——该兜底**不存在**：Scheduler 从未收到该 job（其 JobStore 无记录），SchedulingLoop 只扫描本地 WAITING shard，全仓库无任何 PENDING 扫描。

#### 后果

Scheduler 短暂不可用期间提交的任务永远无法开始，客户端却收到成功响应；CancelJob 只能改状态不能触发切分，用户无任何手段让任务启动。

#### 修复建议

① 3 次重试失败后置错误码/错误信息到响应，并让 job 进入可被重试的显式状态（如 JOB_FAILED 或带 retry 的 PENDING）；② 实现注释声称的 PENDING 扫描（JobService 定时向 Scheduler 重发切分请求，请求幂等）。

## 二、安全

### #4 FFmpeg 命令注入（路径不转义进 sh -c）🔴

**涉及文件**：`ffmpeg_executor.cpp`（Probe:320 / Transcode:495 / Slice:432 / Screenshot:564 / Merge:617 / ExecuteCommand:126）

#### 现象

所有命令经 `/bin/sh -c` 字符串拼接执行，客户端可控的 `input_path`/`output_path` 只包双引号不转义——`"`、`$()`、反引号均未处理。`input_path` 来自 SubmitJob 请求（仅空串检查），经 ShardInfo 流到 Scheduler 的 `Probe()`（popen）与 Worker 的 `Transcode()`（execl sh -c）。

#### 后果

任意客户端在 Scheduler 与所有 Worker 主机上执行任意命令；含 `"` 的路径直接令命令失败 → shard 永久 FAILED。（本项目为无鉴权 localhost 演示平台，实际危害受限，但机制真实存在。）

#### 修复建议

不要走 shell：ffmpeg/ffprobe 用 `fork()+execvp()` 直接传 argv（`execlp("ffmpeg", "ffmpeg", "-i", path, ...)`），彻底消除转义问题（头文件注释声称的 "fork+execvp" 与实际实现不符，属注释与实现漂移）。

## 三、终态判定与数据完整性

### #5 RescheduleShard RPC 失败 → 不可逆 JOB_FAILED 🟠

**涉及文件**：`result_collector.cpp:232-248, 373-380, 402`、`scheduler_service.cpp:329-337`

#### 现象

FAILED shard 的 `RescheduleShard` RPC 失败/超时只打 WARN，本地 shard 留 FAILED；`CheckJobDone` 立即判 JOB_FAILED；单调性守卫（JOB_SUCCESS=6 < JOB_FAILED=7）使后续成功重试无法升级 job。

#### 后果

Scheduler 重启/分区瞬时抖动一次 → job 永久 FAILED，即使所有 shard 最终成功；Scheduler 侧 shard 永久 RUNNING（无人重扫）。

#### 修复建议

RescheduleShard 失败时：① RC 侧重试（带退避）；② 本地标记「待重排」而不是直接 FAILED，由定时兜底重扫；③ 允许 JOB_FAILED 被后续成功降级（需要版本号/终态仲裁）。

### #6 上报失败后 shard 永久泄漏进 running_shards_ 🟠

**涉及文件**：`transcode_worker.cpp:448-456, 654-660`、`RunHeartbeatLoop:849-957`

#### 现象

`ReportShardResult` 3 次重试全失败时 FfmpegExecute/MockExecute 直接 return 不调 `CleanupShard`。注释声称「心跳恢复」——`RunHeartbeatLoop` 只发心跳，**从不重报结果**。

#### 后果

ResultCollector 宕机 10-30s 期间完成的 shard：结果永久丢失，`RunningShardCount` 恒涨 → 达 `max_running_shards` 后 Worker 拒绝一切新分配；Worker 心跳仍活 → WM 不救援；Scheduler 侧 shard 永久 RUNNING → job 无限挂起。`max_running_shards=2` 时两次即永久楔死 Worker。

#### 修复建议

实现 at-least-once 上报：未确认的 shard 结果由心跳循环携带重报（RC 端已幂等，见 #8 的修复），成功后 `CleanupShard`。

### #7 Merge 无互斥：并发/重复 merge 毁掉成品视频 🟠

**涉及文件**：`result_collector.cpp:394-491`

#### 现象

`MarkJobTerminal` 的 Merge 块完全在单调性守卫之外、无 mutex/原子标志。最后两个 shard 并发报 SUCCESS（work_threads=2）→ 双线程都过 CheckJobDone → 两次 Merge 交错写共享的 `filelist.txt` 与同一 `merged.mp4`（-y 互截）；重复/迟到 SUCCESS 上报（:183 幂等路径）再触发 Merge 时 shard 文件已被 `std::remove` 删除，-y 先把成品截 0 字节再失败。

#### 后果

合并视频损坏或缺失，job 已是 SUCCESS 无重试，仅 WARN。`filelist.txt` 固定命名且跨 job 共享（`ffmpeg_executor.cpp:597`）加剧交错。

#### 修复建议

① `MarkJobTerminal` 加「终态已处理」原子标志/互斥，保证 merge 恰好执行一次；② filelist 用含 job_id 的唯一名；③ merge 失败不应保持 SUCCESS（或提供重试入口）。

### #8 重复 FAILED 上报双倍消耗重试预算 🟠

**涉及文件**：`result_collector.cpp:162, 176, 197, 213`、`scheduler_service.cpp:342-375`

#### 现象

stale 检查只拒绝严格更旧的 retry（`incoming_retry < stored_retry`），step-3 守卫只短路 SHARD_SUCCESS。同一 attempt 的重复 FAILED（worker 3 次重试、响应丢失场景）会再持久化 FAILED 并再次调 RescheduleShard——后者无状态守卫，无条件 `retry_count++`、清空 `assigned_worker_id`（即使该 shard 已被重新分配给新 Worker 执行中）。

#### 后果

一次真实失败消耗 2 次 retry；`max_retry=3` 时两次响应丢失即耗尽预算 → 提前 SHARD_FAILED/JOB_FAILED；清空已执行中的分配 → 同一 shard 双执行。

#### 修复建议

① FAILED 上报也做 attempt 幂等（记录已处理过的 attempt_id）；② RescheduleShard 增加状态守卫（仅 `SHARD_FAILED`/`SHARD_RETRYING` 可重排，`SHARD_WAITING`/`SHARD_RUNNING` 直接拒绝）；③ 把 retry_count 作为显式 proto 字段透传（见 #26），替代字符串解析。

## 四、任务卡死（无超时 / 无兜底）

### #9 子进程卡死时 cancel 永不触发 🟠

**涉及文件**：`ffmpeg_executor.cpp:153-199`

#### 现象

`ExecuteCommand` 只在 `fgets` 读循环内轮询 `should_cancel`，无执行超时。ffmpeg 挂死（慢/不可用输入、编解码器死锁）不再输出时，`fgets` 永久阻塞，kill(SIGTERM→SIGKILL) 永不触发。

#### 后果

CancelShard 无效；心跳线程独立存活 → WM 不触发 NotifyWorkerOffline；Scheduler 无 RUNNING 超时扫描 → shard 与 job 永久非终态，且无任何机制可恢复。

#### 修复建议

读循环改 `poll()` 带超时（如 1s），超时即检查 should_cancel 与总执行时长上限；cancel 或超时后 `kill(pid, SIGKILL)` 兜底。

### #10 CheckJobDone 依赖 QueryJob，JobService 宕机即永久挂起 🟠

**涉及文件**：`result_collector.cpp:315-361`

#### 现象

`expected_shard_count` 靠 3 次 QueryJob RPC（各 3s 超时，约 9s 窗口）学习，查询失败即 `return false` 且不记任何待复查状态；ResultCollector 无后台 sweep 线程，`CheckJobDone` 仅由新上报触发。

#### 后果

最后一次上报恰逢 JobService 不可用时，job 永久停在非终态，无任何后续事件再触发判定。

#### 修复建议

① shard_count 在调度时随 AssignShard/NotifyJobServiceStatus 推给 RC，不依赖查询；② RC 增加周期终态扫描线程（结合 #5 的「待重排」标记一并处理）。

### #11 NotifyWorkerOffline 丢失即孤儿，注释声称的重试不存在 🟠

**涉及文件**：`worker_manager.cpp:163-232`、`common_store.cpp:303-317`

#### 现象

`MarkOfflineIfTimeout` 在 RPC 之前已把 worker 置 OFFLINE，而它只对 ONLINE 生效——注释「下一轮会再次检测并重试通知」不成立，RPC 失败后仅 LOG_WARN 无任何重试路径。

#### 后果

Scheduler 重启/瞬时不可用时一次丢失的通知 → 该 worker 的 ASSIGNED/RUNNING shard 在 Scheduler 中永久滞留（运行期无重扫），job 无限挂起。

#### 修复建议

WM 对 OFFLINE 但「通知未确认」的 worker 持续重试 NotifyWorkerOffline，直到成功；或 WM 定期全量广播 worker 状态。

### #12 心跳抖动触发虚假重调度与双执行 🟠

**涉及文件**：`worker_manager.cpp:170-235`、`scheduler_service.cpp:391-450`

#### 现象

心跳超时（10s，无宽限）把网络抖动当执行失败：`NotifyWorkerOffline` 对该 worker 所有 RUNNING shard `retry_count++` 置 WAITING 重分配，**且不向旧 Worker 发 CancelShard**——原 Worker 继续转码。

#### 后果

同一 shard 双份执行（2x CPU/ffmpeg 成本）；重试预算被连接抖动消耗，3 次抖动即误判 JOB_FAILED。

#### 修复建议

① 超时判定加宽限/分级（如连续 2 个周期未心跳才 OFFLINE）；② 重分配前先向旧 Worker 发 CancelShard；③ 双执行由 RC 的 attempt 校验兜底（与 #14/#16 协同）。

### #13 被取消 job 的 shard 继续执行 🟠

**涉及文件**：`scheduler_service.cpp:461-626, 893-978`、`job_service.cpp:289-297`

#### 现象

`CancelJobShards` 明确「不修改本地 shard 状态」，取消标记只存在于 JobService 进程内 store；SchedulingLoop 分配 WAITING shard 前不查 job 状态（Scheduler 的 JobStore 副本也从未同步取消状态）。

#### 后果

取消后 job 的 WAITING shard 照常分配执行到完成，RC 照常合并产出成品——纯浪费计算、三进程状态发散；被杀的 RUNNING shard 无上报成为僵尸，若该 Worker 随后超时，NotifyWorkerOffline 还会把它重新执行。用户可见状态靠枚举大小（CANCELED=8 > SUCCESS=6）掩盖。

#### 修复建议

① Scheduler 侧记录 job 取消状态（JobRecord 增加 canceled 字段，CancelJobShards 置位）；② SchedulingLoop 分配前检查；③ CancelJobShards 对 WAITING shard 一并置 SHARD_CANCELED。

### #14 ScheduleJob 重复调用产生超 EOF shard 🟠

**涉及文件**：`scheduler_service.cpp:94-221`、`job_service.cpp:107-143`

#### 现象

`job_exists` 分支（注释明确是「JobService 重试」场景）不早退：继续重新 ffprobe、重新切分、覆盖 RUNNING 中的 job 状态。第二次探测瞬时失败时回退 `job_duration_fallback_sec=60`，30s 视频 2 shard 变 4 shard。

#### 后果

超 EOF 的 shard（如 `-ss 45` 对 30s 视频）被分配执行：ffmpeg 退出码 0 但输出空文件（FfmpegExecute 无输出校验）→ 合并出损坏成品；或失败重试耗尽 → 整个 JOB_FAILED，真实工作早已成功。

#### 修复建议

① `job_exists` 分支幂等早退（已切分则直接返回现有计划）；② 探测结果缓存进 JobRecord（`duration_sec` 字段已存在）；③ FfmpegExecute 校验输出文件非空（参照 Slice 的 :442 已有先例）。

### #15 /proc/stat 主机级 CPU 使资源感知反向工作 🟠

**涉及文件**：`transcode_worker.cpp:749-800, 153-165`、`scheduler_service.cpp:909-910`

#### 现象

`CollectCpuUsage` 读 `/proc/stat` 第一行 = 主机全核 CPU，非本进程 CPU（进程级应读 `/proc/self/stat`）；该值同时驱动 Worker 过载门（cpu>90 拒收）与 Scheduler 评分（`slots*10 - cpu*0.5`）。本仓库正是单机多 Worker 部署（9004/9010/9011 三份 conf）。另 thread_local 采样器每线程首次调用返回 0，门控对首分配不生效。

#### 后果

一个繁忙的邻居 Worker 让同机空闲 Worker 也报 cpu>90 → 拒收全部新任务；Scheduler 把最忙的 Worker 排最高分——阶段 7 的资源感知特性在真实部署中反向工作。`CollectMemUsage`（/proc/meminfo）同病。

#### 修复建议

改读 `/proc/self/stat`（进程 CPU）与 cgroup 内存（`/sys/fs/cgroup/.../memory.current`）；采样状态从 thread_local 提为全局互斥保护，消除首调 0。

#### #4 FFmpeg 命令注入 → fork+execvp 直接传 argv ✅

**文件**：`ffmpeg_executor.h` + `ffmpeg_executor.cpp`（全线重构）
