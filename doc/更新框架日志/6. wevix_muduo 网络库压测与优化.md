## 二、核心结论

**wevix_muduo 网络库在调优后达到百万 QPS 级别：**

- **峰值吞吐：106.7 万 QPS**（1000 连接 × 64B 小包）
- **持续吞吐：103.6 万 QPS**（500 连接 × 30 秒长跑，3,145 万条消息零失败）
- **低延迟：P50 76µs**（百连接千消息场景）
- **高并发：1000 连接零失败**，同时处理 500 万条消息
- **大消息：1MB echo P50 816µs**

## 四、Bug 分析与修复

### Bug 1：`listen()` backlog = 128 → Accept 队列溢出

**代码位置：** `wevix_muduo/include/wevix_muduo/Socket.h:40`

```cpp
// 修复前
void listen(int backlog = 128);
// 修复后
void listen(int backlog = 4096);
```

**原理：**

Linux 内核维护 Accept Queue（全连接队列）。`listen(fd, backlog)` 设置其上限。队列满时，内核直接**丢弃**新到达的 SYN/ACK 包，客户端触发 TCP 超时重传（RTO 指数退避 1s → 2s → 4s → 8s）。

```
t=0ms:    前 128 个连接进入 Accept Queue ✓
t=1ms:    队列满！第 129+ 个 SYN 被内核丢弃 ✗
t=1~3s:   内核超时重传，客户端卡在 connect() 无法发送数据
t=12s:    最后一个连接建立完成
```

**与传统 muduo 对比：** muduo 通过 `TcpServer::Option` 暴露 backlog，用户显式设置 ≥1024。wevix_muduo 未暴露该参数，内部硬编码 128。

### Bug 2：Acceptor 每次只 accept 一个连接

**代码位置：** `wevix_muduo/src/Acceptor.cpp:37`

```cpp
// 修复前：每次 epoll 事件只 accept 一次
void Acceptor::handleRead() {
    int connFd = serverSock_.accept(clientAddr);
    if (connFd >= 0) { ... }
}

// 修复后：循环 accept 直到 Accept Queue 为空
void Acceptor::handleRead() {
    while (true) {
        int connFd = serverSock_.accept(clientAddr);
        if (connFd >= 0) { ... }
        else { if (errno == EAGAIN) break; ... }
    }
}
```

**原理：** wevix_muduo 的 accept Channel 使用 LT 模式，单次 accept 不会丢连接（epoll 持续返回可读）。但 500 连接 = 500 次 event loop 迭代（epoll_wait → 分发 → 创建 Connection → 处理该连接的首批数据）。循环 accept 将 500 次迭代压缩为 1 次。

**与传统 muduo 对比：** muduo 同样每次只 accept 一个。wevix_muduo 的 accept-loop 是超越原版的主动优化。

### Bug 3：`kMaxEvents = 100` → epoll 事件饥饿

**代码位置：** `wevix_muduo/include/wevix_muduo/Epoll.h:33`

```cpp
// 修复前
static const int kMaxEvents = 100;
// 修复后
static const int kMaxEvents = 4096;
```

**原理：** 每个 IO 线程的 `epoll_wait` 每次最多返回 kMaxEvents 个就绪 fd。500 连接 ÷ 4 线程 = 125 连接/线程，kMaxEvents=100 → 25 个连接被**持续饿死**：

```
ET 模式下 IO 线程事件循环:
  epoll_wait(100 events) → 处理 → 这 100 个 client 收 echo 后立即发下一条
  epoll_wait(100 events) → 还是这 100 个！→ 第 101~125 号永远轮不到
  ...循环 20 轮，前 100 个发完全部消息（~5ms，P50=253µs×20 轮）...
  epoll_wait 终于看到第 101~125 号 → 它们被饿了几毫秒
```

**与传统 muduo 对比（关键差异）：** muduo 使用 `std::vector<epoll_event>` **动态扩容**：

```cpp
// muduo/net/poller/EPollPoller.cc
EventList events_(16);  // 初始 16
// 满载时自动翻倍: 16 → 32 → 64 → 128 → 256 ...
if (numEvents == events_.size())
    events_.resize(events_.size() * 2);
```

wevix_muduo 使用固定 C 数组 `events_[kMaxEvents]`，这是架构层面的差异。扩大到 4096 是必要修复，但根本上应改为 vector 动态扩容。

---

### 根因归因：到底哪个是元凶？

三个 Bug 都参与了性能崩塌，但**根因只有一个**。下面是逐条排除分析。

#### 反证法：只修一个，留另外两个

| 假设场景 | 预估结果 | 结论 |
|---------|---------|------|
| **只修 Bug1**（backlog→4096），留 Bug2+Bug3 | 500 连接瞬间全部入 Accept Queue，无 SYN 丢弃。Bug2 让 accept 慢但 LT 模式不丢连接。Bug3 造成 25 conn/线程饥饿 ≈ 5ms 延迟。**总耗时降至几十毫秒，QPS 恢复到几十万** | ✅ 断崖消失 |
| 只修 Bug2（accept-loop），留 Bug1+Bug3 | accept 快了，但 backlog=128 仍然是瓶颈。372 个 SYN 被丢弃，TCP 重传指数退避。**总耗时依然是 12 秒** | ❌ 断崖依旧 |
| 只修 Bug3（kMaxEvents→4096），留 Bug1+Bug2 | epoll 不再饥饿，所有 fd 公平调度。但 backlog=128 仍然是瓶颈，372 个连接照样等 TCP 重传。**总耗时依然是 12 秒** | ❌ 断崖依旧 |

#### 从数据反推

```
QPS = 总消息数 / 总耗时 = 10,000 / 12.095s ≈ 827 msg/s
```

QPS 825 不是消息处理慢造成的——P50 = 253µs 证明处理本身正常。**QPS 是被 12 秒的总耗时拉低的**。所以问题不是"消息处理慢"，而是"总耗时为什么是 12 秒"。

#### 12 秒的延迟源只能来自 Bug1

- **Bug1（backlog=128）**：372 个 SYN 被丢弃 → TCP 重传指数退避（1s → 2s → 4s → 8s）→ 最后一批连接在 ~8-12s 才建立 → **12 秒延迟源 ✓**
- **Bug2（单次 accept）**：LT 模式，每次 epoll 迭代多花几微秒 → 不会产生秒级延迟
- **Bug3（kMaxEvents=100）**：125 conn/线程中 25 个饥饿，等待 100 个发完 20 条消息。P50=253µs × 20 轮 = **~5ms 延迟**，不是 12 秒

注意：Bug 3 原描述中"它们已经等了 ~12 秒"是不准确的——那 12 秒是整个测试的总耗时，根源在 Bug1。Bug3 造成的饥饿延迟是毫秒级。

#### 结论

```
Bug1 (backlog=128)     ← ★ 根因。制造了 12 秒的连接建立延迟
Bug2 (单次 accept)      ← 放大器。让消化积压队列更慢，但不制造新延迟源
Bug3 (kMaxEvents=100)  ← 并发 Bug。造成毫秒级饥饿抖动，但不是断崖的元凶
```

**验证逻辑**：500 并发下，backlog=128 意味着 74.4% 的连接（372/500）在第一轮 SYN 就被内核丢弃。这些连接全部依赖 TCP 重传恢复，RTO 指数退避直接决定了 12 秒的总耗时。另外两个修复是重要的性能优化，但**如果不修 Bug1，另外两个修了也是白修**。

**修复详情：**

1. **Epoll vector 动态扩容** — 初始 16，epoll_wait 返回数等于容量时翻倍：
   ```cpp
   // Epoll.h — 固定数组 → vector
   std::vector<struct epoll_event> events_;  // 初始 kInitEventListSize=16

   // Epoll.cpp — poll() 中检测扩容
   if (numEvents == static_cast<int>(events_.size()))
       events_.resize(events_.size() * 2);
   ```

2. **TcpServer 暴露 backlog** — 调用链 `TcpServer → Acceptor → Socket::listen(backlog)`：
   ```cpp
   // TcpServer.h — 构造函数新增参数
   TcpServer(const std::string& ip, uint16_t port, int threadNum = 3, int backlog = 4096);

   // Acceptor.h — 透传 backlog
   Acceptor(EventLoop* loop, const std::string& ip, uint16_t port, int backlog = 4096);
   ```
   向后兼容：已有调用点（`rpcprovider.cc`、`echo_server.cpp`）无需修改。

### 三个修复总结

```cpp
// 1. Socket.h:40   — listen backlog 128 → 4096
void listen(int backlog = 4096);

// 2. Acceptor.cpp:37 — 单次 accept → while(EAGAIN)
while (true) { fd = accept(); if (fd<0 && errno==EAGAIN) break; ... }

```

**wevix_muduo 网络库核心架构正确，参数调优后达到单机百万 QPS。** 1000 并发连接、3,145 万条持续消息、零失败——三个 Bug 均为配置参数偏小，与库架构无关。
