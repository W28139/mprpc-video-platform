## 1. 服务端消费 `deadline_ms`

### 修改位置

- `mprpc/src/rpcprovider.cc`

### 改动

`RpcProvider::OnMessage()` 在解码 `RpcHeader` 后、进入业务分发前，新增 deadline 检查：

```cpp
if (rpcHeader.deadline_ms() > 0)
{
    uint64_t nowMs = std::chrono::duration_cast<std::chrono::milliseconds>(
        std::chrono::system_clock::now().time_since_epoch()).count();
    if (nowMs > rpcHeader.deadline_ms())
    {
        SendRpcError(conn, requestId, mprpc::RPC_TIMEOUT,
                    "request deadline exceeded before processing");
        return;
    }
}
```

逻辑：
- `deadline_ms == 0` → 客户端未设置，不检查
- `nowMs > deadline_ms` → 请求已过期，直接回 `RPC_TIMEOUT`，不进入 work pool

同时新增了 `#include <chrono>`。

### 作用

`RpcHeader.deadline_ms` 之前客户端就已经在填充（`mprpcchannel.cc` 中 `NowMs() + timeoutMs`），但服务端从来没读。现在服务端在收到请求的第一时间检查是否过期：

- 请求在 work pool 里排了长队 → 排到时已经超时 → 直接丢弃，不做无效计算
- 客户端不用干等到 socket 超时，服务端主动告知"你来晚了"

这对于后面视频转码这种长耗时场景尤其重要：一个转码任务可能排队 30 秒，如果客户端超时只有 10 秒，服务端不该白算。

## 2. 服务对象所有权明确化

### 修改位置

- `mprpc/include/rpcprovider.h`

### 改动

`NotifyService` 的注释从一句话改为明确的契约说明：

```cpp
// 发布 RPC 服务到 Provider。
// Provider 仅存储裸指针用于方法分发，不接管对象所有权，不会 delete service。
// 调用方必须保证 service 对象在 Provider 生命周期内一直有效。
// 典型用法：栈对象或全局对象，不要用 new 后把生命周期管理丢给 Provider。
void NotifyService(google::protobuf::Service *service);
```

### 作用

之前 `NotifyService(new Service())` 这种调用方式让人困惑：这 `new` 出来的对象谁来 `delete`？框架内部只存裸指针，从不释放。加上注释后：

- 调用方明确知道 Provider 不管 delete
- 不会写出"new 完就不管了等着框架删"的内存泄漏代码
- 推荐用栈/全局对象，跟 Provider 同生命周期

## 3. `done` 闭包调用规范

### 修改位置

- `mprpc/include/rpcprovider.h`

### 改动

`OnMessage` 的注释增加了 done 闭包的调用契约：

```cpp
// done 闭包调用规范：
//   框架将 done 闭包绑定到 SendRpcResponse，统一负责序列化业务响应并发送回包。
//   - 同步方法：protobuf 生成的默认 CallMethod 在返回前自动调用 done->Run()，
//     框架无需额外处理，响应在 CallMethod 返回时已发出。
//   - 异步方法：业务覆写 CallMethod 后，必须在异步操作完成时手动调用
//     done->Run()。漏调会导致请求永久悬挂，客户端一直等到超时。
```

### 作用

这是最容易被忽视的坑：

- 同步业务方法：框架跑得好好的，开发者感受不到 done 的存在
- 异步业务方法：开发者覆写 `CallMethod`，把 done 存起来，然后……忘了调 `done->Run()`

结果就是：客户端超时报错、服务端静默悬挂、没有任何日志告诉你"你忘了调 done"。这个注释让开发者在写异步 Service 时第一眼就能看到这个约束。

## 4. `RpcProvider::Run()` 返回 bool

### 修改位置

- `mprpc/include/rpcprovider.h`
- `mprpc/src/rpcprovider.cc`
- `test/rpc_echo_server.cpp`
- `example/callee/userservice.cc`
- `example/callee/friendservice.cc`

### 改动

`Run()` 从 `void` 改为 `bool`：

- 声明：`bool Run();`，注释说明 true = 正常进入事件循环，false = 启动失败
- 实现：所有早期 return（配置缺失、ZK 连接失败、注册失败）改为 `return false`；`server.start()` 正常返回后 `return true`
- 调用方：三个 main 函数都加了返回值检查，失败时 `LOG_ERROR` + `return EXIT_FAILURE`

### 作用

之前 `Run()` 返回 void，配置错误或 ZK 连接失败时直接 return，调用方无法区分"服务正在运行"和"启动失败已退出"。视频平台第一个阶段就要建多个服务（JobService / WorkerManager / Scheduler / Worker），如果启动脚本以为所有服务都起来了而实际有静默失败的，排查会很痛苦。

## 初始框架完结总结

经过 log 3 ~ log 10 共 8 轮迭代，mprpc 基础框架从"能跑"变成了"可复用"：

| 维度 | 状态 |
|------|------|
| 协议帧 | magic/version + 网络字节序 + 帧大小上限 + deadline_ms |
| 错误语义 | 15 种 `RpcErrorCode`，双向结构化错误回传，服务端坏包也回包 |
| 服务发现 | ZK 临时顺序节点 + `GetChildren` 多实例 + 本地轮询 |
| 客户端缓存 | ServiceCache → SharedZkClient → ConnectionPool 三层 |
| 连接复用 | endpoint 连接池，长连接复用，失败自动重试 + 重新发现 |
| 服务端并发 | IO 线程 + work pool 分离，业务不阻塞网络 |
| 框架初始化 | `Init()` 返回 bool，不再强制 `exit()` |
| 配置读取 | `LoadRequired` / `LoadInt` / `HasKey`，防隐式空值 |
| 防御性 | 服务端主动拒绝过期请求 |
| 契约明确 | 服务对象所有权、done 调用规范文档化 |

## 框架剩余问题与优化方向

核心原则：

> 先开始视频平台业务。业务遇到真实需求时，再把对应 RPC 能力补成通用框架能力。

### 一、随视频平台业务阶段补（业务暴露 → 框架沉淀）

这部分不到具体业务阶段不要提前做，否则就是无靶子射箭：

| 业务阶段 | 暴露的问题 | 对应补 RPC | 复杂度 |
|---------|-----------|-----------|--------|
| Worker 注册/心跳 | Worker 进程活着但业务卡死 | **健康检查**：独立的 `HealthCheck` RPC 或 TCP 层面的探活 | 中 |
| Worker 注册/心跳 | ZK 临时节点因网络抖动误删 | **ZK session expired 自动重注册**：`global_watcher` 中监听 `ZOO_EXPIRED_SESSION_STATE`，触发重连 + 重注册 | 中 |
| 多 Worker 并行调度 | 某些 Worker 负载过高，轮询不够 | **metadata / 权重 / 标签**：Provider 注册时附带 `cpu_cores`/`gpu`/`load` 等，客户端根据标签选择 | 中 |
| mock 高并发进度上报 | 调用量变大，框架行为不可观测 | **metrics**：请求计数、延时直方图、错误率，至少能导出到日志。`trace_id` 字段已在 proto 预留，届时填充即可 | 中 |
| Worker 宕机恢复 | 缓存里的旧地址在被踢掉前反复失败 | **ZK Children Watch + TTL**（Cache Staleness 修复，详见 `doc/zookeeper缓存系统.md` 第七章） | ~80 行 |
| 大量 Worker 并发执行 | work pool 队列无限堆积 | **work queue 上限 + 过载保护**：队列满时返回 `RPC_OVERLOADED` 而非无限排队 | 中 |
| 大量 Worker 并发执行 | `epoll_wait` 事件饥饿 | **kMaxEvents 已改为 vector 动态扩容**（`wevix_muduo` 已修复），暂无风险 | — |
| ResultCollector 重复上报 | 网络超时后客户端重试，服务端执行了两次 | **幂等性**：`request_id` 已有，业务侧加 `attempt_id`，服务端按 `attempt_id` 去重 | 业务侧 |
| Scheduler 并发调度多 Worker | 同步 RPC 逐个调 Worker 太慢 | **async/future RPC**：`CallMethod` 返回 future，Scheduler 一次性向 N 个 Worker 发 shard 再 gather 结果 | 大 |

### 二、业务闭环跑通后再做（需要真实数据支撑）

| 条目 | 为什么现在不做 |
|------|--------------|
| **完整 tracing**（`trace_id` 跨进程透传 + 采集） | 现在调用链深度 = 1（Client → 单一 Provider），trace 价值为零。等服务数 ≥ 3 且出过跨服务排查困难时再补 |
| **完整熔断 / 限流** | 需要先知道正常 QPS 基线是多少，否则熔断阈值全靠猜 |
| **完整 metadata / 权重负载均衡** | 需要先知道"轮询不够"的具体数据（哪个 Worker 被压垮了，为什么） |
| **命名空间整理**（`mprpc` → `wevix::rpc` 之类） | 纯重构，不影响功能，最后统一做 |

### 三、其他设计决策

| 决策 | 结论 | 理由 |
|------|------|------|
| 连接池是否独立成 `.h/.cpp` | 现在不拆 | 当前只有一个消费者（`mprpcchannel.cc`），拆出去增加文件但不减少耦合。等有第二个消费者（如健康检查直连 Worker）或需要独立单测时再拆 |

## 框架审查：面向视频转码平台的额外缺口

这一轮通读了框架全部核心代码后，结合视频转码平台的实际场景（长任务、多 Worker、高并发进度上报），发现以下几个在已有文档中未被充分覆盖或完全遗漏的缺口。它们不是现在就要修的，但值得在进入业务前记录清楚，避免踩坑时一脸懵。

### 1. RpcProvider 没有优雅关闭

**现状：** `RpcProvider::Run()` 里调用 `server.start()` 后进入阻塞事件循环。`TcpServer` 有 `stop()` 方法，但 `RpcProvider` 没有暴露任何 shutdown 机制。进程收到 SIGTERM 时直接被杀，无法：
- 通知 ZK 摘掉自己的临时节点（而不是等 session timeout 30s）
- 等待正在执行的任务完成（drain in-flight）
- 拒绝新请求

**视频平台影响：** Worker 可能正在执行一个 3 分钟的转码分片，收到 SIGTERM 后分片直接丢失，Scheduler 需要等超时才知道 Worker 已死，然后重新分发给其他 Worker——这 3 分钟白算。更糟的是，如果 kill 的时机刚好在 FFmpeg 写输出文件的过程中，文件可能损坏。

**建议修法：** 给 `RpcProvider` 加 `Shutdown()` 方法：① 摘 ZK 节点 ② 拒绝新请求（返回 `RPC_UNAVAILABLE`）③ 设置 drain 超时等待 in-flight 完成 ④ 调 `server.stop()`。约 40 行。

**建议时机：** Worker 进程管理阶段（注册/心跳之后、mock 调度闭环之前）。

### 2. ZK GetData 128 字节硬限制

**现状：** `ZkClient::GetData()` 里 `char buffer[128]` 硬编码。超过 128 字节的数据会被 ZK C SDK 截断，函数静默返回截断后的内容，调用方完全不知道。

**视频平台影响：** 后续要给 Worker 注册加 metadata（GPU 型号 `"NVIDIA GeForce RTX 4090"`、支持的编码器列表 `"h264_nvenc,hevc_nvenc"`、当前负载等），JSON 序列化后轻松超过 128 字节。截断后调度器的标签匹配失效，但排查时会发现 ZK 上显示的 metadata "看起来也对"——因为前 128 字节恰好是合法的 JSON 前缀。

**建议修法：** 先 `stat` 取数据长度，再按需分配缓冲区。或者直接把 buffer 改成 4096，对 ZK 节点数据来说足够（ZK 默认单节点数据上限 1MB，但 RPC 注册信息远不到 4KB）。约 10 行。

**建议时机：** metadata / 权重 / 标签负载均衡阶段，和 ZK session expired 一起改。

### 3. 客户端连接池无空闲回收 + 缺少 TCP keepalive

**现状：**
- `PooledConnection` 没有最后使用时间戳，连接一旦创建就永不关闭。如果 Worker 因网络问题短暂下线，旧连接变成僵尸——下次 RPC 时才发现不可用，触发重试 + 重发现。虽然最终能恢复，但每次故障恢复都多付一次超时代价。
- `ConnectToEndpoint()` 没有设置 `SO_KEEPALIVE`。在 NAT/防火墙/负载均衡器后面，空闲长连接可能在几分钟后被中间设备静默断开，两端都无法感知。

**视频平台影响：** Worker 执行长任务时，Scheduler 和 Worker 之间的 RPC 调用频率低（可能几分钟一次心跳）。中间 NAT 超时（常见 300s）后连接失效，下次心跳 RPC 或 AssignShard 调用时才发现连接断了 → 超时 → 重试 → 延迟 5-10 秒。这会让调度延迟看起来不稳定。

**建议修法：** 
- 客户端 `ConnectToEndpoint` 加 `SO_KEEPALIVE` + `TCP_KEEPIDLE`/`TCP_KEEPINTVL`（约 5 行）
- 连接池加 idle timeout：`PooledConnection` 记录最后使用时间，取连接时如果超过阈值（如 300s）就关闭重建（约 15 行）

**建议时机：** 连接池独立 `.h/.cpp` 时一起做（目前只有一个消费者，不拆）。

### 4. RPC_OVERLOADED 错误码缺失

**现状：** 错误码枚举里有 `RPC_TIMEOUT` 但没有 `RPC_OVERLOADED`。`ThreadPool` 有 `setTaskQueMaxThreshold()` 接口，但 `RpcProvider::Run()` 从未调用过它。work pool 队列可以无限堆积。

**视频平台影响：** 视频平台 mock 高并发时，所有 Worker 同时向 ResultCollector 上报进度。如果 ResultCollector 的 work pool 处理不过来，队列无限增长 → 内存暴涨 → OOM Kill。正确的行为应该是：队列满 → 立刻返回 `RPC_OVERLOADED` → 客户端退避重试。

**建议修法：** proto 加 `RPC_OVERLOADED = 15`；`RpcProvider::Run()` 调 `setTaskQueMaxThreshold()` 并通过配置控制；`OnMessage` 中 dispatch 到 work pool 前检查队列是否满，满则直接返回过载错误。约 30 行。

**建议时机：** mock 高并发进度上报阶段（第一周 mock 闭环之后）。

### 5. 服务端返回 RPC_TIMEOUT 不会触发客户端换 endpoint

**现状：** `mprpcchannel.cc` 只在 CONNECT_FAILED / TIMEOUT / SEND_FAILED / RECV_FAILED 时换 endpoint 重试。但如果服务端主动返回 `RPC_TIMEOUT`（比如本文第 1 项收尾后，deadline 过期被拒绝），客户端不会换一个 Worker 重试，而是直接 `SetControllerFailed`。

**视频平台影响：** 调度器给 Worker-A 发 AssignShard，Worker-A 的 work pool 排队排到 deadline 过期 → 返回 RPC_TIMEOUT。此时 Worker-B 可能是空闲的，但调度器不会换 B 重试，直接把任务标记为失败。调度器的重试逻辑被迫上移到业务层。

**建议修法：** 在 `CallMethod` 的响应解析阶段，如果 `responseHeader.error_code() == RPC_TIMEOUT`，将其视为可重试错误，触发换 endpoint + 重发。约 10 行。

**建议时机：** Scheduler 并发调度多 Worker 阶段，或者第一次发现"明明有其他 Worker 空闲但调度器不用"的时候。
