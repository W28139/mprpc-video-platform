# 内存池集成到 my_muduo —— 完整记录

## 一、探索历程

这套内存池（ThreadCache → CentralCache → PageCache 三层架构）的集成经历了三个阶段：

1. **盲目接入**：按"哪里在 new 就优化哪里"的思路，给 `Channel` 和 `Connection` 加了类级 `operator new/delete`
2. **诚实验证**：发现 `Connection` 的 `make_shared` 绕过了类级 `operator new`（形同虚设），`Channel` 压测后对 E2E 性能无影响（±3%）
3. **找到方向**：真正的热点在消息路径的 STL 容器分配（每消息 4 次 string malloc）内存池的价值在上层（mprpc、消息队列、业务），不在 muduo 这层。

---

## 二、各组件接入状态

| 组件 | 接入方式 | 是否生效 | 说明 |
|------|---------|:---:|------|
| **Channel** | `operator new/delete` | ✅ | `new Channel(...)` 创建，走内存池 |
| **Connection** | `operator new/delete` | ❌ | `std::make_shared` 绕过类级 `operator new`（见第四节） |
| **EventLoop** | 无 | — | 线程数级别，低频，不需要 |
| **Epoll** | 无 | — | 同上 |
| **Buffer** | 无 | — | 内部 `std::vector<char>`，可用 `PoolAllocator` 替换但非热点（见 log3） |
| **ThreadPool** | 无 | — | 全程序 1~2 个，不需要 |
| **Acceptor / TcpServer** | N/A | — | 栈对象 |

**当前只有 Channel 真正在使用内存池。** 每个连接 1 个 Channel + 每个 EventLoop 2 个 Channel。`Connection.h` 中的 `operator new` 保留作为代码示例，但不生效也不影响性能。

## 三、真正的热点：消息路径的 STL 分配

Channel/Connection 是每连接创建一次的长生命周期对象，不是瓶颈。真正的分配热点在这里：

| 步骤 | 代码位置 | 操作 | 堆分配 |
|------|---------|------|:---:|
| ① | `Connection.cpp:61` | `inputBuffer_.retrieveAllAsString()` | 第 1 次 malloc |
| ② | `TcpServer.cpp:139` | `std::string msg = message` | 第 2 次 malloc |
| ③ | `TcpServer.cpp:143` | lambda 按值捕获 `msg` | 第 3 次 malloc |
| ④ | `TcpServer.cpp:145` | `std::string tmp = msg` | 第 4 次 malloc |

**一条 12 字节的消息被拷贝 4 次。** 4KB 消息体、每连接 10 条消息、1000 QPS → 每秒 160MB malloc/copy 流量。

优化分两步：
1. **优先消拷贝**：用 `move` 语义 + `shared_ptr<string>` 传递，4 次 malloc → 1 次，零 API 变更
2. **再换分配器**：要彻底让消息路径走内存池，需把 `std::string` 改为 `PoolString`，但这会破坏公开 API。PoolAllocator 更适合在上层服务中从头使用（详见 log3）

## 四、关键发现：`make_shared` 不调用类级 `operator new`

### 4.1 实测

```cpp
class Foo {
public:
    static void* operator new(size_t size) {
        printf("Foo::operator new(%zu)\n", size); return ::operator new(size);
    }
};
```

| 创建方式 | 调用 `Foo::operator new`？ |
|---------|:---:|
| `new Foo()` | ✅ |
| `std::make_unique<Foo>()` | ✅ |
| `std::shared_ptr<Foo>(new Foo())` | ✅（对象部分） |
| **`std::make_shared<Foo>()`** | **❌** |

### 4.2 原因

`make_shared` 一次性分配"控制块 + 对象"联合内存，用全局 `::operator new` 申请 `sizeof(control_block) + sizeof(T)` 字节，然后 placement-new 构造 T。类级 `operator new(sizeof(T))` 只能表达对象大小，无法传递"还需要控制块空间"的信息，所以 `make_shared` 不可能调用它——这是 C++ 标准行为，不是 bug。

### 4.3 结论

| 场景 | 推荐方案 |
|------|---------|
| `new T` / `make_unique` 创建 | 方案一（类内 `operator new`），零成本 |
| `make_shared` 创建且是热点 | 方案二（`std::allocate_shared` + 自定义 Allocator） |
| `make_shared` 创建但不是热点 | **不接入**，保持 `make_shared` |

本项目：Channel 用方案一（生效 ✅），Connection 用 `make_shared` 但不是热点（维持现状）。

## 五、压测：Channel 接入前后的实际效果

### 微基准（152 字节 = sizeof Channel）

| 场景 | Pool | Malloc |
|------|------|------|
| 单线程 P99 | **16 ns** | 23 ns |
| 多线程(4T) | 38.9M ops/s | **85.9M ops/s** |

单线程下 Pool 略优（1.4×），多线程下反而慢（CentralCache 自旋锁竞争）。**纳秒级差异在网络 syscall（微秒级）面前完全淹没。**

### Echo Server 端到端（500 连接 × 10 消息）

| 配置 | 耗时 | QPS | 差异 |
|------|------|------|:---:|
| 有内存池 | 1138 ms | 4392 msg/s | |
| 无内存池 | 1105 ms | 4523 msg/s | **±3%（噪声）** |

**结论：Channel 接入内存池对真实服务器性能无影响。** 大部分时延来自 TCP 握手和 epoll 调度，而非 152 字节的对象分配。`operator new` 保留作为代码示例即可。

## 七、总结

| 问题 | 答案 |
|------|------|
| 内存池现在有没有用？ | 只有 Channel 在用，但对性能无影响 |
| 为什么 muduo 用不上？ | muduo 的分配都在长生命周期对象或低频路径上，不在每秒百万次的热点 |
| 那内存池的价值在哪？ | 在上层——mprpc 序列化、消息队列、业务逻辑的密集 STL 容器分配 |
| 打通 STL 了吗？ | 已实现 `PoolAllocator`（log3），RPC 反序列化 3.8× 提升 |
| muduo 消息路径怎么优化？ | 先用 `move`/`shared_ptr` 消拷贝（4→1 malloc），PoolAllocator 留给上层 |
