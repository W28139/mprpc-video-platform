# 7. mprpc 压测问题定位与修复

## 日期

2026-07-24

## 背景

`wevix_muduo` 网络库单独压测时表现正常，长连接可达到较高 QPS，短连接也没有明显失败。但接入 `mprpc` 后，压测出现了几个现象：

- ZooKeeper 有大量终端输出
- ZK 模式 QPS 很低
- 短连接模式连接失败或响应失败
- 服务端日志量明显放大
- 后续检查日志时发现 `epoll_ctl add error, errno=17`

本次目标是检查 `mprpc` 和它依赖的 muduo 连接生命周期，区分是网络库问题、RPC 协议问题、ZooKeeper 使用问题还是压测方式问题。

## 问题 1：每次 RPC 都创建 ZooKeeper 会话

### 现象

ZK 模式压测时 ZooKeeper 日志刷屏，QPS 明显偏低。

### 根因

`MprpcChannel::CallMethod()` 每次 RPC 调用都在栈上创建 `ZkClient`、`Start()`（触发 `zookeeper_init` 创建 IO/Watcher 内部线程）、查数据、析构关闭。服务发现被放进了每次 RPC 的热路径。

### 修复：构建三层缓存体系

在 `mprpcchannel.cc` 中构建了三层结构，从近到远依次减少 ZK 访问：

| 层 | 组件 | 作用 |
|----|------|------|
| 第 1 层 | **ServiceCache** — 本地哈希缓存 | `method_path` → 实例列表 + 轮询下标。命中直接返回，不碰 ZK |
| 第 2 层 | **SharedZkClient** — 进程级单例 ZK 连接 | 进程生命周期内唯一 ZK 会话，`std::call_once` 保证只启动一次 |
| 第 3 层 | **ConnectionPool** — TCP 连接池 | `endpoint_key` → 长连接列表，每个 endpoint 最多 N 个连接轮询复用 |

**调用流程**：`GetHostData()` 先查缓存 → 命中则轮询返回一个 endpoint；未命中则通过 `SharedZkClient` 查 ZK（先查新多实例路径 `/mprpc/services/...`，再兜底旧单实例路径），结果写入缓存。

**失败重试**：TCP 连接失败（CONNECT_FAILED / TIMEOUT / SEND/RECV_FAILED）时，自动清掉连接池 + 缓存，重新查 ZK 拿最新实例列表，用新地址重试一次。

### 效果

ZK 模式不再每次创建 ZK 会话，短连接 500 并发 0 失败（62K QPS），长连接 84.7 万 QPS。

### 新问题：缓存时效性（Cache Staleness）

当前缓存失效是**纯被动式**的——只有 TCP 连接实际失败了才会触发 `InvalidateHostData()`。问题场景：

| ZK 变更 | 客户端行为 | 后果 |
|---------|-----------|------|
| 新 Provider 实例上线 | 缓存没有，不感知 | 负载不均 |
| Provider 实例下线 | 缓存仍有旧地址 | 每次都 TCP 超时后才重试 |
| Provider 地址变更 | 同上 | 同上 |

**根因**：`ZkClient::GetData()` / `GetChildren()` 调用 `zoo_get` / `zoo_get_children` 时 watcher 参数传了 `0`（不注册 ZK Watch），`ServiceCache` 也没有 TTL。

**修复方向**：查 ZK 时注册一次性 Children Watch，节点变化回调中清缓存；配合 TTL（如 30s）兜底。

详细设计见 `doc/zookeeper缓存系统.md`。

## 问题 2：ZK watcher context 存在竞态和悬挂指针风险

### 根因

原先 `ZkClient::Start()` 是：

```text
zookeeper_init(..., context=nullptr)
sem_init(&sem)
zoo_set_context(m_zhandle, &sem)
sem_wait(&sem)
```

这里有两个问题：

1. 连接事件可能早于 `zoo_set_context()` 到达，导致 watcher 拿不到 sem，`Start()` 永久阻塞。
2. `sem` 是栈变量，`Start()` 返回后 context 如果不清理，后续 watcher 事件可能访问悬挂指针。

### 修复

改为在 `zookeeper_init` 前创建 sem，并通过 context 参数传入：

```cpp
sem_t sem;
sem_init(&sem, 0, 0);
m_zhandle = zookeeper_init(connstr.c_str(), global_watcher, 30000, nullptr, &sem, 0);
```

连接成功后清空 context 并销毁 sem：

```cpp
zoo_set_context(m_zhandle, nullptr);
sem_destroy(&sem);
```

同时将 ZooKeeper C SDK 日志级别降为 ERROR：

```cpp
zoo_set_debug_level(ZOO_LOG_LEVEL_ERROR);
```

## 问题 3：RPC 客户端单次 send 可能发送不完整

### 根因

原先 `MprpcChannel` 发送请求时使用单次 `send()`。TCP 的 `send()` 不保证一次写完所有数据，尤其在大请求或发送缓冲区紧张时可能只写入部分数据。

### 修复

增加 `SendAll()`：

```cpp
bool SendAll(int fd, const char* data, size_t len, int& savedErrno)
```

循环发送直到全部写完或出现错误。

接收响应也统一为 `RecvAll()`，并增加响应最大帧限制：

```cpp
constexpr uint32_t kMaxRpcFrameSize = 64 * 1024 * 1024;
```

## 问题 4：短连接日志放大

### 现象

短连接压测时，每个请求都会创建和关闭 TCP 连接。如果连接建立、关闭都打 INFO 日志，日志系统会被短连接压测放大。

### 修复

将高频连接日志从 INFO 降为 DEBUG：

```text
RpcProvider::OnConnection
RpcProvider::OnClose
TcpServer::handleNewConnection
TcpServer::handleClose
Connection::handleClose
```

Release 构建下 `LOG_DEBUG` 会被裁剪，避免压测时日志进入热路径。

## 问题 5：accept 循环中的 EAGAIN 被误打成错误

### 现象

`Acceptor` 已经改成循环 accept，非阻塞 socket 最后一定会通过 `EAGAIN/EWOULDBLOCK` 表示 Accept Queue 已空。

原来的 `Socket::accept()` 在 `accept4()` 返回 -1 时直接 `LOG_ERROR`，所以正常的 `EAGAIN` 会被误认为错误并刷日志。

### 修复

`Socket::accept()` 只返回 fd，不负责打印错误。

`Acceptor::handleRead()` 统一分类：

```cpp
if (errno == EAGAIN || errno == EWOULDBLOCK)
    break;

LOG_WARN("Acceptor::handleRead accept failed, errno=%d", errno);
```

## 问题 6：新连接可能在回调和 codec 设置前被读事件抢跑

### 根因

原来 `Connection` 构造函数里会立即：

```text
channel_->useET();
channel_->enableReading();
```

但 `TcpServer::handleNewConnection()` 是在构造 Connection 后才设置：

```text
closeCallback
errorCallback
onMessageCallback
sendCompleteCallback
messageCodec
```

高并发短连接场景下，fd 可能先进入 epoll 并被 IO 线程读到，此时回调或 codec 还没设置好，可能造成请求丢失或错误处理。

### 修复

将读事件注册从构造函数中移出，新增：

```cpp
void Connection::connectEstablished();
```

`TcpServer::handleNewConnection()` 完成所有回调、codec 和连接表注册后，再调用：

```cpp
conn->connectEstablished();
```

这样新连接只有在框架状态完整后才开始接收读事件。

## 问题 7：短连接关闭后 Connection 没有立即从 EventLoop 连接表删除

### 根因

连接关闭时，`TcpServer::connections_` 会删除连接，但 `EventLoop::conns_` 仍保留 shared_ptr，用于定时器超时扫描。

结果：

```text
客户端已关闭
TcpServer 表删除
EventLoop 表仍持有 Connection
Socket fd 不能立刻析构关闭
直到定时器超时才释放
```

短连接高 QPS 下，这会造成短时间内大量关闭连接滞留。

### 修复

新增：

```cpp
void EventLoop::removeConnection(int fd);
```

在 `Connection::handleClose()` 和 `Connection::handleError()` 中立即删除：

```cpp
self->loop_->removeConnection(self->fd());
```

同时定时器超时改为调用 `Connection::forceClose()`，保证超时连接走统一关闭路径。

## 问题 8：ET 模式下 handleRead 没有读到 EAGAIN

### 根因

Connection 使用 ET 模式，理论上一次读事件触发后应该循环读取直到 `EAGAIN/EWOULDBLOCK`。

原先 `handleRead()` 只调用一次 `readFd()`，如果内核缓冲区还有数据，ET 模式下可能不会再次触发读事件。

### 修复

`Connection::handleRead()` 改为循环：

```cpp
while (true)
{
    ssize_t n = inputBuffer_.readFd(fd(), &savedErrno);
    if (n > 0) { totalRead += n; continue; }
    if (n == 0) { peerClosed = true; break; }
    if (savedErrno == EINTR) continue;
    if (savedErrno == EAGAIN || savedErrno == EWOULDBLOCK) break;
    handleError();
    return;
}
```

读取完成后再统一做 codec 解帧。

## 问题 9：EventLoop 线程 ID 记录错误导致 epoll EEXIST

### 现象

第一次修复后，压测功能结果已 0 失败，但检查日志发现：

```text
epoll_ctl add error, fd=xx, errno=17
```

`errno=17` 即 `EEXIST`，表示该 fd 已经被注册到 epoll 中，不能重复添加。

### 根因

#### 背景：`isInLoopThread()` 的作用

muduo 架构中每个 EventLoop 运行在独立 IO 线程。为保证线程安全，同一个 fd 的所有 epoll 操作（ADD / MOD / DEL）都必须在拥有它的 IO 线程中执行，通过 `isInLoopThread()` 判断调用是否在正确线程：

```cpp
bool isInLoopThread() { return threadId_ == getTid(); }
```

- 返回 `true`（IO 线程自己调用）→ 立即执行
- 返回 `false`（其他线程调用）→ 将任务排入 `pendingFunctors` 队列，由 IO 线程稍后串行执行

这就意味着：**`threadId_` 必须记录的是 IO 线程的真实 tid，否则所有线程调度判断全部失效。**

#### 错误：在构造函数中记录 threadId_

修复前的代码在 EventLoop 构造函数中记录 `threadId_`：

```cpp
threadId_(getTid())
```

但 subLoop 的构造和运行是在不同线程中：

| 阶段 | 执行线程 | `threadId_` 记录的 ID |
|------|---------|----------------------|
| 构造函数 `new EventLoop()` | 主线程 | **主线程的 tid** |
| 运行 `EventLoop::run()` | IO 子线程 | — |

subLoop 实际上运行在 IO 子线程，但 `threadId_` 存的是主线程的 tid。**身份错位**导致 `isInLoopThread()` 双向误判：

| 调用方 | 实际线程 | `isInLoopThread()` 判断 | 结果 |
|--------|---------|------------------------|------|
| 主线程调用 `runInLoop()` | 不是 IO 线程 | **误判为 true** | 任务被直接执行，绕过了队列 |
| IO 线程自身操作 | 是 IO 线程 | **误判为 false** | 本应同步执行的清理被排队延后 |

#### 如何导致 EEXIST

短连接压测下 fd 复用极快，误判触发的竞态链路：

```
1. 短连接断开，fd=10 的 Connection 被关闭
2. handleClose() → runInLoop() 在主线程被调用
3. isInLoopThread() 误判为 true → removeChannel() 直接在主线程执行
4. 操作系统快速回收 fd=10，并立即复用于新连接
5. 新连接的 Channel 被添加到 epoll → epoll_ctl(ADD, fd=10)
6. 但步骤 3 中的 epoll_ctl(DEL, fd=10) 尚未在 IO 线程执行
7. 内核发现 fd=10 仍在 epoll 中 → 返回 EEXIST

当 EventLoop::threadId_ 因在构造函数中记录而误设为主线程 ID 时，会引发严重的线程身份判定失效：本应在 IO 线程立即同步执行的连接销毁逻辑（包括从 epoll 中 DEL 描述符及析构 TcpConnection 以 close 描述符），会因 isInLoopThread() 误判为 false 而被迫通过 queueInLoop 进入异步任务队列排队等待。
在高并发短连接场景下，这种“异步延时”产生了一个致命的竞态窗口：IO 线程尚未处理完当前事件循环并执行队列中的 DEL 任务，内核可能已因 close 发生的极快（或连接半关闭状态）将该 FD 编号快速回收，并分配给了主线程刚刚 accept 到的新连接；
此时，由于主线程在调用 runInLoop 时误以为自己就是 IO 线程（身份反转），从而“抢跑”同步执行了新连接的 ADD 操作。这直接导致新旧连接在 epoll 红黑树中发生碰撞——旧的 FD 尚未移除，新的相同 FD 编号便已尝试加入，最终触发内核抛出 EEXIST 错误并导致新连接建立失败。通过将 threadId_ 的记录移至 EventLoop::loop() 中以确保其准确指向真实的运行线程，可以恢复单线程 Reactor 的线性时序，保证“先删旧、再加新”的严格逻辑顺序。
```

该问题出现条件：

- **条件 A：** 旧的 fd=10 必须**彻底关闭**（内核释放了该数字），这样内核才会在下一个 accept 时把 10 分配出来。
- **条件 B：** 逻辑上的 epoll_ctl(DEL, 10) 还没有完成（或者内核还没处理完这个指令）。
- **条件 C：** 新的连接**恰好**在那一万分之一秒内进来，并且**恰好**被分配到了 10。

核心矛盾：**fd 的删除和添加没有在同一个线程按顺序执行**。删除被误判为”已在正确线程”而绕过了 IO 线程的任务队列，导致删除与添加的时序无法保证。当 fd 被快速复用时，添加在删除之前到达内核。

### 修复

将 `threadId_` 的记录从构造函数移到 `EventLoop::run()` 中——即在 IO 线程真正开始运行后再记录：

```cpp
// EventLoop::run() — IO 线程入口
threadId_.store(getTid(), std::memory_order_relaxed);
```

`isInLoopThread()` 对应改为 atomic 读取：

```cpp
bool isInLoopThread() const
{
    return threadId_.load(std::memory_order_relaxed) == getTid();
}
```

修复后：
- 主线程调用 `runInLoop()` → 正确返回 false → 任务排队 → 由 IO 线程按顺序串行执行
- 所有 fd 操作（DEL → ADD）在同一个 IO 线程中顺序执行 → **先删旧，再加新**，竞态消除

### 效果

重新启动服务端并复测后，新增日志区间没有再出现 `epoll_ctl add errno=17`。

## 结论

本次问题主要不在 `wevix_muduo` 基础网络吞吐，而在 RPC 层和连接生命周期：

1. ZK 服务发现进入每次调用热路径，导致 ZK 输出和 QPS 下降。
2. 短连接关闭后连接对象滞留，影响短连接场景。
3. subLoop 线程 ID 记录错误，导致 `runInLoop()` 线程判断失效。
4. accept 循环中的正常 `EAGAIN` 被误打成错误。
5. 新连接读事件注册过早，有回调/codec 设置竞态。
6. RPC 客户端没有完整 send/recv。

修复后：

- direct 短连接 500 并发：0 失败
- ZK 模式 500 并发：0 失败
- direct 长连接 100 并发：约 84.7 万 QPS
- 新日志区间无 epoll EEXIST 错误

当前 `mprpc` 已经从 demo 可跑状态推进到可继续完善基础框架的状态。压测后原计划的 7 个基础能力中，6 个已经在代码中落地：

| 功能点 | 状态 | 关键实现 |
|--------|------|---------|
| RPC request_id | ✅ 已实现 | `RpcHeader.request_id` 生成 → 服务端回传 → 客户端校验匹配，完整闭环 |
| error_code/error_msg | ✅ 已实现 | 15 种 `RpcErrorCode` 枚举 + `RpcResponseHeader.error_code/error_msg` + `MprpcController` 结构化错误 |
| timeout/deadline | ✅ 已实现 | 客户端 `deadline_ms` 填充 + `SO_SNDTIMEO/SO_RCVTIMEO` + 非阻塞 connect 超时 + 超时后重试 |
| 客户端长连接池 | ✅ 已实现 | `PooledConnection` + 每 endpoint 最多 N 连接 + 轮询复用 + 失效清理 |
