```bash

mysql -uroot -p <<'EOF'

CREATE USER IF NOT EXISTS 'video_platform'@'%' IDENTIFIED BY 'video_platform123';

GRANT ALL PRIVILEGES ON video_platform.* TO 'video_platform'@'%';
```

## 〇、Docker 一键部署（阶段 13 推荐）

无需手工安装 ZooKeeper / MySQL / Redis / RabbitMQ / ffmpeg，一条命令拉起全环境（详见
`doc/更新业务日志/15. 阶段13容器化与CI-CD.md`）。

```bash
# 1. 安装 Docker（WSL2 下二选一）
#    Docker Desktop for Windows（启用 WSL2 集成），或
#    sudo apt install docker.io docker-compose-v2 && sudo usermod -aG docker $USER

# 2. 一键启动（首次构建镜像需几分钟）
cd /home/wevix/muduo_im
docker compose up -d --build

# 3. 检查状态
docker compose ps

# 4. 提交任务（容器内运行 job_client，交互输入用管道）
docker compose exec job_service sh -c 'printf "%s\n" "1001" "/data/videos/xxx.mp4" "/data/output" "mp4" "720p" "0" "0" "0" | ./bin/job_client -i /app/conf/job_client.conf'

# 5. 扩展 Worker（worker_id 由容器 hostname 自动生成，无需额外配置）
docker compose up -d --scale transcode_worker=3

# 6. 日志 / 停止（-v 删除 MySQL 数据卷）
docker compose logs -f scheduler_service
docker compose down -v
```

- **视频输入**：`data/videos/`（容器内 `/data/videos/`）；**转码产物**：`data/output/`（容器内 `/data/output/`）
- **服务日志**：`program_log/`；**监控指标**：`localhost:19091-19094/metrics`
- **端口映射**：本机手工部署占用标准端口，compose 默认用替代宿主端口
  （ZK 21810 / MySQL 23306 / Redis 63790 / RabbitMQ 56720 / 平台服务 19001-19005），
  容器内端口不变、集成测试走 `exec` 不受影响；宿主无占用时可改回标准端口
- **实测状态**：9 容器一键启动、全链路任务（提交→转码→合并→SUCCESS）、
  `--scale transcode_worker=3` 均已本机实测通过（2026-08-04）

```bash
cd /home/wevix/muduo_im

# 按依赖顺序启动
./bin/job_service       -i video_platform/conf/job_service.conf &

```

### 停止全部

```bash
pkill -9 -f "bin/job_service|bin/scheduler|bin/worker_manager|bin/transcode|bin/result_collector"
sleep 1
pgrep -f "bin/job_service|bin/scheduler|bin/worker_manager|bin/transcode|bin/result_collector" \
  && echo "还有残留！" || echo "已全部停止"
```

> ⚠️ 不要多次运行启动脚本，否则会同时存在多组进程，导致 ZK 注册冲突。

## 三、提交任务

### 准备测试视频

```bash
# 如果没有视频文件，用 ffmpeg 生成一个 30 秒测试视频
ffmpeg -y -f lavfi -i testsrc=duration=30:size=1280x720:rate=30 \

       -c:v libx264 -preset ultrafast -c:a aac -shortest \
       /tmp/test_video.mp4
```

### 管道提交（推荐）

```bash
printf 'test_user\n/home/wevix/muduo_im/path/test_video.mp4\n/home/wevix/muduo_im/path/temp_out\nmp4\n1080p\n2000\n0\n10\n' \
  | ./bin/job_client -i video_platform/conf/job_client.conf
```

输入顺序：`user_id → input_path → output_dir → format → resolution → bitrate → priority → shard_duration`

| 参数 | 示例值 | 说明 |
|------|--------|------|
| user_id | `test_user` | 用户标识 |
| input_path | `/tmp/test_video.mp4` | 输入视频路径 |
| output_dir | `/tmp/output` | 输出目录 |
| format | `mp4` / `mkv` / `flv` | 目标容器格式 |
| resolution | `720p` / `1080p` / `4k` | 目标分辨率 |
| bitrate | `2000` | 目标码率（kbps），0=保持原码率 |
| priority | `0` | 调度优先级，越大越优先 |
| shard_duration | `15` | 每 shard 时长（秒），0=默认 15s |

> **注意**：`resolution` 和 `bitrate` 由客户端提交后经 `JobInfo → ShardInfo → Worker` 全链路透传，Worker 不再从本地配置读取。每个 job 可使用不同的转码参数。


## 七、架构概览

```
Client/CLI ──SubmitJob──► JobService ──ScheduleJob──► SchedulerService
                                                           │
                                              ListWorkers  │  AssignShard
                                                           ▼
                              WorkerManager ◄──────── TranscodeWorker
                                    ▲                        │
                                    │                        │ ReportProgress
                                    └── Heartbeat            │ ReportResult
                                      {cpu, mem, running}    ▼
                                                     ResultCollector
                                                           │
                                                     JOB_SUCCESS → Merge → 完整视频

                     ┌────────────────────────────────────────────┐
                     │  MySQL（唯一数据源，阶段 9 起）                │
                     │  jobs / shards / workers 三张表             │
                     │  所有服务读写同一份数据，重启不丢失            │
                     └────────────────────────────────────────────┘
```

**5 个微服务职责**：

**5 个微服务职责**：

| 服务 | 职责 |
|------|------|
| **JobService** | 接收客户端提交的转码任务，管理 job 生命周期 |
| **SchedulerService** | ffprobe 探测视频 → 按时间切分 shard → 加权评分选择 Worker 分配 |
| **WorkerManager** | Worker 注册/心跳保活、心跳超时检测、故障 Worker 的 shard 重调度 |
| **TranscodeWorker** | 接收 shard → ffmpeg 转码（fork+exec，支持 cancel kill）→ 上报进度和结果 |
| **ResultCollector** | 收集 shard 结果 → 聚合 → 判定 JOB_SUCCESS/FAILED → Merge 输出完整视频 |

### TranscodeWorker（transcode_worker_9004.conf）

```ini
rpcserverip=127.0.0.1
rpcserverport=9004
zookeeperip=127.0.0.1
zookeeperport=2181
rpcserverio_threads=2
rpcserverwork_threads=2

worker_id=worker_001             # 全局唯一，多 Worker 时需各不相同
cpu_cores=4                      # 上报给调度器的 CPU 核心数
memory_mb=8192                   # 上报给调度器的内存（MB）

executor_mode=ffmpeg             # ffmpeg=真实转码 / mock=sleep 模拟
ffmpeg_work_dir=/tmp/transcode_worker  # FFmpeg 工作目录（切片/转码/截图/合并输出）

# 转码参数（resolution/bitrate）已改为 JobInfo → ShardInfo 透传
# 由客户端提交 job 时指定，不再从 Worker 本地配置读取。
```

### 调度参数（硬编码，后续可配置化）

| 参数 | 值 | 说明 |
|------|------|------|
| 调度间隔 | 2s | `SchedulingLoop` 扫描间隔 |
| 评分公式 | `slots×10 - cpu×0.5 - mem×0.2` | Worker 选择权重 |
| 心跳间隔 | 3s | Worker → WorkerManager |
| 心跳超时 | 10s | 超时标记 OFFLINE，触发 shard 重调度 |
| Metrics 间隔 | 10s | `[SchedulerMetrics]` 输出频率 |
| 过载阈值 | CPU > 90% 或 slots=0 | Worker 拒绝新 shard |

### 切回 Mock 模式

修改 Worker 配置：

```ini
executor_mode=mock
```

Mock 模式不依赖 ffmpeg，用 sleep 模拟执行，适合测试调度和容错逻辑。

## 九、多 Worker 并行与负载均衡

启动多个 Worker 实例：

```bash
./bin/transcode_worker -i video_platform/conf/transcode_worker_9004.conf &   # worker_001
./bin/transcode_worker -i video_platform/conf/transcode_worker_9010.conf &   # worker_002
./bin/transcode_worker -i video_platform/conf/transcode_worker_9011.conf &   # worker_003
```

**阶段 7 资源感知调度**会自动均衡负载：

1. Worker 心跳上报真实 CPU 使用率、内存使用率、运行中 shard 数
2. Scheduler 加权评分选择最优 Worker：`score = slots×10 - cpu×0.5 - mem×0.2`
3. 高负载 Worker 得分低 → 不再被分配新 shard
4. Worker 自身过载保护：`running >= max || cpu > 90%` → 拒绝新 shard
5. `[SchedulerMetrics]` 每 10 秒输出调度快照，可观察负载分布

```bash
# 观察调度效果
grep "SchedulerMetrics" program_log/$(date +%Y-%m-%d)-log.txt | tail -5
# [SchedulerMetrics] round=10 | queue=3 | running=4/8 | workers=3 | assigned=15
```

## 十、可用功能总览

### 核心转码链路

| 功能 | 说明 |
|------|------|
| **提交任务** | `job_client` 交互/管道，指定输入视频、输出目录、分辨率、码率、优先级 |
| **视频探测** | Scheduler 自动调 ffprobe 获取真实时长/分辨率/编码 |
| **Shard 切分** | 按 `shard_duration_sec` 将视频按时间切段，最后一个 shard 自适应剩余时长 |
| **加权调度** | `score = slots×10 - cpu×0.5 - mem×0.2`，按 Worker 负载择优分配 |
| **优先级队列** | shard 按 job.priority 降序 + FIFO 排列，高优先级 job 先分片 |
| **真实转码** | fork+exec 启动 ffmpeg（libx264+AAC），切片+转码一 pass 完成，帧精确 |
| **进度上报** | 实时解析 ffmpeg `out_time_ms=` 输出，RPC 上报 0-100% 进度 |
| **结果聚合** | ResultCollector 收集所有 shard 结果，判定 JOB_SUCCESS/FAILED |
| **视频合并** | JOB_SUCCESS 时自动 concat 所有 shard 输出 → `{job_id}_merged.mp4` |
| **自动截图** | 每个 shard 转码成功后截取视频中点帧 → `screenshot.jpg` |
| **任务取消** | CancelJobShards → 直连 Worker → fork+exec 子进程被 SIGTERM kill |
| **任务查询** | `job_client --query` 查看 job 状态、shard 进度；`--watch` 轮询监控 |

### 容错恢复

| 功能 | 说明 |
|------|------|
| **失败重试** | shard 执行失败 → RescheduleShard → retry_count++ → 重新分配，最多 3 次 |
| **Worker 故障恢复** | 心跳超时 10s → NotifyWorkerOffline → 该 Worker 的 RUNNING shard 重调度 |
| **Scheduler 崩溃恢复** | 重启后扫描残留 ASSIGNED/RUNNING shard → 重置为 WAITING（不增加 retry_count） |
| **幂等防护** | attempt_id 校验，拒绝旧 attempt 的过期结果 |
| **Worker 过载保护** | running>=max 或 cpu>90% → 拒绝新 shard，Scheduler 下一轮分配给其他 Worker |

### 可观测性

| 功能 | 说明 |
|------|------|
| **调度 Metrics** | `[SchedulerMetrics]` 每 10s 输出 queue/running/workers 快照 |
| **结构化日志** | 5 个服务统一日志格式，`grep` 按服务/事件筛选 |
| **Worker 负载上报** | 心跳携带 `/proc/stat` 真实 CPU + `/proc/meminfo` 真实内存使用率 |

## 十一、常见问题

### Q: 服务启动后 Worker 一直是 NOT alive？

旧进程残留导致 ZK 注册冲突或端口占用。全部停掉重来：

```bash
pkill -9 -f "bin/job_service|bin/scheduler|bin/worker_manager|bin/transcode|bin/result_collector"
sleep 3   # 等 ZK 临时节点过期
# 重新启动
```

### Q: Worker 启动时报 "ffmpeg/ffprobe not found in PATH"？

Worker 以 `executor_mode=ffmpeg` 启动时会自动检测 ffmpeg/ffprobe 可用性。安装 ffmpeg：

```bash
sudo apt install ffmpeg    # Debian/Ubuntu
# 或改用 mock 模式：executor_mode=mock
```

### Q: 提交任务后卡在 SCHEDULING 不动？

1. 确认 Worker 已注册：`grep "RegisterWorker success" program_log/*.txt`
2. 确认有 ONLINE Worker：`grep "ONLINE workers" program_log/*.txt`
3. 确认 ffmpeg 可用：`which ffmpeg ffprobe`
4. 确认输入视频路径正确、文件存在

### Q: 输出视频时长不精确？

已修复。切片+转码使用重编码（`libx264`）而非 `-c copy`，帧精确。偏差超过 0.1 秒时检查是否有旧二进制进程残留。

### Q: 多个 job 同时提交时哪个先执行？

阶段 7 实现了优先级队列：`priority` 越大的 job 越先分配 Worker 资源。同优先级按提交时间 FIFO。提交时通过 `priority` 参数控制。

### Q: 多 Worker 时如何确认负载均衡生效？

```bash
# 看 metrics：running/total 应接近 1（均匀分配）
grep "SchedulerMetrics" program_log/*.txt | tail -10

# 看分配日志：不同 Worker 应被选中
grep "assigned shard.*to worker" program_log/*.txt | tail -10
```
