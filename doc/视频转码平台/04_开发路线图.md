# 04. 开发路线

## 总体阶段

建议分 8 个阶段推进：

1. 框架 P0 能力补齐
2. 项目骨架和 proto 设计
3. Worker 注册与心跳
4. mock 任务调度闭环
5. 失败重试和故障恢复
6. 接入 FFmpeg 执行器
7. 资源感知调度和监控
8. 压测、故障测试和文档整理

不要一开始就写完整业务。每个阶段都要有可运行结果。

## 阶段 3：Worker 注册与心跳

### 目标

实现 Worker 生命周期管理。

### 开发内容

- Worker 启动后调用 `RegisterWorker`
- Worker 周期性调用 `Heartbeat`
- WorkerManager 维护 Worker 表
- Worker 心跳超时后标记 OFFLINE
- Scheduler 能查询 ONLINE Worker

### Worker 上报信息

```text
worker_id
ip
port
cpu_cores
memory_mb
max_running_shards
current_running_shards
status
```

### 验收标准

- 启动 3 个 Worker，WorkerManager 能看到 3 个 ONLINE
- 停掉 1 个 Worker，10 秒内状态变 OFFLINE
- Worker 重启后能重新注册

---

## 阶段 4：mock 任务调度闭环

### 目标

先不接 FFmpeg，用 mock executor 跑完整任务链路。

### 开发内容

- Client 提交 job
- JobService 创建 job
- Scheduler 将 job 切成 shard
- Scheduler 分配 shard 给 Worker
- Worker sleep 模拟执行
- Worker 上报进度和结果
- ResultCollector 聚合 shard
- Job 状态最终变 SUCCESS

### mock executor

```text
输入：shard_id, duration_ms
行为：每隔 1 秒上报一次 progress
完成：写一个 result 文件或 result 字符串
```

### 验收标准

- 提交一个 job，可以拆成 N 个 shard
- 多个 Worker 并行执行 shard
- 能查询 job 进度
- 所有 shard 完成后 job 变 SUCCESS

---

## 阶段 5：失败重试和故障恢复

### 目标

让系统在 Worker 失败时能恢复。

### 开发内容

- shard 增加 retry_count
- shard 增加 attempt_id
- Worker 执行失败后上报 FAILED
- Scheduler 重新调度 FAILED shard
- Worker 心跳超时后重新调度 RUNNING shard
- ResultCollector 做幂等处理

### 故障场景

- Worker 执行 shard 时返回失败
- Worker 执行 shard 时进程退出
- Worker 上报结果超时
- ResultCollector 重复收到结果
- Scheduler 重启后恢复未完成任务

### 验收标准

- 杀掉一个正在执行任务的 Worker，任务最终仍能完成
- 同一个 shard 重复上报 SUCCESS，不影响最终结果
- 超过最大重试次数后 job 变 FAILED

## 阶段 6：接入 FFmpeg 执行器

### 目标

让 Worker 可以执行真实视频处理命令。

### 开发内容

- 实现 `FfmpegExecutor`
- 支持视频信息探测
- 支持按时间切片
- 支持 shard 转码
- 支持截图
- 支持结果合并
- 捕获 FFmpeg 返回码
- 失败时记录 stderr 或错误摘要

### 第一版命令

探测：

```bash
ffprobe input.mp4
```

切片：

```bash
ffmpeg -i input.mp4 -ss START -t DURATION part_N.mp4
```

转码：

```bash
ffmpeg -i part_N.mp4 -s 1280x720 output_N.mp4
```

合并：

```bash
ffmpeg -f concat -safe 0 -i filelist.txt -c copy output.mp4
```

### 验收标准

- 能提交一个真实 mp4 文件
- 能生成多个 shard 输出
- 能合并最终结果
- 某个 shard 转码失败时能重试

### 注意

第一版不需要追求完美音视频切片。切片不精确或合并有瑕疵可以接受，重点是分布式任务链路。

## 阶段 7：资源感知调度和监控

### 目标

让调度器不再简单轮询，而是根据 Worker 资源状态分配任务。

### 开发内容

- Worker 上报 CPU、内存、running shard
- Scheduler 维护 Worker 资源快照
- 实现资源匹配策略
- 实现优先级队列
- 实现 Worker 过载保护
- 输出 metrics

### 简单调度策略

```text
available_slots = max_running_shards - current_running_shards
score = available_slots * 10 - cpu_usage * 0.5 - memory_usage * 0.2
```

### 指标

- job_success_total
- job_failed_total
- shard_running
- shard_pending
- shard_retry_total
- worker_online
- worker_offline
- scheduler_queue_size
- rpc_latency_p99

### 验收标准

- 高负载 Worker 不再被继续分配任务
- 低负载 Worker 会获得更多 shard
- 可以看到任务队列长度和 Worker 负载

## 推荐开发顺序总结

```text
框架 P0
  -> proto
  -> Worker 注册/心跳
  -> mock 调度闭环
  -> 失败重试
  -> FFmpeg executor
  -> 资源调度
  -> metrics
  -> 压测和文档
```

## 不建议的开发顺序

不要这样做：

```text
先学很深音视频
  -> 先接复杂 FFmpeg
  -> 再想调度怎么写
  -> 最后发现框架不支持 timeout/连接池/重试
```

正确方式是：

```text
先完成分布式调度闭环
  -> 再把执行器从 mock 替换成 FFmpeg
```

# 第二大阶段：项目深化与工程化

> 第一大阶段（阶段 1-8）完成了核心分布式转码链路。第二大阶段的目标是把项目从"能跑"提升到"生产级"——
> 性能、可靠性、可运维性、用户体验全面升级。

建议分 7 个阶段推进（阶段 9-15）。各阶段相对独立，可按优先级并行或调整顺序。

> **性能优化为什么在最后？** 过早优化是万恶之源。MySQL、Redis、MQ 会彻底改变系统瓶颈——在这些就位之前做 profiling，优化的是旧架构的热路径，中间件一加全变了。等全栈稳定后再 profile，每一分优化投入都有据可查。硬件编码（NVENC）例外——它不依赖架构变更，作为阶段 10 独立提前。

## 阶段 9：数据持久化 — MySQL 替代内存 Store　难度 ⭐⭐⭐

### 现状

JobStore / ShardStore / WorkerStore 是进程内 `unordered_map`，进程重启数据全部丢失。Scheduler 启动恢复只能靠扫残留状态拼凑，不优雅。

### 目标

引入 MySQL 作为持久化存储，服务重启后数据不丢失，跨进程天然共享（不再需要 RPC 同步补充数据）。

### 开发内容

- 设计 3 张核心表：`jobs` / `shards` / `workers`
- 封装轻量 MySQL 访问层（基于 `libmysqlclient` 或 `mysql-connector-c++`）
- 实现连接池（固定大小，预创建，线程安全借用/归还）
- Store 层改为双写：内存缓存 + MySQL 持久化（Write-Through 策略）
- 服务启动时从 MySQL 恢复内存缓存
- Scheduler / ResultCollector / JobService 不再需要"从 RPC 请求构造本地副本"的跨进程同步逻辑

### 表设计概要

```sql
CREATE TABLE jobs (
    job_id       VARCHAR(64) PRIMARY KEY,
    user_id      VARCHAR(64),
    input_path   VARCHAR(512),
    output_path  VARCHAR(512),
    target_format VARCHAR(16),
    target_resolution VARCHAR(16),
    target_bitrate INT,
    duration_sec BIGINT,
    priority     INT DEFAULT 0,
    status       INT DEFAULT 0,
    shard_count  INT DEFAULT 0,
    created_at   BIGINT,
    updated_at   BIGINT,
    INDEX idx_status (status),
    INDEX idx_user (user_id)
);

CREATE TABLE shards (
    shard_id        VARCHAR(128) PRIMARY KEY,
    job_id          VARCHAR(64),
    shard_index     INT,
    start_ms        BIGINT,
    duration_ms     BIGINT,
    status          INT DEFAULT 0,
    assigned_worker VARCHAR(64),
    attempt_id      VARCHAR(128),
    retry_count     INT DEFAULT 0,
    max_retry       INT DEFAULT 3,
    input_path      VARCHAR(512),
    output_path     VARCHAR(512),
    screenshot_path VARCHAR(512),
    target_resolution VARCHAR(16),
    target_bitrate  INT DEFAULT 0,
    created_at      BIGINT,
    updated_at      BIGINT,
    INDEX idx_job (job_id),
    INDEX idx_worker (assigned_worker),
    INDEX idx_status (status)
);

CREATE TABLE workers (
    worker_id       VARCHAR(64) PRIMARY KEY,
    ip              VARCHAR(45),
    port            INT,
    cpu_cores       INT,
    memory_mb       INT,
    cpu_usage       INT DEFAULT 0,
    memory_usage    INT DEFAULT 0,
    running_shards  INT DEFAULT 0,
    max_shards      INT,
    status          INT DEFAULT 0,
    last_heartbeat  BIGINT,
    INDEX idx_status (status)
);
```

### 验收标准

- 杀掉所有服务进程再重启，job 状态和 shard 进度不丢失
- 多个服务进程读写同一 MySQL，数据一致
- 连接池复用，单次 Store 操作延迟 < 2ms

## 阶段 10：硬件编码加速　难度 ⭐

### 目标

利用 GPU 硬件编码器替代 CPU 软编（libx264），大幅提升转码速度。这是第二阶段唯一适合提前做的性能优化——不依赖 MySQL/Redis/MQ 架构变更，单独升级 ffmpeg 参数即可生效。

### 为什么这里做

硬件编码不改架构、不动数据流、不依赖中间件。只改 ffmpeg 命令行参数。早做早受益——每个 shard 转码都快 5-20 倍，后续所有阶段的测试等待时间都缩短。

> 全栈 profiling + 对象池 + 锁优化等通用性能优化放在阶段 15（架构稳定后），原因见总体概览注释。

### 开发内容

#### 10a. GPU 检测

- 启动时探测可用硬件编码器：
  - NVIDIA：检查 `nvidia-smi` + ffmpeg 是否编译了 `h264_nvenc` / `hevc_nvenc`
  - Intel：检查 `/dev/dri/renderD128` + `h264_vaapi`
  - AMD：检查 `h264_amf`
- 检测结果写入 Worker 心跳信息，Scheduler 可据此调度 GPU job 优先给有 GPU 的 Worker

#### 10b. FFmpeg 命令切换

```
软编（当前）:
  ffmpeg -i input -c:v libx264 -preset fast -b:v 2000k output.mp4

硬编 NVENC（新）:
  ffmpeg -hwaccel cuda -hwaccel_output_format cuda \
         -i input -c:v h264_nvenc -preset p4 -b:v 2000k output.mp4

硬编 VAAPI（新）:
  ffmpeg -hwaccel vaapi -hwaccel_output_format vaapi \
         -i input -c:v h264_vaapi -b:v 2000k output.mp4
```

- `FfmpegExecutor::Transcode()` 增加 `encoder` 参数（"libx264" / "h264_nvenc" / "h264_vaapi"）
- 根据 GPU 检测结果自动选择最优编码器
- 保留 `executor_mode` 配置项 `encoder_mode=auto|soft|nvenc|vaapi`

#### 10c. 场景自适应预设

- 用 ffprobe 探测源视频复杂度（码率/运动矢量）
- 简单内容（屏幕录制、静态画面）→ `-preset ultrafast`
- 复杂内容（电影、运动）→ `-preset medium`
- 比固定 `-preset fast` 平均再提升 30%

### 验收标准

- NVENC Worker 转码 1080p 视频速度 > 5x 实时（1 分钟视频 < 12 秒转完）
- 无 GPU 的 Worker 自动回退软编，不影响正常使用
- `encoder_mode=auto` 下自动选择最佳编码器

## 阶段 11：中间件集成　难度 ⭐⭐⭐⭐

### 目标

引入 Redis 缓存热数据和消息队列解耦调度链路，减少 RPC 同步等待。

### 11a. Redis 缓存

- **ZK 服务地址缓存**：当前在 MprpcChannel 内存缓存，改为 Redis `HSET` 集中管理，多进程共享
- **Worker 负载快照**：Scheduler 从 Redis 直接读 Worker 最新心跳数据，不走 WorkerManager ListWorkers RPC
- **Job 进度缓存**：高频 QueryJob 的进度数据写入 Redis（TTL 60s），减少 JobService→ShardStore 的反复扫描
- **分布式锁**：多 Scheduler 实例下用 Redis `SETNX` 防止同一个 shard 被重复分配

### 11b. 消息队列（RabbitMQ / Kafka 选其一）

当前 Scheduler 的 `SchedulingLoop` 是 Pull 模式（每 2s 扫一次），存在调度延迟。

改为消息队列 Push 模式：

```
JobService → Exchange "job.events" → Queue "shard.waiting"
Scheduler ← 消费 Queue → AssignShard
Worker 完成 → Exchange "shard.events" → Queue "result.pending"
ResultCollector ← 消费 Queue → 聚合
```

**选型建议**：初期用 **RabbitMQ**。消息量不大（shard 数级别，非海量），RabbitMQ 的安装运维更简单，且支持 AMQP 标准（后续可无缝迁移）。Kafka 更适合日志/流式大数据场景，这里有些杀鸡用牛刀。

### 验收标准

- Redis 故障不影响核心转码链路（降级为本地缓存）
- MQ 模式下 shard 调度延迟从平均 2s 降到 < 100ms
- MQ 宕机后消息不丢失（持久化队列 + 手动 ACK）

## 阶段 12：可观测性升级　难度 ⭐

### 目标

从 `grep` 日志进化到标准监控面板，让系统状态一目了然。

### 开发内容

- **Prometheus metrics endpoint**：每个服务暴露 `:9090/metrics` HTTP endpoint
  - Counter: `job_submitted_total`, `job_success_total`, `job_failed_total`, `shard_retry_total`
  - Gauge: `shard_running`, `shard_waiting`, `worker_online`, `scheduler_queue_size`
  - Histogram: `rpc_latency_ms`, `transcode_duration_ms`, `schedule_loop_duration_ms`
- **Grafana Dashboard**：
  - Row 1: Job 吞吐（提交/成功/失败 折线图）
  - Row 2: Shard 分布（各状态 shard 数量饼图 + 时间线）
  - Row 3: Worker 负载热力图（CPU/内存/运行中 shard 数）
  - Row 4: RPC 延迟热力图（P50/P90/P99）
- **告警规则**：
  - `worker_online < 1` → 无 Worker 可用
  - `scheduler_queue_size > 100` → 调度堆积
  - `job_failed_rate > 0.3` → 失败率异常
  - `rpc_latency_p99 > 1000ms` → RPC 性能劣化

### 验收标准

- Grafana 面板能看到实时 job/shard/worker 状态
- 告警规则触发后能收到通知（至少日志打印）

## 阶段 13：客户端 GUI — Qt6 桌面应用　难度 ⭐⭐⭐

### 目标

用 Qt6 做一个桌面客户端，取代命令行交互式提交。让项目可以"拿出去演示"。

### 开发内容

- **提交面板**：拖拽视频文件 → 自动填充路径 → 下拉选分辨率/格式/码率 → 点击提交

## 阶段 15：全栈性能优化 + 高级特性　难度 ⭐⭐⭐⭐

> 这是第二阶段的收尾——架构已稳定（MySQL/Redis/MQ/Docker 全部就位），此时做 profiling 才有意义。

### 目标

系统性优化性能 + 补全生产环境必需的能力。

### 15a. 性能优化（架构稳定后）

**热路径剖析**：
- 用 `perf` / `flamegraph` 对全服务做 CPU profiling，找到热点函数
- 用 `valgrind --tool=callgrind` 分析 RPC 调用链的时间分布
- 此时的重点怀疑对象已经和阶段 10 时期不同——MySQL 查询、Redis 网络往返、MQ 序列化才是新热点

**内存优化**：
- **对象池**：为频繁创建销毁的对象（`MprpcController`、RPC 请求/响应）实现 `ObjectPool<T>`，减少 `new/delete`
- **Buffer 零拷贝**：`wevix_muduo` 的 Buffer 已支持 prependable，进一步扩展 `readv` 散射读到多 Buffer 链
- **Proto Arena**：用 protobuf Arena 分配器减少短生命周期 proto 消息的内存碎片
- **ShardRecord 压缩**：当前 `std::string` 字段过多（13 个 string），改为固定大小缓冲区

**并发优化**：
- **Store 锁粒度**：当前 `shared_mutex` 锁整张表，改为分片锁（按 `job_id` hash 到 16 个 bucket）
- **无锁队列**：事件通知用自实现 SPSC lock-free queue
- **RCU 读**：`ListByStatus` / `ListByJob` 考虑 RCU 替换 shared_lock

**网络优化**：
- RPC 连接池预热：Consumer 启动时预建连接
- TCP_NODELAY 开启
- IO 线程与 CPU 绑核

### 15b. 连接池增强

- 健康检查（空闲连接定期 ping）
- 动态伸缩（空闲缩到 2，繁忙扩到 16）
- Circuit breaker（连续失败 3 次暂时摘除 endpoint）

### 15c. 多租户与配额

- `user_id` 关联租户信息表
- 每租户配额：最大并发 job 数、总存储配额、API 调用频率限制
- 超配额时返回明确错误码，GUI 展示配额进度条

### 15d. 安全认证

- RPC 调用方身份认证：在 RpcHeader 中增加 `auth_token` 字段
- Worker 注册时验证 token，防止恶意 Worker 注入
- 敏感操作（取消 job、修改配置）需管理员权限

### 15e. REST API + API 文档

- 在 JobService 上增加 HTTP REST 接口（基于 `libmicrohttpd` 或内嵌 http parser）
- `POST /api/v1/jobs` — 提交任务
- `GET /api/v1/jobs/{id}` — 查询任务
- `GET /api/v1/workers` — Worker 列表
- Swagger / OpenAPI 文档自动生成

### 15f. 配置中心

- 当前配置是静态 `.conf` 文件，改配置需重启
- 接入 etcd/consul 或轻量的 Redis 配置订阅
- 支持热更新：调度间隔、重试次数、评分权重等运行时不重启调整

### 验收标准

- RPC 单次调用 P99 延迟 < 5ms（同机）
- 10 Worker × 100 shard 并发下 Scheduler loop 不堆积
- Store 操作在 1M 记录下不出现明显性能衰减
- REST API 能通过 curl 调用，返回 JSON
- 配置热更新后 10 秒内生效
