## 修复一：S1 SIGPIPE 无防护

### 现象/根因

`Connection::handleWrite` / `sendInLoop` 的 `::send` 未带 `MSG_NOSIGNAL`，库内无任何 `signal(SIGPIPE, SIG_IGN)`（5 个生产服务 main 与 mprpcapplication 均未忽略）。对端断开后继续写 → EPIPE → SIGPIPE → **默认动作终止整个服务进程**；容器化部署中任一 peer 崩溃即可级联杀服务。

### 修复（双保险）

1. **`wevix_muduo/src/Connection.cpp` 两处 `::send` 加 `MSG_NOSIGNAL`**（handleWrite 在 `:139`，sendInLoop 在 `:234`）——主修复，对端断开时返回 EPIPE 走现有错误处理，不再触发信号。
2. **`wevix_muduo/src/TcpServer.cpp:19` 构造时 `::signal(SIGPIPE, SIG_IGN)`**——库级兜底（muduo 原版同款做法），覆盖所有基于网络库创建的进程（5 个生产服务 + MetricsHttpServer 等），及 writev 等其他潜在写路径。

客户端侧 `mprpcchannel.cc:152` 此前已正确使用 MSG_NOSIGNAL，本次对齐服务端。

### 验证

`cmake --build build -j$(nproc)` 全项目编译通过。

## 修复二：S2 Connection::handleRead 编解码循环 UAF

### 现象/根因

`while (messageCodec_(&inputBuffer_, message)) { onMessageCallback_(shared_from_this(), message); }` —— `shared_from_this()` 的临时引用在**回调返回后**即释放；用户回调内同步关闭本连接（如 `conn->forceClose()` 在 loop 线程内联执行 handleClose，erase 掉 TcpServer `connections_` 与 subLoop `conns_` 两个 map 后引用归零）→ Connection 析构 → 回到 while 条件判断访问已析构的 this。无编解码器分支回调后的 `handleClose()` 同样存在。`Channel.cpp:110-112` 已用"回调后立即 return"修复同类问题，handleRead 的循环缺同等保护——历史修复不完整。

### 修复（`wevix_muduo/src/Connection.cpp`）

1. **`handleRead` 入口 `:52` 持有 `ConnectionPtr self(shared_from_this());`**——与 handleClose 内部同手法：函数执行期间引用计数 ≥1，回调内即使关闭连接，对象存活到函数返回。
2. **编解码循环每帧回调前检查 `disconnected_`（`:98`）、回调后检查并 break（`:109`）**——本端已关闭则停止取帧/处理，丢弃关闭前的剩余帧（正确语义：连接已进入回收流程，closeCallback 已通知上层，剩余帧处理无意义）。

### 为什么临时 shared_from_this() 不够

临时对象在完整表达式结束即析构，只保活"回调执行期间"；回调返回后 while 条件、`disconnected_` 检查、peerClosed 分支仍需访问 this——`self` 把保活延长到函数返回。

### 验证

`cmake --build build -j$(nproc)` 全项目编译通过。

## 修复三：S3 内存池 SpanTracker 数组有序性破坏（已定位，待确认）

### 根因推演（核心结论）

问题出在 `expandTrackerArray`（CentralCache.cpp:368-399）把**整个新数组**（含 span_addr=nullptr 的未初始化槽位）排序：nullptr 被排到最前，`sorted_count_ = newSize` 声称全有序；此后新 span 按 `span_count_++` 创建顺序写入这些靠前槽位 → **覆盖已初始化 tracker + 破坏有序前缀**。`getSpanTracker` 二分失配、Phase 2 线性扫描 `[sorted, total)` 因 `sorted > total` 空循环 → 全失配 → free_count 记账跳过、span 永不归还 PageCache、free 内存永不 munmap。

**修正一处推演**：`sorted_count_` 初始值为 0（CentralCache.h:51 `{0}`），故 span 总数 < 1024（首次扩容）期间数组自洽（Phase 2 线性扫描覆盖全部）；**引爆点在 span_count_ 撞到 1024 首次扩容**。

### 修复方案（已设计，代码已还原）

1. `expandTrackerArray`：**删除全数组 `std::sort`**，原序复制 `[0, oldSize)`（排序前缀复制后仍有序），新槽位一律在尾部；`sorted_count_` **保持不变**（不再设 `newSize`）。
2. `getSpanTracker`：加防御 `if (sorted > total) sorted = total;`——不变量一旦被破坏，Phase 2 线性扫描兜底而非空循环。

修复后不变量恢复：`[0, sorted) 有序前缀 + [sorted, span_count_) 未排序尾(≤64) + [span_count_, tracker_count_) 未初始化`。

**遗留**：① tracker 槽位只增不减（span 地址复用产生重复 tracker，数组持续扩容）② 扩容/排序换新数组后旧数组不 delete（无锁读者，RCU 语义）——均与本次有序性 bug 无关，暂不处理。
