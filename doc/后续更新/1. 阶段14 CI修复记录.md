# 阶段 14：CI 失败修复记录（2026-08-09）

## 背景

`git push origin main` 后 CI 三个 job 失败（Build 成功）：

| Job | 失败步骤 | 耗时 |
|-----|---------|------|
| Unit tests | Install runtime deps（apt 装运行时库） | 10s |
| RPC benchmark | Install runtime deps（apt 装运行时库） | 15s |
| Integration (docker compose) | Run integration test（集成测试脚本） | 7m |

## 根因一：Integration —— ZK 冷启动超时导致 worker_manager 崩溃循环

### 现象

本地复现 `docker compose up -d --build` 报 `dependency failed to start: container muduo_im-worker_manager-1 is unhealthy`，容器日志：

```
[ERROR][ZookeeperUtil.cc:266] Create() - znode create error, flag:-110, path:/mprpc
[ERROR][rpcprovider.cc:215] Run() - RpcProvider start failed: create root registry path failed
[ERROR][worker_manager.cpp:383] main() - WorkerManagerService start failed
terminate called without an active exception
```

### 分析

- `flag:-110` = `ZOPERATIONTIMEOUT`：ZK 会话已建立（`Start()` 信号量等待成功）但第一个写请求（`zoo_create /mprpc`）超时——compose 冷启动时 ZK 刚过 healthcheck（ruok 探测），服务器瞬时过载/会话窗口未完全就绪
- `RpcProvider::Run()` 对 root 路径创建失败**fail-fast 返回 false** → 进程退出 → 容器 `restart: unless-stopped` 重启 → 下一次启动成功（冷启动窗口仅数秒），但 compose 的 `depends_on: { condition: service_healthy }` 在等待期间已判 unhealthy 中止整个 up
- CI 上同类事件：WM 崩溃重启循环期间集成测试的 150s 等待窗口耗尽 → fail

### 修复（`mprpc/src/rpcprovider.cc`）

`/mprpc` + `/mprpc/services` 创建失败改为**退避重试 3 次（间隔 1s）**，不再一次失败退出进程。`Create()` 幂等（`zoo_exists` 已存在即返回 true），重试安全。所有 5 个服务（job_service / scheduler / worker_manager / transcode_worker / result_collector）共同受益。

```cpp
bool rootOk = false;
for (int attempt = 1; attempt <= 3 && !rootOk; ++attempt)
{
    rootOk = zkCli.Create("/mprpc", nullptr, 0) &&
             zkCli.Create("/mprpc/services", nullptr, 0);
    if (!rootOk)
    {
        LOG_WARN("create root registry path failed, retry %d/3 after 1s...", attempt);
        sleep(1);
    }
}
if (!rootOk)
{
    LOG_ERROR("RpcProvider start failed: create root registry path failed");
    return false;
}
```

### 验证

本地 `docker compose down -v && docker compose up -d --build && ./scripts/integration_test.sh` 全链路 PASS：提交 → 转码 → 合并 → SUCCESS + 产物校验，worker_manager 稳定 Healthy。

## 根因二：unit-test / benchmark —— runner 预装 apt 索引不完整

### 现象

```
E: Unable to locate package  libprotobuf32t64
E: Unable to locate package  ffmpeg
Error: Process completed with exit code 100
```

只有这两个包找不到（libzookeeper-mt2 / libmysqlclient21 / libhiredis1.1.0 / librabbitmq4 都能找到）。

### 分析（逐步排除）

1. **包名错误？** ❌ 排除——干净 `ubuntu:24.04` 容器里 5 个包全部安装成功；预装 mysql-server 后模拟同样成功
2. **azure 镜像故障？** ❌ 排除——`curl` 探测全部 6 个组件 200，与官方 CDN 文件大小/内容完全一致
3. **pocket 归属矛盾**：libzookeeper-mt2 / libhiredis1.1.0 / ffmpeg 都只在 noble 主源（universe），CI 上 zookeeper/hiredis 找到、ffmpeg 找不到——同一索引文件不可能部分缺失
4. **决定性证据（完整 CI update 日志）**：
   - `Hit:2 http://azure.archive.ubuntu.com/ubuntu noble InRelease` —— 主源 InRelease 缓存命中
   - **noble 主源组件的 Packages/Translation 零 Get/Hit 行**——apt 用 runner 镜像预装的本地索引，未重新下载
   - 实际下载的全是 updates/backports/security（共 11.2MB，完整 update 应 ~35MB+）
   - **结论：runner 镜像预装的 noble 主源索引不完整/不可信，且 InRelease 有效期内 apt 直接 Hit 不更新**

### 修复（`.github/workflows/ci.yml`）

安装前**强制清空重建 apt 索引**，绕过预装缓存：

```yaml
- name: Install runtime deps
  run: |
    sudo rm -rf /var/lib/apt/lists/*
    sudo apt-get update
    sudo apt-get install -y --no-install-recommends \
      libprotobuf32t64 libzookeeper-mt2 libmysqlclient21 libhiredis1.1.0 librabbitmq4 \
      ffmpeg
    # 诊断：安装后打印关键包解析结果，失败时便于定位（不阻断）
    apt-cache policy libprotobuf32t64 ffmpeg libzookeeper-mt2 libhiredis1.1.0 || true
```

unit-test 和 benchmark 两处同步修改（benchmark 无 ffmpeg）。

## 根因三：unit-test 的 artifact 可执行权限丢失（第二轮发现）

apt 修复后 unit-test 前移死在第一步：`./bin/test_buffer: Permission denied`（exit 126）。

**根因**：`download-artifact@v4` 解压丢失可执行位（GitHub Actions 已知行为）。unit-test job 无 checkout，工作区只有 artifact 解压的 bin/，权限全丢；benchmark 有 checkout，git 跟踪的二进制（仓库里提交过 bin/*）覆盖了部分文件，所以只有 unit-test 暴露。

**修复**：两个 job 运行前 `chmod +x bin/*`。

## 根因四：benchmark 缺 ZooKeeper + ZK 4lw 白名单（第二轮/第三轮发现）

apt 修复后 benchmark 前移：`127.0.0.1:2181 Connection refused`——`rpc_echo_server` 是 RPC Provider，启动需连 ZooKeeper 注册（代码注释明确），runner 无 ZK。

**修复**：benchmark job 用 docker 起 `zookeeper:3.8`。第三轮踩坑：ZK 3.8 **默认禁用 4lw 命令**，必须 `-e ZOO_4LW_COMMANDS_WHITELIST=ruok`（与 compose healthcheck 一致），否则 ruok 探测 60s 超时。

## 根因五：integration 的 RC MQ 消费偶发延迟（第三轮，flaky）

同一代码 7e804e2 轮 integration PASS、fbe9791 轮失败：shard_0 SUCCESS、**shard_1 卡 RUNNING 240s** 超时。与项目已知问题吻合：**RC MQ 消费静默失效（result.pending 偶发 ~5 分钟延迟，阶段 10 遗留）**。

**修复**：`integration_test.sh` watch 超时 240s → **420s** 兜底（CI 中 MQ 延迟偶发晚到，7 分钟窗口可覆盖）。

## 最终结果

**2026-08-09 三轮修复后 CI 全绿**（commit `7d1f575`：Build / Unit tests / Integration / RPC benchmark 全部 success）。

累计修复 5 个根因：
