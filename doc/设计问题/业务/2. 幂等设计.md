# 幂等设计（video_platform）

> 覆盖 job_service / scheduler_service / worker_manager / transcode_worker / result_collector 全链路的重复请求防护。
> 与《业务细节设计.md》问题 1（并发 ScheduleJob）配套阅读——那篇讲"为什么必须原子"，这篇讲"重复到达时如何安全地不做第二次"。

## 1. 为什么整个平台必须幂等

分布式环境里"同一个操作到达两次"**无法从源头消除**，本平台存在三个确定的重复来源：

| 重复来源 | 场景 | 例子 |
|----------|------|------|
| **RPC 超时重试** | 请求已发出、响应丢失，客户端无法区分"没到"和"到了但响应丢"，只能重发 | SubmitJob 内联重试 3 次；PendingScanLoop 对 PENDING job 反复调 ScheduleJob |
| **MQ 至少一次投递** | RabbitMQ 默认投递语义就是 at-least-once：消费后 ack 失败 / 消费者崩溃，消息重新投递 | `shard.waiting`、`result.pending` 的消息重投 |
| **进程崩溃恢复重扫** | 服务重启后扫描存量数据继续推进，无法知道崩溃前哪些操作已经做过 | SchedulingLoop 启动时重置残留 ASSIGNED/RUNNING shard |

**幂等键的选取原则**：一律用**业务唯一标识**（`job_id` / `shard_id` / `attempt_id`），绝不用请求序号、时间戳等"每次不同"的值——同一业务操作无论重发多少次，键相同，才能去重。

## 2. 幂等防线总览（分层矩阵）

| 层 | 操作 | 幂等键 | 机制 | 代码位置 |
|----|------|--------|------|----------|
| RPC | ScheduleJob | job_id（判据=shard 集合非空） | 全局互斥 + 幂等早退（fix #14） | `scheduler_service.cpp:143` / `:165-199` |
| 存储 | INSERT jobs / shards | job_id / shard_id 主键 | 唯一索引，冲突静默拒绝 | `mysql_pool.cpp` 建表 / `common_store.cpp` Insert |
| 存储 | 状态推进 Update/UpdateIfStatus | job_id + 期望前置状态 | 单条条件 SQL 原子 | `common_store.cpp:187` |
| RPC | AssignShard 分配 | shard_id | 三重防护：状态复核 + SETNX 锁 + 条件更新 | `scheduler_service.cpp:997-1089` |
| MQ | 消费 shard.waiting / result.pending | shard_id / attempt_id | 消费侧幂等跳过 + 无条件 ACK | `scheduler_service.cpp:1865-1910` |
| RPC | RescheduleShard 重试 | shard_id + attempt_id | stale attempt 忽略 + 终态拒绝 | `scheduler_service.cpp:402-438` |

## 3. 各层详细设计

### 3.1 RPC 层：ScheduleJob（job_id 幂等）

**幂等判据**是"该 job 在 shard 表已有记录"（`ListByJob` 非空，`:167`），**不是**"job 记录已存在"。这是有意为之：

- Scheduler 进程内需要自己的 JobRecord 本地副本，**首次调用就 Insert 了**（`:218`）
- 若以"job 记录存在"为判据，会出现误判：第一次请求刚建完 job 副本、还没切分完，重试请求到达 → 看到 job 存在 → 早退 → 返回空计划 → 该 job 永远没有 shard

所以幂等键落在**切分产物**（shard 集合）上——只有 shard 存在才能证明"切分真的做完了"。

命中幂等时（fix #14）：不重新 ffprobe、不重新切分，直接返回现有 shard 列表（`:168-199`）。前提是问题 1 的全局互斥——互斥保证"检查"与"写"原子，后到者永远看到先到者的完整成果。

### 3.2 存储层：主键约束兜底（最后一道防线）

- `jobs` 表 `PRIMARY KEY (job_id)`，`shards` 表 `PRIMARY KEY (shard_id)`（`mysql_pool.cpp`）
- `JobStore::Insert` / `ShardStore::Insert` 对主键冲突（MySQL errno 1062）**静默返回 false**，语义是"行已存在，幂等拒绝"，不是错误

意义：不管上层 RPC / MQ / 重扫重复多少次、应用层判断是否漏掉，**同一 id 的行在库里只有一份**。这是最底层、不依赖任何业务逻辑的兜底。

### 3.3 状态机推进：UpdateIfStatus 条件更新

状态推进全部带"期望前置状态"，SQL 形如：

```sql
UPDATE jobs SET status=?, shard_count=?, updated_at=? ...
WHERE job_id='?' AND status IN (前置状态列表)
```

（`common_store.cpp:187`，JobStore 与 ShardStore 同构）

- **单条 SQL 原子**：MySQL 行锁保证同一行的检查与更新之间无窗口，等价于把 check-then-act 塞进一条语句
- **幂等语义**：第二次执行同一推进时，前置状态已被第一次推进改变 → `status IN (...)` 不匹配 → `affected_rows=0` → 返回 false → **no-op，安全不做第二次**
- 连接池启用了 `CLIENT_FOUND_ROWS`：值未变化也返回匹配行数，不会把"本来就匹配"误判为"未命中"

典型应用（防旧快照覆盖并发推进，全部由 UpdateIfStatus 承担）：

| 场景 | 条件 | 防什么 |
|------|------|--------|
| PendingScanLoop 推进 PENDING→SCHEDULING（fix #7，`:490-505`） | 仅当仍为 PENDING | 响应丢失场景下，防止把已被别的路径推成 SUCCESS 的 job 回退为 SCHEDULING（永久卡非终态） |
| SubmitJob 推进 SCHEDULING（`job_service.cpp:148-154`） | from_status 快照 | 防止覆盖其他进程对同一 job 的并发推进 |
| RescheduleShard / 终态守卫（`:103-109`） | 快照前置状态 | 防止把已终态 shard 复活 |
| Worker 结果落定 | shard 状态前置 | 防止旧 attempt 的结果覆盖新 attempt 的推进 |

### 3.4 分配竞争：Redis SETNX 分布式锁（多实例/双路径）

`TryAssignShard` 有**三重防护**（`:977-985` 注释），应对"轮询兜底 vs MQ 消息"双路径并发、消息重复投递、多 Scheduler 实例（`--scale`）同时分配同一 shard：

1. **状态复核**（`:997-1016`）：函数入口重新 Get 一次 shard，非 WAITING 直接 skip——调用方拿到的 WAITING 快照可能已被另一条路径推进为 ASSIGNED
2. **分布式锁**（`:1060-1089`）：`SETNX shard:lock:{shard_id} EX 10`，value=`scheduler:{pid}`
   - 拿到锁 → 分配完成后再校验 value 相同才 DEL（防误删他人锁）
   - 锁被占用 → 说明其他实例正在分配 → **skip**（这就是幂等：同一 shard 第二个分配者不会重复分配）
   - TTL 10s → 防持锁进程崩溃后死锁
   - Redis 故障 → **降级放行**，不做分配，交给第 3 道防线
3. **MySQL 条件更新**（WAITING→ASSIGNED）：分配落定用 `UpdateIfStatus`，Redis 故障时后到者 affected_rows=0 → 失败返回，依然只有一个分配者成功

降级路径不破坏幂等：Redis 故障只是"锁失效"，防线 3 的单条条件 SQL 依然保证唯一推进。

### 3.5 MQ 消费：至少一次投递下的消费幂等

投递语义是 at-least-once，所以**消费侧必须幂等，ack 侧选择无条件确认**（`MqConsumeLoop`，`:1865-1910`）：

- shard 不存在 → ack 丢弃（陈旧消息）
- 状态非 WAITING → **幂等跳过**（重复投递 / 轮询已分配）
- 分配落定本身 → TryAssignShard 三重防护（见 3.4）
- **无条件 ACK**：处理完成才 ack；ack 失败只 WARN——Broker 会重投，重投后幂等检查兜底，不会重复执行

为什么"无条件 ACK"而不是"精确一次"：宁可**重复消费**（应用层幂等可挡），不可**丢消息**（消费崩溃后消息回到队列才能被重新处理）。业务数据（shard 状态、结果落定）都在 MySQL，重复执行路径上的每一步都被 3.3/3.4 的条件更新拦成 no-op。

### 3.6 重试幂等：attempt_id

`RescheduleShard` 用 attempt_id 区分"同一次执行"与"新的执行"（`:402-438`）：

- 每次分配生成新 attempt：`shard_id + "_attempt_" + retry_count`（`:1152`）
- 重试请求携带 attempt_id；**与 shard 当前 attempt 不一致 → "duplicate reschedule for stale attempt, ignored"**——重复的 FAILED 上报触发的二次重试不会执行（`:404-415`）
- shard 已终态 → 拒绝重试（`:436-438`）
- 结果上报侧同样做 attempt_id 校验（RC 侧处理新旧 attempt 冲突）

### 3.7 崩溃恢复：SchedulingLoop 启动重置

Scheduler 崩溃重启后，残留的 ASSIGNED/RUNNING shard 重置为 WAITING（不增加 retry_count，`:1215-1240` 附近）。这里的幂等性体现在：

- 重置是"幂等的扫描"：重复扫描多次结果相同（快照副本 + 每次更新前重新 Get，防快照覆盖并发修改）
- 旧 Worker 可能还在执行该 shard 并上报结果 → RC 的 attempt_id 校验处理新旧 attempt 冲突（3.6），不会把旧结果算到新执行头上

## 4. 场景走查：一条重复消息穿越全部防线

以"同一 shard 的分配被触发两次"为例（轮询兜底与 MQ 消息并发，或消息重投）：

```
第一次到达：状态复核(WAITING✓) → SETNX 拿锁✓ → UPDATE WAITING→ASSIGNED 成功 → 释放锁
第二次到达：状态复核(非 WAITING) → skip                       ← 防线1 拦下
（若复核时第一次还没落定）
            状态复核(仍 WAITING) → SETNX 锁被占 → skip        ← 防线2 拦下
（若 Redis 故障降级）
            UPDATE WAITING→ASSIGNED → 已无匹配行 → no-op      ← 防线3 拦下
（任何路径下）
            shards 表主键唯一 → 该 shard_id 只有一行          ← 兜底
```

结论：**重复到达的次数不影响最终状态**——三条防线 + 唯一约束，任一时刻最多一条路径成功推进。

## 5. 设计原则总结

1. **幂等键 = 业务唯一标识**（job_id / shard_id / attempt_id），绝不使用每次请求不同的值
2. **防线分层，逐层兜底**：应用层状态判断（语义最清晰）→ 单条条件 SQL（原子性最强）→ 唯一约束（最无脑）——上层失效时下层仍生效
3. **检查与写必须原子**：要么互斥（ScheduleJob 全局锁），要么单条语句（条件 SQL / SETNX），要么唯一索引——任何"先查后写"的两步操作都是竞态窗口
4. **至少一次投递 + 幂等消费**，不依赖 MQ 的精确一次语义
5. **可降级组件的幂等不降级**：Redis/MQ 故障时组件降级放行，但落定始终经过 MySQL 条件更新，幂等保证不随中间件故障而失效
