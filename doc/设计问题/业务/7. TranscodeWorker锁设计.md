# 7. TranscodeWorker 锁设计（并发同步体系全解）（文档 7）

> 对应 `transcode_worker.cpp` 中全部同步原语的设计。TranscodeWorker 是
> 平台里线程模型最复杂的服务（5 类线程并发），其锁设计覆盖了
> 互斥锁、原子变量、引用计数、线程生命周期四类同步手段。

## 1. 线程模型全景：谁在并发访问什么

```
┌──────────────────────┬────────────────────────────────────────────────┐
│ 线程类型              │ 并发访问的数据                                  │
├──────────────────────┼────────────────────────────────────────────────┤
│ RPC 线程池            │ running_shards_（AssignShard 插入/检查、       │
│ (IO+Work，多个)       │ CancelShard 置 cancelled、QueryShard 读）      │
│ 执行线程（每 shard 1  │ rs->progress 写、rs->cancelled 读、            │
│ 个，多个）            │ CleanupShard、QueuePendingReport、             │
│                      │ 结果上报失败回队                                │
│ 心跳线程（1 个）      │ RunningShardCount、RetryPendingReports、       │
│                      │ CollectCpuUsage、stop_flag 轮询                │
│ main 线程（1 个）     │ heartbeat_stopped 写、heartbeat_thread join    │
└──────────────────────┴────────────────────────────────────────────────┘
```

核心矛盾：**同一份数据被 3 类线程并发访问**，且每种访问的频率、语义不同
（map 需要完整性、单值只需要一致性、线程句柄需要生命周期安全）。

## 2. 同步原语总览

| 原语 | 类型 | 保护的数据 | 访问方 |
|------|------|-----------|--------|
| `mutex_` | `std::mutex`（成员） | `running_shards_` map 整体 | RPC 线程池 + 执行线程 + 心跳线程 |
| `pending_mutex_` | `std::mutex`（成员） | `pending_reports_` 队列 | 执行线程（入队）+ 心跳线程（取/回队） |
| `cpu_mutex` | `std::mutex`（static 局部） | CPU 采样状态（prev_ticks 等） | AssignShard 调用方 + 心跳线程 |
| `progress` / `cancelled` | `std::atomic<int/bool>` | 单变量跨线程读写 | 执行线程写 / QueryShard、心跳读 |
| `heartbeat_stopped` | `std::atomic<bool>` | 线程退出标志 | main 写 / 心跳线程轮询 |
| `shared_ptr<RunningShard>` | 引用计数（控制块原子） | 对象生命周期 | 所有持有者 |
| `executor_thread` + detach | `std::thread` | 线程句柄 | **锁外**操作（纪律） |

**总原则：复合结构（map/vector）用锁保证完整性；单值（flag/进度）用原子量
保证一致性；线程句柄永不进临界区。**

## 3. 逐锁详解

### 3.1 `mutex_`：running_shards_ 的守护锁（核心）

**为什么用锁**：`std::unordered_map` 非线程安全。并发 `find/insert/erase/遍历`
会导致数据竞争——迭代器失效（erase 被 find 读取）、桶重哈希崩溃（insert
与遍历并发）。这是 UB，不是"结果不对"而是"进程可能直接崩"。

**为什么用 `std::mutex` 而非读写锁**（注释 :80 明确写了"非读写锁"）：
临界区全是 O(1) map 操作（微秒级），`std::shared_mutex` 的"读读不互斥"
优势在这么短的临界区内收益为零，反而多一份锁状态维护开销。互斥锁简单、
可预测，是短临界区场景的正确选择。

**为什么是 `mutable`**：`RunningShardCount()` 是 const 方法（:147）但需要
加锁——`mutable` 允许 const 方法内修改锁状态。

#### 6 个临界区逐个分析

**① RunningShardCount（:148，心跳线程）**
- 为什么锁：遍历 map 统计未取消的 shard 数，必须与 insert/erase 互斥
- 为什么遍历而不是维护计数器：计数器需与 map 生命周期严格同步（insert/erase
  各加一次），多一个状态源就多一分不一致风险；shard 数有 `max_running_shards`
  上限，遍历成本恒有界

**② AssignShard 过载检查（:179）**
- 为什么锁：统计 running 数（同上，遍历 map）
- 为什么独立成临界区而非与下面的检查插入合并：过载拒绝是 **soft 语义**——
  误判放行一个 shard 无害（Scheduler 兜底），不值得为它延长锁持有时间；
  `CollectCpuUsage` 在锁外（:177），锁内不做任何 IO/采样

**③ AssignShard 检查+插入（:202，TOCTOU 消除点）**
- 为什么**检查与插入必须合并在同一锁内**：两个并发 AssignShard 对同一 shard——
  若分开：A 检查"不存在"→ B 检查"不存在"→ A 插入 → B 插入 → 双条目互相覆盖。
  锁内 find+insert 保证**同一时刻只有一个线程能通过"不存在"检查**，这是阶段 4
  修过的真实竞态
- 为什么创建 `rs`（make_shared）也在锁内：`rs` 必须在插入前构造完整，避免
  别的线程在 map 里看到一个半初始化的对象

**④ CancelShard（:245）**
- 为什么锁：find 必须与 insert/erase 互斥——否则正在被重新分配的 shard
  （新 attempt 插入 map）可能被旧 attempt 的取消通知误伤
- 为什么 attempt_id 校验在锁内：find 看到的是"此刻"的条目，锁保证校验的
  是当前真实执行的 attempt，不是已替换的旧条目（#1 修复）

**⑤ QueryShard（:293）**
- 为什么锁：find + 填充响应需要 map 不被并发修改
- progress 是 atomic 为什么锁内读还安全：atomic 读在锁内**双保险**——锁保证
  map 完整性，atomic 保证即使未来有人无锁读 progress 也不撕裂（见 3.4）

**⑥ CleanupShard（:626 锁内 erase + :635 锁外 detach）——本文件最重要的死锁设计**

```cpp
std::shared_ptr<RunningShard> rs;
{
    std::lock_guard<std::mutex> lock(mutex_);
    auto it = running_shards_.find(shard_id);
    if (it != running_shards_.end()) {
        rs = it->second;
        running_shards_.erase(it);   // 锁内仅做 O(1) map 操作
    }
}
// 锁外处理线程资源
if (rs && rs->executor_thread.joinable())
    rs->executor_thread.detach();
```

- **为什么锁内绝不 join**：若持锁 join 执行线程——执行线程结束前调
  CleanupShard 想拿 `mutex_` → 主调线程持锁等它结束、它等锁 → **AB-BA 死锁**
- **为什么 detach 而非 join**：CleanupShard 是**执行线程自己调用**的
  （执行完自己清理自己）——join 自己的线程直接抛 `std::system_error`；
  detach 让 OS 在线程退出后回收资源，不阻塞任何调用者
- **shared_ptr 的角色**：锁内把 `rs` 拷出来（引用计数 +1），锁外 detach
  后执行线程仍持有 rs → 对象不会在 detach 瞬间析构，线程访问安全

### 3.2 `pending_mutex_`：待重试上报队列

**为什么锁**：`std::vector` 非线程安全。执行线程入队（`QueuePendingReport`
:655、结果上报失败回队 :713），心跳线程取出（:665）——两类线程并发操作
同一队列。

**为什么 `batch.swap` 取全部而不是逐条取出**（:663-667）：
```cpp
std::lock_guard<std::mutex> lock(pending_mutex_);
batch.swap(pending_reports_);   // O(1) 整队搬走
```
- 锁持有时间最小化——swap 是 O(1)，拿走后锁外做 RPC
- **为什么必须锁外做 RPC**：`ReportShardResult` 超时 5s（:692），若持锁
  发送，心跳线程会被单个结果阻塞 5s，期间执行线程的入队全部排队——
  锁被"长尾 RPC"劫持

**为什么回队要重新加锁**（:713）：RPC 在锁外做，失败后需要把结果放回队列，
入队操作必须重新拿锁（与下一个心跳线程的 swap 互斥）。

**为什么区分"确定性拒绝丢弃 vs 网络失败回队"**（:701-717，#14 修复）：
stale attempt 的旧结果**永远不可能被接受**（shard 已重调度到更高 attempt），
无差别重入队 = 每 3s 无限重试 + WARN 刷屏。只有"网络失败"（RPC 没送达）才
回队等待重试——这是"可重试性"的正确判断标准。

### 3.3 `cpu_mutex`（static 局部）：CPU 采样状态

**为什么锁**：`prev_ticks/prev_time_ms/first_call` 是跨调用保持的采样状态
（:811-813），`CollectCpuUsage` 被 AssignShard（RPC 线程）和心跳线程并发
调用 → 并发读写采样状态 = 数据竞争（计算出的 CPU% 会错乱）。

**为什么是 static 局部 mutex 而非类成员**：`CollectCpuUsage` 是文件级自由
函数，不属于任何类——锁与被保护状态**同作用域同生命周期**（都在函数内
static），封装性最好：这个锁只保护这个函数的状态，不可能被误用去锁别的。

**为什么不用 thread_local**（注释 :805 写了）：thread_local 每个线程独立
采样状态，**第一次调用没有历史数据 → 恒返回 0**——心跳线程和 RPC 线程各自
第一拍都报 0% CPU。共享状态 + 锁保证任何线程调用都能拿到**上一次任意线程**
采样的数据，从第一拍起就有真实值。

**一个如实记录的权衡**：`CollectTreeCpuTicks()`（读 /proc，轻量 IO）在锁内
执行（:819）。读 /proc 是微秒级且调用频率低（3s 心跳 + 分配时），当前可接受；
若未来采集频率提高，可把采样挪出锁（先采样后算差）。

### 3.4 原子变量：什么时候用 atomic 而不是锁

**progress（atomic\<int\>，:103）**：执行线程每 ~1s 写（转码进度回调），
QueryShard 读。**为什么不用锁**：写是高频的（每个 ffmpeg `time=` 输出），
读也是高频的（Scheduler 30s 轮询 QueryShard）——单 int 的读写用锁是
"用大炮打蚊子"：加解锁开销 + 线程调度延迟，atomic 的 acquire/release
语义完全够。且 `int` 读写天然对齐，atomic 保证不撕裂。

**cancelled（atomic\<bool\>，:104）**：CancelShard（锁内）置位，执行线程在
**ffmpeg 进度回调里高频轮询**（每个 time= 输出检查一次）。若读要拿锁，
CancelShard 的写会与执行线程的读互相阻塞——单 flag 用 atomic 零成本。
这也是"锁内写 atomic 是安全的"的典型例子：锁管 map、atomic 管 flag，
两层各自独立。

**heartbeat_stopped（atomic\<bool\>，:1187）**：main 线程写（Provider 退出
后 :1208），心跳线程 `while(!stop_flag)` 轮询——跨线程的退出握手。

**为什么这些不能并入 mutex_ 保护**：锁解决的是"复合结构的完整性"（map 的
迭代/插入互斥），atomic 解决的是"单值的读写一致性"。把单值放进锁体系 =
让高频读全部排队等锁，违背"锁粒度最小化"原则。

### 3.5 shared_ptr：对象生命周期管理（不是锁，但替代了锁）

`rs`（RunningShard）的共享方式：锁内 make_shared 创建 + 插入 map，锁外把
shared_ptr 拷贝进执行线程（:224）——**引用计数的增减由控制块原子操作保证，
这是语言层面就线程安全的**，不需要自定义锁。

为什么执行线程能无锁访问 `rs` 的字段：
- `info`/`attempt_id`：创建后**不变**（immutable），不变数据无锁读安全
- `progress`/`cancelled`：atomic
- `executor_thread`：只在创建线程时写、结束时 detach，使用时机天然串行

## 4. 死锁预防总则（设计纪律）

| 纪律 | 原因 | 代码体现 |
|------|------|---------|
| **锁内绝不做线程同步**（join/detach/启动） | AB-BA 死锁 | CleanupShard :626/:635、AssignShard 锁外启动线程 :224 |
| **锁内绝不做 RPC/长 IO** | 锁被长尾操作劫持 | pending 队列 swap 模式 :665 |
| **检查+插入必须原子** | TOCTOU 双条目 | AssignShard :202 |
| **复合结构用锁、单值用 atomic** | 锁粒度匹配数据结构 | mutex_ / progress / cancelled |
| **锁持有时间最小化** | 减少等待、避免连锁阻塞 | 全部临界区均为 O(1) 或轻量遍历 |
