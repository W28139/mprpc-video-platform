# Merge 互斥集设计（MergeMutex + MergingJobs）

> 文档日期：2026-08-07
> 关联代码：`result_collector.cpp`（MarkJobTerminal 内）
> 关联日志：阶段 8 修复 #7/#10/#11（`doc/更新业务日志/8. 阶段8代码审查与Bug修复.md`）

## 1. 概述

合并产物（Merge）是 ResultCollector 在任务成功后把全部 shard 片段拼成完整视频的操作。本设计用 **一把互斥锁 + 一个"合并中/已合并"集合** 保证：**同一个 job 的 merge 成功时恰好执行一次**、**失败时可自动重试**、**并发触发安全**。

```cpp
// Merge 互斥集：防止并发/重复 merge 毁掉成品视频
static std::mutex& MergeMutex() { static std::mutex m; return m; }
static std::unordered_set<std::string>& MergingJobs()
{
    static std::unordered_set<std::string> s;
    return s;
}
```

## 2. 问题背景（为什么需要）

### 2.1 并发触发是常态，不是意外

`MarkJobTerminal`（触发 merge 的入口）会被**多个线程并发调用**：

```text
触发源 1：MQ 消费线程（MqResultConsumeLoop）→ HandleReportShardResult → CheckJobDone
触发源 2：TerminalSweepLoop（15s 兜底重扫）→ CheckJobDone
触发源 3：直连 RPC 线程（Worker 上报）→ CheckJobDone

任一源判出 JOB_SUCCESS → MarkJobTerminal → merge
```

三个线程可能**同时**（或先后）判出同一 job 成功。

### 2.2 阶段 8 #7 暴露的真实事故：并发 merge 毁掉成品

修复前的代码只有 `MergingJobs` 集合、没有锁，且检查/插入/合并的时机有窗口：

```text
线程 A：CheckJobDone 判 SUCCESS → MarkJobTerminal → 开始 merge
线程 B：（几乎同时）CheckJobDone 判 SUCCESS → MarkJobTerminal → 也进入 merge
后果：
  ① 两个线程同时写同一个 filelist.txt（concat demuxer 的临时清单文件）
     → 串片竞态：A 写一半 B 覆盖 → 合并出的视频片段错乱、损坏
  ② 重复 merge：同一 job 合并两次，重复消耗资源、重复操作输出文件
```

### 2.3 两个维度的重复问题

| 维度 | 场景 | 需要什么 |
|------|------|---------|
| **同时**（并发） | 两个线程同一时刻 merge | 互斥锁（同一时刻只允许一个执行） |
| **先后**（跨轮次） | 锁释放后，下一轮 TerminalSweepLoop（15s 后）又判一次 SUCCESS，再 merge 一次 | 持久记忆（"这个 job 已经合并过了"） |

**只靠锁防不住"先后"**——锁只保护"同一时刻"，保护不了"另一个线程稍后再次进入"。这正是"mutex + set"双组件的原因。

## 3. 设计方式

### 3.1 数据结构：函数内 static（Meyers Singleton 风格）

```cpp
static std::mutex& MergeMutex() { static std::mutex m; return m; }
```

- **全局唯一**：任何线程调用都拿到同一个对象（static 局部变量生命周期 = 程序生命周期）
- **惰性初始化**：首次调用才构造，零启动成本
- **线程安全的初始化**：C++11 magic statics 保证首次构造由编译器加锁，多线程首次并发调用也安全
- 不用类成员/全局变量：声明位置贴近使用点，避免全局初始化顺序问题

### 3.2 使用流程（MarkJobTerminal 的 JOB_SUCCESS 分支）

```text
lock_guard(MergeMutex)                    ← ① 加锁（同一时刻只有一个 merge 流程）
  ├─ MergingJobs().count(job_id)？        ← ② 检查：已合并过？
  │     → 是：skip_merge 直接跳过（幂等）
  │     → 否：insert(job_id)              ← ③ 登记（本 job 进入"合并中"）
  ├─ 收集 shard output_path，按 index 排序
  ├─ FfmpegExecutor::Merge(...)           ← ④ 真正合并（持锁执行！）
  ├─ 成功 → 删除 shard 中间文件
  │        MergingJobs 保留 job_id        ← ⑤ 永久防重（"已合并"记忆）
  └─ 失败 → MergingJobs().erase(job_id)   ← ⑥ 撤销登记（允许下次重试）
          → 打 ERROR，return
```

**关键点：检查、登记、合并、清理全程持锁**（阶段 8 #10/#11 修复：锁不再提前释放）。此前把锁提前释放留下窗口——两个线程都通过检查、都进入合并。

## 4. 为什么是"mutex + set"两层而不是其一

| | 只有 mutex | 只有 set | mutex + set（现状） |
|---|---|---|---|
| 防"同时"（并发执行） | ✅ | ❌（无原子性，检查-插入非原子） | ✅ |
| 防"先后"（下一轮重扫再 merge） | ❌ | ✅ | ✅ |
| 检查的原子性 | ✅（锁内检查） | ❌（无锁时 count 与 insert 之间有窗口） | ✅ |
| 失败重试 | ✅ 天然（没记状态） | ✅（erase 撤销） | ✅ |

**两个组件各管一个维度：mutex 管"同一时刻"，set 管"跨越时刻"；组合起来才是完整的"恰好一次"。**

## 5. 失败处理：可重试的收敛闭环

```text
merge 失败（磁盘满、ffmpeg 挂、文件缺失）
  → MergingJobs().erase(job_id)    ← 撤销"已合并"登记
  → return（job 状态保持 SUCCESS，但无产物）
  → TerminalSweepLoop 每 15s 重扫 → CheckJobDone 再判 SUCCESS
  → MarkJobTerminal 再进 merge（MergingJobs 里没有 → 不跳过）→ 重试
  → 磁盘/ffmpeg 恢复后 merge 成功 → 产物产出、shard 清理、登记保留
```

**成功即永久记忆（不重试），失败即撤销（允许重试）**——这是收敛性的关键：不会因为一次失败永久丢产物，也不会因为成功而重复合并。

## 6. 为什么不用其他方案

| 方案 | 为什么不用 |
|------|-----------|
| 只用互斥锁 | 防不住"先后"重复（下一轮重扫会再 merge） |
| MySQL 状态字段（如 `merged` 列） | 需要改表 + 所有写入路径；且"合并中/已合并"是进程内瞬时状态，DB 表达过重 |
| 每 job 一个 `std::atomic<bool>` map | 与 `unordered_set` 本质等价，set 更简洁 |
| 完全不加防护 | #7 事故：并发 merge 直接毁掉成品视频（串片竞态） |

进程内 set 的前提是 **ResultCollector 单实例**（当前部署下成立）；若将来 RC 多实例部署，需迁移到 DB/Redis 的分布式防重（与阶段 10 分布式锁同类问题）。

## 7. 设计好处总结

1. **成品安全**：并发/重复 merge 从根上消除——串片竞态（共享 filelist.txt）和重复合并都不再可能
2. **恰好一次**：成功时 merge 精确执行一次，产物不重复、中间文件不被重复删除
3. **失败自愈**：失败撤销登记 → TerminalSweepLoop 自动重试 → 环境恢复后收敛，产物不永久缺失
4. **并发安全**：MQ 消费线程 / TerminalSweepLoop / 直连 RPC 线程三个触发源全部安全（同一把锁 + 同一集合）
5. **零成本起步**：Meyers singleton 惰性初始化，无启动开销、无全局顺序问题
6. **跨 job 串行化**（附加收益）：全局锁让不同 job 的 merge 也串行——消除了跨 job 共享 filelist.txt 的潜在串片（#10 修复）
