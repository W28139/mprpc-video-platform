# Job / Shard / Attempt 三层模型设计

> 文档日期：2026-08-07
> 关联代码：`scheduler_service.cpp`（生成）、`result_collector.cpp`（校验）、`transcode_worker.cpp`（消费）、`common_store.h`（数据模型）

## 1. 三层关系总览

视频平台以「任务 → 分片 → 执行尝试」三层粒度组织一次转码：

```text
Job（任务）                          一次用户提交 = 一个输入视频 → 一个完整输出
 │  └ 按时间切片
 ├── Shard 0 ── attempt 0 ── attempt 1 ── ...   ← 同一分片的多次执行尝试
 ├── Shard 1 ── attempt 0 ── attempt 2
 └── Shard N ── attempt 0
```

| 层次 | 语义 | 生命周期 | 标识 |
|------|------|---------|------|
| **Job** | 一次用户提交的完整转码任务 | 提交 → 终态（SUCCESS/FAILED/CANCELED），不可逆 | `job_id` |
| **Shard** | Job 按时间切出的一段子任务（如 30s 视频切成 2×15s） | 创建 → 终态，`job_id` 外键绑定归属 | `shard_id`（全局唯一，绑定 job） |
| **Attempt** | Shard 的**某一次**执行尝试（分配一次、执行一次 = 一个 attempt） | 分配时创建，执行结束即终结 | `attempt_id`（随 retry_count 变化） |

核心关系：**一个 Job 有多个 Shard，一个 Shard 有多次 Attempt**。Attempt 不是持久化实体（无独立表），它挂在 ShardRecord 上：

```cpp
// ShardRecord（shards 表）
std::string shard_id;              // 分片标识，全局唯一
std::string job_id;                // 归属任务
int32_t     retry_count;           // 已重试次数 = 执行代次
std::string attempt_id;            // 当前（最近一次）执行的尝试标识
std::string assigned_worker_id;    // 当前尝试分配给的 Worker
```

## 2. Attempt 的生成规则

attempt_id 由 Scheduler 在 `AssignShard`（分配）时生成（scheduler_service.cpp:1015）：

```text
attempt_id = shard_id + "_attempt_" + retry_count
示例：job_abc_shard_0_attempt_0     ← 第 0 次执行
      job_abc_shard_0_attempt_1     ← 第 1 次执行（重试）
```

每次「失败重试 / 超时重试」流程：`retry_count++` → 生成新 attempt_id → 重置为 WAITING → 重新分配。**格式固定由 Scheduler 单点构造**，消费方（RC）可以安全地从字符串解析出 retry 序号（`parseRetryFromAttempt`）。

## 3. 为什么需要 Attempt——Shard 的多次执行可以并存

一个 Shard 一生会被**执行多次**（失败重试、超时重试、离线重调度），且**新旧执行可能同时在世上**：

```text
超时重扫判定 shard_x 卡死（旧执行其实还活着，只是没心跳）
  → 重置 WAITING → 重新分配 → 新 attempt 开始执行
  → 旧 Worker 之后转码完成，上报结果
  → 同一个 shard_id，两条执行结果都来了
```

此时 `shard_id` 只能回答「是哪个分片」，回答不了「是哪一次执行」——两个执行的结果互相冲突（旧的过期、新的在跑），取消通知也可能误伤。**Attempt 就是"执行代次"的载体**：区分同一 shard 的不同执行，是幂等、防过期、精确取消的共同基础。

## 4. 使用场景与作用

### 场景一：结果上报幂等（防重放）

Worker 转码完成后 `ReportShardResult` **必须携带 attempt_id**。RC 侧（result_collector.cpp:174-196）：

- 同一 attempt 的重复上报（网络重试、MQ 重复投递）→ 状态已是 SUCCESS/FAILED/RETRYING 且 attempt_id 相同 → **直接忽略**，不重复计数、不重复触发重试
- 作用：防「同一结果处理两次」双倍消耗 retry 预算（阶段 8 #8/#3 修复的根因之一）

### 场景二：拒绝旧 Attempt 的迟到结果（防过期覆盖）

核心场景：**新 attempt 已开始执行，旧 attempt 的结果才姗姗来迟**。

```text
Scheduler 判定 shard_x 卡死 → 重分配 → attempt_1（新执行）
旧 Worker 其实没死，完成转码 → 上报 attempt_0 的结果
```

RC 校验（result_collector.cpp:162-169）：从 attempt_id 解析 retry 序号，`incoming_retry < stored_retry` → **拒绝**（"stale result from old attempt, ignored"）。

没有这道校验的后果：旧 attempt 的结果把新 attempt 的状态覆盖成 SUCCESS/FAILED——新执行还在跑，结果已经"落定"，终态判定和重试预算全部错乱。

### 场景三：超时重扫的取消通知精确匹配（防误杀新执行）

Scheduler 的超时重扫（ASSIGNED 卡死 / RUNNING 超时）判定旧执行卡死后，发 `CancelShard(reason=TIMEOUT)` **携带 attempt_id**（scheduler_service.cpp:1389/1479）。Worker 侧（transcode_worker.cpp:207-227）：

```cpp
// 请求带 attempt_id 时仅匹配当前执行的 attempt；
// 不匹配则视为已进入新 attempt，拒绝取消。
```

作用：**重扫的意图是「取消卡死的旧执行、让调度系统安排的合法新执行正常运行」**。若不带 attempt_id，旧通知会把新 attempt 一起杀掉——新执行白分配，可能再次卡死、再次重试，形成死循环式浪费。

### 场景四：用户取消场景无条件取消（与场景三对照）

`CancelJobShards`（用户取消）的通知**不带 attempt_id**（scheduler_service.cpp:665-672）：

```cpp
// 用户取消场景不带 attempt_id：job 已取消，该 shard 的任何执行
// （含重分配后的新 attempt）都该停，命中即取消，无条件匹配
```

为什么两个取消场景行为相反？

| | 超时重扫（TIMEOUT） | 用户取消（CancelJob） |
|---|---|---|
| 意图 | 取消旧执行、**保留新执行** | job 已取消，**所有执行都该停** |
| 带 attempt_id？ | ✅ 需要（精确匹配） | ❌ 不需要（命中即杀） |
| 误杀新执行 | 违背重扫意图（错） | 正是取消语义（对） |

且 shard_id 全局唯一、同一 shard 的所有 attempt 必然同属一个 job——用户取消时杀掉任何 attempt 都不存在误伤"其他任务"。

### 场景五：可观测性

- 所有日志（Scheduler 分配、Worker 执行、RC 处理结果）都输出 attempt_id，可精确追踪「某个 shard 的第几次执行」经历了什么
- 阶段 11 指标按 attempt 维度可分析重试行为

## 5. 设计要点总结

1. **Attempt 是"执行代次"标识，不是独立实体**：挂在 ShardRecord 上随重试递增，单点（Scheduler）构造、格式固定，消费方安全解析
2. **三类防护都建立在 Attempt 上**：幂等（同 attempt 只处理一次）、防过期（旧 attempt 迟到拒绝）、精确取消（TIMEOUT 只杀旧执行）
3. **Attempt 与状态推进（UpdateIfStatus CAS）互补**：CAS 防「旧状态快照覆盖新状态」（状态版本），Attempt 防「旧执行结果干扰新执行」（执行代次）——一个管状态、一个管执行
4. **取消意图决定是否用 Attempt**：要"保新杀旧"（重扫）就带 attempt_id 精确匹配；要"全杀"（用户取消）就无条件——attempt_id 是手段，意图是目的
