## 1. 概述

消息队列是平台引入的**第三个中间件**，定位一句话：**事件通道，可降级组件**——它把"有活可干"和"结果出炉"这两个时刻从"等周期扫描发现"变成"主动喊一声"。

三个中间件的分工与故障语义（这是理解本系列设计的第一把钥匙）：

| 中间件 | 角色 | 管什么 | 故障语义 |
|--------|------|--------|---------|
| **MySQL** | 唯一数据源（真相） | 数据放哪、谁说了算 | **fail-fast**：连不上拒绝服务启动 |
| **Redis** | 读路径加速（镜像/缓存/锁） | 数据怎么读得快 | **降级**：挂了回到阶段 9 行为，按次判断自动恢复 |
| **RabbitMQ** | 事件通道（通知/数据） | 事件怎么及时送达 | **降级**：挂了回到 Pull 轮询 + 直连 RPC，按次判断自动恢复 |

MySQL 管"对不对"，Redis 管"快不快"，MQ 管"及时性"——**后两者都刻意做成可降级组件**：任何中间件的引入都必须回答"它挂了怎么办"，且答案必须是"系统回到它出现之前的可用状态"。

**与文档 3 的分工**：《3. 调度模式演进设计.md》已完整覆盖"调度如何从 2s 轮询变为事件驱动"（TryAssignShard 抽取、SchedulingLoop 共存、自动切换）。本文聚焦 MQ **全貌**：选型、拓扑、MqClient 客户端封装、双通道消息语义、可靠性机制、消费端设计、效果与修复史。

## 2. 为什么引入：没有 MQ 的时代（阶段 9 及之前）

阶段 9（MySQL 化）完成后，调度链路仍是 Pull 模式，两个痛点：

### 2.1 调度延迟被轮询周期钳制

```
SchedulingLoop 线程（固定 2s 一轮）
    ├─ 扫描全部 WAITING shard → 打分 → AssignShard → 推进 ASSIGNED
    └─ 循环（每轮还夹杂超时重扫/启动恢复等可靠性职责）
```

- 任何 shard 就绪，被分配的最坏等待 = 1 个完整周期 2s，**平均 ≈ 1s**（周期中点）
- 转码本身是秒级到分钟级的，1s 的调度延迟对"用户提交 → 出结果"的端到端体验是显著占比

### 2.2 结果上报走直连 RPC

Worker 转码完成 → 直连 ResultCollector 调 `ReportShardResult`（带 3 次重试）。功能可用，但没有"通道"语义——上报的到达依赖网络直达，与调度侧完全异步的链路形态不匹配。

### 2.3 引入后的核心转变

从"周期性扫描谁有活"变成"**有活时主动喊一声**"——shard 就绪的**时刻**被事件直接触发，不再等待周期点。验收线：调度延迟 <100ms（Pull 平均 ~1s）。

## 3. 选型：为什么 RabbitMQ 而不是 Kafka

| 候选 | 结论 | 理由 |
|------|------|------|
| **RabbitMQ** | ✅ 选用 | 消息量是 **shard 级**（千级/天），完全落在 RabbitMQ 的能力区间；AMQP 0-9-1 标准协议，后续可平滑迁移到其他 AMQP broker；rabbitmq-c 客户端库成熟（系统库可直接 link）；topic/direct 等路由语义简单够用 |
| **Kafka** | ❌ 拒绝 | 为百万级吞吐 + 分区日志设计，本平台消息量连它的零头都不到——杀鸡用牛刀；还要引入 partition/replication/offset 管理心智，运维成本不成比例 |
| **纯 RPC（原状）** | ❌ 已被替换 | 只有"调用"语义，没有"事件"语义：无法解耦发布/消费时机，延迟受调用方节奏钳制 |

## 4. 拓扑设计

```
发布端（Scheduler 内部 7 个触发点）         发布端（Worker 转码完成）
   NotifyShardWaiting(shard_id)                TryPublishResultToMq(序列化请求)
            │                                            │
            ▼                                            ▼
   Exchange job.events ──routing key──► Queue shard.waiting     Exchange shard.events ──routing key──► Queue result.pending
   （direct, durable）    "shard.waiting"  （durable）           （direct, durable）   "result.pending"     （durable）
                                                 │                                                        │
                                                 ▼                                                        ▼
                                    Scheduler MqConsumeLoop                                ResultCollector MqResultConsumeLoop
```

| 拓扑要素 | 名字 | 设计决策 |
|----------|------|---------|
| Exchange ×2 | `job.events` / `shard.events` | **direct** + **durable**（Broker 重启拓扑不丢） |
| Queue ×2 | `shard.waiting` / `result.pending` | durable + 非独占 + 非自动删除 |
| Routing key | 与队列**同名** | direct 交换机的 key 即目标队列名，一个 exchange 服务一条事件流，语义直白 |
| 消息持久化 | `delivery-mode=2` | 消息落盘，Broker 重启不丢（验收项"MQ 宕机消息不丢"的基石之一） |

### 4.1 为什么拓扑声明放在发布连接，消费连接只登录 + channel

`ConnectPublish()` 完成全部 `amqp_exchange_declare / queue_declare / queue_bind`；`ConnectConsume()` 只登录 + 开 channel。

- **幂等性**：exchange/queue/binding 同名同参数重复声明无害——任何服务、任何时机声明都是安全的
- **单一职责**：声明集中在一个连接上，消费连接重建（MQ 掉线恢复）无需关心拓扑是否还在

### 4.2 为什么两条事件流分开（job.events 与 shard.events）

两条流的**消费方不同、消息体语义不同**，混用一条流会让消费端被迫区分消息类型：

| 流 | 消费方 | 消息体 | 语义 |
|----|--------|--------|------|
| `job.events` → `shard.waiting` | Scheduler | shard_id 纯文本 | **通知**："有活可干" |
| `shard.events` → `result.pending` | ResultCollector | protobuf 序列化串 | **数据**："结果出炉" |

## 5. 双通道消息语义（核心设计）

### 5.1 shard.waiting = 通知通道：只带 shard_id，消费端重新查 MySQL

消息体 = `shard_id` 纯文本（`content_type=text/plain`）。消费端（Scheduler）收到后**重新查 MySQL** 拿最新状态，再走分配。

**为什么消息不携带 shard 快照**：

> MySQL 是唯一数据源（阶段 9 原则）。消息携带快照反而有**陈旧风险**——shard 可能已被其他路径（轮询兜底、另一条消息）分配，消费端必须查库才能做幂等判断。与阶段 9"不构造本地副本"的原则一脉相承：**通道只传身份（ID），事实永远查库**。

### 5.2 result.pending = 数据通道：必须携带完整数据

消息体 = `ReportShardResultRequest` 的 protobuf 序列化串（`content_type=application/octet-stream`）。

**为什么这条通道必须带数据**：执行结果（`is_success` / `exit_code` / `output_path` / `screenshot_path` / `elapsed_ms`）**不在 MySQL 中**——shard 表只存静态字段，结果不落库（落在 job 终态判定时收敛）。这些数据无法从库中查回，必须随消息传递。

**两条通道的取舍依据**：数据在不在 MySQL？在 → 通知通道（只传 ID，消费端查库，最抗陈旧）；不在 → 数据通道（传全量，消费端直接消费）。

## 6. MqClient 封装设计（rabbitmq-c / AMQP 0-9-1）

`mq_client.h/.cpp`（~460 行），单例，对外接口：`Init / PublishShardWaiting / PublishResult / ConsumeBlocking / Ack / connected / Reconnect`。

### 6.1 双连接双锁（含踩坑史）

**初版单连接 + 单锁为什么必炸**：rabbitmq-c 连接非线程安全。`ConsumeBlocking` 持锁阻塞等消息（最长 2s）期间，ScheduleJob 的 work 线程切分完调 `PublishShardWaiting` 要等**同一把锁** → RPC 处理超过客户端超时 → 实测 `recv response header error! errno:11`，任务无法提交。

**修复：发布（`publish_conn_`/`publish_mutex_`）与消费（`consume_conn_`/`consume_mutex_`）严格分连接分锁**：

- 消费阻塞只等消费锁；发布持锁时间 = 单条 publish（微秒级），互不阻塞
- 拓扑声明由发布连接完成；消费连接只登录 + channel

### 6.2 连接建立与超时兜底

```
OpenChannel: amqp_socket_open → SetSocketTimeouts(fd, 2s) → amqp_login(vhost "/", guest/guest) → channel 1
```

- `SetSocketTimeouts`：`SO_RCVTIMEO` / `SO_SNDTIMEO` 各 2s——**socket 层兜底**，即使上层 poll/consume 逻辑失效，读/写也不会无限阻塞
- guest/guest + vhost "/"：RabbitMQ 默认账号，本平台内网部署场景不引入复杂认证

### 6.3 发布路径

`PublishShardWaiting` / `PublishResult`：

- 消息属性：`delivery_mode=2`（persistent，落盘）
- 发布失败 → LOG_WARN → **重建发布连接重试 1 次** → 仍失败 return false，调用方降级（Scheduler 侧由轮询兜底，Worker 侧回退直连 RPC）

### 6.4 消费路径：poll 移出锁（log 14 Bug 1 的修复产物）

`ConsumeBlocking(queue, body, delivery_tag, timeout_ms)` 的三段式：

```
① 持锁：首次消费该队列时 amqp_basic_consume（consumed_queues_ 记录）
② 无锁 poll(fd, 2s)：超时 → 正常返回 false；错误 → 持锁销毁连接
③ 有数据才持锁：amqp_consume_message(conn, &envelope, {0,0})  ← 0 超时立即尝试
```

**为什么 poll 必须移出锁**（log 14 Bug 1，2026-08-04 复验发现）：

> 初版 poll 在锁内 + 消费线程紧循环 → `consume_mutex_` 几乎 100% 被占 → `connected()` 的 `try_lock_for(1s)` 永远失败 → `consume lock busy` 无限刷屏 + SchedulingLoop 永远判 `(mq=pull)`——**Push 模式被误判为 Pull，调度模式错误降级**。
>
> 修复：poll 期间无并发写者（消费连接只由消费线程销毁），所以 poll 完全不需要锁；锁只保护 conn 内部状态的读写（read/销毁/重建）。

### 6.5 ACK 与 connected()：可靠性单点必须无锁

| 方法 | 实现 | 设计意图 |
|------|------|---------|
| `Ack(tag)` | `try_lock_for(1s)`，拿不到锁 → WARN "ack skipped, msg will redeliver"；`amqp_basic_ack` multiple=false | 消费锁可能被 `ConsumeBlocking` 短暂持有，Ack 不无限等锁——**ack 失败只是重投**，由消费幂等吸收 |
| `connected()` | **无锁**：`consume_alive_.load() && consume_conn_ != nullptr`（`consume_alive_` 为 atomic） | "MQ 在线"是 SchedulingLoop 决定调度模式的**单点判断**，它的误判代价是模式错误降级——必须是原子无锁读取 |
| `Reconnect()` | `try_lock_for(1s)` → 重建消费连接，`consumed_queues_` 清空，basic_consume 由 ConsumeBlocking 惰性重建 | 重建期间不阻塞发布；清空记录保证新连接上重新 consume |

### 6.6 与 RedisClient 同哲学：可降级组件

`Init()`：`mq_enable=0` 直接禁用；连接失败只 LOG_WARN 置 `enabled_=false`，**不拒绝服务启动**（与 MySQL 的 fail-fast 形成对照，与 RedisClient 完全同构）。配置键：`mq_enable / mq_host / mq_port`（8 个 conf：本机 5 个 + docker 3 个；发布端在 Scheduler，故 job_service/worker_manager 无 mq 配置）。

## 7. 可靠性机制：at-least-once 语义的完整拼图

"MQ 宕机消息不丢"由四层拼图构成：

| 层 | 机制 | 防什么 |
|----|------|--------|
| ① | **durable queue**（Broker 重启队列还在） | 队列消失 |
| ② | **delivery-mode=2**（消息落盘） | 消息丢失 |
| ③ | **手动 ACK**（`Ack` 处理成功后才确认；不 ack 的消息 Broker 重投） | 消费中途崩溃丢消息 |
| ④ | **消费幂等**（查库判断 + 三重防护） | 重投导致重复分配/重复处理 |

**为什么消费端（几乎）无条件 ACK**——消息的"职责"是**触发一次检查**，检查已做即完成职责：

- **分配失败**（无 worker/过载/锁占用）→ 不重回队列，否则无限重投风暴；由 SchedulingLoop 兜底扫描 5s 内再试
- **重复投递**（Broker 重发）→ 查 MySQL 非 WAITING 即幂等跳过，配合 TryAssignShard 三重防护（状态复核 + Redis 分布式锁 + MySQL 条件更新）
- **RC 侧**：`MqResultConsumeLoop` 对处理结果也**无条件 Ack**（含解析失败 `ack & drop`）——处理失败的情况由 RC 的重试判定（`HandleReportShardResult` 内部 FAILED→RETRYING 逻辑）走既有重试链路，不依赖消息重投

> ⚠️ 代码事实注记：`mq_client.h` 头注释写"处理成功才 ack"，但实际 `MqResultConsumeLoop`（`result_collector.cpp:556-559`）是无条件 Ack——以代码为准，语义为"消费成功即完成职责"。

**正确性底线**：MQ 是 at-least-once 通道，重复由幂等吸收，丢失由轮询兜底扫描吸收——**MQ 从不承诺 exactly-once，系统整体却是 exactly-once 的**（一个 shard 至多被一个 worker 执行、结果至多落定一次）。

## 8. 消费端与发布端设计

### 8.1 Scheduler：MqConsumeLoop（分配触发）

```
循环:
  !connected() → Reconnect() 失败 → WARN + sleep 2s（SchedulingLoop 轮询是兜底）
  成功 → INFO "MQ reconnected, resume push scheduling"
  → ConsumeBlocking("shard.waiting", 2s)
  → 查 MySQL 幂等判断:
      shard 不存在 → WARN "ack & drop (stale msg)"
      状态非 WAITING → "skip (idempotent)"（已被轮询分配/重复投递）
  → LoadOnlineWorkers + TryAssignShard → 无条件 Ack
```

分配实现与轮询**共用** `TryAssignShard`（详见文档 3 §3.1）：终态检查 → 状态复核 → 加权打分 → 分布式锁 → AssignShard → 推进 ASSIGNED → job RUNNING。两个来源行为完全一致，杜绝逻辑漂移。

### 8.2 Scheduler：NotifyShardWaiting 的 7 个发布点

helper（`scheduler_service.cpp:59-70`）门卫 `mq.inited() && mq.enabled()`，发布失败只 WARN（轮询兜底）。**原则：任何 shard 变为 WAITING 的路径都必须发布**：

| # | 调用点 | 触发时机 |
|---|--------|---------|
| 1 | ScheduleJob（:265） | 切分新建每个 shard 后 |
| 2 | RescheduleShard（:435） | 重试重置 WAITING 后 |
| 3 | NotifyWorkerOffline（:505） | Worker 离线批量重置 WAITING 后 |
| 4-5 | SchedulingLoop 启动恢复（:1085/:1103） | 崩溃重启残留 ASSIGNED/RUNNING → WAITING |
| 6 | ASSIGNED 卡死超时重置（:1417） | 分配超时（30s） |
| 7 | RUNNING 超时重置（:1504） | 卡死检测重置（5min） |

（文档 3 记载为 4 个触发点，是阶段 10 当时的计数；现行代码为 7 处——**凡重置为 WAITING 即发布**。）

### 8.3 ResultCollector：MqResultConsumeLoop（结果聚合）

```
循环:
  !connected() → Reconnect() 失败 → WARN + sleep 2s（Worker 回退直连 RPC）
  → ConsumeBlocking("result.pending", 2s)
  → ParseFromString → HandleReportShardResult(req, resp) → 无条件 Ack
```

核心复用：`HandleReportShardResult` 是 static 公共方法——**RPC handler 与 MQ 消费共用同一实现**，聚合/重试/终态判定逻辑零改动（幂等由 attempt_id + 状态检查兜底）。

### 8.4 Worker：结果上报 MQ 优先，回退直连 RPC

`TryPublishResultToMq`：`SerializeToString` → `PublishResult`，失败回退直连 `rc_stub.ReportShardResult`（**3 次重试**）。每次上报独立判断，MQ 恢复自动切回。

## 9. 降级哲学与共存

与 Redis 完全同哲学：**没有切换状态机，每轮按当前事实决定自己的行为**（详见文档 3 §3.5，这里只给全景）：

```
MQ 在线:  SchedulingLoop interval=5000ms (mq=push)  ← Push 主路径 + 5s 兜底扫描
MQ 掉线:  SchedulingLoop 自动恢复 2000ms (mq=pull)  ← 降级为阶段 9 行为，任务仍完成
          结果上报同时回退直连 RPC
MQ 恢复:  Reconnect 成功 → 消费线程继续消费 → SchedulingLoop 检测 connected()==true → 自动切回 push
```

**为什么 MQ 在线时轮询不彻底停掉**：SchedulingLoop 还承担 Push 无法替代的可靠性职责——超时重扫（ASSIGNED 30s / RUNNING 5min 卡死检测）、启动恢复、progress_watch 卡死确认。且 5s 兜底覆盖 Push 的新故障面（消息丢失/发布失败）：**最坏情况是回到阶段 9 的延迟，绝不丢任务**。

配套细节：超时重扫从"每 15 轮"改为**按时间 30s**——interval 随 MQ 状态在 2s↔5s 间变化，按轮次会导致重扫周期漂移（15×5s=75s）。

## 10. 设计效果（实测验证）

| 验收项 | 结果 |
|--------|------|
| **调度延迟 <100ms**（验收核心） | ✅ **实测 33ms**：shard 创建 → MQ 消费分配 33ms（对比 Pull 平均 ~1s，量级下降 30 倍） |
| MQ 故障全链路不回归 | ✅ 8 shard 全 JOB_SUCCESS：分配走 Pull 轮询、结果走直连 RPC，`interval=2000ms (mq=pull)` 自动接管 |
| MQ 恢复自动切回 | ✅ 新任务 SUCCESS，`interval=5000ms (mq=push)`，MqConsumeLoop 恢复消费 |
| MQ 宕机消息不丢 | ⏳ 代码就绪（durable + persistent + 手动 ACK + 消费幂等），**真实 Broker 重启实测待用户 sudo**（本机无权限操作 rabbitmq 服务） |
| 全链路功能 | ✅ MQ 正常时 2 shard 全 SUCCESS：Worker 侧 `SUCCESS published to MQ`、RC 消费聚合 JOB_SUCCESS |

**修复史（两个真实缺陷）**：

| Bug | 现象 | 根因 | 修复 |
|-----|------|------|------|
| 单连接单锁（阶段 10 初版） | 提交任务卡死，`recv response header error! errno:11` | ConsumeBlocking 持锁阻塞，发布等同一把锁 → RPC 超时 | 双连接双锁，发布/消费互不阻塞 |
| 消费锁占用（log 14 Bug 1） | `consume lock busy` 刷屏 + SchedulingLoop 永远 `(mq=pull)` | poll(2s) 在锁内 + 紧循环 → consume_mutex_ 几乎 100% 被占 → connected() 永远拿不到锁 | ① poll 移出锁 ② connected() 改 `consume_alive_` 原子无锁读取 ③ 销毁分支持锁且先置标志 |

> 启示：Push 模式下"MQ 在线"的判断本身是可靠性的**新单点**——它的误判代价是调度模式错误降级，因此 connected() 必须是原子无锁的读取。

## 11. 遗留与边界

1. **真实 Broker 重启测试待执行**（用户 sudo）：`stop_app` → 提交任务（消息应积压在持久化队列）→ `start_app` → 任务恢复完成。代码路径已全部就绪，只差一次真实重启验证
2. **rabbitmqctl 本机不可用**（任何子命令输出 Usage）：影响运维便利性（无法命令行查队列），不影响功能；排查 erlang cookie/脚本路径
3. **guest/guest 默认账号**：内网单机部署可接受；多租户/公网场景需换账号或加 VHost 隔离
4. **消息体积**：result.pending 消息体 = 序列化请求（含路径字符串），shard 级消息量下远低于 AMQP 限制，无需分块/压缩
5. **MQ 单实例**：Broker 本身无高可用（rabbitmq 集群超出本阶段范围）；宕机期间的调度延迟退化到 Pull 级别，任务不丢
