## 1. 概述：第三个中间件

消息队列是平台引入的**第三个中间件**，定位一句话：**事件通道，可降级组件**——它把"有活可干"和"结果出炉"这两个时刻从"等周期扫描发现"变成"主动喊一声"。

三个中间件的分工与故障语义（这是理解本系列设计的第一把钥匙）：

| 中间件 | 角色 | 管什么 | 故障语义 |
|--------|------|--------|---------|
| **MySQL** | 唯一数据源（真相） | 数据放哪、谁说了算 | **fail-fast**：连不上拒绝服务启动 |
| **Redis** | 读路径加速（镜像/缓存/锁） | 数据怎么读得快 | **降级**：挂了回到阶段 9 行为，按次判断自动恢复 |
| **RabbitMQ** | 事件通道（通知/数据） | 事件怎么及时送达 | **降级**：挂了回到 Pull 轮询 + 直连 RPC，按次判断自动恢复 |

MySQL 管"对不对"，Redis 管"快不快"，MQ 管"及时性"——**后两者都刻意做成可降级组件**：任何中间件的引入都必须回答"它挂了怎么办"，且答案必须是"系统回到它出现之前的可用状态"。

**与文档 3 的分工**：《3. 调度模式演进设计.md》已完整覆盖"调度如何从 2s 轮询变为事件驱动"（TryAssignShard 抽取、SchedulingLoop 共存、自动切换）。本文聚焦 MQ 本身：**先讲共享与解耦这条关键前提，再把两个应用点分开记录，最后是两者共用的基础设计**。

## 2. 共享与解耦：理解 MQ 的第一条关键前提

### 2.1 每个服务进程各自持有一个 MqClient 单例——共享代码，不共享内存

`MqClient` 是进程内单例，但**每个服务进程各自持有一个**，彼此没有共享任何内存或连接：

| 进程 | MqClient 角色 | 用到的连接 | 职责 |
|------|--------------|-----------|------|
| **Scheduler** | 发布 + 消费 | `publish_conn_` + `consume_conn_`（双连接） | 7 个发布点发通知 + MqConsumeLoop 消费分配 |
| **TranscodeWorker** | 只发布 | `publish_conn_` | 转码完成发布结果 |
| **ResultCollector** | 只消费 | `consume_conn_` | MqResultConsumeLoop 消费结果聚合 |

**共享的是代码**（同一个 `mq_client.h/.cpp`、同一套可靠性机制、同一个降级哲学）；**共享的还有 Broker 上的通道**（同一个 queue、同一批消息）；**但绝不共享的是各进程自己的连接、锁、内存状态**。

> **与 RedisClient 完全同理**：每个进程也各自持有一个 RedisClient 单例，连接是进程私有的（redisContext 非线程安全，进程内单连接 + mutex）；共享的只有 Redis **server 端**的数据（`worker:load` hash、`mprpc:endpoints` hash、`shard:lock:*` 锁 key——所有进程读写 server 上同一份数据）。MQ 与 Redis 一脉相承：**共享的永远是"服务端的数据/通道"，不共享的永远是"客户端进程的连接与内存"**。

### 2.2 两个应用点总览（全文结构预告）

| | 应用点 1：调度通知 | 应用点 2：结果上报 |
|---|---|---|
| 通道 | `job.events` → `shard.waiting` | `shard.events` → `result.pending` |
| 发布端 | Scheduler（内部 7 个触发点） | Worker（转码完成） |
| 消费端 | Scheduler MqConsumeLoop | ResultCollector MqResultConsumeLoop |
| 消息体 | shard_id 纯文本（通知） | 序列化结果请求（数据） |
| 解决什么 | 调度延迟被 2s 轮询钳制（1s → 33ms） | 结果上报直连 RPC 无"通道"语义 |
| 降级路径 | SchedulingLoop 恢复 2s 轮询 | Worker 回退直连 RPC（3 次重试） |
| 是否依赖另一条 | **否**（完全独立） | **否**（完全独立） |

**本文组织结构**：第 3、4 节分别记录两个应用点；第 5 节总结独立与共享；第 6 节起是两者**共用**的基础设计（选型/拓扑/消息语义/客户端封装/可靠性）。

## 3. 应用点 1：调度通知通道（`job.events` → `shard.waiting`）

### 3.1 解决什么问题

阶段 9 调度链路是 Pull 模式：SchedulingLoop 固定 2s 一轮扫描 WAITING shard → 任何 shard 就绪后最坏等 1 个完整周期 2s、**平均 ≈1s**（周期中点）。转码是秒级到分钟级的，1s 调度延迟在"用户提交 → 出结果"的端到端体验里是显著占比。

引入后：**不是"Pull 改成 Push"，而是"Pull + Push 双模式共存，按 `connected()` 每轮自动切换"**——

```
MQ 在线:  SchedulingLoop interval=5000ms (mq=push)  ← Push 主路径 + 5s 兜底扫描
MQ 掉线:  SchedulingLoop 自动恢复 2000ms (mq=pull)  ← 降级为阶段 9 行为，任务仍完成
MQ 恢复:  Reconnect 成功 → 消费线程继续消费 → SchedulingLoop 检测 connected()==true → 自动切回 push
```

> 追问：为什么 MQ 在线时轮询不彻底停掉？——SchedulingLoop 还承担 Push 无法替代的可靠性职责：超时重扫（ASSIGNED 30s / RUNNING 5min 卡死检测）、启动恢复、progress_watch 卡死确认。且 5s 兜底覆盖 Push 的新故障面（消息丢失/发布失败）：**最坏情况是回到阶段 9 的延迟，绝不丢任务**。配套细节：超时重扫从"每 15 轮"改为**按时间 30s**——interval 随 MQ 状态在 2s↔5s 间变化，按轮次会导致重扫周期漂移（15×5s=75s）。

### 3.2 7 个发布点（凡重置为 WAITING 即发布）

helper（`scheduler_service.cpp:59-70`）门卫 `mq.inited() && mq.enabled()`，发布失败只 WARN（轮询兜底）。**原则：任何 shard 变为 WAITING 的路径都必须发布**：

| # | 调用点（调用NotifyShardWaiting） | 触发时机 |
|---|--------|---------|
| 1 | ScheduleJob（:265） | 切分新建每个 shard 后 |
| 2 | RescheduleShard（:435） | 重试重置 WAITING 后 |
| 3 | NotifyWorkerOffline（:505） | Worker 离线批量重置 WAITING 后 |
| 4-5 | SchedulingLoop 启动恢复（:1087/:1105） | 崩溃重启残留 ASSIGNED/RUNNING → WAITING |
| 6 | ASSIGNED 卡死超时重置（:1419） | 分配超时（30s） |
| 7 | RUNNING 超时重置（:1506） | 卡死检测重置（5min） |

（文档 3 记载为 4 个触发点，是阶段 10 当时的计数；现行代码为 7 处——**凡重置为 WAITING 即发布**。）

### 3.3 消费端：MqConsumeLoop（`scheduler_service.cpp:1607-1676`）

```
循环:
  !connected() → Reconnect() 失败 → WARN + sleep 2s（SchedulingLoop 轮询是兜底）
  成功 → INFO "MQ reconnected, resume push scheduling"
  → ConsumeBlocking("shard.waiting", 2s)
  → 查 MySQL 幂等判断:
      shard 不存在 → WARN "ack & drop (stale msg)"
      状态非 WAITING → "skip (idempotent)"（已被轮询分配/重复投递）
  → LoadOnlineWorkers + TryAssignShard → 无条件 Ack
```

分配实现与轮询**共用** `TryAssignShard`（详见文档 3 §3.1）：终态检查 → 状态复核 → 加权打分 → 分布式锁 → AssignShard → 推进 ASSIGNED → job RUNNING。两个来源行为完全一致，杜绝逻辑漂移。

## 4. 应用点 2：结果上报通道（`shard.events` → `result.pending`）

### 4.1 解决什么问题

阶段 9：Worker 转码完成 → 直连 ResultCollector 调 `ReportShardResult`（带 3 次重试）。功能可用但没有"通道"语义——上报的到达依赖网络直达，与调度侧完全异步的链路形态不匹配。MQ 让结果"出炉"成为事件流的一环。

### 4.2 价值评估：为什么这条通道值得做（诚实版本）

**先承认它不解决什么**——与调度通道不同，这条通道没有痛点级价值：

- **不解决延迟问题**：Worker 转码完**立即**上报，没有轮询周期可被钳制——调度通道的痛点（2s 周期、平均 1s 延迟）在结果链路根本不存在
- **不解决削峰问题**：结果上报是秒级/分钟级事件流（千级/天），直连 RPC 毫无压力

**它真正带来的收益**（按量级排序）：

1. **结果不丢的窗口更大**（唯一的"硬"收益）：RC 短暂不可用（重启中）时，直连 RPC 3 次重试耗尽即丢——之后只能靠 shard 卡 RUNNING → 5min 超时重扫 → 重置 WAITING → **重复转码**兜底；而 MQ 消息在队列积压，RC 恢复后照常消费，一次转码结果不浪费。这把"结果丢失"从"大概率触发重复转码"降为"几乎不发生"
2. **Worker 发完即走**：上报不依赖 RC 在不在线（同步 RPC 也就等几毫秒，收益小但真实）
3. **事件流统一**：分配与结果都是事件，监控/重放/审计走同一套链路（软价值）

**为什么还是做了——关键在边际成本，不在收益**：

- **共享 MqClient**：应用点 1 已把 MqClient、拓扑声明、可靠性机制全部搭好，无新增依赖
- **拓扑声明幂等**：`shard.events`/`result.pending` 只是多两个 declare，任何时机声明都安全
- **消费复用**：`HandleReportShardResult` 是 static 公共方法，RPC handler 与 MQ 消费共用同一实现，零重复逻辑
- **回退路径现成**：失败回退直连 RPC，原路径从未删除

**收益有限（不丢结果窗口 + 解耦）但成本几乎为零（搭应用点 1 的便车）= 值得做**；反过来，如果它需要独立引入一套基础设施，那就不值。

> 一句话：**应用点 1 是"问题驱动"（有痛点），应用点 2 是"能力驱动"（有便车）——它的存在理由不是收益大，而是成本小。**（面试时能主动讲清这一层，比全盘背书"MQ 让结果上报通道化"高级得多。）

### 4.4 发布端：Worker（MQ 优先，回退直连 RPC）

转码完成后（`transcode_worker.cpp:381-395`）先构造 `ReportShardResultRequest`（MQ 与 RPC 共用的同一请求结构），然后：

```cpp
// MQ 优先：publish 成功即视为已投递，RC 消费后走同一聚合逻辑
if (TryPublishResultToMq(result_req))          // :395
    result_reported = true;                     // 发布成功 → 不再走 RPC
// MQ 行不通，RPC 重试 3 次（retry>0 时 sleep 1s）
for (int retry = 0; retry < 3 && !result_reported; ++retry)
    rc_stub.ReportShardResult(&ctrl, &result_req, &result_resp, nullptr);
```

- **发布成功 = 上报完成**：Worker 不等 RC 确认（消息进队列即视为投递），**不会再走 RPC**——一次上报只走一条路径
- **失败回退**：`PublishResult` 失败（含重建重试）→ 直连 RPC 最多 3 次，成功且 `accepted()` 为止
- **每次上报独立判断**：MQ 恢复后自动切回 MQ——与调度模式（push/pull）无关

### 4.5 消息形态：Broker 上长什么样

| 维度 | 值 |
|------|-----|
| Exchange / Routing key | `shard.events`（direct, durable）/ `result.pending` |
| content_type | `application/octet-stream`（二进制 protobuf） |
| delivery_mode | 2（persistent，落盘——Broker 重启不丢） |
| body | `ReportShardResultRequest` 的 `SerializeToString` 序列化串 |
| 消息体字段 | shard_id / job_id / worker_id / attempt_id / is_success / exit_code / error_msg / output_path / elapsed_ms / shard_index |

与调度通道的对比：调度通道是**通知**（只传 shard_id，消费端查库）；这里是**数据**（结果不落库，必须随消息传全量——见 6.3 双通道语义）。

### 4.6 消费端：RC MqResultConsumeLoop（四步循环，`result_collector.cpp:504-553`）

```
循环（每 2s 轮询一次队列）:
  ① 连接保障: !connected() → Reconnect()，失败 → WARN + sleep 2s（期间 Worker 走直连 RPC）
  ② 阻塞消费: ConsumeBlocking("result.pending", body, delivery_tag, 2000)（:527）
              超时无消息 → 返回 false → continue（循环顶部检查连接）
  ③ 解析+处理: req.ParseFromString(body)
              成功 → HandleReportShardResult(&req, &resp)（:538）
              失败 → WARN "failed to parse ... ack & drop"（:542-544）
  ④ 确认: mq.Ack(delivery_tag)（:547）——失败 → WARN "broker may redeliver"
```

**核心复用**：第 ③ 步的 `HandleReportShardResult` 是 static 公共方法（`result_collector.cpp:50`）——**RPC handler（`:45`）与 MQ 消费（`:538`）共用同一实现**，聚合/重试/终态判定逻辑零改动。**两个入口、一个处理器**：谁收到结果都走同一套幂等 + 聚合逻辑，杜绝逻辑漂移。

### 4.7 聚合入口：HandleReportShardResult（四道检查 + 终态收敛）

收到结果后依次过四道检查（`result_collector.cpp:50-115`）：

| 检查 | 条件 | 处理 |
|------|------|------|
| ① 存在性 | shard 不在 MySQL | 拒绝（accepted=false）——陈旧消息 |
| ② attempt 幂等 | 上报的 retry 数 < 库里已记录的 retry 数 | 拒绝——旧 attempt 的过期结果 |
| ③ 已成功幂等 | shard 已 SHARD_SUCCESS | accepted=true，不再处理——重复上报/重投 |
| ④ 同 attempt 重复 | FAILED/RETRYING 且 attempt_id 相同 | 走重试判定（FAILED→RETRYING） |

通过后：shard → SUCCESS → `CheckJobDone` 查同 job 全部 shard 终态 → 全终态则收集 output_path → `Merge` 产出合并视频 → `MarkJobTerminal` 落 job 终态。

> 面试要点：结果通道的幂等**不依赖 MQ 的 exactly-once**（MQ 是 at-least-once，会重投）——幂等全靠这四道"查库 + attempt 校验"，MQ 只负责送达。

### 4.8 失败路径与兜底（每条失败都有归处）

| 失败点 | 后果 | 兜底 |
|--------|------|------|
| MQ 发布失败（含重建重试） | `PublishResult` false | Worker 回退直连 RPC（3 次，sleep 1s） |
| RC 不可用（重启中） | MQ 路径：消息积压在 durable 队列，RC 恢复后照常消费；RPC 路径：重试耗尽 → 结果丢 | 结果丢后 shard 卡 RUNNING → Scheduler 5min 超时重扫 → 重置 WAITING → 重复转码 |
| 消费解析失败 | 消息无法处理 | ack & drop（`result_collector.cpp:542-544`）；若真需要重试走 HandleReportShardResult 的 FAILED→RETRYING 链路 |
| ACK 失败 | Broker 重投同一条 | 幂等检查 ②③④ 吸收（至多重复处理一次，不重复落定） |

**正确性底线**：结果至多落定一次（shard 状态推进有 MySQL 条件更新 + attempt 幂等）；结果丢失由"超时重扫 → 重复转码"兜底——MQ 从不是结果正确性的依赖，只是让"结果不丢"从大概率重复转码变成几乎不重复。

### 4.9 与调度通道的独立性

**两条通道零功能依赖**：通道独立（两个 exchange/queue）、降级判断独立（Scheduler 的 `connected()` 管调度，Worker 的上报判断管结果）、代码路径独立（两个消费线程）。因此"调度走 Pull 但结果走 MQ"、"调度走 Push 但结果回退 RPC"等**交叉组合全部成立**——MQ 任何程度的故障只会让对应链路降级，绝不连锁瘫痪。

## 5. 两个应用点的独立与共享（总结）

| 维度 | 独立 | 共享 |
|------|------|------|
| 通道 | 两个 exchange/queue 完全分开 | Broker 同一个（故障一起挂） |
| 降级判断 | 各自独立、按次判断 | 同一哲学：新增通道 + 原路径永做兜底 |
| 代码路径 | 三个进程各自一个 MqClient 单例 | 同一个 `mq_client.h/.cpp` 封装 |
| 可靠性 | — | 同一套：durable + delivery-mode=2 + 手动 ACK + 消费幂等 |
| 内存/连接 | **绝不共享**（各进程私有连接、锁、内存） | 共享的只有 Broker 上的队列与消息 |

> 一句话：**两个应用点共享"代码与通道"，不共享"内存与连接"；功能上零依赖，降级上互不牵连**——这是"可降级组件"设计的必然要求：通道独立，MQ 故障时两条链各自回到阶段 9 行为，系统最坏 = 阶段 9 延迟，绝不丢任务。

## 6. 共同基础：选型、拓扑、消息语义、封装、可靠性

### 6.1 为什么选 RabbitMQ 而不是 Kafka？

| 候选 | 结论 | 理由 |
|------|------|------|
| **RabbitMQ** | ✅ 选用 | 消息量是 **shard 级**（千级/天），完全落在 RabbitMQ 的能力区间；AMQP 0-9-1 标准协议，后续可平滑迁移到其他 AMQP broker；rabbitmq-c 客户端库成熟（系统库可直接 link）；topic/direct 等路由语义简单够用 |
| **Kafka** | ❌ 拒绝 | 为百万级吞吐 + 分区日志设计，本平台消息量连它的零头都不到——杀鸡用牛刀；还要引入 partition/replication/offset 管理心智，运维成本不成比例 |
| **纯 RPC（原状）** | ❌ 已被替换 | 只有"调用"语义，没有"事件"语义：无法解耦发布/消费时机，延迟受调用方节奏钳制 |

> 追问：为什么不用 Redis 的 pub/sub 当事件通道？——Redis pub/sub 是 **fire-and-forget**（消费方不在线消息直接丢），无法满足"MQ 宕机消息不丢"的可靠性要求；MQ 需要的是 durable 队列 + 持久化消息 + 手动 ACK 的 at-least-once 语义，这正是 RabbitMQ 的领域。

### 6.2 拓扑设计

```
发布端（Scheduler 内部 7 个触发点）         发布端（Worker 转码完成）
   NotifyShardWaiting(shard_id)                TryPublishResultToMq(序列化请求)
            │                                            │
            ▼                                            ▼
   Exchange job.events ──routing key──► Queue shard.waiting     Exchange shard.events ──routing key──► Queue result.pending
   （direct, durable）    "shard.waiting"  （durable）           （direct, durable）   "result.pending"     （durable）
                                                 │                                                        │
                                                 ▼                                                        ▼
                                    Scheduler MqConsumeLoop                                ResultCollector MqResultConsumeLoop
```

| 拓扑要素 | 名字 | 设计决策 |
|----------|------|---------|
| Exchange ×2 | `job.events` / `shard.events` | **direct** + **durable**（Broker 重启拓扑不丢） |
| Queue ×2 | `shard.waiting` / `result.pending` | durable + 非独占 + 非自动删除 |
| Routing key | 与队列**同名** | direct 交换机的 key 即目标队列名，一个 exchange 服务一条事件流，语义直白 |
| 消息持久化 | `delivery-mode=2` | 消息落盘，Broker 重启不丢（"MQ 宕机消息不丢"验收项的基石之一） |

> 追问①：为什么拓扑声明放在发布连接，消费连接只登录 + channel？（`ConnectPublish` 完成全部 `amqp_exchange_declare / queue_declare / queue_bind`，`ConnectConsume` 只登录 + 开 channel）——① **幂等性**：exchange/queue/binding 同名同参数重复声明无害，任何服务、任何时机声明都安全；② **单一职责**：声明集中在一个连接上，消费连接重建（MQ 掉线恢复）无需关心拓扑是否还在。
> 追问②：为什么两条事件流分开（job.events 与 shard.events）？——两条流的**消费方不同、消息体语义不同**（见 6.3）：混用一条流会让消费端被迫区分消息类型。

### 6.3 双通道消息语义为什么不同（核心设计）

**`shard.waiting` = 通知通道**：消息体 = `shard_id` 纯文本（`content_type=text/plain`）。消费端（Scheduler）收到后**重新查 MySQL** 拿最新状态，再走分配。

**`result.pending` = 数据通道**：消息体 = `ReportShardResultRequest` 的 protobuf 序列化串（`content_type=application/octet-stream`），必须携带完整数据。

**分界依据一句话：数据在不在 MySQL？**

| 通道 | 数据在 MySQL？ | 消息体 | 为什么 |
|------|---------------|--------|--------|
| `shard.waiting` | ✅ 在（shard 状态/参数都在库里） | 只传 shard_id | 传快照反而有**陈旧风险**——shard 可能已被其他路径（轮询兜底、另一条消息）分配，消费端必须查库才能做幂等判断。**通道只传身份（ID），事实永远查库**（与阶段 9"不构造本地副本"原则一脉相承） |
| `result.pending` | ❌ 不在（执行结果：`is_success`/`exit_code`/`output_path`/`screenshot_path`/`elapsed_ms` 不落库，在 job 终态判定时收敛） | 传全量序列化请求 | 这些数据无法从库中查回，必须随消息传递 |

### 6.4 MqClient 封装：双连接双锁（含踩坑史）

`mq_client.h/.cpp`（~460 行），单例，对外接口：`Init / PublishShardWaiting / PublishResult / ConsumeBlocking / Ack / connected / Reconnect`。

**初版单连接 + 单锁为什么必炸**：rabbitmq-c 连接非线程安全。`ConsumeBlocking` 持锁阻塞等消息（最长 2s）期间，ScheduleJob 的 work 线程切分完调 `PublishShardWaiting` 要等**同一把锁** → RPC 处理超过客户端超时 → 实测 `recv response header error! errno:11`，任务无法提交。

**修复：发布（`publish_conn_`/`publish_mutex_`）与消费（`consume_conn_`/`consume_mutex_`）严格分连接分锁**——消费阻塞只等消费锁；发布持锁时间 = 单条 publish（微秒级），互不阻塞。

**连接建立与超时兜底**：`amqp_socket_open` → `SetSocketTimeouts(fd, 2s)`（`SO_RCVTIMEO`/`SO_SNDTIMEO` 各 2s——**socket 层兜底**，即使上层 poll/consume 逻辑失效，读/写也不会无限阻塞）→ `amqp_login`（guest/guest + vhost "/"，内网部署不引入复杂认证）→ channel 1。

**发布路径**：消息属性 `delivery_mode=2`（persistent 落盘）；发布失败 → LOG_WARN → **重建发布连接重试 1 次** → 仍失败 return false，调用方降级。

**消费路径（三段式，`ConsumeBlocking` `mq_client.cpp:295`）**：

```
① 持锁：首次消费该队列时 amqp_basic_consume（consumed_queues_ 记录）
② 无锁 poll(fd, 2s)：超时 → 正常返回 false；错误 → 持锁销毁连接
③ 有数据才持锁：amqp_consume_message(conn, &envelope, {0,0})  ← 0 超时立即尝试
```

> 追问：为什么 poll 必须移出锁？（log 14 Bug 1，2026-08-04 复验发现）——初版 poll 在锁内 + 消费线程紧循环 → `consume_mutex_` 几乎 100% 被占 → `connected()` 的 `try_lock_for(1s)` 永远失败 → `consume lock busy` 无限刷屏 + SchedulingLoop 永远判 `(mq=pull)`——**Push 模式被误判为 Pull，调度模式错误降级**。修复依据：poll 期间无并发写者（消费连接只由消费线程销毁），所以 poll 完全不需要锁；锁只保护 conn 内部状态的读写（read/销毁/重建）。

**`Ack`/`connected`/`Reconnect` 的锁策略**——可靠性单点必须无锁：

| 方法 | 实现 | 设计意图 |
|------|------|---------|
| `Ack(tag)` | `try_lock_for(1s)`，拿不到锁 → WARN "ack skipped, msg will redeliver"；`amqp_basic_ack` multiple=false | 消费锁可能被 `ConsumeBlocking` 短暂持有，Ack 不无限等锁——**ack 失败只是重投**，由消费幂等吸收 |
| `connected()` | **无锁**：`consume_alive_.load() && consume_conn_ != nullptr`（`consume_alive_` 为 atomic） | "MQ 在线"是 SchedulingLoop 决定调度模式的**单点判断**，它的误判代价是模式错误降级——必须是原子无锁读取 |
| `Reconnect()` | `try_lock_for(1s)` → 重建消费连接，`consumed_queues_` 清空，basic_consume 由 ConsumeBlocking 惰性重建 | 重建期间不阻塞发布；清空记录保证新连接上重新 consume |

**与 RedisClient 同哲学（可降级组件）**：`Init()` `mq_enable=0` 直接禁用；连接失败只 LOG_WARN 置 `enabled_=false`，**不拒绝服务启动**（与 MySQL 的 fail-fast 形成对照，与 RedisClient 完全同构）。配置键：`mq_enable / mq_host / mq_port`（8 个 conf：本机 5 个 + docker 3 个；发布端在 Scheduler，故 job_service/worker_manager 无 mq 配置）。

### 6.5 可靠性：at-least-once 的完整拼图

"MQ 宕机消息不丢"由四层拼图构成：

| 层 | 机制 | 防什么 |
|----|------|--------|
| ① | **durable queue**（Broker 重启队列还在） | 队列消失 |
| ② | **delivery-mode=2**（消息落盘） | 消息丢失 |
| ③ | **手动 ACK**（`Ack` 处理成功后才确认；不 ack 的消息 Broker 重投） | 消费中途崩溃丢消息 |
| ④ | **消费幂等**（查库判断 + 三重防护） | 重投导致重复分配/重复处理 |

**为什么消费端（几乎）无条件 ACK**——消息的"职责"是**触发一次检查**，检查已做即完成职责：

- **分配失败**（无 worker/过载/锁占用）→ 不重回队列，否则无限重投风暴；由 SchedulingLoop 兜底扫描 5s 内再试
- **重复投递**（Broker 重发）→ 查 MySQL 非 WAITING 即幂等跳过，配合 TryAssignShard 三重防护（状态复核 + Redis 分布式锁 + MySQL 条件更新）
- **RC 侧**：`MqResultConsumeLoop` 对处理结果也**无条件 Ack**（含解析失败 `ack & drop`）——处理失败的情况由 RC 的重试判定（`HandleReportShardResult` 内部 FAILED→RETRYING 逻辑）走既有重试链路，不依赖消息重投

> ⚠️ 代码事实注记：`mq_client.h` 头注释写"处理成功才 ack"，但实际 `MqResultConsumeLoop`（`result_collector.cpp:547-549`）是无条件 Ack——以代码为准，语义为"消费成功即完成职责"。

**正确性底线**：MQ 是 at-least-once 通道，重复由幂等吸收，丢失由轮询兜底扫描吸收——**MQ 从不承诺 exactly-once，系统整体却是 exactly-once 的**（一个 shard 至多被一个 worker 执行、结果至多落定一次）。

## 7. 降级哲学与共存（两个应用点全景）

```
                调度通道                                  结果通道
MQ 在线:  SchedulingLoop interval=5000ms (mq=push)   Worker → MQ 上报成功
MQ 掉线:  SchedulingLoop 自动恢复 2000ms (mq=pull)   Worker 回退直连 RPC（3 次重试）
MQ 恢复:  connected()==true → 自动切回 push          每次上报独立判断 → 自动切回 MQ
```

与 Redis 完全同哲学：**没有切换状态机，每轮/每次按当前事实决定自己的行为**——调度按每轮 `connected()`，结果按每次上报判断。两条链独立降级、独立恢复，互不拖累。

## 8. 效果与修复史（实测验证）

| 验收项 | 结果 |
|--------|------|
| **调度延迟 <100ms**（验收核心） | ✅ **实测 33ms**：shard 创建 → MQ 消费分配 33ms（对比 Pull 平均 ~1s，量级下降 30 倍） |
| MQ 故障全链路不回归 | ✅ 8 shard 全 JOB_SUCCESS：分配走 Pull 轮询、结果走直连 RPC，`interval=2000ms (mq=pull)` 自动接管 |
| MQ 恢复自动切回 | ✅ 新任务 SUCCESS，`interval=5000ms (mq=push)`，MqConsumeLoop 恢复消费 |
| MQ 宕机消息不丢 | ⏳ 代码就绪（durable + persistent + 手动 ACK + 消费幂等），**真实 Broker 重启实测待用户 sudo**（本机无权限操作 rabbitmq 服务） |
| 全链路功能 | ✅ MQ 正常时 2 shard 全 SUCCESS：Worker 侧 `SUCCESS published to MQ`、RC 消费聚合 JOB_SUCCESS |

**修复史（两个真实缺陷）**：

| Bug | 现象 | 根因 | 修复 |
|-----|------|------|------|
| 单连接单锁（阶段 10 初版） | 提交任务卡死，`recv response header error! errno:11` | ConsumeBlocking 持锁阻塞，发布等同一把锁 → RPC 超时 | 双连接双锁，发布/消费互不阻塞 |
| 消费锁占用（log 14 Bug 1） | `consume lock busy` 刷屏 + SchedulingLoop 永远 `(mq=pull)` | poll(2s) 在锁内 + 紧循环 → consume_mutex_ 几乎 100% 被占 → connected() 永远拿不到锁 | ① poll 移出锁 ② connected() 改 `consume_alive_` 原子无锁读取 ③ 销毁分支持锁且先置标志 |

> 启示：Push 模式下"MQ 在线"的判断本身是可靠性的**新单点**——它的误判代价是调度模式错误降级，因此 connected() 必须是原子无锁的读取。

## 9. 遗留与边界

1. **真实 Broker 重启测试待执行**（用户 sudo）：`stop_app` → 提交任务（消息应积压在持久化队列）→ `start_app` → 任务恢复完成。代码路径已全部就绪，只差一次真实重启验证
2. **rabbitmqctl 本机不可用**（任何子命令输出 Usage）：影响运维便利性（无法命令行查队列），不影响功能；排查 erlang cookie/脚本路径
3. **guest/guest 默认账号**：内网单机部署可接受；多租户/公网场景需换账号或加 VHost 隔离
4. **消息体积**：result.pending 消息体 = 序列化请求（含路径字符串），shard 级消息量下远低于 AMQP 限制，无需分块/压缩
5. **MQ 单实例**：Broker 本身无高可用（rabbitmq 集群超出本阶段范围）；宕机期间的调度延迟退化到 Pull 级别，任务不丢
