## 1. 概述

视频平台的**数据层**经历了两次架构跃迁：

| 阶段 | 数据层形态 | 数据一致性归谁管 |
|------|-----------|----------------|
| 阶段 1-8 | 每进程内存 `unordered_map` Store + RPC 携带快照跨进程同步 | 跨进程同步 RPC（10+ 处"从请求构造本地副本"） |
| 阶段 9（MySQL） | **MySQL 为唯一数据源**，3 张表，多进程直读直写 | 数据库（单语句原子性 + 条件更新 CAS） |
| 阶段 10（Redis） | MySQL 之上叠加 **Redis 读路径加速**（快照镜像/进度缓存/分布式锁/服务发现集中缓存） | 仍归数据库；Redis 是可降级加速件，不承担正确性 |

一句话总结本文：**MySQL 解决"数据放哪、谁说了算"（一致性 + 持久化），Redis 解决"数据怎么读得快、多进程怎么共享热数据"（性能 + 可用性）。两者故障语义刻意不同——MySQL 挂了必须 fail-fast，Redis 挂了自动降级回阶段 9 行为。**

## 2. 为什么引入：无中间件时代（阶段 1-8）的真实痛点

阶段 1-8 的三个 Store（JobStore / ShardStore / WorkerStore）是进程内单例，多进程部署时各进程 Store **完全隔离**，跨进程共享靠 RPC 把数据"复制"过去。这套架构能跑通全链路，但留下了四个结构性缺陷：

### 2.1 进程重启数据全丢

内存 Store 意味着服务重启后对过去一无所知。Scheduler 崩溃恢复只能靠"启动扫描残留状态拼凑"——**这是把数据库的活外包给了启动逻辑**，而且拼出来的状态未必与崩溃前一致。

### 2.2 数据副本漂移：同一份数据有 N 份拷贝

跨进程同步 = 每个进程持有权威数据的**快照副本**，同步靠 RPC。典型恶果：

- **JobService 的 QueryJob 查不到 `assigned_worker_id`**——该字段只存在于 Scheduler 进程，JobService 永远不知道 shard 分给了谁
- **ResultCollector 判终态要跨进程 QueryJob 查 shard_count**（阶段 5 的 3 次重试逻辑）——为了一个本应本地可查的数据发 RPC，还可能要重试
- 10+ 处"从 RPC 请求构造本地副本"的代码：每次新增字段都要同步改复制逻辑，副本之间互相污染

### 2.3 阶段 4 #S4 已预告的竞态，MySQL 化后被放大

阶段 4 曾发现同进程内的快照覆盖竞态（SchedulingLoop 用旧副本覆盖 RescheduleShard 写入的 retry_count），修复方式是"写前重新 Get"。但这个窗口期方案在跨进程场景下不可接受——**5 个进程并发写同一行数据，重读与写入之间必然存在被他人修改的窗口**。

### 2.4 阶段 10 前的读路径全部走 RPC/轮询

阶段 9 完成后数据是权威了，但读路径仍昂贵：

- Scheduler 分配循环每轮调用 **WorkerManager ListWorkers RPC** 拿 Worker 负载快照
- 调度是 **Pull 模式**：SchedulingLoop 每 2s 轮询一次 WAITING shard，平均分配延迟 ~1s
- ZK 服务地址缓存是**每进程私有**的：一个进程发现实例变更，其他进程 30s 内还在打旧地址

## 3. MySQL 持久化设计（阶段 9）

### 3.1 为什么是"纯 MySQL 直读直写"而不是"双写内存缓存 + MySQL"

路线图原文规划的是"双写 + 读内存缓存"，但实现前推演发现它与"删除跨进程同步逻辑"**存在内在矛盾**：读内存缓存时，进程 B 看不到进程 A 写入 MySQL 的更新——删掉同步 RPC 后，各进程的内存缓存会**永久陈旧**（Scheduler 永远读不到 RC 写的 job 终态）。

纯 MySQL 方案把一致性责任整体移交给数据库：

```
写入 → MySQL 立即可见 → 所有进程下一次读取即最新（跨主机同样成立）
```

代价是每次读多一次 SQL——本机单条 PK 查询实测 <0.2ms，数据量千级，**缓存收益为零，复杂度收益为负**。因此阶段 9 明确：不加缓存，缓存留到阶段 10 只做"读路径加速"。

### 3.2 存储方案对比（为什么是 MySQL 而不是别的）

| 方案 | 结论 | 理由 |
|------|------|------|
| **MySQL** | ✅ 选用 | 团队已有（ZooKeeper 之外）最熟的关系型数据源；jobs/shards/workers 是结构化关系数据（job→shard 一对多、shard→worker 外键关系、状态机字段），天然适合 SQL；单语句条件更新（CAS）是解决跨进程快照覆盖的最廉价手段 |
| **Redis 作主存储** | ❌ 拒绝 | 快照/缓存语义，不提供条件更新原子性（虽可用 Lua/事务模拟）；数据无强一致性保证；宕机丢数据的默认语义与"任务状态不可丢"需求冲突 |
| **内存 Store + 同步 RPC（阶段 1-8）** | ❌ 已被替换 | 见第 2 节四大痛点 |
| **Kafka/消息日志作存储** | ❌ 过重 | 千级数据量、5 个服务，杀鸡用牛刀；消息系统是事件流而非查询友好存储，QueryJob 需要即时点查 |

### 3.3 访问层设计：MysqlPool 连接池

`mysql_pool.h/.cpp`（libmysqlclient C API 封装），核心决策：

| 设计点 | 决策 | 为什么 |
|--------|------|--------|
| **连接池形态** | 固定大小预创建（`mysql_pool_size`，默认 4），mutex + condition_variable 借用/归还，Acquire 超时（1s）返回 nullptr | 服务是 RPC 多线程并发模型，每条连接非线程安全；预创建保证启动即可用，杜绝运行时频繁建连 |
| **初始化失败** | **fail-fast**：预创建失败拒绝服务启动 | MySQL 是唯一数据源，连不上服务无法工作——快速失败优于带病运行 |
| **保活** | 借用时 `mysql_ping`，死连接销毁重建 | 长连接可能被 MySQL 端超时回收 |
| **CLIENT_FOUND_ROWS** | 连接标志 | UPDATE 值未变化时 affected_rows 仍返回**匹配行数**——否则"全量覆盖更新"（刷新心跳、写相同状态）会被误判为未命中，条件更新的返回值语义就错了 |
| **utf8mb4** | 连接字符集 | 路径等字段可含中文 |
| **自动建表** | Init 时 `CREATE TABLE IF NOT EXISTS`（与 `sql/schema.sql` 一致） | 部署零步骤；schema.sql 保留为参考与手动管理入口 |
| **防注入** | `MysqlConnectionGuard::Escape`（mysql_real_escape_string） | input_path 等客户端输入进 SQL |
| **RAII** | `MysqlConnectionGuard`：构造借用、析构归还 | 异常路径不会泄漏连接 |

### 3.4 Store 层设计：接口不变、内部全 SQL

三个 Store 的**对外接口零改动**，内部从 `unordered_map + shared_mutex` 换成 SQL：

| 原方法 | MySQL 实现 |
|--------|-----------|
| Insert | INSERT，duplicate key(1062) → false |
| Update | UPDATE ... WHERE id（委托 UpdateIfStatus 空条件） |
| Get | SELECT ... WHERE id LIMIT 1 |
| ListAll / ListByStatus(-1) | SELECT 全表 |
| ListByJob / ListByWorker / ListByStatus | SELECT ... WHERE 条件 |
| InsertOrUpdate | INSERT ... ON DUPLICATE KEY UPDATE |
| MarkOfflineIfTimeout | 单条条件 UPDATE（行级原子，替代锁内检查） |
| **UpdateIfStatus（新增）** | UPDATE ... WHERE id AND status IN (expect...)，**CAS 条件推进** |

接口不变的收益：5 个服务的调用方代码几乎零改动，迁移成本集中在 Store 内部一行；而新增的 `UpdateIfStatus` 是**跨进程并发正确性的关键**——详见《8. 防并发覆盖机制设计.md》。核心思想一句话：

> **MySQL 化后"Get → 修改 → Update"的 read-modify-write 窗口从进程内（有锁）暴露为跨进程（无锁）。解法不是缩小窗口，而是把"检查前置状态 + 写入"合并为一条原子 UPDATE——先到的写者生效，后到的旧快照不覆盖已改变的状态。**

### 3.5 配套删减：跨进程同步 RPC 全面退役

MySQL 化后，RPC 框架卸下"数据复制"职责，回归"功能调用"：

| 删除的 RPC | 原调用方 | 删除原因 |
|-----------|---------|---------|
| `JobService.UpdateJobStatus` | Scheduler ×2、RC MarkJobTerminal | JobService 直接读 MySQL；旧快照写入反而**污染权威数据**（覆盖 Scheduler 刚写的 assigned_worker_id） |
| `ResultCollector.NotifyJobCanceled` | JobService.CancelJob | CancelJob 直接写 MySQL 标记 CANCELED，RC 读同一份数据自动收敛 |

同时删除 6 处"从 RPC 请求构造本地副本"（SubmitJob、PendingScanLoop、CheckJobDone 的跨进程 QueryJob 重试、ReportShardResult 副本构造等）。**保留的 RPC 全部是功能调用**（ScheduleJob / AssignShard / 心跳 / 通知……），不再携带数据快照。

三个兜底循环（SchedulingLoop 重扫、TerminalSweepLoop 终态判定、PendingScanLoop、启动恢复扫描）全部保留——数据源从内存变为 MySQL，行为不变，且因直接读共享数据而更简单。

### 3.6 表设计

3 张表（`video_platform/sql/schema.sql`）：

- **jobs**：job_id PK + 状态机字段 + 转码参数（shard_duration_sec 补齐路线图 DDL 的遗漏）
- **shards**：全字段对齐 ShardRecord，5 个索引（PRIMARY + idx_job + idx_worker + idx_status）
- **workers**：worker_id PK + 负载/槽位字段 + gpu_count（预留）

### 3.7 与阶段 1-8 的对比总结

| 维度 | 阶段 1-8（无 MySQL） | 阶段 9（MySQL） |
|------|---------------------|----------------|
| 数据位置 | N 份进程内副本 | 1 份共享数据库 |
| 跨进程一致性 | 同步 RPC + 快照复制（10+ 处） | 数据库原子性 + CAS 条件更新（0 处复制代码） |
| 崩溃恢复 | 启动扫描"拼凑"残留状态 | 数据还在，直接读 |
| 跨服务查询 | 查不到就 RPC 跨查（QueryJob 无 assigned_worker_id） | 直读 MySQL，字段全可见 |
| 竞态防护 | 进程内锁 + "写前重读"（窗口存在） | 单语句原子条件更新（窗口为零） |
| 单次操作延迟 | 内存 O(1) | SQL ~0.2ms（见 §5.1） |

## 4. Redis 设计（阶段 10）

### 4.1 为什么是"可降级组件"：与 MySQL 的故障语义刻意不同

这是整个 Redis 设计的**出发点**，值得单独强调：

| 组件 | MySQL | Redis |
|------|-------|-------|
| 角色 | 唯一数据源（真相） | 读路径加速（镜像/缓存/锁） |
| 故障语义 | **fail-fast**：Init 失败拒绝服务启动 | **降级**：Init 失败只 WARN，enabled()=false，调用方走回退路径 |
| 为什么 | 连不上服务无法工作，带病运行只会产生更多错误 | 负载快照的真相源是 MySQL（心跳仍写 MySQL）、进度的真相源是 MySQL、锁是防御性保护——Redis 故障时系统**完整回退到阶段 9 行为** |
| 兜底 | 无（单实例即单点） | 每次调用独立判断降级，Redis 恢复自动切回（**按次判断，无状态机**） |

一句设计原则：**引入任何中间件都必须回答"它挂了怎么办"，且答案必须是"系统回到挂掉之前的可用状态"，而不是"系统一起挂"。** Redis 的四个用途全部满足这一点。

### 4.2 为什么引入：读路径的四个具体加速点

| 用途 | 无 Redis 时 | 引入后 |
|------|------------|--------|
| Worker 负载快照 | Scheduler 每轮分配调 ListWorkers RPC | `HGETALL worker:load` 一次 RTT 取全量 |
| Job 进度缓存 | 每次 QueryJob 一次 `ShardStore::ListByJob` SQL | 命中缓存直接反序列化返回（GUI 高频轮询场景） |
| 分布式锁 | 无（单实例时靠条件更新） | SETNX 在发 AssignShard RPC **之前**拦截竞争方 |
| ZK 服务地址缓存 | 每进程私有，实例变更感知滞后 | `mprpc:endpoints` 集中管理，HDEL 全集群同时失效 |

### 4.3 客户端封装：RedisClient（业务层）与 MprpcRedisClient（框架层）

两层各有一个最小化客户端，语义同构：

| 设计点 | 业务层 RedisClient | 框架层 MprpcRedisClient |
|--------|-------------------|------------------------|
| 位置 | `video_platform/`（业务代码） | `mprpc/`（框架层，服务发现热路径） |
| 命令集 | HSet / HGetAll / Get / SetEx / SetNxEx / Del | HGet / HSet / Expire / HDel（刻意最小化，只服务 ZK 缓存） |
| 初始化 | main() 显式 `Init()` | **懒初始化**（`std::once_flag` 首次命令时拉起——框架层无法要求所有调用方改 main） |
| 连接模型 | 单连接 + mutex（调用频率低，连接池无收益；redisContext 非线程安全） | 同左 |
| 超时 | connect/command 均 2s | 同左 |
| 命令失败 | 断开重建连接重试 1 次，仍失败返回 false 由调用方降级 | 同左 |
| 为什么分层 | — | 不把业务代码下沉进 mprpc：避免 mprpc → video_platform 反向依赖，破坏分层 |

### 4.4 用途一：Worker 负载快照（HSET worker:load）

**写（WorkerManager Heartbeat）**：`UpdateHeartbeat` 成功（alive=true）后从 MySQL Get 全量记录，拼快照串写入：

```
HSET worker:load {worker_id} → "ip|port|cpu_cores|memory_mb|max_running|current_running|cpu_usage|memory_usage|ts"
```

- **为什么 alive=true 才写**：避免幽灵快照——心跳更新失败（worker 实际已失联）时残留旧快照会误导调度
- **为什么心跳时还读一次 MySQL**：心跳请求只带负载，ip/port/max_running 是注册时写入的；MySQL 是唯一真相源，读一次 PK 查询（<0.2ms）拼完整快照，逻辑最简——**镜像可以读真相源，真相源永远不是镜像**

**读（Scheduler `LoadOnlineWorkers`）**：先 `HGETALL worker:load`，按内嵌 ts 过滤（`now - ts > 20s` 视为 OFFLINE，与心跳超时阈值一致），有存活数据直接构造 `ListWorkersResponse` 返回；快照空/全过期/Redis 不可用则回退 `wm_stub.ListWorkers` RPC。

**为什么单 key 多 field 而非每 worker 一个 key**：Scheduler 分配循环需要**一次拿全部 ONLINE Worker**——`HGETALL` 一次 RTT 等价于 ListWorkers RPC 的一次返回。每 worker 一个 key 要 `SCAN worker:load:*`（多轮 RTT + 游标）或额外维护集合。

**field 无单独 TTL 的解法**：HSET 的 field 不能单独设 TTL，所以**值内嵌时间戳**，读侧过期过滤；残留 field 由下次同名心跳覆盖，无泄漏。

### 4.5 用途二：Job 进度缓存（SETEX job:progress:{id}）

JobService QueryJob：先 `GET job:progress:{job_id}`，命中直接 `ParseFromString` 返回；miss 走原 MySQL 查询，`error_code==0` 时 `SerializeToString` + `SETEX` TTL 60s 写回。RC ReportShardResult 推进成功后 `DEL` 该 key。

- **为什么缓存整个响应串而非只缓存 shard 列表**：QueryJob 响应 = job_info + 全部 shard，构造成本主要在 `ShardStore::ListByJob` 一次 SQL。缓存整个串 = 一次反序列化替换一次 SQL 扫描，改动最小、收益最大；只缓存 shard 列表反而要改响应构造逻辑
- **为什么 TTL 60s 且结果落定立即 DEL**：终态不可滞后（DEL 精确失效）；进行中进度靠 TTL 自然刷新，接受最多 60s 近似（进度本为近似值，实时推送留待阶段 12 GUI）

### 4.6 用途三：分布式锁（SETNX）

`SET shard:lock:{shard_id} scheduler:{pid} NX EX 10`，完整设计见《4. 分布式锁设计.md》。核心要点：

- **三层防线**：状态复核（查库非 WAITING 即 skip）→ SETNX 锁（拦截最贵的 AssignShard RPC）→ MySQL 条件更新（正确性最终底线）。**锁是防护不是依赖，所以可以安全降级**
- **value 校验释放**：释放前 GET 校验 `cur == lock_value` 才 DEL——防 TTL 未过期前锁被抢、持锁方完成后误删他人锁
- **故障降级放行**：SETNX 失败后 GET 区分"锁被占用"（skip）与"Redis 故障"（**降级放行**，靠 MySQL 条件更新兜底）——Redis 挂了不能停摆整个调度

### 4.7 用途四：ZK 服务地址缓存集中化（框架层 mprpc:endpoints）

`GetHostData` 从"进程内缓存 + ZK 直读"升级为**三层链路**：

```
1. 本地缓存（30s TTL 内命中）→ 直接返回，零 Redis/ZK 交互（热路径：12 万 QPS 量级）
2. Redis HGET mprpc:endpoints → 命中填本地缓存返回（省一次 ZK 往返）
3. ZK 拉取 → 双写本地 + Redis（HSET + EXPIRE 30s）
```

- **为什么 30s TTL**：集中管理的价值 = 实例变更后其他进程及时感知。本地缓存无限期会让每个进程永远吃自己的旧缓存，Redis 集中管理名存实亡；30s 保证最多 30s 全集群重新发现，且热路径 30s 内零 Redis/ZK 交互，性能不回退
- **连接失败为什么 HDEL 集中字段**：清本地缓存只影响本进程，其他进程 30s 内仍轮询死实例；HDEL 后**所有进程同时失效**，一起重拉 ZK——"多进程共享失效"是集中管理相对进程内缓存的核心收益
- **为什么锁顺序"先 Redis 后写本地"**：Redis 网络操作 2s 超时，绝不持 ServiceCacheMutex——否则 Redis 卡死会连带卡死整个服务发现热路径
- **键值格式**：key=`mprpc:endpoints`，field=method 路径，value=CSV endpoint 列表（endpoint 不含逗号，拼接/解析安全）；轮询 index 仍本地维护（负载均衡语义是进程视角的）

### 4.8 与阶段 9（无 Redis）的对比总结

| 维度 | 阶段 9（仅 MySQL） | 阶段 10（+Redis） |
|------|-------------------|------------------|
| Worker 负载获取 | 每轮分配 ListWorkers RPC | Redis 快照一次 RTT，RPC 仅作降级 |
| QueryJob | 每次 SQL 扫描 | 缓存命中直接返回，60s TTL |
| 多 Scheduler 防重复分配 | 仅 MySQL 条件更新（落定阶段拦截） | SETNX 在发 RPC 前拦截 + 条件更新兜底 |
| 服务发现 | 每进程私有缓存，变更感知滞后 | 集中缓存 + HDEL 全集群同时失效 |
| 正确性依赖 | MySQL | **仍是 MySQL**（Redis 全部用途可降级） |

## 6. 局限性与边界

1. **MySQL 单实例无高可用**：MySQL 故障 = 平台不可用（启动即拒绝）。生产化需主从/多实例，超出当前阶段范围
2. **Redis 无持久化要求**：镜像/缓存/锁数据均可从 MySQL 或 ZK 重建，宕机丢数据无害——这正是"可降级组件"的底气
3. **分布式锁 TTL 竞窗存在**：GET 校验与 DEL 两步之间的竞窗，最坏 = 重复分配一次，由消费幂等 + 条件更新兜底（单实例部署下不存在）
4. **进度缓存最多 60s 滞后**：TTL 语义接受近似；实时进度推送留待 GUI 阶段
5. **Redis 进程内降级是"一锤定音"**：懒初始化失败后 enabled()=false 直到重启进程——与业务层语义一致，属既定设计
6. **条件更新只保护状态字段**：WHERE 仅约束 status，同 id 的其他纯数据并发写不受保护（本系统中所有写都由状态推进驱动，不构成实际问题）

## 7. 演进脉络与收益总结

```
阶段 1-8   每进程内存 Store + RPC 快照同步（N 份副本，一致性靠复制）
   │        痛点：重启丢数据 / 副本漂移 / 跨进程竞态 / 查询缺字段
   ▼
阶段 9     MySQL 唯一数据源（1 份真相，一致性靠数据库）
   │        收益：重启不丢、跨服务直读、CAS 根除快照覆盖、删除 2 个同步 RPC + 6 处副本构造
   ▼
阶段 10    + Redis 读路径加速（真相仍在 MySQL，镜像/缓存/锁全部可降级）
            收益：负载快照 1 RTT、进度缓存、SETNX 预拦截、服务发现全集群共享失效
```

最终的分工一句话：

> **MySQL 管"对不对"（一致性、持久化、并发正确性），Redis 管"快不快"（读路径加速、共享热数据）——把"对"的东西放在可降级的位置，是中间件引入的第一原则。**
