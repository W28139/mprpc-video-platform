# MySQL 与 Redis 中间件设计

---

## 1. 概述

**MySQL 解决"数据放哪、谁说了算"（一致性 + 持久化）**

**Redis 解决"数据怎么读得快、多进程怎么共享热数据"（性能 + 可用性）。**

**两者故障语义刻意不同——MySQL 挂了必须 fail-fast，Redis 挂了自动降级。**

---

## 2. 为什么引入

阶段 1-8 的三个 Store（JobStore / ShardStore / WorkerStore）是进程内单例，多进程部署时各进程 **完全隔离**，跨进程共享靠 RPC 把数据"复制"过去。能跑通全链路，但留下三类结构性缺陷——前两类是数据问题（MySQL 解决），第三类是读路径问题（Redis 解决）：

### 2.1 进程重启数据全丢（MySQL 解决）

内存 Store 重启后对过去一无所知，Scheduler 崩溃恢复只能靠"启动扫描残留状态拼凑"——**把数据库的活外包给了启动逻辑**，拼出来的状态也未必与崩溃前一致。

### 2.2 数据副本漂移：同一份数据有 N 份拷贝（MySQL 解决）

跨进程同步 = 每个进程持有权威数据的快照副本。典型恶果：

- **QueryJob 查不到 `assigned_worker_id`**——该字段只存在于 Scheduler 进程
- **RC 判终态要跨进程 QueryJob 查 shard_count**——本应本地可查的数据发 RPC，还可能重试
- 10+ 处"从 RPC 请求构造本地副本"的代码，每加一个字段都要同步改复制逻辑

### 2.3 读路径昂贵（Redis 解决）

- 调度每轮调 **WorkerManager ListWorkers RPC** 拿负载快照
- **Pull 模式**每 2s 轮询一次 WAITING shard，平均分配延迟 ~1s
- ZK 服务地址缓存**每进程私有**，实例变更最多滞后 30s 才发现

## 3. MySQL 持久化设计

> 面试叙事主线（面试官的问题链）：**为什么选它（3.1）→ 连接层怎么接入（3.2）→ 数据层怎么迁移（3.3）→ 并发正确性怎么保证（3.4）→ 删掉了什么（3.5）→ 表怎么设计（3.6）→ 效果如何（3.7）**

### 3.1 为什么用 MySQL 做存储？为什么不用内存缓存、Redis 或 Kafka？

**动机**：早期架构是 N 份进程内副本 + RPC 复制，MySQL 作为**唯一数据源**一次性解决第 2 节的三类痛点——重启丢数据、副本漂移、跨进程竞态（一致性 + 持久化整体交给数据库）。

**为什么不用"内存缓存 + MySQL 双写"**："内存缓存加速读 + MySQL 持久化"是最先想到的方案，但推演后发现它与"删除跨进程同步逻辑"**存在内在矛盾**：读内存缓存时，进程 B 看不到进程 A 写入 MySQL 的更新——一旦删掉同步 RPC，各进程的内存缓存会**永久陈旧**（Scheduler 永远读不到 RC 写的 job 终态）。

纯 MySQL 方案把一致性责任整体移交给数据库：

```
写入 → MySQL 立即可见 → 所有进程下一次读取即最新（跨主机同样成立）
```

代价是每次读多一次 SQL——本机单条 PK 查询实测 <0.2ms，数据量千级，**缓存收益为零，复杂度收益为负**。因此不加缓存，缓存留到后续阶段只做"读路径加速"（见第 4 节）。

### 3.2 MySQL 怎么接入的？连接层怎么设计？

`mysql_pool.h/.cpp`（libmysqlclient C API 封装），核心决策：

| 设计点 | 决策 | 为什么 |
|--------|------|--------|
| **连接池形态** | 固定大小预创建（`mysql_pool_size`，默认 4），mutex + condition_variable 借用/归还，Acquire 超时（1s）返回 nullptr | 服务是 RPC 多线程并发模型，每条连接非线程安全；预创建保证启动即可用，杜绝运行时频繁建连 |
| **初始化失败** | **fail-fast**：预创建失败拒绝服务启动 | MySQL 是唯一数据源，连不上服务无法工作——快速失败优于带病运行 |
| **保活** | 借用时 `mysql_ping`，死连接销毁重建 | 长连接可能被 MySQL 端超时回收 |
| **CLIENT_FOUND_ROWS** | 连接标志 | UPDATE 值未变化时 affected_rows 仍返回**匹配行数**——否则"全量覆盖更新"（刷新心跳、写相同状态）会被误判为未命中，条件更新的返回值语义就错了 |
| **utf8mb4** | 连接字符集 | 路径等字段可含中文 |
| **自动建表** | Init 时 `CREATE TABLE IF NOT EXISTS`（与 `sql/schema.sql` 一致） | 部署零步骤；schema.sql 保留为参考与手动管理入口 |
| **防注入** | `MysqlConnectionGuard::Escape`（mysql_real_escape_string） | input_path 等客户端输入进 SQL |
| **RAII** | `MysqlConnectionGuard`：构造借用、析构归还 | 异常路径不会泄漏连接 |

### 3.3 Store 层怎么从内存迁移到 SQL？

三个 Store 的**对外接口零改动**，内部从 `unordered_map + shared_mutex` 换成 SQL——迁移成本集中在 Store 内部，5 个服务的调用方代码几乎零改动：

| 原方法 | MySQL 实现 |
|--------|-----------|
| Insert | INSERT，duplicate key(1062) → false |
| Update | UPDATE ... WHERE id（委托 UpdateIfStatus 空条件） |
| Get | SELECT ... WHERE id LIMIT 1 |
| ListAll / ListByStatus(-1) | SELECT 全表 |
| ListByJob / ListByWorker / ListByStatus | SELECT ... WHERE 条件 |
| InsertOrUpdate | INSERT ... ON DUPLICATE KEY UPDATE |
| MarkOfflineIfTimeout | 单条条件 UPDATE（行级原子，替代锁内检查） |
| **UpdateIfStatus（新增）** | UPDATE ... WHERE id AND status IN (expect...)，**CAS 条件推进** |

### 3.4 多进程并发写同一行数据，怎么保证不互相覆盖？

这是 MySQL 化后**最关键**的并发问题（完整设计见《8. 防并发覆盖机制设计.md》），核心思想一句话：

> **MySQL 化后"Get → 修改 → Update"的 read-modify-write 窗口从进程内（有锁）暴露为跨进程（无锁）。解法不是缩小窗口，而是把"检查前置状态 + 写入"合并为一条原子 UPDATE——先到的写者生效，后到的旧快照不覆盖已改变的状态。**

实现是新增的 `UpdateIfStatus`（`UPDATE ... WHERE id AND status IN (expect...)`，CAS 条件推进）：5 个进程并发推进同一 shard 状态时，只有状态符合预期的写者生效（affected_rows=1），其余写者 affected_rows=0 判定失败、重读后重试。`MarkOfflineIfTimeout` 同理用单条条件 UPDATE 替代锁内检查。

### 3.5 表结构怎么设计的？

3 张表（`video_platform/sql/schema.sql`）：

- **jobs**：job_id PK + 状态机字段 + 转码参数（含 shard_duration_sec）
- **shards**：全字段对齐 ShardRecord，5 个索引（PRIMARY + idx_job + idx_worker + idx_status）
- **workers**：worker_id PK + 负载/槽位字段 + gpu_count（预留）

### 3.6 改造前后对比如何？

| 维度 | 早期（无 MySQL） | 引入 MySQL 后 |
|------|---------------------|----------------|
| 数据位置 | N 份进程内副本 | 1 份共享数据库 |
| 跨进程一致性 | 同步 RPC + 快照复制（10+ 处） | 数据库原子性 + CAS 条件更新（0 处复制代码） |
| 崩溃恢复 | 启动扫描"拼凑"残留状态 | 数据还在，直接读 |
| 跨服务查询 | 查不到就 RPC 跨查（QueryJob 无 assigned_worker_id） | 直读 MySQL，字段全可见 |
| 竞态防护 | 进程内锁 + "写前重读"（窗口存在） | 单语句原子条件更新（窗口为零） |
| 单次操作延迟 | 内存 O(1) | SQL ~0.2ms（见 §5.1） |

## 4. Redis 设计（阶段 10）

### 4.1 为什么是"可降级组件"：与 MySQL 的故障语义刻意不同

这是整个 Redis 设计的**出发点**，值得单独强调：

| 组件 | MySQL | Redis |
|------|-------|-------|
| 角色 | 唯一数据源（真相） | 读路径加速（镜像/缓存/锁） |
| 故障语义 | **fail-fast**：Init 失败拒绝服务启动 | **降级**：Init 失败只 WARN，enabled()=false，调用方走回退路径 |
| 为什么 | 连不上服务无法工作，带病运行只会产生更多错误 | 负载快照的真相源是 MySQL（心跳仍写 MySQL）、锁只是防御性保护——Redis 故障时系统**完整回退到阶段 9 行为** |
| 兜底 | 无（单实例即单点） | 每次调用独立判断降级，Redis 恢复自动切回（**按次判断，无状态机**） |

一句设计原则：**引入任何中间件都必须回答"它挂了怎么办"，且答案必须是"系统回到挂掉之前的可用状态"，而不是"系统一起挂"。** Redis 的三个用途全部满足这一点。

### 4.2 为什么引入：读路径的三个具体加速点

| 用途 | 无 Redis 时 | 引入后 |
|------|------------|--------|
| Worker 负载快照 | Scheduler 每轮分配调 ListWorkers RPC | `HGETALL worker:load` 一次 RTT 取全量 |
| 分布式锁 | 无（单实例时靠条件更新） | SETNX 在发 AssignShard RPC **之前**拦截竞争方 |
| ZK 服务地址缓存 | 每进程私有，实例变更感知滞后 | `mprpc:endpoints` 集中管理，HDEL 全集群同时失效 |

> 刻意**不做查询缓存**：QueryJob 的 SQL 单条 PK + 一次 ListByJob 实测 <0.5ms，缓存收益为零——Redis 只解决 MySQL 管不到的三件事（跨进程共享热数据 / 原子原语 / 跨进程缓存失效），这是它与"传统缓存"定位的区别。

### 4.3 客户端封装：RedisClient（业务层）与 MprpcRedisClient（框架层）

两层各有一个最小化客户端，语义同构：

| 设计点 | 业务层 RedisClient | 框架层 MprpcRedisClient |
|--------|-------------------|------------------------|
| 位置 | `video_platform/`（业务代码） | `mprpc/`（框架层，服务发现热路径） |
| 命令集 | HSet / HGetAll / SetNxEx / Get / Del（刻意最小化，只服务负载快照 + 分布式锁） | HGet / HSet / Expire / HDel（刻意最小化，只服务 ZK 缓存） |
| 初始化 | main() 显式 `Init()` | **懒初始化**（`std::once_flag` 首次命令时拉起——框架层无法要求所有调用方改 main） |
| 连接模型 | 单连接 + mutex（调用频率低，连接池无收益；redisContext 非线程安全） | 同左 |
| 超时 | connect/command 均 2s | 同左 |
| 命令失败 | 断开重建连接重试 1 次，仍失败返回 false 由调用方降级 | 同左 |
| 为什么分层 | — | 不把业务代码下沉进 mprpc：避免 mprpc → video_platform 反向依赖，破坏分层 |

### 4.4 用途一：Worker 负载快照（HSET worker:load）

> 面试叙事主线：**解决什么问题（1）→ 谁写、什么时候写（2）→ 谁读、在线怎么判（3）→ 为什么不用现成的 RPC（4）→ 为什么不直读 MySQL（5）→ 快照与 RPC 返回的数据有什么区别（6）→ 为什么别处还直接走 RPC（7）→ 残留与一致性（8）→ Redis 挂了怎么办（9）**

**Q1：这个快照解决什么问题？**

Scheduler 每轮分配 shard 前要拿到"当前在线 worker 及其负载"列表。阶段 9 的实现是每轮调一次 WorkerManager 的 ListWorkers RPC——跨进程往返 + protobuf 序列化 + ZK 服务发现，是调度热路径上最贵的一次交互。负载快照把"每轮一次 RPC"换成"一次 Redis `HGETALL`"（一次 RTT 拿全量），读路径从"请求-响应"变成"读共享镜像"。

先立一个前提，后续所有问答都基于它：**快照不是 MySQL 的替代品，也不是 ListWorkers RPC 的替代品**——它是 MySQL workers 表的一份"负载视图"镜像，真相源永远是 MySQL（心跳仍写 MySQL），Redis 只做分发加速，挂了可以完整回退。

**Q2：数据哪来？谁写？什么时候写？**

写者唯一：WorkerManager 的 Heartbeat handler（Worker 每 3s 心跳一次），**先真相后镜像**：

```
1. WorkerStore::UpdateHeartbeat() → MySQL 条件 UPDATE（status≠OFFLINE 才成功），返回 alive
2. alive==true 时：读一次 MySQL 该 worker 全量记录 → 拼快照串 → HSET worker:load {worker_id}
```

快照串 9 字段（`worker_manager.cpp:99-104`）：

```
ip|port|cpu_cores|memory_mb|max_running|current_running|cpu_usage|memory_usage|ts
```

> 追问①：为什么 alive 才写？——alive=false 说明这次心跳连 MySQL 都没写进去（worker 已 OFFLINE 或未注册），此时写快照会制造"幽灵快照"误导调度。**写镜像以写入真相源成功为前提**，保证快照永远是 MySQL 的子集视图。
> 追问②：为什么写快照前还要读一次 MySQL？——心跳请求只带负载（cpu/mem/running），ip/port/max_running 是注册时写入的；MySQL 是唯一真相源，一次 PK 查询（<0.2ms）拼完整快照，逻辑最简——**镜像可以读真相源，真相源永远不是镜像**。
> 追问③：为什么快照串用 `|` 分隔的扁平格式而不是 JSON？——字段固定 9 个且不含 `|`，一次 split 解析完成、零依赖；JSON 序列化/反序列化多引入一个重量级依赖，收益为零。

**Q3：谁读？在线怎么判定？**

读者是 Scheduler 的 `LoadOnlineWorkers`（`scheduler_service.cpp:739`），三处调用：调度主循环、ASSIGNED/RUNNING 超时重扫、MQ 消费线程。读路径：

```
HGETALL worker:load → 解析 9 字段 → now - ts > 20s 视为 OFFLINE 跳过（:770）→ 构造 ListWorkersResponse 等价物
```

**关键点：在线判定在读者侧，不在写者侧。** WM 的 alive **只决定"这次心跳要不要写快照"，不决定"谁在线"**——快照里残留着所有曾 alive 心跳过的 worker（包括已死的），**谁在线由 Scheduler 按 ts 新鲜度判定**。两套判定刻意**共用同一个 20s 常量**（与 WM `HeartbeatTimeoutCheck` 的超时阈值一致），所以快照路径与 RPC 路径对"谁在线"的结论等价，替换/回退不会出现语义漂移。

**Q4：为什么不用现成的 ListWorkers RPC？**

RPC 不是"读不到"，是**"读得贵"**：每轮分配一次跨进程往返 + 序列化 + 服务发现 + 连接池。调度是 2s 轮询 + MQ 事件触发的高频路径，把共享存储闲置、每次远程调用，是拿架构资源填传输损耗。快照 `HGETALL` 一次 RTT 等价于 ListWorkers 的一次返回，替换无缝。

> 追问：它是缓存吗？——是，但更精确说是"**RPC 结果的物化镜像**"：缓存的是"一次跨进程 RPC 的返回"，不是"一次 SQL 查询的结果"。这解释了为什么不能放进程内缓存（其他进程读不到，而 RPC 恰恰是跨进程读），也解释了为什么 QueryJob 的 SQL（<0.5ms）刻意不缓存而这里缓存（瓶颈是 RPC 不是 SQL）。

但注意：**RPC 没有被删除**——它是"Redis 挂了"的完整回退路径，也是管理面查询（GUI/CancelJobShards）的真相接口。快照只是给"调度器读在线负载"这一个高频场景加速。

**Q5：为什么不直读 MySQL workers 表？**

选型时权衡过三个方案（ListWorkers RPC / 直读 MySQL / Redis 镜像），直读 MySQL 被否掉的理由：

1. **绕过数据所有者**："谁在线"的完整语义（20s 超时、status 状态机、HeartbeatTimeoutCheck 线程、离线通知重试）都在 WM 端。直读 = Scheduler 重复实现这套判定 + 直接依赖 workers 表 schema——WM 改表、改在线语义，Scheduler 必须同步改，一套逻辑两处维护。
2. **MySQL 是 fail-fast 组件**：直读路径没有降级可言——MySQL 挂了系统本就要挂；而 Redis 挂了可以回退 RPC。直读等于把一条本可降级的读路径改成了不可降级。
3. **读得最重**：SQL 解析 + 连接池借用归还 + 行到 protobuf 的映射，比 Redis 一次内存哈希读贵一个量级。

> 核心一句话：**负载数据的所有者是 WM——直读 MySQL 是让 Scheduler 绕过数据所有者去读它的私有表；Redis 镜像让 WM 主动"发布"一份快照，Scheduler 被动"订阅"——MySQL 管数据归属（真相），Redis 管数据分发（共享）。**

**Q6：快照里的数据和 RPC 返回的数据有什么区别？**

| 维度 | Redis 快照 | ListWorkers RPC |
|------|-----------|----------------|
| 数据源 | WM 心跳时主动推的镜像 | MySQL 实时全量 |
| 覆盖 | 曾 alive 心跳过的 worker（含已死残留） | 全部注册 worker |
| status 字段 | ❌（9 字段无 status） | ✅ |
| gpu_count | ❌ | ✅ |
| 在线判定 | Scheduler 端 ts 新鲜度过滤 | WM 端 status 状态机 |
| 时效 | 最多 20s 滞后 | 实时 |

所以快照是**负载视图**（调度打分用：负载 + 新鲜度），RPC 是**管理视图**（查询/展示用：状态 + 完整字段）。快照刻意不存 status：调度不需要"这个 worker 的完整状态"，只需要"负载够不够、数据新不新鲜"。

**Q7：那为什么 CancelJobShards、GUI 还直接走 RPC？为什么不统一走快照？**

这是最容易被追问的点。两处走 RPC 是有意的，不是漏网：

- **CancelJobShards**（`scheduler_service.cpp:598`）：任务终态时给 ASSIGNED/RUNNING shard 所在 worker 发取消通知，请求 `filter_status=UNKNOWN` 全量。走快照有两个致命问题：① **快照不保证完整**——WM 的 `HSet` 失败只 WARN 不重试（`worker_manager.cpp:105`）、Redis 故障期间的 worker 压根没写，**活着的 worker 可能不在快照里**，漏发 = 它白转码；② 取消是低频 + 正确性关键路径，宁可多花一次 RPC 求准确，省性能在低频路径上没有意义。
- **GUI worker 面板**（`gui/rpc_client.cpp:168`）：要展示 ON/OFFLINE 状态和 gpu_count——快照从字段结构上就给不了；且 2s 轮询一次，频率不高。
- **LoadOnlineWorkers 内部回退分支**（`scheduler_service.cpp:810`）：那是降级路径本身，RPC 必须留作兜底。

> 一句话：**能用快照的标准是——高频 + 容忍滞后 + 只需要负载字段**。低频、管理面、正确性关键的读取一律走 RPC 真相接口。调度热路径已全部走快照；剩下的直接 RPC 各有不可替代的理由，不是"漏改"。

**Q8：快照会脏吗？残留和一致性怎么处理？**

- **残留**：HSET 的 field 不能单独设 TTL，所以值内嵌 ts、读侧过期过滤（Q3 的 20s 判定即"读侧过期"）；死 worker 的残留 field 由下次同名心跳覆盖——重注册后第一次心跳即刷新，无泄漏。不设 EXPIRE 的另一个原因：TTL 到期删除是写者负担，而读侧过滤零成本——**20s 语义本来就在读侧**。
- **单 key 多 field 而非每 worker 一个 key**：调度循环要"一次拿全量"——`HGETALL` 一次 RTT 等价于 ListWorkers 的一次返回；每 worker 一个 key 得 `SCAN worker:load:*`（多轮 RTT + 游标）或额外维护一个集合 key。
- **不一致**：允许，且只有"快照滞后于 MySQL"一个方向。调度容忍 20s 滞后——评分用负载，一个过期的 worker 最多被少用一轮，下轮 ts 过滤自然剔除；正确性底线在 MySQL 条件更新（分配时 WAITING→ASSIGNED 才是最终裁决），快照只影响"选谁"，不影响"分得对不对"。

**Q9：Redis 挂了怎么办？**

完整回退阶段 9 行为：`HGETALL` 失败/快照空/全过期 → 回退 `wm_stub.ListWorkers` RPC（`scheduler_service.cpp:792-797`），按次判断、无状态机，Redis 恢复自动切回。因为真相在 MySQL、RPC 路径从未删除，Redis 对调度器只是加速层——这就是"可降级组件"语义，与 MySQL 的 fail-fast 刻意区分。

一个现实考量：**边际成本为零**——阶段 10 本就为分布式锁和 ZK 地址缓存引入 Redis，快照是"搭便车"，没有新增任何依赖面；反过来，若系统本来没有 Redis，此用途直读 MySQL 才是更合理的简化（少一份镜像维护，读到的还永远是最新心跳）。**中间件的价值排序永远先问"它挂了我怎么办"，再问"它带来了什么"——这两个问题答案都成立，才值得引入。**

### 4.5 用途二：分布式锁（SETNX）

> 面试叙事主线：**解决什么问题（1）→ 为什么进程内锁/条件更新不够（2）→ 三层防线（3）→ 锁怎么拿（4）→ 锁怎么放（5）→ 释放为什么要 GET 校验（6）→ SETNX 失败如何区分占用与故障（7）→ 竞争场景走查（8）→ 边界与设计原则（9）**

**Q1：这个锁解决什么问题？**

同一 shard 被两个 Worker 同时执行 → 双倍转码资源浪费 + 两份结果互相覆盖 + Merge 产物错乱。三个真实竞争来源：

| 竞争来源 | 场景 |
|----------|------|
| 双路径并发 | SchedulingLoop 轮询线程与 MqConsumeLoop 消费线程**同时**触达同一 shard（MQ 在线时两者共存） |
| 消息重复投递 | RabbitMQ at-least-once：ack 失败/消费者崩溃 → 同一条 `shard.waiting` 重投 |
| 多实例部署 | `docker compose --scale scheduler=2` 时两个 Scheduler 进程同时扫到同一 shard |

**Q2：为什么不用进程内锁？为什么不能只靠 MySQL 条件更新？**

- **`std::mutex` 只保护"同一进程内的线程"**——挡得住双路径并发，**挡不住多实例**（两个进程各有各的锁）。必须用所有实例共享的互斥设施，即 Redis（MySQL 条件更新是另一条路径，见下）。
- **条件更新（`UPDATE ... WHERE status='WAITING'`）单条 SQL 原子**，但它只能拦截**落定**阶段：竞争双方都会走到直连 Worker 的 AssignShard RPC（最贵一步：网络调用 + Worker 端开始干活），只是最后写库时一方失败。锁的意义是**在发 RPC 之前就拦截掉竞争方**，而不是等落定时才发现。

**Q3：三层防线是什么？为什么三层都要？**

`TryAssignShard` 对"重复分配"设三道防线（`scheduler_service.cpp:896-899` 注释）：

```
第 1 层：状态复核（函数入口）— 重新查库，shard 已非 WAITING → skip
        🛡 防：调用方快照过期（另一条路径刚推进）
第 2 层：Redis SETNX 分布式锁 ★ — 拿不到锁且确认被占用 → skip
        🛡 防：多实例/双路径在"同一时刻"竞争
第 3 层：MySQL 条件更新（落定）— UPDATE ... WHERE status='WAITING'，0 行 → 失败
        🛡 防：所有上层防线失效时的最终兜底
```

每层防不同失败模式：第 1 层防"过期快照"（最常见，零成本）；第 2 层防"同时竞争"（拦截最贵的 AssignShard RPC）；第 3 层防"锁失效"（Redis 故障降级时的正确性兜底）。**锁不是正确性的唯一依赖，正确性底线永远是 MySQL 条件更新。**

**Q4：锁怎么获取？**

一条命令原子完成"判断不存在 + 设置 + 过期"（`scheduler_service.cpp:906-912`）：

```
SET shard:lock:{shard_id} scheduler:{pid} NX EX 10
```

- **NX**：仅当 key 不存在才设置——抢锁的原子判定
- **value = `scheduler:{pid}`**：持锁者身份标识（构造见 `:906`），释放时校验用
- **EX 10（TTL 10s）**：防持锁进程崩溃后锁永不释放（死锁）。持锁时间 = 一次分配（状态复核 + RPC + 条件更新，毫秒级），10s 是极端情况的几百倍余量

> 追问①：value 为什么用 `scheduler:{pid}` 而不是随机串/UUID？——身份标识要**可读、可排查**：日志里看到 value 就能定位"哪个实例在持锁"（进程号），随机串没有这个价值却多了生成成本；本机部署下 pid 唯一性足够。
> 追问②：容器 `--scale` 多实例部署下，两个容器的主进程 pid 会相同（pid 命名空间隔离，各自从 1 起算，常见 PID 1），value 撞车有影响吗？——有，但可控：value 撞车只削弱"释放时防误删"这一层（A 释放时校验 `cur == lock_value` 对 B 的锁也成立，极端情况下会误删 B 的锁），**而防误删本就不是正确性依赖**——最坏情况 = 重复分配一次，由第 3 层条件更新 + 消费幂等兜底；且误删需要"持锁超过 TTL（10s）"为前提，正常毫秒级持锁窗口几乎不可能。这与 Q5 追问② 是同一处取舍。

**Q5：锁怎么释放？**

释放前 GET 校验 value 相同才 DEL（`scheduler_service.cpp:936-942`）：

```cpp
auto release_lock = [&]() {
    if (!lock_acquired) return;
    std::string cur;
    bool found = false;
    if (redis.Get(lock_key, cur, found) && found && cur == lock_value)
        redis.Del(lock_key);
};
```

> 追问①：为什么释放前要 GET 校验？——经典陷阱：A 持锁执行变慢超过 TTL，锁被 B 抢走；A 完成后直接 `DEL` 就把 B 的锁删了。校验 `cur == lock_value`（"锁还是不是我拿的那把"）再删，避免误删他人锁。
> 追问②：GET 校验与 DEL 是两步，有没有竞窗？——有：A 校验通过后、DEL 前锁恰好过期被 B 抢走，A 的 DEL 会误删 B 的锁。**已知取舍**：锁的语义是"防重复分配"而非"互斥临界区"，最坏情况 = 重复分配一次，由第 3 层条件更新 + 消费幂等兜底；单实例部署下此竞窗不存在。

**Q6：SETNX 失败如何区分"锁被占用"与"Redis 故障"？**

SETNX 返回 false 有两种截然不同的原因，处理必须不同（`scheduler_service.cpp:914-933`）：

```cpp
if (redis.Get(lock_key, cur, found) && found)
    return false;   // 锁被占用 → 竞争方在干，本实例跳过（最安全）
else
    LOG_WARN("... degrade to MySQL conditional update");  // Redis 故障 → 降级放行
```

- **锁被占用（GET 成功）** → skip：竞争方在干，我不插手
- **Redis 故障（GET 失败/超时）** → **降级放行**：不能因为 Redis 挂了让整个调度停摆。锁是"优化防护"，正确性靠第 3 层——降级后两个竞争方都会发 AssignShard RPC（浪费一次调用），但落定阶段只有一个能成功

> 追问：为什么故障不 fail-fast？——与 RedisClient 整体语义一致（可降级组件：连接失败只 WARN 不拒绝启动）。Redis 是加速/防护件，不是正确性依赖。

**Q7：所有竞争场景怎么被拦住？（走查）**

| 场景 | 竞争方 | 被哪层拦住 |
|------|--------|-----------|
| 轮询与 MQ 同时分配 | 本进程两个线程 | 第 1 层：先到者推进后，后到者查到非 WAITING |
| 两个线程恰好同时通过复核 | 同上（竞窗） | 第 2 层 SETNX：只有一个拿到锁 |
| 多实例（scale=2）同时分配 | 两个进程 | 第 2 层：共享 Redis，只有一个拿到锁 |
| Redis 故障 | 任意 | 第 2 层降级放行 → 第 3 层：后到者 UPDATE 0 行失败 |
| 持锁进程崩溃 | — | TTL 10s 自动过期，其他实例可接管（不死锁） |
| 消息重复投递（同一条 shard.waiting） | 同一线程处理两次 | 第 1 层：第二次查到已非 WAITING → skip |

**结论：无论竞争如何组合，同一 shard 最多只有一个路径完成"落定"（ASSIGNED）**——这就是锁 + 条件更新组合的最终一致性保证。

**Q8：边界与设计原则**

1. **锁是防护不是依赖**：正确性底线在 MySQL 条件更新，锁只是提前拦截、减少浪费——所以可以安全降级
2. **TTL 与持锁时间的量级差**：毫秒级持锁 vs 10s TTL，正常流程永远不会撞 TTL；撞了也只是"多分配一次"，由幂等兜底
3. **value 校验的哲学**：所有"删除/覆盖"型操作（DEL 锁、释放、条件更新）都要带身份/前置状态校验——与 `UpdateIfStatus` 的期望前置状态同一思想
4. **锁粒度 = shard 级**：`shard:lock:{shard_id}` 只锁单个 shard 不锁全局——分配天然并行，互不阻塞

> 代码与日志出处：《11. 阶段10中间件集成.md》第一批（Redis 分布式锁 + TTL 陷阱说明）。

### 4.6 用途三：ZK 服务地址缓存集中化（框架层 mprpc:endpoints）

> 面试叙事主线：**解决什么问题（1）→ 改造前的痛点（2）→ 三层链路（3）→ 为什么 30s TTL（4）→ 为什么 HDEL 共享失效（5）→ 为什么先 Redis 后写本地（6）→ 键值格式与轮询（7）→ 深挖：为什么不用 ZK Watcher / 为什么统一 TTL（8）→ Redis 挂了怎么办（9）**

**Q1：这个缓存解决什么问题？**

mprpc 客户端发 RPC 前要服务发现——查 ZK 上 `/mprpc/services/{service}/{method}/instance-*` 拿 provider 的 ip:port（调用点 `mprpcchannel.cc:919`）。改造前是**每进程私有缓存 + ZK 直读**，问题有两个：① 实例变更（provider 下线/扩容）后各进程**感知滞后且不同步**——每进程各有自己的缓存，一个进程发现变更，其他进程还要等自己的 TTL 到期；② 信息孤岛——新进程冷启动没有缓存，必须自己读 ZK，读到的结果其他进程也看不到。

Redis 作为**集中缓存**让"第一个进程拉到的结果"所有进程共享，且"失效"一次作用于全集群。

**Q2：改造前的痛点具体在哪？**

| 场景 | 改造前（进程内缓存 + ZK 直读） | 改造后（+Redis 集中缓存） |
|------|-------------------------------|--------------------------|
| 实例变更 | 每个进程各自最多滞后 30s 才重新发现，且发现时刻互不相同 | 下一次发现后写入 Redis，**所有进程共享最新地址** |
| 新进程冷启动 | 必须自己读 ZK | 直接 HGET Redis 命中，省一次 ZK 往返 |
| 连接失败 | 清自己缓存，其他进程继续轮询死实例 | HDEL 集中字段，**所有进程同时失效**一起重拉 |

**Q3：三层链路怎么工作？**

`GetHostData`（`mprpcchannel.cc:364-414`）从"进程内缓存 + ZK 直读"升级为三层：

```
第 1 层：本地缓存（30s TTL 内命中）→ 直接返回，零 Redis/ZK 交互（热路径：12 万 QPS 量级）
        代码：:368-381
第 2 层：Redis HGET mprpc:endpoints → 命中填本地缓存返回（省一次 ZK 往返）
        代码：:386-410
第 3 层：ZK 拉取 → 双写本地 + Redis（HSET + EXPIRE 30s）
        代码：QueryEndpointList :286-349
```

**每层省什么/防什么**：本地缓存省"每次 RPC 一次网络交互"（这是 `bench_rpc_stress` 12 万 QPS 的基础）；Redis 省"每进程各自访问 ZK"（信息共享）；ZK 是真相源（Provider 注册的唯一地方）。

失效路径（`InvalidateHostData :418-430`）：RPC 连接失败 → 清本地缓存 + HDEL Redis 集中字段 → 下次发现重新拉 ZK。调用点在 `:937` 与 `:976`（首次失败/重试失败）。

**Q4：为什么本地缓存 30s TTL？**

集中管理的价值 = **实例变更后其他进程及时感知**。本地缓存无限期会让每个进程永远吃自己的旧缓存——Redis 集中管理名存实亡。30s 是"变更感知延迟"与"热路径成本"的折中：保证最多 30s 全集群重新发现，且热路径 30s 内零 Redis/ZK 交互，性能不回退。

> 追问：为什么不是 10s 或 60s？——10s 感知更快，但热路径 Redis 交互多 3 倍；60s 交互更少，但变更感知慢一倍。服务发现的变更在"分钟级最终一致"内足够（与 4.4 负载快照的 20s 心跳超时同级量级），30s 是不牺牲热路径性能前提下最快的感知。

**Q5：连接失败为什么 HDEL 集中字段？**

清本地缓存只影响本进程——其他进程 30s 内仍轮询死实例。**HDEL 后所有进程同时失效、一起重拉 ZK**——"多进程共享失效"是集中管理相对进程内缓存的核心收益：一次连接失败，全集群同一时刻恢复对真相源的重新发现，而不是各自按自己的 TTL 错峰失效。

> 追问：HDEL 失败怎么办？——Redis 不可用时 HDEL 失败无碍（`:424` 注释）：各进程本地缓存 30s TTL 到期后自愈，只是"共享失效"退化为"各自失效"，正确性不受影响。

**Q6：为什么锁顺序"先 Redis 后写本地"？**

Redis 网络操作 2s 超时，**绝不持 `ServiceCacheMutex` 执行**——否则 Redis 卡死会连带卡死整个服务发现热路径（每次 RPC 都过 GetHostData，锁被卡住的进程全线停摆）。代码里的证据：

- 层 2 的 `HGET` 在锁外执行（`:384` 注释）
- 层 3 的 `HSET`/`EXPIRE` 也在锁外（`:319-320` 注释），只有写本地缓存才进锁（`:336`）

> 追问：那本地缓存为什么还要锁？——`ServiceCache()` 是全局 map，多线程并发访问需要互斥；但锁只保护**内存操作**（查/写 map），绝不包**网络操作**（Redis 命令）。这是"锁的范围最小化"的一个实例。

**Q7：键值格式为什么是 CSV？轮询 index 为什么本地维护？**

- **key=`mprpc:endpoints`，field=method 路径，value=CSV endpoint 列表**——endpoint 是 `ip:port` 不含逗号，拼接/解析安全，一次 split 完成（与 4.4 快照串用 `|` 分隔同一思路：固定简单格式，零 JSON 依赖）
- **轮询 index 仍是进程私有**（`PickEndpoint :357` 的静态原子计数器 `nextEndpoint`）——负载均衡语义是**进程视角**的：每个进程独立轮询，N 个进程各自均匀分摊，叠加后整体均匀

> 追问：为什么不在 Redis 里存轮询状态？——共享轮询状态需要跨进程原子操作（且进程数变化时无法重新均匀分摊）；进程本地轮询零协调成本，每个进程均匀访问所有 endpoint，多个进程叠加后整体自然均匀。

**Q8：深挖：为什么不用 ZK Watcher？为什么整个 hash 统一 TTL？**

- **为什么不用 ZK Watcher 实现即时通知**：Watcher 是一次性触发，需要 session 重连后重注册、处理触发风暴，复杂度远高于"TTL 过期重拉"。服务发现对"分钟级最终一致"足够（平台没有毫秒级敏感的实例变更），30s 轮询是更简单的可靠方案。
- **为什么整个 hash 统一 EXPIRE 30s 而不是每 field 单独 TTL**：与 4.4 `worker:load` 同一个问题——**HSET 的 field 不能单独设 TTL**。用 EXPIRE 整个 key 有个良性性质：只要有任意一个 method 在拉取，`HSET + EXPIRE` 就重置整个 hash 的 TTL——**hash 一直在使用就一直不过期**（活跃服务发现永不中断）；不活跃 field 由整体过期 + 连接失败的 HDEL 兜底。

**Q9：Redis 挂了怎么办？**

`redis.enabled()` 为 false 时直接跳过层 2（`:387`），落 ZK 直读——行为与改造前完全一致。与 4.4/4.5 同一哲学：**Redis 对服务发现只是共享加速层，正确性永远在 ZK**——可降级组件，挂了完整回退阶段 9 行为，恢复自动切回。

> 与 4.4 的一句话对比：负载快照缓存的是"**业务 RPC 的结果**"（ListWorkers 等价物），这里缓存的是"**服务发现的结果**"（ZK 读的等价物）——两者设计模式同构：真相在 ZK/MySQL，Redis 是共享分发层，挂了完整回退。

### 4.8 与阶段 9（无 Redis）的对比总结

| 维度 | 阶段 9（仅 MySQL） | 阶段 10（+Redis） |
|------|-------------------|------------------|
| Worker 负载获取 | 每轮分配 ListWorkers RPC | Redis 快照一次 RTT，RPC 仅作降级 |
| 多 Scheduler 防重复分配 | 仅 MySQL 条件更新（落定阶段拦截） | SETNX 在发 RPC 前拦截 + 条件更新兜底 |
| 服务发现 | 每进程私有缓存，变更感知滞后 | 集中缓存 + HDEL 全集群同时失效 |
| 正确性依赖 | MySQL | **仍是 MySQL**（Redis 全部用途可降级） |
