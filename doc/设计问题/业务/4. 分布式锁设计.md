# 分布式锁设计：shard 分配防重复（文档 4）

> 对应 `TryAssignShard` 中的 Redis SETNX 锁（`scheduler_service.cpp:1012-1042`）。
> 阶段 10 第一批引入（2026-08-03），是"多实例/双路径并发分配"的正确性防护之一。
> 配套：《幂等设计.md》3.4（三层防线视角）、《调度模式演进设计.md》3.2（锁与分配的关系）。

## 1. 设计原因：同一个 shard 为什么可能被重复分配

**重复分配的后果**：同一 shard 被两个 Worker 同时执行 → 双倍转码资源浪费 + 两份结果互相覆盖 + Merge 产物错乱。这在"多个入口可以触达同一 shard"的系统里是真实风险：

| 竞争来源 | 场景 |
|----------|------|
| **双路径并发** | SchedulingLoop 轮询线程与 MqConsumeLoop 消费线程**同时**扫描/收到同一 shard（MQ 在线时两者共存） |
| **消息重复投递** | RabbitMQ at-least-once：ack 失败/消费者崩溃 → 同一条 `shard.waiting` 重投 |
| **多实例部署** | `docker compose --scale scheduler=2` 时，两个 Scheduler 进程同时扫到同一 shard |

**为什么不能用进程内锁**：`std::mutex` 只保护"同一进程内的线程"——能挡住双路径并发，但挡不住多实例（两个进程各有各的锁）。必须用**所有实例共享的互斥设施**：Redis（MySQL 条件更新是另一种路径，见下）。

**为什么不能只靠 MySQL 条件更新**：`UPDATE ... WHERE status='WAITING'` 单条 SQL 本身是原子的（这也是第三层防线），但它只能拦截"落定"阶段。如果没有锁，竞争双方都会走到**直连 Worker 的 AssignShard RPC**（最贵的一步：网络调用 + Worker 端开始干活），只是最后写库时一方失败——锁的意义是**在发 RPC 之前就拦截掉竞争方**，而不是等落定时才发现。

## 2. 设计方式：三层防线，锁是第二层

`TryAssignShard` 对"重复分配"设了三道防线（`scheduler_service.cpp:977` 注释）：

```
第 1 层：状态复核（函数入口）
  重新查库，shard 已非 WAITING → skip
  🛡 防：调用方快照过期（另一条路径刚推进）

第 2 层：Redis SETNX 分布式锁 ★ 本文主题
  SETNX 拿不到锁 → 确认被占用 → skip
  🛡 防：多实例/双路径在"同一时刻"竞争

第 3 层：MySQL 条件更新（落定阶段）
  UPDATE ... WHERE status='WAITING'，不匹配 → 0 行 → 失败返回
  🛡 防：所有上层防线失效时的最终兜底
```

**为什么三层都要**：每层防不同的失败模式——第 1 层防"过期快照"（最常见，零成本），第 2 层防"同时竞争"（拦截最贵的 AssignShard RPC），第 3 层防"锁失效"（Redis 故障降级时的正确性兜底）。**锁不是正确性的唯一依赖，正确性的底线永远是 MySQL 条件更新**。

## 3. 锁的详细设计（Redis SETNX）

### 3.1 获取锁

```cpp
// SET key value NX EX ttl：单条命令原子完成"判断不存在 + 设置 + 过期"
// 成功 → +OK；key 已存在 → nil（返回 false = 未取得锁）
lock_value = "scheduler:" + std::to_string(::getpid());
if (redis.SetNxEx(lock_key, lock_value, 10))   // shard:lock:{shard_id}, TTL 10s
{
    lock_acquired = true;
}
```

底层就是一条命令（`redis_client.cpp` `SetNxEx`）：`SET shard:lock:{id} scheduler:{pid} NX EX 10`。

- **NX**：仅当 key 不存在时设置——"抢锁"的原子判定
- **value = `scheduler:{pid}`**：持锁者身份标识，释放时校验用
- **EX 10（TTL 10s）**：防持锁进程崩溃后锁永不释放（死锁）。持锁时间 = 一次分配（状态复核 + RPC + 条件更新，毫秒级），10s 是极端情况的几百倍余量

### 3.2 释放锁

```cpp
auto release_lock = [&]() {
    if (!lock_acquired) return;
    std::string cur;
    bool found = false;
    if (redis.Get(lock_key, cur, found) && found && cur == lock_value)
        redis.Del(lock_key);
};
```

**为什么释放前要 GET 校验 value**：经典陷阱——A 持锁执行变慢超过 TTL，锁被 B 抢走；A 完成后直接 `DEL` 就把 B 的锁删了。校验 `cur == lock_value`（锁还是我拿的那把吗？）再删，避免误删他人锁。

**已知取舍**：GET 校验与 DEL 是两步操作，之间仍有竞窗（A 校验通过后、DEL 前，锁恰好过期被 B 抢走，A 的 DEL 误删 B 的锁）。日志 11 的评估：锁的语义是"防重复分配"而非"互斥临界区"，最坏情况 = 重复分配一次，由第 3 层条件更新 + 消费幂等兜底；单实例部署下此竞窗不存在。

### 3.3 锁被占用 vs Redis 故障：必须区分

SETNX 返回 false 有两种截然不同的原因，处理必须不同（`scheduler_service.cpp:1026-1042`）：

```cpp
if (redis.Get(lock_key, cur, found) && found)
{
    // 锁被占用 → 其他实例正在分配，本实例跳过（最安全的行为）
    return false;
}
else
{
    // Redis 故障 / 锁不存在 → 降级放行（MySQL 条件更新兜底）
    LOG_WARN("... degrade to MySQL conditional update");
}
```

- **锁被占用（GET 成功）** → skip：竞争方在干，我不插手
- **Redis 故障（GET 失败/超时）** → **降级放行**：不能因为 Redis 挂了让整个调度停摆。锁是"优化防护"，正确性靠第 3 层——降级后两个竞争方都会发 AssignShard RPC（浪费一次调用），但落定阶段只有一个能成功

**为什么故障不 fail-fast**：与 RedisClient 整体语义一致（可降级组件：连接失败只 WARN 不拒绝启动）。Redis 是加速/防护件，不是正确性依赖。

## 4. 怎么解决问题：竞争场景走查

| 场景 | 竞争方 | 被哪层拦住 |
|------|--------|-----------|
| 轮询与 MQ 同时分配 | 本进程两个线程 | 第 1 层状态复核（先到者推进后，后到者查到非 WAITING） |
| 两个线程恰好同时通过复核 | 同上（竞窗） | 第 2 层 SETNX：只有一个拿到锁 |
| 多实例（scale=2）同时分配 | 两个进程 | 第 2 层 SETNX：共享 Redis，只有一个拿到锁 |
| Redis 故障 | 任意 | 第 2 层降级放行 → 第 3 层条件更新：后到者 UPDATE 0 行失败 |
| 持锁进程崩溃 | — | TTL 10s 后锁自动过期，其他实例可接管（不死锁） |
| 消息重复投递（同一条 shard.waiting） | 同一线程处理两次 | 第 1 层：第二次查到已非 WAITING → skip |

**结论：无论竞争如何组合，同一 shard 最多只有一个路径完成"落定"（ASSIGNED）**——这就是锁 + 条件更新组合的最终一致性保证。

## 5. 边界与设计原则

1. **锁是防护不是依赖**：正确性底线在 MySQL 条件更新，锁只是提前拦截、减少浪费——所以可以安全降级
2. **TTL 与持锁时间的量级差**：毫秒级持锁 vs 10s TTL，正常流程永远不会撞 TTL；撞了也只是"多分配一次"，由幂等兜底
3. **value 校验的哲学**：所有"删除/覆盖"型操作（DEL 锁、释放、条件更新）都要带身份/前置状态校验，防止旧操作破坏新状态——与 `UpdateIfStatus` 的期望前置状态同一思想
4. **锁粒度 = shard 级**：`shard:lock:{shard_id}`，只锁单个 shard，不锁全局——分配天然并行，互不阻塞
