# 6. NotifyWorkerOffline 待重试设计（通知送达保证）（文档 6）

> 对应 `HeartbeatTimeoutCheck` 线程中的 `pending_notify` 待重试集合
> （`worker_manager.cpp:193-292`），阶段 8 #11 修复引入。
> 它是调度可靠性的三大兜底之一（`NotifyWorkerOffline`）的**送达保证机制**，
> 与超时重扫（文档 5）、启动恢复互补。

## 1. 设计背景：故障恢复链路的关键一跳

**故障恢复主链路**（Worker 死亡时）：

```
Worker 心跳停止（20s）
   → MarkOfflineIfTimeout 原子置 OFFLINE        （worker_manager.cpp:189-193）
   → NotifyWorkerOffline RPC 通知 Scheduler     （worker_manager.cpp:202-215）
   → Scheduler 把该 Worker 名下 ASSIGNED/RUNNING
     的 shard 重置 WAITING → 重新分配给其他 Worker
```

其中 **NotifyWorkerOffline 是 RPC 调用**——可能失败：Scheduler 宕机、网络抖动、5s 超时（`nw_ctrl.SetTimeoutMs(5000)`）。

## 2. 问题：通知失败会发生什么？—— ASSIGNED shard 永久卡死

### 2.1 "下一轮会重试"是错的

外层注释（`worker_manager.cpp:182-183`）写的是：

> NotifyWorkerOffline RPC 失败时不重试——心跳超时检查每 2 秒运行一次，如果 Scheduler 暂时不可用，下一轮会再次检测并重试通知。

但这个假设**不成立**。下一轮扫描时（`worker_manager.cpp:185`）：

```cpp
if (w.status != static_cast<int32_t>(WorkerStatus::WORKER_ONLINE))
    continue;
```

Worker **已经被标记 OFFLINE** → 直接 `continue`，永远进不了 `MarkOfflineIfTimeout` 分支（它的 WHERE 条件也是 `status=ONLINE`，对已 OFFLINE 的 Worker 是 no-op）。**通知失败后，扫描循环永远不会再对它触发通知**——除非有显式的重试机制。

### 2.2 Scheduler 侧为什么不能兜底

Scheduler 的超时重扫（文档 5）对 ASSIGNED shard 的处理是（`scheduler_service.cpp:1315-1316`）：

```cpp
// 原 Worker 不在 ONLINE 列表：已离线/注销
// 跳过该片，不重置——NotifyWorkerOffline 会负责重调度
continue;
```

**关键**：重扫发现原 Worker 已不在 ONLINE 列表时，明确依赖 `NotifyWorkerOffline` 来做重调度——**这条路径和通知是互相依赖的关系**：

| 路径 | 触发 | 依赖 |
|------|------|------|
| `NotifyWorkerOffline`（即时） | WM 心跳超时检测 | 通知必须送达 Scheduler |
| 超时重扫（30s/5min 兜底） | shard 状态超时 | 原 Worker 仍在 ONLINE 列表才 QueryShard；**已 OFFLINE 则跳过，依赖通知** |

两条路径互相指向对方，**通知一旦丢失，ASSIGNED shard 就陷入死锁：永久卡在 ASSIGNED，永不重调度**（RUNNING shard 有 5 分钟超时兜底能恢复，但那是分钟级的慢恢复）。

### 2.3 Scheduler 宕机场景

若通知失败是因为 Scheduler 宕机：期间 WM 的扫描每 2s 都看到"已 OFFLINE"而跳过；等 Scheduler 恢复后，**没有 pending 机制的话通知永远不会重发**——一批 shard 永久卡死，且没有任何日志能发现（除了最初的失败 WARN）。

### 2.4 小结

| 不加待重试 | 后果 |
|------------|------|
| ASSIGNED shard | **永久卡死**（重扫与通知互相依赖，通知丢失则死锁） |
| RUNNING shard | 5 分钟超时慢恢复，期间任务毫无进展 |
| Scheduler 短暂宕机 | 通知永久丢失，恢复后无人重发 |
| 可观测性 | 只有一条失败 WARN，之后静默 |

## 3. 设计：pending_notify 待重试集合

### 3.1 结构

```cpp
// 阶段 8 #11：NotifyWorkerOffline RPC 失败的 worker 需要持续重试
static std::unordered_set<std::string> pending_notify;   // 待重试 worker_id 集合
static std::mutex notify_mutex;                          // 保护该集合
```

函数内 **static** 容器：进程级共享、生命周期持续到进程退出。`HeartbeatTimeoutCheck` 每 2s 一轮，集合在整个进程存活期间有效。

### 3.2 生命周期（一轮循环内）

```
扫描阶段（:169-235）
   └─ 通知失败 → 加锁 insert(worker_id) → 入集合          (:229-232)
   └─ 通知成功 → 无事发生

重试阶段（:237-292，本轮扫描结束后）
   └─ 加锁拷贝快照 to_retry，解锁后遍历                    (:239-243)
   └─ 对每个 pending worker：
       ├─ 复查：worker 已回 ONLINE？ → 丢弃 pending        (:247-262, fix #5)
       ├─ 重发 NotifyWorkerOffline → 成功 → 加锁 erase    (:277-283)
       └─ 再失败 → 留在集合，下一轮继续试                  (:284-290)
```

**失败永不离场**：重发失败不 erase，集合里的 worker 每 2s 重试一次，直到成功或 worker 复活——即 **at-least-once 送达语义**。

### 3.3 为什么拷贝快照再遍历（:239-243）

遍历 `to_retry` 时不持锁——重发成功的 `erase`（:282）发生在本轮遍历中，若直接遍历 `pending_notify` 本体并在循环内 erase 当前迭代器以外的元素会引发迭代器失效/漏删。**拷贝快照 + 锁只保护拷贝瞬间**，遍历和修改分离，逻辑简单无竞态。

## 4. fix #5 复查：为什么重试前先查 Worker 存活状态（:247-262）

**场景**：网络分区 → Worker 被标 OFFLINE → 通知失败入集合 → **网络恢复，Worker 活着回来并重新注册（status 回 ONLINE）** → 若盲目重发 `NotifyWorkerOffline`，Scheduler 会把**存活 Worker 正在执行的 shard** 重置 WAITING 重新分配 → **双份转码**（旧执行的结果靠 attempt_id 校验拒绝，但白白浪费一次转码 + 窗口期内可能出乱子）。

**修复**：重试前 `Get(worker_id)` 复查 `status == ONLINE`：

```cpp
auto w_opt = WorkerStore::GetInstance().Get(worker_id);
if (w_opt.has_value()
    && w_opt->status == static_cast<int32_t>(WorkerStatus::WORKER_ONLINE))
{
    // worker 已复活，丢弃 pending，不再通知
    pending_notify.erase(worker_id);
    continue;
}
```

> 注：`UpdateHeartbeat` 语义调整后（`WHERE status<>OFFLINE`，文档见 common_store.h），
> OFFLINE Worker 的复活路径从"心跳自动恢复"变为"**重新注册恢复**"（Worker 侧收到
> `alive=false` 后重发 RegisterWorker）。复查条件（`status==ONLINE`）对两种恢复路径都正确。

## 5. 为什么加锁

### 5.1 事实：当前是单线程访问

`pending_notify` 的所有读写（insert :231 / 拷贝 :241-242 / erase :260、:282）都在 `HeartbeatTimeoutCheck` **这一个线程内**（扫描块和重试块是同一轮循环的两个阶段）。严格意义上当前不存在并发。

### 5.2 那为什么还加锁——三个理由

1. **static 容器的进程级共享性**：函数内 static 变量是进程内共享资源，生命周期贯穿整个进程。C++11 只保证 static 局部变量的**初始化**是线程安全的（magic statics），**初始化后的读写访问不自动安全**。一旦未来任何代码（如 RPC handler 线程池、注册回调）需要读写该集合，没有锁就是数据竞争（UB）。
2. **防御性声明**：把容器声明为"受保护资源"，从结构上**禁止**未来不加锁的访问——成本趋近于零（每轮 2 次锁，2s 才一轮），换来的是未来扩展时不会踩数据竞争。
3. **跨代码块的一致性**：insert 在扫描阶段、erase 在重试阶段，两处相距几十行。锁让"这两个块操作的是同一份受保护状态"这一事实显式化，防止未来重构时把重试逻辑拆到独立线程时遗漏加锁。

## 6. 整体设计闭环

```
Worker 死亡
   │
   ▼
MarkOfflineIfTimeout（原子置 OFFLINE）            ← 与 Heartbeat 行锁互斥，消除 TOCTOU
   │
   ▼
NotifyWorkerOffline ──成功──► Scheduler 重调度     ← 即时路径（秒级）
   │
   失败
   │
   ▼
pending_notify 集合 ──每 2s 重试──► 成功 → 出集合
   │                                     │
   │                                     ▼
   └─ worker 已复活（ONLINE）→ 丢弃      重调度完成，shard 重新执行
```

**设计要点**：
- 重试无限次直到成功（at-least-once），不设重试上限——通知是幂等的（Scheduler 侧 `NotifyWorkerOffline` 对非终态 shard 重置 WAITING，重复通知最多是重复把已 WAITING 的 shard 置 WAITING，无害）
- 重试前复查 worker 存活，防止把活 Worker 的执行误重置（fix #5）
- 失败日志持续打 WARN（:286-289），可观测性上每 2s 能发现"通知一直没送达"——而旧设计只有一条失败日志后就静默
