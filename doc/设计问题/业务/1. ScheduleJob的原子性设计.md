## 问题 1：为什么 ScheduleJob 必须作为原子单元？（并发 ScheduleJob 混合分片计划）

### 1.1 一句话结论

`ScheduleJob` 内部是「幂等检查 → ffprobe 探测 → 切分落库 → shard_count 回填」四段操作，**必须整体持锁串行执行**。否则同一 job 的并发请求会同时通过"还没有 shard"的幂等检查（check-then-act 竞态），各自探测、各自落库，导致**两套分片计划交错混合**：shard 集合与 shard_count 不一致，下游转码、合并、终态判断全部错乱。

### 1.3 并发来源：同一 job 的两个调用方

同一个 job 的 `ScheduleJob` 可能同时到达两个请求：

| 调用方 | 触发时机 |
|--------|----------|
| **SubmitJob 内联重试** | RPC 超时后 sleep 1s 重试，最多 3 次。网络超时意味着"请求已发出、响应没回来"——**服务端可能已经受理并切分了**，但客户端不知道，会重发 |
| **PendingScanLoop 后台线程** | SubmitJob 重试耗尽后 job 留在 PENDING，JobService 的扫描线程（2s 一轮）发现后重新发起 `ScheduleJob` |

典型时序：第一次调用响应丢失 → 客户端内联重试请求 A 到达，同时扫描线程请求 B 到达（或 A 的重试与 B 先后紧贴）→ 两个 RPC 工作线程并发进入 `ScheduleJob`。

### 1.4 为什么无锁会出问题 —— check-then-act 竞态

`ScheduleJob` 的幂等检查是"查 shard 表为空 → 才切分"，但**检查与写入之间不是原子的**。两个请求 A、B 并发进入时：

| 步骤 | 请求 A | 请求 B |
|------|--------|--------|
| ① 幂等检查（`:167`） | `ListByJob` 看到空集 → 判定"需要切分" | 同时看到空集 → 也判定"需要切分" |
| ② ffprobe 探测（`:227`） | 探测成功：30s 视频 / 15s 分片 = **2 片** | 探测失败 → 回退 `job_duration_fallback_sec=60s` = **4 片** |
| ③ 切分落库（`:275`） | 插入 `job_shard_0`、`job_shard_1` | 插入 `job_shard_0..job_shard_3` |

注意 ② 中两个请求算出不同 shard_count 并非偶然：ffprobe 探测是外部进程调用，可能因文件被占用、瞬时 IO 问题而失败，失败即回退配置值——**同一次视频，两次请求完全可能算出不同的分片数**（即使参数相同）。

③ 的落库表现由两个事实决定：

- shard_id = `job_id + "_shard_" + i`（`:285`），两个计划的前缀段**必然撞同一个主键**
- `shards` 表 `PRIMARY KEY (shard_id)`（`mysql_pool.cpp` 建表语句）；`ShardStore::Insert` 对主键冲突（MySQL errno 1062）**静默返回 false**（幂等拒绝、不打错误日志），而 `:309` 的调用处**不检查返回值**

于是两个计划按到达顺序交错落库，最终表里的行是两套计划的**混合体**：A 的 `shard_0/1`（区间 [0-15s)、[15s-30s)）+ B 的 `shard_2/3`（区间 [30s-45s)、[45s-60s)）。这四行时间区间连续但**覆盖了 60s**，而视频实际只有 30s——最后两片是超 EOF 的冗余分片；反过来交错（B 先落库）则 2 片计划的 shard 行丢失，区间 0-30s 的转码永远缺块。

### 1.5 危害链条

混合落库后，每个请求仍按**自己算出的 shard_count** 回填 job 记录（`:317-321`）并写进响应（`:345`），并与 `:326-334` 发布 MQ `shard.waiting` 事件。最终不一致沿链路放大：

```
shard 表行 = 两套计划的混合（区间重叠/超 EOF/部分丢失）
    │
    ├─► job.shard_count 与实际行数不一致（如 count=2，表里 4 行）
    │
    ├─► MQ 发布了不存在的 shard 的等待事件（消费线程查库落空/跳过）
    │
    └─► ResultCollector 按 shard_count 等"所有分片完成"后 Merge：
           - 行数 > count：多余的 shard 永远 WAITING/FAILED，job 卡死或误判失败
           - 行数 < count：等不齐，job 永久卡非终态
           - 区间错乱：合并产物缺段 / 时长不符（超 EOF 的冗余分片转码必失败）
```

### 1.6 解决方案：全局互斥 + 幂等早退

**第一道防线（互斥）**：函数入口 `std::lock_guard<std::mutex> schedule_lock(g_schedule_job_mutex)`（`:144`），把「幂等检查 + 探测 + 切分落库 + shard_count 回填」整体串行化：

- 请求 A 先拿锁，完整跑完四段，释放锁
- 请求 B 此时才进入，**重新执行幂等检查**——此时能看到 A 写入的 shard（MySQL 共享，`:167` 的 `existing_shards.empty()` 为假）

**第二道防线（幂等早退，fix #14）**：B 在锁内看到已有 shard 后直接返回现有计划（`:168-199`，`accepted=true` + 现有 shard 列表 + 现有行数），**不再重复探测和切分**。两道防线配合的效果：后到者永远"继承"先到者的分片计划，而不是再写一份。

锁的本质是关掉 check-then-act 的竞态窗口：让后到的请求看到前一个请求的成果，而不是与它同时读到"空"。MySQL 行锁/唯一索引无法单独兜底——因为幂等检查（SELECT 集合为空）与批量 INSERT 是两个操作，且 Insert 对冲突是静默吞掉的，检查端无法感知部分失败。

### 1.7 为什么一把全局锁就够

- **低频路径**：`ScheduleJob` 只在 job 提交 / PENDING 重试时调用（job 提交是用户级低频操作），锁竞争可以忽略
- **互斥粒度 vs 复杂度**：按 job 粒度加锁（per-job mutex 或行级锁）能提高吞吐，但对低频路径纯属过度设计，还引入"锁表生命周期"管理问题
- **耗时可接受**：一次切分 = 一次 ffprobe（秒级）+ N 条 INSERT（毫秒级），串行化后最坏情况是并发提交的 job 排队等待，不会饥饿
