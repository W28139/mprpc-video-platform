# Grafana 面板的可观测性设计

---

> **文档定位**：站在**使用者**角度。本部分的代码实现由 Claude 生成，本文不讲实现细节，只讲两件事——**为什么这么设计**（需求层面的理由）和**如何使用**（部署与读面板）。

## 1. 这是什么

一套插上即用的监控体系，覆盖「埋点 → 暴露 → 抓取 → 展示 → 告警」全链路：

```text
5 个服务各自暴露 /metrics（HTTP 端口 9091-9097，独立配置项 metrics_port）
        │
        ▼
Prometheus（15s 抓取，配置产物 prometheus.yml）
        │
        ├──► Grafana Dashboard（导入即用的 4 行面板，grafana-dashboard.json）
        └──► 告警：Prometheus 集群级规则（alerts.yml）+ 服务日志兜底（双轨）
```

**交付物**（`video_platform/observability/`）：

| 文件 | 作用 |
|------|------|
| `prometheus.yml` | Prometheus 抓取配置（9091-9097） |
| `alerts.yml` | 4 条 PromQL 集群级告警规则 |
| `grafana-dashboard.json` | Grafana 面板，导入即用，零配置 |
| `README.md` | 部署指南 |

配套：每个服务多一个配置项 `metrics_port`，启用后服务内自动提供 `/metrics`（Prometheus 标准格式，curl 即可直接看）。

---

## 2. 为什么需要它

阶段 1-10 系统已跑通全链路，但排查问题只能 `grep` 各服务日志，**没有任何统一视图**：

| 问题 | 后果 |
|------|------|
| 任务吞吐多少？提交/成功/失败各多少？ | 没有总量概念，说不出系统"忙不忙" |
| shard 分布如何？积压在哪个状态？ | 调度异常只能翻日志猜 |
| Worker 负载随时间怎么变化？ | 扩容/缩容决策没有数据支撑 |
| RPC 延迟劣化了吗？哪条链路的？ | 性能问题在用户感知后才被发现 |
| 出问题谁告诉你？ | 没有告警——靠人盯着，而不是系统主动报告 |

**为什么选 Prometheus + Grafana**：业界标准监控栈，生态成熟、免自研展示层；本项目只需要按标准格式暴露指标，抓取、存储、可视化、告警全部复用现成组件。

## 3. 为什么这么设计

> 本节是「需求定义」——这些设计意图是我提出的，实现由 Claude 完成。

### 3.1 埋点设计：一次埋点，全服务受益

RPC 延迟指标埋在每个服务的**客户端链路上**（服务间所有调用都走 RPC）。因此只需要一个埋点，全部服务之间的调用延迟就都能观测到，标签区分具体方法（如 `SchedulerService.ScheduleJob`），无需为每个服务单独埋点。

### 3.2 可降级：观测面绝不能影响可用性

`metrics_port <= 0` 时不启用，服务照常运行。**观测是监控系统的"外挂"**——Prometheus 挂了、metrics 端口挂了，业务不受任何影响（与项目里 Redis/MQ 的可降级组件语义一致，这是本项目一贯的故障面最小化原则）。

### 3.3 为什么每个服务独立端口（9091-9097）

规格里的 `:9090` 是单服务主机写法。本项目单机部署 5 个服务（含 3 个 worker 实例），必须互斥分配端口。若将来每个服务独立主机部署，可统一改回 9090。

### 3.4 面板 4 行 = 4 个观察维度：量 → 态 → 因 → 延

| 行 | 内容 | 回答的问题 |
|----|------|-----------|
| Row 1 | Job 吞吐（提交/成功/失败速率） | 有没有流量？忙不忙？ |
| Row 2 | Shard 分布（当前饼图 + 状态时间线） | 流量卡在哪？积压什么状态？ |
| Row 3 | Worker 负载热力图（CPU/内存/运行中 shard） | 资源够不够？该不该扩容？ |
| Row 4 | RPC 延迟（热力图 + P50/P90/P99） | 链路快不快？哪条链变慢了？ |

**从上往下是一套排查逻辑**：先看有没有流量 → 再看流量卡在哪 → 再看资源够不够 → 再看链路快不快。面试回答面板设计就讲这条主线。

面板布局上的两个设计细节（都属于"怎么读"的问题）：

- **同一状态两个图**：饼图看"此刻"的积压构成，时间线看"从什么时候开始"堆积——排查问题必须两者都要（只看现状找不到开始时间，只看趋势不知道当前严重程度）
- **热力图而不是折线**：Worker 负载折线只能看"现在多高"，热力图能看"80-100% 区间持续了多久"——扩缩容决策要的是后者

### 3.5 告警双轨：没装 Prometheus 也有告警

- **Prometheus 侧**（alerts.yml）：集群级 PromQL，4 条规则，触发后送 Alertmanager 通知（邮件/webhook）
- **服务日志兜底**：每个服务进程内内置告警评估器，30s 一轮，触发/恢复直接打印日志

**为什么双轨**：验收要求"告警至少日志打印"——若只依赖 Prometheus，没部署监控时告警就完全失效。双轨保证**无论装不装监控，异常都能被发现**；装上后 Prometheus 侧提供集群级聚合口径，双轨并存。

4 条告警规则及其"为什么"：

| 告警 | 阈值 | 为什么盯它 |
|------|------|-----------|
| 无在线 Worker | `worker_online < 1` 持续 1min | 平台彻底不可用，critical |
| 调度队列积压 | `queue_size > 100` 持续 2min | Worker 容量不足或调度异常，提前于用户感知扩容 |
| 任务失败率 > 30% | 5min 窗口，持续 5min | 转码链路故障（输入问题/ffmpeg 问题），快速定位 |
| RPC P99 > 1s | 持续 5min | 长尾延迟劣化，链路或中间件异常信号 |

### 3.6 指标口径设计（每个指标为什么这么定义）

口径是需求的核心——面试被追问"指标怎么定义的"，答这些：

- **job_submitted_total 在"参数校验通过后"计数**：校验失败的请求不计，保证失败率的分母 = 平台实际受理的任务数，不是所有请求数
- **scheduler_queue_size = WAITING + ASSIGNED**：调度器"已接受但还没跑起来"的全部工作才是真正的积压（ASSIGNED 是已分配未开始，也是积压）。它和 shard_waiting 严格区分，不重复
- **失败率口径**：`失败 / 提交`（Prometheus 集群级）与 `失败 / 终态`（进程内兜底，因单进程拿不到提交数）两套口径，阈值一致、稳态数值近似——双轨共存时口径差异是刻意设计，不是 bug
- **shard_count 全状态显式上报（含 0）**：某个状态归零后若停止上报，Prometheus 保留旧值，饼图上出现**永不消失的残留扇区**——显式置 0 保证曲线实时归零
- **P99 与 Prometheus 算法一致**（累计桶 + 线性插值），保证进程内告警与 Prometheus 侧数值可比

## 4. 如何使用

### 4.1 快速验证（不需要安装任何东西）

```bash
# 服务启动后直接 curl，Prometheus 标准文本格式
curl -s http://127.0.0.1:9091/metrics | head            # job_submitted_total 等
curl -s http://127.0.0.1:9092/metrics | grep shard_     # shard 状态分布
curl -s http://127.0.0.1:9093/metrics | grep worker_    # worker 负载
curl -s http://127.0.0.1:9094/metrics | grep job_       # 任务成功/失败计数
curl -s http://127.0.0.1:9095/metrics | grep transcode  # 转码耗时直方图
```

### 4.2 部署 Prometheus

```bash
sudo apt install prometheus
prometheus --config.file=video_platform/observability/prometheus.yml
# Web UI: http://localhost:9090 → Status/Targets 应看到 5-7 个 UP；Rules 看到 4 条
```

### 4.3 部署 Grafana 并导入面板

```bash
sudo apt install -y grafana   # 或下载 tar.gz 免安装运行
```

1. 登录 Grafana（默认 admin/admin）
2. **Data sources** → Add Prometheus，URL 填 `http://localhost:9090`
3. **Dashboards** → New → Import → 上传 `grafana-dashboard.json`，数据源选刚添加的 Prometheus
4. 看到 4 行面板即成功；Row 3 顶部下拉可筛选单个 Worker

### 4.4 告警

- 没装 Prometheus：服务日志直接出现 `ALERT [xxx] firing/recovered`（兜底生效）
- 装了 Prometheus：规则触发后送 Alertmanager，按需配置邮件/webhook

### 4.5 故障演练（验证监控真的有用）

```bash
# 场景 1：无 Worker 告警
kill <transcode_worker_pid>
# ~20s 心跳超时 → worker_online 归 0 → 约 1 分钟内日志出现 ALERT [worker_offline] firing

# 场景 2：失败率告警
./bin/job_client submit --input /nonexistent.mp4
# 任务 FAILED → job_failed_total +1 → ALERT [job_failed_rate_high] firing
```

## 5. 效果

全部实测验证：

- **链路通**：curl 5 个端口均返回标准指标；非 /metrics 路径返回 404
- **指标联动**：提交真实视频 → 3 shard 全 SUCCESS → `job_submitted_total=1`、`job_success_total=1`、`transcode_duration_ms_count=3`、`shard_count{status=SUCCESS}=3` 采样正确
- **告警生效**：kill worker → `ALERT [worker_offline] firing`，重启后 `recovered`；提交不存在的输入 → `ALERT [job_failed_rate_high] firing`
- **真实部署**：Prometheus 2.45 + Grafana 12.0.0，5 target 全部 UP、4 条规则加载、面板导入后数据可查
- **附带收益**：部署实测中监控暴露并修复了 2 个框架级缺陷（ZK 同步调用无限阻塞导致调度停摆、RabbitMQ 消费锁死）——**这正是可观测性的价值：grep 日志时代"系统卡了看不出卡在哪"，有了监控后问题被快速定位**
