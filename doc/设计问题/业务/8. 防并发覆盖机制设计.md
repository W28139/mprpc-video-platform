# 防并发覆盖机制设计（UpdateIfStatus 条件更新）

> 文档日期：2026-08-07
> 关联代码：`video_platform/src/common_store.cpp`、`video_platform/include/video_platform/common_store.h`
> 关联日志：阶段 4 #S4（`doc/更新业务日志/4. 阶段4代码审查与Bug修复.md`）、阶段 9（`doc/更新业务日志/10. 阶段9数据持久化MySQL.md`）

## 1. 概述

本机制是视频平台**所有状态推进点的写入规范**：任何把 job/shard 状态从一个值推进到另一个值的写操作，都必须走

```cpp
Store::UpdateIfStatus(id, {快照前置状态}, record)
```

它在 SQL 层面把「检查前置状态」和「写入」合并为**一条原子的 `UPDATE ... WHERE id AND status IN (...)`**，从根上消除多进程并发下的「读-改-写」竞态（lost update / 快照覆盖）。

一句话：**先到的写者生效，后到的旧快照不覆盖已改变的状态。**

---

## 2. 背景与问题

### 2.1 架构演变：一致性从「进程内」变为「跨进程」

阶段 1-8，平台是**每进程内存 Store**（`unordered_map + shared_mutex`）。每个微服务操作自己的副本，进程之间通过 RPC 同步——状态一致性问题被「跨进程同步 RPC」兜住，进程内的互斥锁保证了同进程读写互斥。

阶段 9（MySQL 持久化）把数据源收敛为**三个进程共享的 MySQL 表**（jobs/shards/workers），并顺势删除了 `UpdateJobStatus` / `NotifyJobCanceled` 两个跨进程同步 RPC。从此：

- **一致性责任全部移交数据库**，多进程写同一行
- 「Get → 修改 → Update」的 **read-modify-write 窗口**从进程内（有锁保护）暴露为跨进程（无锁保护）
- 后写覆盖先写：一个进程拿着旧快照，可以把另一个进程刚推进的状态**踩回去**

### 2.2 竞态本质

所有事故都是同一模式：

```
时间 →
进程 A:  Get(id) → 快照 {status=X}
进程 B:  Get(id) → 快照 {status=X}
进程 B:  Update(id, {status=Y})        ← B 先写，状态变为 Y
进程 A:  Update(id, {status=Z})        ← A 用旧快照覆盖！X 不再是当前状态，但 A 不知道
```

Check-then-act 的经典竞态：**检查与写入之间的窗口期**，另一进程改变了被检查的对象。

### 2.3 具体事故场景（都是真实发生或推演过的）

| # | 场景 | 后果 |
|---|------|------|
| 1 | **Scheduler 超时重扫**把 RUNNING shard 重置为 WAITING，同时 **RC 已写入 SUCCESS** | SUCCESS 被覆盖回 WAITING，终态判定破坏，任务永远无法收敛 |
| 2 | **Scheduler 分配循环**把 WAITING→ASSIGNED，同时**用户 CancelJob** 已标记 CANCELED | 已取消的 shard 被「复活」继续执行 |
| 3 | **CancelJob** 把 job 标记 CANCELED，同时 **RC 并发写入 SUCCESS** | 成功的任务显示为已取消，或者反之 |
| 4 | **PendingScanLoop** 重调 ScheduleJob 后推进状态，响应丢失场景下 job 实际已 SUCCESS | 已 SUCCESS 的 job 被回退为 SCHEDULING，**永久卡非终态** |
| 5 | **启动恢复扫描**（进程崩溃重启）重置 ASSIGNED/RUNNING→WAITING，与并发写互踩 | 覆盖其他进程刚推进的状态 |
| 6 | **阶段 4 #S4（内存版原型）**：SchedulingLoop 用快照副本覆盖 RescheduleShard 刚写入的 `retry_count`/`attempt_id` | retry_count 被清零、attempt_id 不一致，阶段 5 的幂等校验和重试上限失效 |

事故 #6 是机制的最早原型问题（阶段 4 时还是内存版，同进程内竞态）；阶段 9 MySQL 化后问题从「同一进程的两个线程」放大为「5 个进程并发写同一行」，频率和危害都显著上升。

---

## 3. 设计目标

1. **根除 read-modify-write 竞态**：不是缩小窗口，而是让「检查+写入」原子化
2. **跨进程安全**：正确性不依赖任何进程内锁或跨进程同步 RPC（后者已被删除）
3. **低开销**：不引入事务、悲观锁、分布式锁等重机制
4. **调用方表达力**：支持「期望状态 ∈ 集合」的推进（如 `{ASSIGNED, RUNNING}`）
5. **可判定**：调用方能知道推进是否成功，据此决定后续动作（如是否发事件）

---

## 4. 方案设计

### 4.1 核心思想：乐观并发控制（CAS）

机制本质是数据库层的 **Compare-And-Swap**：

- **Compare**：前置状态必须等于快照时的值（`status IN (expect...)`）
- **Swap**：满足才写入新状态

不满足则整条 UPDATE 无效果（匹配 0 行），不覆盖任何已改变的状态。

### 4.2 API 设计

```cpp
// 条件更新：仅当 id 存在且 status ∈ expect_statuses 时才整行覆盖
// 返回 true = 推进成功；false = 条件不满足（状态已被其他进程改变）或 DB 错误
bool JobStore::UpdateIfStatus(const std::string& job_id,
                              const std::vector<int32_t>& expect_statuses,
                              const JobRecord& job);

bool ShardStore::UpdateIfStatus(const std::string& shard_id,
                                const std::vector<int32_t>& expect_statuses,
                                const ShardRecord& shard);
```

**空集合语义**：`expect_statuses` 为空 = 无条件更新。`Update()` 就是 `UpdateIfStatus(id, {}, record)` 的委托——保持原有无条件写接口，同时让所有状态推进点显式传前置状态。

### 4.3 SQL 形态与原子性

```sql
UPDATE shards SET status=2, assigned_worker='...', ...
 WHERE shard_id='...' AND status IN (1);
```

关键点：

- **单语句原子性**：MySQL 对单条 UPDATE 的 WHERE 匹配与写入是原子的，不需要事务包裹。并发执行时行锁天然串行化，先到先得，后到者 WHERE 不匹配、0 行受影响
- **无窗口**：没有「先 SELECT 检查再 UPDATE」两步，检查条件直接内嵌在写入语句里，竞态窗口为零
- **CLIENT_FOUND_ROWS**（连接池 Flag）：UPDATE 后 `affected_rows` 在「值未变化」时仍返回匹配行数——否则「全量覆盖更新」（比如刷新心跳、重写相同状态）会被误判为未命中。这是本机制返回值的正确性基石
- 返回值 = `AffectedRows() > 0`，即为「我的推进是否生效」

### 4.4 调用方契约

```cpp
// 标准三段式：快照 → 本地修改 → 条件更新
auto opt = Store::Get(id);
if (!opt.has_value()) { /* 处理不存在 */ }

auto record = opt.value();
int from_status = record.status;      // ① 快照前置状态
record.status = NEW_STATUS;           // ② 本地修改（仅改状态相关字段）
record.updated_at = NowMs();

bool ok = Store::UpdateIfStatus(id, {from_status}, record);  // ③ 条件推进
if (ok) { /* 推进成功：可以发事件/计数/通知 */ }
else     { /* 被并发修改：谁先到谁赢，通常静默忽略，由兜底循环收敛 */ }
```

失败处理的哲学：**不重试、不覆盖，交给兜底循环收敛**。系统的四个兜底循环（SchedulingLoop 重扫、TerminalSweepLoop 终态判定、PendingScanLoop、启动恢复扫描）会基于最新状态重新决策——例如 RC 写 SUCCESS 失败说明状态已被 Scheduler 改掉，下一次上报或重扫会再走一遍判定。

### 4.5 与备选方案的对比（为什么不用别的）

| 方案 | 为什么不用 |
|------|-----------|
| **悲观锁（`SELECT ... FOR UPDATE`）** | 需要事务 + 显式持有锁，锁期间占用连接池连接；而本场景单条 UPDATE 已原子，悲观锁是杀鸡用牛刀，且事务化后所有调用点都要改造成事务块 |
| **版本号字段（`version` 列，`WHERE version=n`）** | 需要额外列 + 每次更新自增 + 所有读改写成携带版本。状态字段本身就是天然的版本号——expect 集合还更精确（期望特定状态而非「任意比 n 新」），例如启动恢复只允许 `{ASSIGNED, RUNNING}` 被重置，不允许重置已是 WAITING 的 |
| **进程内互斥锁** | 阶段 9 前有效（同进程竞争），MySQL 化后竞争发生在**跨进程**，进程内锁完全无效 |
| **分布式锁（Redis SETNX）** | 阶段 10 已用于 AssignShard 防「同一个 shard 被分配给两个 worker」。但分布式锁解决的是**互斥**（同一时刻只允许一个操作者），本机制解决的是**版本**（旧快照不得覆盖新状态）——两者互补：互斥锁管「谁能动」，CAS 管「动了之后不踩别人」。且分布式锁有锁过期/释放失败等额外故障面，CAS 无条件这类问题 |
| **「Get 重读防御」（阶段 4 #S4 的修复）** | check-then-act：写前重新 Get 一次拿最新状态，再基于最新状态写。窗口依然存在（重读与写入之间仍可能被并发修改），只是从「大概率踩」降为「小概率踩」。阶段 9 用 CAS 正式取代 |

## 7. 收益总结

1. **根除快照覆盖**：检查+写入原子化，竞态窗口为零——不是降低概率，是消除
2. **多进程天然安全**：正确性由 MySQL 单语句原子性保证，不依赖进程内锁、不依赖跨进程同步 RPC（后者已删除的前提条件）
3. **零额外开销**：单条 UPDATE，无事务、无锁持有；实测 `UpdateIfStatus` 平均 0.166ms（阶段 9 压测记录），满足 <2ms 验收线
4. **返回语义可决策**：`bool` 返回值让调用方知道推进是否生效——启动恢复扫描只在成功后才发 `NotifyShardWaiting` 事件，避免发无效事件
5. **期望集合表达力**：`{ASSIGNED, RUNNING}` 这类「多个合法前置状态」的推进，一个参数表达
6. **架构简化**：是删除 `UpdateJobStatus` / `NotifyJobCanceled` 两个跨进程同步 RPC 的可行性前提——没有 CAS，快照推状态会互相污染权威数据
7. **与分布式锁互补**：锁管互斥（同一 shard 不被分配两次）、CAS 管版本（旧快照不踩新状态），各自解决不同维度

## 8. 局限性与边界

1. **条件只保护状态字段**：`WHERE` 条件仅约束 `status`，同 id 的其他并发写（如只改负载、只改心跳）不受保护。本系统中所有写都由状态推进驱动，不构成实际问题；但若有纯数据字段的并发写，需另行设计
2. **调用方必须显式传快照状态**：如果调用方偷懒传空集合，就退化为无条件覆盖——`Update()` 就是这条退路。规范靠代码审查约束
3. **失败后不重试**：「谁先到谁赢」依赖兜底循环收敛。若某条路径没有兜底循环兜底（理论上都要有），推进丢失后只能等下一次触发——这也是所有状态推进点都处于某个循环内（SchedulingLoop/TerminalSweepLoop/PendingScanLoop）的原因
4. **组合一致性仍需额外机制**：CAS 保证单行推进正确，但跨多行的组合操作（如「全部 shard 成功 → job SUCCESS」的判定与合并）仍需要 MergeMutex 等进程内串行化手段——CAS 不替代它们
