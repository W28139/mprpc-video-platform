# 容器化与 CI/CD 设计

---

> **文档定位**：站在**使用者**角度，从零讲清楚容器化与 CI/CD。本部分的代码实现由 Claude 生成，本文只讲三件事——**目的是什么**（为什么需要它）、**如何使用**（命令怎么跑）、**如何体现**（面试怎么讲）。文中会先把两个基础概念讲透（如果你完全没接触过，先看第 1 节）。

## 1. 前置概念（什么是容器化？什么是 CI/CD？）

### 1.1 容器化：把"应用 + 环境"打包成模板

传统部署的问题：程序依赖操作系统里装了一堆库（protobuf、MySQL 客户端、ffmpeg……），换个机器就要重新装一遍，版本还未必对得上——"在我机器上能跑，到你机器上就跑不了"。

**容器化 = 把程序连同它需要的环境一起打包**。几个概念的类比：

| 概念 | 类比 | 说明 |
|------|------|------|
| **Dockerfile** | 菜谱 | 一步步说明怎么做镜像（装什么依赖、拷贝什么文件） |
| **镜像（image）** | 半成品食材包 | 按菜谱做出来的东西，包含程序 + 全部依赖，可复制、可分发 |
| **容器（container）** | 从食材包做出来的一份菜 | 镜像的运行实例，跑起来就是一个个独立进程 |
| **docker compose** | 一桌宴席的菜单 | 一次启动多个容器的编排清单（哪些菜、什么顺序、端口怎么对外） |
| **数据卷（volume）** | 可拔插的 U 盘 | 容器删了数据还在；视频输入/输出就存在这里 |

好处：**一条命令拉起来**、任何机器行为一致、版本锁死（镜像里就是 ZK 3.8 + MySQL 8.0 + Redis 7 + RabbitMQ 3.12，不会装错版本）。

### 1.2 CI/CD：代码改动后的自动化验证

- **CI（持续集成）**：每次把代码 push 到 GitHub，**云端自动**编译、跑测试、跑全链路验证——不用你手动在本地验证，改坏了当场红叉告诉你
- **CD（持续交付/部署）**：验证通过后自动发布部署。本项目只做了 CI 部分（CD 是后续扩展，面试时可以说"CI 已完成，CD 留作后续"）

## 2. 目的是什么

### 2.1 容器化解决"部署难"

本项目的部署现状：**9 个进程**（5 个自研服务 + ZooKeeper + MySQL + Redis + RabbitMQ）。手工部署意味着：

- 4 个中间件要自己下载、安装、配版本，缺一不可
- 端口冲突（本机已跑着 2181/3306/6379/5672……）
- **启动顺序**问题：MySQL 还没就绪服务就连不上，全得手动排队
- 换个机器（比如面试官要在自己电脑上跑）整套重新来

容器化之后：`docker compose up -d --build` 一条命令，9 个容器按依赖顺序自动拉起。

### 2.2 容器化解决"扩展难"

Worker 不够用？手工部署要复制配置、改端口、改 worker_id。容器化后一条命令：

```bash
docker compose up --scale transcode_worker=3 -d
```

3 个 Worker 副本自动注册（每副本唯一 worker_id 由 `ResolveWorkerId()` 保证：环境变量 > 配置 > hostname）。

### 2.3 CI 解决"验证难"

改一次代码（比如动了调度逻辑），你要手动：起 5 个服务 + 4 个中间件 → 提交视频任务 → 盯日志等 SUCCESS → 检查产物。CI 让这一切自动化：**push 代码后云端自动跑完整套验证**，改坏了当场红叉。

## 3. 项目里做了什么（整体结构）

```text
docker/Dockerfile          镜像配方（多阶段构建，一份配方产出全部 5 个服务）
docker-compose.yml         一键编排：4 中间件 + 5 平台服务
docker/conf/*.conf         6 份 docker 专用配置（host 指向 compose 服务名）
.github/workflows/ci.yml   CI 流水线（4 个 job）
scripts/integration_test.sh 集成测试（CI 里跑的核心验证脚本）
```

### 3.1 Dockerfile：多阶段构建

一份菜谱做两遍：

- **Stage 1 builder（厨师）**：装编译工具 + 依赖 → 编译出全部二进制
- **Stage 2 runtime（上菜的）**：只要运行时库 + ffmpeg + 二进制 + 配置，**不带编译工具链**——镜像更小、更安全

**为什么只写一个 Dockerfile**：本项目一个 CMake 工程一次编译产出全部二进制（5 个服务共用同一份库），写 5 个独立 Dockerfile 内容 90% 重复且要编译 5 遍。单镜像 + compose 用 `command` 区分启动哪个服务，天然支持 `--scale`。

### 3.2 docker-compose.yml：一键编排

- **4 个中间件**（zookeeper:3.8 / mysql:8.0 / redis:7 / rabbitmq:3.12）——版本锁死
- **5 个平台服务**——共用同一镜像，`command` 指定各自启动命令和配置
- **healthcheck + depends_on**：每个中间件自带健康检查（如 MySQL 用 `mysqladmin ping`），服务只会在依赖的中间件**确认就绪后**才启动——解决启动顺序问题
- **数据卷**：MySQL 数据（`mysql-data`）、视频输入/输出（`./data/videos`、`./data/output`）——容器删了数据不丢
- **Worker 不映射端口**：`--scale` 多副本时宿主端口映射会冲突，容器间经 ZK 服务发现互通

### 3.3 CI 流水线：4 个 job

```text
push / PR ──► build（编译全部二进制，上传 artifact）
                ├──► unit-test   单元测试（buffer/threadpool/rpc_protocol）
                ├──► integration 集成测试（真实构建镜像 + 全链路验证）★ 最重
                └──► benchmark   RPC 压测（性能基线）
```

**integration 是 CI 的核心（也是"唯一的真实验证点"）**，它验证的是完整业务闭环：

```bash
# scripts/integration_test.sh 做的事（自动）：
1. 等 9 个容器全部 running（最多 150s）
2. ffmpeg testsrc 生成 30 秒测试视频
3. 容器内 job_client 提交转码任务（重试兜底）
4. --watch 轮询到 SUCCESS（超时 240s）
5. 校验 data/output/{job_id}_merged.mp4 产物存在
```

> 这比大多数项目的 CI（只跑单元测试）强一个档次：**它验证的是"这个系统真的能转码出成品视频"**，而不是"代码能编译"。

## 4. 如何使用

### 4.1 本机一键启动全环境（需装 Docker）

```bash
# 构建镜像并启动全部 9 个容器（第一次构建较慢，之后秒级）
docker compose up -d --build

# 查看状态（9 个容器 healthy/running）
docker compose ps

# 跟踪某服务日志
docker compose logs -f scheduler_service

# 手动跑集成测试（本机也可执行）
./scripts/integration_test.sh

# 扩容：Worker 从 1 个变成 3 个
docker compose up --scale transcode_worker=3 -d

# 停止并删除（含 MySQL 数据卷）
docker compose down -v
```

### 4.2 通过 compose 网络访问服务

容器间通过 **compose 服务名**互通（如配置里 `mysqlhost=mysql` 而不是 `127.0.0.1`），宿主访问靠替代端口映射（本机标准端口被手工部署占用，故用 `19001`/`21810`/`23306` 等）：

| 服务 | 容器内端口 | 宿主端口 |
|------|-----------|---------|
| job_service RPC | 9001 | 19001 |
| job_service metrics | 9091 | 19091 |
| ZooKeeper | 2181 | 21810 |
| MySQL | 3306 | 23306 |

### 4.3 CI 的使用（GitHub Actions）

1. 代码 push 到 `main` 或发 PR → 自动触发
2. GitHub 仓库页面 **Actions** 标签页看流水线：4 个 job 逐个跑，绿勾 = 通过，红叉 = 失败
3. 集成测试失败时自动 dump 全部服务日志（`docker compose logs`），不用自己猜哪一步挂了

> 本项目的 CI 配置已完成并本机实测通过（9 容器 + 集成测试 PASS + scale 扩容），**绿勾待 push 到 GitHub 后生效**——这是阶段 13 的遗留项。

## 5. 为什么这么设计（设计要点）

### 5.1 可移植性：`-DENABLE_NATIVE_MARCH=OFF`

编译默认带 `-march=native`（用当前 CPU 的全部指令集优化）。但镜像可能在 A 机器构建、B 机器运行（如 CI 服务器构建 → 服务器运行），两个 CPU 不同就可能跑不起来。关掉后镜像任何机器都能跑，代价是少量性能损失。

### 5.2 启动顺序：healthcheck + depends_on

```yaml
depends_on:
  mysql: { condition: service_healthy }
```

没有它的问题：服务启动早于 MySQL 就绪 → 连库失败直接退出，而容器重启策略可能造成反复崩溃。有了健康检查，**只有中间件确认能提供服务了，依赖它的服务才开始启动**。ZK 的健康检查还有个坑：`CMD-SHELL` 默认走 dash（不支持 /dev/tcp 探测），要显式 `bash -c`。

### 5.3 双轨配置：docker/conf/ 与本地 conf/ 分离

容器内网络环境不同（host 用 compose 服务名、IP 用 0.0.0.0），配置文件单独一份（`docker/conf/`），本地开发不受影响。

### 5.4 CI 的 job 为什么这么编排

- **artifact 复用二进制**：integration/benchmark 不再重新编译，省时间
- **integration 失败时 dump 日志**：`if: failure()`——排查问题不需要重新跑一遍
- **integration 用 `down -v` 收尾**：每次 CI 都是干净环境，不留脏数据（可复现性）

## 6. 真实环境踩坑（面试故事素材）

容器化实测暴露的 6 个问题，每个都是一句话能讲完的面试素材：

| # | 问题 | 一句话讲法 |
|---|------|-----------|
| 1 | 22.04 的 protobuf 3.12 编译不了仓库提交的 3.21 生成码 | 基础镜像必须与开发环境 protobuf 版本一致，22.04→24.04 |
| 2 | `rpcserverip=0.0.0.0` 时服务注册了错误地址 | 新增 `GetLocalIp()`，ZK 注册/Worker 上报自动换容器实际 IP |
| 3 | `--scale` 扩容后 worker_id 冲突 | `ResolveWorkerId()`：环境变量 > 配置 > hostname |
| 4 | ZK healthcheck 走 dash 不支持 /dev/tcp | 显式 `bash -c` |
| 5 | 宿主端口被本机手工部署占用 | compose 改用替代端口 21810/23306/19001 等（容器内不变） |
| 6 | worker 配置漏改 `worker_id` 加载逻辑 | docker 启动崩溃循环，启动校验同步改造 |

## 7. 如何体现（面试怎么讲）

**定位一句话**："容器化与 CI/CD 部分我用 Claude 实现，我负责部署目标、验证方案与验收。"

**讲三条主线（全部使用者视角）**：

1. **目的**：手工部署 9 个进程太痛苦（版本/端口/启动顺序）→ 一条命令拉起；改代码后验证太费时 → 自动化流水线
2. **做了什么**：多阶段构建的单镜像 + compose 编排（healthcheck 依赖顺序、数据卷、scale 扩容）+ CI 4 个 job——重点讲 **integration 是"唯一的真实验证点"**：真实构建镜像、真实提交视频、真实转码、校验产物
3. **验收**：9 容器一键启动实测、集成测试 PASS、`--scale transcode_worker=3` 扩容实测、每个 Worker 唯一 worker_id

**避雷**：
- 不背 Dockerfile/YAML 细节，被追问就说"实现由 Claude 生成，我关注部署目标与验收"
- 被追问"你怎么保证 Claude 实现得对"：答本机实测——compose 全启动、集成测试跑通、扩容验证
- 被追问"这有什么难的"：讲第 6 节的真实问题（尤其 #2 容器环境 IP 问题——那类问题只有真正部署过才踩得到）

**面试中的定位**：网络库/RPC 是"深度自研"信号，容器化与 CI/CD 是"工程化交付"信号——两者结合回答面试官最爱问的"你这个项目怎么保证质量、怎么交付"。
