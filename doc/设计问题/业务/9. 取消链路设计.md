# 取消链路设计（CancelJob 全链路）

> 文档日期：2026-08-07
> 关联代码：`job_service.cpp`、`scheduler_service.cpp`、`transcode_worker.cpp`、`ffmpeg_executor.cpp`、`result_collector.cpp`
> 关联机制：`doc/视频转码平台/06_防并发覆盖机制设计.md`（本链路的状态保证依赖 UpdateIfStatus）
> 关联日志：阶段 8 #12/#13/#19/#20（`doc/更新业务日志/8. 阶段8代码审查与Bug修复.md`）

## 1. 概述

取消任务 = 让一个已提交的任务**不再产出、不再被调度、并尽快停掉正在执行的转码**。

链路跨 4 个服务、5 个环节：

```text
用户 / GUI ──CancelJob──► JobService
   │ ① 状态标记（强保证）      │   job → CANCELED（CAS）
   │                           │   非终态 shard → CANCELED（CAS）
   │                           ▼
   │            ② CancelJobShards RPC（best-effort，5s 超时）
   │                           ▼
   │                        Scheduler
   │                           │ ③ 本地非终态 shard → CANCELED（CAS）
   │                           │ ④ ListWorkers 查 ip:port → 逐个直连 Worker
   │                           ▼
   │             ⑤ CancelShard RPC（best-effort，3s 超时/个）
   │                           ▼
   │                        TranscodeWorker
   │                           │ 置 cancelled 原子标志（不直接杀进程）
   │                           │ 执行线程检测标志 → SIGTERM → 5s → SIGKILL
   │                           ▼
   │                        ffmpeg 子进程终止
   └──── 取消操作本身无论传播成败都返回成功
```

**核心设计哲学：取消分「状态保证」和「执行保证」两层，前者强保证、后者尽力而为。** 取消的**语义**（任务不再产出、不再被调度、终态不可逆）由状态层通过 MySQL 条件更新强保证；取消的**即时性**（正在跑的转码尽快停下）依赖 RPC 通知 + 进程信号，只能尽力而为。

## 2. 取消的三层保证

### 第一层：状态保证（强保证）

取消操作一旦发出，以下状态变化**必然**落库（只要 MySQL 可用，单条原子 UPDATE，无网络依赖）：

1. `job.status → JOB_CANCELED`（CANCELED=8，枚举最大值）
2. 该 job 所有**非终态** shard → `SHARD_CANCELED`

这两步的强保证来自 `UpdateIfStatus` 的 CAS 语义（详见 06 文档）。而状态一旦落库，**系统所有后续路径都会尊重它**——这是「任务被保证取消」的根基：

| 路径 | 守卫点 | 效果 |
|------|--------|------|
| 分配循环 | `TryAssignShard` 前 `MarkShardCanceledIfJobTerminal`（scheduler:893） | 已取消 job 的残留 WAITING shard 直接 CANCELED，不分配 |
| 超时重扫 | ASSIGNED 超时 / RUNNING 超时先查 job 终态（scheduler:1279 / 1480） | 终态残留 shard 直接 CANCELED，不重置 WAITING |
| Worker 离线 | `NotifyWorkerOffline` 查 job 终态（scheduler:487） | 终态任务残留执行不重调度 |
| 失败重排 | `RescheduleShard` 终态守卫（scheduler:348，#4 修复） | 已取消 shard 不复活为 WAITING |
| PENDING 兜底 | `PendingScanLoop` 仅当仍 PENDING 才推进（CAS） | 未切分就被取消的 job 不会被重新切分 |
| 终态判定 | `MarkJobTerminal` 状态单调性检查 `status > job.status`（RC） | job 已是 CANCELED(8) 后，SUCCESS(6)/FAILED(7) 无法覆盖——**取消不可逆** |

### 第二层：调度保证（CAS 双保险）

取消与正常调度并发竞争时，靠条件更新**先到者赢**，后到者的旧快照被静默拒绝：

- CancelJob 的 job 标记与 RC 的 SUCCESS/FAILED 推进互踩时，只有一条生效
- Worker 侧 `CancelShard` 带 `attempt_id` 精确匹配（transcode_worker:214，#1 修复）：shard 已被重新分配为新 attempt 时，旧 attempt 的取消通知**拒绝执行**，不误伤新执行

### 第三层：执行保证（best-effort）

正在执行的转码**尽力**停下（详见第 3 节），不可保证点与兜底见第 4 节。

## 3. 链路各环节详解

### 3.1 入口：JobService::CancelJob（job_service.cpp:273）

```text
① Get(job_id) 不存在 → 返回错误
② CAS：job → CANCELED（from_status 快照 + UpdateIfStatus）
③ 遍历 shard：非终态（非 SUCCESS/FAILED/CANCELED）逐个 CAS → CANCELED
   └ 已终态 shard 跳过——防止破坏 RC 的终态判定
④ CancelJobShards RPC 委托 Scheduler（5s 超时）
   └ 无论成败都只打日志，不影响返回值
⑤ 返回 error_code=0
```

要点：

- **状态先行**：①② 全部是本地 SQL，不依赖任何跨进程 RPC。即使 ④ 完全失败，取消的状态语义也已成立——② 的 shard 标记是整条链路唯一「不依赖网络」的取消屏障（Scheduler 不可达时靠它兜住，详见 3.2）
- **③ 覆盖未切分任务**：shard 列表为空时无事可做——job 的 CANCELED 状态本身就是保证（PendingScanLoop 的 CAS 会拒绝复活）
- **④ 是唯一跨进程调用，且刻意设计为 best-effort**：日志中明确写「workers not notified (best-effort)」。取消操作对用户的语义是「我发起了取消」而不是「我确认停掉了所有 Worker」——后者在分布式系统里无法同步保证

### 3.2 中间层：SchedulerService::CancelJobShards（scheduler_service.cpp:546）

```text
① 列出该 job 所有 shard
② 收集有 assigned_worker_id 且非 SUCCESS/FAILED 的 shard（含 CANCELED）
   └ 2026-08-07 修复：按 worker 指派收集而非按状态——JobService 标记
     CANCELED 时保留了 assigned_worker_id/attempt_id，此时快照里已无
     RUNNING/ASSIGNED，按状态收集恒为空、Worker 收不到取消
   └ SUCCESS/FAILED 执行已结束，通知纯浪费，排除
③ ListWorkers RPC（3s 超时）→ worker_id → ip:port 映射
   └ 失败 → 跳过全部通知，返回计数
④ 逐个直连 Worker 发 CancelShard（带 attempt_id，3s 超时，失败累计 skipped）
   └ attempt 精确匹配：已重新分配的新 attempt 被 Worker 拒绝，防误伤新执行
⑤ 返回 total / notified / skipped（可观测）
```

**为什么这里不再标记 shard？**

- **2026-08-07 删除冗余标记**：CancelJobShards 原有一个「本地非终态 shard 全部标 CANCELED」的步骤（阶段 8 #13 修复引入，当时各进程内存 Store 隔离，Scheduler 必须自己标）。阶段 9 MySQL 化后，该步骤与 JobService::CancelJob 的标记写的是**同一张表、同一批行**，且 CancelJob 同步执行完标记后才发本 RPC——正常路径下本步骤遍历到的全是已标记的 CANCELED/SUCCESS/FAILED，纯空转。保留价值只剩「JobService 标记失败（MySQL 瞬时故障）时补漏」，概率极低，故删除，由 JobService 标记 + 全系统终态守卫兜底
- **先标本地再通知的顺序依赖不再存在**：原注释「先标记本地，再通知 Worker（顺序不可反）」针对的是内存版（Worker 取消结果上报到 RC 不经过 Scheduler Store，必须先改自己视图）；现在共享 MySQL，JobService 已把非终态 shard 标 CANCELED，Scheduler 侧无需重复
- **勿删 JobService 侧标记**：关键事实——RC 的 `HandleReportShardResult` CAS 只检查 **shard 前置状态**，**不检查 job 是否已终态**。因此「取消后 shard 不推进到 SUCCESS」的唯一屏障就是 **shard 已被标 CANCELED 本身**。JobService 侧标记是唯一**不依赖任何 RPC** 的屏障：CancelJobShards RPC 失败（Scheduler 不可达/网络分区）时，它保证取消仍然立即生效
  - 若删掉 JobService 侧标记，最坏情况：Scheduler 不可达 → shard 保持 RUNNING → Worker 正常上报 → CAS `{RUNNING}→SUCCESS` 成功 → `CheckJobDone` 判定 SUCCESS → `MarkJobTerminal(SUCCESS)` 的单调性检查拒绝覆盖 job（job 保持 CANCELED）→ **但 merge 块在单调性判断之外照样执行，产出合并成品**——取消任务产出成品，违反第 4.5 节的代价边界
- **2026-08-07 修复（通知收集按 worker 指派）**：原收集条件「状态 ∈ {RUNNING, ASSIGNED}」基于①的 ListByJob 快照，而快照到达时非终态 shard 已被 JobService 标 CANCELED——**正常路径下收集恒为空，用户取消时 Worker 实际收不到 CancelShard 通知，ffmpeg 必然跑完**（结果上报被 RC 拒绝丢弃）。修复：① 收集条件改为「`assigned_worker_id` 非空且非 SUCCESS/FAILED」——JobService 标记只改 status、保留 worker 指派与 attempt_id，CANCELED shard 仍能命中正在执行的 Worker（SUCCESS/FAILED 执行已结束，通知纯浪费，排除）；② 通知带上 attempt_id——shard 已被重新分配为新 attempt 时 Worker 拒绝取消，防旧通知误伤新执行（与超时重扫的通知模式一致）。Worker 侧对已结束执行返回「shard not found」幂等无害

### 3.3 执行层：TranscodeWorker::CancelShard（transcode_worker.cpp:198）

```text
① mutex 保护下查 running_shards_ map
② 请求带 attempt_id 时精确匹配当前执行 attempt
   └ 不匹配 → 拒绝（"shard moved to new attempt, cancel ignored"）
③ 命中 → 置 it->second->cancelled = true（原子标志）
④ 响应 canceled=true
```

**为什么只置标志、不直接杀进程？**

- **线程安全**：ffmpeg 子进程由执行线程创建并 `waitpid` 回收，跨线程直接 `kill` 会与执行线程的 waitpid/资源清理产生竞态（执行线程可能正持有该 PID 做回收）
- **优雅退出**：ffmpeg 写文件中途被 SIGKILL 会留下损坏的中间产物；SIGTERM 让 ffmpeg 自行收尾
- **解耦**：取消请求是 RPC 线程处理的，执行是独立线程——标志位是最小同步面

### 3.4 执行终止：FfmpegExecute + ExecuteCommand（ffmpeg_executor.cpp:175-275）

执行线程通过 `cancel_cb` 检测标志，检测点有两个（保证响应及时）：

```text
转码主循环
  ├─ poll 超时（无输出）→ 检查 cancel_cb → kill(SIGTERM)
  ├─ 每行进度输出 → ParseProgress → 检查 cancel_cb → kill(SIGTERM)  ← 快速响应
  └─ 总时长 ≥ 1h → kill(SIGKILL)（kMaxExecMs 看门狗，防永久阻塞）

cancel 路径：SIGTERM → WNOHANG 等待 10×500ms → 未退 → SIGKILL
```

转码返回后 `FfmpegExecute` 再检查一次 `cancelled`：已取消则 `CleanupShard` 并**直接返回、不上报结果**——从源头避免「被取消的 shard 报 SUCCESS」污染终态（阶段 8 #19 修复：截图期间/重试睡眠期间到达的 cancel 曾被忽略，现在执行完成后仍检查）。

### 3.5 收敛：ResultCollector

Worker 被取消后不上报，那 job 最终状态如何确定？**不需要确定——job 已经被 CancelJob 置为 CANCELED**。RC 侧是纯防御：

- 若取消通知丢失（Worker 不可达），Worker 转码完成后上报结果 → `HandleReportShardResult` 的 CAS（`{from_status}`）发现 shard 已是 CANCELED → **结果被拒绝**，不覆盖
- `CheckJobDone` 把 CANCELED 计入失败集；即使它判定 JOB_FAILED 并调 `MarkJobTerminal`，单调性检查 `CANCELED(8) > FAILED(7)` 拒绝 → **job 保持 CANCELED**
- 各兜底循环（SchedulingLoop 5s/15s、TerminalSweepLoop 15s）周期重扫，最终收敛

## 4. 为什么是 best-effort？——不可保证点与兜底

「best-effort」限定的是**执行层的 RPC 通知**（3.1 的 ④ 和 3.2 的 ⑤），**不是状态层**。逐不可保证点分析：

### 4.1 Scheduler 不可达（CancelJobShards RPC 失败）

- **后果**：Worker 收不到取消通知，继续转码到完成
- **兜底**：① job/shard 已在 JobService 本地标 CANCELED（①②不依赖网络）；② Worker 上报结果被 RC 的 CAS 拒绝；③ 分配循环/超时重扫/离线通知的终态守卫不复活；④ job 保持 CANCELED（单调性）
- **净效果**：取消语义成立，**只是浪费了计算资源**——这正是「尽力」的代价上限

### 4.2 Worker 不可达（CancelShard RPC 失败 / Worker 崩溃）

- **后果**：正在执行的转码停不下来
- **兜底**：
  - Worker 崩溃 → `NotifyWorkerOffline` → job 终态检查 → 残留 shard 直接 CANCELED，不重调度
  - Worker 活着但网络分区 → 转码完成上报 → 结果被 RC 拒绝；或超时重扫（ASSIGNED 30s+观察窗 / RUNNING 5min）→ 终态检查 → CANCELED
  - 转码中途崩溃 → ffmpeg 进程退出 → 无上报 → 超时重扫收敛

### 4.3 通知到达但进程不退（SIGTERM 后卡死）

- **兜底**：5s 宽限后 SIGKILL；再不行还有 kMaxExecMs 看门狗（1h SIGKILL）
- 注意：这是单进程内可强保证的路径（信号 + 等待 + 强杀），真正的「尽力」只在跨进程 RPC 环节

### 4.4 attempt 竞态（取消通知撞上重新分配）

- **场景**：shard 超时被重置 WAITING 重新分配后，旧 Worker 才收到取消通知
- **兜底**：Worker 侧 attempt_id 精确匹配 → 拒绝取消，新 attempt 不受影响；新 attempt 分配本身又被 job 终态守卫拦截（job 已 CANCELED 则不会再分配）

### 4.5 为什么可以接受 best-effort？

分布式系统中「让远端进程停下」无法原子保证（网络分区无解）。本设计把代价边界画得很清楚：

> **best-effort 的最坏情况 = 已经启动的转码跑完，产出被丢弃。** 永远不会出现：取消后任务继续被调度、被重试、被合并产出成品、或被显示为非取消状态。

状态层保证（第 2 节）圈住了所有不可接受的后果，执行层尽力缩短资源浪费的持续时间。

## 5. 竞态窗口分析（取消 vs 并发操作）

| 并发方 | 竞争行 | 谁赢 | 机制 |
|--------|--------|------|------|
| RC 推进 SUCCESS vs CancelJob | job 行 | 先到者赢；cancel 先到 → RC 单调性拒绝；SUCCESS 先到 → cancel CAS 失败，job 保持 SUCCESS | 单调性 + CAS |
| RC 落定 shard 结果 vs CancelJob 标 shard | shard 行 | cancel 先 → 结果 CAS 失败被忽略 | CAS |
| RescheduleShard 复活 vs CancelJob | shard 行 | cancel 先 → 终态守卫拒绝复活（#4） | 终态守卫 |
| 分配循环分配 vs CancelJob | shard 行 | cancel 先 → 分配前终态检查拦截 | 终态守卫 |
| Worker 完成上报 vs cancel 标志 | 进程内 | cancel 先 → 不上报；上报先 → 结果被 CAS 拒绝 | 标志 + CAS |
| 超时重扫重置 WAITING vs CancelJob | shard 行 | cancel 先 → 重扫终态检查直接 CANCELED | 终态守卫 |

**一致性结论**：job=SUCCESS ⇒ 所有 shard 必已 SUCCESS（CheckJobDone 判定前提）⇒ CancelJob 的 shard 遍历全部跳过，不会产生「SUCCESS job 带 CANCELED shard」的矛盾状态。

**取消不可逆**：CANCELED=8 是枚举最大值，`MarkJobTerminal` 只接受单调推进，job 一旦 CANCELED 永不再变。唯一的例外是取消本身（CANCELED 就是最终态，无后续状态）。

## 7. 局限与遗留

1. **通知是串行的**（阶段 8 #23，PLAUSIBLE 级）：CancelJobShards 逐个 Worker 同步 3s 超时，已分配 shard 多时取消延迟累计；可改并行 + 超时聚合，低优先级
2. **取消不回收已分配的 Worker 槽位**：被取消但仍在转码的 shard 会占着 Worker 的 running 槽直到执行结束（或超时重扫）——slot 释放依赖执行终止，同样受 best-effort 约束
3. **通知失败无重试**：CancelJobShards 失败不重试（靠兜底循环收敛）；若要更积极的即时取消，可给「通知失败但 shard 仍非终态」的场景加重试
4. **GUI 侧无二次确认/取消结果展示**：取消操作返回成功即关窗，notified/skipped 计数只进日志（阶段 12 可加交互）
