# 5. SchedulingLoop 超时重扫设计（卡死检测与恢复）（文档 5）

> 对应 `SchedulingLoop` 中的 `-- 0. 阶段 8：RUNNING/ASSIGNED 超时重扫（每 30 秒，按时间）--` 段
> （`scheduler_service.cpp:1361-1678`）。
> 它是调度可靠性的三大兜底之一，与 NotifyWorkerOffline（心跳超时）和启动恢复（进程崩溃）互补。

## 1. 设计背景：为什么需要超时重扫

**故障形态**：Worker 接受 shard 后**卡死**——ffmpeg 进程挂起、不产出不退出，但 Worker 进程本身活着、心跳照发（`/proc` 采集正常）。这种"活着但没干活"的假死：

- **心跳检测救不了**：`NotifyWorkerOffline` 只在心跳超时（Worker 彻底失联）时触发，卡死的 Worker 心跳正常 → 永远不会触发
- **结果上报救不了**：卡死的 ffmpeg 永远不产生结果，RC 等不到结果
- **后果**：shard 永久停留在 ASSIGNED/RUNNING，任务永远卡在"等待中"——**没有超时重扫，卡死就是永久的**

**三个兜底的分工**：

| 兜底机制 | 触发条件 | 对付的故障 |
|----------|----------|-----------|
| `NotifyWorkerOffline` | 心跳超时（Worker 失联） | Worker 进程挂掉/网络断 |
| **超时重扫（本文）** | shard 状态超时（30s/5min） | **Worker 活着但任务卡死** |
| 启动恢复 | Scheduler 进程重启 | Scheduler 自身崩溃 |

## 2. 触发与节奏

### 2.1 按时间 30s，不按轮次

```cpp
int64_t now_ms = NowMs();
if (now_ms - last_rescan_ms >= kTimeoutRescanIntervalMs)   // 30000ms
{
    last_rescan_ms = now_ms;
    ...
```

为什么按时间（`last_rescan_ms`）而不是"每 15 轮"：`SchedulingLoop` 的 interval 随 MQ 状态在 **2s↔5s 间动态变化**（阶段 10 共存改造），按轮次会导致重扫周期漂移（15×5s=75s）——按时间保证重扫频率恒定。

### 2.2 两个不同的超时阈值

| 状态 | 阈值 | 理由 |
|------|------|------|
| ASSIGNED | **30s** | 分配了却迟迟不开始转码，可疑性高，需要快点查 |
| RUNNING | **5min** | 正常转码可能持续很久（长视频/慢机器），不能误杀 |

### 2.3 先建 Worker 地址表

重扫命中后需要**直连原 Worker**（QueryShard 确认 / CancelShard 通知），所以先调 `ListWorkers` 构建 `worker_id → (ip, port)` 映射（`:1376-1405`）。ListWorkers 失败 → 地址表为空 → 各 shard 命中"查不到 Worker 地址"分支全部保守跳过本轮——**宁可这轮不处理，也不在不知道地址时乱动**。

## 3. ASSIGNED 超时（30s）：先问后判

### 3.1 核心原则：超时 ≠ 卡死

ASSIGNED 超时只是"30s 无信号"，而**正常执行的 Worker 从不向 Scheduler 报进度**（进度只发 ResultCollector）——慢视频 30s 没动静完全正常。所以 `#1 修复` 的语义修正：**不能无条件重置，必须先直连原 Worker QueryShard 确认执行状态**（`:1426` 起）。

### 3.2 流程

```
ASSIGNED 超时命中
  ├─ 状态复核（重新 Get，仍为 ASSIGNED？不是 → 跳过）
  ├─ 终态守卫（job 已终态？→ shard 标 CANCELED，#17）
  └─ 直连原 Worker QueryShard 问进度 → 四种结果（见下表）
```

### 3.3 QueryShard 四种结果的处置

| 结果 | 含义 | 处置 |
|------|------|------|
| `progress = -1` | Worker 已不持有该 shard（执行完已清理） | **不重置**——结果已上报/在途，重置会导致双份执行；清掉观察记录，等结果 |
| `progress` 前进（比上次大 / 首次观察） | 正常在干活 | **不重置**——刷新观察窗（stall=0）+ **刷新 updated_at 续期超时窗**，下轮不命中 |
| `progress` 停滞（与上次相同） | 可疑 | stall_rounds+1；**连续 2 轮停滞（~60s）→ 判定卡死** |
| QueryShard RPC 失败 | Worker 活着但 RPC 停摆（work 线程卡死） | 与停滞同语义，连续 2 轮无法确认 → 判定卡死（防"心跳正常但服务死"永久跳过） |

### 3.4 progress_watch_ 记账本

```cpp
struct ProgressWatch {
    int progress = -1;      // 上次观察到的进度百分比
    int stall_rounds = 0;   // 连续停滞轮数
};
std::unordered_map<std::string, ProgressWatch> progress_watch_;  // shard_id → 观察记录
```

**为什么需要它**：重扫每 30s 一轮，是"无记忆"的。没有记账本就无法区分"刚停"和"停了 1 分钟"。`progress` 记住上次的进度值（判断有没有前进），`stall_rounds` 记住停了几轮（判断够不够判死）。

**为什么 2 轮才判死**：转码中途有短暂停顿很正常（初始化、写文件收尾），1 次停滞就判死会**误杀慢任务**；连续 2 轮（约 60s）无进展才可信。代价是卡死检测最长延迟 ~90s（30s 超时 + 2×30s 观察），这是"不误杀"换来的保守。

**为什么 progress=100 也在检测范围**：100% 只代表"转码完成"，ffmpeg 可能**在收尾阶段挂起**（pipe 不 EOF、结果不上报）——这种形态的卡死同样要兜底，不能因为 100 就放行。

**清理**：每轮重扫开头先清掉已离开 ASSIGNED/RUNNING 的条目（`:1357-1372`），防止 shard 终态后记账本泄漏。

## 4. 判定卡死后的重置流程（ASSIGNED）

```
判定卡死（停滞 2 轮 / RPC 失败 2 轮）
  ├─ 1. 通知原 Worker CancelShard（reason=TIMEOUT）  ← best-effort
  │       带 attempt_id 精确匹配：防误伤并发的新 attempt
  │      （重扫与分配循环是不同线程，shard 可能已被重新分配）
  ├─ 2. 清掉 progress_watch_ 条目
  ├─ 3. 判断重试预算：
  │       retry_count >= max_retry → 终态 SHARD_CANCELED（不再分配）
  │       else → retry_count++ → 状态 WAITING + 清 assigned_worker_id/attempt_id
  │                → 条件更新（expect ASSIGNED）→ NotifyShardWaiting 立即重分配
  └─ 4. 计数 + 日志（timed_out 汇总）
```

**CancelShard 的用意**（`:1517-1522` 注释）：旧 ffmpeg 被 kill——不浪费资源、**不留迟到结果**。cancel 失败只 WARN（best-effort），因为即使旧 Worker 继续执行完，它的结果也会被 RC 的 attempt 校验拒绝（见下）。

**为什么重置要 `retry_count++`**：retry_count 推进 → 下次分配的 attempt_id 不同（`shard_id_attempt_{retry_count}`）→ **旧 Worker 的迟到结果带着旧 attempt_id，被 RC 的 attempt 校验正确拒绝**——"新执行"与"旧执行"的身份由此区分，防旧结果污染新执行。

**为什么预算耗尽标 CANCELED 而非 FAILED**：这里是"卡死取消"（系统放弃），不是"转码失败"（业务失败）——SHARD_CANCELED 语义更准确；job 的终态由 RC 按 shard 集合判定。

## 5. RUNNING 超时（5min）：不问了，直接判

```cpp
// ── #1 修复：重置语义修正（与 ASSIGNED 分支对齐）──
// RUNNING 5 分钟超时本身已是很强的卡死信号（远超正常转码时长），
// 无需 QueryShard 确认，直接：通知原 Worker 取消 + retry 语义修正。
```

与 ASSIGNED 分支的差异就在**跳过 QueryShard 确认**——5 分钟不动远超任何正常转码节奏，再问就是浪费时间。其余流程完全对齐：终态守卫 → CancelShard 通知（地址表查找）→ 预算判断（耗尽 → CANCELED / 否则 retry++ → WAITING → NotifyShardWaiting）。

## 6. 与其他机制的分工与配合

| 机制 | 关系 |
|------|------|
| `NotifyWorkerOffline` | 互补：心跳超时管"人没了"，重扫管"人活着但没干活" |
| 启动恢复 | 互补：Scheduler 重启时扫残留，一次性的；重扫是周期性的 |
| `TryAssignShard` 三重防护 | 重扫重置为 WAITING 后与分配循环并发，靠状态复核 + SETNX + 条件更新保证只有一方推进 |
| RC 的 attempt_id 校验 | 重扫取消旧执行 + 新 attempt 推进，迟到结果被 RC 拒收 |
| `NotifyShardWaiting` | 阶段 10 起，重置为 WAITING 即发 MQ 事件立即重分配（不等下轮轮询） |
| 条件更新（expect ASSIGNED/RUNNING） | 重扫与并发推进之间的防覆盖（`.UpdateIfStatus`） |
