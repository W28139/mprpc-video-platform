# 调度模式演进设计：Pull 轮询 → MQ 推送（文档 3）

> 对应 `scheduler_service.cpp:326-334` 注释："替代'等 SchedulingLoop 轮询'（平均 1s 延迟 → <100ms）"。
> 阶段 10 第二批（2026-08-03）核心架构变更，详见业务日志《11. 阶段10中间件集成.md》。

## 1. 之前怎么设计：Pull 轮询（阶段 9 及之前）

### 1.1 机制

调度完全由一个后台线程驱动——`SchedulingLoop` 定时**主动拉取**可分配任务：

```
SchedulingLoop 线程（固定 2s 一轮）
    │
    ├─ 1. 扫描 ShardStore 全部 WAITING 状态的 shard（全表扫描）
    ├─ 2. 对每个 WAITING shard：加权打分选 Worker（阶段 7 起）
    ├─ 3. 直连 Worker 调 AssignShard RPC → 推进 ASSIGNED
    └─ 4. 循环往复（每轮还夹杂超时重扫/启动恢复等可靠性职责）
```

关键特征：

- **周期驱动**：所有新任务的分配都要"等到下一个 2s 周期点"
- **延迟的数学期望**：shard 在任何时刻就绪，被分配的最坏等待 = 1 个完整周期 2s，**平均等待 ≈ 1s**（2s 周期的中点）
- **批量扫描**：每轮全量扫 WAITING 表，任务多时一次处理一批（吞吐 OK，但单任务延迟被周期钳制）
- **职责混叠**：同一个循环既做"分配"（性能敏感）又做"可靠性"（超时重扫每 15 轮、启动恢复、卡死检测），两者耦合在一个轮次里

### 1.2 当时的形态

分配逻辑直接内联在 `SchedulingLoop` 循环体内（约 150 行），只有一个调用方；代码位置 `scheduler_service.cpp:859` 附近（阶段 10 前）。

## 2. 现在怎么设计：MQ Push 调度（阶段 10 第二批）

### 2.1 事件拓扑

```
发布端（Scheduler 内部 4 个触发点）
    │  NotifyShardWaiting(shard_id)
    ▼
Exchange job.events（direct, durable）──► Queue shard.waiting（durable）
                                                │  delivery-mode=2（持久化消息）
                                                ▼
                                    MqConsumeLoop（独立消费线程）
                                                │  收到消息 → 立即分配
                                                ▼
                                       TryAssignShard（与轮询共用）
```

**核心转变**：从"周期性扫描谁有活"变成"有活时主动喊一声"——shard 就绪的**时刻**被事件直接触发，不再等待周期点。

### 2.2 两个通道的职责区分

| 通道 | 类型 | 消息体 | 消费端如何取数据 |
|------|------|--------|------------------|
| `shard.waiting` | **通知通道** | 只有 `shard_id` | 收到后**重新查 MySQL** 拿最新状态 |
| `result.pending` | **数据通道** | 序列化的 `ReportShardResultRequest` | 执行结果（is_success/exit_code/output_path/screenshot_path）**不在 MySQL 中**，必须随消息传递 |

设计要点（日志 11 Q&A）：`shard.waiting` 只是"有活可干"的信号，消费端查库而非信任消息快照——因为 **MySQL 是唯一数据源**，消息携带快照反而有陈旧风险（shard 可能已被其他路径分配），且查库才能做幂等判断。与阶段 9"不构造本地副本"的原则一致。

### 2.3 发布端：4 个触发点

`NotifyShardWaiting(shard_id)` helper（`scheduler_service.cpp:124-133`，发布失败只 WARN，由轮询兜底；实际 AMQP 发送在 `MqClient::PublishShardWaiting`）：

| 调用点 | 触发时机 |
|--------|----------|
| `ScheduleJob` | 切分新建 shard 后（每个 shard 一条消息） |
| `RescheduleShard` | 重试重置 WAITING 后 |
| `NotifyWorkerOffline` | Worker 离线批量重置 WAITING 后 |
| SchedulingLoop 启动恢复 + 超时重扫 | 残留/超时 shard 重置 WAITING 后 |

**原则**：任何 shard 状态变为 WAITING 的路径都必须发布——保证 Push 模式下所有"活"都有事件触发。

### 2.4 消费端：MqConsumeLoop

独立线程（`:1839-1920`），流程：

```
connected() 检查 → 连接故障则 Reconnect()（2s 重试）
→ ConsumeBlocking("shard.waiting", 2s 超时)
→ 查 MySQL 幂等判断：
     shard 不存在 → ack & drop（陈旧消息）
     状态非 WAITING → 幂等跳过（重复投递/已被轮询分配）
→ LoadOnlineWorkers + TryAssignShard → 分配
→ 无条件 ACK（处理完成即确认）
```

## 3. 用到了什么方法

### 3.1 TryAssignShard：分配逻辑抽取为公共函数

原 SchedulingLoop 内联的 ~150 行分配循环体抽成文件级函数（`:988` 起）：**终态检查 → 状态复核 → 加权打分 → 分布式锁 → AssignShard → 推进 ASSIGNED → job RUNNING**。

意义：轮询（SchedulingLoop）与消息（MqConsumeLoop）**两个来源共用同一分配实现**，打分/锁/推进行为完全一致——否则两套逻辑迟早漂移出不同的调度行为。

### 3.2 MqClient 双连接双锁（含踩坑史）

rabbitmq-c 连接非线程安全。初版**单连接 + 单锁**：`ConsumeBlocking` 持锁阻塞等消息（最长 2s），导致 ScheduleJob 的 work 线程切分完调 `NotifyShardWaiting`（内部走 `MqClient::PublishShardWaiting`）要等同一把锁 → **RPC 处理超时**（实测 `recv response header error! errno:11`），任务无法提交。

修复：**发布（publish_conn_/publish_mutex_）与消费（consume_conn_/consume_mutex_）严格分连接分锁**——消费阻塞只等消费锁，发布持锁时间 = 单条 publish（微秒级）。拓扑声明由发布连接完成（幂等），消费连接只登录 + channel。

### 3.3 无条件 ACK 的语义设计

消息的"职责"是**触发一次检查**（该 shard 是否可分配），检查已做即完成职责。因此：

- 分配失败（无 worker/过载/锁占用）→ **不重回队列**，否则无限重投风暴；由 SchedulingLoop 兜底扫描再试（5s 内）
- 重复投递（Broker 重发）→ 消费侧幂等吸收：查 MySQL 非 WAITING 即跳过，配合 TryAssignShard 的**三重防护**（状态复核 + Redis 分布式锁 + MySQL 条件更新）
- ack 失败 → WARN，Broker 重投，幂等检查兜底

### 3.4 SchedulingLoop 共存改造：可靠性职责不丢

MQ 在线时 SchedulingLoop **降频到 5s 而不是停掉**（`:1333-1337`）——因为它还承担 Push 模式无法替代的职责：

| 职责 | 归属 | 说明 |
|------|------|------|
| 分配 | MQ（正常路径）/ 轮询（兜底） | Push 正常 <100ms，消息丢失/发布失败由 5s 兜底 |
| 超时重扫（ASSIGNED 30s / RUNNING 5min 卡死检测） | SchedulingLoop | 与 MQ 无关的可靠性 |
| 启动恢复（残留 ASSIGNED/RUNNING → WAITING） | SchedulingLoop | Scheduler 崩溃恢复 |
| progress_watch 卡死确认（QueryShard 二次确认） | SchedulingLoop | Worker 假死检测 |

配套改动：超时重扫由"每 15 轮"改为**按时间 30s**（`last_rescan_ms`，`:1366-1369`）——interval 随 MQ 状态在 2s↔5s 间变化，按轮次会导致重扫周期漂移（15×5s=75s）。

### 3.5 自动切换：无状态机、按次判断

MQ 状态由 `MqClient::connected()`（消费连接对象是否存在）**单点决定**：

- **掉线**：`ConsumeBlocking` 检测到连接故障 → 销毁消费连接 → 消费线程 2s 周期 `Reconnect()`；SchedulingLoop 每轮检查 `connected()==false` → 自动恢复 **2s 全量扫描**（降级为阶段 9 行为，任务仍可完成；Worker 结果上报同时回退直连 RPC）
- **恢复**：`Reconnect()` 成功 → 消费线程继续消费；SchedulingLoop 检测到 `connected()==true` → 自动降频 5s

与 Redis 降级同哲学：**没有切换状态机，每轮按当前事实决定自己的行为**，故障与恢复都是自然的（不依赖任何恢复事件传递）。

## 4. 前后对比

| 维度 | Pull 轮询（阶段 9） | MQ Push（阶段 10） |
|------|--------------------|--------------------|
| 触发方式 | 周期扫描（2s 固定） | 事件触发（即时） |
| 平均调度延迟 | ~1s（2s 周期中点） | **实测 33ms** |
| 最坏延迟 | 2s | 消息丢失时保底 5s（兜底扫描） |
| 分配逻辑 | 内联在循环体内 | 抽取为 TryAssignShard，双来源共用 |
| 可靠性职责 | 与分配耦合在同一循环 | 分配（Push）与可靠性（扫描）解耦 |
| 故障模式 | 无新故障面 | 新增故障面（消息丢失/发布失败）→ 由兜底扫描覆盖 |
| 结果通道 | 直连 RPC 上报 | `result.pending` 数据通道（MQ 优先，回退直连） |

## 5. 收益

1. **调度延迟量级下降**：平均 1s → 33ms（验收线 <100ms），高延迟敏感任务（用户提交 → 出结果的端到端时间）显著缩短
2. **可靠性不降级**：Push 引入的新故障面（发布失败、消息丢失）由 5s 兜底扫描 + 无条件 ACK 语义完整覆盖——最坏情况只是退回阶段 9 的延迟，不会丢任务
3. **职责分离**：分配（性能敏感，事件驱动）与可靠性（超时/恢复，周期驱动）解耦，各自可按需演进
4. **结果通道同步升级**：Worker → RC 的结果上报也走 MQ（`result.pending`），RC 消费复用与 RPC 完全相同的 `HandleReportShardResult`，聚合/重试/终态判定逻辑零改动
5. **故障自动切换无需人工介入**：MQ 掉线 → Pull 轮询接管（任务仍完成）→ 恢复 → 自动切回 Push，全程无状态机、按次判断

## 7. 演进中的修复（log 14 Bug 1，2026-08-04）

Push 模式上线后复验发现 MqClient 消费锁缺陷：`ConsumeBlocking` 锁内 poll(2s) + 消费线程紧循环 → `consume_mutex_` 几乎 100% 被占 → `connected()` try_lock_for(1s) 永远失败 → `consume lock busy` 刷屏 + `SchedulingLoop` 永远 `(mq=pull)`（Push 被误判为 Pull）。

修复：① poll 移出锁（消费连接只由消费线程销毁，poll 期间无并发写者）② `connected()` 改用 `std::atomic<bool> consume_alive_` 无锁读取 ③ 销毁分支持锁且先置标志。验证：`interval=5000ms (mq=push)` 首次正确识别、刷屏消失。

> 启示：Push 模式下"MQ 在线"的判断（connected()）本身是可靠性的新单点——它的误判代价是调度模式错误降级，因此必须是原子无锁的读取。
