# FFmpeg 执行器设计（FfmpegExecutor）

> 文档日期：2026-08-07
> 关联代码：`video_platform/src/transcode_worker/ffmpeg_executor.cpp`、`video_platform/include/video_platform/ffmpeg_executor.h`
> 关联日志：阶段 8 重构（修复 #4/#9/#13/#16/#20/#25/#27）

## 1. 概述：把 FFmpeg 当黑盒

FFmpeg 在本平台中**不是库、不是模块，而是一个被进程隔离的外部工具**。`FfmpegExecutor` 是它唯一的门面——全静态方法集合，每个方法 = 「输入视频 + 参数 → 产出」，内部细节（音视频编码、滤镜、参数拼接）对平台完全透明：

```text
平台代码 ──► FfmpegExecutor（唯一入口）──fork+exec──► ffmpeg/ffprobe 子进程
                  ▲ 静态方法，无状态，线程安全
                  │
       Worker（转码/截图）  Scheduler（探测时长）  ResultCollector（合并产物）
```

被三个服务复用、无实例化、天然线程安全——这是全静态设计的理由。

## 2. 为什么用子进程而非线程/库（接口视角的设计决策）

FFmpeg 也可以作为库（libav*）嵌入进程用线程调用。本平台刻意选择**子进程模式**，理由按重要性排序：

| 决策点 | 子进程（现状） | 线程 + 库嵌入 |
|--------|---------------|---------------|
| **崩溃隔离** | ffmpeg 崩了（损坏文件/编码器 bug）只牺牲本次转码，Worker 存活、上报 FAILED、系统自愈 | 整个 Worker 进程崩溃，所有在跑执行全挂 |
| **可强杀** | 信号可强杀（SIGTERM→SIGKILL），卡死也能终止 | 线程杀不死，只能等它检查标志 |
| **不可信输入** | 用户上传的视频是外部输入，风险隔离在子进程 | 与平台共享地址空间 |
| **资源回收** | 进程退出 OS 全回收（内存/文件句柄） | 泄漏累积 |
| **使用方式** | 拼命令行（ffmpeg 的标准用法，成熟生态） | 手动管理 AV 上下文，复杂度高一个量级 |

**一句话：子进程换来「它炸了不连累我、它卡了我能杀了它」——这是取消机制（第 6 节）和故障自愈的前提。**

## 3. 接口设计（黑盒方法表）

| 方法 | 黑盒语义 | 输入 → 产出 | 调用方 |
|------|---------|------------|--------|
| `Probe(input)` | 问"这个视频是什么" | 视频文件 → 时长/分辨率/编码信息 | Scheduler（切分前探测真实时长） |
| `Transcode(input, output, res, bitrate, start, dur, progress_cb, cancel_cb)` | "把这段视频转码成目标格式"（切片+转码一 pass） | 视频 + 区间 + 目标参数 → 转码产物 + 进度回调 | Worker（核心执行） |
| `Screenshot(input, ts, output)` | "截一帧图" | 视频 + 时间点 → 图片文件 | Worker（转码成功后截取中点帧，随结果上报） |
| `Merge(inputs, output)` | "把几段视频首尾相接" | 有序片段列表 → 完整视频 | ResultCollector（任务成功时合并产物） |
| `Slice(input, start, dur, output)` | "切一段出来" | 视频 + 区间 → 切片 | 预留（当前一 pass 方案未使用） |
| `CheckAvailable()` | "ffmpeg 装了吗" | 无 → 布尔 | Worker 启动检查（不可用则拒绝启动） |
| `ExecuteCommand(argv, progress_cb, should_cancel)` | 通用执行器（内部核心） | 命令行 + 回调 → 执行结果（成功/退出码/错误尾巴） | 以上所有方法的底座 |

所有方法返回统一结果结构（`FfmpegResult`：成功与否 + 退出码 + 错误信息尾部），调用方不关心 ffmpeg 内部。

## 4. 通用执行器 ExecuteCommand 的设计（核心）

所有方法最终都走同一个底座：**fork+exec+pipe 拉起子进程、管道读输出、poll 轮询、按事件响应**。

### 4.1 进程启动：fork+execvp 直接传 argv

```text
pipe() → fork()
  子进程：stdin 指向 /dev/null，stdout/stderr 都接管道 → execvp(argv) 直接执行
  父进程：关闭写端，poll + read 读子进程输出
```

- **不走 `/bin/sh -c` 拼接字符串**（阶段 8 #4）：输入路径等参数可能含特殊字符，shell 拼接存在命令注入面；execvp 传 argv 数组从根上消除
- **stdout/stderr 合一**：ffmpeg 的进度和错误都走管道，父进程统一处理

### 4.2 主循环：poll + read，按事件响应

```text
while (!killed) {
    poll(管道, 1s 超时)
      ├─ 有数据 → read → 逐行提取
      │     ├─ 解析进度行 → progress_cb(百分比)
      │     └─ 行尾检查 should_cancel() → 命中则 kill(SIGTERM)   ← 取消主检测点
      └─ 超时（子进程安静 1s）→ 检查 should_cancel()             ← 取消备检测点
      每轮检查总耗时 ≥ 1h → kill(SIGKILL)                        ← 看门狗
}
```

三个设计要点：

1. **poll 带超时而非阻塞读**（#9）：阻塞 fgets 会让"子进程卡死不输出"变成"父进程永久挂起"；带超时轮询让取消指令即时生效
2. **取消双检测点**：每行进度（ffmpeg ~0.5s 吐一行，取消延迟约 0.5s）+ poll 超时（子进程安静时），保证两种状态都能及时响应
3. **看门狗按实际耗时**（#16）：此前只在 poll 超时分支累加耗时，ffmpeg 持续吐输出时"卡死"的进程永远不被判定——改为 `steady_clock` 每轮实际计时，1 小时总时长上限，超时 SIGKILL，**保证执行器永不永久阻塞**

### 4.3 取消路径：优雅 → 强杀

```text
检测到 should_cancel → kill(pid, SIGTERM)
                     → waitpid 轮询 10×500ms（给 5 秒优雅退出）
                     → 未退 → kill(pid, SIGKILL) 兜底
```

SIGTERM 让 ffmpeg 自己收尾（写文件中途被杀会留损坏产物），5s 宽限后强杀保证一定能停下来。**这是第 2 节"可强杀"设计在实现层的落地。**

### 4.4 结果判定：三态区分

| 结束方式 | 判定 | 语义 |
|---------|------|------|
| 正常退出且退出码 0 | `success=true` | 任务完成 |
| 正常退出但退出码非 0 | `success=false`，带 stderr 尾部（512B） | ffmpeg 自己报错（如输入损坏、参数非法） |
| 被取消（should_cancel 触发） | 退出码正确获取（#20：防局部变量遮蔽） | 取消路径，调用方据此区分"取消"与"失败" |
| 被看门狗/超时杀死 | `success=false` | 异常终止，调用方按失败处理 |

### 4.5 专项超时：Probe 15s

Probe 是**同步调用**（Scheduler 切分前必须拿到时长），一旦 ffprobe 挂死（损坏文件/慢挂载点）会阻塞调用线程——Scheduler 里 2 个并发 Probe 就能占满线程池瘫痪平台（#13）。故 Probe 单独设 15s 总上限，超时 SIGKILL 并返回无效信息，调用方回退配置默认时长。

## 5. 平台集成数据流

### 5.1 Scheduler：切分前探测（Probe）

```text
ScheduleJob
  → Probe(input) 探测真实视频时长      ← 失败回退 job_duration_fallback_sec
  → 按时长切分 shard（最后一个 shard 时长自适应）
  → shard 记录写入 MySQL
```

### 5.2 Worker：执行 + 进度 + 取消（Transcode + Screenshot）

```text
AssignShard（分配到达）
  → 生成 attempt_id，插入 running_shards_（含原子取消标志）
  → 执行线程：Transcode(..., progress_cb, cancel_cb)
      ├─ progress_cb → 更新 running_shard->progress  ← Scheduler 可直连 QueryShard 查实时进度
      └─ cancel_cb   → 读取消标志 ← CancelShard RPC 置位
  → 转码返回：已取消 → CleanupShard + 不上报（阶段 8 #19：防被取消 shard 报 SUCCESS）
            正常     → Screenshot 截中点帧 → ReportShardResult（产物 + 截图路径）
```

### 5.3 ResultCollector：合并产物（Merge）

```text
MarkJobTerminal(JOB_SUCCESS)
  → 收集所有 shard 的 output_path → 按 shard_index 排序 → Merge() → 完整视频
  → merge 失败只打 WARN 不改变终态（MergeMutex + 原子标志保证恰好执行一次；
    TerminalSweepLoop 每 15s 重扫自动重试，磁盘/ffmpeg 恢复后收敛）
```

## 6. 可靠性与兜底

| 环节 | 机制 | 防什么 |
|------|------|--------|
| 启动检查 | `CheckAvailable`：executor_mode=ffmpeg 时 ffmpeg/ffprobe 不可用 → **拒绝启动**（fail-fast） | 环境缺依赖时静默失败难排查 |
| 命令注入 | fork+execvp 直接传 argv，不走 shell | 输入路径/参数含特殊字符 |
| 永久阻塞 | 1h 看门狗（执行）+ 15s 上限（探测） | 卡死进程拖垮调用方 |
| 取消卡死 | SIGTERM → 5s → SIGKILL | 取消后停不下来 |
| 输出洪水 | 错误信息只留尾部 512B | 日志内存膨胀 |
| 依赖缺失 | `executor_mode=mock` 保留 mock 执行器（sleep 模拟） | 无 ffmpeg 环境仍可跑通全链路 |

## 7. 设计要点总结

1. **黑盒封装**：FFmpeg 对平台是"外部工具"，接口是"输入视频 + 参数 → 产物"，细节不泄漏
2. **子进程模式**：崩溃隔离 + 可强杀 + 生态白嫖，是取消与自愈机制的前提
3. **单一底座**：所有方法共享 fork+exec+pipe 执行器，行为一致（进度/取消/超时/错误）只实现一遍
4. **事件驱动主循环**：poll 轮询 + 逐行响应，取消毫秒级生效、卡死可判定、永不永久阻塞
5. **三态结果**：成功 / 失败 / 取消明确区分，调用方按语义处理（取消不上报、失败可重试）
6. **双保险**：启动 fail-fast + mock 降级，环境缺失要么早暴露、要么可替代
