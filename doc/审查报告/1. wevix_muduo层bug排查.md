## 二、严重问题

### S1. SIGPIPE 无防护：服务端写路径可能被对端断开直接杀死整个服务进程

> **状态**：✅ 已修复（2026-08-11）——两处 `::send` 加 `MSG_NOSIGNAL` + `TcpServer` 构造 `signal(SIGPIPE, SIG_IGN)` 双保险，编译通过

- **位置**：`wevix_muduo/src/Connection.cpp:139`（handleWrite 的 `::send`）、`:234`（sendInLoop 的 `::send`）；库内无任何 `signal(SIGPIPE, SIG_IGN)`
- **问题**：`::send()` 未带 `MSG_NOSIGNAL`（对比 `mprpc/src/mprpcchannel.cc:152` 客户端侧正确使用了 MSG_NOSIGNAL）。**5 个生产服务 main（job_service/scheduler_service/worker_manager/transcode_worker/result_collector）与 `mprpc/src/mprpcapplication.cc` 均未忽略 SIGPIPE**（已逐一确认），忽略 SIGPIPE 的只有测试/工具 main。
- **触发场景**：客户端超时关闭/RST 后服务端继续写响应（如阶段 5"worker 被杀"场景：scheduler 向已死 worker 的 provider 连接写、或 worker 向已超时断开的 scheduler 写转码响应）→ `send` 返回 EPIPE → 内核发 SIGPIPE → **默认动作终止整个服务进程**。容器化部署中任一 peer 崩溃即可级联杀服务。
- **修复建议**：Connection 所有 `send` 加 `MSG_NOSIGNAL`，或库初始化时统一 `signal(SIGPIPE, SIG_IGN)`。

### S2. Connection::handleRead 编解码循环 UAF：用户回调内关闭本连接后循环继续访问已析构的 this

> **状态**：✅ 已修复（2026-08-11）——`handleRead` 入口持有 `ConnectionPtr self` 保活 + 每帧回调前后检查 `disconnected_` 及时退出，编译通过

- **位置**：`wevix_muduo/src/Connection.cpp:95-114`（无编解码器分支 `:119-124` 同样存在）
- **问题**：`while (messageCodec_(&inputBuffer_, message)) { onMessageCallback_(shared_from_this(), message); }` —— `shared_from_this()` 的临时引用在**回调返回后**才释放；若用户回调内同步触发本连接关闭并耗尽最后一个引用（如回调内调用 `conn->forceClose()`——在 loop 线程内联执行 handleClose，erase 掉 TcpServer `connections_` 与 subLoop `conns_` 两个 map 后引用归零 → Connection 及 channel_ 析构），while 循环的下一次条件判断访问的是**已释放的成员**。
- **触发场景**："响应即关"类 RPC 模式、或 onMessage 回调中调用 `forceClose()`（muduo 社区常见写法）。当前 mprpc 因 OnMessage 走 work pool + `RpcResponseContext` 持有 conn 而未触发，属**库级潜伏缺陷**。注意 `Channel.cpp:110-112` 注释明确承认"回调可能同步销毁 Channel 自身"并在 handleEvent 用"回调后立即 return"修复，但 **handleRead 的循环没有同等保护——历史修复不完整**。
- **修复建议**：每帧回调前检查 `disconnected_`（或先循环提取完所有帧再统一回调）；回调后 `return` 或 `break`。

### S3. 内存池 SpanTracker 数组有序性被破坏：二分查找失效 → span 永不归还 PageCache（静默内存驻

- **位置**：`wevix_muduo/src/memory_pool/CentralCache.cpp:368-399`（`expandTrackerArray`）、`:323-366`（`getSpanTracker`）
- **问题**：`expandTrackerArray` 把新数组按 `span_addr` 排序，但**新 emplaced 的 tracker（span_addr=nullptr）被排到数组最前**；之后新 span 按 `span_count_++` 的创建顺序（=分配顺序，非地址序）填充这些靠前槽位 → 有序区间不再按地址有序。`getSpanTracker` 的二分查找依赖有序必然失配，线性扫描范围 `[sorted, total)` 为空 → 返回 nullptr。**进一步推演：初始数组虽全 nullptr 但新 span 按创建顺序写入同样破坏有序性——即 span 总数 < ~1088（首次 ensureSorted 触发线）期间，所有 tracker 查找基本全部失配**。失配时各处均有 `if (tracker)` 兜底（不崩溃），后果是：`fetchRange` 的 `free_count` 记账静默跳过、`performDelayedReturn` 扫描全部落空 → **所有归回的块永远留在 central free list，span 永不 deallocateSpan，free 内存永不 munmap**（`updateSpanFreeCount` 的整 span 回收、PageCache 的 `releaseExcessSpans` 均成死路径）。讽刺的是：该池"回收"功能只在"几乎不发生回收"（地址序=创建序）时才工作。
- **触发场景**：任何发生"分配→释放→再分配"内存往返的长跑服务（span 复用导致地址序错乱是必然的）；压测峰值后 RSS 居高不下。
- **修复建议**：不要在扩容时排序未初始化槽位；改为只对已初始化 tracker 排序 + 未排序尾部线性扫描（现状的 `ensureSorted` 尾部设计其实是正确的，问题出在 `expandTrackerArray` 提前排序 + 后续无序初始化覆盖了有序区）。

## 三、中等问题

### M1. 线程池/事件循环无异常隔离：任一回调抛异常 → std::terminate 杀进程

- **位置**：`wevix_muduo/src/ThreadPool.cpp:160`（`if (task) task();` 无 try/catch）、`EventLoop.cpp:178`（`tasks.front()()`）
- **触发场景**：用户 onMessage/RPC handler 抛异常（反序列化失败、业务异常）→ 工作线程或 IO 线程 std::terminate，进程直接崩溃。库层无任何兜底。
- **修复建议**：`task()` 调用包 try/catch，捕获后 LOG_ERROR 不中断线程循环。

### M2. sendInLoop 无 disconnected_ 检查：关闭后排队的数据会把 channel 重新注册回 epoll

- **位置**：`wevix_muduo/src/Connection.cpp:209-256`
- **问题**：`send()`（`:189-207`）先查 `disconnected_` 再 queueInLoop，但检查与排队之间 handleClose 可先执行；排队的 sendInLoop 随后执行 `outputBuffer_.append` + `channel_->enableWriting()` → `Epoll::updateChannel`（`Epoll.cpp:77`）对 inEpoll_=false 的 channel 执行 **EPOLL_CTL_ADD**，把已进入关闭流程的连接重新挂回 epoll。随后 Connection 析构时该 epoll 条目持悬垂 data.ptr（当前仅依赖 close 时内核自动移除条目才不触发 UAF）；若 fd 已被复用，新连接注册时 EPOLL_CTL_ADD 会 EEXIST 失败导致新连接失联。
- **修复建议**：`sendInLoop` 首行加 `if (disconnected_) return;`。

### M3. handleWrite 对 send 失败只打日志不处理：连接悬挂

- **位置**：`wevix_muduo/src/Connection.cpp:119-143`
- **问题**：`send < 0` 仅 LOG_ERROR。EPIPE/ECONNRESET 时输出缓冲永不排空、连接空转（ET 下 EPOLLOUT 边沿已消费，无新事件）；EAGAIN 时同样悬挂，仅靠 10s 空闲扫描兜底强杀。与 sendInLoop（`:252-255` 有 faultError → handleClose 处理）行为不一致。
- **修复建议**：参照 sendInLoop，对 EPIPE/ECONNRESET/其他硬错误调用 handleClose()。

### M4. ThreadPool 背压超时静默丢任务

- **位置**：`wevix_muduo/include/wevix_muduo/ThreadPool.h:77-84`
- **问题**：队列满 wait_for 1s 后放弃真实任务、返回一个"空任务"的 future，无任何日志。`addTask` 路径（`TcpServer::handleMessage` 的 work pool 分发）任务被静默丢弃 → 该 RPC 请求永无响应，仅靠客户端超时重试掩盖。
- **修复建议**：超时丢弃时打 WARN/ERROR 并记录任务来源；或对 addTask 采用阻塞策略。

> 注：本项与 `doc/审查报告/2. mprpc层bug排查.md` 的 S2 为**同一根因**（TcpServer work pool 分发 + ThreadPool 丢弃语义），两层审查交叉确认。

## 五、存疑项

1. **D1. `Buffer::makeSpace` 碎片整理存在重叠 `std::copy`（UB）**（`Buffer.cpp:280-283`）：当 `readerIndex_ ∈ (kCheapPrepend, 8+readable)` 时源区间与目标区间重叠，`std::copy` 对重叠区间是 UB（libstdc++ 对 char 实际走 memmove 而安全，但标准上不保证）。当前索引增长模式实测安全，**存疑**在于可移植性。建议改用 `std::memmove`。
2. **D2. `Buffer::prepend` / `retrieveAsString` 无边界校验**（`Buffer.cpp:147-160`、`:89-97`）：prependableBytes() 不足时下溢 → OOB 写；len > readableBytes() 时越界读。库内 `prepend` 无调用者、`retrieveAsString` 唯一调用点 `mprpccodec.h:175` 有 total_len 校验，当前均安全；作为公开 API 无防御。建议加 assert 或返回 bool。

## 六、确认无问题的关键点（审查通过项）

- `Channel::handleEvent`（Channel.cpp:77-113）：每个回调后立即 return，历史 UAF（同批 EPOLLIN|RDHUP|OUT 事件）已正确修复；先写后读的顺序修复合理。
- EventLoop 的 pendingTasks 锁 + eventfd 唤醒无丢失唤醒（push 在锁内、写 eventfd 在锁外但严格在 push 之后）；doPendingTasks swap 减锁范围正确。
- handleClose 幂等（`disconnected_` 检查 + 所有调用路径均在 loop 线程）；Connection 引用计数保活（lambda 捕获 self）设计正确。
- CentralCache 锁序（index 自旋锁 → PageCache mutex）单向，无死锁；`expandTrackerArray` 的 deque 引用稳定性成立。
- TcpServer 析构顺序（stop → 线程 join → 成员逆序销毁）下，EventLoop 销毁时 epollfd 尚存活、销毁后无悬垂分发。
- ThreadPool::stop() 会排空队列（线程退出前执行完剩余任务），TcpServer 的 `this` 捕获任务在 stop 期间安全。

## 七、结论与优先修复建议

1. **S1（SIGPIPE）** 优先级最高——修复成本最低（一处 signal 或 4 个 send 点），影响面最大（5 个生产服务都可被对端断开直接杀死），是分布式环境中必然发生的场景。
2. **S2（handleRead UAF）** 与已修复的 Channel::handleEvent 同根，属"历史修复不完整"，建议补上。
3. **S3（内存池回收失效）** 最隐蔽——不崩溃但长跑服务 RSS 持续增长，且压测场景掩盖（压测多为分配为主、释放后不再观测 RSS），建议修复后做一次内存往返压测验证 RSS 回落。
4. M1/M2/M3 属标准的健壮性补齐，改动小可顺手处理。

> 说明：S1-S3 修复后建议跑 echo 压测（bench_echo_stress）+ 单元测试回归；S3 需额外验证内存池回收路径（分配→释放→再分配循环后观察 RSS）。
