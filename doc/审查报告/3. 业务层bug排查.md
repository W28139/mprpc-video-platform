# 3. 业务层 Bug 排查报告

> 审查日期：2026-08-10
> 审查方式：只读代码审查（子代理深度审查 + 人工整理），未修改任何代码
> 审查范围：`video_platform/` 全部 5 个微服务（job_service / scheduler_service / worker_manager / transcode_worker / result_collector）、common_store（MySQL 化）、ffmpeg_executor、mq_client / redis_client / mysql_pool
> 结论：**整体 8/10** —— 架构与防御设计扎实（MySQL 条件更新防覆盖、attempt 幂等、MQ/轮询双路径、组件可降级），但状态机存在 3 个可导致任务**永久卡死或双份执行**的可靠性缺口

关键枚举（状态机语义基准）：
- JOB：PENDING=1, SCHEDULING=3, RUNNING=4, SUCCESS=6, FAILED=7, CANCELED=8
- SHARD：WAITING=2, ASSIGNED=3, RUNNING=4, SUCCESS=5, FAILED=6, RETRYING=7, CANCELED=8

## 一、发现总览

| 级别 | 数量 | 概要 |
|------|------|------|
| 严重 | 3 | S1 RETRYING 死状态；S2 崩溃恢复 attempt_id 复用致双份执行；S3 切分半途崩溃致 shard 永久缺失 |
| 中等 | 7 | 终态回退覆盖、Merge 永不重试、孤儿 ffmpeg、MQ/Redis 永久降级、MySQL 失败误判、取消链路 best-effort、RUNNING 误杀（存疑） |
| 轻微 | 11 | 见第四节 |

## 二、严重问题

### S1. RETRYING 是死状态——RescheduleShard 网络失败后 shard 永久卡死，job 永不终态

- **位置**：`video_platform/src/result_collector/result_collector.cpp:215-224`
- **依据**：RC 在 3 次 RescheduleShard 网络失败后把 shard 置 `SHARD_RETRYING`；对照 scheduler 侧所有状态扫描入口——`SchedulingLoop` 只 `ListByStatus(WAITING/ASSIGNED/RUNNING)`（scheduler_service.cpp:1069-1070、1218-1221、1521），**启动恢复**只处理 ASSIGNED/RUNNING（1073-1109），`NotifyWorkerOffline` 只处理 ASSIGNED/RUNNING（461-465）。grep 全量确认：RETRYING 在 scheduler 中只出现在"更新条件/设置值"（398/417/429 行），**没有任何扫描或重置 RETRYING 的路径**。
- **触发场景**：Worker 转码失败上报 → RC 置 FAILED → 调 RescheduleShard；若 Scheduler 崩溃/网络分区（>7s 的 1s+2s+4s 退避窗口），3 次 RPC 全失败 → RC 置 RETRYING。Scheduler 恢复后该 shard 无任何路径再处理 → 永久卡死，`CheckJobDone` 永远判不完（in_progress>0）→ **job 永久停在 RUNNING/SCHEDULING，且无任何日志告警**。
- **修复建议**：① RC 网络失败路径不置 RETRYING、保持 FAILED（靠 worker 侧 PendingReport 重试或 scheduler 后续重扫）；② 或 scheduler 的 SchedulingLoop/startup recovery 把 RETRYING 一并按 WAITING 处理（注意此时 retry_count 已由 RC 预增的语义对账）。

### S2. Scheduler 崩溃重启的 startup recovery 不递增 retry_count → attempt_id 复用 → 双份执行 + 旧 attempt 结果被接受

- **位置**：`video_platform/src/scheduler_service/scheduler_service.cpp:1073-1109`
- **依据**：recovery 把 RUNNING/ASSIGNED 直接置 WAITING，**未改 retry_count**；而同一文件两条正常重调度路径都 `retry_count++`：NotifyWorkerOffline（495-497）、超时重扫（1406、1493）。`attempt_id = shard_id + "_attempt_" + retry_count`（scheduler 997 行 / worker 134-135 行），RC 的 attempt 幂等校验只比较数字大小（result_collector.cpp:83-95）。
- **触发场景**：Scheduler 被 kill -9 时 Worker 上 RUNNING 的 shard 无人通知；重启后 recovery 把 shard 置 WAITING（retry_count 仍为 0）→ 重新分配 → **新 attempt_id 与旧 attempt 完全相同**。旧 worker 继续转码并上报 attempt_0 结果：① 旧结果 SUCCESS，RC 接受（0>=0 通过），新 worker 白跑；② 旧结果 FAILED，RC 触发 RescheduleShard，随后新 worker 的 SUCCESS（attempt_0）因 `0 < 1` 被拒 → 需第三次执行；③ 两个 worker 同时用 `-y` 写同一 output_path（ffmpeg_executor.cpp:567），双写竞争可损坏产物。
- **修复建议**：recovery 重置时同样 `retry_count++`（保证 attempt_id 变化），并 best-effort 通知旧 worker 取消；或 attempt_id 引入随机/时间戳成分，从根上消除同 retry 数字的碰撞。

### S3. ScheduleJob 幂等返回与"切分中途崩溃"组合 → 部分 shard 计划永久缺失，job 卡死

- **位置**：`video_platform/src/scheduler_service/scheduler_service.cpp:124-157`（幂等返回）+ `:245`（逐条 Insert）
- **触发场景**：5 个 shard 的计划崩溃在插入第 3 个之后（kill -9/MySQL 抖动使 Insert 静默失败——Insert 返回值未检查）。重启后 `ListByJob` 非空 → 幂等返回 3 个 shard → 缺失 2 个永不创建 → 3 个全 SUCCESS 后 `CheckJobDone` 的 `success_count(3) >= expected(5)` 永不成立，failed_count=0 也不触发 FAILED 分支 → **job 永久卡 SCHEDULING**。
- **修复建议**：幂等路径校验 `existing_shards.size() == job.shard_count`，不一致时补建缺失 shard（按 shard_index 差集）。

## 三、中等问题

### M1. SubmitJob 用"快照状态"作为条件更新条件 → 终态可能被回退覆盖

- **位置**：`video_platform/src/result_collector/job_service/job_service.cpp:147-153`
- **问题**：`UpdateIfStatus(job_id, {from_status}, JOB_SCHEDULING)`，from_status 是 `Get` 快照（不限定 PENDING）。对比 PendingScanLoop 正确写法（419 行 `{JOB_PENDING}`）。
- **触发场景**：单 shard 短视频任务（转码 <1s），RC 在 JobService 的 `Get` 与 `UpdateIfStatus` 之间把 job 置 SUCCESS → 条件 `{SUCCESS}` 匹配 → **SUCCESS 被覆盖回退为 SCHEDULING**。兜底是 RC TerminalSweepLoop 15s 后重新判定，但存在状态回退窗口。
- **修复建议**：expect 改为 `{JOB_PENDING}`。

### M2. Merge 失败/RC 重启后永不重试，merged 产物永久缺失

- **位置**：`video_platform/src/result_collector/result_collector.cpp:421-426`
- **问题**：merge 失败仅 `MergingJobs().erase(job_id)` 并注释"will retry via TerminalSweepLoop"，但 **TerminalSweepLoop 明确跳过终态 job**（459-462 行），merge 失败时 job 已置 SUCCESS → 重试路径不存在。RC 进程重启（MergingJobs 进程内集合丢失）同理。
- **触发场景**：merge 时磁盘满/ffmpeg 故障/RC 重启 → job 显示 SUCCESS 但无 `{job_id}_merged.mp4`。
- **修复建议**：merge 失败/中断时将 job 回退到非终态（如新增 JOB_MERGING 过渡态），由 sweep 补 merge。

### M3. Worker 无信号处理 → ffmpeg 孤儿进程残留，与重调度后的新执行双写同一输出文件

- **位置**：`video_platform/src/transcode_worker/transcode_worker.cpp:874-996`（main 无 signal handler）+ `ffmpeg_executor.cpp:567`（恒带 `-y`）
- **触发场景**：worker 被 SIGKILL（docker stop 强制/崩溃）→ ffmpeg 子进程变孤儿继续转码、持续写 output_path；Scheduler 重调度后新 worker 对**同一路径**再次 `-y` 打开 → 双写竞争可能损坏产物，且孤儿 ffmpeg 长时间占 CPU。
- **修复建议**：worker 安装 SIGTERM/SIGINT handler 遍历 `running_shards_` 通知执行线程触发 cancel_cb（已有 kill 机制，只缺信号入口）；执行前按 shard_id 清理残留孤儿进程。

### M4. MQ/Redis 启动时连接失败 → enabled_ 永久 false → 降级永不恢复（"恢复自动切回"承诺失效）

- **位置**：`video_platform/src/mq_client.cpp:113-128`（Init 失败 `enabled_ = false`）+ `:398`（Reconnect 第一行 `if (!inited_ || !enabled_) return false`）+ `redis_client.cpp:43-47`
- **触发场景**：docker compose 中 MQ/Redis 比 scheduler 晚就绪 → 永久 Pull 模式。功能正确性不损（轮询兜底），但 Push 低延迟优化与头文件注释"MQ 恢复后调度自动切回 Push 模式"（mq_client.h:82）不成立。
- **修复建议**：Reconnect/重连成功后恢复 `enabled_=true`；或 Init 失败只置连接标志、enabled_ 由每次调用动态判断。

### M5. MySQL 故障时 Store 静默失败，nullopt 被误判为"记录不存在"，导致错误决策

- **位置**：`video_platform/src/common_store.cpp:239-253`（`Get` 查询失败返回 nullopt，与不存在同义）+ `mysql_pool.h:47`（Acquire 等待 1s 超时返回 nullptr）
- **触发场景**：MySQL 短暂不可用 → `MarkShardCanceledIfJobTerminal`（scheduler_service.cpp:42-43）把"查询失败"当作"job 不存在"→ 终态 job 的残留 shard 不被 CANCELED → 被重新分配执行（浪费 + 潜在双份）；`ScheduleJob`（95-122 行）把查询失败当新 job → 从请求重建并覆盖。
- **修复建议**：Store 增加错误区分（Get 返回 optional+错误码），或调用方对关键决策点做失败快速拒绝而非降级处理。

### M6. 取消链路是 best-effort：CancelShard 通知失败 → 任务继续执行，迟到结果把 CANCELED 覆盖回 SUCCESS

- **位置**：`job_service.cpp:292-327` + `scheduler_service.cpp:647-677` + `result_collector.cpp:127-137`（对结果**无条件接受快照状态**，from_status 是 CANCELED 也照样 `UpdateIfStatus({CANCELED}→SUCCESS)` 成功）
- **触发场景**：用户取消时 worker 网络不可达 → 转码跑完整个 shard（资源浪费）；结果上报后 shard 从 CANCELED 变 SUCCESS（job 因单调性保护保持 CANCELED，数据层面脏但自洽）。
- **修复建议**：RC 对 CANCELED/终态 shard 的结果直接拒绝不覆盖；取消路径对未确认的 worker 做重试/补偿。

### M7. RUNNING 5 分钟超时无确认直接重置——慢转码可能被误杀（存疑）

- **位置**：`scheduler_service.cpp:1429-1512`
- **问题**：RUNNING 超时直接"通知取消 + 重置 WAITING"，不像 ASSIGNED 路径（1270-1345）有 QueryShard + progress 观察窗。注释称"5 分钟是强卡死信号"，但 4K/慢机器上单 shard 转码 >5min 是现实可能（shard_duration_sec 上限 3600）。
- **影响**：误杀 → 双份执行（同 S2 的文件竞争与重试浪费）。
- **修复建议**：RUNNING 超时前先 QueryShard 确认一次（复用 progress_watch_ 机制）。

## 五、结论与优先修复建议

按"卡死/双份/资源"三档优先级：

1. **S1（RETRYING 死状态）+ S3（切分半途缺失）**：任务永久卡死类，用户可感知（job 卡 RUNNING/SCHEDULING 永不终态），建议优先修。
2. **S2（attempt_id 复用）**：双份执行 + 产物损坏风险，崩溃恢复路径，建议与 S1 同批修。
3. **M3（孤儿 ffmpeg）+ M4（永久降级）**：前者是资源泄漏 + 双写损坏，后者是部署顺序问题（compose 场景真实存在），建议次批。
4. **M1/M2/M5/M6**：状态回退/错误归因类，防御性修复，成本低可顺手做。
5. 轻微项按需处理，L1（死代码）建议下个重构周期清理。

> 说明：S1-S3 修复后建议跑一遍集成测试（提交→转码→合并→SUCCESS）+ 故障注入（kill scheduler、kill worker、MySQL 抖动）回归。
