# 4. 性能优化建议

> 审查日期：2026-08-10
> 审查方式：只读代码审查（子代理深度审查 + 人工整理），未修改任何代码
> 审查范围：wevix_muduo + mprpc + video_platform 全项目
> 基线：echo 17 万 QPS P50~60us；RPC 直连长连接 12.3 万 QPS P50 403us；50 并发约 5 万 QPS；Store 操作平均 ~0.2ms

## 二、详细发现

### 1. 【高】每次 RPC 固定 4 次 setsockopt 系统调用

- **位置**：`mprpc/src/mprpcchannel.cc:736-741`（`SendRequestAndReadResponse` 内，长连接复用路径上每次调用 `SetSocketTimeout` → SND/RCV 各 2 次 = 4 次 setsockopt syscall）
- **瓶颈**：12.3 万 QPS × 4 ≈ 50 万次 setsockopt/秒，纯系统调用开销；50 并发下每条 RPC 白付 ~1-3us
- **预期收益**：P50 403us 可降 ~3-8%（~10-30us 量级），RPC QPS 提升 5-10%
- **改造成本**：中。方案：连接建立时按默认超时设一次 socket 超时；调用级超时（`SetTimeoutMs`）> 默认时才重设；或改用 poll/getsockopt 实现调用级超时

### 2. 【高】RpcLatencyHistogram 热路径与注释不符，每次调用加全局锁

- **位置**：`mprpc/src/mprpcmetrics.cc:670-684`
- **瓶颈**：注释声称"首次注册缓存指针，此后无锁"，实际实现是**每条 RPC 无条件 `std::lock_guard cacheMutex` + hash 查找**。50 线程并发争一把锁，且每条 RPC 还要为 `RpcLatencyGuard` 拼接一次 `service_name + "." + method_name` 字符串（mprpcchannel.cc:823，1 次堆分配）
- **预期收益**：每条 RPC 省一次锁 + hash（~100-200ns 含等待），顺带省 1 次字符串构造
- **改造成本**：低。注册后缓存 `MetricHistogram*` 到 thread_local 或 shared_ptr 快照，查找路径无锁

### 3. 【中高】RPC 帧数据端到端 6-8 次全量拷贝 / 8-10 次堆分配

- **位置**：
  - 发送链：`mprpcchannel.cc:885-899` — request_payload 拼接（1 拷贝）→ `BuildRpcFrame` 整帧再拷贝（1 拷贝）
  - 接收链：`mprpcchannel.cc:774-786` — responseFrameBody 分配 → `DecodeRpcFramePayload` 的 substr（1 拷贝）→ `DecodeRpcResponsePayload` 的 2 次 substr → `ParseFromString`
  - 服务端：`rpcprovider.cc:86-104` `DecodeRequestHeader` 2 次 substr；`rpcprovider.cc:36-44` 拼接 + BuildRpcFrame 再拷贝
  - 编解码器层：`mprpccodec.h:175-177` — `frameBody = buf->retrieveAsString(total_len)`（1 拷贝）+ `*payload = frameBody.substr(...)`（再 1 拷贝）
- **瓶颈**：一条 RPC 同份数据被整段 memcpy 6-8 次、堆分配 8-10 次。压测 64B 小报文时绝对收益有限，但大报文（视频元数据、批量任务）和 P99 延迟改善明显
- **预期收益**：小报文每条 RPC 省 ~1-2us（P50 中 ~5%）；大报文（>10KB）可省 30-50% 传输路径延迟
- **改造成本**：中。`BuildRpcFrame` 改为直接写预分配发送缓冲（一次 reserve + 顺序填 4+2+2+payload）；解码链改 offset 指针解析（`ParseFromArray` 带长度指针重载），消除 substr

### 4. 【中】MqConsumeLoop 每条消息全量 LoadOnlineWorkers（Redis HGETALL + 9 字段字符串解析）

- **位置**：`video_platform/src/scheduler_service.cpp:1658-1662`（每条 `shard.waiting` 消息一次 `LoadOnlineWorkers` → `redis.HGetAll` + `substr/atoll` 解析循环，见 739-824）
- **瓶颈**：Push 调度主路径上每条消息一次 Redis 网络往返 + 字符串解析；分配速率 10/s 时每秒 10 次全量 HGETALL
- **预期收益**：单次分配延迟降低 ~0.5-1ms（含网络往返）；高分配速率下明显
- **改造成本**：低。加 1s TTL 的 worker 列表缓存（Redis 快照本就 20s 过期语义，缓存 1s 无损）

### 5. 【中】MysqlPool 每次 Acquire 都 mysql_ping（一次网络往返）

- **位置**：`video_platform/src/mysql_pool.cpp:138`
- **瓶颈**：每次 Store 操作（Get/Update/List）都发 COM_PING 到 MySQL。本地 ~0.05-0.1ms，"Store 平均 0.2ms"中 ping 约占一半
- **预期收益**：Store 操作延迟降 30-50%（0.2ms → ~0.1ms）
- **改造成本**：低。连接记录上次 ping 时间戳，30s 内跳过

### 6. 【中低】三个后台循环全表扫描

- **位置**：`worker_manager.cpp:180`（HeartbeatTimeoutCheck 每 2s `ListAll()` 全表 workers）、`result_collector.cpp:452`（TerminalSweepLoop 每 15s `ListAll()` 全表 jobs，含大量终态 job）+ 每个非终态 job 再 ListByJob、`job_service.cpp:353`（PendingScanLoop 每 10s `ListAll()` 全表 jobs）
- **瓶颈**：数据量随压测/运行累积（千级 job）后每轮全表拉取 + 全列解析（每行 16 列 stoi/stoll）；TerminalSweepLoop 对终态 job 白查
- **预期收益**：库表 1 万行时每轮省 ~10-50ms 后台开销
- **改造成本**：低。`SELECT ... WHERE status=...` 直接过滤，索引已存在（`idx_status`）

### 7. 【中低】Store 全列 UPDATE

- **位置**：`video_platform/src/common_store.cpp:186-224`（JobStore）与 `318-357`（ShardStore）的 `UpdateIfStatus`
- **瓶颈**：每次仅推进 status/updated_at 却 UPDATE 全部 13-16 列（行锁范围、binlog 体积、网络字节都放大；状态推进在调度/上报路径上很频繁）
- **预期收益**：每次状态推进 SQL 体量减 60-80%
- **改造成本**：低。SET 子句只写变化列

### 8. 【中低】echo/无 codec 路径每消息 1 次 string 拷贝 + 1 次堆分配

- **位置**：`wevix_muduo/src/Connection.cpp:104`（`retrieveAllAsString`）+ `Buffer.cpp:89-97`（无条件构造 string）
- **瓶颈**：echo 17 万 QPS 下每消息一次全量拷贝 + 分配（read 本身零拷贝已做到，瓶颈在 string 化）；RPC 路径 `Connection.cpp:92-99` 的 codec 循环同样每帧构造 string
- **预期收益**：echo P50 60us 中省 ~2-4us；与第 3 条合并改造（offset 解析）后收益叠加
- **改造成本**：中（回调接口改 `const char*, size_t` 或 string_view）

### 9. 【中低】GetPooledConnection 全局池锁 + 每 RPC shared_ptr 两次原子 refcount

- **位置**：`mprpc/src/mprpcchannel.cc:635-650`
- **瓶颈**：50 线程争一把 `ConnectionPoolMutex` 全局锁；每次返回连接 shared_ptr 拷贝 2 次 refcount 原子操作
- **预期收益**：每条 RPC 省 ~50-100ns 锁等待
- **改造成本**：低（per-endpoint 分片锁）

### 10. 【低】MetricHistogram::Observe 的 3 个共享原子写（cache-line 竞争）

- **位置**：`mprpc/src/mprpcmetrics.cc:185-193`
- **瓶颈**：每条 RPC 所有线程对同一 histogram 的 `bucketCounts_[idx]` / `count_` / `sum_` 写同一 cache line
- **预期收益**：50 并发下省部分原子冲突（~50-100ns/条）
- **改造成本**：中（per-thread 样本缓冲 + 定期归并）

### 11. 【低】EventLoop::run 每轮循环构造 vector（每 batch 一次堆分配）

- **位置**：`wevix_muduo/src/EventLoop.cpp:90`
- **预期收益**：每 epoll batch 省 1 次 malloc/free
- **改造成本**：低（成员复用 + clear）

### 12. 【低】handleTimer 每次触发遍历全部连接（O(N)）

- **位置**：`wevix_muduo/src/EventLoop.cpp:191-219`
- **瓶颈**：subLoop 每 5s 全连接扫描 + 锁；连接 1000+ 时可观
- **改造成本**：低（惰性清理/超时桶）

### 13. 【低】其他小项

- **WM Heartbeat 每次心跳多余 1 次 WorkerStore::Get**（`worker_manager.cpp:95-98`）— request 里已有全部快照字段，省 1 次 MySQL SELECT。成本低
- **Worker AssignShard 每次分配 CollectCpuUsage 全量扫描 /proc**（`transcode_worker.cpp:139`）— 每分配一次扫描线程+子进程 stat，~50-100us；可复用心跳 3s 采集结果。成本低
- **Buffer::makeSpace 扩容打 LOG_WARN**（`Buffer.cpp:268`）— 高吞吐下偶发刷屏 + WARN 全格式开销；降级为 DEBUG。成本低
- **日志系统本身**：Release 下 RPC/echo 热路径无 INFO/WARN 级日志（DEBUG 编译为零开销），业务低频 INFO（调度/心跳/分配各一条）可接受；`AsyncLogger::append` 每次 notify_one + 2 次堆分配在每秒 <100 条时无影响。**不构成当前瓶颈**
- **TcpServer::handleMessage 每消息 make_shared**（`TcpServer.cpp:149`）— work pool 模式每消息 1 次堆分配，RPC 服务端每条请求 1 次；可接受

## 三、Top 5 建议清单

1. 去掉每次 RPC 的 4 次 setsockopt（超时改为连接建立时设置 + 调用级超时用 poll 实现）— `mprpcchannel.cc:736`
2. `RpcLatencyHistogram` 热路径改为 thread_local 缓存指针，消除与注释不符的每次加锁 — `mprpcmetrics.cc:670`
3. 帧编解码链去拷贝：`BuildRpcFrame` 直接写发送缓冲、解码链改 offset/`ParseFromArray` 指针解析，端到端省 6-8 次全量拷贝 — `mprpccodec.h:175`、`mprpcchannel.cc:885`、`rpcprovider.cc:86`
4. MqConsumeLoop 的 `LoadOnlineWorkers` 加 1s TTL 缓存，消除每条消息一次 HGETALL — `scheduler_service.cpp:1660`
5. MysqlPool `mysql_ping` 降频到 30s 一次 + Store 全列 UPDATE 改增量列更新 — `mysql_pool.cpp:138`、`common_store.cpp`

## 四、结论

网络库内核（Buffer 三区模型、readv 零拷贝、ET 处理、UAF 修复）本身质量很好；当前最大的浪费集中在 **RPC 框架层的系统调用（setsockopt）与全局锁（metrics 缓存）**，其次是 **帧数据在 string 间的反复拷贝**——这三项恰好都在 P50 403us 的构成里，优先处理前两条即可获得可测的 RPC 延迟/QPS 收益。业务层（调度/Store/MQ）无 N+1 或严重慢查询，主要是后台循环全表扫和消息级 Redis 往返的降频优化。
