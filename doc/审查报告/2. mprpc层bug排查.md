# 2. mprpc 层 Bug 排查报告

> 审查日期：2026-08-10
> 审查方式：只读代码审查（子代理深度审查 + 人工整理），未修改任何代码
> 审查范围：`mprpc/` 框架源码（channel / codec / provider / ZookeeperUtil / 连接池 / mprpcredis）及支撑层关键路径
> 结论：**整体健壮性 8/10** —— 协议层防护和故障降级设计成熟，主要失分在 ZK 回调 ctx 并发正确性 UB 与 work pool 静默丢请求两个隐蔽缺陷

## 一、发现总览

| 级别 | 数量 | 概要 |
|------|------|------|
| 严重 | 2 | S1 ZK 回调 ctx UAF/泄漏竞态；S2 work pool 满时静默丢弃 RPC 请求 |
| 中等 | 6 | 超时重试 at-least-once、ZK 启动失败永久禁用、半包 DoS 面、串行拉取、request 生命周期、Redis 永久降级 |
| 轻微 | 5 | 死连接检测、错误帧归因、无"不超时"选项、CLOCK_REALTIME、CSV 无转义 |
| 存疑 | 3 | 见第五节 |

## 二、严重问题

### S1. ZK 异步回调 ctx 存在 use-after-free 竞态与泄漏竞态（并发 UB）

- **位置**：`mprpc/src/ZookeeperUtil.cc:31-58`（回调）+ `:341-343` / `:374-376`（成功路径）
- **代码依据**：

```cpp
// GetDataCb（watcher 回调线程执行）
ctx->rc = rc;
...
sem_post(&ctx->sem);                                    // :38
if (ctx->caller_gone.load(std::memory_order_acquire))   // :40
    delete ctx;                                         // :41
```
```cpp
// GetData 成功路径（调用线程）
if (!WaitZooAsync(ctx, 3000)) { ... store(true) ... }   // :333-340
std::string result = ctx->data;
sem_destroy(&ctx->sem);
delete ctx;                                             // :341-343
```

- **问题**：`sem_post` 与 `sem_timedwait` 返回构成同步点，但**回调线程在 post 之后的 `caller_gone.load` 与调用线程的 `delete ctx` 之间没有任何同步**：
  - 成功路径（每次正常 GetData/GetChildren 都会发生）：调用方 `sem_timedwait` 返回 0 → 直接 `delete ctx`；回调线程此刻可能尚未执行 `caller_gone.load` → 对已释放内存做 atomic load（UB）。实际通常读到旧值 false 而不 delete，表现为隐形 UB；极端调度下（内存被复用）可能 double free。
  - 超时路径：调用方 `store(true)` 之后不再碰 ctx（由回调回收）——但回调的 load 可能**先于**调用方的 store 执行（load 读到 false → 不 delete），此时调用方已离开、回调不回收 → **ctx 泄漏**（含 sem_t、data/children 字符串），每次 ZK 超时约 50% 概率泄漏。而 ZK 卡死（阶段 11 修复的场景）恰恰会让该路径反复触发。
- **触发场景**：任何一次 ZK 读（服务发现的常规热路径）都有 UAF 窗口；ZK 挂起/慢响应时每次超时都伴随概率性泄漏。
- **修复建议**：成功路径在 `delete ctx` 之前先 `ctx->caller_gone.store(true, memory_order_release)`——无论 load 与 store 谁先谁后，回调都不会再 delete，UAF 窗口消除；或回调侧改用 `exchange` 语义保证"恰好一个线程负责 delete"。

### S2. ThreadPool 队列满时静默丢弃 RPC 请求，且无任何错误反馈

- **位置**：`wevix_muduo/include/wevix_muduo/ThreadPool.h:103-108` + `wevix_muduo/src/TcpServer.cpp:146-154`
- **代码依据**：

```cpp
// submitTask 背压超时（1s）后：
if (!notFull_.wait_for(lock, std::chrono::seconds(1), ...))
{
    auto emptyTask = ...; (*emptyTask)();   // 空任务代替真实任务执行
    return emptyTask->get_future();          // 真实任务已被静默丢弃
}
```
```cpp
// TcpServer::handleMessage（IO 线程）：
workThreadPool_->addTask([this, conn, msg]() { onMessageCallback_(conn, *msg); });
```

- **问题**：当 work pool 队列满（阈值 10000）且 1 秒内无空位时，`submitTask` 丢弃真实任务。对 RPC 服务端来说，**请求帧已被 codec 消费但永远不会进入业务处理**——不回包、不记日志、不关连接，客户端只能等到超时（且超时还会触发重试放大负载）。同时 `addTask` 最多阻塞 IO 线程 1s，期间该 IO 线程所有连接暂停读事件。
- **触发场景**：业务处理慢（如真实 ffmpeg 转码阻塞 2 个默认 work 线程）+ 瞬时请求洪峰，队列积压超过 10000。恢复后无自愈机制，属诊断黑洞。
- **修复建议**：`addTask`（void 版）失败时打 ERROR 日志并直接 `conn->forceClose()`（或回 RPC_TIMEOUT 错误帧），让客户端立即感知而非干等；为队列满预留快速失败回调。

## 三、中等问题

### M1. RPC_TIMEOUT 被当作"连接级失败"清池重发 → at-least-once 重复执行

- **位置**：`mprpc/src/mprpcchannel.cc:953-957`
- **问题**：超时**不能证明请求未被服务端执行**（可能仍在 work 队列/处理中，只是响应晚到），重发后服务端可能执行两次。当前业务靠 `UpdateIfStatus` 等幂等设计兜底，但框架层面对外暴露的是非幂等语义。此外重试会再消耗一个完整 timeoutMs，总耗时最坏 2×timeoutMs+。
- **触发场景**：任何服务端处理慢于客户端超时的调用。
- **修复建议**：文档明确"重试语义 = at-least-once，调用方必须幂等"；或将 TIMEOUT 移出自动重试清单，由调用方显式决定。

### M2. ZK 客户端一次性启动失败 → 进程内服务发现永久失效

- **位置**：`mprpc/src/mprpcchannel.cc:197-206`
- **问题**：`std::call_once` 包裹 `SharedZkClient().Start()`，`started` 只在 once 块内赋值一次；失败后 `EnsureSharedZkClientStarted()` 永远返回 false。ZK 瞬时不可用会永久禁用本进程服务发现，直到进程重启；ZK 恢复后无任何自愈路径。
- **触发场景**：进程启动时 ZK 尚未就绪（compose 冷启动竞态），或 ZK 宕机期间新起的服务进程。
- **修复建议**：失败后允许周期重试（如每次调用时检查 `zoo_state` 为 CONNECTING 则重新 `Start()`），或为 Start 引入 TTL 失效重建。

### M3. 半包帧可长期占用服务端内存；非法 total_len 只清缓冲不关连接（DoS 面）

- **位置**：`mprpc/include/mprpccodec.h:162-167` + `wevix_muduo/src/Buffer.cpp:179-233` + `wevix_muduo/src/EventLoop.cpp:191-219`
- **问题**：① 恶意客户端可声明合法上限 64MB 的 `total_len`，然后每 <10s 发少量字节保持 `lastActiveTime_` 刷新，绕过 10s 空闲剔除，让单连接长期占用 64MB 内存；TcpServer 无连接数上限，多连接叠加可直接拖垮服务内存。② `total_len` 非法时只 `retrieveAll` 不关闭连接，攻击者可无限发送坏帧头，且每次都会连带清掉同流中的合法帧。③ 服务端 `DecodeRequestHeader` 失败路径（rpcprovider.cc:306-313）同样只回错帧不关连接。
- **触发场景**：半公开网络中的恶意客户端（协议层防 DoS 设计缺口）。
- **修复建议**：非法 total_len/magic 直接 `conn->forceClose()`；增加每连接输入缓冲上限（半包超限即断开）和全局连接数上限；半包超时独立于活动超时。

### M4. 服务发现 ZK 拉取为逐 child 串行同步阻塞，最坏 N×3s 卡死调用线程

- **位置**：`mprpc/src/mprpcchannel.cc:296-306`
- **问题**：`GetChildren` 后对每个 child 依次 `zk.GetData(childPath)`，每次内部异步+3s 超时。同一 method 注册 N 个实例时最坏 N×3s 阻塞（本地缓存 miss 且 Redis miss 时），同步 RPC 调用线程被整体拖住。无整体超时上限。
- **触发场景**：实例扩容后本地缓存过期 + Redis 不可用 + ZK 响应慢。
- **修复建议**：并行拉取（线程池/fan-out）或对整体加超时；实例数大时改用单次批量读取协议。

### M5. 服务端 request 对象生命周期与异步 done 不兼容（API 隐患）

- **位置**：`mprpc/src/rpcprovider.cc:377-412`
- **问题**：protobuf 标准语义是"done 被调用前 request/response 仍有效"。本实现把 request 所有权留在 `unique_ptr`，`CallMethod` 一返回即析构；而 response 被放进 `RpcResponseContext` 延后释放（:402），两者语义不对称。当前平台业务全部同步调用 `done->Run()`，暂时安全；但任何异步业务实现（在 done 中访问 request）将直接 UAF。
- **触发场景**：未来接入异步 service 实现（协程化/任务队列化处理）。
- **修复建议**：request 所有权也移交 context（与 response 对称），或文档明确"CallMethod 返回后 request 失效"的框架约定。

### M6. Redis 启动期连接失败 → 集中缓存永久禁用，与"恢复自动切回"承诺不符

- **位置**：`mprpc/src/mprpcredis.cc:44-71`（`EnsureInitLocked`）
- **问题**：`inited_ = true` 在首次初始化时无条件置位；连接失败置 `enabled_ = false` 后**不再有任何重连入口**（后续所有 `enabled()` 直接短路返回）。只有命令执行失败路径会重建连接，但启动期失败是永久性的一次性失败——Redis 之后恢复，本进程也永远不会再走集中缓存。功能有 ZK 直读兜底，但"按次降级，恢复自动切回"在启动场景不成立，且无日志提示状态已固化。
- **修复建议**：启动失败后允许按 TTL/调用频率重试初始化（用时间戳节流）。

## 四、轻微问题

| # | 位置 | 问题 | 建议 |
|---|------|------|------|
| L1 | `mprpcchannel.cc:621-650` | 连接池空转死连接检测缺失，依赖"失败-清池"被动恢复；服务端 10s 空闲剔除制造死连接，每次代价一次完整超时往返 | 复用前 `recv(MSG_PEEK|MSG_DONTWAIT)` 探测或缩短失败收敛路径 |

| L3 | `mprpccontroller.cc:48-52` | `SetTimeoutMs` 非正数归一为 0，而 0 被解释为"未设置→默认 5s"，不存在显式无限等待 | 文档明确语义 |
| L4 | `ZookeeperUtil.cc:62-76` | `WaitZooAsync` 用 `CLOCK_REALTIME` 计算绝对超时，NTP 回拨会使超时意外延长 | 改用 `CLOCK_MONOTONIC` + `sem_clockwait` |
| L5 | `mprpcchannel.cc:248-281` + `rpcprovider.cc:255-257` | ZK 注册数据 CSV 无转义、`GetData` 对 `value_len` 无上限（边缘威胁面） | 防御性校验即可 |

## 五、存疑项

1. **`ZkClient::Start()` 失败路径的 `sem_destroy` 与 watcher 线程**（ZookeeperUtil.cc:194-201）：`zookeeper_close` 后立即 `sem_destroy(&sem)`，若 global_watcher 回调仍有 in-flight，`sem_post(sem)` 会操作已销毁的信号量。建议 close 前先 `zoo_set_context` 置空。
2. **`Connection::sendInLoop` 对已 remove 的 Channel 访问**（Connection.cpp:209-256）：work 线程排队的 send 任务可能晚于 handleClose 执行，对已断开 fd 的 send 返回 EPIPE → handleClose 幂等返回。不崩溃但依赖任务队列顺序，属时序噪音。
3. **`EndpointCacheEntry.nextIndex` 双轨轮询**（mprpcchannel.cc:351-359, 377-378）：并发下本地缓存路径的 nextIndex 在锁内自增，语义正确；两套计数器并存仅影响分布均匀性，无正确性问题。

## 六、结论与优先修复建议

1. **S1（ZK ctx 竞态）** 应最先修——服务发现是热路径，且超时场景反复触发，修复成本极低（一行 store）。
2. **S2（work pool 静默丢请求）** 是诊断黑洞，建议改成失败快速失败 + ERROR 日志。
3. **M2（ZK 启动失败永久禁用）** 影响部署鲁棒性，与阶段 13 的 compose 冷启动场景直接相关。
4. 其余 M 级问题多数属于"文档语义明确"或"防御性增强"，可在后续迭代处理。

> 说明：S1/S2/M1/M2 的修复涉及框架层行为，改完需重跑单元测试（test_rpc_protocol 等）+ RPC 压测（bench_rpc_stress）回归。
