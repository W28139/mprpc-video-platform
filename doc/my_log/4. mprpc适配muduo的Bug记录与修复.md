> 背景：将自己写的 mprpc 框架接入自己写的 wevix_muduo 网络库，修复参数解析错误和日志路径问题，并将帧编解码能力植入 muduo，实现网络层自动处理粘包/拆包。

## Bug #1：客户端参数解析错误 + nullptr Controller 崩溃

### 现象

客户端运行后，要么直接报 `format: command -i <configfile>` 并退出，要么段错误崩溃。

### 根因分析

**原因 A — 未传 `-i` 参数：**
`MprpcApplication::Init()` 强制通过 `getopt(argc, argv, "i:")` 解析 `-i <configfile>`。直接 `./user_consumer` 运行必然失败。

**原因 B — Controller 传 nullptr：**
`calluserservice.cc` 中调用方式：

```cpp
stub.Login(nullptr, &request, &response, nullptr);   // nullptr controller!
stub.Register(nullptr, &req, &rsp, nullptr);          // nullptr controller!
```

当 `mprpcchannel.cc` 中序列化/网络操作失败时，直接调用 `controller->SetFailed(...)`，对空指针解引用 → 段错误。

**原因 C — 响应变量写错：**
Register 的响应存在 `rsp` 里，判断条件却写成了 `response.result().errcode()`（用的是 Login 的 `response` 变量），导致检查的是上一步的结果。

### 修复方案

**`example/caller/calluserservice.cc`：**

| 修改点 | 修改前 | 修改后 |
|--------|--------|--------|
| 头文件 | 无 | `#include "mprpccontroller.h"` |
| Controller | `stub.Login(nullptr, ...)` | `MprpcController ctl; stub.Login(&ctl, ...)` |
| Register 响应检查 | `response.result().errcode()` | `rsp.result().errcode()` |
| 错误处理 | 无 `Failed()` 检查 | 添加 `ctl.Failed()` → 打印 `ErrorText()` |

## Bug #2：日志文件生成位置错误

### 现象

日志文件 `2026-7-23-log.txt` 生成在 `bin/` 目录，希望放在项目根目录的 `program_log/` 下。

### 根因

`mprpc/src/logger.cc` 中使用相对路径打开文件。二进制在 `bin/` 中运行，当前工作目录就是 `bin/`，所以日志落在 `bin/`。

### 修复方案

```cpp
// 修改前
sprintf(file_name, "%d-%d-%d-log.txt", ...);

// 修改后：用相对于 bin/ 的路径指到 program_log/
sprintf(file_name, "../program_log/%d-%d-%d-log.txt",
        nowtm->tm_year + 1900, nowtm->tm_mon + 1, nowtm->tm_mday);
```

## 架构改进：帧编解码器进入 muduo

### 问题背景

最初的 mprpc 协议设计有两个缺陷：

1. **请求有帧头，响应没有。** 请求端用 `[header_size(4B)] + [RpcHeader] + [args]` 格式，响应端却是裸 protobuf 直接发。客户端只能靠 `recv()` 循环读到 `FIN` 才能判断收完——这依赖 TCP 的半关闭语义，不够可靠，大响应也有被 1024 字节缓冲区截断的风险。

2. **帧边界判断在应用层。** `rpcprovider.cc` 的 `OnMessage` 里手动检查 `message.size() >= 4`、截取 `header_size`、再截 `args_size`。如果 TCP 拆包导致一次 `OnMessage` 没收到完整帧，解析失败后数据就直接丢弃了——因为 muduo 的 `retrieveAllAsString()` 已经把 Buffer 清空了，没地方暂存半帧。

### 设计目标

让 muduo 的 Connection 承担帧提取职责：**把粘包/拆包问题封在网络库里，应用层只拿完整帧。**

实现这个目标需要三个前提：

1. **统一帧格式**——请求和响应都使用长度前缀，codec 才能统一处理
2. **Buffer 暂存半帧**——数据不足时留在 Buffer，等下次 `handleRead` 追加再试
3. **codec 可插拔**——muduo 不绑定 RPC 协议，不同协议可以换不同 codec

### 这就是自己写 muduo 的原因

通用 muduo追求通用性，把 Buffer 直接暴露给用户，帧解析完全交给上层。这对于一个要给所有人用的库是正确的。

但我们的场景不同：**mprpc 和 wevix_muduo 是一起设计的，mprpc 是我们唯一的上层协议。** 这意味着我们可以把 RPC 的帧格式认知下沉到 muduo 里，让网络层和应用层之间的接口更干净。这正是自己写 muduo 的核心优势——不是重复造轮子，而是**为自己的协议定制网络栈**。

```
通用 muduo：     我们自己：
                
Buffer (原始)    Buffer + RpcMessageCodec  ← 网络层就懂 RPC 帧
  ↓                ↓
应用自己切帧      OnMessage(完整帧)        ← 应用只关心业务
```

### 修改内容

#### 0. 统一帧格式：请求和响应都加长度前缀

这是 codec 工作的基础——必须在帧的最前面用固定长度字段标明整帧大小。

```
修改前:
  请求: [header_size(4B)] + [RpcHeader] + [args]         ← 有内层头，缺外层
  响应: [protobuf 裸数据]                                  ← 完全没有头

修改后:
  请求: [total_len(4B)] + [header_size(4B)] + [RpcHeader] + [args]
         ↑ codec 读这个
  响应: [response_size(4B)] + [protobuf 数据]
         ↑ codec 同样可以读这个
```

`total_len` 和 `response_size` 本质上是一回事：**帧最前面的 4 字节无符号整数，告诉 codec 整帧有多长。** 请求和响应完全对称。

#### 1. muduo 侧：Connection 增加 MessageCodec

**`wevix_muduo/include/wevix_muduo/Connection.h`：**

```cpp
// 帧编解码器：从 Buffer 中尝试提取一个完整帧
// 返回 true → 成功提取一帧（message 被填充），Buffer 已消费
// 返回 false → 数据不足，留在 Buffer 等下次追加
using MessageCodec = std::function<bool(Buffer*, std::string&)>;

void setMessageCodec(MessageCodec cb);
```

**`wevix_muduo/src/Connection.cpp`** 的 `handleRead` 改为：

```cpp
if (messageCodec_)
{
    // 循环提取完整帧，每帧回调一次 onMessage
    // 不完整数据留在 inputBuffer_ 等下次 read 追加
    std::string message;
    while (messageCodec_(&inputBuffer_, message))
    {
        if (onMessageCallback_)
            onMessageCallback_(shared_from_this(), message);
    }
}
else
{
    // 无 codec：保留旧行为，完全向后兼容
    std::string message = inputBuffer_.retrieveAllAsString();
    if (onMessageCallback_)
        onMessageCallback_(shared_from_this(), message);
}
```

关键点：codec 只消费完整帧。不完整的数据 `peek()` 不 `retrieve()`，留在 Buffer 里。下次 `handleRead` 读到新数据后 `while` 循环再试。

#### 2. muduo 侧：TcpServer 透传 codec

**`TcpServer.h`** 增加 `setMessageCodec(Connection::MessageCodec cb)`。  
**`TcpServer::handleNewConnection()`** 中自动应用到每个新连接：

```cpp
if (messageCodec_) {
    conn->setMessageCodec(messageCodec_);
}
```

#### 3. mprpc 侧：RPC 专用 codec

**`mprpc/include/mprpccodec.h`：**

```cpp
inline bool RpcMessageCodec(wevix_muduo::Buffer* buf, std::string& message)
{
    // 帧格式：[total_len(4B)] + [payload(total_len bytes)]
    if (buf->readableBytes() < 4) return false;      // 连长度头都不够

    uint32_t total_len = 0;
    std::memcpy(&total_len, buf->peek(), 4);

    if (buf->readableBytes() < 4 + total_len) return false;  // 数据不够

    buf->retrieve(4);                           // 消费 total_len 头
    message = buf->retrieveAsString(total_len);  // 提取 payload
    return true;
}
```

codec 完全不解析 payload 内容——不关心里面是 RpcHeader 还是 HTTP header。只管"帧有多长"。应用层收到的 message 是 `[header_size(4B)] + [RpcHeader] + [args]`，和之前格式完全兼容。

#### 4. RpcProvider 一行启用

```cpp
// rpcprovider.cc Run()：
server.setMessageCodec(RpcMessageCodec);
server.start();
```

`OnMessage` 不再需要做 `message.size() >= 4` 检查——muduo 已经保证了。

#### 5. 客户端 wire format 对齐

```cpp
// mprpcchannel.cc 发送端：
std::string send_rpc_str;
send_rpc_str +=  header_size(4B二进制) + rpc_header_str + args_str;
uint32_t total_len = send_rpc_str.size();
send_rpc_str.insert(0, std::string((char*)&total_len, 4));  // 外层帧头
```

```cpp
// mprpcchannel.cc 接收端：
// 先读 4 字节 → response_size
// 再读 response_size 字节 → 完整响应
```

### 客户端和 muduo 的关联

从代码层面看，客户端用的是 raw socket，没有调用 muduo 的任何类。但从**协议层面**看，客户端和服务端共享同一套帧格式：

```
客户端                   服务端 muduo
┌──────────┐            ┌─────────────────────┐
│ 组帧逻辑  │            │ RpcMessageCodec      │
│ total_len │  ──TCP──► │ peek(4) → total_len  │
│ payload   │            │ 等够了 → retrieve()  │
└──────────┘            └─────────────────────┘
      ↑                          ↑
      同样的长度前缀协议
```

这就是**专属于 RPC 的 muduo**：muduo 本身就是为 mprpc 协议而写的，所以在 Connection 层植入 RPC 帧格式的认知是合理的。如果用的是通用 muduo，这种耦合会被认为是分层破坏；但这里 muduo 和 mprpc 是一起设计的，这种"下沉"反而是正确的架构选择。

### 架构分层

```
        ┌──────────────────────────────┐
        │        Application (RPC)      │
        │    OnMessage(conn, 完整帧)    │  ← 只处理业务
        └──────────────┬───────────────┘
                       ▲ 完整帧
        ┌──────────────┴───────────────┐
        │      MessageCodec (帧编解码)  │  ← 层间接口
        │  从 Buffer 循环提取完整帧      │
        │  半帧暂留 Buffer 等下次        │
        └──────────────┬───────────────┘
                       ▲ raw bytes
        ┌──────────────┴───────────────┐
        │   Buffer (readv 散射读)       │
        │   Connection::handleRead()    │  ← muduo 网络层
        └──────────────┬───────────────┘
                       ▲ TCP segments
        ┌──────────────┴───────────────┐
        │     Linux Kernel (epoll)      │
        └──────────────────────────────┘
```

### 两级 4 字节帧头

| 层级 | 字段 | 消费方 | 职责 |
|------|------|--------|------|
| 外层 | `total_len` | `RpcMessageCodec`（muduo 层） | 帧边界：从 Buffer 中截出完整一帧 |
| 内层 | `header_size` | `OnMessage`（应用层） | 协议解析：提取 RpcHeader 中的 service/method/args_size |

## 附录：完整 RPC 调用链路

```
┌─ 客户端 mprpcchannel.cc ─────────────────────────────────────────────┐
│                                                                       │
│  ① stub.GetFriendsList(&ctl, &req, &rsp, nullptr)                    │
│     ↓                                                                 │
│  ② 序列化参数:  request → args_str (protobuf)                         │
│     ↓                                                                 │
│  ③ 封装 RPC 头:  RpcHeader {service_name, method_name, args_size}     │
│     序列化头:    rpc_header_str (protobuf)                            │
│     ↓                                                                 │
│  ④ 组帧:                                                              │
│     ┌──────────────┬──────────────┬─────────────────┬────────────┐   │
│     │ total_len 4B │ header_size 4B│ rpc_header_str   │  args_str  │   │
│     └──────────────┴──────────────┴─────────────────┴────────────┘   │
│      ↑ codec 用     ↑ OnMessage 用                                    │
│     ↓                                                                 │
│  ⑤ ZkClient::GetData("/服务名/方法名") → ip:port                      │
│     ↓                                                                 │
│  ⑥ socket() → connect() → send(完整帧)                                │
└───────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼ TCP 流
┌─ 服务端 muduo + rpcprovider.cc ──────────────────────────────────────┐
│                                                                       │
│  ⑦ Epoll → handleRead → Buffer::readFd()  读取原始字节                │
│     ↓                                                                 │
│  ⑧ RpcMessageCodec:                                                   │
│     peek(4B) → total_len                                              │
│     readableBytes() < 4+total_len → return false（数据留在 Buffer）   │
│     够了 → retrieve(4) + retrieveAsString(total_len) → message        │
│     ↓                                                                 │
│  ⑨ OnMessage(conn, message) ← 保证完整一帧                             │
│     此时 message: [header_size(4B)] + [RpcHeader] + [args]            │
│     ↓                                                                 │
│  ⑩ 反序列化 RpcHeader → service_name, method_name, args_size          │
│     查 m_serviceMap → 找到 service 对象和 method 描述符                │
│     ↓                                                                 │
│  ⑪ request->ParseFromString(args_str) → 还原请求对象                   │
│     ↓                                                                 │
│  ⑫ service->CallMethod(...) → 业务方法 → done->Run()                  │
│     ↓                                                                 │
│  ⑬ SendRpcResponse:                                                   │
│     SerializeToString → [response_size(4B)] + [数据]                  │
│     conn->send(响应帧)                                                 │
└───────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─ 客户端 mprpcchannel.cc ─────────────────────────────────────────────┐
│                                                                       │
│  ⑭ 读 4 字节 → response_size                                         │
│     循环读 response_size 字节 → response_str                          │
│     response->ParseFromString(response_str) → 还原响应对象             │
│     ↓                                                                 │
│  ⑮ 调用方检查 controller.Failed() / response.result()                 │
└───────────────────────────────────────────────────────────────────────┘
```

### 数据流视角

```
TCP segments (可能任意拆分)
       │
       ▼
   Buffer (累积，不清空)
       │
       ▼
   RpcMessageCodec (while 循环：够了就提一帧，不够等下次)
       │
       ▼
   OnMessage (一调用 = 一完整帧)
       │
       ├─ header_size → RpcHeader → service_name / method_name
       ├─ args_str → Request protobuf
       └─ service->CallMethod()
              │
              ▼
          SendRpcResponse
              │
              ▼
       [response_size][response_data] → conn->send()
```

## 总结

| 项目 | 类型 | 状态 |
|------|------|------|
| 客户端 nullptr controller + 响应变量错误 | 🔴 Bug | ✅ 已修复 |
| 日志路径错误 | 🟢 配置 | ✅ 已修复 |
| 请求/响应统一长度前缀帧格式 | 🔵 架构 | ✅ 已完成 |
| MessageCodec 植入 muduo Connection | 🔵 架构 | ✅ 已完成 |
| 客户端 wire format 对齐 | 🔵 架构 | ✅ 已完成 |

**核心设计思路：**

1. **帧边界是网络层的事。** 在消息最前面放 `total_len`，让 codec 无需解析业务 protobuf 就能截帧。Buffer 暂存半帧，`while` 循环提取完整帧，应用层只拿成品。
2. **自己写 muduo 的原因：为 mprpc 定制网络栈。** 通用 muduo 要保持协议无关，帧解析必须放在上层。但我们的 muduo 只为 mprpc 服务，把 RPC 帧格式认知下沉到 Connection 层，换来更干净的应用层接口。
3. **codec 可插拔但默认适配 RPC。** 没设 codec 时行为完全不变（向后兼容），设了 codec 后 Connection 自动处理粘包/拆包。未来换协议只需换 codec 实现。
