# PoolAllocator —— 打通内存池与 STL 容器的最后一公里

## 一、为什么需要 PoolAllocator

### 1.1 回顾：类级 operator new 的局限性

log1 中为 `Channel` 和 `Connection` 添加了类级 `operator new/delete`，试图让对象走内存池。但这种方法有两个根本局限：

| 局限 | 说明 |
|------|------|
| **不能用于 STL 容器** | `std::string`、`std::vector`、`std::map` 内部分配由 `std::allocator` 控制，不走类级 `operator new` |
| **与 `make_shared` 不兼容** | `make_shared` 用全局 `::operator new` 分配"控制块+对象"联合内存，绕过类级 `operator new` |

**而项目中绝大部分堆分配发生在 STL 容器内部：**

```
Buffer::buffer_       → std::vector<char>          → std::allocator → malloc
Connection::inputBuffer_ → Buffer (内含 vector)      → std::allocator → malloc
消息处理中的 std::string → std::string              → std::allocator → malloc
业务层的各种容器       → std::vector/map/unordered_map → std::allocator → malloc
```

**结论：不解决 STL 容器的问题，内存池永远被隔离在"自娱自乐"的状态。**

### 1.2 PoolAllocator 是什么

`PoolAllocator<T>` 是一个符合 C++17 标准的 STL 分配器模板。它把 `std::allocator` 的 `allocate`/`deallocate` 调用重定向到你的内存池：

```
std::vector<char, PoolAllocator<char>> vec;
    ↓
vec.resize(1024)
    ↓
PoolAllocator<char>::allocate(1024)
    ↓
MemoryPool::allocate(1024)          ← 进入三层内存池
    ↓
ThreadCache → CentralCache → PageCache
```

## 二、实现

### 2.1 完整代码

文件：`include/my_muduo/memory_pool/PoolAllocator.h`（71 行）

```cpp
#pragma once
#include "my_muduo/memory_pool/MemoryPool.h"
#include <cstddef>
#include <new>

namespace wevix_muduo {
namespace memory_pool {

template <typename T>
class PoolAllocator {
public:
    using value_type      = T;
    using size_type       = std::size_t;
    using difference_type = std::ptrdiff_t;
    using propagate_on_container_move_assignment = std::true_type;
    using is_always_equal = std::true_type;          // ①

    PoolAllocator() = default;
    ~PoolAllocator() = default;
    template <typename U> PoolAllocator(const PoolAllocator<U>&) noexcept {}  // ②

    [[nodiscard]] T* allocate(std::size_t n)
    {
        if (n == 0) return nullptr;                 // ③
        if (n > max_size()) throw std::bad_array_new_length();
        void* ptr = MemoryPool::allocate(n * sizeof(T));
        if (!ptr) throw std::bad_alloc();
        return static_cast<T*>(ptr);
    }

    void deallocate(T* ptr, std::size_t n) noexcept
    {
        if (!ptr || n == 0) return;
        MemoryPool::deallocate(ptr, n * sizeof(T));
    }

    std::size_t max_size() const noexcept
    {
        return static_cast<std::size_t>(-1) / sizeof(T);
    }
};

// 所有 PoolAllocator 实例等价 —— stateless
template <typename T, typename U>
bool operator==(const PoolAllocator<T>&, const PoolAllocator<U>&) noexcept
{ return true; }

template <typename T, typename U>
bool operator!=(const PoolAllocator<T>&, const PoolAllocator<U>&) noexcept
{ return false; }

} // namespace memory_pool
} // namespace wevix_muduo
```

### 2.2 关键设计点

| 标记 | 设计点 | 为什么重要 |
|:---:|------|------|
| ① | `is_always_equal = true` | 告诉 STL 所有 PoolAllocator 实例等价。容器 move 时不需要重新分配——直接"偷"对方的指针即可 |
| ② | 泛型拷贝构造 | `PoolAllocator<int>` 可以转为 `PoolAllocator<char>`，这是 `std::vector::rebind` 的要求 |
| ③ | `n == 0` 返回 `nullptr` | C++ 标准允许 allocator 的 `allocate(0)` 返回 `nullptr`。避免无意义的 8 字节分配 |
| ④ | `operator==` 定义在类外 | 如果在类内用 `friend` 模板声明，每个类模板实例化都会生成一份，导致 GCC 报"redefinition"错误（见附录） |

### 2.3 便捷类型别名

在使用方可以定义别名，让代码和标准 STL 一样简洁：

```cpp
template <typename T>
using PoolVector = std::vector<T, PoolAllocator<T>>;

using PoolString = std::basic_string<char, std::char_traits<char>, PoolAllocator<char>>;
```

### 2.4 内存池端：不需要任何调整

经过测试验证，现有的 `MemoryPool::allocate/deallocate` API 已经覆盖了所有边界情况：

| 边界 | 内存池行为 | STL 兼容性 |
|------|-----------|:---:|
| `size == 0` | 自动调整为 `ALIGNMENT(8)` 再分配 | ✅ 但 PoolAllocator 在 `n==0` 直接返回 `nullptr`，不走此路径 |
| `size > 256KB` | 自动 fallback 到 `malloc/free` | ✅ vector 大块扩容时透明切换 |
| 多线程并发 | ThreadCache 是 `thread_local` 的，天然无锁隔离 | ✅ 满足 C++ 对 allocator 的线程安全要求 |
| 对齐 | 8 字节对齐 | ✅ 满足所有基础类型和 64 位指针的对齐要求 |

## 三、压测验证

运行 `./bin/pool_alloc_test`：

### 3.1 正确性

```
PoolVector<char> (模拟 Buffer)     → OK
PoolString                         → OK
PoolVector<int>                    → OK
混合大小 (模拟消息路径)              → OK
空容器                              → OK
```

PoolAllocator 与 `std::vector`、`std::basic_string` 的完整生命周期（构造、扩容、缩容、析构）均正常工作。

### 3.2 性能

| 测试场景 | PoolAllocator | std::allocator | 提升 |
|---------|:---:|:---:|:---:|
| String 分配 (50000次, 256B) | 0.39 ms | 0.54 ms | **1.4×** |
| Vector\<char\> Buffer 模拟 (20000次) | 0.42 ms | 0.82 ms | **2.0×** |
| RPC 反序列化模拟 (10000消息×20字段) | 1.40 ms | 5.37 ms | **3.8×** |

RPC 场景下 3.8 倍提升的原因：每条消息有 20 个小字段，每个字段触发一次 string 分配。PoolAllocator 让这 200,000 次小分配全部走 ThreadCache 的无锁 TLS 快路径，而 glibc malloc 每次都要竞争 arena 锁。

## 四、应用场景

### 4.1 mprpc 框架（最佳场景）⭐

```cpp
// RPC 请求/响应的内部存储
class RpcMessage {
    PoolString method_name_;    // "GetUserInfo"
    PoolVector<char> payload_;  // 序列化后的 protobuf 数据
    PoolVector<PoolString> headers_;
};
```

**每一个 RPC 调用**都涉及消息的构造和析构，全部走内存池。QPS 越高优势越明显。

### 4.2 消息队列 ⭐

```cpp
struct QueueMessage {
    uint64_t id;
    PoolString topic;
    PoolVector<char> body;
    PoolString timestamp;
};
```

消息队列的本质就是大量小对象的快速入队/出队，与 ThreadCache 的无锁设计完美匹配。

### 4.3 业务层 ⭐

```cpp
// IM 群聊消息分发
void broadcastToGroup(const Message& msg, PoolVector<UserId>& members) {
    for (auto& uid : members) {
        PoolString payload = serialize(msg, uid);  // ← 走内存池
        sendToUser(uid, payload);
    }
}
```

## 五、能否用于 muduo 的消息路径？

这是从 log1 第三节延伸的核心问题。回顾消息路径的 4 次 malloc：

| 步骤 | 代码位置 | 操作 | 当前分配器 |
|------|---------|------|------|
| ① | `Connection.cpp:61` | `inputBuffer_.retrieveAllAsString()` | `std::string` → malloc |
| ② | `TcpServer.cpp:139` | `std::string msg = message` | `std::string` → malloc |
| ③ | `TcpServer.cpp:143` | lambda 按值捕获 `msg` | `std::string` 拷贝 → malloc |
| ④ | `TcpServer.cpp:145` | `std::string tmp = msg` | `std::string` 拷贝 → malloc |

### 5.1 答案：技术上可以，但要改 API

有了 PoolAllocator，可以用 `PoolString` 替换 `std::string`：

```cpp
// 用 PoolString 替换 std::string 后
PoolString message = inputBuffer_.retrieveAllAsPoolString();  // ← 走内存池
// ... 后续所有拷贝都自动走内存池
```

但问题是：**`std::string` 遍布 muduo 的公开 API**：

```cpp
// Connection.h
void send(const std::string& data);          // 改成 PoolString 就破坏 API

// TcpServer.h  
using MessageCallback = std::function<void(const ConnectionPtr&, std::string&)>;
//                                                        ↑ 所有用户回调都用 std::string&
```

如果把 `std::string` 全面替换为 `PoolString`，所有使用 muduo 的业务代码都要跟着改。**收益是有的（3-4 倍分配性能），但侵入性太大。**

### 5.2 更务实的方案：不换类型，消除拷贝

与其纠结用什么分配器，不如先把 4 次拷贝优化掉：

```cpp
// TcpServer::handleMessage —— 优化后
void TcpServer::handleMessage(const ConnectionPtr& conn, std::string& message)
{
    if (!onMessageCallback_) return;

    auto msgPtr = std::make_shared<std::string>(std::move(message));  // ① move 而非拷贝
    submitInWorkPool(
        [this, conn, msgPtr]()               // ② 只拷贝 shared_ptr，不再拷贝 string
        {
            onMessageCallback_(conn, *msgPtr); // ③ 直接使用，不再有 tmp 拷贝
        });
}
// 效果：4 次 malloc + 3 次 memcpy → 1 次 malloc + 0 次 memcpy
```

在 muduo 这层，**先消除无意义的拷贝**比换分配器更优先。PoolAllocator 的价值留在上层（mprpc、消息队列、业务层），那里你完全控制 API，不受历史兼容的约束。



## 六、总结

| 问题 | 答案 |
|------|------|
| PoolAllocator 怎么实现？ | 71 行模板代码，核心就是 `allocate → MemoryPool::allocate` 的转发。内存池无需调整 |
| 复杂吗？ | 复杂度集中在 C++ 模板细节（operator== 重定义、rebind），业务逻辑本身很简单 |
| 用于 muduo 有提升吗？ | 类的 operator new 路径：无提升（已压测证实）。STL 容器路径：替换内部 vector/string 有理论提升，但侵入 API 得不偿失 |
| 用于上层有提升吗？ | **有。** RPC 反序列化 3.8×、String 分配 1.4×、Vector Buffer 2.0× |
| muduo 消息路径怎么优化？ | 优先用 move 语义消除无意义拷贝（4→1 次 malloc），再考虑 PoolAllocator |

**PoolAllocator 的价值不在 muduo 这一层。它的使命是让内存池突破 STL 的围墙，进入 mprpc、消息队列和复杂业务逻辑——那里才是真正的每秒百万次分配的主战场。**


## 附录：PoolAllocator 模板细节

### operator== 为什么必须在类外定义

```cpp
// ❌ 错误写法（类内 friend 模板）
template <typename T>
class PoolAllocator {
    template <typename U, typename V>
    friend bool operator==(const PoolAllocator<U>&, const PoolAllocator<V>&);
    // GCC: error: redefinition — 因为 PoolAllocator<int> 和 PoolAllocator<char>
    // 各自实例化时都会生成这个模板，导致同一作用域内出现两个相同的定义
};

// ✅ 正确写法（类外定义）
template <typename T, typename U>
bool operator==(const PoolAllocator<T>&, const PoolAllocator<U>&) noexcept
{ return true; }
```

### 为什么不需要 rebind

C++17 废弃了 `allocator::rebind`，改为 `std::allocator_traits` 自动推导。只要 `PoolAllocator` 有泛型拷贝构造函数（`template<U> PoolAllocator(const PoolAllocator<U>&)`），`std::vector<bool>` 等需要 rebind 的容器就能自动推导出 `PoolAllocator<bool>` 来使用。
