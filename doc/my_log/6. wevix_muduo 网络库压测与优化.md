## 二、核心结论

**wevix_muduo 网络库在调优后达到百万 QPS 级别：**

- **峰值吞吐：106.7 万 QPS**（1000 连接 × 64B 小包）
- **持续吞吐：103.6 万 QPS**（500 连接 × 30 秒长跑，3,145 万条消息零失败）
- **低延迟：P50 76µs**（百连接千消息场景）
- **高并发：1000 连接零失败**，同时处理 500 万条消息
- **大消息：1MB echo P50 816µs**

## 四、Bug 分析与修复

### Bug 1：`listen()` backlog = 128 → Accept 队列溢出

**代码位置：** `wevix_muduo/include/wevix_muduo/Socket.h:40`

```cpp
// 修复前
void listen(int backlog = 128);
// 修复后
void listen(int backlog = 4096);
```

**原理：**

Linux 内核维护 Accept Queue（全连接队列）。`listen(fd, backlog)` 设置其上限。队列满时，内核直接**丢弃**新到达的 SYN/ACK 包，客户端触发 TCP 超时重传（RTO 指数退避 1s → 2s → 4s → 8s）。

```
t=0ms:    前 128 个连接进入 Accept Queue ✓
t=1ms:    队列满！第 129+ 个 SYN 被内核丢弃 ✗
t=1~3s:   内核超时重传，客户端卡在 connect() 无法发送数据
t=12s:    最后一个连接建立完成
```

**与传统 muduo 对比：** muduo 通过 `TcpServer::Option` 暴露 backlog，用户显式设置 ≥1024。wevix_muduo 未暴露该参数，内部硬编码 128。

### Bug 2：Acceptor 每次只 accept 一个连接

**代码位置：** `wevix_muduo/src/Acceptor.cpp:37`

```cpp
// 修复前：每次 epoll 事件只 accept 一次
void Acceptor::handleRead() {
    int connFd = serverSock_.accept(clientAddr);
    if (connFd >= 0) { ... }
}

// 修复后：循环 accept 直到 Accept Queue 为空
void Acceptor::handleRead() {
    while (true) {
        int connFd = serverSock_.accept(clientAddr);
        if (connFd >= 0) { ... }
        else { if (errno == EAGAIN) break; ... }
    }
}
```

**原理：** wevix_muduo 的 accept Channel 使用 LT 模式，单次 accept 不会丢连接（epoll 持续返回可读）。但 500 连接 = 500 次 event loop 迭代（epoll_wait → 分发 → 创建 Connection → 处理该连接的首批数据）。循环 accept 将 500 次迭代压缩为 1 次。

**与传统 muduo 对比：** muduo 同样每次只 accept 一个。wevix_muduo 的 accept-loop 是超越原版的主动优化。

### Bug 3：`kMaxEvents = 100` → epoll 事件饥饿

**代码位置：** `wevix_muduo/include/wevix_muduo/Epoll.h:33`

```cpp
// 修复前
static const int kMaxEvents = 100;
// 修复后
static const int kMaxEvents = 4096;
```

**原理：** 每个 IO 线程的 `epoll_wait` 每次最多返回 kMaxEvents 个就绪 fd。500 连接 ÷ 4 线程 = 125 连接/线程，kMaxEvents=100 → 25 个连接被**持续饿死**：

```
ET 模式下 IO 线程事件循环:
  epoll_wait(100 events) → 处理 → 这 100 个 client 收 echo 后立即发下一条
  epoll_wait(100 events) → 还是这 100 个！→ 第 101~125 号永远轮不到
  ...循环 20 轮，前 100 个发完全部消息...
  epoll_wait 终于看到第 101~125 号 → 它们已经等了 ~12 秒
```

**与传统 muduo 对比（关键差异）：** muduo 使用 `std::vector<epoll_event>` **动态扩容**：

```cpp
// muduo/net/poller/EPollPoller.cc
EventList events_(16);  // 初始 16
// 满载时自动翻倍: 16 → 32 → 64 → 128 → 256 ...
if (numEvents == events_.size())
    events_.resize(events_.size() * 2);
```

wevix_muduo 使用固定 C 数组 `events_[kMaxEvents]`，这是架构层面的差异。扩大到 4096 是必要修复，但根本上应改为 vector 动态扩容。

```cpp
// 1. Socket.h:40   — listen backlog 128 → 4096
```
