## 1. 业务故事：这个项目在做什么

用户提交一个视频，系统自动：
**拆（切分成 shard）→ 分（调度给多台 Worker 并行转码）→ 收（收集结果）→ 拼（合并成完整视频）→ 报（状态可查询）**。

用「100 页 PDF 拆给 10 个同事翻译再拼回来」理解即可——对象换成视频，切片按时间轴。

一个 2 小时 4K 视频 → 720p：单机 ffmpeg 转 2 小时；本系统拆 240 个 shard 分给 10 个 Worker 并行 → 约 8 分钟。

**为什么选视频处理这个业务**（`doc/视频转码平台/03_系统设计.md`）：天然可拆分（时间轴）、计算密集（并行收益大）、耗时够长（能展示进度/故障恢复/超时）、不依赖外部系统、结果可验证。

**分层哲学**：
- 网络库管「字节流与事件」——谁也不知道上面跑的是 RPC 还是 HTTP（ⓑ 背景）
- RPC 框架管「语义与分发」——帧拆好后查表调业务方法（ⓑ 背景）
- 业务层管「调度/转码/收集」——完全不碰 socket（★ 吃透对象）

## 3. 模块地图

### 3.1 背景知识速览 ⓑ：业务代码用到的框架特性

> 网络库 / mprpc 不做逐函数深挖，只列业务代码真正依赖的能力（穿透式阅读业务代码时需要它们解释"为什么这样写"）。

**wevix_muduo 给业务的保证**：
- `TcpServer::start()` 阻塞运行在 mainLoop，subLoops 跑在 IO 线程池——业务 main 最后一行就是 `provider.Run()`
- work pool（`enableWorkPool`）：RPC 业务方法在 work 线程执行，不阻塞 IO 线程——慢业务（MySQL/ffmpeg）不会拖垮网络
- `conn->send()` 是异步的：进 outputBuffer + EPOLLOUT 触发发送——所以服务端回复不阻塞
- 连接超时 10s（subLoop 扫描 forceClose）——**这是 mprpc 客户端"清空连接池重试"修复的根因**（服务端回收空闲连接 → 客户端本地 fd 看似有效实则已关）

**mprpc 给业务的保证**（业务代码每个 RPC 调用都依赖这些）：
- 服务端四步启动：`MprpcApplication::Init`（-i 配置，校验 ZK 必填）→ `provider.NotifyService(new XxxImpl())` → `provider.Run()`
- 客户端 Stub 调用同步阻塞，默认超时 5000ms，可 `controller.SetTimeoutMs()` 覆盖
- 连接级失败（CONNECT/TIMEOUT/SEND/RECV_FAILED）自动重试恰好 1 次：清连接池 → 失效发现缓存 → 重新发现
- 直连模式 `MprpcChannel(ip, port)` 绕过 ZK——Scheduler→Worker 的 AssignShard/CancelShard/QueryShard 用它
- 服务发现 ZK 路径 `/mprpc/services/{svc}/{method}/instance-*`；0.0.0.0 时注册实际网卡 IP（`GetLocalIp`）
- 帧上限 64MB；结构化错误码 14 种；deadline_ms 让服务端快速拒绝过期请求

| 文件 | 内容 | 说明 |
|------|------|------|
| common.proto | JobInfo / ShardInfo / WorkerInfo / WorkerLoad + JobStatus/ShardStatus 枚举 | 跨服务共享实体；ShardInfo 含 target_resolution(15)/target_bitrate(16) 透传字段 |
| job.proto | JobService：SubmitJob / QueryJob / CancelJob / ListJobs | 用户入口（阶段 12 加 ListJobs） |

| worker.proto | WorkerService：AssignShard / CancelShard / QueryShard；WorkerManagerService：RegisterWorker / Heartbeat / ListWorkers | 两个 service 在一个文件 |
| result.proto | ResultCollectorService：ReportShardResult / ReportShardProgress | ReportShardResultRequest 含 screenshot_path(11) |

**基础设施**：
- `common_store.h` — JobStore/ShardStore/WorkerStore 三个单例，MySQL 为唯一数据源（阶段 9 从内存 map 迁移）；**UpdateIfStatus 条件更新**是核心并发原语
- `mysql_pool` — libmysqlclient 连接池（预创建、借用归还、ping 保活、CLIENT_FOUND_ROWS、自动建表）
- `redis_client` — hiredis 封装，**可降级**（连不上只 WARN，不拒启动）；worker 快照 + 进度缓存 + SETNX 分布式锁
- `mq_client` — rabbitmq-c 封装，双连接双锁（发布/消费分离）、durable 拓扑、手动 ACK、poll 移出锁（阶段 10/12 修复）
- `ffmpeg_executor` — ffmpeg/ffprobe 封装（fork+execvp 防注入、poll+should_cancel、SIGTERM→SIGKILL、进度解析、1h 上限）

**GUI（Qt6）**：rpc_client（QRunnable 异步 RPC）+ 三页签（任务/Worker/日志）+ 提交对话框。

**服务内部结构**（以 job_service 为范式，各服务同构）：
```
main：AsyncLogger → MprpcApplication::Init → MysqlPool(失败拒启) → Redis/MQ(可降级)
      → metrics(可选端口) → 后台线程(扫描/消费) → RpcProvider.NotifyService → Run 阻塞
```

**每个服务内部的线程构成**（吃透业务代码必看的并发模型）：

| 服务 | 后台线程 | 职责 |
|------|---------|------|
| job_service | PendingScanLoop | 每 10s 重试 PENDING job 的 ScheduleJob |
| scheduler_service | SchedulingLoop + MqConsumeLoop | 轮询调度兜底（2s/5s）+ MQ 消费即时调度 |
| worker_manager | HeartbeatTimeoutCheck | 每 2s 超时判定（20s）+ NotifyWorkerOffline |
| transcode_worker | RunHeartbeatLoop + 每 shard 一个执行线程 | 心跳 3s + ffmpeg 执行（锁外启动，CleanupShard detach） |
| result_collector | TerminalSweepLoop + MqResultConsumeLoop | 每 15s 终态兜底 + MQ 消费结果 |

> 注意：这些后台线程**不走 RPC 框架**，是普通 std::thread + 条件变量轮询。RPC 框架只服务 5 个服务的监听端口。

## 4. 核心实体与状态机

### Job：PENDING → SPLITTING → SCHEDULING → RUNNING → MERGING → SUCCESS
### Shard：CREATED → WAITING → ASSIGNED → RUNNING → SUCCESS

```
                    ┌───────── FAILED (重试超限/不可恢复) ─────────┐
                    ▼                                             │
PENDING ─► SPLITTING ─► SCHEDULING ─► RUNNING ─► MERGING ─► SUCCESS
              ▲             │            ▲
              └─────────────┴────────────┘ (shard 重试中 job 保持 RUNNING)
                    
CANCELED：PENDING/RUNNING 可取消
```

**关键原则**：Job 的终态由 ResultCollector 判定（所有 shard 都完成才 SUCCESS）；shard 失败可重试（retry_count < max_retry 时回到 WAITING 重新调度）。

## 5. 完整数据流（一条视频的旅程）

> 骨架版（服务级别）→ 代码级表格（函数级，来源：3 个源码 agent 报告，2026-08-05）。

### 5.1 服务级流程图

```
job_client (CLI/GUI)
  │ SubmitJob RPC
  ▼
job_service ──► 校验参数 ──► JobStore 落 MySQL（PENDING）
  │ ScheduleJob RPC（重试3次，失败由 PendingScanLoop 每10s兜底）
  ▼
scheduler_service ──► ffprobe 探测时长（失败回退 job_duration_fallback_sec）
  │               ──► 按 shard_duration_sec 切分 → ShardStore 落 MySQL（WAITING）
  │               ──► 4 个 WAITING 触发点 → MQ 发布 shard.waiting（或轮询兜底）
  │               ──► SchedulingLoop(2s/5s) + MqConsumeLoop → TryAssignShard
  │                     ├─ LoadOnlineWorkers（Redis 快照优先，回退 ListWorkers RPC）
  │                     ├─ 评分选 Worker（slots*10 - cpu*0.5 - mem*0.2）
  │                     ├─ Redis SETNX shard:lock 分布式锁（10s EX）
  │                     └─ AssignShard RPC → Worker
  ▼
transcode_worker ──► 过载保护 → attempt_id 生成 → 锁外启动执行线程
  │               ──► FfmpegExecute：切片+转码一 pass（-ss/-t + libx264，-progress pipe:1）
  │               ──► 进度：每解析一行进度 → ReportShardProgress（纯日志）
  │               ──► 完成：Screenshot 中点截图 → 结果上报（MQ 优先→RPC 3次→心跳兜底）
  ▼
result_collector ──► HandleReportShardResult（RPC 与 MQ 消费共用）
  │               ──► attempt 幂等 → UpdateIfStatus 状态推进 → 失败触发 RescheduleShard
  │               ──► CheckJobDone → MarkJobTerminal（成功则 Merge，失败则重试/FAILED）
  │               ──► Redis DEL 进度缓存 → TerminalSweepLoop 每15s兜底
  ▼
JOB_SUCCESS ──► GUI 双击预览（ffplay 播放 {job_id}_merged.mp4）
```

### 5.3 每步背后的设计问题（穿透式理解的问题清单，见 03 报告）

1. 为什么任务提交用 RPC 而不是 HTTP？为什么 AssignShard 不阻塞到转码完成？
2. 为什么 Scheduler 既要 MQ 推送又要轮询兜底？MQ 故障时系统会怎样？
3. 为什么 Redis 挂了系统还能跑，MySQL 挂了却不行（可降级 vs fail-fast）？
4. 为什么 shard 重试要有 attempt_id？重复上报/延迟上报怎么防？
5. 为什么 Worker 负载走心跳 RPC + Redis 快照而不是 ZK？
6. 为什么 JobService/Scheduler/RC 的共享数据都走 MySQL + UpdateIfStatus？
7. 为什么 PendingScanLoop/TerminalSweepLoop/HeartbeatTimeoutCheck 三个后台扫描线程存在？

## 8. 核心流程图

> 图 3 ★是业务主线（吃透对象）；图 1/2 ⓑ是背景知识（理解业务代码"为什么这样写"时回来查）。

### 图 1 ⓑ：网络库事件循环（EventLoop 一次迭代）

```
                        EventLoop::run()  [每个线程一个 loop]
                              │
                              ▼
                    epoll_->poll(-1)  ────────────┐ 超时(实际为-1无限阻塞，防御分支)
                              │                  │
                              ▼                  ▼
                     activeChannels≠空?      epollTimeoutCallback_
                              │ 是
                              ▼
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
       wakeChannel_      timerChannel_     conn Channel ×N
       (eventfd)         (timerfd)         handleEvent()
        handleWakeup     handleTimer        ├─ write 回调先于 read（防ET卡死）
       read 清空计数        │ 重置闹钟        ├─ 每回调后立即 return（防UAF）
                          │ 仅 subLoop     └─ 回调可能销毁 this
                          ▼
                扫描 conns_ 超时(10s)
                → forceClose + removeConnection
                              │
                              ▼
                    doPendingTasks()
              swap 整批取出 → 锁外逐个执行
             （跨线程任务：runInLoop 投递的）
                              │
                              ▼
                       回到 while(!stop_)

跨线程安全三件套：
  send() 非本线程 → runInLoop → queueInLoop（锁内 push + eventfd 写 1 字节唤醒）
  handleClose → runInLoop([self]{...}) 保活再销毁
  subLoop 超时扫描 → forceClose → runInLoop(handleClose)
```

### 图 2 ⓑ：RPC 调用链路（一次 stub 调用的完整旅程）

```
业务代码 stub.Method(&ctrl, &req, &resp, nullptr)
      │
      ▼
MprpcChannel::CallMethod
  ├─ 1. 序列化请求 + RpcHeader（request_id=原子自增，deadline_ms=now+timeout）
  │       BuildRpcFrame → [total_len][magic MR][ver=1][payload]
  │
  ├─ 2. 服务发现（三层）：
  │       本地 ServiceCache(TTL 30s, 轮询) ──miss──► Redis mprpc:endpoints
  │        ──仍miss──► ZK GetChildren(/mprpc/services/{svc}/{method}/instance-*)
  │                    逐个 GetData → ip:port 列表 → 双写本地+Redis
  │
  ├─ 3. GetPooledConnection(endpoint)：池未满新建（上限8），满则轮询复用
  │
  ├─ 4. SendRequestAndReadResponse（持连接锁）：
  │       EnsureConnected：非阻塞 connect + poll(POLLOUT, timeout)
  │       SetSocketTimeout：SO_SNDTIMEO/RCVTIMEO 每次按本次 timeout 刷新
  │       SendAll(MSG_NOSIGNAL) → RecvAll(4B total_len, 校验≤64MB) → RecvAll(帧体)
  │       DecodeRpcFramePayload：校验 magic/version
  │       DecodeRpcResponsePayload：response_size 一致 → request_id 匹配
  │       → error_code 校验 → response->ParseFromString
  │
  ├─ 5. 失败重试（仅 CONNECT/TIMEOUT/SEND/RECV_FAILED，恰好1次）：
  │       DropEndpointConnections(清整池) → InvalidateHostData(本地+Redis HDEL)
  │       → 重新 QueryEndpointList → 新 endpoint 重发
  │
  └─ 6. SetControllerFailed(错误码+文本) / RunDone

服务端（对称旅程）：
  RpcProvider::Run → TcpServer(io线程) + work pool + ZK 注册 instance-*
      │
      ▼
  Connection 读 → RpcMessageCodec 拆帧（半包等待/粘包循环）→ 完整 payload
      │
      ▼
  RpcProvider::OnMessage（work 线程）
    ├─ DecodeRequestHeader：header_size/args_size 一致性校验
    ├─ deadline 过期检查 → RPC_TIMEOUT 快速拒绝
    ├─ 查 m_serviceMap → service/method 不存在回包（不干等）
    ├─ 反射 New request/response + NewCallback(done)
    ├─ service->CallMethod → 业务填充 response → done->Run()
    │     （漏调 done 则客户端等到超时）
    └─ SendRpcResponse：BuildRpcResponseFrame + conn->send（不 shutdown，异步发送）
```

### 图 3 ★：平台任务生命周期（一条视频从提交到 SUCCESS）

```
[提交]  job_client ──SubmitJob──► JobService::SubmitJob
          ├─ 校验 → JobStore.Insert(PENDING) → metrics计数
          ├─ 调 Scheduler.ScheduleJob ×3（失败→PendingScanLoop 每10s兜底）
          └─ UpdateIfStatus PENDING→SCHEDULING
                │
[切分]  ▼
        Scheduler::ScheduleJob（全局互斥串行）
          ├─ FfmpegExecutor::Probe 探测时长（失败回退60s）
          ├─ shard_count = ceil(duration / shard_duration)
          ├─ 逐个 ShardStore.Insert(WAITING, max_retry=3)
          └─ PublishShardWaiting → RabbitMQ shard.waiting
                │
[调度]  ▼
        MqConsumeLoop（消费消息）  /  SchedulingLoop（2s或5s轮询兜底）
          └─ TryAssignShard ×N：
             ├─ 复核状态+终态检查 → LoadOnlineWorkers(Redis快照→RPC回退)
             ├─ 评分：slots*10 - cpu*0.5 - mem*0.2 → 选最高分 worker
             ├─ SETNX shard:lock:{id} EX 10（Redis 故障降级放行）
             ├─ AssignShard RPC（超时5s）
             └─ UpdateIfStatus WAITING→ASSIGNED（attempt_id 写入）→ job→RUNNING
                │
[执行]  ▼
        Worker::AssignShard
          ├─ 过载保护 → 锁内插 running_shards_ → 锁外起线程
          ├─ FfmpegExecute：Transcode(-ss/-t 切片+转码一pass, -progress pipe:1)
          │   └─ 每行进度 → ReportShardProgress（RC 纯日志）
          ├─ Screenshot(中点帧)
          └─ 结果上报：MQ result.pending 优先 → RPC×3 → pending_reports_ 兜底
                │
[收集]  ▼
        ResultCollector::HandleReportShardResult（RPC 与 MQ 消费共用）
          ├─ attempt 幂等（旧 attempt 拒绝）→ SUCCESS/FAILED 条件更新
          ├─ 失败 → RescheduleShard(退避3次) → retry<3 则回 WAITING 再调度
          │         retry≥3 → SHARD_FAILED → CheckAndMarkJobFailed
          ├─ CheckJobDone：success_count ≥ expected → MarkJobTerminal(SUCCESS)
          └─ MarkJobTerminal：MergeMutex 防重复 → Merge(concat) → 删分片
                │
[终态]  ▼
        JOB_SUCCESS → Redis DEL job:progress 缓存 → GUI 可预览 merged.mp4
        兜底：TerminalSweepLoop 每15s重扫非终态job；Scheduler 超时重扫30s/5min
```

**三条降级路径值得记住**（面试高频）：
1. MQ 挂 → Scheduler 切 2s 轮询、Worker 结果直连 RPC → 恢复自动切回
2. Redis 挂 → 快照/缓存/锁全部降级（回退 RPC/放行靠 MySQL 条件更新兜底）
3. Scheduler 挂 → PendingScanLoop 保留 job，恢复后自动重试
